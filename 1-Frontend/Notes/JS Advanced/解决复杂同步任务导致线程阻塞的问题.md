# 解决复杂同步任务导致线程阻塞

## 一、问题本质是什么

JavaScript 在浏览器主线程中执行时，如果某个同步任务执行时间过长，就会阻塞：

1. 页面渲染
2. 点击响应
3. 输入反馈
4. 动画执行

这类问题通常表现为：

1. 页面卡顿。
2. 按钮点了没反应。
3. 滚动掉帧。
4. 浏览器提示页面无响应。

一句话概括：**长时间占用主线程，会让 UI 和交互一起被“冻住”。**

---

## 二、两类核心解决思路

| 方案         | 核心思想                               | 适合场景                       |
| ------------ | -------------------------------------- | ------------------------------ |
| **另起线程** | 把重计算移出主线程                     | 图像处理、大量运算、解析任务   |
| **函数切片** | 不离开主线程，但把长任务拆成多个短任务 | 必须依赖主线程上下文的连续计算 |

---

## 三、方案一：使用 Web Worker 另起线程

### 3.1 适用场景

如果任务主要是“**纯计算**”，且不依赖 DOM，那么最直接的办法就是放进 **Web Worker**。

典型场景：

1. 大量数据统计。
2. 图片像素处理。
3. 文本解析。
4. 文件切片与哈希计算。

### 3.2 基础示例

#### `worker.ts`

```ts
self.addEventListener("message", event => {
  const source = event.data as number[]

  // 模拟复杂计算
  const total = source.reduce((sum, item) => sum + item, 0)

  self.postMessage(total)
})
```

#### 主线程中使用

```ts
const worker = new Worker(new URL("./worker.ts", import.meta.url), {
  type: "module",
})

worker.postMessage([1, 2, 3, 4, 5])

worker.addEventListener("message", event => {
  console.log("计算结果：", event.data)
  worker.terminate()
})
```

### 3.3 这种方案的优点

1. 真正把重任务移出主线程。
2. 页面渲染和交互不会被这段计算直接卡死。
3. 适合 CPU 密集型任务。

### 3.4 限制

1. Worker 内不能直接操作 DOM。
2. Worker 内不能访问 `window`，通常使用 `self`。
3. 主线程和 Worker 之间通信需要消息传递。

---

## 四、Worker 中的通信与数据限制

主线程和 Worker 之间通过：

1. `postMessage`
2. `message` 事件

进行通信。

### 4.1 一个重要限制

传递的数据受 **结构化克隆算法** 约束，不是什么对象都能直接传。

通常能传：

1. 普通对象
2. 数组
3. `Map`
4. `Set`
5. `ArrayBuffer`
6. `Blob`

通常不能直接传：

1. DOM 节点
2. 函数
3. 带复杂原型链的某些对象实例

### 4.2 性能补充

如果传输的是大二进制数据，可以进一步使用 **Transferable**，避免复制开销，例如 `ArrayBuffer`。

## 五、方案二：通过 Blob URL 动态创建 Worker

如果不想单独维护一个 Worker 文件，也可以临时构造脚本字符串。

```ts
const workerScript = `
self.addEventListener("message", event => {
	const total = event.data.reduce((sum, item) => sum + item, 0)
	self.postMessage(total)
})
`

const blob = new Blob([workerScript], { type: "text/javascript" })
const workerScriptURL = URL.createObjectURL(blob)

const worker = new Worker(workerScriptURL)

worker.postMessage([1, 2, 3])

worker.addEventListener("message", event => {
  console.log(event.data)
  worker.terminate()
  URL.revokeObjectURL(workerScriptURL)
})
```

### 5.1 适用场景

1. 临时工具型逻辑。
2. 动态拼装小段 Worker 代码。
3. Demo 或实验性场景。

### 5.2 不足

1. 可读性较差。
2. 不利于维护和类型提示。
3. 复杂业务里通常不如单独文件清晰。

## 六、方案三：函数切片

### 6.1 什么时候不能直接用 Worker

有些任务虽然很重，但又必须跑在主线程，比如：

1. 需要和当前渲染节奏强关联。
2. 需要渐进式更新页面状态。
3. 需要频繁访问主线程可用 API。

这时更常见的办法是：**把一个长任务拆成多个短任务，分多帧执行。**

### 6.2 核心思想

不要一次执行 5000ms 的同步任务，而是每次只执行一小段，例如控制在 8ms 到 16ms 以内，把剩余部分交给下一帧继续。

### 6.3 示例：基于生成器切片

```ts
function* complexCalculate() {
  let count = 0
  const endTime = performance.now() + 5000

  while (performance.now() < endTime) {
    count += 1
    yield count
  }

  return count
}

function timeSlice(): Promise<number> {
  return new Promise(resolve => {
    const iterator = complexCalculate()

    const run = () => {
      const frameStart = performance.now()
      let result: IteratorResult<number, number>

      do {
        result = iterator.next()
      } while (!result.done && performance.now() - frameStart < 16)

      if (result.done) {
        resolve(result.value)
      } else {
        requestAnimationFrame(run)
      }
    }

    run()
  })
}
```

### 6.4 为什么用 `requestAnimationFrame`

因为它会尽量配合浏览器下一帧渲染节奏，常用于“把大任务拆到多帧里执行”。

---

## 七、函数切片的优缺点

### 7.1 优点

1. 不需要另开线程。
2. 保持主线程逻辑连续。
3. 能显著降低页面“完全卡死”的感觉。

### 7.2 缺点

1. 总执行时间通常会更长。
2. 切得越细，调度成本越高。
3. 它只是“减少卡顿”，不是把计算成本变没。

### 7.3 一个正确认知

函数切片优化的是“**用户感知流畅度**”，不一定优化“**总耗时**”。

---

## 八、Worker 和函数切片怎么选

| 判断问题                             | 更推荐的方案        |
| ------------------------------------ | ------------------- |
| 任务是否纯计算、能脱离 DOM？         | **Worker**          |
| 任务是否需要留在主线程逐步推进？     | **函数切片**        |
| 是否主要担心页面彻底失去响应？       | 优先考虑 **Worker** |
| 是否只是想让长循环不要一次卡死页面？ | 可用 **函数切片**   |

可以简单理解为：

1. **能搬走就搬走**，优先 Worker。
2. **搬不走再切片**，用分帧执行。

---

## 九、补充：不要只盯着“怎么拆”，也要先看能不能“少做”

在真正优化前，还应该先问三个问题：

1. 这段计算是不是本来就不该这么重。
2. 能不能缓存结果。
3. 能不能减少数据量或降低计算频率。

很多阻塞问题，根源并不是“没有用 Worker”，而是“主线程上做了本不该做那么多的事”。

---

## 十、小结

1. 复杂同步任务导致线程阻塞，本质上是主线程被长任务长时间占用。
2. 最直接的解决方案是使用 Web Worker，把重计算移出主线程。
3. 如果任务不能离开主线程，可以通过函数切片把长任务拆成多个短任务。
4. Worker 解决的是“线程隔离”，函数切片解决的是“执行节奏分散”。
5. 真正优化时，应先考虑是否能减少任务本身，再决定是开线程还是切片。
