# 移动 web

## 一、一句话理解

移动端开发的重点不只是“页面缩小后还能看”，而是要同时处理视口、像素密度、触控交互和多设备真实表现。

---

## 二、移动端预览与调试

在桌面浏览器中开发移动端页面时，通常会先使用开发者工具模拟手机环境。

### 1. 常见步骤

1. 打开开发者工具
2. 切换到移动设备模拟模式
3. 选择设备型号或手动调整宽度
4. 检查布局、字号、点击区域和滚动表现

这类调试适合做快速验证，但并不能完全替代真机测试。

---

## 三、移动端开发和 PC 端开发的主要区别

### 1. 浏览器环境差异

| 维度               | 移动端情况               |
| ------------------ | ------------------------ |
| **浏览器内核较新** | H5 / CSS3 支持通常更好   |
| **基本不考虑 IE**  | 兼容压力相对小           |
| **视口机制不同**   | 默认布局视口往往比屏幕宽 |

### 2. 屏幕与交互差异

| 问题                 | 常见解决思路                   |
| -------------------- | ------------------------------ |
| **屏幕尺寸差异大**   | `flex`、百分比、`rem`、`vw/vh` |
| **多倍屏更清晰**     | 使用多倍图                     |
| **手指点击不够精准** | 扩大可点击区域                 |

## 四、视口 viewport

### 1. 什么是视口

**视口（viewport）** 可以理解为浏览器用来显示网页内容的“窗口区域”。

### 2. 移动端为什么要重置视口

很多移动浏览器默认布局视口较宽，如果不处理，页面会被整体缩小，导致：

- 字太小
- 布局比例异常
- 交互体验差

### 3. 常用视口配置

```html
<meta name="viewport" content="width=device-width, initial-scale=1.0" />
```

| 配置                     | 说明                   |
| ------------------------ | ---------------------- |
| **`width=device-width`** | 让视口宽度等于设备宽度 |
| **`initial-scale=1.0`**  | 初始缩放比例为 1       |

### 4. 关于禁止缩放

你可能会见到这样的写法：

```html
<meta
  name="viewport"
  content="width=device-width, initial-scale=1, maximum-scale=1, minimum-scale=1, user-scalable=no"
/>
```

它的作用是限制用户缩放页面，但现代实际项目里通常需要谨慎，因为这会影响可访问性体验。

### 5. 刘海屏和安全区意识

在全面屏设备上，还要注意顶部状态栏、底部手势区域等安全区问题，不能只按普通矩形屏幕去理解可用空间。

## 五、多倍屏与像素概念

### 1. 屏幕尺寸

屏幕尺寸通常指屏幕对角线长度，单位是英寸。

### 2. 物理像素

物理像素是真实屏幕上的发光点数量。

### 3. 逻辑像素 / CSS 像素

前端开发时更常接触的是逻辑像素，也就是 CSS 意义上的像素。

### 4. 为什么会出现多倍屏

高密度屏幕会在更小的物理面积里放进更多像素点，从而让画面更细腻。

这意味着：

- 同样尺寸的图片，在高密度屏上更容易显得模糊
- 需要更高清的资源图配合显示

---

## 六、多倍图

### 1. 什么是多倍图

多倍图指的是：为适配高像素密度屏幕，提供比视觉显示尺寸更大的图片资源。

例如：

- 页面想显示 `100px × 100px`
- 设计师可能提供 `200px × 200px` 或 `300px × 300px` 图片

### 2. 常见理解

| 说法       | 含义                              |
| ---------- | --------------------------------- |
| **2 倍图** | 图片资源尺寸通常是显示尺寸的 2 倍 |
| **3 倍图** | 图片资源尺寸通常是显示尺寸的 3 倍 |

### 3. 对开发的影响

| 场景                | 处理方式                      |
| ------------------- | ----------------------------- |
| **普通图片**        | 按显示尺寸缩放展示            |
| **背景图 / 精灵图** | 常配合 `background-size` 缩放 |

---

## 七、设计稿与换算

很多移动端设计稿以 `750px` 宽度作为基准，这通常对应 2 倍图设计思路。

因此开发时，经常会有这样的经验规则：

设计稿尺寸 ÷ 2 = 逻辑像素参考值

例如：

设计稿上量出来 `200px`，开发时往往按 `100px` 的逻辑尺寸理解。

> **注意**：具体是否直接除 2，也要看团队设计规范和适配方案，不是所有项目都机械套这个规则。

## 八、移动端常见布局方案

### 1. 流式布局

也叫百分比布局，核心是大量使用 `%` 让盒子随容器变化。

### 2. flex 布局

适合横向排列、自适应分配空间，是现代移动端最常用方案之一。

### 3. rem 布局

通过根字号统一缩放页面尺寸，适合历史移动端方案。

### 4. vw / vh

直接基于视口宽高计算尺寸，现代项目使用越来越多。

| 方案           | 特点                         |
| -------------- | ---------------------------- |
| **百分比布局** | 简单直接，但表达能力有限     |
| **flex**       | 组件级布局极强               |
| **rem**        | 适合整体缩放                 |
| **vw / vh**    | 直接和视口挂钩，现代方案常见 |

## 九、移动端交互设计注意点

### 1. 点击区域要足够大

移动端是手指操作，不能按 PC 端鼠标精度来设计。

### 2. 字体不能太小

过小字体会直接影响可读性。

### 3. 间距要更宽松

移动端组件之间需要更容易点中和区分。

### 4. 滚动体验要顺畅

避免固定高度过多、嵌套滚动混乱等问题。

### 5. 触控事件要按移动端习惯设计

移动端更强调滑动、长按、下拉等连续手势，很多交互问题不是布局错了，而是点击区域、滚动冲突和反馈时机没处理好。

## 十、经典“两边固定，中间自适应”思路

这类布局在移动端和响应式页面里都很常见。

### 1. 传统思路

- 两侧区域固定宽度
- 中间区域自适应剩余空间

### 2. 旧写法

可以通过绝对定位 + 中间留白实现。

### 3. 更现代的推荐方式

实际项目里更推荐直接使用 `flex`：

```css
.layout {
  display: flex;
}

.left,
.right {
  width: 80px;
}

.center {
  flex: 1;
  min-width: 0;
}
```

这种方式比传统绝对定位方案更稳定、维护成本更低。

## 十一、真机测试为什么不能省

桌面模拟器可以快速看布局，但这些问题往往只有真机更容易暴露：

1. 点击区域是否真的好点。
2. 滚动是否顺滑。
3. 输入框、键盘弹起后布局是否错位。
4. 刘海屏、安全区和浏览器工具栏是否影响展示。
5. 图片清晰度和性能是否符合预期。

所以移动端开发里，模拟器更像第一轮筛查，真机才是最终体验校验。

## 十二、小结

| 知识点           | 结论                               |
| ---------------- | ---------------------------------- |
| **移动端视口**   | 需要通过 `meta viewport` 正确设置  |
| **多倍屏**       | 高密度屏幕需要更高清资源           |
| **多倍图**       | 常见于 2x / 3x 图片资源            |
| **主流布局方案** | `flex`、百分比、`rem`、`vw/vh`     |
| **现代实践**     | 新项目通常优先 `flex` + 响应式单位 |
