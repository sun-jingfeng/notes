这几个主题表面分散，其实都和现代前端的运行机制有关，可以按 4 组来理解：

| 主题组                 | 解决的问题                         |
| ---------------------- | ---------------------------------- |
| **跨域**               | 浏览器为什么会拦请求、后端如何放行 |
| **防抖 / 节流**        | 高频事件怎么控频                   |
| **ES6 模块化**         | 代码怎么拆分和组织                 |

## 二、同源策略与跨域

### 2.1 什么是同源

浏览器判断两个地址是否同源，主要比较这 3 项：

1. 协议。
2. 域名或主机。
3. 端口。

只要这三项里有一项不同，就属于**不同源**。

### 2.2 同源策略限制的是什么

同源策略是浏览器的一项安全机制，用来限制不同源页面之间的随意访问。

常见受限能力包括：

1. DOM 访问。
2. Ajax / Fetch 响应读取。
3. 部分 Cookie、存储和凭证访问。

### 2.3 一个容易误解的点

很多跨域请求**不是发不出去**，而是**响应结果会被浏览器拦截**，所以前端看起来像“请求失败”。

## 三、跨域的常见解决方案

### 3.1 CORS

**CORS** 是现代前后端分离开发中最常见的跨域方案。

特点：

1. 前端一般不需要特殊处理。
2. 是否放行由后端通过响应头决定。
3. 支持现代浏览器中的主流跨域场景。

服务端常见做法：

```js
const cors = require("cors")
app.use(cors())
```

### 3.2 简单请求与预检请求

并不是所有跨域请求都会直接进入业务接口。

有些请求会先发一个 `OPTIONS` 预检请求，用来确认：

1. 服务端是否允许这个来源。
2. 是否允许这个请求方法。
3. 是否允许这些自定义请求头。

常见会触发预检的场景：

1. 使用了 `PUT`、`DELETE`、`PATCH` 等方法。
2. 使用了自定义请求头。
3. 请求体类型不是简单表单类型。

### 3.3 JSONP

JSONP 是较早期的跨域方案，本质上利用了 `script` 标签不受同源策略限制。

特点：

1. 只支持 `GET`。
2. 不是标准 Ajax。
3. 现代业务中已很少作为主方案。

```html
<script>
  function callbackFn(res) {
    console.log(res)
  }
</script>
<script src="http://localhost:3006/api/jsonp?callback=callbackFn"></script>
```

### 3.4 CORS 和 JSONP 对比

| 方案  | 优点                   | 缺点                           |
| ----- | ---------------------- | ------------------------------ |
| CORS  | 现代标准方案，使用自然 | 需要服务端配合                 |
| JSONP | 兼容旧环境             | 仅支持 GET，能力弱且安全边界差 |

## 四、防抖与节流

### 4.1 防抖是什么

防抖指的是：事件触发后不立即执行，而是等待一段时间；如果等待期间再次触发，就重新计时。

适合场景：

1. 搜索框输入联想。
2. 停止输入后再发请求。
3. 窗口尺寸变化结束后再重算布局。

```js
function debounce(fn, delay) {
  let timer = null

  return function (...args) {
    clearTimeout(timer)
    timer = setTimeout(() => {
      fn.apply(this, args)
    }, delay)
  }
}
```

### 4.2 节流是什么

节流指的是：在一段时间内，无论事件触发多少次，函数最多只执行一次。

适合场景：

1. 滚动事件。
2. 鼠标移动事件。
3. 拖拽过程中的位置更新。

```js
function throttle(fn, delay) {
  let timer = null

  return function (...args) {
    if (timer) return

    timer = setTimeout(() => {
      fn.apply(this, args)
      timer = null
    }, delay)
  }
}
```

### 4.3 防抖与节流的区别

| 对比项   | 防抖             | 节流                 |
| -------- | ---------------- | -------------------- |
| 核心目标 | 只执行最后一次   | 限制执行频率         |
| 更适合   | 停止输入后再处理 | 持续过程中按频率处理 |

### 4.4 一个实战判断标准

1. 如果你关心“最终结果”，优先防抖。
2. 如果你关心“过程中的连续反馈”，优先节流。

### 4.5 常见进阶点

真实项目里，经常还会继续补：

1. 立即执行版本。
2. 取消执行能力。
3. 尾触发或头触发选项。

## 五、ES6 模块化

### 5.1 为什么需要模块化

当项目变大后，如果所有变量和函数都写在一个文件里，会带来：

1. 变量污染。
2. 依赖混乱。
3. 文件难维护。

模块化的目标就是把代码拆成独立文件，并建立清晰的导入导出关系。

### 5.2 `export` 与 `export default`

```js
export const name = "Tom"

export function add(a, b) {
  return a + b
}
```

```js
export default function sum(a, b) {
  return a + b
}
```

```js
import { name, add } from "./utils.js"
import sum from "./sum.js"
```

### 5.3 两者区别

| 写法         | 特点                                         |
| ------------ | -------------------------------------------- |
| **具名导出** | 一个模块可导出多个，导入名通常保持一致       |
| **默认导出** | 一个模块通常只有一个默认导出，导入名可自定义 |

### 5.4 模块化的收益

1. 文件职责更清晰。
2. 依赖关系更明确。
3. 更适合工程化构建和静态分析。

## 六、Promise

### 6.1 什么是 Promise

**Promise** 是 JavaScript 中处理异步操作的对象，用来表示“未来某个时间点才会拿到的结果”。

它让异步代码比传统回调更清晰。

### 6.2 Promise 的三种状态

| 状态        | 含义   |
| ----------- | ------ |
| `pending`   | 进行中 |
| `fulfilled` | 已成功 |
| `rejected`  | 已失败 |

状态一旦从 `pending` 进入成功或失败，就不会再改变。

### 6.3 基本写法

```js
const p = new Promise((resolve, reject) => {
  const success = true

  if (success) {
    resolve("成功结果")
  } else {
    reject("失败原因")
  }
})

p.then(res => {
  console.log(res)
}).catch(err => {
  console.log(err)
})
```

### 6.4 链式调用

```js
Promise.resolve(1)
  .then(res => res + 1)
  .then(res => res + 1)
  .then(res => {
    console.log(res)
  })
```

### 6.5 `then` 返回的还是 Promise

这是链式调用能成立的关键。

如果 `then` 里：

1. 返回普通值，后续会收到这个值。
2. 返回 Promise，后续会等待它完成。
3. 抛出错误，后续会进入失败链路。

### 6.6 常见静态方法

| 方法                   | 作用                           |
| ---------------------- | ------------------------------ |
| `Promise.resolve()`    | 生成成功状态的 Promise         |
| `Promise.reject()`     | 生成失败状态的 Promise         |
| `Promise.all()`        | 全部成功才成功，一个失败就失败 |
| `Promise.allSettled()` | 等待全部完成，不管成功还是失败 |
| `Promise.race()`       | 取最先完成的结果               |

### 6.7 Promise 和 `async/await` 的关系

`async/await` 本质上是 Promise 的语法糖。

也就是说：

1. `await` 等的是 Promise。
2. `async` 函数返回的仍然是 Promise。

所以理解 Promise 是理解 `async/await` 的前提。

## 七、宏任务与微任务

### 7.1 宏任务（macrotask）

常见宏任务：

1. 整体脚本执行。
2. `setTimeout`。
3. `setInterval`。
4. DOM 事件回调。

### 7.2 微任务（microtask）

常见微任务：

1. `Promise.then / catch / finally`。
2. `queueMicrotask()`。
3. `MutationObserver`。

### 7.3 执行优先级

一轮事件循环中，通常是：

```text
先执行一个宏任务
  -> 再清空当前轮产生的所有微任务
  -> 再进入下一轮宏任务
```

## 八、事件循环

### 8.1 为什么会有事件循环

JavaScript 主线程是单线程的，但又要处理同步代码、异步回调、事件响应，所以需要一套调度机制来协调执行顺序，这套机制就是 **Event Loop**。

### 8.2 一个经典例子

```js
console.log(1)

setTimeout(() => {
  console.log(2)
}, 0)

Promise.resolve().then(() => {
  console.log(3)
})

console.log(4)
```

输出顺序是：

```js
1
4
3
2
```

原因：

1. 先执行同步代码：`1`、`4`。
2. 再清空当前轮的微任务：`3`。
3. 最后执行下一轮宏任务：`2`。

### 8.3 一个常见误区

`setTimeout(fn, 0)` 不等于“立即执行”，它只是“最早在下一轮宏任务里执行”。

### 8.4 一句话理解事件循环

**事件循环就是：主线程不断从任务队列中取任务执行，并在每轮宏任务后清空微任务队列。**

## 九、小结

1. 跨域的核心是浏览器同源策略，现代项目通常使用 CORS 解决。
2. 防抖适合“只要最后一次”，节流适合“限制频率”。
3. ES6 模块化让代码更适合拆分与维护。
4. Promise 是现代异步编程基础，`async/await` 是它的语法糖。
5. 宏任务、微任务和事件循环共同决定了异步代码的执行顺序。
6. 学这篇时，重点不是把 7 个名词孤立记忆，而是理解“浏览器限制、事件控频、模块拆分、异步执行”这四条主线。
