# 逆变、协变

## 一、一句话理解

逆变和协变本质上都在解释: 当类型有父子关系时，函数参数和返回值的兼容方向为什么不是同一个方向。

---

## 二、先理解变型在讨论什么

逆变、协变本质上讨论的是：**当类型之间存在继承关系时，函数参数和返回值的兼容方向如何变化。**

我们先准备一个继承链：

```ts
class Parent {
  house() {}
}

class Son extends Parent {
  car() {}
}

class GrandSon extends Son {
  sleep() {}
}
```

关系可以理解为：

```text
Parent <- Son <- GrandSon
```

---

## 三、协变

协变通常出现在**返回值位置**。

### 1. 直观理解

如果别人期望你返回一个 `Son`，那你返回一个更具体的 `GrandSon` 通常也是可以接受的。

```ts
type Fn = () => Son

const fn: Fn = () => {
  return new GrandSon()
}
```

### 2. 为什么成立

因为 `GrandSon` 也是 `Son`，只是“能力更多”。

对调用方来说：

1. 它原本只要求拿到 `Son`。
2. 实际拿到 `GrandSon` 也不会更糟。

这就是返回值的协变。

---

## 四、逆变

逆变通常出现在**函数参数位置**。

### 1. 直观理解

如果某个位置要求一个“能处理 `Son` 的函数”，那一个“能处理更宽泛 `Parent` 的函数”通常也能胜任。

```ts
type Fn = (p: Son) => void

const fn: Fn = (p: Parent) => {
  console.log("ok")
}
```

### 2. 为什么成立

因为调用方最多只会传 `Son` 或 `Son` 的子类，而 `Parent` 类型的函数本来就能接收这些值。

### 3. 但调用时仍以原类型要求为准

```ts
fn(new Son())
fn(new GrandSon())
// fn(new Parent()) // 报错
```

虽然函数实现写的是 `Parent`，但变量类型仍然是 `(p: Son) => void`，所以调用时必须符合 `Son` 的约束。

---

## 五、一个简化结论

| 位置   | 常见变型 |
| ------ | -------- |
| 返回值 | 协变     |
| 参数   | 逆变     |

### 1. 可以这样记

1. 返回值：返回更具体的，通常没问题。
2. 参数：接收更宽泛的，通常没问题。

---

## 六、为什么这在 TypeScript 里会显得复杂

因为 TypeScript 既要保证类型安全，又要兼顾 JavaScript 生态的可用性，所以对函数参数的处理并不是所有地方都完全一致。

尤其要注意：

1. 普通函数类型。
2. 对象方法。
3. 类方法。
4. 回调场景。

它们在严格模式下会有细微差异。

---

## 七、`strictFunctionTypes` 与双向协变问题

在 `strictFunctionTypes` 相关语义下，函数参数检查会更严格。

### 1. 属性写法更接近严格函数检查

```ts
type Obj = {
  fn: (p: Son) => void
}

const obj1: Obj = {
  fn(p: Parent) {},
}

const obj2: Obj = {
  fn(p: Son) {},
}

// const obj3: Obj = {
//   fn(p: GrandSon) {}
// }
```

这里 `Parent` 往往可以，`GrandSon` 往往不行，因为它把参数收得更窄了。

### 2. 方法写法有时更宽松

```ts
type Obj = {
  fn(p: Son): void
}
```

这种方法签名写法在历史兼容原因下，可能表现得更宽松，很多人会把它理解成一种“参数双向协变”现象。

### 3. 为什么要知道这个差异

因为它解释了：

1. 为什么某些看似类似的写法，一个能过一个不能过。
2. 为什么数组、事件回调、方法声明有时会显得“没那么严格”。

这里真正要抓住的是: TypeScript 会在类型安全和 JavaScript 生态兼容之间做一些折中，所以不同写法的表现可能不完全一样。

---

## 八、业务开发中怎么用这个知识

这部分知识真正的价值，不是让你死记“逆变协变”四个字，而是帮你理解这些现象：

1. 回调参数为什么不能随便写得更窄。
2. 返回值为什么能返回更具体的子类型。
3. 某些方法签名为什么看起来“不够严格”。
4. 泛型库设计里为什么参数位置和返回值位置意义不同。

---

## 九、快速记忆方式

1. 返回值位置通常看协变: 返回更具体的通常安全。
2. 参数位置通常看逆变: 接收更宽泛的通常更安全。
3. 一旦感觉规则混乱，先回到“调用方到底会传什么、会拿到什么”去理解。

---

## 十、总结

1. 协变通常对应返回值，逆变通常对应参数。
2. 返回更具体的类型通常是安全的，接收更宽泛的参数通常也是安全的。
3. TypeScript 中函数参数兼容会受到具体写法和严格配置影响。
4. 方法签名和函数属性写法在参数检查上可能表现不同。
5. 学这篇时，重点不是术语本身，而是看懂“为什么这个函数能赋值，另一个不行”。
