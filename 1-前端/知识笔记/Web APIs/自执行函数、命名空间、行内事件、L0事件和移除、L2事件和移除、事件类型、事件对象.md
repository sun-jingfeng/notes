# 自执行函数、命名空间、行内事件、L0/L2、事件类型、事件对象

## 一、这篇的主线

这一篇看起来是 6 个分散知识点，但其实可以串成两条主线：

1. 代码如何避免全局污染：自执行函数、命名空间。
2. 事件如何绑定和处理：行内事件、L0/L2、事件对象。

把这两条主线理清，知识点就不会显得零散。

---

## 二、自执行函数（IIFE）

自执行函数是“定义完立即执行”的函数写法，也叫 IIFE。

### 2.1 常见写法

```js
;(function () {
  console.log("立即执行")
})()
```

### 2.2 传参写法

```js
;(function (name) {
  console.log(name)
})("张三")
```

### 2.3 常见用途

| 用途       | 说明                       |
| ---------- | -------------------------- |
| 隔离作用域 | 避免变量污染全局           |
| 初始化代码 | 页面加载时立即执行某段逻辑 |

### 2.4 为什么旧代码里常见 IIFE

在 ES6 模块化和 `let` / `const` 普及之前，IIFE 是非常常见的隔离变量作用域手段。

### 2.5 现在还要不要继续写 IIFE

| 场景                   | 更推荐                  |
| ---------------------- | ----------------------- |
| 现代工程化项目         | ES Modules / 块级作用域 |
| 读老代码、维护传统脚本 | 需要看懂 IIFE           |
| 临时隔离一小段脚本     | 可以用，但不是首选      |

## 三、命名空间

命名空间本质上是用对象把一组变量或方法包起来，避免全局变量冲突。

```js
const utils = {
  formatDate() {},
  formatPrice() {},
}
```

### 3.1 它解决什么问题

如果很多工具函数都直接挂在全局作用域，很容易重名、覆盖、难维护。命名空间就是一种更有组织的全局管理方式。

### 3.2 和 IIFE 的关系

1. IIFE 偏向“隔离私有变量”。
2. 命名空间偏向“对外暴露一个统一入口”。

在旧项目里，这两者经常配合使用。

### 3.3 真实开发里怎么理解它的历史位置

IIFE 和命名空间本质上都属于“模块化普及前的过渡方案”。

也就是说：

1. 现在写新项目时，优先 ES Modules。
2. 维护老代码时，能理解 IIFE + 命名空间的意图非常重要。
3. 重构时，通常是把它们逐步迁移到更明确的模块边界里。

## 四、行内事件、L0 事件、L2 事件

这三种写法本质上都在回答一个问题：事件逻辑到底绑在哪里。

### 4.1 行内事件

行内事件指的是直接在 HTML 标签上写事件处理代码。

```html
<button onclick="handleClick(1)">点击</button>
```

不推荐的原因：

1. 结构和行为耦合。
2. 复杂逻辑难管理。
3. 调试和复用都不方便。

### 4.2 DOM L0 事件

L0 事件是早期的事件绑定写法，直接给元素的 `on事件名` 赋值。

```js
btn.onclick = function () {
  console.log("clicked")
}
```

### 4.3 DOM L2 事件

L2 事件是现代常用写法，通过 `addEventListener()` 绑定。

```js
btn.addEventListener("click", function () {
  console.log("clicked")
})
```

### 4.4 为什么现代开发更推荐 L2

| 对比项                   | 行内事件 | L0   | L2   |
| ------------------------ | -------- | ---- | ---- |
| 结构和行为分离           | 差       | 一般 | 好   |
| 同一事件绑定多个处理函数 | 差       | 否   | 可以 |
| 移除控制能力             | 弱       | 一般 | 更强 |
| 现代推荐度               | 低       | 低   | 高   |

L2 更适合复杂业务场景，因为它更灵活、更容易维护，也更方便和事件捕获、冒泡、委托这些机制配合。

### 4.5 从老代码迁移时的常见顺序

如果项目里还存在大量行内事件或 L0 事件，比较稳的迁移顺序通常是：

1. 先把 HTML 里的行内事件拿掉。
2. 再把 `onclick = fn` 这类 L0 写法改成 `addEventListener()`。
3. 再按需要整理事件委托、解绑和模块边界。

## 五、事件移除

### 5.1 L0 事件移除

```js
btn.onclick = null
```

### 5.2 L2 事件移除

L2 事件移除必须传入同一个函数引用。

```js
function handleClick() {
  console.log("clicked")
}

btn.addEventListener("click", handleClick)
btn.removeEventListener("click", handleClick)
```

### 5.3 一个常见坑

如果绑定时用了匿名函数，后面通常没法直接移除。

所以当事件需要解绑时，最好提前把处理函数保存成具名函数或变量。

### 5.4 什么时候一定要提前保留函数引用

1. 组件或页面销毁时需要解绑。
2. 滚动、resize、定时轮询这类高频逻辑需要停掉。
3. 事件只想在某个阶段生效。

## 六、常见事件类型

### 6.1 鼠标事件

| 事件         | 说明     |
| ------------ | -------- |
| `click`      | 单击     |
| `dblclick`   | 双击     |
| `mousedown`  | 鼠标按下 |
| `mouseup`    | 鼠标抬起 |
| `mousemove`  | 鼠标移动 |
| `mouseenter` | 鼠标移入 |
| `mouseleave` | 鼠标移出 |

### 6.2 键盘事件

| 事件      | 说明     |
| --------- | -------- |
| `keydown` | 键盘按下 |
| `keyup`   | 键盘抬起 |

### 6.3 表单事件

| 事件     | 说明         |
| -------- | ------------ |
| `input`  | 输入内容变化 |
| `change` | 值变化并确认 |
| `focus`  | 获得焦点     |
| `blur`   | 失去焦点     |
| `submit` | 表单提交     |

### 6.4 一个判断标准

1. 需要实时响应输入，常用 `input`。
2. 只关心最终确认结果，常用 `change`。
3. 需要监听键盘动作，常用 `keydown`。

## 七、事件对象

事件触发时，浏览器会把当前事件相关信息打包成一个对象传给回调函数，这个对象就叫事件对象。

```js
btn.addEventListener("click", function (event) {
  console.log(event)
})
```

### 7.1 常见属性

| 属性                  | 说明                     |
| --------------------- | ------------------------ |
| `type`                | 当前事件类型             |
| `target`              | 真正触发事件的元素       |
| `currentTarget`       | 当前绑定事件的元素       |
| `clientX` / `clientY` | 相对浏览器可视区域的位置 |
| `pageX` / `pageY`     | 相对整个文档的位置       |
| `offsetX` / `offsetY` | 相对当前元素左上角的位置 |

### 7.2 `target` 和 `currentTarget` 的区别

这是事件委托里最常见的一组概念：

1. `target` 是真正点到的那个元素。
2. `currentTarget` 是当前绑定监听器的元素。

如果列表父元素上做事件委托，这两个值经常不一样。

### 7.3 常见方法

```js
event.preventDefault()
event.stopPropagation()
```

1. `preventDefault()`：阻止默认行为。
2. `stopPropagation()`：阻止事件继续冒泡。

### 7.4 一个边界提醒

`stopPropagation()` 不是越早写越安全。它会直接改变事件链路，所以应该只在确实要阻断上层逻辑时才用。

如果只是为了区分点击来源，很多时候先判断 `event.target` 是否匹配目标元素，会比直接阻断冒泡更稳。

---

## 八、小结

1. IIFE 和命名空间本质上都在解决全局污染问题，只是侧重点不同。
2. 行内事件、L0、L2 代表了三种事件绑定思路，现代开发优先使用 `addEventListener()`。
3. 事件是否方便移除，关键在于有没有保留同一个函数引用。
4. 学事件对象时，重点不是只记属性名，而是理解它如何服务于事件委托、坐标获取和默认行为控制。
5. 学这一篇时，要把“作用域管理”和“事件处理模型”两条主线建立起来，而不是把知识点孤立去背。
