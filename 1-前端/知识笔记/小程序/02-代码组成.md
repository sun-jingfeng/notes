# 小程序代码组成

## 一、一句话理解

小程序开发的第一步，不是先背 API，而是先建立“一个页面由多种文件协作完成”的认知：配置、结构、样式、逻辑是分开的。

---

## 二、小程序页面为什么不是单文件

在 Web 里，初学阶段常把 HTML、CSS、JavaScript 放在同一个页面里；而在小程序里，一个页面通常天然就是多文件协作。

最常见的几类文件：

| 文件类型 | 作用     | 类比 Web        |
| -------- | -------- | --------------- |
| `json`   | 配置     | 页面 / 工程配置 |
| `wxml`   | 结构模板 | HTML            |
| `wxss`   | 样式     | CSS             |
| `js`     | 逻辑脚本 | JavaScript      |

一个基础页面目录：

```text
pages/
  index/
    index.js
    index.json
    index.wxml
    index.wxss
```

所以学这篇的真正目标，不是记住后缀名，而是知道“哪个问题该去哪个文件处理”。

---

## 三、先看四类文件的职责边界

| 文件   | 管什么                       | 不该干什么           |
| ------ | ---------------------------- | -------------------- |
| `json` | 配置页面行为和外观           | 不写业务逻辑         |
| `wxml` | 写页面结构和模板绑定         | 不写复杂逻辑         |
| `wxss` | 写样式                       | 不负责数据和业务     |
| `js`   | 写数据、事件、请求和生命周期 | 不直接操作浏览器 DOM |

这套分工越早建立清楚，后面学组件、通信、生命周期时越不容易乱。

---

## 四、JSON：负责配置，不负责业务

### 1. 常见配置文件

| 文件                  | 作用           | 是否运行时动态修改 |
| --------------------- | -------------- | ------------------ |
| `app.json`            | 全局配置       | 否                 |
| 页面同名 `json`       | 当前页面配置   | 否                 |
| `project.config.json` | 开发者工具配置 | 一般由工具维护     |

### 2. `app.json` 示例

```json
{
  "pages": ["pages/index/index", "pages/detail/detail"],
  "window": {
    "navigationBarTitleText": "示例应用"
  }
}
```

### 3. 理解重点

- `app.json` 更像项目总配置。
- 页面 `json` 更像当前页面的个性化配置。
- 这类文件是静态配置，不是写业务代码的地方。

### 4. 语法注意点

1. 不能写注释。
2. 键名必须是双引号。
3. 末尾不能多写逗号。

---

## 五、WXML：负责页面结构

### 1. 什么是 WXML

**WXML** 是小程序的结构模板语言，作用类似 Web 里的 HTML。

```html
<view class="container">
  <text id="title">欢迎学习小程序</text>
</view>
```

### 2. 为什么不是直接写 HTML

因为小程序不是浏览器环境，它没有完整 DOM，也不是直接运行在普通网页里，所以使用的是受控模板语言和受控组件体系。

### 3. 理解边界

- 可以把 WXML 理解成“结构层”。
- 它长得像 HTML，但不是完整 HTML。
- 它的能力依赖小程序组件体系，而不是浏览器标签体系。

---

## 六、数据绑定和模板控制

### 1. 数据绑定

WXML 通过 `{{}}` 把 `js` 里的数据映射到页面上。

```html
<text id="{{id}}">{{msg}}</text>
```

```js
Page({
  data: {
    id: 1,
    msg: "开课吧",
  },
})
```

注意点：

1. 变量名区分大小写。
2. 未定义的值不会按预期显示。
3. 模板层适合简单表达式，不适合堆复杂业务逻辑。

### 2. 条件渲染

```html
<text wx:if="{{name === '呷哺'}}">吃火锅</text>
<text wx:elif="{{name === '肯德基'}}">吃汉堡</text>
<text wx:else>回家做饭</text>
```

`block` 不会渲染成真实节点，适合给一组标签统一加条件：

```html
<block wx:if="{{visible}}">
  <view>内容 1</view>
  <view>内容 2</view>
</block>
```

### 3. 列表渲染

```html
<view wx:for="{{food}}" wx:key="id">
  <text>{{item.name}}</text>
</view>
```

```js
Page({
  data: {
    food: [
      { id: 1, name: "西红柿鸡蛋面" },
      { id: 2, name: "香菜蛋花汤" },
      { id: 3, name: "白菜炖粉条" },
    ],
  },
})
```

`wx:key` 的作用和 Vue / React 里的 `key` 思路类似，用来帮助框架更高效地更新视图。

常见写法：

1. `wx:key="id"`
2. `wx:key="*this"`

## 七、模板复用和公共属性

### 1. 模板复用

如果一段结构反复出现，可以抽模板：

```html
<template name="hotel">
  <text>{{name}}：</text>
  <text wx:for="{{food}}" wx:key="id">
    {{index ? '、' : ''}}{{item.name}}
  </text>
</template>
```

```html
<template is="hotel" data="{{ name: '呷哺', food }}"></template>
```

### 2. 常见公共属性

| 属性               | 含义         |
| ------------------ | ------------ |
| `id`               | 节点唯一标识 |
| `class`            | 样式类名     |
| `style`            | 内联样式     |
| `hidden`           | 是否隐藏     |
| `data-*`           | 自定义数据   |
| `bind*` / `catch*` | 事件绑定     |

这些写法和 Web 很像，但它们作用于小程序组件系统，不是浏览器 DOM。

## 八、WXSS：负责样式层

### 1. 什么是 WXSS

**WXSS** 是小程序的样式语言，作用类似 CSS，用来描述 WXML 的视觉效果。

### 2. 样式来源

| 样式来源        | 说明         |
| --------------- | ------------ |
| `app.wxss`      | 全局样式     |
| 页面同名 `wxss` | 页面局部样式 |
| 行内 `style`    | 内联样式     |
| `@import`       | 导入其他样式 |

### 3. WXSS 和 CSS 的区别

1. 支持 `rpx` 响应式单位。
2. 可用 `@import`。
3. 资源、域名、环境受平台限制。
4. 不能把浏览器里的所有 CSS 经验原样照搬。

### 4. `rpx` 的理解方式

`rpx` 是为了更方便地适配不同宽度设备，可以简单理解为：页面宽度在逻辑上被切成 750 份。

所以它更像“小程序布局体系中的常用单位”，而不是单纯换个名字的 `px`。

## 九、JS：负责数据、事件和生命周期

页面脚本入口示例：

```js
Page({
  data: {
    title: "首页",
  },
  onLoad() {
    console.log("页面加载")
  },
})
```

它通常负责：

1. 数据定义。
2. 事件处理。
3. 生命周期逻辑。
4. 网络请求。
5. 页面状态更新。

一个关键认知：小程序里不是直接操作浏览器 DOM，而是通过数据更新驱动视图变化。

---

## 十、把四类文件串成一个页面思路

可以这样理解一个页面的协作关系：

```text
json 决定页面配置
  -> wxml 决定页面结构
  -> wxss 决定页面长什么样
  -> js 决定页面数据从哪里来、怎么变、用户操作后发生什么
```

如果做一个商品列表页：

- `json` 配导航标题和页面能力。
- `wxml` 渲染商品列表结构。
- `wxss` 写卡片、间距、颜色。
- `js` 发请求、存列表数据、处理点击事件。

这就是“代码组成”真正想说明的内容。

## 十一、模块化和项目组织

小程序的 JavaScript 也支持模块化，不是所有逻辑都堆进页面脚本。

```js
// A.js
export default class A {
  constructor(name) {
    this.name = name
  }
}
```

```js
// index.js
import A from "./A"

Page({
  data: {
    fruit: new A("苹果"),
  },
})
```

这意味着：

- 页面脚本只放页面本身逻辑。
- 公共方法、工具函数、请求封装可以继续拆模块。
- 页面越复杂，越需要提前做好职责划分。

---

## 十二、学习这篇时最容易混淆的点

| 容易混淆的点                       | 正确认识                      |
| ---------------------------------- | ----------------------------- |
| **`json` 里也能写逻辑**            | 不对，`json` 主要负责配置     |
| **`wxml` 就是 HTML**               | 只是类似，不是完整浏览器 HTML |
| **`wxss` 就是 CSS 原封不动搬过来** | 有相似性，但也有平台约束      |
| **`js` 负责直接操作 DOM**          | 小程序不是浏览器 DOM 模式     |

---

## 十三、小结

| 知识点       | 结论                                                         |
| ------------ | ------------------------------------------------------------ |
| **页面组成** | 一个页面通常由 `json`、`wxml`、`wxss`、`js` 四类文件协同完成 |
| **职责边界** | 配置、结构、样式、逻辑要分开理解                             |
| **模板能力** | 数据绑定、条件渲染、列表渲染是 WXML 核心能力                 |
| **真正重点** | 知道问题该落在哪个文件，而不是只记后缀名                     |
