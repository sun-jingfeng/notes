# 微信小程序宿主环境

## 一、什么是宿主环境

宿主环境指的是微信客户端为小程序提供的运行环境。它负责加载代码、组织页面、调度 API、提供微信能力，并把你的项目真正运行起来。

一句话理解：

```text
小程序不是在浏览器里跑，而是在微信客户端这个宿主里跑。
```

这也是小程序和普通 Web 前端最重要的区别之一。

---

## 二、宿主环境提供了什么

它至少做了这几件事：

1. 解析代码包。
2. 管理页面与组件。
3. 提供 `wx` API。
4. 负责逻辑层与渲染层协作。
5. 接入微信能力，比如扫码、支付、登录、分享。

这也是为什么很多普通网页做不到的事，小程序却可以直接调用。

### 2.1 为什么前端要先理解它

因为后面学生命周期、组件通信、性能优化时，很多限制和设计选择都来自宿主环境，而不是来自 JavaScript 语法本身。

---

## 三、小程序的双层运行模型

可以先建立一个最重要的模型：

```text
逻辑层（JS）
    ↓ setData / 事件通信
渲染层（WXML / WXSS）
```

### 3.1 逻辑层负责什么

1. 数据状态。
2. 页面逻辑。
3. 事件处理。
4. 网络请求。

### 3.2 渲染层负责什么

1. 页面结构。
2. 视觉样式。
3. 界面展示。

### 3.3 为什么要这样分层

因为这样更利于：

1. 性能控制。
2. 安全约束。
3. 平台统一管理。

### 3.4 和 Web 前端的直觉差别

在浏览器里经常会想到“直接改 DOM”，但在小程序里这条路不成立，因为逻辑层和渲染层是分开的。

---

## 四、`setData` 为什么重要

在小程序里，逻辑层不会像浏览器那样直接改 DOM，页面更新通常依赖 `setData` 把数据同步给渲染层。

```js
Page({
  data: {
    count: 0,
  },
  add() {
    this.setData({
      count: this.data.count + 1,
    })
  },
})
```

### 4.1 注意点

1. 直接改 `this.data.xxx` 不能驱动视图更新。
2. `setData` 是通信过程，不宜频繁发送大对象。
3. 与界面无关的大数据不应该都塞进 `data`。

### 4.2 `setData` 常见性能坑

1. 高频事件里频繁调用 `setData`。
2. 一次同步整个大对象，而不是只更新变化字段。
3. 把纯缓存数据也放进 `data`。

### 4.3 一个实战判断

只要数据需要驱动页面显示，才放进 `data`；否则优先放在实例字段或其他状态容器里。

## 五、App、Page 和组件

### 5.1 `App()`

`App()` 用来注册整个小程序应用，通常写在 `app.js`。

```js
App({
  globalData: {
    motto: "好好学习",
  },
  onLaunch() {
    console.log("应用启动")
  },
})
```

### 5.2 `getApp()`

在其他文件里可以通过 `getApp()` 获取全局应用实例。

```js
const app = getApp()
console.log(app.globalData.motto)
```

### 5.3 `Page()`

每个页面通过 `Page()` 注册。

```js
Page({
  data: {
    text: "This is page data.",
  },
  onLoad() {},
  onShow() {},
  onReady() {},
  onHide() {},
  onUnload() {},
})
```

### 5.4 自定义组件

当页面结构重复或功能需要封装时，可以建立自定义组件。

组件目录通常也包含：

1. `json`
2. `wxml`
3. `wxss`
4. `js`

其中组件的 `json` 里要声明：

```json
{
  "component": true
}
```

### 5.5 父子组件通信

1. 父传子：通过 `properties`。
2. 子传父：通过 `triggerEvent()`。

```js
this.triggerEvent("tapBall", { tap: true })
```

## 六、应用和页面生命周期

### 6.1 App 生命周期

| 生命周期   | 含义                   |
| ---------- | ---------------------- |
| `onLaunch` | 小程序初始化完成时触发 |
| `onShow`   | 小程序进入前台时触发   |
| `onHide`   | 小程序进入后台时触发   |

### 6.2 页面生命周期

| 生命周期   | 含义                 |
| ---------- | -------------------- |
| `onLoad`   | 页面加载时触发       |
| `onShow`   | 页面显示时触发       |
| `onReady`  | 首次渲染完成时触发   |
| `onHide`   | 页面暂时不可见时触发 |
| `onUnload` | 页面被销毁时触发     |

### 6.3 一个常见误区

`onLoad` 和 `onShow` 不一样：

1. `onLoad` 更偏页面实例建立。
2. `onShow` 更偏页面再次被看见。

如果页面从别处返回再次展示，往往会触发 `onShow`，不一定重新触发 `onLoad`。

## 七、用户点开小程序后发生了什么

可以粗略理解为：

```text
点击小程序入口
  -> 微信初始化宿主环境
  -> 读取本地缓存或下载代码包
  -> 创建 App 实例
  -> 触发 App.onLaunch
  -> 创建首页页面实例
  -> 渲染首页
```

这个流程为什么重要：

1. 它决定了初始化逻辑应该放在哪。
2. 它决定了性能问题最容易出现在什么阶段。

## 八、页面跳转、前后台状态和资源清理

### 8.1 前后台状态

1. 用户离开小程序但未销毁时，小程序进入后台。
2. 用户再次回到小程序时，小程序回到前台。

### 8.2 页面跳转方式

1. `tabBar` 切换。
2. `navigator` 组件。
3. 路由 API，如 `wx.navigateTo()`、`wx.redirectTo()`、`wx.navigateBack()`。

### 8.3 一个重要提醒

页面切换不代表所有异步任务都会自动清理，比如定时器、轮询、监听器，很多时候都需要你在 `onHide` 或 `onUnload` 阶段手动释放。

## 九、宿主环境提供的 API 和事件系统

### 9.1 `wx` API

几乎所有常用能力都挂在 `wx` 对象下。

常见分类：

1. 网络请求。
2. 存储。
3. 文件。
4. 媒体。
5. 设备。
6. 界面。
7. 位置。
8. 开放能力。

### 9.2 API 的几个常见规律

| 规律      | 说明            |
| --------- | --------------- |
| `wx.on*`  | 监听事件类接口  |
| `*Sync`   | 同步接口        |
| `wx.get*` | 获取数据 / 状态 |
| `wx.set*` | 写入数据 / 状态 |

### 9.3 常见事件

| 事件         | 含义     |
| ------------ | -------- |
| `tap`        | 轻触     |
| `longpress`  | 长按     |
| `touchstart` | 触摸开始 |
| `touchmove`  | 触摸移动 |
| `touchend`   | 触摸结束 |

### 9.4 冒泡与捕获

1. `bindtap` 表示普通绑定，参与冒泡。
2. `capture-bind:tap` 表示捕获阶段处理。
3. `catchtap` 常用于阻止事件继续冒泡。

复杂组件交互里，很多“点击了子元素却触发父元素逻辑”的问题，本质上都是事件传播机制没理顺。

---

## 十、开发时的几个常见坑

1. 把大量非视图数据塞进 `data`。
2. 页面离开后忘记清理定时器。
3. 混淆 `onLoad` 和 `onShow`。
4. 把小程序 API 当成浏览器 API 使用。
5. 试图直接按 Web 的方式操作 DOM。

---

## 十一、小结

1. 宿主环境本质上就是微信客户端为小程序提供的运行系统，小程序所有能力边界都建立在它之上。
2. 小程序的关键机制是逻辑层与渲染层分离，所以更新页面依赖 `setData`，而不是直接改 DOM。
3. `App()`、`Page()`、组件系统、`wx` API、生命周期和事件系统，都是理解宿主环境的核心入口。
4. 真正掌握宿主环境，关键是理解它为什么和 Web 不同，以及这些差异如何影响性能、通信和页面组织方式。
5. 这篇学懂后，后续看小程序生命周期、组件通信、性能优化都会顺很多。
