# 微信小程序应用场景

## 一、一句话理解

小程序不是所有业务都能放进去的万能容器，它最适合的是依赖微信生态入口、使用链路短、用户希望即用即走的轻量业务场景。

---

## 二、小程序在业务中的典型定位

小程序最适合承载的是“微信内可快速触达”的业务，而不是所有前端场景都强行迁移过去。

### 1. 典型适用场景

1. 门店服务。
2. 电商活动。
3. 会员中心。
4. 工具类轻应用。
5. 内容分发与营销活动。

### 2. 为什么这些场景适合

因为它们通常具备：

1. 微信生态入口强。
2. 使用链路短。
3. 用户无需额外下载 App。

### 3. 一个更实用的判断方式

| 业务特点                         | 小程序是否合适 |
| -------------------------------- | -------------- |
| **高频、轻量、入口依赖微信**     | 很合适         |
| **需要快速活动承接和转化**       | 很合适         |
| **重度复杂交互、长期沉浸式使用** | 未必最优       |
| **深度系统能力或高性能动画依赖** | 要谨慎评估     |

---

## 三、小程序常见开发流程

一个更实用的开发流程通常是：

```text
需求梳理 → 原型 / 视觉稿 → 页面结构搭建 → 数据模型设计 → 交互实现 → 接口联调 → 测试发布
```

### 1. 前端实现时的常见顺序

1. 先用 `WXML + WXSS` 还原页面。
2. 再补页面 `data` 和模板绑定。
3. 最后完成交互与接口逻辑。

### 2. 为什么这样做

这样可以把“界面结构问题”和“逻辑联调问题”拆开处理，降低开发混乱度。

---

## 四、交互反馈为什么重要

在移动端场景里，很多操作不是瞬时完成的，所以必须给用户及时反馈，否则用户会怀疑“是不是没点上”。

### 1. 常见反馈类型

1. 触摸反馈。
2. Toast 提示。
3. 模态框提示。
4. 加载状态。
5. 下拉刷新与上拉加载。

---

## 五、触摸反馈与按钮状态

### 1. `hover-class`

适合给点击区域提供按压态。

### 2. `loading`

如果按钮会触发耗时请求，应及时展示加载中状态。

```html
<button loading="{{loading}}">提交</button>
```

### 3. 核心原则

用户一触发操作，最好立刻看到：

1. 按压反馈。
2. 加载反馈。
3. 成功或失败反馈。

小程序场景里，无反馈通常比慢一点更容易让用户流失。

---

## 六、Toast 与模态框如何选

| 场景               | 推荐方式 |
| ------------------ | -------- |
| 成功提示、轻提示   | Toast    |
| 错误原因说明       | 模态框   |
| 需要用户确认下一步 | 模态框   |

### 1. Toast 示例

```js
wx.showToast({
  title: "已发送",
  icon: "success",
  duration: 1500,
})
```

### 2. 模态框示例

```js
wx.showModal({
  title: "提示",
  content: "当前操作失败，请检查网络后重试",
  confirmText: "重试",
  cancelText: "取消",
})
```

### 3. 选择原则

Toast 不适合承载复杂说明；需要用户明确理解并做选择时，优先用模态框。

---

## 七、滚动场景

### 1. 下拉刷新

适合重新拉取当前页数据。

### 2. 上拉触底

适合列表分页加载。

### 3. `scroll-view`

如果只是页面内某个区域滚动，通常使用 `scroll-view`，而不是把整个页面都做成滚动容器。

这其实对应的是一个更大的判断：问题到底是页面级滚动，还是局部区域滚动。

---

## 八、网络通信

小程序里最常见的网络能力是 `wx.request()`。

### 1. 两种基本请求方式

1. `GET`：参数通常拼在 URL 上。
2. `POST`：参数通常放在 `data` 中。

### 2. 一个基础示例

```js
wx.request({
  url: "https://example.com/api/news",
  method: "POST",
  data: {
    id: 2,
  },
  success(res) {
    console.log(res.data)
  },
})
```

### 3. 上线环境要注意什么

1. 必须走 HTTPS。
2. 域名通常要在管理平台完成配置。
3. 本地调试能通，不代表线上一定能通。

这意味着小程序的网络问题，除了代码本身，还经常和平台配置直接相关。

---

## 九、微信登录与用户身份

登录场景通常会面对两个问题：

1. 如何识别“这是谁”。
2. 如何判断“这是不是同一个用户”。

### 1. `wx.login()` 的作用

它会拿到临时登录凭证 `code`。

### 2. `openid` 的意义

`openid` 是用户在当前小程序中的唯一身份标识，通常用来：

1. 标识用户。
2. 判断新老用户。
3. 建立用户业务数据关联。

### 3. 一个关键安全点

`AppSecret` 不能放在前端页面里直接暴露，换取 `openid` 的核心流程一般应该放在服务端或云函数里处理。

这部分的重点不是死记 API，而是分清前端、服务端和平台密钥之间的边界。

## 十、本地缓存

### 1. 为什么要缓存

缓存常用于：

1. 恢复用户状态。
2. 减少重复请求。
3. 做非强实时数据的快速展示。

### 2. 读取缓存

```js
const value = wx.getStorageSync("userInfo")
```

### 3. 写入缓存

```js
wx.setStorageSync("userInfo", {
  nickname: "Tom",
})
```

### 4. 什么时候适合缓存

比如商城首页、城市列表、最近浏览记录这类“允许短时间不完全实时”的内容。

换句话说，缓存适合提升体验，但不能拿来替代权威数据源。

---

## 十一、设备能力

小程序宿主环境可以直接提供很多设备级能力。

### 1. 常见能力

1. 扫码。
2. 拍照。
3. 蓝牙。
4. 网络状态获取。
5. 屏幕亮度控制。
6. 地理位置。

### 2. 它的业务价值

这也是小程序相比普通网页的重要优势之一，因为很多能力在浏览器里要么受限、要么体验明显更差。

这正是小程序在业务选型里很有竞争力的一点：它不只是一个页面容器，还能接入更丰富的微信宿主能力。

---

## 十二、把业务场景和技术能力串起来

```text
业务需要微信内高触达和轻量使用
  -> 选择小程序承接入口
  -> 通过交互反馈、网络请求、登录、缓存、设备能力完成完整业务体验
```

---

## 十三、总结

1. 小程序最适合微信内轻量、高触达的业务场景。
2. 真实开发流程通常是结构、数据、逻辑分步推进。
3. 交互反馈、网络请求、登录、缓存、设备能力是业务开发高频能力。
4. 实战里不要只会调 API，更要理解何时用 Toast、何时缓存、何时走服务端。
5. 学这篇的重点，是把“小程序能做什么、常怎么做”建立成完整业务心智。
