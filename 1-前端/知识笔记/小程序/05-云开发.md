# 微信小程序云开发

## 一、什么是云开发

**云开发** 是微信提供的一套小程序后端基础能力，让开发者在很多中小型场景下不必自己从零搭服务器、数据库和文件存储，就能完成业务开发。

它的核心思想是：

```text
前端页面 + 云函数 + 云数据库 + 云存储 + 微信生态能力
```

可以把它理解成：平台帮你托管了一部分常见后端基础设施，但业务建模、权限设计、环境隔离、成本控制这些工程问题，并不会自动消失。

---

## 二、云开发提供了哪些核心能力

| 能力         | 作用                       |
| ------------ | -------------------------- |
| **云函数**   | 在云端执行后端逻辑         |
| **云数据库** | 存储结构化业务数据         |
| **云存储**   | 上传和管理文件             |
| **云调用**   | 在云函数中调用微信开放能力 |

### 1. 它解决了什么问题

1. 中小项目后端搭建成本高。
2. 登录鉴权流程复杂。
3. 文件存储和基础运维门槛高。

### 2. 但不要误解

云开发不是“没有后端”，而是“后端能力被平台封装了”。数据安全、权限设计、接口边界这些问题依然存在。

### 3. 先建立一个基本分工意识

| 部分           | 更适合放什么                                 |
| -------------- | -------------------------------------------- |
| **小程序前端** | 页面展示、用户交互、轻量数据提交             |
| **云函数**     | 权限校验、敏感逻辑、聚合计算、第三方服务调用 |
| **云数据库**   | 业务数据存储、查询、状态更新                 |
| **云存储**     | 图片、附件、音视频等文件资源                 |

一旦分工不清，项目后面最容易出现的问题就是：前端直接改库、云函数职责混乱、环境和权限一起失控。

---

## 三、什么时候适合用云开发

### 1. 适合

1. 中小型业务。
2. 活动页、工具类、社区类小程序。
3. 快速验证原型。
4. 团队后端资源有限的项目。

### 2. 不太适合

1. 超大规模复杂系统。
2. 强定制基础设施需求。
3. 非微信生态为主的通用后台系统。

### 3. 一个实战判断标准

如果你的项目同时满足下面几条，云开发通常比较合适：

1. 用户主要来自微信生态。
2. 业务读写模型不算特别复杂。
3. 需要快速上线或快速验证。
4. 团队更希望少做基础设施和运维工作。

反过来，如果你已经有成熟后端体系，或者业务需要跨端共享一整套统一服务，云开发就更适合作为局部能力，而不是唯一后端方案。

---

## 四、如何开通云开发

### 1. 基本流程

```text
创建小程序项目 → 打开开发者工具 → 开通云开发 → 创建云环境 → 绑定环境到项目
```

### 2. 什么是环境

**环境** 可以理解成一套彼此独立的云资源集合，里面包含：

1. 数据库。
2. 存储空间。
3. 云函数。
4. 运行配置。

### 3. 实战建议

至少区分：

1. 测试环境。
2. 正式环境。

不要把所有开发、测试、线上业务都放在同一个环境里。

### 4. 为什么环境隔离要尽早做

因为云开发的很多资源都是“跟环境绑定”的：

1. 云数据库数据不该混用。
2. 云函数配置不该互相污染。
3. 测试上传的文件不该直接进入正式资源空间。

如果项目一开始就把环境混在一起，后面再拆通常成本更高。

---

## 五、云函数

### 1. 什么是云函数

云函数是一段运行在云端的代码，适合承载：

1. 需要隐藏密钥的逻辑。
2. 数据库读写。
3. 调用第三方服务。
4. 需要服务端权限的处理。

### 2. 小程序端调用方式

```js
wx.cloud.callFunction({
  name: "login",
  data: {
    from: "index",
  },
  success(res) {
    console.log(res)
  },
})
```

### 3. 适合放进云函数的逻辑

1. 用户身份计算。
2. 权限校验。
3. 订单写入。
4. 敏感接口转发。

不要把所有逻辑都塞进前端页面里。

### 4. 不适合放进云函数的逻辑

1. 纯前端展示计算。
2. 可以直接在页面本地处理的简单格式转换。
3. 频繁、高并发且没有必要经过服务端的轻量 UI 行为。

云函数不是“所有代码的收纳盒”。它更适合承接需要服务端身份、权限或安全边界的逻辑。

---

## 六、云调用

**云调用** 是指在云函数里调用微信开放接口的能力。

### 1. 常见相关标识

| 标识      | 含义                                   |
| --------- | -------------------------------------- |
| `appid`   | 当前小程序应用标识                     |
| `openid`  | 同一用户在同一小程序中的唯一标识       |
| `unionid` | 同一用户在同一开放平台主体下的统一标识 |

### 2. 它为什么重要

很多用户身份、消息、订阅、开放数据相关能力，都需要在云函数或服务端语境里完成，而不是直接在前端暴露。

---

## 七、云存储

云存储用于处理文件上传、下载和管理。

### 1. 常见操作

```js
wx.cloud.uploadFile({
  cloudPath: "avatar/user-1.png",
  filePath: localPath,
})
```

```js
wx.cloud.downloadFile({
  fileID,
})
```

### 2. 典型场景

1. 头像上传。
2. 图片素材保存。
3. 临时文件托管。
4. 用户内容附件管理。

### 3. 一个常见误区

很多人把云存储当成“上传完就结束”，但真实项目里还要继续考虑：

1. 文件命名是否可追踪。
2. 是否需要按业务目录分层。
3. 上传失败、替换旧文件、删除废弃资源怎么处理。

---

## 八、云数据库

### 1. 基本概念

云数据库中最常见的组织单位是：

```text
数据库 → 集合 collection → 文档 document
```

可以粗略理解为：

```text
集合 ≈ 表
文档 ≈ 一条记录
```

### 2. 常见系统字段

| 字段      | 含义                 |
| --------- | -------------------- |
| `_id`     | 记录唯一标识         |
| `_openid` | 记录创建者的用户标识 |

其中 `_openid` 对做用户级数据隔离非常重要。

### 3. 基本 CRUD

```js
const db = wx.cloud.database()
const todoCollection = db.collection("todo")

todoCollection.add({
  data: {
    title: "学习云开发",
    done: false,
  },
})
```

```js
todoCollection.where({ done: false }).get()
todoCollection.doc(id).update({ data: { done: true } })
todoCollection.doc(id).remove()
```

### 4. 数据建模时先想三件事

1. 这份数据是按用户隔离，还是按业务实体隔离。
2. 这条记录未来最常见的查询条件是什么。
3. 哪些字段允许前端直接写，哪些必须经由云函数。

很多初学者的第一版表结构能跑，但一到真实业务就会暴露出权限和查询设计不清的问题。

## 九、权限、安全与环境隔离

这是初学者最容易忽视的部分。

### 1. 常见风险

1. 前端直接写库导致越权。
2. 没有按用户隔离数据。
3. 测试环境误写到正式环境。
4. 敏感逻辑放在小程序前端暴露。

### 2. 基本建议

1. 重要写操作尽量经由云函数。
2. 按用户身份设计数据库权限。
3. 开发、测试、线上环境分开。
4. 不要把密钥、敏感规则写在前端页面。

### 3. 一个最容易踩的坑

看起来“能从前端直接写数据库”很方便，但只要权限没设计好，就可能变成任意用户都能改别人的数据。

所以更稳的思路通常是：

1. 查询类能力按场景评估是否开放。
2. 关键写操作尽量走云函数。
3. 在云函数里结合 `openid` 做用户身份校验。

## 十、配额与成本理解

云开发不是完全无限资源。

### 1. 常见消耗来源

1. 云函数调用次数。
2. 数据库存储与读写。
3. 文件存储与下载流量。
4. 带宽与 CDN 消耗。

### 2. 为什么要关注配额

因为业务一旦增长，数据库读写、图片上传、音视频内容、实时通信都会迅速放大资源消耗。

### 3. 成本判断不要只看“现在够不够用”

更实际的判断方式是看业务增长后哪些环节最先放大：

1. 图片和文件多，存储与下载流量先涨。
2. 列表刷新频繁，数据库读次数先涨。
3. 云函数里聚合逻辑过多，请求量一高调用成本就会上去。

所以项目初期就应该养成“按链路看成本”的习惯，而不是只盯某一个资源项。

## 十一、一个实战思路

比如做一个“图片打卡”小程序，可以这样拆：

1. 前端页面负责拍照和展示。
2. 图片通过云存储上传。
3. 打卡记录写入云数据库。
4. 统计逻辑放入云函数。

这样前后端边界就会比较清楚。

### 1. 再往前走一步，可以这样理解职责边界

```text
页面负责收集和展示
  ↓
云存储负责承接文件
  ↓
云函数负责权限和业务处理
  ↓
云数据库负责保存结果数据
```

这条链路一旦清楚，后面无论是做打卡、社区、表单提交还是内容管理，小程序云开发的设计都会更稳定。

---

## 十二、小结

1. 云开发适合微信生态里的中小型业务、原型验证和后端资源有限的项目。
2. 它不是“没有后端”，而是平台替你托管了一部分后端基础设施。
3. 小程序前端、云函数、云数据库、云存储一定要尽早分清职责边界。
4. 真正容易出问题的地方通常不是 API 不会调，而是环境隔离、权限控制、数据建模和成本判断做得太晚。

---

## 十二、学习云开发时的正确认知

1. 它能让你更快做出产品，但不会自动替你做好架构。
2. 它降低了后端接入门槛，但不会消灭权限、安全、成本问题。
3. 它特别适合“先做起来”，但项目一旦变复杂，仍然要回到工程化设计。

---

## 十三、总结

1. 云开发是微信提供的一套后端基础设施能力。
2. 核心能力包括云函数、云数据库、云存储和云调用。
3. 它适合中小型小程序快速搭建，但不等于不需要后端思维。
4. 真正用好云开发的关键，在于环境隔离、权限设计和职责拆分。
5. 学这篇时，重点不是记 API 名字，而是理解它如何重构小程序开发方式。
