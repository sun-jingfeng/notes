# 微信小程序底层框架

## 一、一句话理解

小程序底层框架的核心，不是“像网页一样自由渲染”，而是把逻辑层、渲染层和原生能力拆开，在可控前提下换取开发效率、性能和平台治理能力。

---

## 二、小程序为什么采用 Hybrid 架构

**Hybrid 架构** 可以理解为：既借助 Web 技术的灵活开发效率，又利用原生能力补足性能和系统能力。

小程序之所以不完全走纯 Web 或纯原生，核心是要同时满足这几个目标：

1. 页面更新要快。
2. 体验不能太差。
3. 平台要可控、可审核。
4. 开发效率要高。

---

## 三、为什么不能纯原生

如果完全用原生实现，小程序代码就必须和微信客户端一起发版，这会导致：

1. 开发迭代速度过慢。
2. 每次更新都高度依赖客户端版本。
3. 业务开发灵活性不足。

这显然不符合小程序“快速开发、快速上线、快速迭代”的目标。

---

## 四、为什么也不能简单等同于网页

如果完全按传统网页模式来做，又会遇到几个问题：

1. 浏览器环境开放过度，平台控制难。
2. DOM 操作自由度高，但安全与一致性更难保证。
3. JS 和渲染抢同一线程时，容易影响交互体验。

所以小程序最终选择的是一套受控的、分层的、带宿主约束的运行模型。

---

## 五、小程序底层的核心分层

可以先建立这样一个基本理解：

```text
逻辑层（JavaScript）
	↓
数据通信 / setData
	↓
渲染层（WXML / WXSS 对应视图）
	↓
部分能力再连接到原生组件和系统能力
```

### 1. 逻辑层

负责：

1. 页面状态。
2. 事件响应。
3. 网络请求。
4. 数据处理。

### 2. 渲染层

负责：

1. 结构展示。
2. 样式呈现。
3. 用户界面更新。

### 3. 原生能力层

负责：

1. 地图。
2. 画布。
3. 输入框。
4. 摄像头。
5. 支付、定位等系统能力。

---

## 六、JavaScript 为什么能运行，但又不能操作 DOM

小程序里可以写 JavaScript，是因为宿主环境提供了 JavaScript 引擎；但它并不是浏览器环境，所以不会把完整 DOM、`window`、`document` 那一套直接开放给你。

### 1. 这样设计的原因

1. 提升安全性。
2. 保持平台一致性。
3. 限制不受控的页面操作。
4. 让渲染行为走统一框架通道。

### 2. 这带来的直接结果

1. 不能像网页那样 `document.querySelector()` 改 DOM。
2. 视图更新主要依赖数据驱动。
3. 写法上更像“声明式视图 + 受控更新”。

---

## 七、为什么小程序不用原生 HTML 标签

小程序使用的是自己的组件体系，比如 `view`、`text`、`button`，而不是直接开放完整 HTML 标签集合。

### 1. 好处

1. 标签体系更收敛，学习和约束更统一。
2. 平台更容易控制渲染和安全边界。
3. 可以为组件注入微信宿主特有能力。

### 2. 本质理解

这不是“不会做 HTML”，而是“故意不开放完整 HTML”。

---

## 八、`setData` 为什么重要

小程序里，逻辑层和渲染层不是直接共享同一个 DOM 树，所以页面更新通常依赖 `setData` 这类数据同步机制。

### 1. 这意味着什么

每次你更新状态，本质上是在把逻辑层的数据变更同步给渲染层。

### 2. 性能启发

1. 不要频繁传大对象。
2. 不要把无关字段反复整包更新。
3. 高频交互场景要控制更新粒度。

### 3. 一句话理解

小程序性能优化里，很多问题最后都会落到：**数据同步成本是不是过高。**

---

## 九、逻辑层和渲染层如何通信

可以把这个过程理解成：

```text
逻辑层产生新数据
	-> 通过框架通道同步给渲染层
	-> 渲染层根据新数据更新界面
```

这意味着页面卡顿时，不一定是“渲染慢”，也可能是：

1. 同步数据太频繁。
2. 一次同步的数据量太大。
3. 页面同时有很多依赖这批数据的视图更新。

所以很多小程序性能问题，根源并不在某个样式属性，而在通信和更新粒度。

---

## 十、原生组件为什么特殊

像 `input`、`textarea`、`map`、`canvas` 这类组件，并不完全等同于普通 `view`、`text`。

### 1. 它们特殊在哪

它们的渲染和能力实现往往有微信客户端原生层参与。

### 2. 为什么要这样设计

| 组件类型             | 为什么更适合原生参与           |
| -------------------- | ------------------------------ |
| `input` / `textarea` | 键盘控制、输入体验更好         |
| `map`                | 地图绘制复杂，原生性能更强     |
| `canvas`             | 图形绘制需求高，原生接口更高效 |

### 3. 对开发者意味着什么

1. 它们通常性能更强。
2. 但行为也更受宿主环境约束。
3. 某些层级、覆盖、渲染顺序问题要按小程序规则处理，而不是照搬浏览器经验。

---

## 十一、理解底层框架对开发有什么帮助

如果你知道小程序不是 DOM 直改模型，就更容易理解这些问题：

1. 为什么很多 Web 库不能直接搬过来。
2. 为什么页面更新要尽量精细化。
3. 为什么原生组件既强大又“有脾气”。
4. 为什么性能问题往往不是 CSS，而是数据传输和渲染机制。

---

## 十二、总结

1. 小程序底层采用的是 Hybrid 架构，而不是纯网页或纯原生方案。
2. 它把逻辑层、渲染层和部分原生能力分开处理，以兼顾效率、性能和平台控制。
3. 小程序能写 JavaScript，但没有浏览器里的完整 DOM 环境。
4. 页面更新的关键不在直接改节点，而在数据驱动和同步机制。
5. 学这篇的重点，是建立正确运行模型，这会直接影响你后续的性能优化和组件理解。
