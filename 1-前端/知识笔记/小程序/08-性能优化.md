# 微信小程序性能优化

## 一、小程序性能优化到底在优化什么

小程序性能优化，本质上是在优化这几个核心体验：

1. 启动速度。
2. 页面切换速度。
3. 数据更新速度。
4. 列表和复杂界面渲染流畅度。
5. 兼容性与稳定性。

### 1.1 优先级怎么排

真实项目里通常优先看三件事：

1. 首屏是不是慢。
2. 列表滚动是不是卡。
3. `setData` 是不是过多。

因为这三类问题最容易直接影响用户感知。

---

## 二、启动性能

### 2.1 用户看到的启动过程

小程序启动时，微信会先展示启动页，然后加载代码包、初始化宿主环境、创建页面实例，最后进入首屏。

### 2.2 启动慢通常慢在哪

1. 主包太大。
2. 首页依赖资源太多。
3. 启动阶段同步逻辑过重。
4. 首屏请求太多。

### 2.3 对应优化思路

| 问题         | 常见优化方向                     |
| ------------ | -------------------------------- |
| 主包太大     | 分包、删无用资源、压缩静态文件   |
| 首页依赖太多 | 延后非首屏逻辑、懒加载非关键资源 |
| 同步逻辑过重 | 初始化拆阶段、避免启动时做重计算 |
| 首屏请求太多 | 合并请求、延后非关键请求         |

---

## 三、分包加载

### 3.1 为什么分包

把不是首屏必须的页面和资源放到分包里，可以减少启动时必须下载的体积。

### 3.2 基本配置示例

```json
{
  "pages": ["pages/index/index", "pages/logs/logs"],
  "subPackages": [
    {
      "root": "packageA",
      "pages": ["pages/apple/apple"]
    },
    {
      "root": "packageB",
      "pages": ["pages/banana/banana"]
    }
  ]
}
```

### 3.3 使用分包的原则

1. 首页相关页面放主包。
2. 低频页面放分包。
3. 不要把高频公共逻辑切得过碎。

### 3.4 一个常见误区

分包不是拆得越多越好。如果公共依赖被反复带入，或者高频页面被拆散，体验反而可能更差。

---

## 四、代码包体积控制

### 4.1 常见方向

1. 删除无用代码和资源。
2. 精简 WXML 结构。
3. 压缩图片和静态资源。
4. 避免把大量素材直接塞入主包。
5. 合理拆分分包。

### 4.2 一个认知

代码包体积不是单纯为了过平台限制，更直接关系到首屏速度和用户等待成本。

### 4.3 一个实际判断标准

如果资源不是首屏必须看到的，就要先想：

```text
能不能压缩
能不能延后加载
能不能移出主包
```

## 五、页面切换成本

每次 `wx.navigateTo()` 都会创建新的页面层级，而 `wx.navigateBack()` 会销毁当前页面并返回上一层。

### 5.1 这意味着什么

1. 页面越多，切换成本越高。
2. 页面初始化逻辑过重时，跳转体验会明显变差。
3. 不合理的多层跳转会增加页面栈压力。

### 5.2 实战建议

1. 减少不必要的深层跳转。
2. 页面进入时只做必要初始化。
3. 重逻辑尽量延后执行。

## 六、数据通信优化

这是小程序性能优化里最核心的一块。

### 6.1 为什么 `setData` 成本高

因为它不是简单赋值，而是逻辑层向渲染层做一次数据同步。

### 6.2 优化原则

1. 多次更新尽量合并成一次。
2. 与界面无关的数据不要放进 `data`。
3. 不要传超大对象和长字符串。
4. 只更新真正需要变动的字段。

### 6.3 一个典型示例

```js
// 不推荐
this.setData({ a: 1 })
this.setData({ b: 2 })

// 更推荐
this.setData({
  a: 1,
  b: 2,
})
```

### 6.4 与界面无关的数据怎么放

```js
this.setData({
  title: "页面标题",
})

this._cacheData = {
  longText: "这段数据不需要参与渲染",
}
```

### 6.5 一个最常见的收益点

很多页面卡顿并不是因为算法多复杂，而是因为频繁、大体积地 `setData`。这通常是最值得优先检查的地方。

## 七、WXML 和列表层面的优化

### 7.1 减少不必要的事件绑定

每个绑定都会增加通信和处理成本，列表场景里尤其明显。

### 7.2 谨慎使用大 `dataset`

不要在节点的 `data-*` 上挂过大对象，否则事件回传时会带来额外开销。

### 7.3 控制节点复杂度

如果视图层结构过深、节点过多，也会增加渲染成本。

### 7.4 列表场景怎么判断

如果一个列表同时存在：

1. 节点很多。
2. 每项事件很多。
3. 每次更新数据量很大。

那它就很容易成为性能问题集中区。

## 八、系统信息、基础库和降级能力

### 8.1 获取系统信息

```js
const info = wx.getSystemInfoSync()
console.log(info.SDKVersion)
```

常见字段包括：

1. 品牌和机型。
2. 系统版本。
3. 微信版本。
4. 基础库版本。
5. 屏幕尺寸。

### 8.2 `wx.canIUse()`

```js
wx.canIUse("button.open-type.contact")
wx.canIUse("text.selectable")
```

它的价值在于：

1. 判断能力是否存在。
2. 做兼容分支。
3. 避免老版本环境直接报错。

### 8.3 一个现实问题

如果你依赖新 API，却没有兼容方案，线上老版本用户可能直接无法使用关键功能。

---

## 九、一个实用优化清单

1. 首屏页面尽量轻。
2. 主包尽量小，非首屏内容尽量分包。
3. `setData` 少而准，不要频繁大对象同步。
4. 列表里控制节点数量和事件绑定数量。
5. 用 `wx.canIUse()` 做能力判断。
6. 不要忽略弱网、低端机、旧基础库环境。

---

## 十、小结

1. 小程序性能优化的主战场是启动、页面切换和数据通信，其中 `setData` 往往是最高频、最有收益的检查点。
2. 分包加载和代码体积控制主要影响启动速度，页面初始化逻辑和请求策略也同样重要。
3. 列表节点复杂度、事件绑定数量、`dataset` 体积都会影响渲染表现。
4. 真正有效的优化，不是背技巧，而是理解小程序的运行模型、通信成本和用户最容易感知到的卡顿点。
5. 学这一篇时，要把优化思路按“启动 -> 切换 -> 数据更新 -> 列表渲染 -> 兼容降级”串起来。
