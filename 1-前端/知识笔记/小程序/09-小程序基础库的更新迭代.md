# 小程序基础库的更新迭代

## 一、什么是小程序基础库

小程序基础库可以理解为小程序运行时依赖的一套底层能力集合，它负责支撑组件系统、事件系统、数据绑定、通信机制和大量 API 的实际运行。

一句话理解：

```text
业务代码写在项目里，但真正让这些代码跑起来的底层能力，很多都来自基础库。
```

---

## 二、基础库和业务代码是什么关系

你的业务代码写在小程序项目里，而基础库是运行这些代码所依赖的底层环境能力。

你写的这些能力：

1. `view`、`button` 等组件。
2. `setData` 更新视图。
3. `wx.request()`、`wx.login()` 这类 API。

背后都依赖基础库实现。

### 2.1 为什么它重要

因为很多功能能不能用、行为是否一致、某些 Bug 是否被修复，都和基础库版本直接相关。

---

## 三、基础库通常包含什么

从理解层面看，它覆盖的主要是：

1. 组件系统。
2. 数据绑定。
3. 事件处理。
4. 页面通信。
5. 小程序 API 支持。

### 3.1 为什么它不放在业务代码包里

小程序基础库是内置在微信客户端中的，而不是随着每个业务小程序重复打包。

这样做的好处：

1. 减少业务代码包体积。
2. 平台可以统一修复底层问题。
3. 新能力可以随着客户端和基础库升级逐步开放。

这也是为什么很多能力升级时，你并不一定要改小程序源码，但仍然可能获得新支持。

---

## 四、基础库版本号怎么理解

基础库版本号通常遵循 `semver` 思路，例如 `2.3.1`。

| 部分    | 含义       |
| ------- | ---------- |
| `Major` | 大版本变更 |
| `Minor` | 功能迭代   |
| `Patch` | 修复补丁   |

### 4.1 如何获取当前基础库版本

```js
const info = wx.getSystemInfoSync()
console.log(info.SDKVersion)
```

### 4.2 为什么前端要关心版本号

因为很多 API、组件属性、平台行为，都可能依赖最低基础库版本。

常见场景：

1. 某个新组件在旧版本不可用。
2. 某个 API 在某个版本后才支持。
3. 某个历史 Bug 只在老版本出现。

这决定了你是否需要：

1. 做兼容判断。
2. 写降级逻辑。
3. 设置最低基础库要求。

## 五、版本比较与兼容判断

有时候你需要比较两个版本的新旧。

```js
function compareVersion(v1, v2) {
  const arr1 = v1.split(".")
  const arr2 = v2.split(".")
  const len = Math.max(arr1.length, arr2.length)

  while (arr1.length < len) arr1.push("0")
  while (arr2.length < len) arr2.push("0")

  for (let index = 0; index < len; index++) {
    const num1 = parseInt(arr1[index], 10)
    const num2 = parseInt(arr2[index], 10)

    if (num1 > num2) return 1
    if (num1 < num2) return -1
  }

  return 0
}
```

使用示例：

```js
compareVersion("1.11.0", "1.9.9")
compareVersion("1.11.0", "1.11.0")
compareVersion("1.11.0", "1.99.0")
```

### 5.1 `compareVersion` 和 `canIUse` 的区别

1. `compareVersion` 更像自己控制的版本比较工具。
2. `wx.canIUse()` 更像判断某个具体能力是否可用。

真实项目里更常见的做法是：

```text
能用 canIUse 判断能力时优先判断能力
需要做更细版本控制时再比较版本号
```

### 5.2 真实开发里怎么快速判断

| 场景                                | 更推荐                |
| ----------------------------------- | --------------------- |
| 只想知道某个 API / 组件能力能不能用 | `wx.canIUse()`        |
| 需要做版本门槛提示或最低版本拦截    | 版本号比较            |
| 需要做灰度发布或问题版本规避        | 版本号比较 + 业务开关 |

一个常见经验是：优先按“能力是否存在”做判断，只有在业务明确依赖某个版本区间行为时，再去引入版本比较。

## 六、基础库是怎么更新的

基础库更新通常不是你主动下载一个 SDK，而是随着微信客户端生态逐步迭代。

```text
微信客户端版本更新
    ↓
新基础库能力准备
    ↓
灰度推送 / 逐步放量
    ↓
稳定后正式可用
```

### 6.1 为什么要灰度

因为新基础库一旦有问题，影响的不是一个项目，而是大量小程序，所以平台通常会先小范围验证，再逐步放开。

### 6.2 如果有问题会怎样

严重问题可能会回退版本，或者通过后续补丁版本修复。

### 6.3 这为什么会直接影响业务上线

因为基础库更新不是你项目单独升级，而是平台能力侧的整体变化。

这意味着：

1. 你今天测试通过的能力，不代表所有线上用户立刻都处于同一基础库环境。
2. 你看到的 bug，可能不是业务代码写错，而是某些版本下的基础库行为差异。
3. 发布策略不能只看“开发者工具里能不能跑”，还要看真实用户覆盖和灰度节奏。

---

## 七、开发者应该怎么应对基础库更新

### 7.1 不要盲目追新

新能力很好，但要先确认：

1. 目标用户的基础库覆盖情况。
2. 是否有兼容策略。
3. 是否会影响线上老用户。

### 7.2 更实用的做法

1. 关注官方更新日志。
2. 对关键功能做 `canIUse` 判断。
3. 在测试环境先验证新能力。
4. 对重要业务功能保留回退方案。

### 7.3 一个真实项目视角

基础库升级不是“看到新 API 就立刻上”，而是要判断：

1. 这个能力是不是业务关键路径。
2. 低版本用户占比高不高。
3. 不能用时有没有可接受的降级方案。

### 7.4 排查基础库兼容问题时的顺序

遇到“某些用户能用、某些用户不能用”的问题时，比较稳的排查顺序通常是：

1. 先确认出问题的能力最低基础库要求。
2. 再确认用户实际基础库版本。
3. 再看是不是应该用 `canIUse` 做能力判断。
4. 最后再判断是不是业务降级逻辑、本地缓存或页面条件分支出了问题。

很多兼容问题最后查出来，并不是 API 本身失效，而是项目里压根没有把“能力判断”和“降级处理”做完整。

---

## 八、什么时候要设置最低基础库

如果业务强依赖某个新能力，而且缺少合理降级方案，就要考虑设置最低基础库要求。

### 8.1 这样做的利与弊

| 做法           | 好处                   | 风险               |
| -------------- | ---------------------- | ------------------ |
| 兼容老版本     | 覆盖用户更多           | 开发和测试成本更高 |
| 提高最低基础库 | 实现更简单，能力更统一 | 会损失一部分老用户 |

这本质上是业务覆盖率和研发成本之间的取舍。

### 8.2 最低基础库和降级方案怎么选

| 选择           | 更适合                                     |
| -------------- | ------------------------------------------ |
| 继续兼容旧版本 | 老用户占比高、业务覆盖优先、能力可替代     |
| 提高最低基础库 | 新能力是核心路径、降级代价高、测试成本过大 |

真正要做的不是“永远兼容”或“永远提版本”，而是结合用户分布、业务收益和维护成本做选择。

### 8.3 一个现实提醒

如果你决定提高最低基础库，最好同步明确：

1. 哪个能力是触发门槛的关键原因。
2. 老版本用户会看到什么提示。
3. 项目文档和测试范围是否已经更新。

---

## 九、小结

1. 小程序基础库是支撑小程序运行的底层能力集合，组件、API、事件系统、数据绑定等都和它密切相关。
2. 基础库版本直接影响功能可用性、兼容性和 Bug 表现，所以前端必须有版本意识。
3. 版本处理不只是会比较版本号，更重要的是会判断“该不该兼容、该不该降级、该不该设置最低版本”。
4. 真实项目里，`canIUse`、灰度验证、回退方案、最低基础库要求，往往是一起考虑的。
5. 学这篇时，重点不是背版本号规则，而是理解“平台能力更新会如何影响你的业务代码和发布策略”。
