## I. Microservices Overview

### 1.1 What Are Microservices?

**Microservices** are an architectural style that builds an application as a collection of small, independently deployable services.

**Key characteristics:**

| Characteristic | Description |
| ------------ | --------------------------------- |
| **Separate processes** | Each service runs in its own process |
| **Business focus** | Built around a specific business capability |
| **Lightweight communication** | Communicate through HTTP/REST or message queues |
| **Independent deployment** | Can be deployed, scaled, and maintained independently |

### 1.2 Comparing Architectures

#### Monolithic vs. Microservice Architecture

| Dimension | Monolith | Microservices | Microservice tradeoffs |
| ------------ | ---------------- | -------------------------------- | ------------------------------ |
| **Deployment** | Deploy as one unit | Independent deployments and rapid iteration | Complex operations requiring containerization and automation |
| **Technology stack** | One shared stack | Each service can choose independently | Heterogeneity increases learning and maintenance costs |
| **Scalability** | Scale the entire application | Scale individual services as needed | Network communication and latency overhead |
| **Fault tolerance** | One failure can affect everything | Fault isolation | Cross-service data consistency is difficult |
| **Development efficiency** | Fast initially, slower later | Slower initially, faster later; autonomous teams | More complex integration and end-to-end testing |

#### Microservices vs. SOA

| Aspect | SOA | Microservices |
| ------------ | ------------ | -------- |
| **Management** | Centralized through an ESB | Decentralized |
| **Service granularity** | Larger | Smaller |
| **Deployment** | Usually as a whole | Independent |
| **Technology selection** | Uniform | Flexible |

### 1.3 Service Decomposition and Adoption Principles

**Decompose progressively around business boundaries; finer granularity is not always better.**

| Principle | Description | Common mistake |
| ---------------- | -------------------------------------------------- | -------------------------------- |
| **Single responsibility** | One service focuses on one core business capability | Splitting by database table creates excessively small services |
| **High cohesion, low coupling** | Keep services internally self-contained and reduce frequent cross-service calls | One endpoint traverses too many downstream services |
| **Independent data** | Each service should own its data boundary where possible | Several services share the same core business tables |
| **Gradual evolution** | Evolve from a modular monolith, extracting fast-changing modules first | Splitting everything at the beginning of the project |
| **Fault tolerance first** | Design timeouts, retries, fallbacks, and monitoring from the start | Checking only successful calls and ignoring failures |

| Good candidates for microservices | Cases where adoption can wait |
| ---------------------------- | ------------------------------------------ |
| **Clear business boundaries and relatively independent modules** | **Small team, simple business, rapidly changing requirements** |
| **Services need independent scaling or deployment** | **The monolith remains maintainable and the benefits of splitting are unclear** |
| **Clear team responsibilities and a need for autonomous development** | **Operations, monitoring, and automation are not ready** |

> 💡 Many projects are better served by starting with a **modular monolith** and extracting services gradually once boundaries stabilize.

## III. Service Registration and Discovery

### 3.1 How Registration and Discovery Work

Service instances change dynamically in a microservice architecture through scaling and failure recovery, so a registry centrally manages instance information.

```text
┌──────────┐    Register      ┌──────────────┐
│ Service A│ ──────────────▶  │              │
└──────────┘                  │   Registry   │
                              │ (Nacos, etc.)│
┌──────────┐    Discover      │              │
│ Service B│ ◀──────────────  └──────────────┘
└──────────┘
```

**Three roles in service governance:**

| Role | Description |
| -------------- | ---------------------------------------------------------------- |
| **Service provider** | Exposes endpoints for other services to call |
| **Service consumer** | Calls endpoints exposed by other services |
| **Registry** | Records and monitors instance status and pushes changes (such as Nacos or Eureka) |

| Question | Mechanism |
| ------------------------------------------ | ------------------------------------------------------------------ |
| How does a consumer know the provider's address? | Providers register at startup; consumers subscribe to and fetch service information |
| How does a consumer learn about status changes? | Providers report health through **heartbeats**; the registry removes abnormal instances and notifies consumers |
| Which provider instance should a consumer choose? | A **load-balancing** algorithm selects one instance |

> 💡 **Choose one registry per project:** Nacos (recommended with Spring Cloud Alibaba) or Eureka (Netflix's solution, common in older projects).

### 3.2 Nacos Service Registration

Deploy and start the Nacos **server** first, then add the Nacos **client** capabilities needed by the project. Nacos commonly serves two purposes: **service registration/discovery** and **configuration management**. They can be used separately or together.

| Capability | Starter | Purpose | Typical scenario |
| ---------------- | -------------------------------------------------------------- | -------------------------------- | ---------------------------- |
| **Service registration/discovery** | `spring-cloud-starter-alibaba-nacos-discovery` | Instance registration, subscriptions, health checks | Order service calling user service |
| **Configuration management** | `spring-cloud-starter-alibaba-nacos-config` | Centralized configuration, dynamic refresh, listeners | Shared configuration, dynamic routes, feature switches |

> 💡 For registration only, add `nacos-discovery`. To read and listen for configuration changes as well, also add `nacos-config`.

#### Deploy the Nacos Server

**Approach 1: Docker (Recommended)**

```bash
docker run -d \
  --name nacos \
  -p 8848:8848 \
  -p 9848:9848 \
  -e MODE=standalone \
  -e JVM_XMS=256m \
  -e JVM_XMX=256m \
  -e NACOS_AUTH_ENABLE=true \
  -e NACOS_AUTH_TOKEN=<base64EncodedRandomKeyOfAtLeast32Bytes> \
  -e NACOS_AUTH_IDENTITY_KEY=serverIdentity \
  -e NACOS_AUTH_IDENTITY_VALUE=security \
  -v /path/to/nacos/conf/application.properties:/home/nacos/conf/application.properties \
  -v /path/to/nacos/logs:/home/nacos/logs \
  nacos/nacos-server:v2.5.4
```

> 💡 With authentication enabled, Nacos 2.x requires `NACOS_AUTH_TOKEN` (the Base64 encoding of a random key of at least 32 bytes) plus `NACOS_AUTH_IDENTITY_KEY` and `NACOS_AUTH_IDENTITY_VALUE`; otherwise startup fails. On Mac Apple Silicon (M1/M2/M3), add `--platform linux/amd64` after `docker run -d` if the image does not start.

- Console: http://localhost:8848/nacos ; before Nacos 2.4.0 the admin account defaulted to `nacos`/`nacos`. Since 2.4.0 there is no default password: with authentication enabled, initialize the `nacos` admin password on first login
- Routine use: `docker start nacos` to start; `docker stop nacos` to stop

> 💡 The 2.5.x line shown here is still maintained (2.5.4, August 2026). Nacos 3.x moves the console to its own port, 8080 (`http://localhost:8080`, publish `-p 8080:8080`), and requires a token for admin APIs by default. Spring Cloud Alibaba 2025.0.x (Boot 3.5) and 2025.1.x (Boot 4) ship the Nacos 3.x client, which checks which features the server supports, so it also works against a 2.5.x server.

**Approach 2: Official Installation Package**

Download `nacos-server-xxx.tar.gz` from [Nacos releases](https://github.com/alibaba/nacos/releases), extract it, then run:

```bash
# Linux/Mac
sh bin/startup.sh -m standalone

# Windows
bin/startup.cmd -m standalone
```

#### Configuration Files and Persistence

Nacos server configuration resides at `conf/application.properties` in the installation directory. For Docker, bind-mount it from the host with `-v`, then restart the container after changes.

By default, Nacos uses embedded **Derby**, storing data under `data/derby-data/`; destroying the container loses that data. Use **MySQL** persistence in production:

| Step | Action |
| ---- | ---- |
| **1. Initialize the schema** | Run the bundled `conf/nacos-mysql.sql` script to create the required MySQL tables |
| **2. Update configuration** | Declare the database type and connection settings in `application.properties` |

```properties
# Switch persistence to MySQL
spring.datasource.platform=mysql
db.num=1
db.url.0=jdbc:mysql://127.0.0.1:3306/nacos?characterEncoding=utf8&connectTimeout=1000&socketTimeout=3000&autoReconnect=true&useUnicode=true&serverTimezone=UTC
db.user=root
db.password=your_password
```

> 💡 With multiple Docker Compose containers, use the MySQL **service name** (or container name), such as `mysql`, in `db.url.0` rather than `localhost`; inside the Nacos container, `localhost` refers to the Nacos container itself. Docker resolves these names through its internal DNS.

#### Integrate the Project

**1. Add the dependency**

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

**2. Configure application.yml**

```yaml
spring:
  application:
    name: demo-service           # Service name
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848  # Nacos server address
        namespace: dev               # Namespace for environment isolation
        group: DEFAULT_GROUP         # Group
```

| Setting | Purpose | Typical usage |
| ----------------- | ------------ | -------------------------------------------------------------------- |
| **server-addr** | Nacos address | `localhost:8848` locally; usually cluster addresses or a domain in production |
| **namespace** | Environment isolation | Separate dev, test, and prod namespaces; services in different namespaces cannot discover one another |
| **group** | Grouping within an environment | Defaults to `DEFAULT_GROUP`; group by team/project within a namespace to narrow discovery |
| **application.name** | Registered service identifier | Consumers normally discover and call the service by this name |

**3. Enable service discovery**

| Annotation | Purpose |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| **@EnableDiscoveryClient** | Enable registration and fetching service lists. Place on the application class; works with Nacos, Eureka, etc. |

```java
@SpringBootApplication
@EnableDiscoveryClient  // Enable service discovery
public class DemoServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoServiceApplication.class, args);
    }
}
```

> 💡 Since Spring Cloud Edgware, a `DiscoveryClient` implementation such as `spring-cloud-starter-alibaba-nacos-discovery` on the classpath enables registration through auto-configuration; `@EnableDiscoveryClient` can be omitted.

### 3.3 Nacos Heartbeats and Instance Removal

A **Nacos heartbeat** is a periodic report from the Nacos client indicating that the current instance is alive. Its main purpose is to maintain **ephemeral instance** health and prevent consumers from calling crashed or unreachable instances. Client heartbeat-based liveness primarily applies to **ephemeral instances**, with `ephemeral=true`.

#### 1. Heartbeat-Related Configuration

The setting most directly related to heartbeats is `ephemeral`:

```yaml
spring:
  cloud:
    nacos:
      discovery:
        ephemeral: true   # true: ephemeral instance relying on client heartbeats
```

| Setting | Meaning | Impact on heartbeats |
| -------------- | ---- | ---------------- |
| **ephemeral=true** | Ephemeral instance | Relies on continuous client heartbeats; common default with Spring Cloud Alibaba |
| **ephemeral=false** | Persistent instance | Managed through the registry's persistent-instance mechanisms rather than the default client-heartbeat model |

> 💡 Most Spring Cloud Alibaba projects can retain `ephemeral=true`. In interviews and everyday development, Nacos heartbeats usually refer to **ephemeral-instance liveness**.

#### 2. Heartbeat and Removal Flow

```text
Service starts and registers its instance
  ↓
Nacos records service name, IP, port, metadata, etc.
  ↓
Client sends periodic heartbeats
  ↓
Nacos updates the last-heartbeat timestamp
  ↓
No heartbeat before timeout: mark the instance unhealthy
  ↓
Continued timeout without recovery: remove the instance
  ↓
Consumers receive the change and update their local service lists
```

| Concept | Description |
| ---------------- | -------------------------------------------------------------------- |
| **Ephemeral instance** | Common Spring Cloud Alibaba/Nacos default; relies on client heartbeats |
| **Heartbeat** | Periodic client liveness signal, not a business request |
| **Unhealthy instance** | Heartbeats have been absent for a while; excluded from normal traffic distribution |
| **Instance removal** | Delete an unrecovered instance from the registry so consumers stop discovering it |

#### 3. Ephemeral vs. Persistent Instances

| Aspect | Ephemeral (ephemeral=true) | Persistent (ephemeral=false) |
| -------------- | ------------------------------------------------- | ------------------------------------------- |
| **Relies on client heartbeats** | Yes; clients continuously report liveness | Does not follow this client-heartbeat model |
| **Common scenarios** | Mainstream Spring Cloud Alibaba registration/discovery | Special governance or explicitly managed instance state |
| **Interview focus** | Heartbeats, unhealthy status, removal, consumer awareness of changes | Explain that this is not the mainstream default path |

| Scenario | Nacos behavior | Effect on calls |
| ------------------------ | ---------------------------------------------- | ---------------------------------------------- |
| **Healthy instance** | Receives heartbeats and maintains healthy status | Consumers discover and load-balance to it |
| **Process crash / machine power loss** | Heartbeats stop; instance is eventually marked unhealthy and removed | New requests are no longer assigned to it |
| **Network instability / connection failure** | Temporary heartbeat failures may mark the instance abnormal | False removal is possible; consider retries, monitoring, and fault tolerance |
| **Graceful shutdown** | Instance deregisters proactively without waiting for a heartbeat timeout | Faster removal; fewer calls to old instances during rolling deployment |

> 💡 In Spring Cloud Alibaba, start with the model "ephemeral instances plus heartbeat-based liveness." Nacos 2.x uses persistent connections and gRPC extensively for Naming/Config communication; from a governance perspective, clients still continuously report instance liveness to the registry.

#### 4. Engineering Recommendations

| Recommendation | Reason |
| -------------------------- | -------------------------------------------------------------------- |
| **Prefer default heartbeat settings** | Excessively frequent heartbeats increase registry load and susceptibility to transient instability |
| **Use graceful shutdown too** | Heartbeats detect whether instances remain alive; they do not replace proactive deregistration during deployment |
| **Distinguish liveness from business availability** | Healthy heartbeats do not guarantee a healthy database, thread pool, or downstream dependency |
| **Combine the registry with monitoring** | Discovery is not full observability; logs, metrics, and alerts are still needed |

### 3.4 Eureka Registration (Netflix Solution, Optional Reading)

As with Nacos, deploy **Eureka Server** first, then configure clients in business services. Disable the server's self-registration and registry fetching so it acts only as a registry. Clients set `defaultZone` to its address and can use `prefer-ip-address: true` to register by IP.

#### Eureka Server Configuration

```yaml
server:
  port: 8761

eureka:
  instance:
    hostname: localhost
  client:
    register-with-eureka: false   # Server does not register itself
    fetch-registry: false         # Server does not fetch services
    service-url:
      defaultZone: http://${eureka.instance.hostname}:${server.port}/eureka/
```

#### Eureka Client Configuration

```yaml
eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/
  instance:
    prefer-ip-address: true  # Register using an IP address
```

## IV. Service Calls

Services make remote HTTP calls through `RestClient` (or the older `RestTemplate`) or through declarative interface clients such as OpenFeign and Spring's HTTP Service Clients.

### 4.1 Service Discovery and Load Balancing

**What happens when calling by service name:**

A request to a **service name** such as `http://user-service/...` performs three steps: fetch the service's instances from the registry → select one according to a load-balancing policy → send the actual HTTP request to that instance's IP and port. **Spring Cloud LoadBalancer** selects the instance (round robin by default when several exist).

> 💡 Normally use a **`@LoadBalanced` RestClient** or **OpenFeign** to let the framework handle this. To manually fetch and select instances, use `DiscoveryClient`:

```java
@Service
public class DemoService {

    @Autowired
    private DiscoveryClient discoveryClient;

    public URI chooseUserServiceInstance() {
        // 1. Fetch the instance list by service name
        List<ServiceInstance> instances = discoveryClient.getInstances("user-service");
        if (instances == null || instances.isEmpty()) {
            throw new IllegalStateException("No available instances of user-service");
        }

        // 2. Load balancing: choose one instance (randomly here)
        ServiceInstance instance = instances.get(
            ThreadLocalRandom.current().nextInt(instances.size())
        );

        // 3. Return the selected instance's address, such as http://192.168.1.10:8081
        //    The caller then sends the HTTP request to uri + "/users/" + id
        return instance.getUri();
    }
}
```

### 4.2 RestClient and RestTemplate

**RestClient** (Spring Framework 6.1+, Spring Boot 3.2+) is Spring's recommended synchronous HTTP client, with a fluent API. **RestTemplate** is the older template-style client: it is in maintenance mode, and Spring plans to deprecate it formally in Spring Framework 7.1 and remove it in 8.0. For calls by **service name**, mark the client's builder or bean with **@LoadBalanced** so Spring Cloud LoadBalancer resolves the name and selects an instance.

**Four elements of a remote call:** service name (for instance discovery), HTTP method and path, request parameters or body, and response type.

#### 1. Register a Load-Balanced RestClient

```java
@Configuration
public class RestClientConfig {

    @Bean
    @LoadBalanced   // Every RestClient built from this builder resolves service names through LoadBalancer
    public RestClient.Builder restClientBuilder() {
        return RestClient.builder();
    }
}
```

#### 2. Make a Remote Call with RestClient

```java
@Service
public class DemoService {

    private final RestClient restClient;

    public DemoService(RestClient.Builder builder) {
        // clone(): the builder bean is a shared singleton, so copy it before customizing
        // Use the service name instead of IP:port; LoadBalancer chooses an instance per request
        this.restClient = builder.clone().baseUrl("http://user-service").build();
    }

    // GET with a path variable; the JSON body is converted to User
    public User getUser(Long userId) {
        return restClient.get()
                .uri("/users/{id}", userId)
                .retrieve()
                .body(User.class);
    }

    // Generic response types need a ParameterizedTypeReference
    public List<User> getUsers() {
        return restClient.get()
                .uri("/users")
                .retrieve()
                .body(new ParameterizedTypeReference<List<User>>() {});
    }

    // Custom headers, status handling, and access to the full response
    public ResponseEntity<User> createUser(User user) {
        return restClient.post()
                .uri("/users")
                .header("Authorization", "Bearer token")
                .contentType(MediaType.APPLICATION_JSON)
                .body(user)
                .retrieve()
                .onStatus(HttpStatusCode::is4xxClientError, (request, response) -> {
                    throw new IllegalStateException("user-service rejected the request: " + response.getStatusCode());
                })
                .toEntity(User.class);
    }
}
```

| Method | Description |
| ------------------------------------- | ------------------------------------------------------------ |
| `get()` / `post()` / `put()` / `delete()` | Selects the HTTP method |
| `uri(template, variables...)` | Path with `{placeholders}` expanded from the arguments |
| `header()` / `contentType()` / `body()` | Request headers and body (the body is serialized to JSON) |
| `retrieve()` | Sends the request; 4xx/5xx responses throw `RestClientResponseException` subclasses by default |
| `onStatus(predicate, handler)` | Replaces the default error handling for matching status codes |
| `body(Class)` / `toEntity(Class)` / `toBodilessEntity()` | Reads the body, the full `ResponseEntity`, or only the status and headers |

#### 3. RestTemplate in Existing Code

```java
@Configuration
public class RestTemplateConfig {

    @Bean
    @LoadBalanced  // Enable LoadBalancer for service-name calls
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}

// Simple call: URL + response type
User user = restTemplate.getForObject("http://user-service/users/" + userId, User.class);

// exchange: custom headers and access to the status code
HttpHeaders headers = new HttpHeaders();
headers.set("Authorization", "Bearer token");
HttpEntity<Void> entity = new HttpEntity<>(headers);

ResponseEntity<User> response = restTemplate.exchange(
    "http://user-service/users/{id}",
    HttpMethod.GET,
    entity,
    User.class,
    userId
);
User body = response.getBody();
HttpStatusCode status = response.getStatusCode();  // Spring 6 returns HttpStatusCode
```

| RestTemplate | RestClient equivalent |
| ---------------------------------- | ------------------------------------------------------------ |
| `getForObject(url, User.class)` | `get().uri(url).retrieve().body(User.class)` |
| `postForEntity(url, body, User.class)` | `post().uri(url).body(body).retrieve().toEntity(User.class)` |
| `exchange(url, method, entity, type)` | `method(method).uri(url).headers(...).retrieve().toEntity(type)` |
| `new RestTemplate()` | `RestClient.create()` or `RestClient.builder()...build()` |

### 4.3 OpenFeign

**OpenFeign** is a declarative HTTP client: interfaces and annotations describe which endpoint to call on which service. The framework generates implementations at runtime and performs discovery, load balancing, and HTTP calls. Two annotations are central:

| Annotation | Purpose |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **@EnableFeignClients** | On the application class, enables Feign and scans/registers `@FeignClient` interfaces. For interfaces in other packages (such as an API module), specify `basePackages` or `clients`. |
| **@FeignClient** | Declares an HTTP client interface. `name`/`value` is the service name used for discovery/load balancing; `fallback`/`fallbackFactory` provide circuit-breaker fallbacks. |

Add the dependency → Annotate the application with `@EnableFeignClients` → Define a `@FeignClient` interface matching the provider's REST signatures → Inject it and call it like a local method.

> **Note**: since Spring Cloud 2022.0, the Spring Cloud team treats OpenFeign as **feature-complete**: it receives bug fixes and small community changes only, and the team suggests Spring's HTTP Service Clients for new code. OpenFeign remains widely used and supported in the current release trains.

#### 1. Add the Dependency

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-openfeign</artifactId>
</dependency>
```

#### 2. Enable Feign

```java
@SpringBootApplication
@EnableFeignClients  // Enable Feign clients
public class DemoServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoServiceApplication.class, args);
    }
}
```

#### 3. Define the Feign Interface

```java
@FeignClient(name = "user-service", fallback = UserClientFallback.class)
public interface UserClient {

    @GetMapping("/users/{id}")
    User getUserById(@PathVariable("id") Long id);

    @PostMapping("/users")
    User createUser(@RequestBody User user);

    @GetMapping("/users")
    List<User> getUsers(@RequestParam("ids") List<Long> ids);
}
```

#### 4. Use the Feign Client

```java
@Service
public class DemoService {

    @Autowired
    private UserClient userClient;

    public String getUserName(Long userId) {
        // Call the remote service like a local method
        User user = userClient.getUserById(userId);
        return user.getName();
    }
}
```

#### 5. Feign Configuration

```yaml
# Spring Cloud OpenFeign 4.x (Spring Cloud 2022.0+); earlier versions used the feign. prefix
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connectTimeout: 5000   # Connection timeout
            readTimeout: 5000      # Read timeout
            loggerLevel: BASIC     # Logging level: NONE/BASIC/HEADERS/FULL
      compression:
        request:
          enabled: true   # Request compression
        response:
          enabled: true   # Response compression
```

#### 6. Logging

Feign can log requests and responses for troubleshooting. Regardless of how its logging level is configured, set the Feign interface package to **DEBUG** in **logging.level**, because Feign outputs at DEBUG and otherwise remains silent.

**Logging levels**

| Level | Description |
| ----------- | ------------------------------------------- |
| **NONE** | No logging (default) |
| **BASIC** | Request method, URL, response status, and duration only |
| **HEADERS** | BASIC plus request/response headers |
| **FULL** | Request/response headers and bodies for inspecting parameters and results |

**Approach 1: YAML Configuration**

Set `loggerLevel` in `spring.cloud.openfeign.client.config`. `default` applies globally; individual service names provide per-service configuration:

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            loggerLevel: FULL
          user-service:
            loggerLevel: BASIC

logging:
  level:
    com.example.api.client: DEBUG   # Feign interface package; must be DEBUG
```

**Approach 2: Java Configuration (Logger.Level Bean)**

Declare a `Logger.Level` bean in a configuration class and choose its scope through annotations:

```java
// Configuration class
public class DefaultFeignConfig {
    @Bean
    public Logger.Level feignLogLevel() {
        return Logger.Level.FULL;
    }
}

// Applies to one Feign client only
@FeignClient(value = "user-service", configuration = DefaultFeignConfig.class)
public interface UserClient { ... }

// Applies to all Feign clients (on the application class)
@EnableFeignClients(defaultConfiguration = DefaultFeignConfig.class)
@SpringBootApplication
public class DemoServiceApplication { ... }
```

- **Single client:** Set `configuration = DefaultFeignConfig.class` on `@FeignClient`.
- **Global:** Set `defaultConfiguration = DefaultFeignConfig.class` on `@EnableFeignClients`.

YAML changes logging by environment without code changes; Java configuration can manage the logger, interceptors, encoders/decoders, etc. together.

#### 7. Connection Pooling (OpenFeign with OKHttp)

Feign defaults to URLConnection without connection reuse. Switching to OKHttp enables connection pooling and improves high-concurrency performance.

**1. Add the dependency**

```xml
<!-- ok-http -->
<dependency>
    <groupId>io.github.openfeign</groupId>
    <artifactId>feign-okhttp</artifactId>
</dependency>
```

**2. Enable connection pooling**

```yaml
spring:
  cloud:
    openfeign:
      okhttp:
        enabled: true   # Enable OKHttp connection-pool support
```

#### 8. RequestInterceptor

**RequestInterceptor** is Feign's request-interceptor interface, invoked before each request is sent. It can modify `RequestTemplate`, for example to add common headers carrying tokens, TraceId, tenant IDs, or current-user information. Declare a `RequestInterceptor` bean in a configuration class and apply it through `@EnableFeignClients(defaultConfiguration = FeignConfig.class)` or `@FeignClient(configuration = FeignConfig.class)`; it then runs for every request from that client.

```java
@Configuration
public class FeignConfig {
    @Bean
    public RequestInterceptor requestInterceptor() {
        return template -> {
            // UserContext is a ThreadLocal holder filled by an MVC interceptor from the incoming X-User-Id header
            Long userId = UserContext.getUserId();
            if (userId != null) {
                template.header("X-User-Id", userId.toString());
            }
        };
    }
}
```

#### 9. Best Practices

| Practice | Description |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Separate API module** | Put Feign interfaces and DTOs in a shared API module; consumers specify scanning with `@EnableFeignClients(basePackages = "xxx.api.client")` or `@EnableFeignClients(clients = {UserClient.class})`. |
| **Timeouts and retries** | Set `connectTimeout` and `readTimeout` in `spring.cloud.openfeign.client.config`; retry cautiously to avoid duplicate writes, optionally with circuit breaking. |
| **Circuit breaking and fallbacks** | Configure `fallback` or `fallbackFactory` on `@FeignClient` with Sentinel/Resilience4j in production, preventing downstream failures from overwhelming callers. |
| **Connection pools** | Enable OKHttp pooling in production to reduce connection setup overhead and improve concurrency. |
| **Logging levels** | Use NONE or BASIC in production, enabling FULL for troubleshooting; distinguish environments in YAML to control log volume. |
| **Common headers** | Add tokens, TraceId, tenant IDs, etc. centrally through `RequestInterceptor` instead of implementing them per endpoint. |
| **API design** | Avoid oversized request/response bodies; paginate list endpoints and keep method semantics aligned with the provider's REST contract. |

### 4.4 HTTP Service Clients (@HttpExchange)

**HTTP Service Clients** (Spring Framework 6+, backed by `RestClient` since 6.1) are Spring's own declarative clients: an interface annotated with `@HttpExchange` becomes a proxy that sends requests through a `RestClient`. They need no Spring Cloud dependency, and with the `@LoadBalanced` builder they call services by name.

```java
@HttpExchange("/users")
public interface UserApi {

    @GetExchange("/{id}")
    User getUserById(@PathVariable Long id);

    @PostExchange
    User createUser(@RequestBody User user);
}

@Configuration
public class HttpServiceConfig {

    @Bean
    public UserApi userApi(RestClient.Builder builder) {   // The @LoadBalanced builder
        RestClient restClient = builder.clone().baseUrl("http://user-service").build();
        HttpServiceProxyFactory factory = HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(restClient))
                .build();
        return factory.createClient(UserApi.class);
    }
}
```

| Annotation | Purpose |
| ---------------------------------------------- | ------------------------------------------------------- |
| `@HttpExchange` | Shared base path, headers, and content type on the interface |
| `@GetExchange` / `@PostExchange` / `@PutExchange` / `@DeleteExchange` | HTTP method and path on each method |
| `@PathVariable` / `@RequestParam` / `@RequestBody` / `@RequestHeader` | Map method arguments, as in Spring MVC |

> 💡 Spring Framework 7 (Spring Boot 4) adds `@ImportHttpServices`, which registers groups of HTTP service interfaces and configures them through properties, replacing the factory code.

### 4.5 Choosing a Service-Call Client

| Aspect | RestClient | RestTemplate | OpenFeign | HTTP Service Client |
| ---------------------- | ----------------------- | --------------------- | ----------------------------- | ------------------------------- |
| **Style** | Fluent, imperative | Template methods | Declarative interface | Declarative interface |
| **Dependency** | Spring Framework 6.1+ | Spring Framework | Spring Cloud OpenFeign | Spring Framework 6+ |
| **Status** | ✅ Recommended | Maintenance mode; deprecation planned | Feature-complete | ✅ Recommended |
| **Load balancing** | `@LoadBalanced` builder | `@LoadBalanced` bean | Built in | Through a `@LoadBalanced` RestClient |
| **Fallbacks** | Manual | Manual | `fallback` / `fallbackFactory` | Manual or Resilience4j |
| **Best for** | Dynamic URLs, fine-grained control | Existing code | Existing Spring Cloud projects | New declarative clients |

> 💡 For new code, use **RestClient** for individual calls and **HTTP Service Clients** or **OpenFeign** for shared, contract-style APIs. Use **WebClient** only when the application is reactive.

## V. Load Balancing

For calls by **service name** through RestClient, RestTemplate, or OpenFeign, **Spring Cloud LoadBalancer** chooses one instance from the available set.

### 5.1 Client-Side Load Balancing

Microservices typically use **client-side load balancing**: the caller obtains instances from the registry, selects one locally according to a policy, then sends the request, without an independent load-balancer proxy.

```text
                    ┌─────────────────┐
                ┌──▶│ user-service-1  │
                │   └─────────────────┘
┌──────────┐    │   ┌─────────────────┐
│  Caller  │────┼──▶│ user-service-2  │
└──────────┘    │   └─────────────────┘
                │   ┌─────────────────┐
                └──▶│ user-service-3  │
                    └─────────────────┘
(The caller includes the load balancer)
```

### 5.2 Spring Cloud LoadBalancer

Spring Cloud 2020+ replaces discontinued Ribbon with **LoadBalancer** for service-name resolution and instance selection.

| Annotation | Purpose |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **@LoadBalanced** | Marks `RestClient.Builder`, `RestTemplate`, or `WebClient.Builder` beans so service-name requests use LoadBalancer for resolution and balancing; without it, calls need concrete IP/port addresses rather than registry discovery. |

| Client | How to enable |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **RestClient** | Add **@LoadBalanced** to a `RestClient.Builder` `@Bean`; clients built from it use LoadBalancer. |
| **RestTemplate** | Add **@LoadBalanced** to its `@Bean`; requests from that bean then use LoadBalancer. |
| **OpenFeign** | No extra annotation; with `spring-cloud-starter-loadbalancer` on the classpath, Feign resolves and balances `@FeignClient(name = "serviceName")` automatically. |

For RestClient or RestTemplate calls, explicitly add `spring-cloud-starter-loadbalancer` if no other starter brings it in transitively. With OpenFeign it is usually transitive, so adding it again is unnecessary.

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>
```

### 5.3 Common and Custom Load-Balancing Policies

Without customization, the default is **RoundRobin**. Spring Cloud LoadBalancer includes:

| Policy | Description |
| -------------------------- | ------------ |
| **RoundRobinLoadBalancer** | Round robin (default) |
| **RandomLoadBalancer** | Random selection |

> 💡 Earlier Ribbon versions offered WeightedResponseTime, BestAvailable, etc.; these disappeared with Ribbon. LoadBalancer includes only RoundRobin and Random; implement custom policies for more complex needs.

To customize selection, declare a `ReactorLoadBalancer<ServiceInstance>` bean, obtain the service's `ServiceInstanceListSupplier` through `LoadBalancerClientFactory`, and wrap it in a policy. LoadBalancer loads this class into each service's own child context, so do not annotate it with `@Configuration` (or keep it outside component scanning). Register it with `@LoadBalancerClients(defaultConfiguration = LoadBalancerConfig.class)` for all services, or `@LoadBalancerClient(name = "serviceName", configuration = LoadBalancerConfig.class)` for one service. Example switching to **random** selection:

```java
// No @Configuration: registered through @LoadBalancerClient(s)
public class LoadBalancerConfig {

    @Bean
    ReactorLoadBalancer<ServiceInstance> randomLoadBalancer(
            Environment environment,
            LoadBalancerClientFactory clientFactory) {
        String name = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new RandomLoadBalancer(
            clientFactory.getLazyProvider(name, ServiceInstanceListSupplier.class),
            name
        );
    }
}

// Apply to all services (or annotate the application class instead)
@Configuration
@LoadBalancerClients(defaultConfiguration = LoadBalancerConfig.class)
public class LoadBalancerClientsConfig { }
```

## VI. Service Gateway

### 6.1 What Does a Gateway Do?

An **API Gateway** is the **unified entry point** for a microservice architecture. External requests pass through it for routing, authentication/authorization, rate limiting, circuit breaking, logging, and monitoring; backend services need not be exposed individually to clients.

| Function | Description |
| ------------ | ------------------------------------------------ |
| **Unified entry point** | Clients access the gateway, which forwards to the appropriate service |
| **Routing** | Forward according to paths, headers, and other rules |
| **Authentication/authorization** | Validate tokens and permissions centrally and reject failures |
| **Rate limiting/circuit breaking** | Protect backend services from traffic overload and failures |
| **Logging/monitoring** | Centralize request logs and timing for troubleshooting and monitoring |

**Common gateway options:**

| Solution | Characteristics |
| ------------------------ | ---------------------------------------------------------------------- |
| **Spring Cloud Gateway** | Nonblocking WebFlux-based reactive gateway with good performance; maintained by Spring (recommended) |
| **Zuul 1.x** | Blocking Servlet model with lower performance; no longer maintained by Netflix |
| **Kong / APISIX** | Based on Nginx/OpenResty and independent of Java; suitable for multilingual microservices |

```text
    Client request
        ↓
    ┌─────────┐
    │ Gateway │
    └────┬────┘
         │ Forward according to routing rules
    ┌────┴─────┬──────────┬──────────┐
    ↓          ↓          ↓          ↓
  user       demo       xxx          …  (other microservices)
```

### 6.2 Spring Cloud Gateway

**Spring Cloud Gateway** is Spring's WebFlux-based reactive gateway. **Routes** determine which requests are forwarded to which services.

| Concept | Description |
| --------------- | -------------------------------------------------------------------- |
| **Route** | Forwarding rule consisting of id, uri, predicates, and filters |
| **id** | Unique route identifier |
| **uri** | Destination; `lb://user-service` discovers and load-balances by service name |
| **predicates** | Determine whether a request matches the route (such as Path, Method, Header) |
| **filters** | Modify matched requests or responses (such as adding headers or stripping path prefixes) |

**Request processing flow:**

```text
    Request reaches Gateway
        ↓
    RoutePredicateHandlerMapping (test route predicates in order; stop at the first match)
        ↓
    FilteringWebHandler (combine route GatewayFilters and GlobalFilters into an Order-sorted chain)
        ↓ Pre phase (filter chain runs forward)
    NettyRoutingFilter forwards to the destination service
        ↓ Post phase (filter chain runs in reverse)
    Response returns to the client
```

> 💡 If multiple routes match a request, the **earlier configured route wins**. Put specific paths before wildcard routes.

#### 1. Add the Dependency

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-gateway</artifactId>
</dependency>
```

> 💡 This gateway is based on reactive **WebFlux** and is incompatible with **Spring MVC**. For an existing MVC monolith, create a separate gateway module and do not combine `spring-boot-starter-web` with `spring-cloud-starter-gateway` in one module.
>
> **Version note**: Spring Cloud Gateway 4.3 (Spring Cloud 2025.0) deprecates `spring-cloud-starter-gateway` in favor of `spring-cloud-starter-gateway-server-webflux` and binds its properties under `spring.cloud.gateway.server.webflux.*`. The `spring.cloud.gateway.*` keys shown here (routes, default-filters, globalcors) are then migrated only when `spring-boot-properties-migrator` is on the classpath; otherwise they are ignored, so rename them when upgrading. A Spring MVC-based variant, `spring-cloud-starter-gateway-server-webmvc`, also exists.

#### 2. Route Configuration Example

`Path` matches request paths; `StripPrefix=1` removes the first segment (for example, `/api/users/1` becomes `/users/1`); `AddRequestHeader` adds a header to forwarded requests. `lb://serviceName` discovers instances from the registry and load-balances between them.

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: lb://user-service                    # lb fetches instances from the registry
          predicates:
            - Path=/api/users/**                   # Match requests starting with /api/users
          filters:
            - StripPrefix=1                        # Remove the first path segment, /api

        - id: demo-service
          uri: lb://demo-service
          predicates:
            - Path=/api/demo/**
          filters:
            - StripPrefix=1
            - AddRequestHeader=X-Request-Source, gateway   # Identify gateway-originated requests downstream
```

#### 3. Predicate Factories

Predicates determine whether requests match a route and are configured under its `predicates`. Common predicates:

| Predicate | Description | Example |
| -------------------------- | ----------------- | ---------------------------------------------------- |
| **Path** | Path matching | `Path=/api/**` |
| **Method** | HTTP method | `Method=GET,POST` |
| **Header** | Header matching | `Header=X-Token, \d+` |
| **Query** | Query parameter | `Query=name, jack` or `Query=name` |
| **Cookie** | Require a matching cookie | `Cookie=chocolate, ch.p` |
| **Host** | Request domain | `Host=**.example.org` |
| **RemoteAddr** | Client IP range | `RemoteAddr=192.168.1.1/24` |
| **After** / **Before** / **Between** | Time range | `After=2024-01-01T00:00:00+08:00[Asia/Shanghai]` |
| **Weight** | Weighted routing (canary rollout) | `Weight=group1, 8` |

> 💡 A route can have several predicates; **all must match** for the route to apply (AND relationship).

#### 4. Filter Factories

Filters modify matching requests or responses and are configured under a route's `filters`. Common filters:

| Filter | Description |
| ------------------------- | ---------------------------------------------------------------- |
| **AddRequestHeader** | Add a request header |
| **RemoveRequestHeader** | Remove a request header |
| **AddResponseHeader** | Add a response header |
| **StripPrefix** | Remove the first N path segments (such as `/api/users/1` → `/users/1`) |
| **PrefixPath** | Prepend a path prefix (such as `/users/1` → `/api/users/1`) |
| **RewritePath** | Rewrite paths with regular expressions |
| **Retry** | Retry failed forwarding; configurable count and status codes |
| **CircuitBreaker** | Requires Resilience4j; forwards to a fallback URI when triggered |
| **RequestRateLimiter** | Redis-based token-bucket rate limiting |
| **DedupeResponseHeader** | Remove duplicate response headers, such as CORS headers added by both gateway and service |

**StripPrefix path transformations:**

| StripPrefix value | Original path | Forwarded path |
| -------------- | ------------------ | ----------- |
| 1              | `/api/users/1`     | `/users/1`  |
| 2              | `/api/v1/users/1`  | `/users/1`  |

**default-filters:** Route-level `filters` apply only to that route. Move shared filters, such as common request headers, into `default-filters` to apply them to every route:

```yaml
spring:
  cloud:
    gateway:
      default-filters:
        - AddRequestHeader=X-Request-Source, gateway
      routes:
        - id: user-service
          uri: lb://user-service
          predicates:
            - Path=/api/users/**
          filters:
            - StripPrefix=1    # This filter applies only to this route
```

> 💡 `default-filters` provides global configuration in YAML but differs from the `GlobalFilter` interface: the former applies built-in filter factories to all routes, while the latter implements custom filtering in Java.

#### 5. GatewayFilter

**GatewayFilter** is a **route-level filter**, applying only to a matched route and suitable for route-specific logic.

| Scenario | Why GatewayFilter fits |
| -------------------- | --------------------------------------------------------- |
| **Path rewriting** | Change one service's forwarding path without affecting others |
| **Route-specific headers** | Add headers, tracing markers, or canary markers for one downstream service |
| **Local authorization** | Extra permission checks apply only to selected routes |
| **Local retries/rate limiting** | Enable `Retry`, `RequestRateLimiter`, etc. for specific endpoints |

**Common approaches:**

| Approach | Implementation | Suitable uses |
| --------------------------- | ----------------------------------------------- | -------------------------------------- |
| **Built-in GatewayFilter** | Configure directly in a route's `filters` | `StripPrefix`, `AddRequestHeader`, etc. |
| **Custom GatewayFilter** | Extend `AbstractGatewayFilterFactory` | Reusable, parameterized route-level logic |

Method signature: `Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain)`. Put pre logic before `chain.filter(exchange)` and post logic after it with `.then(Mono.fromRunnable(...))`.

**Custom route-level filter example:**

```java
@Component
public class CheckTokenGatewayFilterFactory
    extends AbstractGatewayFilterFactory<CheckTokenGatewayFilterFactory.Config> {

  public CheckTokenGatewayFilterFactory() {
    super(Config.class);
  }

  @Override
  public List<String> shortcutFieldOrder() {
    return List.of("headerName", "required");
  }

  @Override
  public GatewayFilter apply(Config config) {
    return (exchange, chain) -> {
      String token = exchange.getRequest()
          .getHeaders()
          .getFirst(config.getHeaderName());

      if (config.isRequired() && (token == null || token.isBlank())) {
        exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return exchange.getResponse().setComplete();
      }
      return chain.filter(exchange);
    };
  }

  public static class Config {
    private String headerName = "Authorization";
    private boolean required = true;

    public String getHeaderName() {
      return headerName;
    }

    public void setHeaderName(String headerName) {
      this.headerName = headerName;
    }

    public boolean isRequired() {
      return required;
    }

    public void setRequired(boolean required) {
      this.required = required;
    }
  }
}
```

Corresponding YAML route configuration:

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: demo-service
          uri: lb://demo-service
          predicates:
            - Path=/api/demo/**
          filters:
            - StripPrefix=1
            - CheckToken=Authorization,true
```

> 💡 Removing `GatewayFilterFactory` from `CheckTokenGatewayFilterFactory` yields its YAML filter name, `CheckToken`. To control order explicitly, wrap the custom filter in `OrderedGatewayFilter`.

#### 6. GlobalFilter

**GlobalFilter** is a **global filter**, applying to requests passing through the gateway and suitable for shared cross-cutting logic.

| Scenario | Why GlobalFilter fits |
| ------------------ | --------------------------------------------------- |
| **Centralized authentication** | Validate tokens, login state, and tenant information for all requests |
| **Distributed tracing** | Generate or forward TraceId centrally instead of configuring each route |
| **Access logs** | Record URI, status, and duration for monitoring and auditing |
| **Shared context propagation** | Handle user, language, source, and other common headers centrally |

Unlike route filters, `GlobalFilter` is not listed directly in YAML `filters`. **Implement the interface and register a bean** instead. Usually combine it with `@Order`: smaller values execute earlier.

```java
@Component
@Order(-1)   // Smaller values execute earlier; authentication usually runs near the start
public class AuthGlobalFilter implements GlobalFilter {

  @Override
  public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    ServerHttpRequest request = exchange.getRequest();

    // Pre: validate the token and return 401 immediately on failure
    String token = request.getHeaders().getFirst("Authorization");
    if (token == null || !validateToken(token)) {
      exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
      return exchange.getResponse().setComplete();
    }

    // Continue through subsequent filters and forward the request; post logic runs in then
    return chain.filter(exchange).then(Mono.fromRunnable(() -> {
      // Post: record access logs, measure duration, etc.
    }));
  }

  private boolean validateToken(String token) {
    // Validate JWTs, etc. in a real project
    return true;
  }
}
```

| Point | Description |
| -------------- | ------------------------------------------------------ |
| **@Order(-1)** | Run early; commonly used for global authentication/logging |
| **pre** | Before `chain.filter(exchange)`; may intercept and return immediately |
| **post** | Inside `.then(Mono.fromRunnable(...))`; runs after forwarding completes |

#### 7. GatewayFilter vs. GlobalFilter

| Aspect | GatewayFilter | GlobalFilter |
| ---------------- | -------------------------------------------------- | ------------------------------------------------- |
| **Scope** | One route | All routes |
| **Registration** | YAML `filters` / `RouteLocator` / custom factory | Implement `GlobalFilter` and register a bean |
| **Granularity** | Fine-grained, service-specific configuration | Coarse-grained, shared cross-cutting logic |
| **Typical uses** | Paths, route-specific headers, local rate limits/retries | Authentication, logs, TraceId, shared context propagation |
| **Parameterized reuse** | Suitable, especially custom `GatewayFilterFactory` | Usually driven by common code rather than route parameters |

| Requirement | Better choice |
| ---------------------------------- | -------------------- |
| **Apply to one route only** | **GatewayFilter** |
| **Run for all requests** | **GlobalFilter** |
| **Pass parameters per route through YAML** | **GatewayFilter** |
| **Centralize login checks, logging, tracing** | **GlobalFilter** |

> 💡 Ask whether the requirement is **a rule for one route** or **cross-cutting logic shared by all traffic**. Prefer `GatewayFilter` for the former and `GlobalFilter` for the latter.

#### 8. Dynamic Routing with Nacos

Changes to static YAML routes require a gateway restart. **Dynamic routing** stores routes in Nacos; the gateway loads them at startup and registers a listener. Nacos configuration changes refresh the routing table automatically without a restart.

**Implementation:** Maintain JSON routes in Nacos (Data ID such as `gateway-routes.json`) → Load and listen through `NacosConfigManager.getConfigAndSignListener` → Parse JSON into `RouteDefinition` objects in the callback, write them with `RouteDefinitionWriter`, and publish `RefreshRoutesEvent`.

**① Nacos route configuration (JSON)**

Create a configuration in the Nacos console with Data ID `gateway-routes.json` and JSON format:

```json
[
  {
    "id": "user-service",
    "uri": "lb://user-service",
    "predicates": [
      { "name": "Path", "args": { "_genkey_0": "/api/users/**" } }
    ],
    "filters": [
      { "name": "StripPrefix", "args": { "_genkey_0": "1" } }
    ]
  },
  {
    "id": "demo-service",
    "uri": "lb://demo-service",
    "predicates": [
      { "name": "Path", "args": { "_genkey_0": "/api/demo/**" } }
    ],
    "filters": [
      { "name": "StripPrefix", "args": { "_genkey_0": "1" } }
    ]
  }
]
```

**Multiple Path patterns:** `Path` binds its arguments to a `patterns` list. In JSON, pass each pattern as a shortcut argument (`_genkey_0`, `_genkey_1`, …); a key named `pattern` matches no configuration property in Gateway 3.x/4.x, so such a route never matches. To match multiple paths for one service, use either approach:

| Approach | Description |
|------|------|
| **One route, multiple paths** | Use `_genkey_0`, `_genkey_1`, etc. in `args`, one pattern per entry, to match several paths with one route. |
| **Multiple routes** | Create one route per path pointing to the same `uri`; more routes, but a simple structure. |

Multiple-path example (one route):

```json
{
  "id": "demo-service",
  "uri": "lb://demo-service",
  "predicates": [
    { "name": "Path", "args": { "_genkey_0": "/api/demo/**", "_genkey_1": "/api/search/**" } }
  ],
  "filters": []
}
```

**② Listen and refresh routes in the gateway**

Use `NacosConfigManager.getConfigAndSignListener` to load configuration and register a listener. Nacos changes trigger `receiveConfigInfo`; parse JSON into a `RouteDefinition` list, delete old routes, write new ones, then publish `RefreshRoutesEvent` for the gateway to apply them.

```java
@Component
@RequiredArgsConstructor
public class DynamicRouteLoader {

    private final RouteDefinitionWriter routeDefinitionWriter;
    private final ApplicationEventPublisher publisher;
    private final NacosConfigManager nacosConfigManager;

    private final ObjectMapper objectMapper = new ObjectMapper();
    private static final String DATA_ID = "gateway-routes.json";
    private static final String GROUP = "DEFAULT_GROUP";
    private final Set<String> currentRouteIds = ConcurrentHashMap.newKeySet();

    @PostConstruct
    public void init() throws NacosException {
        String configInfo = nacosConfigManager.getConfigService()
                .getConfigAndSignListener(DATA_ID, GROUP, 5000, new Listener() {
                    @Override
                    public Executor getExecutor() { return null; }

                    @Override
                    public void receiveConfigInfo(String configInfo) {
                        updateRoutes(configInfo);
                    }
                });
        updateRoutes(configInfo);
    }

    private synchronized void updateRoutes(String json) {
        if (json == null || json.isBlank()) return;
        try {
            List<RouteDefinition> routes = objectMapper.readValue(
                    json, new TypeReference<List<RouteDefinition>>() {});
            // 1. Delete old routes and wait for all deletions to complete
            Mono.when(currentRouteIds.stream()
                            .map(id -> routeDefinitionWriter.delete(Mono.just(id)))
                            .toArray(Mono[]::new))
                    .block();
            currentRouteIds.clear();
            // 2. Save new routes sequentially and wait for completion
            for (RouteDefinition route : routes) {
                routeDefinitionWriter.save(Mono.just(route)).block();
                currentRouteIds.add(route.getId());
            }
            // 3. Publish the refresh event afterward
            publisher.publishEvent(new RefreshRoutesEvent(this));
        } catch (Exception e) {
            throw new RuntimeException("Failed to update dynamic routes", e);
        }
    }
}
```

| Implementation point | Description |
| -------- | ---- |
| **Ordering** | `delete` and wait with `block()`, then `save` and `block()`, then publish `RefreshRoutesEvent` to avoid races |
| **Concurrency** | Use `ConcurrentHashMap.newKeySet()` for `currentRouteIds` and `synchronized` on `updateRoutes` to prevent concurrent initial load/listener callbacks |
| **Mono.when** | Pass `.toArray(Mono[]::new)` to avoid varargs compatibility issues |

> 💡 `getConfigAndSignListener` returns current configuration and registers a listener; Nacos pushes invoke it automatically. Deserialize with Jackson's `ObjectMapper`; `RouteDefinition` maps to JSON fields `id`, `uri`, `predicates`, and `filters`.

> **Note:** When both Hutool and Jackson are present, these classes share names and IDEA may auto-import the wrong one:
>
> | Class | ✅ Correct (Jackson) | ❌ Easily confused (Hutool) |
> | ---------------- | ----------------------------------------------- | ---------------------------------- |
> | `ObjectMapper`   | `com.fasterxml.jackson.databind.ObjectMapper`   | `cn.hutool.json.ObjectMapper`      |
> | `TypeReference`  | `com.fasterxml.jackson.core.type.TypeReference` | `cn.hutool.core.lang.TypeReference`|
>
> Verify that imported packages start with `com.fasterxml.jackson`. With Spring Boot 4 (Jackson 3), the equivalents are `tools.jackson.databind.ObjectMapper` and `tools.jackson.core.type.TypeReference`.

| Aspect | Static YAML routes | Dynamic Nacos routes |
| ------------ | -------------------------- | ------------------------------------ |
| **Location** | Gateway application.yml | Nacos configuration center |
| **Applying changes** | Restart the gateway | Nacos pushes changes; gateway reloads them live |
| **Use cases** | Few, stable routes | Frequent changes, environment management, canary releases |

#### 9. Cross-Origin Configuration (CORS)

With separate frontend/backend applications, direct frontend calls to the gateway are subject to browser same-origin rules. Return CORS headers centrally at the gateway; downstream services need no additional CORS configuration.

```yaml
spring:
  cloud:
    gateway:
      globalcors:
        cors-configurations:
          '[/**]':
            allowedOriginPatterns: "*"   # In production, specify frontend domains such as https://app.example.com
            allowedMethods: "*"
            allowedHeaders: "*"
            allowCredentials: true
            maxAge: 3600
```

| Setting | Description |
| ---------------------- | ---- |
| **allowedOriginPatterns** | Allowed origin patterns; `*` means any. With `allowCredentials: true`, a wildcard is allowed only here, not in `allowedOrigins` (Spring Framework 5.3+ / Spring Cloud Gateway 3.0+) |
| **allowCredentials** | Whether cookies may be included |
| **maxAge** | Preflight response cache lifetime in seconds |

> **Note:** Once CORS is configured at the gateway, avoid `@CrossOrigin` or `CorsFilter` in services, which can duplicate CORS headers and cause browser errors. If unavoidable (such as a third-party service already adding them), add `DedupeResponseHeader` to `default-filters`:

```yaml
spring:
  cloud:
    gateway:
      default-filters:
        - DedupeResponseHeader=Access-Control-Allow-Origin Access-Control-Allow-Credentials, RETAIN_UNIQUE
```

## VII. Configuration Center

### 7.1 Why Use a Configuration Center?

When each microservice maintains its own application.yml, common settings (database addresses, logging levels, etc.) are scattered across services and require separate redeployments to change. A **configuration center** stores configuration externally (such as in Nacos), manages it centrally, and supports runtime refresh.

| Capability | Description |
| ------------ | ------------------------------------------------------------------ |
| **Centralized management** | Store service configurations together; one change can affect multiple services |
| **Dynamic refresh** | Apply changes without restarting services (live updates) |
| **Environment isolation** | Isolate dev/test/prod with namespaces or profiles |
| **Version management** | Nacos retains history for diffs and one-click rollback |

| Aspect | Service registry | Configuration center |
| -------------- | -------------------------------------------------- | ---------------------------------------------------- |
| **Managed data** | Instance addresses, ports, metadata, health | Runtime settings, switches, thresholds, rules, connection parameters |
| **Typical values** | `serviceName`, IP, port, instance status | Data-source addresses, logging levels, rate-limit rules, gateway routes |
| **Sources of change** | Instances joining/leaving, heartbeats, scaling | Configuration releases, environment changes, dynamic adjustments |
| **Direct consumers** | Service call paths | Application initialization and runtime behavior |
| **Representative components** | Nacos Naming / Eureka | Nacos Config / Spring Cloud Config |

> 💡 Nacos offers both **registry** and **configuration-center** capabilities, but they address different questions: where services are and whether they are alive, versus how services should run.

### 7.2 Integrating Nacos Configuration

Nacos provides registration/discovery and configuration management. For configuration integration, clients connect and fetch settings early in startup before initializing the application context.

**Spring Cloud projects commonly read Nacos configuration in two ways:**

| Approach | Mechanism | Suitable scenarios |
| ---------------- | ------------------------------------------------------- | -------------------------------------------------- |
| **Declarative** | `@ConfigurationProperties`, `@RefreshScope`, `@Value` | Inject business settings such as switches, thresholds, and timeouts into beans |
| **Programmatic** | `NacosConfigManager` → `ConfigService` | Manually fetch configuration, register listeners, process JSON/rules/dynamic routes |

> 💡 Prefer **declarative configuration** for ordinary business settings. Use **NacosConfigManager** when custom configuration-reading and callback logic is required.

#### 1. Add the Dependency

```xml
<!-- Nacos configuration center -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>
```

Remote configuration is imported with Spring Boot's standard **`spring.config.import`** mechanism. Spring Cloud Alibaba recommends it, and 2025.1.x (Spring Boot 4) no longer supports `bootstrap.yml` at all.

| Approach | Spring Cloud Alibaba | Description |
| ------------------------- | -------------------------------- | ------------------------------------------------------------ |
| **`spring.config.import`** | 2021.0+; the only option in 2025.1.x | ✅ Lists Nacos Data IDs in `application.yml`; no extra dependency |
| **`bootstrap.yml`** | Legacy; removed in 2025.1.x | Needs `spring-cloud-starter-bootstrap`; `shared-configs` / `extension-configs` and automatic Data IDs |

#### 2. application.yml Configuration

Put the Nacos server address, namespace, and group under `spring.cloud.nacos.config`, then list the Data IDs to import:

```yaml
spring:
  application:
    name: demo-service
  profiles:
    active: dev
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        namespace: dev              # Namespace
        group: DEFAULT_GROUP        # Default group for the imports below
  config:
    import:
      - optional:nacos:common.yaml                                                # Shared configuration
      - optional:nacos:${spring.application.name}.yaml                            # Service configuration
      - optional:nacos:${spring.application.name}-${spring.profiles.active}.yaml  # Service + environment
```

| Import syntax | Meaning |
| ----------------------------------------- | ------------------------------------------------------------ |
| `nacos:<dataId>` | Import a Data ID from the default group; startup fails if it cannot be loaded |
| `optional:nacos:<dataId>` | Import if present; a missing Data ID does not stop startup |
| `nacos:<dataId>?group=<group>` | Use another group for this Data ID |
| `nacos:<dataId>?refreshEnabled=false` | Disable live refresh for this Data ID (enabled by default) |

#### 3. Shared Configuration

Shared configuration contains values used by several services (common database addresses, logging levels, middleware connections, etc.). Store one copy in Nacos and import it in every service, as `common.yaml` above.

**Create in the Nacos console:** Configuration Management → Configuration List → Select namespace → Create configuration. Enter Data ID (such as `common.yaml`), Group (such as `DEFAULT_GROUP`), and content.

#### 4. Service-Specific Configuration

Service-specific Data IDs follow the convention below and are listed explicitly in `spring.config.import`:

```text
${spring.application.name}-${spring.profiles.active}.${file-extension}
Example: <serviceName>-<profile>.<extension>
```

| Data ID | Description |
| -------------------------- | ---------------------------------- |
| `<serviceName>-<profile>.yaml` | Settings specific to the service and environment |
| `<serviceName>.yaml` | Service settings independent of profile |
| `common.yaml` (or another shared ID) | Common settings shared by services |

> 💡 In the legacy `bootstrap.yml` mode, the client loads `<serviceName>.<extension>` and `<serviceName>-<profile>.<extension>` automatically, and shared files are declared with `spring.cloud.nacos.config.shared-configs`.

#### 5. Loading and Precedence

**Loading sequence:**

```text
Startup → Read application.yml → spring.config.import pulls each Nacos Data ID → Initialize ApplicationContext
```

**Precedence (high → low):** Spring Boot's config-data rules apply: an imported source overrides the file that imports it, and a later import overrides an earlier one.

| Priority | Configuration source |
| ------ | ------------------------------------------------- |
| Highest | Command-line arguments and environment variables |
| ↓ | Nacos `<serviceName>-<profile>.yaml` (imported last) |
| ↓ | Nacos `<serviceName>.yaml` |
| ↓ | Nacos `common.yaml` (imported first) |
| ↓ | Local `application-<profile>.yml` / `application.yml` |

> 💡 Remote Nacos configuration overrides local `application.yml`. Keep each key in one place, or override it at deployment time with an environment variable or command-line argument, which still wins.

#### 6. Live Configuration Updates

Changes in Nacos can take effect **without restarting** the microservice.

**Prerequisites:**

| Condition | Description |
| ---- | ---- |
| **Nacos Config integrated** | `spring-cloud-starter-alibaba-nacos-config` is present and connects to the correct namespace/group |
| **Configuration actually loaded** | Data ID, namespace, group, and `spring.config.import` or `bootstrap.yml` must match |
| **Refresh enabled for the Data ID** | Imports refresh by default (`refreshEnabled=false` turns it off); in bootstrap mode, set `refresh: true` on `shared-configs` / `extension-configs` |
| **Code reads refreshable values** | Use `@ConfigurationProperties` or `@RefreshScope + @Value`, not fixed one-time reads |

> 💡 **Changing Nacos configuration does not guarantee a live application update.** The client must receive the change, and the code must read values through a refreshable mechanism.

| Approach | Live updates | Mechanism |
| --------------------------------------- | -------------- | ------------------------------------------------------------------------- |
| **@ConfigurationProperties** | ✅ Supported | After Nacos publishes `RefreshEvent`, Spring Cloud rebinds properties automatically without another annotation |
| **@RefreshScope** + **@Value** | ✅ Supported | Refresh destroys/recreates the bean and reinjects `@Value` |
| **@Value alone** (no `@RefreshScope`) | ❌ Unsupported | Injected once when the bean is created; does not change afterward |

```java
// ✅ @ConfigurationProperties: Nacos changes refresh properties automatically
@Data
@Component
@ConfigurationProperties(prefix = "app.demo")
public class DemoConfig {
    private int maxItems;
}

// ✅ @RefreshScope + @Value: also supports live Nacos updates
@RestController
@RefreshScope
public class DemoController {
    @Value("${app.demo.maxItems}")
    private int maxItems;
}

// ❌ @Value without @RefreshScope: no live updates
@RestController
public class DemoController {
    @Value("${app.demo.maxItems}")
    private int maxItems;  // Does not change after injection
}
```

**Choosing between the approaches:**

| Annotation | Suitable scenarios |
| ------------------------------ | -------------------------------------------------------------- |
| **@ConfigurationProperties** | Many properties with a shared prefix; type-safe, supports nesting and IDE completion |
| **@RefreshScope** + **@Value** | A few individual properties used in Controllers/Services |

### 7.3 NacosConfigManager

**NacosConfigManager** is a **Spring bean** supplied by Spring Cloud Alibaba that manages the Nacos Config client and exposes its underlying `ConfigService`. It enables **programmatic** reads, listener registration, and custom handling of configuration changes, complementing declarative property binding.

| Aspect | Declarative binding | Programmatic reads with `NacosConfigManager` |
| ------ | -------------- | ------------------------------- |
| **Reading** | Automatically bind settings to bean fields | Call `ConfigService` explicitly |
| **Live updates** | Spring Cloud refreshes beans | Developer handles callbacks and memory updates |
| **Suitable content** | Business switches, thresholds, connection parameters | Dynamic routes, rule JSON, blocklists/allowlists, script configuration |
| **Complexity** | Low | Higher, but more flexible |

#### 1. What Problem Does It Solve?

Standard Nacos integration injects configuration into Spring beans. Some settings require immediate custom actions when changed rather than just injecting a field, for example:

| Scenario | Why `NacosConfigManager` fits |
| ---- | ------------------------------- |
| **Dynamic routes** | Rebuild `RouteDefinition` objects and refresh the gateway routing table |
| **Rules** | Refresh in-memory caches or rule engines for rate limits, blocklists, and allowlists |
| **Large JSON objects** | JSON/text configuration is unsuitable for many separate `@Value` fields |
| **Non-bean scenarios** | Changes must invoke initialization logic rather than merely update a property |

#### 2. Relationship with `ConfigService`

`NacosConfigManager` is an **entry point**; its underlying `ConfigService` performs configuration retrieval, listener registration, and publishing.

```text
NacosConfigManager
  ↓ Provides
ConfigService
  ↓ Executes
getConfig / addListener / getConfigAndSignListener / publishConfig
```

The relationship can be understood as:

| Component | Role |
| ---- | ---- |
| **NacosConfigManager** | Spring-managed adapter reusing the project's Nacos connection settings |
| **ConfigService** | Official Nacos client interface for reading, listening, and publishing configuration |
| **@ConfigurationProperties / @RefreshScope** | Spring-style declarative consumption of configuration |

> 💡 A key reason to use `NacosConfigManager` is that you **do not need to create another Nacos client or repeat server-addr, namespace, and authentication settings**. Reuse the client initialized by Spring Cloud Alibaba.

#### 3. Common Methods

`NacosConfigManager` has few entry-point methods; first obtain `ConfigService`:

```java
@Component
@RequiredArgsConstructor
public class RuleLoader {

  private final NacosConfigManager nacosConfigManager;

  public void load() throws NacosException {
    ConfigService configService = nacosConfigManager.getConfigService();
    String json = configService.getConfig("rule-config.json", "DEFAULT_GROUP", 5000);
    // Parse json and refresh local rules
  }
}
```

| Method | Owning class | Purpose |
| ---- | ------ | ---- |
| `getConfigService()` | `NacosConfigManager` | Get the underlying Nacos configuration client |
| `getConfig(dataId, group, timeoutMs)` | `ConfigService` | Fetch current configuration explicitly |
| `addListener(dataId, group, listener)` | `ConfigService` | Listen for subsequent changes to a configuration |
| `getConfigAndSignListener(...)` | `ConfigService` | Fetch initial configuration and immediately register a listener |

#### 4. Relationship with Automatic Refresh

`NacosConfigManager` is **not** an automatic-refresh switch; it operates at a different level from `@RefreshScope`.

| Approach | What happens after a change |
| ---- | -------------------- |
| **`@ConfigurationProperties`** | Spring rebinds properties automatically |
| **`@RefreshScope + @Value`** | Bean is recreated and fields reinjected |
| **`NacosConfigManager + Listener`** | Callback is invoked; the developer decides how to update in-memory state |

If a `NacosConfigManager` listener does nothing after receiving a change, business state does not update automatically. Typically perform one of these actions in the callback:

| Common callback action | Description |
| ---------------- | ---- |
| **Update an in-memory cache** | Refresh allowlists, rate-limit rules, route definitions, etc. |
| **Reparse configuration** | Convert the latest JSON/YAML into objects |
| **Trigger application refresh** | Reregister routes, update thread-pool parameters, rebuild rule tables |

#### 5. When to Use It

| Situation | Recommendation |
| ---- | ---- |
| **Ordinary business settings** | Prefer `@ConfigurationProperties` or `@RefreshScope + @Value` |
| **Custom listener logic required** | Use `NacosConfigManager` |
| **Only one configuration value needed** | Usually unnecessary without custom callback handling |
| **Reuse an existing Nacos client** | Prefer `NacosConfigManager` over manually initializing `ConfigService` |

> **Note:** `NacosConfigManager` depends on `spring-cloud-starter-alibaba-nacos-config`. A project with only `nacos-discovery` generally lacks configuration-center capabilities.

### 7.4 Spring Cloud Config (Overview)

Spring's official configuration center uses Git or file storage. Choose it or Nacos Config.

| Aspect | Nacos Config | Spring Cloud Config |
| ------------ | ---------------------------------- | -------------------------------------------------- |
| **Storage** | Database (MySQL / embedded) | Git repository / filesystem |
| **Dynamic refresh** | Native push support; changes take effect within seconds | Requires Spring Cloud Bus or manual `/actuator/refresh` |
| **Visual editing** | Edit directly in the Nacos console | No built-in UI; edit Git content directly |
| **Use cases** | Spring Cloud Alibaba ecosystem (mainstream) | Pure Spring Cloud ecosystem |

```yaml
# Example Config Server configuration
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/xxx/config-repo
          search-paths: config
          default-label: main
```

## VIII. Complete Microservice Request Path

### 8.1 A Request's Full Journey

Combining the preceding concepts, a typical request follows this path:

```text
Client request
  ↓
Gateway (route matching, authentication, rate limiting, logging)
  ↓
LoadBalancer (select an instance by service name)
  ↓
Business service such as user-service
  ↓
OpenFeign / RestClient calls other microservices
  ↓
Nacos registration/discovery supplies instance information; heartbeats maintain instance health during operation
  ↓
Nacos Config supplies dynamic configuration
```

| Stage | Question addressed | Common components |
| ------------------ | ------------------------------------------ | ------------------------------------------ |
| **Unified entry point** | Where client requests arrive first | **Spring Cloud Gateway** |
| **Service discovery** | How to find instances and remove unreachable ones | **Nacos / Eureka** |
| **Service calls** | How services make HTTP/RPC calls | **OpenFeign / RestClient / HTTP Service Clients** |
| **Load balancing** | How to select among multiple instances | **Spring Cloud LoadBalancer** |
| **Configuration management** | How to centralize and dynamically refresh service configuration | **Nacos Config / Spring Cloud Config** |
| **Governance and protection** | Rate limiting, circuit breaking, fallbacks, monitoring | **Sentinel / Resilience4j / monitoring systems** |

### 8.2 Minimum Viable Microservice Stack

A typical Spring Cloud microservice setup usually includes at least these capabilities:

| Capability | Preferred solution | Description |
| ------------ | -------------------------------- | -------------------------------------------------- |
| **Registration/discovery** | **Nacos** | Can also provide configuration; common with Spring Cloud Alibaba |
| **Service calls** | **OpenFeign** | Declarative calls with less code |
| **Load balancing** | **LoadBalancer** | Default in newer versions; replaces Ribbon |
| **Gateway** | **Spring Cloud Gateway** | Unified entry point, routing, authentication, filtering |
| **Configuration center** | **Nacos Config** | Dynamic refresh and environment management |
| **Fault tolerance** | **Sentinel / Resilience4j** | Rate limiting, circuit breaking, fallbacks |

> 💡 The complete stack is **registration/discovery + service calls + load balancing + gateway entry point + configuration center + fault tolerance**, covering the core responsibilities of the main microservice components.
