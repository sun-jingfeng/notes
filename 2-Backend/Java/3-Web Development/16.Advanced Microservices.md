## I. Circuit Breaking and Fallbacks

### 1.1 Cascading Failures

A **cascading failure** occurs when a service in a microservice call chain fails (for example, by timing out or crashing), blocking upstream threads and exhausting resources until the entire chain becomes unavailable.

```text
Service A ──────────▶ Service B ──────────▶ Service C (failed)
    │                     │
    ▼                     ▼
Blocked until timeout  Blocked until timeout
    │                     │
    ▼                     ▼
Resource exhaustion    Resource exhaustion
    │
    ▼
Cascading failure
```

Common high-availability measures:

| Measure | Description |
| -------------- | ---------------------- |
| **Multiple instances** | Avoids a single point of failure |
| **Load balancing** | Distributes load |
| **Circuit breaking/fallbacks** | Fails fast to prevent cascading failures |
| **Rate limiting** | Controls traffic to protect services |
| **Health checks** | Detects unhealthy instances promptly |

### 1.2 Sentinel Overview

**Sentinel** is Alibaba's open-source traffic-management component, centered on **resources**. Assign resource names to protected endpoints or methods, then configure rate-limiting, circuit-breaking and other rules for them. Rule violations throw `BlockException`, handled by `blockHandler`; exceptions from business logic are handled by `fallback`.

| Concept / attribute | Description |
| ---------------- | -------------------------------------------------------------------------------------------- |
| **Resource** | Marks a protected method with `@SentinelResource(value = "resourceName")`; the name is used when configuring rules in the dashboard |
| **blockHandler** | Handles `BlockException` from rate limiting or circuit breaking; accepts the original parameters plus `BlockException` and returns a fallback result |
| **fallback** | Handles business exceptions; accepts the original parameters plus `Throwable` and returns a fallback result |

### 1.4 Resource Definitions and Fallbacks

#### 1. @SentinelResource

`value` defines the resource name. Rate limiting or circuit breaking invokes `blockHandler`; business exceptions invoke `fallback`.

```java
@Service
public class DemoService {

    @SentinelResource(
        value = "queryById",
        blockHandler = "queryByIdBlockHandler",
        fallback = "queryByIdFallback"
    )
    public String queryById(Long id) {
        return remoteService.findById(id);
    }

    // Fallback for rate limiting/circuit breaking (BlockException)
    public String queryByIdBlockHandler(Long id, BlockException ex) {
        return "Service busy; please try again later";
    }

    // Fallback for business exceptions (Throwable)
    public String queryByIdFallback(Long id, Throwable ex) {
        return "Service temporarily unavailable";
    }
}
```

> **Note**: By default, `blockHandler` and `fallback` methods must be in the **same class** as the original method, with the same return type and original parameters followed by `BlockException` / `Throwable`. For another class, specify `blockHandlerClass` / `fallbackClass`; those methods must be **static**.

#### 2. Integrating Feign with Sentinel

For downstream timeouts or failures during remote calls, enable Sentinel support for Feign and specify a **fallbackFactory** on `@FeignClient`. Rate-limited or failed calls use the fallback implementation, which can inspect the exception cause.

```yaml
feign:
  sentinel:
    enabled: true
```

```java
@FeignClient(name = "user-service", fallbackFactory = UserClientFallbackFactory.class)
public interface UserClient {
    @GetMapping("/users/{id}")
    User getUserById(@PathVariable("id") Long id);
}

@Component
public class UserClientFallbackFactory implements FallbackFactory<UserClient> {
    @Override
    public UserClient create(Throwable cause) {
        return new UserClient() {
            @Override
            public User getUserById(Long id) {
                log.error("User service call failed: {}", cause.getMessage());
                User fallback = new User();
                fallback.setName("Unknown user");
                return fallback;
            }
        };
    }
}
```

### 1.5 Core Rules

| Feature | Description |
| ---------------- | -------------------------- |
| **Flow control** | QPS / concurrent-thread limits |
| **Circuit breaking** | Slow-call ratio / exception ratio / exception count |
| **Hotspot parameter limits** | Limits specific parameter values |
| **System protection** | CPU / load / inbound QPS |
| **Authorization rules** | Allowlist/denylist control |

> 💡 Web requests are automatically registered using URL paths as resource names (e.g. `/api/xxx/{id}`). Resources explicitly marked with `@SentinelResource(value = "xxx")` use `value`. An endpoint must receive at least one request before it appears in the dashboard's resource call tree.

#### 1. Flow Control

Dashboard → **Resource Call Tree** → the resource's **Flow Control** button, or **Flow Rules** → Add.

**Basic Fields:**

| Field | Description |
| ------------ | ----------------------------------------------- |
| **Resource name** | Resource to limit |
| **Origin** | Calling microservice name; `default` applies regardless of origin |
| **Threshold type** | **QPS** (requests per second) or **thread count** (concurrent threads) |
| **Per-instance threshold** | Threshold for each instance |
| **Flow-control mode** | Direct / associated / call-chain |
| **Flow-control behavior** | Fail fast / Warm Up / queueing |

**Flow-Control Modes:**

| Mode | Description | Additional field |
| -------- | -------------------------------------------------------- | ---------- |
| **Direct** | Measures the current resource; limits it when its threshold is reached | — |
| **Associated** | Limits the current resource when an associated resource reaches its threshold (e.g. writes trigger limits on reads) | Associated resource name |
| **Call-chain** | Counts only requests entering the current resource through a specified entry | Entry resource name |

> 💡 **Call-chain mode** requires `web-context-unify: false`; otherwise all web entries share one context and cannot be distinguished by chain.

**Flow-Control Behaviors:**

| Behavior | Description | Additional field |
| ------------ | --------------------------------------------------------------------------- | ---------------- |
| **Fail fast** | Immediately throws `FlowException` (default) | — |
| **Warm Up** | Gradually raises the threshold from `per-instance threshold / coldFactor` (coldFactor fixed at 3) to the configured value | Warm-up duration (seconds) |
| **Queueing** | Queues at a steady rate; rejects requests exceeding the wait timeout, smoothing traffic bursts | Timeout (milliseconds) |

**Configuration Examples:**

| Scenario | Resource | Threshold type | Per-instance threshold | Mode | Behavior | Additional field | Effect |
| ---------- | ----------- | -------- | -------- | -------- | -------- | --------------- | -------------------------------------------------------- |
| QPS limiting | `queryById` | QPS | 100 | Direct | Fail fast | — | Rejects requests beyond 100 per second per instance |
| Cold-start warm-up | `queryById` | QPS | 200 | Direct | Warm Up | Warm-up: 10s | Raises the threshold from 200/3 ≈ 66 to 200 over 10 seconds after startup |
| Associated limiting | `queryById` | QPS | 50 | Associated | Fail fast | Associate `saveData` | Limits `queryById` when `saveData` reaches 50 QPS, protecting writes |

#### 2. Circuit-Breaking Strategies

Dashboard → **Resource Call Tree** → the resource's **Circuit Breaking** button, or **Circuit-Breaking Rules** → Add.

**State Transitions:**

```text
CLOSED (normal) ──breaker trips──▶ OPEN (reject calls; use fallback)
   ▲                                │
   │                                │ open duration expires
   │                                ▼
   └───── probe succeeds ────── HALF_OPEN (allow one probe)
                                    │
                                    │ probe fails
                                    └──▶ back to OPEN
```

**Common Fields:**

| Field | Description |
| ---------------- | -------------------------------------------------------- |
| **Resource name** | Resource whose circuit is protected |
| **Strategy** | Slow-call ratio / exception ratio / exception count |
| **Open duration (s)** | Time spent OPEN before entering HALF_OPEN |
| **Minimum requests** | Minimum requests in the observation window before evaluating the breaker, avoiding misleading small samples |
| **Observation window (ms)** | Statistical window; default 1000ms |

**Strategy-Specific Fields:**

| Strategy | Specific fields | Trigger |
| -------------- | -------------------------- | ------------------------------------ |
| **Slow-call ratio** | Maximum RT (ms), ratio threshold (0–1) | Fraction of requests exceeding maximum RT ≥ ratio threshold |
| **Exception ratio** | Ratio threshold (0–1) | Fraction of failed requests ≥ ratio threshold |
| **Exception count** | Exception count | Failed request count ≥ count threshold |

> 💡 RT = Response Time.

**Configuration Examples:**

| Scenario | Strategy | Maximum RT | Ratio/count threshold | Open duration | Minimum requests | Window | Effect |
| ---------- | ---------- | ------- | --------------- | -------- | ---------- | -------- | ----------------------------------------------------- |
| Slow-call ratio | Slow-call ratio | 200ms | 0.5 | 10s | 5 | 1000ms | With at least 5 requests in 1s, opens for 10s if ≥ 50% take >200ms |
| Exception ratio | Exception ratio | — | 0.3 | 5s | 10 | 1000ms | With at least 10 requests in 1s, opens for 5s if ≥ 30% fail |
| Exception count | Exception count | — | 3 | 10s | 5 | 1000ms | With at least 5 requests in 1s, opens for 10s if ≥ 3 fail |

> 💡 All these rules can be configured in the Dashboard. In production, push rules through Nacos for persistence so a dashboard restart does not lose them.

## II. Distributed Transactions

### 2.1 The Distributed Transaction Problem

Each microservice has its own database. When one business operation spans services, local transactions guarantee ACID only within one database and cannot coordinate cross-database commits or rollbacks.

```text
Service A (local write) ──▶ Service B (remote call) ──▶ Service C (remote call)
      │                      │                       │
     DB1                    DB2                     DB3
```

**CAP Theorem:** During a network partition (P), a distributed system must choose between consistency (C) and availability (A):

| Property | Description |
| ----------------------------------- | ---------------------------------------- |
| **C**onsistency | All nodes see the same data at the same time |
| **A**vailability | Every request receives a response, which may not contain the latest data |
| **P**artition tolerance | The system continues operating during network partitions |

Choosing a distributed transaction solution is fundamentally a tradeoff between consistency and availability:

| Consistency model | Description | Seata modes |
| -------------- | ---------------------------------------- | --------------- |
| **Strong consistency** | All nodes agree when the transaction finishes; higher latency | XA |
| **Eventual consistency** | Temporary inconsistency is allowed but eventually resolved; higher availability | AT, TCC, SAGA |

### 2.2 Distributed Transactions with Seata

**Seata**, Alibaba's open-source distributed transaction solution, has three architectural roles:

| Role | Description |
| --------------------------------- | ------------------------------------------------------------------ |
| **TC (Transaction Coordinator)** | Maintains global/branch transaction states and coordinates global commit or rollback |
| **TM (Transaction Manager)** | Defines the global transaction boundary and requests its start, commit or rollback from TC |
| **RM (Resource Manager)** | Manages branch transactions, registers them with TC and reports their status |

```text
┌──────────────────────────────────────────┐
│                    TM                    │
│   (initiating microservice: the method   │
│   annotated with @GlobalTransactional)   │
└────────────┬─────────────────────────────┘
             │ ① Begin global transaction / ④ Request commit or rollback
             ▼
┌────────────┴─────────────────────────────┐
│                    TC                    │
│              (Seata Server)              │
└─────┬────────────────────────┬───────────┘
      │ ② Register branch      │ ② Register branch
      │ ③ Report branch state  │ ③ Report branch state
      ▼                        ▼
┌─────┴──────────┐       ┌─────┴──────────┐
│       RM       │       │       RM       │
│ Microservice A │       │ Microservice B │
│     (DB1)      │       │     (DB2)      │
└────────────────┘       └────────────────┘
```

TC requires **separate deployment** (Seata Server); TM and RM are embedded in each microservice as SDK components.

**`@GlobalTransactional` and xid Propagation:** Annotate only the **TM's (transaction initiator's)** entry method with `@GlobalTransactional`; RMs do not need it. When TM begins a transaction, Seata generates a globally unique **xid**. Feign / RestTemplate client interceptors **automatically add it to request headers** for downstream propagation. Downstream RMs detect xid through Seata's data-source proxy, register branches with TC and report status automatically, without business-code changes.

**TM Code (Initiator):**

```java
@Service
public class BizService {

    @Autowired
    private RemoteServiceB remoteServiceB;

    @Autowired
    private RemoteServiceC remoteServiceC;

    @GlobalTransactional(name = "create-biz", rollbackFor = Exception.class)
    public void createBiz(BizDTO dto) {
        // 1. Local write (RM registers a branch with TC)
        bizMapper.insert(dto);

        // 2. Remote call to service B (RM registers a branch with TC)
        remoteServiceB.bindData(dto.getId(), dto.getParam1());

        // 3. Remote call to service C (RM registers a branch with TC)
        remoteServiceC.bindData(dto.getId(), dto.getParam2());

        // Any failure → TM notifies TC → TC coordinates rollback across RMs
    }
}
```

> 💡 Add `@GlobalTransactional` only to the TM entry method. Other RMs implement ordinary business methods; Seata's data-source proxy automatically handles branch registration and status reporting.

#### 3. Transaction Modes

| Mode | Mechanism | Intrusiveness | Use cases |
| -------- | --------------------------------------------------------------- | ------ | ---------------------------- |
| **AT** | Automatically records snapshots (undo_log) and rolls back on failure; transparent to business logic | None | Most scenarios (recommended) |
| **TCC** | Business code implements Try (reserve), Confirm and Cancel (rollback) | High | High performance and fine-grained resource control |
| **SAGA** | Participants provide forward and compensating operations; failures trigger stepwise compensation | Moderate | Long workflows with many participants |
| **XA** | Database XA two-phase commit; database guarantees strong consistency | None | Traditional scenarios with strict consistency requirements |

#### 4. XA Mode

**XA** is the **Distributed Transaction Processing (DTP)** standard defined by X/Open, supported by major databases including MySQL, Oracle and PostgreSQL. Seata XA uses this standard, relying on the database for native strong consistency.

**Two-Phase Process:**

| Phase | Work |
| ------------------ | ------------------------------------------------------------------------------------------- |
| **Phase 1 (execute)** | Each RM executes business SQL **without committing**, registers its branch with TC and reports status |
| **Phase 2 (commit)** | TC evaluates branch statuses: **all successful** → instruct every RM to **commit**; **any failure** → instruct every RM to **roll back** |

**XA vs AT:**

| Comparison | XA mode | AT mode |
| ------------ | --------------------------------- | --------------------------------- |
| **Consistency** | Strong (consistent when the transaction finishes) | Eventual (asynchronous phase-two compensation) |
| **Phase 1** | Executes SQL **without committing**, retaining database locks | Executes SQL and **commits immediately**, releasing local locks |
| **Lock duration** | From phase 1 through the end of phase 2 | Local locks released immediately; global locks prevent dirty writes |
| **Performance** | Long lock retention can block operations | Shorter lock retention; higher throughput |
| **undo_log** | Not required | Required in every business database |
| **Proxy mode** | `data-source-proxy-mode: XA` | Default; setting may be omitted |
| **Use cases** | Strict consistency with some blocking acceptable | Most applications; prefer AT |

> 💡 XA requires explicit `data-source-proxy-mode: XA` in microservice configuration and **does not require** an undo_log table.

#### 5. AT Mode

AT is Seata's **default and most widely used** mode, requiring no business-code changes. Its data-source proxy intercepts SQL and records before/after snapshots in **undo_log**; failures trigger reverse compensation using those snapshots.

**Two-Phase Process:**

| Phase | Operation |
| ------------------ | ---------------------------------------------------------------------- |
| **Phase 1 (execute)** | Executes business SQL and **commits immediately**, automatically recording before/after snapshots in undo_log |
| **Phase 2 (commit)** | Global success → delete undo_log asynchronously; failure → compensate and roll back using undo_log |

AT commits local transactions in phase 1, unlike XA's prolonged database locks. A **global lock** prevents dirty writes by other global transactions to the same row, allowing shorter local-lock retention and higher throughput.

> 💡 Every participating database needs an **undo_log** table. See [Seata's official documentation](https://seata.apache.org/docs/user/quickstart) for DDL. AT is the default proxy mode, so `data-source-proxy-mode` may be omitted.

#### 6. TCC Mode

TCC requires business code to implement two phases: **Try** reserves resources; a successful global transaction invokes **Confirm**, while failure invokes **Cancel** to release reservations.

| Annotation | Purpose |
| ----------------------------------- | ------------------------------------------------------ |
| **@LocalTCC** | Marks the interface as TCC |
| **@TwoPhaseBusinessAction** | Marks the Try method and specifies `commitMethod` and `rollbackMethod` |
| **@BusinessActionContextParameter** | Adds parameters to the context for Confirm/Cancel |

For resource reservations, Try freezes resources (decreases available quota and increases frozen quota), Confirm deducts frozen quota, and Cancel releases it:

```java
@LocalTCC
public interface ResourceTccService {

    @TwoPhaseBusinessAction(
        name = "deductResource",
        commitMethod = "confirm",
        rollbackMethod = "cancel"
    )
    boolean tryDeduct(
        @BusinessActionContextParameter(paramName = "resourceId") Long resourceId,
        @BusinessActionContextParameter(paramName = "count") Integer count
    );

    boolean confirm(BusinessActionContext context);

    boolean cancel(BusinessActionContext context);
}

@Service
public class ResourceTccServiceImpl implements ResourceTccService {

    @Override
    @Transactional
    public boolean tryDeduct(Long resourceId, Integer count) {
        // Try: reserve resources (available quota -count, frozen quota +count)
        resourceMapper.freeze(resourceId, count);
        return true;
    }

    @Override
    @Transactional
    public boolean confirm(BusinessActionContext context) {
        // Confirm: deduct frozen quota (frozen quota -count)
        Long resourceId = context.getActionContext("resourceId", Long.class);
        Integer count = context.getActionContext("count", Integer.class);
        resourceMapper.deductFrozen(resourceId, count);
        return true;
    }

    @Override
    @Transactional
    public boolean cancel(BusinessActionContext context) {
        // Cancel: release frozen quota (frozen quota -count, available quota +count)
        Long resourceId = context.getActionContext("resourceId", Long.class);
        Integer count = context.getActionContext("count", Integer.class);
        resourceMapper.releaseFrozen(resourceId, count);
        return true;
    }
}
```

TCC implementations must handle three problems:

| Problem | Scenario | Solution |
| ---------- | ------------------------------------------------------------- | ---------------------------------------------- |
| **Empty rollback** | Try never executes (e.g. timeout), but TC still sends Cancel | Cancel checks whether Try ran and returns immediately if not |
| **Idempotency** | Confirm/Cancel may be repeated because of network retries | Record transaction state; return immediately if already handled |
| **Suspension** | Cancel arrives before Try because of network delay, so Try runs afterward | Try checks whether cancellation already occurred and skips execution if so |

## III. Message-Driven Systems

### 3.1 Message Queue (MQ) Basics

Synchronous calls between microservices (OpenFeign) create tight coupling and expose downstream services directly to traffic peaks. Operations that **do not need an immediate result** (such as asynchronous notifications or data synchronization) can use a **message queue (MQ)** for asynchronous decoupling.

| Comparison | Synchronous call (OpenFeign) | Message-driven (MQ) |
| ------------ | ---------------------- | ----------------------------------- |
| **Coupling** | Caller depends directly on the callee | Sender depends only on messaging middleware |
| **Response model** | Blocks waiting for a result | Returns after sending; consumer processes asynchronously |
| **Traffic spikes** | Directly hit downstream services and may overwhelm them | Messages accumulate in Broker; consumers process at their capacity |
| **Failure handling** | Caller must retry or use a circuit breaker | Middleware ensures delivery, with dead-letter queues as a fallback |

**Core MQ Model:**

```text
Producer ──▶ Broker ──▶ Consumer
                        │
                  Topic / Queue
                (messages stored by topic/queue)
```

| Concept | Description |
| ---------------------- | ---------------------------------------------------------------- |
| **Producer** | Sends messages |
| **Consumer** | Receives and processes messages |
| **Broker** | Messaging server that receives, stores and delivers messages |
| **Topic / Queue** | Categorized message channel; producers publish to topics and consumers subscribe |
| **Consumer Group** | Only one instance in a group consumes a given message, avoiding duplicate consumption |

**Mainstream Messaging Systems:**

| System | Throughput | Ordering | Delayed messages | Transactional (half) messages | Characteristics | Use cases |
| ------------ | ------ | -------------- | -------------- | -------- | --------------------------- | ------------------------ |
| **RabbitMQ** | Medium | Ordered within a queue | Plugin required | ❌ | Lightweight, low latency, flexible routing | Small/medium systems with rich routing needs |
| **Kafka** | Extremely high | Ordered within a partition | ❌ (custom implementation) | ❌ (offers producer transactions instead) | High throughput, persistence, stream processing | Big data, logs, stream processing |
| **RocketMQ** | High | Configurable ordered messages | Native support | ✅ | High throughput, feature-rich, widely used in China | E-commerce, finance and other common Chinese deployments |

Using native middleware APIs tightly couples business code to the chosen system, requiring extensive changes when switching. Spring Cloud Stream addresses this with a unified abstraction.

### 3.2 RabbitMQ

**RabbitMQ** is open-source messaging middleware based on **AMQP (Advanced Message Queuing Protocol)**. Known for its lightweight design, low latency and flexible routing, it is widely used in small and medium microservice systems.

#### 1. The AMQP Model

RabbitMQ follows **Producer → Exchange → Queue → Consumer**. Exchanges route messages to one or more queues according to their type and routing rules.

```text
Producer ── RoutingKey ──▶ Exchange ──match──▶ Queue ──▶ Consumer
                              │                 ▲
                              └── Binding ───────┘
                           (BindingKey defines the matching rule)
```

| Concept | Description |
| ---------------------- | ------------------------------------------------------- |
| **Producer** | Sends messages to an exchange |
| **Exchange** | Receives and routes messages to queues according to type and rules; does not store messages |
| **Queue** | Stores messages awaiting consumption |
| **Binding** | Defines an exchange-to-queue routing rule, including a BindingKey |
| **Consumer** | Retrieves and processes messages from a queue |
| **RoutingKey** | Routing key supplied by the producer when sending |
| **BindingKey** | Matching key specified in a binding; compared against RoutingKey by the exchange |
| **Virtual Host** | Resource isolation boundary, similar to a database schema; default `/` |

#### 2. Exchange Types

| Type | RoutingKey matching | Typical use |
| ----------- | ------------------------------------------------------- | ----------------------------------------- |
| **Direct** | Exact match: RoutingKey equals BindingKey | Targeted delivery, such as routing by event type |
| **Fanout** | Ignores RoutingKey; broadcasts to all bound queues | Broadcast notifications, such as system announcements |
| **Topic** | Wildcards: `*` matches one word; `#` matches zero or more words | Pattern-based categories, such as `log.#` for all log events |
| **Headers** | Matches message header attributes without RoutingKey (less common) | Routing by multiple attribute conditions |

**Direct Exchange:**

```text
Producer ── RoutingKey: "error" ──▶ Direct Exchange
                                        │
                           BindingKey: "error" → Queue A → Consumer A
                           BindingKey: "info"  → Queue B → Consumer B
```

Only Queue A receives the message because RoutingKey exactly matches BindingKey.

**Fanout Exchange:**

```text
Producer ──▶ Fanout Exchange
                  │
                  ├──▶ Queue A → Consumer A
                  ├──▶ Queue B → Consumer B
                  └──▶ Queue C → Consumer C
```

Every bound queue receives the message; RoutingKey is ignored.

**Topic Exchange Wildcards:**

| Wildcard | Meaning | Example BindingKey | Matching RoutingKeys |
| ------ | ---------------- | --------------- | ------------------------------------ |
| `*` | Matches exactly one word | `log.*` | `log.info`, `log.error` |
| `#` | Matches zero or more words | `log.#` | `log`, `log.info`, `log.info.detail` |

> 💡 One queue can be **bound multiple times** to the same exchange with different BindingKeys. A message matching any binding is delivered to that queue. For example, an alert queue bound with both `"error"` and `"warning"` receives both severity levels.

> 💡 The default exchange is Direct with the empty name `""`. Every queue is automatically bound to it using its own queue name as BindingKey.

**JSON Serialization:**

The default is Java serialization (`SimpleMessageConverter`); JSON is recommended:

```java
@Configuration
public class RabbitConfig {

    @Bean
    public MessageConverter messageConverter() {
        return new Jackson2JsonMessageConverter();
    }
}
```

A **MessageConverter declared as a `@Bean` acts as the global converter**, shared by `RabbitTemplate` and listener containers. It serializes Java objects when sending and deserializes message bodies when consuming. Whether sending uses it depends on the API:

| Sending API | Input | Uses the global converter? |
| -------- | ---- | ----------------- |
| `convertAndSend(exchange, routingKey, object)` | Business object (POJO) | Yes; converter serializes it into a message body |
| `send(exchange, routingKey, message)` | Prebuilt `Message` | No; sends it unchanged to Broker |

Consumer method arguments are produced by the container's configured converter deserializing the message body. If messages originate elsewhere (another service or raw bytes), use `Message` or `byte[]` parameters and parse them yourself.

| Method | Description |
| ---------------------------- | -------------------------------------------- |
| `convertAndSend(e, rk, msg)` | Sends to the specified exchange with a RoutingKey |
| `convertAndSend(queue, msg)` | Sends to the default exchange with the queue name as RoutingKey |
| `@RabbitListener(queues)` | Listens to specified queues, automatically deserializes messages and invokes the method |

**Work Queue:**

Multiple consumers share a queue to improve processing speed. RabbitMQ defaults to **round-robin delivery**, without accounting for differences in consumer processing capacity.

```text
Producer ──▶ Queue ──▶ Consumer 1
                  ──▶ Consumer 2
```

Set `prefetch` to control how many messages a consumer reserves. Taking the next message only after finishing the previous one lets **faster consumers handle more work**:

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1    # Prefetch one message; take the next after processing it
```

| Setting | Description |
| ------------ | ----------------------------------------------------------------------------- |
| **prefetch** | Maximum unacknowledged messages per consumer; 1 distributes work by processing progress. Default 250 since Spring AMQP 2.0; only 0 means unlimited |

#### 5. Declaring Exchanges, Queues and Bindings

**Approach 1: @Bean Declarations**

```java
@Configuration
public class RabbitConfig {

    // Declare a Direct exchange
    @Bean
    public DirectExchange demoExchange() {
        return ExchangeBuilder.directExchange("demo.exchange").durable(true).build();
    }

    // Declare a durable queue
    @Bean
    public Queue demoQueue() {
        return QueueBuilder.durable("demo.queue").build();
    }

    // Declare the binding (queue ← exchange, routingKey = "demo.created")
    @Bean
    public Binding demoBinding(Queue demoQueue, DirectExchange demoExchange) {
        return BindingBuilder.bind(demoQueue).to(demoExchange).with("demo.created");
    }
}
```

| Builder | Common methods |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| **`ExchangeBuilder`** | `directExchange(name)` / `topicExchange(name)` / `fanoutExchange(name)` → `.durable(true).build()` |
| **`QueueBuilder`** | `durable(name)` (durable queue) / `nonDurable(name)` (non-durable queue) → `.build()` |
| **`BindingBuilder`** | `bind(queue).to(exchange).with(routingKey)` / `.noargs()` (Fanout requires no RoutingKey) |

> 💡 Constructors work too: `new DirectExchange("demo.exchange")`, `new Queue("demo.queue", true)`. Builders make chaining clearer and simplify adding options such as `lazy()` or `deadLetterExchange()`.

***

**Approach 2: @RabbitListener Declarations**

Declare directly in the consumer annotation for conciseness. Declaration is **idempotent**: existing queues/exchanges are reused and bindings ensured; absent ones are created and bound.

```java
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "demo.queue", durable = "true"),           // Declare the queue
    exchange = @Exchange(name = "demo.exchange", type = ExchangeTypes.DIRECT),  // Declare the exchange
    key = "demo.created"                                              // Binding routingKey
))
public void handleMessage(String message) {
    log.info("Message received: {}", message);
}
```

| Approach | Advantages | Disadvantages |
| ------------------------ | ---------------------- | ------------------ |
| **@Bean** | Centralized management, clear structure | More configuration-class code |
| **@RabbitListener annotation** | Declaration alongside consumption; concise | Distributed across consumers |

#### 6. Message Reliability

Messages can be lost at any stage from producer to consumer. Protect each segment:

```text
Producer ──①──▶ Exchange ──②──▶ Queue ──③──▶ Consumer
```

| Segment | Risk | Solution |
| ------------------------- | ------------------------------ | --------------------------------- |
| **① Producer → Exchange** | Send failure or nonexistent exchange | Publisher Confirm (custom retry logic required) |
| **② Exchange → Queue** | Routing failure (no matching queue) | Publisher Return (usually configuration error; alert) |
| **③ Queue → Consumer** | Consumer processing failure | Consumer Ack (auto + local retries + DLQ fallback) |
| **Queue storage** | RabbitMQ crash loses messages | Persistence of exchange + queue + messages |

**Producer Reconnection:**

Network instability can prevent clients from connecting to RabbitMQ. Enable retries after connection failures:

```yaml
spring:
  rabbitmq:
    connection-timeout: 1s           # Connection timeout
    template:
      retry:
        enabled: true                # Enable send retries
        initial-interval: 1000ms     # Initial retry interval
        multiplier: 1                # Retry interval multiplier
        max-attempts: 3              # Maximum attempts
```

> **Note**: Reconnection is **blocking**; the current thread waits during retries, making it unsuitable for high-frequency sending.

***

**Publisher Confirms:**

When enabled, Broker returns ack/nack when the message reaches the exchange:

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated    # Asynchronous confirmation callback (recommended)
    publisher-returns: true               # Enable returns
    template:
      mandatory: true                     # Invoke the return callback on routing failure instead of silently discarding
```

| publisher-confirm-type | Description |
| ------------------------- | ---------------------------------------- |
| **none** | Disabled (default) |
| **simple** | Blocks synchronously for confirmation; lower performance |
| **correlated** | Asynchronous callback, nonblocking; recommended |

**Both modes require custom retry logic after failure**; they differ in how confirmation is received:

| Comparison | simple | correlated (recommended) |
| ------------ | -------------------------------------------- | ------------------------------------------- |
| **Obtaining the result** | Blocks in `waitForConfirms(timeout)` | Receives it asynchronously in `setConfirmCallback` |
| **Performance** | Low (thread suspended while waiting) | High (nonblocking; returns immediately after sending) |
| **Retry point** | After `waitForConfirms()` returns `false` | In the callback's `ack == false` branch |

**simple Mode:**

```java
boolean ack = rabbitTemplate.invoke(operations -> {
    operations.convertAndSend(exchange, routingKey, message);
    return operations.waitForConfirms(1000);  // Block for up to 1s
});
if (!ack) {
    // Custom retry logic (e.g. persist to DB, then resend asynchronously)
    log.error("Message did not reach Exchange; retrying");
}
```

**correlated Mode (Recommended):**

Pass a message identifier in `CorrelationData` so the callback can identify the failed message:

```java
@Configuration
public class RabbitConfig {

    @Bean
    public RabbitTemplate rabbitTemplate(ConnectionFactory connectionFactory) {
        RabbitTemplate template = new RabbitTemplate(connectionFactory);
        template.setMessageConverter(new Jackson2JsonMessageConverter());

        // Confirm callback: whether the message reached the exchange; implement retries for ack=false
        template.setConfirmCallback((correlationData, ack, cause) -> {
            if (!ack) {
                String msgId = correlationData != null ? correlationData.getId() : "unknown";
                log.error("Message did not reach Exchange, id: {}, cause: {}", msgId, cause);
                // Custom retry logic (e.g. retrieve the original message from DB by msgId and resend)
            }
        });

        // Return callback: message reached the exchange but no queue matched (usually an incorrect routingKey)
        template.setReturnsCallback(returned -> {
            log.warn("Message not routed to Queue, exchange: {}, routingKey: {}",
                returned.getExchange(), returned.getRoutingKey());
        });

        return template;
    }
}
```

Pass `CorrelationData` when sending to track the specific message in the callback:

```java
CorrelationData correlationData = new CorrelationData(UUID.randomUUID().toString());
rabbitTemplate.convertAndSend(exchange, routingKey, message, correlationData);
```

***

**Consumer Acknowledgments:**

Consumers acknowledge messages to Broker after processing; unacknowledged messages are redelivered:

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto             # Default: ack on normal return, nack on exception
        retry:
          enabled: true                    # Enable local retries
          max-attempts: 3                  # Maximum attempts, including the first
          initial-interval: 1000           # Initial retry interval (ms)
          multiplier: 2                    # Retry interval multiplier
        default-requeue-rejected: false    # Do not requeue after retries are exhausted (use with DLQ)
```

| acknowledge-mode | Description |
| ------------------- | --------------------------------------------------- |
| **none** | Automatic acknowledgment: delivery counts as success (messages may be lost) |
| **auto** | Normal method return produces ack; exception produces nack (default; **covers most scenarios**) |
| **manual** | Code calls `channel.basicAck()`. Required when consumer work is asynchronous (e.g. starts another thread), because `auto` would ack before that work finishes; acknowledge manually after completion |

**ack / nack / reject and Their Timing:**

| Response | Meaning | Typical trigger |
| ---------- | ---------------------- | ---------------------------------------------------------------------------------------- |
| **ack** | Processing succeeded | Normal consumer return in auto mode, or manual `basicAck` |
| **nack** | Failed; may request requeue | Spring sends nack on an exception; supports requeue selection and batches |
| **reject** | Failed; rejects one message | Like nack but single-message only; RejectAndDontRequeueRecoverer sends reject(requeue=false) |

Both nack and reject tell Broker that processing failed. Broker uses **requeue** to decide: true requeues; false discards or dead-letters if a DLX is configured. For one message with the same requeue setting, their effect is equivalent; nack additionally supports batching.

> 💡 `auto` with local retries covers most scenarios: normal processing automatically acks; exceptions trigger retries; exhaustion produces reject (or nack with requeue=false), with a DLQ as fallback.

***

**Failed-Message Recovery (MessageRecoverer):**

Messages are discarded by default after retries are exhausted. Spring AMQP provides three `MessageRecoverer` implementations:

| Implementation | Response to Broker after failure | Behavior |
| ------------------------------------ | ----------------------------------- | ---------------------------------------------------------- |
| **RejectAndDontRequeueRecoverer** | reject(requeue=false) | Discards the message (default) |
| **ImmediateRequeueMessageRecoverer** | nack(requeue=true) | Requeues the message (may fail again; use cautiously) |
| **RepublishMessageRecoverer** | ack (original acknowledged after forwarding) | Publishes the failed message to an error exchange for manual handling (**recommended**) |

```text
consumer ──retries exhausted──▶ RepublishMessageRecoverer ──▶ error.exchange ──▶ error.queue
                                                                          │
                                                                    Manual diagnosis / compensation
```

```java
@Bean
public MessageRecoverer messageRecoverer(RabbitTemplate rabbitTemplate) {
    return new RepublishMessageRecoverer(rabbitTemplate, "error.exchange", "error");
}
```

> 💡 Declare `error.exchange` and a failed-message queue beforehand. Bind the queue with binding key `"error"`, matching RepublishMessageRecoverer's routing key. Failed messages include exception stack traces for diagnosis and manual compensation.

***

**Persistence:**

RabbitMQ exchanges, queues and messages are stored in memory by default; a restart or crash can lose metadata and messages. **Persistence** writes all three to disk so they can recover after restart. Each layer is necessary:

- Nondurable exchange → disappears on restart; producers cannot send.
- Nondurable queue → disappears on restart; messages have no destination.
- Nonpersistent message → queue survives restart, but its messages are lost.

| Object | Persistence setting |
| ------------ | ---------------------------------------------------------- |
| **Exchange** | Declare `durable = true` (default) |
| **Queue** | Declare `durable = true` (`new Queue(name, true)`) |
| **Message** | `MessageDeliveryMode.PERSISTENT` (Spring AMQP default) |

> 💡 In Spring AMQP, exchanges, queues and messages are durable/persistent by default, usually requiring no extra configuration. Persistence adds some disk I/O overhead but is necessary for business messages requiring reliable delivery.

***

**Lazy Queues:**

RabbitMQ traditionally keeps messages in memory for low latency, risking data loss on crashes and memory pressure during backlogs. **Lazy Queues**, introduced in 3.6.0, write incoming messages directly to disk, retaining only recent messages in memory (default 2048), and support millions of messages. **Since version 3.12, all queues default to lazy behavior.**

| Comparison | Default queue | Lazy queue |
| -------------- | ------------------ | ---------------------------------- |
| **Storage** | Memory first | Direct to disk; only a few recent messages in memory |
| **Capacity** | Memory-limited | Millions of messages |
| **Consumption latency** | Low (direct memory access) | Slightly higher (disk-to-memory loading) |
| **Crash safety** | Nonpersistent messages are lost | Messages already on disk are safer |

Before 3.12, specify `x-queue-mode: lazy` at declaration. Prefer **all beans** (queue, exchange and binding in configuration) or **all annotations** (`@QueueBinding`) to avoid confusion from scattered declarations.

**Bean Approach:**

```java
@Bean
public Queue lazyQueue() {
    return QueueBuilder.durable("xxx.queue")
        .lazy()    // Equivalent to .withArgument("x-queue-mode", "lazy")
        .build();
}
// Declare the corresponding exchange and binding in the same configuration class
```

**Annotation Approach (@QueueBinding Declares Lazy Queue, Exchange and Binding Together):**

```java
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "xxx.queue", durable = "true",
        arguments = @Argument(name = "x-queue-mode", value = "lazy")),
    exchange = @Exchange(name = "xxx.exchange", type = ExchangeTypes.DIRECT),
    key = "xxx.routing.key"
))
public void handleMessage(String message) { /* ... */ }
```

> 💡 With persistence and publisher confirms enabled, RabbitMQ acknowledges the producer **after persistence completes**, aligning persistence with confirmation.

#### 7. Message Time to Live (TTL)

**TTL (Time To Live)** is the expiration time of a message or queue. A message that remains unconsumed beyond its TTL is discarded or forwarded to a dead-letter queue if a DLX is configured.

| Scope | Description |
| ---------- | -------------------------------------------------------------------- |
| **Queue-level** | `x-message-ttl` at queue declaration gives every message the same TTL |
| **Message-level** | The `expiration` property when sending applies only to that message |

If both queue and message TTL apply, use **the smaller value**. Messages without a TTL do not expire.

**Queue-Level TTL:**

```java
@Bean
public Queue ttlQueue() {
    return QueueBuilder.durable("ttl.queue")
        .ttl(60_000)   // Milliseconds; 60 seconds here; equivalent to .withArgument("x-message-ttl", 60_000)
        .build();
}
```

**Message-Level TTL:**

```java
rabbitTemplate.convertAndSend("demo.exchange", "demo.created", payload, message -> {
    message.getMessageProperties().setExpiration("30000");  // String value in milliseconds; 30 seconds
    return message;
});
```

| Comparison | Queue-level TTL | Message-level TTL |
| ---------- | ----------------------- | ------------------------------ |
| **Use case** | Same expiry for all queued messages | Different expiry for messages in one queue |
| **Implementation** | `QueueBuilder.ttl()` / `x-message-ttl` | `MessageProperties.setExpiration()` |
| **After expiry** | Dead-lettered if DLX configured, otherwise discarded | Same |

> **Note**: RabbitMQ does not deliver messages that have already expired in a queue. With per-message TTL, however, removal or dead lettering can wait until the message reaches the head: expired messages behind unexpired ones may still occupy resources and count in queue statistics. This head-of-line delay makes mixed TTLs unsuitable for precise TTL + DLX scheduling; use separate queues for different TTLs or a **delayed-message** solution. There is also a delivery race: a message may expire after being written to the socket but before the consumer receives it. See [RabbitMQ: Time-To-Live and Expiration](https://www.rabbitmq.com/docs/ttl).

#### 8. Dead-Letter Queues (DLQ)

Three situations make a message a **dead letter**:

| Condition | Description |
| ------------ | -------------------------------------------- |
| **Rejected** | Consumer reject/nack with `requeue = false` |
| **TTL expired** | Message or queue TTL elapsed before consumption |
| **Queue full** | Queue reaches `max-length`; oldest messages are discarded |

Configure a **Dead Letter Exchange (DLX)** and **Dead Letter Queue (DLQ)** for a business queue so dead letters are routed automatically:

```java
@Configuration
public class DlqConfig {

    // ========== Dead-letter exchange + queue ==========
    @Bean
    public DirectExchange dlxExchange() {
        return ExchangeBuilder.directExchange("dlx.exchange").durable(true).build();
    }

    @Bean
    public Queue dlqQueue() {
        return QueueBuilder.durable("dlq.queue").build();
    }

    @Bean
    public Binding dlqBinding(Queue dlqQueue, DirectExchange dlxExchange) {
        return BindingBuilder.bind(dlqQueue).to(dlxExchange).with("dlq");
    }

    // ========== Business queue (configured with DLX) ==========
    @Bean
    public Queue bizQueue() {
        return QueueBuilder.durable("biz.queue")
            .deadLetterExchange("dlx.exchange")     // Specify the dead-letter exchange
            .deadLetterRoutingKey("dlq")            // Specify the dead-letter routing key
            .build();
    }
}
```

> 💡 A dedicated consumer can read DLQ messages for alerts, logging or manual redelivery.

#### 9. Business Idempotency

**Idempotency** means that executing a business operation once or repeatedly has the same effect on business state. Network retries, consumer restarts and other events can cause duplicate delivery, so consumers must be idempotent.

**Approach 1: Unique Message ID**

Attach a globally unique ID to each message. After successful processing, record it; skip subsequent messages with the same ID:

```java
@Bean
public MessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    converter.setCreateMessageIds(true);  // Automatically generate a unique ID for each message
    return converter;
}
```

Consumer flow: receive message → check whether its ID was processed → if not, perform business work and record the ID → otherwise discard.

***

**Approach 2: Check Business State (Recommended)**

Use the business object's own state, without separately storing message IDs. For example, before changing a record to "confirmed," verify that it is "pending":

```java
@RabbitListener(queues = "simple.queue")
public void handleMessage(Long dataId) {
    // WHERE id = ? AND status = 'pending' → only pending records are updated
    int rows = bizMapper.updateStatusIfPending(dataId);
    if (rows == 0) {
        log.info("Already processed; skipping: {}", dataId);
    }
}
```

| Approach | Advantages | Disadvantages |
| ---------------- | ------------------ | ------------------------------- |
| **Unique message ID** | General-purpose; works for any business operation | Extra ID storage/lookups add overhead |
| **Business-state check** | No extra storage; good performance | Requires business-specific conditions |

> 💡 In production, combine consumer idempotency with **publisher confirms + consumer acknowledgments + retries + persistence** for end-to-end reliability. Even if MQ notification fails, scheduled status checks can provide a fallback to ensure eventual consistency.

#### 10. Delayed Messages

RabbitMQ does not natively support delayed messages; use the **DelayExchange plugin**. **TTL + DLX** can emulate delays, but differing delays require separate queues or a uniform queue TTL, limiting flexibility. Prefer the plugin.

**Installing the Plugin:**

**Approach 1: Download the .ez Plugin and Copy It into the Container (Existing Image)**

1. Download `rabbitmq_delayed_message_exchange-*.ez` matching your RabbitMQ version from [GitHub Releases](https://github.com/rabbitmq/rabbitmq-delayed-message-exchange/releases), e.g. plugin 3.13.0 for RabbitMQ 3.13.x.
2. Copy the `.ez` file into the container's plugin directory and enable it:


**Declare a Delayed Exchange and Consume Messages:**

**Approach 1: @Bean Declarations**

The delayed exchange type is `x-delayed-message`. Use `CustomExchange` and set `x-delayed-type` to the routing type used when the delay expires (such as `direct` or `topic`):

```java
@Configuration
public class DelayMQConfig {

    @Bean
    public CustomExchange delayExchange() {
        Map<String, Object> args = new HashMap<>();
        args.put("x-delayed-type", "direct");
        return new CustomExchange("delay.exchange", "x-delayed-message", true, false, args);
    }

    @Bean
    public Queue delayQueue() {
        return QueueBuilder.durable("delay.queue").build();
    }

    @Bean
    public Binding delayBinding(Queue delayQueue, CustomExchange delayExchange) {
        return BindingBuilder.bind(delayQueue).to(delayExchange).with("delay").noargs();
    }
}
```

The consumer simply listens with `@RabbitListener(queues = "delay.queue")`.

**Approach 2: @RabbitListener Declarations**

```java
@RabbitListener(bindings = @QueueBinding(
    value = @Queue(name = "delay.queue", durable = "true"),
    exchange = @Exchange(name = "delay.exchange", delayed = "true"),
    key = "delay"
))
public void handleDelayMessage(String message) {
    log.info("Delayed message received: {}", message);
}
```

**Sending Delayed Messages:**

Specify the delay in milliseconds through the `x-delay` header. Use `setDelayLong(Long)` (Spring AMQP 3.1.2+): `setDelay(Integer)` is deprecated, and large delays (such as several days) can overflow an int.

```java
public void sendDelayMessage(String exchange, String routingKey, Object message, long delayMs) {
    rabbitTemplate.convertAndSend(exchange, routingKey, message, msg -> {
        msg.getMessageProperties().setDelayLong(delayMs);
        return msg;
    });
}
```

**Comparing the Approaches:**

- **TTL + DLX (no plugin)**: set queue or message TTL. Expired messages become dead letters and move to a DLX, where a bound business queue consumes them, indirectly implementing a delay. Different delays require a separate queue per TTL or a uniform queue-level TTL, resulting in many queues or limited flexibility.
- **DelayExchange plugin**: delays at exchange level. Messages remain at the exchange until due, then route according to `x-delayed-type`. One queue can receive messages with arbitrary delays; usage is simple and precise.

| Approach | Description |
| ---------------------- | --------------------------------------------------------------------------------- |
| **DelayExchange plugin** | Recommended; exchange-level delay, precise and simple |
| **TTL + DLX** | No plugin; expiry/dead-lettering implements delay, but different delays need different queues and flexibility is limited |

**Delayed-Message Example: Handling Task Timeouts**

Cancel a business operation automatically if it is not confirmed within a deadline. Sending one message with a 30-minute delay is simple, but high concurrency creates long-lived MQ backlogs; most tasks are confirmed quickly, so retained messages waste resources.

**Optimization: staged delay checks.** Use progressively longer delays to check task state. Stop once confirmed; if still pending and not expired, send the next delayed check. If the deadline passes without confirmation, cancel the task and roll back its effects.

```text
Start task → delay 10s → check → pending → delay 10s → check → pending → delay 30s → ...
                            → confirmed → finish
                                                               → expired → cancel task and roll back
```

Example delay stages: `10s, 10s, 10s, 15s, 15s, 30s, 30s, 60s, 60s, 120s, 300s, 600s, 600s` (approximately 30 minutes total).

```java
@Component
public class DelayCheckHandler {

    // Delay stages (milliseconds)
    private static final long[] DELAY_STEPS = {
        10_000, 10_000, 10_000, 15_000, 15_000,
        30_000, 30_000, 60_000, 60_000, 120_000,
        300_000, 600_000, 600_000
    };

    @RabbitListener(bindings = @QueueBinding(
        value = @Queue(name = "delay.check.queue", durable = "true"),
        exchange = @Exchange(name = "delay.exchange", delayed = "true"),
        key = "delay.check"
    ))
    public void handleDelayCheck(DelayCheckMessage msg) {
        BizRecord record = bizMapper.selectById(msg.getBizId());
        if (record == null || record.getStatus() != BizStatus.PENDING) {
            return;  // Record absent, confirmed or cancelled; finish
        }

        int step = msg.getStep();
        if (step >= DELAY_STEPS.length) {
            // Deadline passed without confirmation; cancel and roll back
            bizMapper.cancel(msg.getBizId());
            remoteService.rollback(msg.getBizId());
            return;
        }

        // Send the next delayed check
        msg.setStep(step + 1);
        rabbitTemplate.convertAndSend("delay.exchange", "delay.check", msg, m -> {
            m.getMessageProperties().setDelayLong(DELAY_STEPS[step]);
            return m;
        });
    }
}
```

| Approach | Advantages | Disadvantages |
| -------------- | ----------------------------------- | ---------------------------- |
| **Single long delay** | Simple implementation | Large, long-lived backlogs waste resources |
| **Staged delays** | Ends early on confirmation; less MQ load and better resource use | Slightly more complex |

### 3.3 Spring Cloud Stream

#### 1. Overview

**Spring Cloud Stream** provides a unified messaging programming model, allowing RabbitMQ, Kafka, RocketMQ and others to be swapped without changing business code.

```text
Application code (StreamBridge / Consumer / Function)
    │
    ▼
Binding (input / output)
    │
    ▼
Binder (adapter hiding middleware differences)
    │
    ▼
Messaging middleware (RabbitMQ / Kafka / RocketMQ)
```

| Concept | Description |
| --------------- | -------------------------------------------------------------------- |
| **Binder** | Middleware adapter hiding implementation differences (e.g. RabbitMQ Binder, Kafka Binder) |
| **Binding** | Bridge between application and middleware; input for consumers, output for producers |
| **Destination** | Message destination: RabbitMQ exchange or Kafka topic |

Modern versions (Spring Cloud 2022+) recommend the **functional model**, with three function types:

| Function type | Purpose | Typical use |
| -------------------- | -------------------------------------- | -------------- |
| **`Supplier<T>`** | Produces messages periodically (once per second by default); less common | Scheduled polling/publishing |
| **`Function<T, R>`** | Consumes one message and produces another | Transformation, routing |
| **`Consumer<T>`** | Consumes without a return value | Receiving and processing events |

In practice, **producers most often use `StreamBridge`** for on-demand sending without polling constraints, and **consumers use `Consumer<T>`**. `Function<T, R>` suits message transformation.

> 💡 Legacy `@EnableBinding` + `@StreamListener` are deprecated; use the functional model for new projects.

#### 2. Add the Dependency

Choose the Binder starter for your messaging system:

| Middleware | Dependency |
| ------------ | -------------------------------------- |
| **RabbitMQ** | `spring-cloud-starter-stream-rabbit`   |
| **Kafka**    | `spring-cloud-starter-stream-kafka`    |
| **RocketMQ** | `spring-cloud-starter-stream-rocketmq` |

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-stream-rabbit</artifactId>
</dependency>
```

#### 3. Producer (StreamBridge)

`StreamBridge.send(bindingName, payload)` sends to the specified binding:

```java
@Service
public class BizService {

    @Autowired
    private StreamBridge streamBridge;

    public void createData(Object data) {
        bizMapper.insert(data);
        // Configure the binding name under bindings in YAML
        streamBridge.send("data-created", data);
    }
}
```

#### 4. Consumer

Declare a `Consumer<T>` bean; Spring Cloud Stream automatically connects it to the input binding:

```java
@Configuration
public class EventHandler {

    @Bean
    public Consumer<String> dataCreated() {
        return message -> {
            log.info("Message received: {}", message);
        };
    }
}
```

#### 5. Message Transformation (Function)

`Function<T, R>` consumes one message and produces another, suitable for format conversion or routing:

```java
@Bean
public Function<InputMessage, OutputMessage> transform() {
    return input -> {
        OutputMessage output = new OutputMessage();
        output.setId(input.getId());
        output.setContent("Processed: " + input.getData());
        return output;
    };
}
```

Message flow: `input-topic` → `transform` → `output-topic`. Configure both `-in-0` and `-out-0` bindings.

#### 6. Binding Configuration

```yaml
spring:
  cloud:
    stream:
      bindings:
        # ========== Producer binding ==========
        # StreamBridge.send("data-created", payload) uses this name
        data-created:
          destination: demo-topic            # Actual topic/exchange name
          content-type: application/json
        # ========== Consumer binding ==========
        # Naming convention: <functionName>-in-<index>
        dataCreated-in-0:
          destination: demo-topic            # Matches the producer destination
          group: demo-group                  # Consumer group; only one instance in the group consumes each message
      function:
        definition: dataCreated              # Active function bean names; separate multiple names with semicolons
```

**Binding Naming Convention:**

| Direction | Format | Example (function `dataCreated`) |
| ---------- | ---------------------- | ---------------------------- |
| **input** | `<functionName>-in-<index>` | `dataCreated-in-0` |
| **output** | `<functionName>-out-<index>` | `dataCreated-out-0` |

> 💡 `index` starts at 0 and is always 0 for a single input/output. `StreamBridge` binding names are chosen directly and do not follow this restriction.

| Setting | Description |
| ----------------------- | -------------------------------------------------------- |
| **destination** | Actual topic/exchange name |
| **content-type** | Serialization format; default `application/json` |
| **group** | Consumer group; only one instance consumes each message to avoid duplicates |
| **function.definition** | Active function bean names, separated by semicolons |

> **Note**: Without `group`, every consumer instance receives the message (broadcast mode). **Set a group in production** so only one instance in each group consumes a given message.

#### 7. Consumer Retries and Dead-Letter Queues

**Retry Configuration:**

Spring Cloud Stream defaults to 3 processing attempts, including the initial attempt, on consumer failure. Adjust through `consumer` settings:

```yaml
spring:
  cloud:
    stream:
      bindings:
        dataCreated-in-0:
          destination: demo-topic
          group: demo-group
          consumer:
            concurrency: 5                     # Concurrent consumer threads; default 1
            max-attempts: 3                    # Total attempts, including the first; 1 disables retries
            back-off-initial-interval: 1000    # Initial retry interval (ms)
            back-off-multiplier: 2.0           # Retry interval multiplier
            back-off-max-interval: 10000       # Maximum retry interval (ms)
```

| Setting | Description | Default |
| ----------------------------- | --------------------------------------- | ------ |
| **concurrency** | Concurrent consumer threads | 1 |
| **max-attempts** | Total attempts, including the first; 1 means no retry | 3 |
| **back-off-initial-interval** | Initial retry interval (ms) | 1000 |
| **back-off-multiplier** | Retry interval multiplier | 2.0 |
| **back-off-max-interval** | Maximum retry interval (ms) | 10000 |

***

**Dead-Letter Queue (DLQ):**

Messages are discarded by default after retry exhaustion. Enabling a **DLQ** routes failed messages there for diagnosis and manual compensation.

**RabbitMQ DLQ:**

```yaml
spring:
  cloud:
    stream:
      rabbit:
        bindings:
          dataCreated-in-0:
            consumer:
              auto-bind-dlq: true              # Automatically create and bind the DLQ
              republish-to-dlq: true           # Attach exception stack traces to DLQ headers for diagnosis
```

***

**Kafka DLQ:**

```yaml
spring:
  cloud:
    stream:
      kafka:
        bindings:
          dataCreated-in-0:
            consumer:
              enable-dlq: true                 # Enable the DLQ
              dlq-name: demo-topic.dlq         # DLQ topic name (optional; has a default)
```

> 💡 A dedicated consumer can read DLQ messages for alerts, logging or manual redelivery.

## V. Microservice Best Practices

### 5.1 Service Decomposition Principles

**When to Decompose:**

| Project type | Recommendation |
| ------------------ | ---------------------------------------------- |
| **Startup project** | Start with a monolith for rapid development/experimentation; split as scale grows |
| **Clearly large-scale project** | Start with microservices to avoid later decomposition costs |

**Goal:** high cohesion and low coupling. **High cohesion** means each service has a focused responsibility and closely related business logic. **Low coupling** means relatively independent functions with fewer dependencies on other services.

**Decomposition Approaches and Principles:**

| Dimension | Guideline | Description |
| ---------- | ---------- | ---------------------------- |
| **Approach** | Vertical split | Split by business module, such as users or orders |
| | Horizontal split | Extract common services for reuse |
| **Principles** | Single responsibility | Each service does one thing |
| | Business boundaries | Divide by business domain (DDD) |
| | Data independence | Each service owns its database |
| | Stable interfaces | Services communicate through stable interfaces |
| | Incremental decomposition | Split the monolith gradually |

### 5.2 Project Structure

| Approach | Description |
| ---------------- | ---------------------------------------------------- |
| **Independent projects** | Separate, independent project per service; suits large teams deploying independently |
| **Maven aggregation** | Multiple modules under a parent, with unified dependency versions and one-step builds |

Typical Maven aggregate layout:

```text
project-root/
├── pom.xml                    # Parent project (central dependency versions)
├── xxx-common/                # Shared module (utilities, DTOs, Feign interfaces, etc.)
│   └── pom.xml
├── xxx-gateway/               # Gateway
│   └── pom.xml
├── xxx-service-a/             # Business service A
│   └── pom.xml
└── xxx-service-b/             # Business service B
    └── pom.xml
```

> 💡 Shared modules (`xxx-common`) usually hold shared entities, DTOs, Feign interfaces and utilities, included by business services through Maven dependencies.

### 5.3 Inter-Service Communication Principles

| Scenario | Recommended approach | Selection rationale |
| ------------ | ---------------------------- | ------------------------------------------ |
| **Synchronous calls** | OpenFeign + LoadBalancer | Caller needs the result, such as a query or resource validation |
| **Asynchronous decoupling** | Message queues (RocketMQ / Kafka) | No immediate result needed; throughput and decoupling matter |
| **Event-driven** | Spring Cloud Stream | Services communicate through loosely coupled events; publisher need not know the consumers |

### 5.4 Microservice Authentication and User Propagation

**Overall Approach:** the gateway validates authentication centrally (e.g. JWT), then writes the authenticated user ID into the `X-User-Id` header of the forwarded request. Downstream service interceptors parse that header into `UserContext` (a ThreadLocal holder). Feign's **RequestInterceptor** reads the user ID from `UserContext` and adds it to outgoing headers, preserving user context across service calls.

```text
Client ──JWT──▶ Gateway (validates JWT; writes X-User-Id header)
                  │
                  ▼
              Microservice A (interceptor reads X-User-Id → UserContext)
                  │
              Feign call (RequestInterceptor reads UserContext → writes X-User-Id header)
                  │
                  ▼
              Microservice B (interceptor reads X-User-Id → UserContext)
```

**① Gateway: Add Headers After Validation**

Validate JWT in the gateway's `GlobalFilter`, then add the user ID from the token claims to the forwarded request headers:

```java
// header() sets or replaces the value, so a client-supplied X-User-Id is overwritten
ServerWebExchange newExchange = exchange.mutate()
    .request(builder -> builder.header("X-User-Id", String.valueOf(userId)))
    .build();
return chain.filter(newExchange);
```

> **Note**: downstream services trust `X-User-Id` without checking it. On allowlisted paths that skip JWT validation, strip any incoming value with `builder.headers(headers -> headers.remove("X-User-Id"))`, and keep microservices reachable only through the gateway so the header cannot be forged.

**② Microservice: Read Headers into ThreadLocal**

Define a Spring MVC interceptor in the shared module; including that module enables it in each microservice:

```java
public class UserInfoInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String userId = request.getHeader("X-User-Id");
        if (userId != null) {
            UserContext.setUserId(Long.valueOf(userId));
        }
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        UserContext.clear();  // Clear when the request ends to prevent memory leaks
    }
}
```

```java
// The gateway also depends on the shared module but runs on WebFlux, so load this only where Spring MVC exists.
// Register the class through component scanning or the module's AutoConfiguration.imports file.
@Configuration
@ConditionalOnClass(DispatcherServlet.class)
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new UserInfoInterceptor());
    }
}
```

**③ Propagate the User in OpenFeign Calls**

When Feign calls downstream services, a `RequestInterceptor` copies the current user ID from `UserContext` into request headers:

```java
@Configuration
public class FeignConfig {
    @Bean
    public RequestInterceptor requestInterceptor() {
        return template -> {
            Long userId = UserContext.getUserId();
            if (userId != null) {
                template.header("X-User-Id", userId.toString());
            }
        };
    }
}
```

| Stage | Approach |
| -------------- | ---------------------------------------------------- |
| **Gateway** | GlobalFilter validates JWT and writes the `X-User-Id` header |
| **Within a microservice** | HandlerInterceptor reads `X-User-Id` into `UserContext` |
| **Feign call** | RequestInterceptor reads `UserContext` and writes the outgoing `X-User-Id` header |

### 5.5 Security Practices

Gateways and microservices commonly use **Spring Security's OAuth2 Resource Server** (`spring-boot-starter-oauth2-resource-server`, renamed `spring-boot-starter-security-oauth2-resource-server` in Spring Boot 4, with `spring.security.oauth2.resourceserver.jwt.issuer-uri` or `jwk-set-uri` configured) to validate JWTs: valid tokens are accepted; other requests receive 401.

```java
@Configuration
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/public/**").permitAll()   // Allowlisted endpoints; no authentication required
                .anyRequest().authenticated()                    // All other requests require authentication
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()));  // Parse and validate JWTs
        return http.build();
    }
}
```
