## I. Elasticsearch Overview

### 1.1 What Is Elasticsearch?

**Elasticsearch (ES)** is a distributed, RESTful search and analytics engine based on Apache Lucene. It stores JSON documents and uses inverted indexes for full-text search and aggregations. Common uses include site search, log storage/retrieval, metrics analysis, and APM.

**Key features:**

| Feature | Description |
| -------------- | -------------------------------------------------- |
| **Full-text search** | Tokenization and inverted indexes, with fuzzy matching, highlighting, and suggestions |
| **Near real-time** | Newly written documents become searchable in about 1 second by default (refresh interval) |
| **Distributed** | Shards and replicas support horizontal scaling |
| **REST API** | CRUD and aggregations use HTTP + JSON |
| **Analytics** | Metric aggregations (sum, avg) and bucket aggregations (terms, date_histogram) |

### 1.2 Elasticsearch vs. Relational Databases (Concept Mapping)

| ES concept | Relational database | Description |
| ----------- | ------------ | ---------------------------- |
| **Index** | Database | Collection of related documents |
| **Document** | Row | One JSON data record |
| **Field** | Column | Key-value pair in a document |
| **Mapping** | Table schema | Definitions of field types, analyzers, etc. |
| **Type** | (Removed) | Deprecated in 7.x and removed in 8.x; one structure per index |

### 1.3 Common Use Cases

| Scenario | Description |
| -------------- | ------------------------------------------ |
| **Site search** | Full-text search, filtering, and sorting for products, articles, users, etc. |
| **Log storage** | Log storage/retrieval in ELK, with Kibana |
| **Metrics analysis** | Aggregate time-series/metrics data for dashboards |
| **APM** | Store and query application performance monitoring data |

### 1.4 Introduction to ELK and Lucene

**ELK** combines Elasticsearch, **Kibana** (visualization and Dev Tools), and **Logstash** / **Beats** (data collection). The stack is widely used for log analysis, real-time monitoring, and more.

| Component | Role |
| ----------------- | ------------------------ |
| **Elasticsearch** | Store, search, and aggregate data |
| **Kibana** | Visualization and Dev Tools console |
| **Logstash / Beats** | Collect data and import it into ES |

**Lucene** is Apache's Java search-engine library and the foundation of ES. It provides high-performance inverted indexing and extensibility, but is Java-only and not distributed. ES adds REST APIs, distribution, and horizontal scaling.

## II. Inverted Indexes and Tokenization

### 2.1 Forward and Inverted Indexes

A **forward index** indexes by document ID, making record lookup fast. Searching by term requires scanning documents to check whether they contain it (such as `LIKE '%keyword%'`), which is inefficient.

An **inverted index** tokenizes document content into **terms**, then indexes each term with the IDs of documents containing it. Queries find document IDs by term, then retrieve the documents by ID.

| Concept | Description |
| ---------- | ------------------------------------------ |
| **Document** | Each data record is a document |
| **Term** | Word/token obtained by analyzing document content |
| **Forward index** | Index by document ID; fast by ID, slow by term |
| **Inverted index** | Index terms with document IDs; find IDs by term, then retrieve documents |

Inverted indexes underpin full-text search. **Analyzers** tokenize both indexed document content and user search input.

### 2.2 IK Analyzer

Chinese text needs word segmentation by meaning; the **IK analyzer** is commonly used. Its modes are **ik_smart** (coarse-grained) and **ik_max_word** (fine-grained, maximum segmentation).

Test analysis in Kibana Dev Tools (the sample sentence means "programmers learning Java is great"):

```http
POST /_analyze
{
  "analyzer": "ik_smart",
  "text": "程序员学习 Java 太棒了"
}
```

| Stage | Description |
| -------------- | -------------------------------- |
| **Indexing** | Analyze documents into terms for the inverted index |
| **Searching** | Analyze user input and match the resulting terms against the inverted index |

To extend the dictionary, configure `ext_dict` in `IKAnalyzer.cfg.xml` under the IK plugin's `config` directory, pointing to a dictionary file such as `ext.dic` with one term per line.

## III. Installation and Quick Start

### 3.1 Docker Deployment

```bash
# Shared network so Kibana can reach ES by container name
docker network create es-net

# Single node (development/testing)
docker run -d \
  --name elasticsearch \
  --network es-net \
  -p 9200:9200 -p 9300:9300 \
  -e "discovery.type=single-node" \
  -e "xpack.security.enabled=false" \
  -e "ES_JAVA_OPTS=-Xms512m -Xmx512m" \
  --restart unless-stopped \
  docker.elastic.co/elasticsearch/elasticsearch:8.18.8

# Verify: http://localhost:9200 should return cluster information as JSON
curl http://localhost:9200

# Install the IK analyzer plugin (its version must match the Elasticsearch version), then restart
docker exec elasticsearch bin/elasticsearch-plugin install --batch \
  https://get.infini.cloud/elasticsearch/analysis-ik/8.18.8
docker restart elasticsearch
```

| Port | Description |
| ----- | ------------------------ |
| **9200** | HTTP REST API for applications and Kibana |
| **9300** | Inter-node transport; usually need not be exposed |

> 💡 In production, enable `xpack.security.enabled=true` and configure credentials. Adjust `-Xms` / `-Xmx` to the node's memory capacity. Keep the server's major version aligned with the Java client: Spring Boot 3.5 manages Elasticsearch Java client 8.18.x, while Spring Boot 4 manages 9.x.

### 3.2 Kibana Dev Tools (Recommended)

Kibana's **Dev Tools → Console** lets you write REST requests directly for learning and debugging.

```bash
# Start Kibana on the same network (it must be able to reach ES)
docker run -d --name kibana --network es-net -p 5601:5601 \
  -e ELASTICSEARCH_HOSTS=http://elasticsearch:9200 \
  --restart unless-stopped \
  docker.elastic.co/kibana/kibana:8.18.8
```

Open http://localhost:5601 in a browser and run the examples below in **Dev Tools → Console** on the left.

### 3.3 Your First Index and Documents

```http

PUT /demo_index
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 0
  },
  "mappings": {
    "properties": {
      "docId":   { "type": "keyword" },
      "title":   { "type": "text" },
      "content": { "type": "text" },
      "count":   { "type": "integer" },
      "createAt": { "type": "date" }
    }

}

# Write a document with a specified _id
PUT /demo_index/_doc/1
{
  "docId": "article-1",
  "title": "Getting Started with Elasticsearch",
  "content": "Elasticsearch is a distributed search and analytics engine.",
  "count": 100,
  "createAt": "2024-01-15T10:00:00Z"

# ES generates _id automatically when it is omitted
POST /demo_index/_doc
{
  "docId": "article-2",
  "title": "The Second Article",
  "content": "Full-text search and aggregation are strengths of ES.",
  "count": 200,
  "createAt": "2024-01-16T12:00:00Z"
}

  }

```

## IV. Core Concepts

### 4.1 Index

An **index** is a collection of related documents stored in one or more shards. At creation, specify `settings` (shard count, replicas, refresh_interval, etc.) and `mappings` (field types and analyzers).

- **number_of_shards:** Number of primary shards; cannot be changed in place (use the split/shrink APIs or reindex into a new index).
- **number_of_replicas:** Replicas per primary shard; adjustable dynamically.
- **refresh_interval:** Defaults to 1s; controls how soon writes become searchable.

### 4.2 Documents and Metadata

Each record is a JSON **document**. System fields start with `_`:

| Metadata | Description |
| ---------- | ---------------------------- |
| **_index** | Containing index |
| **_id** | Document ID; can be specified in PUT |
| **_source** | Original JSON body |
| **_score** | Query relevance score (search only) |

### 4.3 Mapping

**Mapping** defines field types and behavior in an index. Common types:

| Type | Description |
| ---------- | -------------------------------------- |
| **text** | Analyzed for full-text search; unsuitable for sorting/aggregation |
| **keyword** | Not analyzed; exact matching, sorting, aggregation |
| **long / integer / short** | Numeric values; support aggregation and sorting |
| **date** | Dates in multiple formats; aggregation and range queries |
| **boolean** | Boolean values |
| **nested** | Nested objects whose child fields can be queried independently |

Common mapping attributes: **type** (field data type); **index** (whether indexed; defaults to true, false prevents searching); **analyzer** (such as ik_smart); **properties** (child fields for object types).

> 💡 ES dynamically infers undeclared field mappings. Define mappings explicitly in production to avoid unexpected types.

### 4.4 Shards and Replicas

- **Shard:** An index is split across nodes for horizontal scaling and parallel search.
- **Replica:** Each primary shard can have zero or more replicas for availability and read throughput.
- The primary shard count cannot be changed in place (only through split/shrink or reindexing); the replica count can change dynamically through `_settings`.

## V. Index and Document Operations

### 5.1 Index Management

```http
# List indexes
GET /_cat/indices?v

# View index mappings
GET /demo_index/_mapping

# View index settings
GET /demo_index/_settings

# Delete an index
DELETE /demo_index
```

Once created, the index and mapping **cannot be modified** in ways such as changing existing field types; **new fields can be added**:

```http
PUT /demo_index/_mapping
{
  "properties": {
    "newField": { "type": "integer" }
  }
}
```

### 5.2 Document CRUD

```http
# Create/fully replace (PUT specifies _id and overwrites an existing document)
PUT /demo_index/_doc/1
{ "docId": "article-1", "title": "Title", "content": "Content", "count": 10 }

# Partial update (only specified fields change; others are retained)
POST /demo_index/_update/1
{
  "doc": { "count": 20 }
}

# Delete by _id
DELETE /demo_index/_doc/1

# Delete by query (use with care)
POST /demo_index/_delete_by_query
{
  "query": { "match": { "title": "To be deleted" } }
}
```

### 5.3 Bulk Writes

Use the **Bulk API** for large batches. A request contains multiple lines of operations (index/update/delete), reducing network round trips.

```http
POST /_bulk
{"index":{"_index":"demo_index","_id":"2"}}
{"docId":"bulk-2","title":"Bulk Document One","content":"Content One","count":1}
{"index":{"_index":"demo_index","_id":"3"}}
{"docId":"bulk-3","title":"Bulk Document Two","content":"Content Two","count":2}
```

> 💡 Every line must be valid JSON; operation and data lines alternate, and the final line must end with a newline.

## VI. DSL Queries

### 6.1 Query Structure

Put the query under `query`, with optional `sort`, `from/size` (pagination), `_source` (returned fields), `highlight`, etc.

```http
GET /demo_index/_search
{
  "query": { ... },
  "sort": [ { "createAt": "desc" } ],
  "from": 0,
  "size": 10,
  "_source": ["title", "content"],
  "highlight": {
    "fields": { "title": {}, "content": {} }
  }
}
```

### 6.2 Common Query Clauses

ES queries are **leaf queries** (specific values in fields, such as match, term, range) or **compound queries** (combine leaf queries or modify scoring, such as bool and function_score). Common clauses:

| Clause | Description |
| ----------- | ---------------------------------------- |
| **match** | Analyze text before matching for full-text search |
| **multi_match** | Like match, but search multiple fields for the same keyword; more fields reduce performance |
| **match_phrase** | Match a phrase with the same word order |
| **term** | Exact match without analysis (keyword, numeric, date, boolean) |
| **terms** | Exact match against multiple values (like IN) |
| **range** | Range conditions (gt, gte, lt, lte) |
| **exists** | Field exists |
| **bool** | Combine must, should, must_not, and filter |

**multi_match** example:

```http
GET /demo_index/_search
{
  "query": {
    "multi_match": {
      "query": "search keywords",
      "fields": ["title", "content"]
    }
  }
}
```

### 6.3 Compound bool Queries

```http
GET /demo_index/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "content": "search engine" } }
      ],
      "filter": [
        { "range": { "count": { "gte": 10, "lte": 1000 } } },
        { "term": { "status": "published" } }
      ],
      "must_not": [
        { "term": { "deleted": true } }
      ]
    }
  }
}
```

- **must:** Must match and contributes to scoring.
- **should:** Matching increases the score. When should clauses exist and there is neither must nor filter, `minimum_should_match` defaults to 1; otherwise it defaults to 0. Set it explicitly if needed.
- **filter:** Must match without contributing to scoring; cache-friendly and suitable for filtering.
- **must_not:** Must not match.

### 6.4 Sorting and Pagination

- **sort:** Sort by fields; for `text`, use its `.keyword` subfield if available.
- **from + size:** Returns the top 10 by default; `from` is the starting offset and `size` the result count. `from + size` is capped at 10,000 by default (`index.max_result_window`).

**Deep pagination:** With a large from value (such as page 99 at 10 records per page, from=990), every shard retrieves and sorts many records before merging, increasing memory use and reducing performance. Alternatives:
- **search_after:** Fetch the next page using the previous result's sort values; no depth limit, but forward-only. Suitable for infinite scrolling and migration.
- **scroll:** Maintains a result snapshot in memory; no longer officially recommended, but useful for one-time exports.

```http
GET /demo_index/_search
{
  "query": { "match_all": {} },
  "sort": [ { "createAt": "desc" }, { "docId": "asc" } ],
  "from": 0,
  "size": 20
}
```

> `_id` cannot be used directly for sorting or aggregation. Here, `docId` is an application-written unique business identifier mapped as `keyword` (with doc_values enabled by default), allowing sorting and aggregation.

### 6.5 Highlighting

```http
GET /demo_index/_search
{
  "query": { "match": { "content": "Elasticsearch" } },
  "highlight": {
    "pre_tags": ["<em>"],
    "post_tags": ["</em>"],
    "fields": {
      "title": {},
      "content": { "fragment_size": 150, "number_of_fragments": 3 }
    }
  }
}
```

The response includes a `highlight` object containing matching fragments wrapped in tags.

## VII. Aggregations

Put aggregations under `aggs`, alongside `query`. Aggregations can nest metrics or sub-buckets inside buckets. The examples assume fields such as `category` and `status` are mapped as `keyword`. The **three elements** are aggregation name, type, and field. A sibling `query` restricts the documents participating in aggregation; without it, all documents participate.

### 7.1 Metric Aggregations

Compute sum, avg, min, max, value_count, cardinality, etc. on a field.

```http
GET /demo_index/_search
{
  "size": 0,
  "aggs": {
    "total_count": { "sum": { "field": "count" } },
    "avg_count":   { "avg": { "field": "count" } },
    "unique_ids":  { "cardinality": { "field": "docId" } }
  }
}
```

### 7.2 Bucket Aggregations

Group by a dimension using **terms** (field values), **date_histogram** (time intervals), or **range** (numeric ranges). Nest **aggs** within buckets for metrics such as sum or stats per group.

```http
GET /demo_index/_search
{
  "size": 0,
  "query": { "term": { "category": "phones" } },
  "aggs": {
    "by_status": {
      "terms": { "field": "status", "size": 10 },
      "aggs": {
        "sum_count": { "sum": { "field": "count" } }
      }
    }
  }
}
```

> 💡 A terms aggregation on a **text** field fails. Use its **keyword** subfield or a separate keyword field in the mapping.

### 8.2 Document Entity and Repository

```java
@Document(indexName = "demo_index")
@Data
public class DemoDoc {
    @Id
    private String id;
    @Field(type = FieldType.Keyword)
    private String docId;
    @Field(type = FieldType.Text)
    private String title;
    @Field(type = FieldType.Text)
    private String content;
    @Field(type = FieldType.Integer)
    private Integer count;
    @Field(type = FieldType.Date)   // Default format: date_optional_time || epoch_millis, matching the index mapping
    private LocalDateTime createAt;
}

public interface DemoRepository extends ElasticsearchRepository<DemoDoc, String> {
    List<DemoDoc> findByTitle(String title);
    Page<DemoDoc> findByContentContaining(String content, Pageable pageable);
}
```

- **ElasticsearchRepository** provides save, findById, delete, paginated queries, etc.
- Method-name parsing supports `findByXxx`, `findByXxxContaining`, etc., translating them into DSL queries.

### 8.3 Building DSL with ElasticsearchOperations

Spring Boot 3 / Spring Data Elasticsearch 5.x (and Spring Boot 4 / Spring Data Elasticsearch 6.x) use **ElasticsearchOperations + NativeQuery** for complex queries. `NativeQuery` accepts query objects from the newer Elasticsearch Java API Client. Older `NativeSearchQueryBuilder` and `ElasticsearchRestTemplate` do not apply to this default client stack.

```java
import co.elastic.clients.elasticsearch._types.SortOrder;
import org.springframework.data.elasticsearch.client.elc.NativeQuery;
import org.springframework.data.elasticsearch.core.ElasticsearchOperations;

@Autowired
private ElasticsearchOperations operations;

public List<DemoDoc> search(String keyword, int from, int size) {
    NativeQuery query = NativeQuery.builder()
        .withQuery(q -> q.match(m -> m.field("content").query(keyword)))
        .withSort(s -> s.field(f -> f.field("createAt").order(SortOrder.Desc)))
        .withPageable(PageRequest.of(from / size, size))
        .build();
    SearchHits<DemoDoc> hits = operations.search(query, DemoDoc.class);
    return hits.stream().map(SearchHit::getContent).collect(Collectors.toList());
}
```

| Component | Description |
| -------------------------- | -------------------------------------- |
| **ElasticsearchRepository** | Entity CRUD and derived method-name queries |
| **ElasticsearchOperations** | Complex queries, aggregations, and bulk operations with NativeQuery |
| **RestClient** | Lowest-level client with manually written JSON requests (replaced by `Rest5Client` in Spring Boot 4) |

### 8.4 Writing and Updating

```java
@Autowired
private DemoRepository demoRepository;

public void save(DemoDoc doc) {
    demoRepository.save(doc);  // Update if an id exists; otherwise insert
}

public void saveAll(List<DemoDoc> list) {
    demoRepository.saveAll(list);  // Bulk write
}
```

> 💡 For large batches, consider **ElasticsearchOperations.bulkIndex** to avoid the bottleneck of saving documents individually.

### 8.5 RestHighLevelClient (7.x, Overview Only)

Since ES 8.x, the official recommendation is the new **Java API Client**; **RestHighLevelClient** is deprecated. For existing 7.x projects still using it, the workflow is: create a Request (such as CreateIndexRequest, IndexRequest, SearchRequest) → prepare mapping/DSL parameters → send through `client.indices().create()`, `client.index()`, `client.search()`, etc. → parse responses (such as GetResponse.getSourceAsString(), SearchResponse.getHits()). Build query conditions with **QueryBuilders** (matchQuery, termQuery, boolQuery, etc.) and pass them to `request.source().query(...)`.

## IX. Operations and Caveats

### 9.1 Cluster Health and Common cat APIs

```http
GET /_cluster/health?pretty
GET /_cat/indices?v
GET /_cat/nodes?v
GET /_cat/shards?v
```

- **green:** All primaries and replicas are assigned. **yellow:** Some replicas are unassigned (common on a single node). **red:** Some primary shards are unassigned and require investigation.

### 9.2 Caveats

| Item | Description |
| ------------ | -------------------------------------------------------- |
| **Shard count** | Set at index creation; changing it requires split/shrink or reindexing, so plan carefully to avoid too many or too few |
| **text vs. keyword** | Use text for full-text search; keyword or .keyword for sorting, aggregation, exact matches |
| **Deep pagination** | Large from+size hurts performance; limit depth or use search_after |
| **Production configuration** | Enable security; configure JVM heap, disk watermarks, and shard allocation |

### 9.3 Relationship to ELK

Elasticsearch commonly combines with **Kibana** (visualization, Dev Tools) and **Logstash / Beats** (data collection) as ELK/Elastic Stack for logs and observability. ES handles storage and retrieval; log indexes can use **Index Lifecycle Management (ILM)** for hot/cold tiering and deletion policies.
