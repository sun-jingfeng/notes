# Git 分支与合并

## 分支操作

### 查看分支

```bash
git branch           # 查看本地分支
git branch -r        # 查看远程分支
git branch -a        # 查看本地和远程分支
git branch -av       # 查看本地和远程分支，并显示最后一次提交信息
git branch -vv       # 查看本地分支关联的远程分支
```

### 创建分支

```bash
git branch <新分支名字>                   # 从当前分支创建新分支
git branch <新分支名字> <旧分支名字>       # 从指定分支创建新分支
```

### 切换分支

```bash
git checkout <分支名字>                   # 切换到指定本地分支
git checkout -b <新分支名字>              # 创建新分支并切换到它
git switch <分支名字>                     # 切换到指定本地分支（Git 2.23+ 推荐）
git switch -c <新分支名字>                # 创建新分支并切换到它（Git 2.23+ 推荐）
```

### 重命名分支

```bash
git branch -m <新名字>                    # 重命名当前分支
git branch -m <旧名字> <新名字>            # 重命名指定分支
```

### 删除分支

```bash
git branch -d <分支名字>                  # 删除本地分支（已合并）
git branch -D <分支名字>                  # 强制删除本地分支（未合并也可删除）
```

## 合并分支

### 命令

```bash
git merge <分支名字>                                      # 将指定分支合并到当前分支，自动提交
git merge --no-commit <分支名字>                          # 将指定分支合并到当前分支，不自动提交
git merge --squash <分支名字>                             # 将指定分支的更改压缩为一个提交应用到当前分支
git merge <分支名字1> <分支名字2> ... <分支名字n>          # 将多个分支合并到当前分支，自动提交
git merge --abort                                        # 当合并遇到冲突时，终止当前合并
```

### 解决冲突

当合并时遇到冲突：

1. 手动编辑冲突文件，解决冲突标记：
   - `<<<<<<<` 当前分支的内容
   - `=======` 分隔线
   - `>>>>>>>` 要合并分支的内容
2. 添加解决后的文件：`git add <文件>`
3. 继续合并：`git commit` 或 `git merge --continue`

### 排查冲突来源

冲突不合常理时（如按 dev → test → uat 顺序合并却大量冲突），先定位是哪次提交引入的：

```bash
git merge-base <分支A> <分支B>                    # 查看两分支的合并基点
git log --oneline <分支A>..<分支B>                # 查看 B 有而 A 没有的提交
git merge-base --is-ancestor <哈希值> <分支>       # 判断某提交是否已在分支中（退出码 0 表示是）
git show --name-only --format="" <哈希值>          # 列出某次提交改动了哪些文件
git diff --name-only --diff-filter=U              # 列出当前处于冲突（未合并）状态的文件
git diff --name-status <分支A> <分支B>            # 对比两分支的文件差异清单
```

**判断技巧**：把「冲突文件清单」与「可疑提交改动的文件清单」做对比，若高度重合，即可确认冲突源于该提交。

### revert 导致的合并冲突

**成因**：某功能在分支 A 上被 `revert` 撤销，而该功能同时存在于分支 B 并被继续开发。此时合并基点里有该功能，A 侧删除、B 侧修改，必然产生冲突。冲突块常表现为**一侧为空**，并非真正的内容分歧。

**陷阱**：只有「双方都改过」的文件才会报冲突。**仅被 revert 改过、目标分支未再触碰的文件会静默采用 revert 的结果**，无任何冲突提示，导致功能被悄悄撤销、留下引用缺失的半成品代码。

因此 `git merge -X theirs <分支>` 并不可靠 —— 它只处理**冲突块**，上述静默文件仍保留 revert 后的内容，合并会「成功」但代码是坏的。

排查静默受影响的文件：

```bash
git show --name-only --format="" <revert哈希值> | sort -u > /tmp/a.txt   # revert 改动的文件
git diff --name-only <合并基点> <目标分支> | sort -u > /tmp/b.txt        # 目标分支改动的文件
comm -23 /tmp/a.txt /tmp/b.txt                                          # 只在 a 中 = 会被静默撤销
```

### 让合并结果与目标分支完全一致

当「当前分支应当整体采用目标分支的内容」时（如 revert 污染后重新对齐），无需删除分支重建，也无需 force push：

```bash
git merge --no-commit --no-ff <目标分支>          # 允许出现冲突，此处不解决
git read-tree -u --reset <目标分支>               # 丢弃冲突状态，索引与工作区重置为目标分支的内容
git commit --no-edit -m "Merge branch '<目标分支>' into <当前分支>"
```

原理：`read-tree -u --reset` 执行时 `MERGE_HEAD` 仍然存在，因此提交后仍是**含两个父提交的正常合并**，历史完整、目标分支被正确标记为已合并。

验证结果：

```bash
git diff --stat HEAD <目标分支>                   # 输出为空 = 两者内容完全一致
git merge-base --is-ancestor <目标分支> HEAD      # 退出码 0 = 目标分支已完整合入
```

**相比删除分支重建的优点**：不触碰远程分支保护规则，且 revert 提交作为历史被保留，可追溯。

### 演练合并（不影响当前工作区）

合并方案没把握时，先用 worktree 在独立目录试跑，工作区与在途合并均不受影响：

```bash
git worktree add -q --detach <临时目录> <分支>     # 基于指定分支检出到临时目录
# 在临时目录内试跑合并并检查结果
git worktree remove --force <临时目录>            # 删除临时工作区
git worktree list                                # 查看所有工作区
```

## 变基

### 命令

```bash
git rebase <分支名字>       # 将当前分支变基到指定分支
git rebase -i HEAD~<n>      # 交互式变基，基于前 n 次提交
git rebase -i <哈希值>       # 交互式变基，基于指定哈希值的提交
git rebase --continue       # 解决冲突后继续变基
git rebase --abort          # 放弃变基，恢复到变基前的状态
```

### 交互式变基用法

**修改历史提交信息：**
1. 将要修改提交信息的每个提交的 `pick` 更改为 `r`（reword），保存退出
2. 逐个修改提交信息，保存退出

**将多个历史提交合并为一个：**
1. 将要合并的每个提交的 `pick` 更改为 `s`（squash），保存退出
2. 修改提交信息，保存退出

### 说明

- 变基会重写提交历史，**不要对已推送到远程的提交进行变基**
- 当前分支的变基操作不会影响其他分支

## Cherry-pick

选择性地将某些提交应用到当前分支。

### 命令

```bash
git cherry-pick <commit>                     # 将指定的某个提交应用到当前分支
git cherry-pick <commit1> <commit2>          # 依次应用多个指定的提交
git cherry-pick <commit1>..<commit2>         # 应用从 commit1（不含）到 commit2（含）的提交
git cherry-pick <commit1>^..<commit2>        # 应用从 commit1（含）到 commit2（含）的提交
git cherry-pick -n <commit>                  # 不自动提交，而是把修改内容放入暂存区
git cherry-pick --skip                       # 冲突时跳过当前 cherry-pick 的提交
git cherry-pick --continue                   # 解决冲突后继续 cherry-pick 过程
git cherry-pick --abort                      # 放弃 cherry-pick 操作，恢复到操作前的状态
```

## 误删分支恢复

```bash
git reflog                           # 查看操作记录，找到删除前的 commit
git checkout -b <分支名> <哈希值>     # 从该 commit 创建新分支
```
