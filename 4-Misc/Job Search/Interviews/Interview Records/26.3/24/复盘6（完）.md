**我的答案要点**

- 有 4 年外包开发经验。
- 前端主要使用 Vue、React，后端主要使用 Java。
- 具备前后端全栈协作能力，也做过 AI 提效和智能体落地。
- 做过项目负责人和 6 人技术小组组长。

**评价**
- 优点：基本把学历、年限、技术栈、带团队和 AI 经验都交代到了，信息覆盖面较全。
- 不足：回答偏“简历罗列”，没有先把自己最有辨识度的标签打出来，比如“前端出身，近一年在做全栈交付和 AI 落地”；另外“对前后端的理解”没有真正展开。

**参考答案要点**

**话术示例**

### 3. 父子项目架构与旧项目复用方案【7 分】

**问题**：你提到这是一个父子项目结构，具体怎么做的？为什么这么设计？

**我的答案要点**
- 需求要求旧项目能够复用，所以最终形成了 1 个父项目加 5 个子项目的结构。
- 技术上采用 iframe 嵌入方案，而不是微前端。
- 实现了统一登录、父子通信、风格切换、子项目独立部署和独立登录。

**评价**
- 优点：回答里已经带出了“为什么要这么做”和“方案落地后解决了哪些问题”，说明你不是只记住了架构名词，而是知道它对应的项目约束。
- 不足：虽然说了为什么不用微前端，但还缺一层更明确的对比，比如“为什么这个场景下 iframe 比 qiankun 之类方案更合适”。

**参考答案要点**
- 先说业务约束：必须复用旧系统，还要保证新功能快速接入。
- 再说方案权衡：iframe 的通信、登录透传、样式隔离和改造成本更适合当前项目节奏。
- 最后补一句边界：这不是通用最优方案，而是当前业务和交付周期下的最优解。

**话术示例**
这个项目的关键约束是必须复用两个旧系统，同时还要补三块新功能。如果强行做标准微前端，改造成本和接入周期都会更长，而我们又是同源部署，所以最后我选了父项目加 iframe 子项目的方案。这样做的好处是旧系统改造最少，样式天然隔离，父子之间通过约定好的通信机制做统一登录、风格切换和状态同步，交付速度更符合项目要求。

### 4. 跨 iframe 边界截图怎么实现【7 分】

**问题**：跨 iframe 边界的截图当时是怎么实现的？

**我的答案要点**
- 这类方案不是系统级截图，无法天然跨越 iframe 原生边界。
- 子项目点击截图按钮后，通过 `postMessage` 把事件通知给父项目。
- 如果截图区域跨越父子边界，就分别获取父项目和子项目对应区域的内容，转换成 Canvas 后再做拼接。

**评价**
- 优点：问题根因说对了，知道这是 `html2canvas` 的能力边界，不是简单调参能解决的；方案也体现了你能从浏览器机制层面定位问题。
- 不足：表达顺序还有点乱，最好按“根因、前提、实现、风险”来讲，会更像完整工程方案。

**参考答案要点**
- 根因：DOM 转 Canvas 方案无法直接跨 iframe 渲染。
- 前提：父子页面同源，否则无法安全读取内容。
- 做法：父项目统一发起截图，子项目配合返回边界或局部内容，最后在父项目完成 Canvas 拼接。
- 风险点：滚动偏移、像素比、异步渲染时机、跨域限制都要处理。

**话术示例**
这个问题的本质是，像 `html2canvas` 这种方案并不是真正去截系统屏幕，而是把当前 DOM 重绘成 Canvas，所以它天然过不了 iframe 边界。我的处理方式是把截图能力收敛到父项目，由子项目通过 `postMessage` 触发截图请求。如果发现截图区域跨到了父子边界，就分别在父项目和子项目里取对应区域的内容，最后在父项目里把两块 Canvas 拼起来。这个方案能成立的前提是父子同源，否则很多内容拿不到。

### 5. Vue、React 与 Vite 的使用情况【5 分】

**问题**：根据转写，题意大致是：你之前主要用 Vue，后来也用 React，那 Vite 一般是在什么情况下使用？

**我的答案要点**
- 之前项目里 Vue 用得比较多。
- 后来因为部门合并，技术栈调整，也开始使用 React。
- 无论之前 Vue 项目还是后来的 React 项目，自己基本都用 Vite。

**评价**
- 优点：传达出了技术栈迁移过程，也说明自己对 Vite 比较熟。
- 不足：没有真正回答“为什么用 Vite、适合什么场景”，这会让面试官感觉答偏了。

**参考答案要点**
- Vite 适合现代前端项目，优势是开发环境启动快、热更新快、配置相对轻量。
- Vue 和 React 都能配合 Vite 使用，它更像构建工具，不是框架本身。
- 如果项目强依赖旧 webpack 生态或复杂遗留构建链，才可能继续沿用旧方案。

**话术示例**
我之前确实 Vue 用得更多，后来团队技术栈逐步增加了 React，但在构建工具上我基本都优先用 Vite。原因很直接，它在开发阶段启动和热更新都更快，项目初始化和维护成本也比较低。对我来说，Vite 不是某个框架专属的选择，而是现代前端项目里比较顺手的一套构建方案。

### 7. ES6 有哪些常见新特性【5 分】【错】

**问题**：你有关注过 ES6 的一些新特性吗？可以简单介绍一下吗？

**我的答案要点**
- 说到了箭头函数、解构、对象属性简写。
- 说到了 Promise，以及后来的 `async/await`。
- 提到了箭头函数和普通函数在 `this` 指向上的区别。

**错误点**：把 `async/await` 当成 ES6 特性说了。

**评价**
- 优点：至少覆盖了语法和异步两个大类，属于能答上的状态。
- 不足：回答不够成体系，而且把 `async/await` 直接算成 ES6 严格来说不严谨；另外漏掉了 `let/const`、模板字符串、模块化、类、展开运算符等高频点。

**参考答案要点**
- 可以按四类讲：变量声明、函数与对象语法、模块与类、异步能力。
- 高频特性包括 `let/const`、模板字符串、解构赋值、默认参数、剩余参数、箭头函数、类、模块化、Promise。
- 如果时间有限，至少要覆盖 `let/const` 和 Promise，这两类几乎必提。

**话术示例**
ES6 我一般会从几类去记。第一类是语法层面的增强，比如 `let/const`、模板字符串、解构赋值、展开运算符和默认参数；第二类是函数和对象的写法优化，比如箭头函数、对象属性简写、类；第三类是模块化能力，比如 `import/export`；第四类是异步能力，最核心的是 Promise。它们共同的作用就是让 JavaScript 在可读性、模块化和异步表达上比以前成熟很多。

### 8. ES6 新增的数据类型 BigInt 和 Symbol【6 分】

**问题**：ES6 新增了一些变量类型，这块你了解吗？

**我的答案要点**
- 回答到了 `BigInt` 和 `Symbol`。
- 说明 `BigInt` 用于超出 `number` 安全边界的大整数。
- 说明 `Symbol` 具有唯一性，不同实例默认不相等。

**评价**
- 优点：核心概念没有答反，至少知道 `BigInt` 和 `Symbol` 是什么。
- 不足：说法不够完整。严格讲 JavaScript 的原始类型后来还包括 `BigInt`，而 `Symbol` 的常见用途没有展开，比如作为唯一属性键、避免命名冲突。

**参考答案要点**
- `BigInt` 解决的是超出 `Number.MAX_SAFE_INTEGER` 后整数精度丢失的问题。
- `Symbol` 的重点不是“地址不同”，而是它代表唯一标识，常用于对象私有化语义和避免 key 冲突。
- 回答时可以带一个简单应用场景，会更像真正理解过。

**话术示例**
这块我会重点记两个类型。一个是 `BigInt`，它是为了解决大整数超出普通 `number` 安全范围后的精度问题；另一个是 `Symbol`，它表示一个唯一值，常见用法是给对象定义不会轻易冲突的属性键。面试里如果展开讲，我一般会顺手补一句应用场景，这样不会只停留在概念背诵。

### 9. 大屏图形很多时怎么做性能优化【7 分】

**问题**：如果做数据大屏，图表和图形特别多，性能要求又高，你会怎么优化？

**我的答案要点**
- 提到了浏览器缓存，以及对较大的 PNG 数据做缓存。
- 提到了响应式层面用 `shallowRef`、`shallowReactive` 之类浅层声明优化。
- 举了一个前端算法耗时 2 秒导致页面卡死，后来用 Web Worker 解决的案例。

**评价**
- 优点：你不是只会说“做缓存、做优化”，而是能举出真实卡顿案例和具体解决手段，这点很有说服力。
- 不足：内容有点散，缺少“渲染层、数据层、线程层、排查层”这种结构化表达；另外如果是大屏图表，还可以补采样、降频、虚拟化和图表实例复用。

**参考答案要点**
- 渲染层：减少不必要重绘，复用图表实例，控制动画和高频更新。
- 数据层：做分片加载、采样、节流防抖，避免每次全量重算。
- 线程层：重计算任务放到 Web Worker，避免阻塞主线程。
- 排查层：用浏览器 Performance、Memory、FPS 面板定位长任务和重绘热点。

**话术示例**
如果是大屏场景，我一般会从四层去看性能。第一层是渲染层，尽量减少重复渲染、控制高频刷新、能复用的图表实例就不要反复销毁重建；第二层是数据层，大数据量要做采样、分片和节流，避免每次都全量计算；第三层是线程层，像复杂算法或大数据处理可以放到 Web Worker；第四层是排查层，用 Performance 和 FPS 面板先定位瓶颈。我之前就遇到过一次前端算法执行两秒把页面卡死，后来把计算迁到 Worker 后效果就明显好了。

### 12. 如何约束 AI 避免重复造轮子【8 分】

**问题**：如果让 AI 帮你写页面，它很容易重复造轮子、手写一堆已经有的代码，这块怎么约束？

**我的答案要点**
- 会用全局提示词和项目级规则文件做约束。
- 会把基本信息、代码规范、组件封装约束等持久化到规则中。
- 会把 AI 常犯错误记录下来，后续继续补充。
- 任务拆解会更细，不会一句“按设计图实现”就直接丢给 AI。
- 会明确告诉 AI 页面拆分、组件边界、主调方式和传参方式。

### 21. 10 万条数据渲染卡死怎么解决【6 分】

### 23. Redis 雪崩、击穿、穿透怎么理解【2 分】【错】

**问题**：你之前用过 Redis，那雪崩、击穿、穿透这三个概念你怎么理解？

**我的答案要点**
- 先介绍了 Redis 在项目里用于缓存复杂计算后的网格数据。
- 对“雪崩”的回答偏到了微服务链路雪崩和压力测试上。
- 没有把缓存雪崩、缓存击穿、缓存穿透三个概念明确区分开。

**错误点**：把雪崩、击穿、穿透答偏到微服务链路了。

**评价**
- 优点：至少能讲出 Redis 的一个真实使用场景。
- 不足：这题答偏了，而且是后端高频基础题，必须补齐。缓存雪崩、击穿、穿透的定义、区别和应对策略都要能稳定说出来。

**参考答案要点**
- **缓存雪崩**：大量缓存同一时间失效，请求全部打到数据库。解决思路是过期时间加随机值、多级缓存、限流降级。
- **缓存击穿**：某个热点 key 失效瞬间，大量并发同时打到数据库。解决思路是热点数据不过期、互斥锁、单飞机制。
- **缓存穿透**：查询的数据本身不存在，请求绕过缓存持续打数据库。解决思路是缓存空值、布隆过滤器、参数校验。
- 最后要说明三者的区别：雪崩是“很多 key 同时失效”，击穿是“一个热点 key 被打穿”，穿透是“查不存在的数据”。

**话术示例**
这三个概念我会这样区分。缓存雪崩是大量 key 在同一时间集中失效，流量一下子打到数据库；缓存击穿是某一个热点 key 失效后，被高并发瞬间打穿；缓存穿透是用户查的就是不存在的数据，缓存里没有、数据库里也没有，请求会一直穿过去。对应的处理方式也不一样，雪崩要避免集中过期并做好限流降级，击穿要保护热点 key，比如加互斥锁或让热点数据不过期，穿透则要缓存空值或者用布隆过滤器拦住无效请求。

| **面对不会的问题相对诚实** | 像 React Native 没有经验、小程序经验较旧，都没有硬编。 |
| **能主动反问岗位方向** | 最后有去确认岗位是前端全栈、App、小程序以及 Python AI 开发方向，说明你会判断岗位匹配度。 |

## 四、待改进与盲区

### 4.1 技术回答

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **自我介绍** | 信息全，但定位不够突出。 | 固化一句个人标签，例如“前端出身，能做全栈交付，也在做 AI 落地”。 |
| **项目业务介绍** | 讲了行业背景，但项目价值收口弱。 | 补“解决什么问题、给谁用、带来什么价值”。 |
| **iframe 截图** | 方案是对的，但表达较乱。 | 固定成“根因 → 前提 → 实现步骤 → 风险点”四段式。 |
| **Vite 使用场景** | 答偏成技术栈迁移过程。 | 准备“为什么用 Vite、适合什么项目”的标准答案。 |
| **复杂页面经验** | 只说拆组件，没有体现复杂度控制能力。 | 准备一个具体页面案例，讲状态流、配置化和性能处理。 |
| **ES6** | 答得散，且有概念不够严谨的地方。 | 补齐 `let/const`、模块化、类、Promise 等主干特性。 |
| **大数据表格** | 没有抓住虚拟化这个核心。 | 重点准备虚拟滚动、分块渲染、占位高度、服务端分页。 |
| **Redis 三兄弟** | 答偏到微服务雪崩。 | 必须单独背熟“定义、区别、解决方案”。 |

### 4.2 表达与结构

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **结论前置不足** | 很多回答都是先铺细节，后给结论。 | 先用一句话回答核心结论，再展开细节。 |
| **结构化表达偏弱** | 内容是有的，但不够分层。 | 常用模板固定成“背景 → 方案 → 原因 → 结果”或“问题 → 根因 → 方案 → 效果”。 |
| **容易顺着转写噪声讲** | 工具名、术语名在口语里容易被带偏。 | 面试时主动说标准名称，比如 Vite、Cursor、MCP、Redis。 |
| **对考点判断还不够准** | 像大表格那题，面试官重点是性能而不是产品形态。 | 听到场景题先判断面试官在考什么，再组织回答。 |

### 4.3 AI 协作相关

| 问题 | 不足 | 可补内容 |

## 六、小结

这场一面的优势在于，你的项目经历有明显复杂度，尤其是父子项目集成、跨 iframe 截图、大屏性能和 AI 协作方法，这些都比普通前端经历更有辨识度。短板主要在两类题上，一类是基础知识回答不够成体系，比如 ES6 和 Redis；另一类是场景题容易没有第一时间抓住考点。接下来只要把“结构化表达”和“后端高频基础”补一轮，你在前端全栈和 AI 应用类岗位上的稳定性会明显提升。
