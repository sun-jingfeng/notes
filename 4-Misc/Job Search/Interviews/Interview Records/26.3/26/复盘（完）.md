### 2. Vue3 浅层响应式 API 的区别与适用场景【7.5 分】

**问题**：请讲一下普通响应式和浅层响应式的区别，以及 `shallowRef` / `shallowReactive` 的使用场景。

**我的答案要点**
- 说明普通响应式会对深层属性继续做代理。
- 说明浅层响应式只关注第一层引用变化，不关心内部深层属性变化。
- 提到地图实例、第三方对象、接口返回的大对象等适合用浅层响应式。
- 强调浅层响应式的价值主要是减少不必要侦听，提升性能。

**评价**
- 优点：核心概念答对了，也能结合地图实例、第三方库对象这类真实场景来解释，不是纯背定义。
- 不足：表达里术语有些混乱，比如 `shallowRef` 和 `shallowReactive` 的边界没有讲得很利落；另外可以补一句“内部属性变化想触发更新时，需要整体替换引用”。

**参考答案要点**
- 普通响应式会递归代理深层对象；浅层响应式只追踪第一层。
- `shallowRef` 适合包裹大型对象、第三方实例、DOM 或地图对象。
- `shallowReactive` 适合只需要顶层属性变化触发更新的对象结构。
- 如果深层属性变化也要更新，要么整体替换引用，要么不要用浅层响应式。

**话术示例**
普通响应式会继续往对象深层做代理，而浅层响应式只关心第一层引用有没有变。像地图实例、第三方图层对象、接口返回的大对象，这些我很多时候并不关心它内部每个字段的变化，只想知道它有没有被创建出来或者整体有没有替换，这种场景就适合用 `shallowRef` 或 `shallowReactive`。这样能减少不必要的侦听，性能会更稳一些。

### 3. Vue2 和 Vue3 响应式原理、数组响应式差异【8 分】

**问题**：请讲一下 Vue2 和 Vue3 的响应式原理差异，以及数组响应式相关的典型区别。

**我的答案要点**
- 提到 Vue2 基于 `Object.defineProperty`。
- 提到 Vue3 基于 `Proxy`，并强调懒代理特性。
- 说明 Vue2 深层大对象初始化成本更高。
- 提到 Vue2 数组索引修改有经典坑，需要用特定方式处理。
- 说明 Vue3 可以直接通过索引变更触发响应。

**评价**
- 优点：这一题整体答得比较扎实，原理、性能差异和数组场景都覆盖到了。
- 不足：如果再严谨一点，可以补充 Vue2 对新增属性和删除属性的限制，以及 Vue3 `Proxy` 在拦截能力上更完整这一层。

**参考答案要点**
- Vue2 用 `Object.defineProperty`，需要在初始化阶段做属性劫持，对新增属性和数组某些操作支持不完整。
- Vue3 用 `Proxy`，对对象整体做代理，支持更多拦截能力，深层对象按访问再代理。
- Vue2 的典型坑包括数组按索引改值和对象后加属性不响应。
- Vue3 在对象和数组变更侦测上都更自然，性能与可维护性更好。

**话术示例**
Vue2 和 Vue3 响应式的核心差异在于底层实现。Vue2 用的是 `Object.defineProperty`，它要在初始化阶段把属性都劫持一遍，所以深层大对象开销会比较大，而且像数组索引修改、新增属性这类场景都有一些历史坑。Vue3 改成了 `Proxy`，它是对整个对象做代理，深层属性通常也是访问到了再继续代理，所以能力更完整，数组和对象的变更也更自然。

### 4. 组合式函数的定位与截图组件封装【7 分】

**问题**：组合式函数是什么？你是怎么用它封装截图能力的？

**我的答案要点**
- 说明组合式函数用于抽离不带模板的逻辑。
- 提到截图能力是通过事件触发、动态挂载渲染层来实现。
- 说明截图弹层需要挂到 HTML 根节点较上层位置。
- 表达了组合式函数里也能使用框架生命周期能力。

**评价**
- 优点：回答带了真实项目案例，说明你确实把组合式函数用在复杂交互逻辑里，而不只是简单封装请求。
- 不足：对“为什么是组合式函数而不是组件”的解释还可以更标准，最好明确成“无模板复用逻辑”和“有模板 UI 载体”的拆分边界。

**参考答案要点**
- 组合式函数的核心价值是复用状态和逻辑，不直接承担模板展示。

**话术示例**
我理解组合式函数本质上是复用一段不带模板的状态和逻辑。像截图这个能力，核心不是页面结构，而是弹层挂载、事件触发、区域控制和结果返回，所以我把它写成组合式函数会更顺手。如果某块东西本身带稳定的 UI 结构，我就会拆成组件；如果主要是在管理逻辑和状态，我更倾向于用组合式函数。

**我的答案要点**
- 提到可以借助闭包或模块级作用域来保存共享状态。
- 说明在组合式函数外声明响应式变量，多个调用方可以共用。
- 能解释 ES 模块只初始化一次这一点。

**评价**
- 优点：整体思路是对的，已经触达“模块级单例状态”和“闭包持久化”的核心。
- 不足：表达有点绕，容易把“闭包”“模块缓存”“单例状态”混成一个概念；最好直接讲清是“模块级共享状态 + 导出统一接口”。

### 7. Vue 组合式函数和 React Hooks 的异同与限制【6 分】

**问题**：组合式函数和 React Hooks 有什么异同？为什么 React Hooks 只能写在顶层？

**我的答案要点**
- 认为两者都用于抽离不带模板的复用逻辑。
- 说明 React Hooks 受调用顺序和数量稳定性的约束。
- 能解释 Hooks 不能放在条件分支和普通嵌套函数里。
- 提到 Vue 组合式 API 相对更灵活。

**评价**
- 优点：核心限制讲到了，尤其是“顺序不能变”这一点抓得比较准。
- 不足：前半段把两者说得过于等同了。它们目标相似，但依赖的运行机制、状态绑定方式和约束强度并不一样，回答时最好先说“定位相似，机制不同”。

**参考答案要点**
- 两者都服务于逻辑复用，但 Vue 组合式 API 和 React Hooks 的运行模型不同。
- React Hooks 强依赖组件渲染顺序，因此必须顶层、稳定调用。
- Vue 的组合式 API 本身更像独立响应式工具，使用限制相对少。
- 回答时先说相同点，再说“状态挂载机制不同导致约束不同”。

**话术示例**
我会把它们理解成“定位相似，但机制不同”。相似点是都在解决逻辑复用问题，但 React Hooks 的状态挂载强依赖组件渲染顺序，所以它必须写在顶层，不能放在条件分支里，不然下一次渲染时状态索引就会乱。Vue 组合式 API 会更灵活一些，因为它的响应式能力本身更独立，不完全绑定在那套 Hooks 规则上。

### 8. 长任务定位、Web Worker 与分片执行【7.5 分】

**问题**：什么是长任务？项目中遇到长任务卡顿时，你怎么定位和优化？

**我的答案要点**
- 说明浏览器主线程里一段耗时很长的 JS 会阻塞页面交互。
- 提到用浏览器 Performance 面板和火焰图定位长任务。
- 举了插值算法计算矩阵数据导致页面卡住的真实案例。
- 说明优化方案可以是 Web Worker 或分片执行。
- 最终项目里用了 Web Worker 把纯计算移出主线程。

**评价**
- 优点：这是本场回答里比较强的一题，有真实案例、有定位手段，也有方案权衡。
- 不足：如果再补一句“长任务通常超过 50ms 会被浏览器标记”为长任务，回答会更标准；另外分片执行的原理可以再说得清晰一点。

**参考答案要点**
- 长任务指主线程上持续占用较长时间、阻塞渲染和交互的任务。

**话术示例**
长任务本质上就是主线程上一段执行时间过长的任务，它会直接阻塞渲染和交互。我一般会先用 Performance 面板录制，先确认是不是长任务，再看火焰图定位具体函数。我之前遇到过一个插值计算把页面卡住的场景，最后是把纯计算逻辑挪到 Web Worker 里，主线程只负责收参数和接结果。如果任务没法完全移出去，那就再考虑时间切片或分片执行。

### 9. 浏览器渲染时机与 requestAnimationFrame【5.5 分】

**问题**：浏览器渲染大概发生在什么时候？在密集计算场景里，怎么通过分片执行把主线程让出来？

**我的答案要点**
- 能意识到渲染和 JS 执行会竞争主线程。
- 提到要控制单次任务时长，避免阻塞一帧。
- 提到了用 `requestAnimationFrame` 做分片调度的思路。
- 也提到了可以结合 `performance` 时间戳做切片控制。

**评价**
- 优点：方向是对的，知道核心目标是“不要让单段任务长时间霸占主线程”。
- 不足：这一题理论表达不够稳，渲染时机和事件循环细节回答得比较模糊；可以把重点收口到“任务切片 + 每帧让出控制权”上，不要硬讲不确定的底层细节。

**参考答案要点**
- 浏览器会在事件循环中择机进行布局、绘制和合成，核心是渲染要拿到主线程时间片。
- 如果 JS 一直长时间执行，浏览器就无法及时完成一帧渲染。
- 优化时可把大任务拆成多个小片段，每片执行后通过 `requestAnimationFrame`、`setTimeout` 或调度器把控制权交回浏览器。
- 重点不在死记时机术语，而在说明“如何保证主线程周期性空出来”。

**话术示例**
这题我会抓住一个核心点就够了，就是渲染也要抢主线程时间，所以如果一段 JS 一直跑，浏览器就没机会顺利完成下一帧。真正优化时，我会把密集任务拆成很多小片段，每执行一小段就主动把控制权让出来，比如通过 `requestAnimationFrame` 再进入下一段。这样即使总任务量没变，页面也不会一直卡死在那一段同步执行里。

### 11. iframe 通信与 postMessage 风险【5 分】【错】

**问题**：跨 iframe 通信一般怎么做？`postMessage` 有什么风险？

**我的答案要点**
- 说明技术选型时会先看父子项目是否同源。
- 提到静态共享信息会放在父窗口可访问的地方。
- 动态事件通过 `postMessage` 传递。
- 知道 `postMessage` 需要配置目标域，避免安全风险。

**错误点**：把 `postMessage` 本身说成了只能同源使用，边界说窄了。

**评价**
- 优点：整体工程思路是对的，知道同源会影响直接访问窗口对象和共享静态上下文，也知道 `postMessage` 有 `targetOrigin` 安全配置。
- 不足：一个关键点不够准确，`postMessage` 本身就是为跨窗口甚至跨源通信设计的，不应把它和“直接读写父子窗口对象”混为一谈。

**参考答案要点**
- 同源限制的是直接访问父子窗口中的 DOM、变量和对象。
- `postMessage` 可以用于跨源通信，但必须严格校验 `targetOrigin` 和消息来源。
- 若同源，可结合共享存储、直接调用、窗口属性访问等方式；若跨源，通常只能走 `postMessage` 这类安全通道。
- 回答时要把“直接访问能力”和“消息通道能力”分开讲。

**话术示例**
这类通信我会先区分两件事。第一件事是父子窗口能不能直接访问彼此的对象和上下文，这个是受同源策略限制的；第二件事是能不能发消息，这个 `postMessage` 本身就是支持跨窗口甚至跨源通信的。工程里如果同源，我会多用共享上下文和直接访问；如果不同源，就老老实实走 `postMessage`，并且把 `targetOrigin` 和来源校验配严。

### 12. Immer 原理与深层状态修改【4.5 分】

**问题**：如果状态要求不可变，但又要修改深层属性，通常怎么处理？了不了解 Immer 的原理？

**我的答案要点**
- 知道不用 Immer 时，深层不可变更新会比较麻烦。
- 提到 Immer 让写法更接近直接修改。
- 记得 Immer 内部和 `Proxy` 有关系。
- 但对具体更新机制和术语解释不够完整。

**评价**
- 优点：至少抓到了 Immer 的使用价值和大致方向，没有完全答偏。
- 不足：这题明显准备不足，对 Immer 的“草稿对象、代理、最终生成新对象”这条主线说得不够清楚，容易让人感觉只停留在用过层面。

**参考答案要点**
- 不可变更新的难点是深层对象修改时代码冗长。
- Immer 通过代理生成草稿对象，允许开发者用“看起来像可变”的方式写更新逻辑。
- 最终会根据修改痕迹生成新的不可变结果，而不是直接改原对象。
- 回答时最好再补一句它常用于 React 状态更新场景。

**话术示例**
如果状态要求不可变，深层属性更新手写起来会很啰嗦，所以很多场景会用 Immer。它的核心思路是先给你一个代理过的草稿对象，你写代码时看起来像是在直接改它，但最终它会根据这些修改生成一份新的不可变对象，而不是直接改原数据。这样既能保持不可变约束，又能把深层更新代码写得更自然。
