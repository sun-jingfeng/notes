### 3. 从 0 到 1 的技术选型、架构搭建和多省复用怎么做【7 分】

**问题**：你更详细说一下这个从 0 到 1 项目的技术选型、架构搭建，以及后面不同省份复用是怎么做的。

**我的答案要点**
- 作为 6 人小组技术组长，项目开始时会先组人、分任务、做技术选型。
- 前端因为有旧系统复用、同源部署、时间紧、内部系统对体验容忍度较高，选择了嵌入式整合方案，复用两个旧系统并新开发三个子系统页面。
- 后续扩到不同省份时，前端通过主分支和省份分支的方式做共性与差异化管理。
- 后端把共性能力沉淀成公共微服务，每个省份保留独立微服务承接差异化需求。
- 共性服务负责登录、权限、气象数据查询等，差异能力单独实现，避免相互影响。

**评价**
- 优点：回答抓住了“为什么这么选”和“怎么支持复用”两个关键点，能体现技术组长视角。
- 不足：前端方案的名字和边界讲得不够准确，分支复用也容易被继续追问，例如如何避免长期分支漂移、如何管理公共能力回流；后端服务划分也可以讲得更结构化。

**参考答案要点**
- 先从约束条件出发解释选型，而不是直接报方案名。
- 前端重点说清：旧系统整合方式、统一登录、统一权限、公共导航、通信机制。
- 多省复用除了分支，还要补一层“配置化 + 公共模块 + 差异模块”的思路，避免让面试官觉得只是靠分支硬分叉。
- 后端重点说共性服务、差异服务、接口边界和部署隔离。

**话术示例**
这个项目当时的核心约束有三个，一个是必须复用已有系统，一个是周期很紧，一个是内部业务系统对极致交互体验要求没那么高，所以我在前端方案上更看重接入成本和交付效率。我的做法是把主站统一起来，把登录、权限、导航这些公共能力收口，再把旧系统和新页面接进去。到后面扩省份的时候，我的思路不是简单复制一套，而是把共性能力尽量收在公共层，差异能力再按省份拆开，前端侧靠公共主线加差异分支，后端侧靠共性微服务加省份独立服务，保证复用和隔离都能兼顾。

### 5. 你是什么时候开始使用 AI 的，现在用到什么程度【8 分】

**问题**：你从什么时候开始使用 AI，现在用到什么程度，对行业进展有持续关注吗？

**我的答案要点**
- 从去年年初开始系统使用 AI。
- 现在大约一半代码会借助 AI 完成，主要是重复性、输入输出明确、机械性的代码。
- 前端会让 AI 处理样板代码、简单组件、明确函数；自己负责基础框架、项目配置、组件拆分。
- 后端也类似，自己先把骨架、分层、关键配置定好，再让 AI 补全同类代码。
- 持续关注模型和工具变化，也会主动学习新概念并尝试落地。

**评价**
- 优点：有明确的人机分工，不是泛泛地说“AI 提效”；能体现你不是完全依赖 AI，而是在驾驭它。
- 不足：表达上有些重复，可以提炼成一句方法论，例如“人定边界，人做架构，AI 做重复实现，人做验收”。

**参考答案要点**
- 先给原则：AI 负责高重复、低歧义、容易验证的工作。
- 再分别举前端和后端的落地场景。
- 最后补风险控制：代码审查、边界检查、风格一致性检查。

**话术示例**
我是从去年年初开始比较系统地使用 AI 的，到现在已经是日常开发的一部分了。我的用法比较明确，AI 主要承担高重复、低歧义、容易验证的工作，比如样板代码、同类接口、基础组件这类内容；架构设计、关键链路、项目配置和最后验收还是我自己来把控。这样做的好处是效率能提上去，但项目可控性不会丢。

### 9. 你平时怎么约束 AI，规范流程是什么【7.5 分】

**问题**：你平时是怎么约束 AI 的？有没有固定的开发规则或规范流程？

**我的答案要点**
- 主要依赖全局级、项目级、任务级三层规则。
- 会把一些通用约束放在全局规则里。
- 会把项目特定规范和任务限定放在更细颗粒度的规则里。

**评价**
- 优点：回答方向是对的，说明你已经有规则分层意识。
- 不足：这一题说得太短，没有举例。面试官其实在确认你是否有可复用的方法论，应该至少给出一两个实际规则样例。

**参考答案要点**
- 规则分层：全局规则、项目规则、任务规则。
- 每层举例：全局是输出风格和技术背景，项目是架构和命名规范，任务是这次要改哪些文件、哪些不能动。
- 最后补充验收方式：AI 产出后仍然要人工 review。

**话术示例**
我对 AI 的约束一般会分三层。第一层是全局规则，比如技术背景、输出风格、一些长期稳定的偏好；第二层是项目级规则，比如当前项目的目录结构、命名规范、组件写法、接口分层；第三层是任务级规则，比如这次只允许改哪些模块、哪些公共能力不能碰、输出要达到什么验收标准。这样做的目的就是把边界先收紧，避免 AI 产出看起来很快，但最后不容易落到项目里。

### 10. 遇到上下文过长和 AI 幻觉怎么处理【6 分】【错】

**问题**：平时会遇到上下文很多、AI 回答不稳定或者出现幻觉吗？你怎么处理？

**我的答案要点**
- 承认会遇到上下文超量和回答不稳定的问题。
- 你的做法是尽量把问题提得更具体，把范围限定到少量组件或明确模块。
- 强调 AI 生成代码必须人工审查，开发者要对项目有强把控。
- 当时还提到“现在模型上下文都不大”，随后被面试官指出近期上下文压缩和扩容能力已有进展。

**错误点**：对当前大模型上下文能力的判断偏旧，表述成了普遍事实。

**评价**
- 优点：你抓住了真正核心的问题，即人要先收束范围、控制输入、审核输出，这个方向本身没问题。
- 不足：对行业最新进展的判断有一点滞后，被面试官现场纠正；这种题不能把阶段性认知说成绝对结论，应该给自己留出弹性表述空间。

**参考答案要点**
- 先说现象：复杂任务、多轮对话、上下文漂移时，稳定性确实会下降。
- 再说处理方式：任务拆分、上下文裁剪、补充结构化摘要、局部验证、人工 review。
- 最后补一句：模型上下文能力在变强，但并不等于可以无脑堆上下文，输入质量和任务边界仍然重要。

**话术示例**
这个问题我确实遇到过，尤其是在任务跨度比较大、多轮对话比较长的时候，AI 的稳定性会下降。我现在的处理方式不是一味堆上下文，而是先把任务拆小，把目标模块、输入输出、限制条件说清楚，必要时自己先整理一版摘要，再让它在一个更窄的范围里工作。模型的上下文能力这段时间确实在变强，但我的理解是，输入越结构化、边界越清楚，结果还是会更稳定，所以人工收束上下文这件事还是不能省。

**评价**
- 优点：没有硬说自己会 C 端监控。
- 不足：先说“B 端和 C 端差距不大”有点冒进，容易让对方觉得你对 C 端关键链路理解不够。更稳妥的方式是承认交集和差异并存，再强调可迁移能力。

**参考答案要点**
- 先承认主战场是 B 端。
- 再说明共通点：组件化、权限、状态管理、性能、可维护性。
- 再说明差异点：C 端更关注埋点、监控、转化、性能和用户体验指标。
- 最后补一句：虽然实战较少，但迁移学习成本可控。

**话术示例**
我过去的主战场确实是 B 端，这一点我会先说清楚。B 端和 C 端在组件化、工程化、状态管理这些底层能力上是相通的，但 C 端会更看重埋点、监控、性能指标、转化链路这些内容，这部分我的实战相对少一些。我的想法是，不会把自己包装成已经做过很多 C 端监控的人，但如果岗位需要，我能比较快把这块补上。

### 12. 你能接受工作强度吗，当前状态和基础工程化能力怎么样【7 分】

**问题**：这里是大小周、日均工时 9.5，你能接受吗？你现在是离职还是在职，在北京吗？工程化组件提炼这类能力以前有吗？

**我的答案要点**
- 明确表示可以接受大小周和较高工时。
- 当前是离职状态，在北京，居住位置可灵活调整。
- 组件提炼和工程化能力有基础，认为组件化开发是常规能力。

**评价**
- 优点：态度明确，沟通效率高，状态信息回答干净利落。
- 不足：关于工程化能力这部分只说“是基础能力”，略空。可以顺手举一个组件提炼、公共能力抽象或规范沉淀的例子，可信度会更强。

**参考答案要点**
- 状态信息保持简洁直接。
- 工程化能力不要只抽象表态，至少补一个实际场景，例如公共表单组件、表格组件、通用 hooks、权限包装组件等。
- 如果岗位很看重高强度，可以补一句自己在高压节奏下如何保证质量。

**话术示例**
工作强度这块我可以接受，我之前的项目节奏也比较快。现在我是离职状态，也在北京，地点上可以配合公司安排。工程化这块我不只是停留在“组件化开发”这个口号上，过去在项目里也做过公共能力抽取，比如把重复页面里的通用逻辑、公共组件或者统一权限能力收出来，所以如果团队需要我在业务推进之外兼顾一部分工程化建设，我是能接得住的。

### 13. 你对公司业务和岗位怎么看，是否愿意承担双业务线备份【7 分】

**问题**：介绍完公司业务后，你怎么看这个岗位？岗位可能会涉及两条业务线备份，你是否能适应？

**我的答案要点**
- 主动了解了对方业务，包括短剧、AI 漫剧、国内业务、后台前端岗位等。
- 表示自己前端和全栈都可以做。
- 对 AI 相关业务方向有兴趣，也愿意适应双业务线协作模式。

**评价**
- 优点：态度积极，能顺着对方业务去接话，表达了适配意愿。
- 不足：后半段你试图从后端节点和模型路由角度展开业务理解，但当时信息不充分，容易说得发散。更稳妥的做法是围绕“我能承担什么价值”来回应。

**参考答案要点**
- 回应岗位时聚焦适配点：B 端后台、AI 业务、快迭代、跨栈协同。
- 双业务线备份重点说学习速度、切换能力、优先级管理。
- 不要在信息不足时过度猜对方技术方案。

**话术示例**
我听下来，这个岗位对我有两个比较匹配的点。一个是它本身是 B 端后台加 AI 业务方向，这和我过去的经验连接度比较高；另一个是它需要一定的跨栈理解和快节奏交付能力，这也是我比较擅长的。双业务线备份这件事我可以接受，我过去在项目里也做过跨模块和跨角色协同，切换任务对我不是问题，关键是先把主线优先级和边界管理好。

### 14. 你的职业规划和最突出的亮点是什么【8 分】

**问题**：你能说一下自己的职业规划吗？你觉得自己最突出的亮点是什么？

**我的答案要点**
- 你认为自己最大的亮点是主动成长。
- 因为 AI 时代来了，认为只会单点能力不够，所以主动补全 Java 和全栈能力。
- 对新技术持开放态度，会主动学习并快速落地。
- 职业规划上仍以前端为核心主方向，同时把自己拓展成全栈型人才。

**评价**
- 优点：价值观表达比较完整，主动学习、适应变化、愿意跨栈成长，这些都和当前岗位比较契合。
- 不足：这题讲了很多理念，但缺少更落地的结果支撑。可以补一两句具体成果，例如过去一年做成了哪些跨栈交付、带来了什么实际变化。

**参考答案要点**
- 亮点不要只说“爱学习”，要说“主动学习并已经形成结果”。
- 职业规划要稳定：以前端为主线，逐步扩展全栈和 AI 工程协作能力。
- 最好把成长方向和岗位价值连接起来。

**话术示例**
我觉得我最突出的地方，不是简单地说自己爱学习，而是我会主动把学习转成结果。比如团队要求组长前后端都要能带的时候，我没有排斥，而是花了一整年去补 Java 和全链路交付能力；AI 工具出来之后，我也不是停留在体验层，而是尽快把它变成日常开发效率的一部分。我的长期规划还是以前端为主线，因为这是我的核心竞争力，但我会继续把自己往全栈和 AI 工程协作方向拓，提升自己在复杂业务里的承担范围。

## 四、待改进与盲区

### 4.1 技术回答

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **CI/CD 与工程工作流** | 只说没做过，显得工程化经验偏弱 | 准备一版标准回答，覆盖 lint、test、build、deploy、rollback、质量门禁等关键词 |
| **多省复用方案** | 前端复用几乎都落在“分支管理”上，容易被质疑长期维护成本 | 补充“公共模块、配置化、差异模块、主干回流策略”这套说法 |

| **C 端差异理解** | 先说 B 端 C 端差距不大，容易踩雷 | 准备一版 B 端与 C 端差异对比，重点补埋点、监控、转化、性能指标 |
| **英语能力表达** | 结论有，但缺少证据和维度 | 用“读文档、写沟通、基础口语”三维表达法替代一句带过 |

### 4.2 表达与结构

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **项目表述顺序** | 经常前端、后端、AI 混讲，层次不够清晰 | 统一用“业务目标 -> 技术约束 -> 方案 -> 自己负责 -> 结果”结构回答 |
| **方法论外显不足** | 你脑子里其实有方法，但说出来时容易只给结论不给框架 | 针对 AI 使用、架构选型、流程规范，每题准备一句总原则和三点展开 |
| **信息不足时容易延展** | 对对方业务技术方案会尝试继续猜，容易发散 | 信息不充分时先回到“我能承担什么价值”，少猜对方内部实现 |
| **优势证据不够结果化** | “主动成长”说得对，但缺少成果闭环 | 给每个优势配一个结果，例如“补 Java 后承担了哪些后端交付” |

## 六、小结

这一面整体不是技术深挖型，而是偏项目承担范围、工程视角、AI 使用方式和成长性判断。你的优势是项目经历真实、AI 使用有实际落地、技术广度和全栈补位能力比较符合对方预期。短板主要集中在大型项目工作流、工程化体系表达、以及少数题上的口径不够稳。只要把项目表达再收束一些，并补齐 CI/CD、复用治理和 C 端差异这几类标准题，后续同类岗位的通过率会明显更高。
