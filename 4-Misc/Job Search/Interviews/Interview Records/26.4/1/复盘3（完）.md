### 1. 自我介绍与 AI 相关项目介绍【6.5 分】

**问题**：请做自我介绍，并重点介绍一个你做过的、有挑战且贴合 AI 场景的项目。

**我的答案要点**
- 记录过简，待补充。
- 从后续追问可推断，你介绍了一个本地部署模型接入的对话系统项目。
- 你提到了使用 FastAPI 和 LangChain 搭建后端能力，并与前端联动完成对话系统。

**评价**
- 优点：项目方向和岗位要求基本匹配，能快速把话题带到 AI 对话系统和 Agent 实践上。
- 不足：从后续大量追问来看，项目介绍更像“我做了什么”，但没有把“为什么这样设计、解决了什么问题、最终效果如何”讲透。面试官因此需要不断往架构、幻觉治理、上下文管理等细节里深挖。

**参考答案要点**
- 先用一句话说明个人定位，比如“前端出身，近一年重点做 AI 应用接入和工程化落地”。
- 项目介绍按“业务场景 -> 我的职责 -> 技术架构 -> 关键难点 -> 结果”五段展开。
- AI 项目一定要主动补齐模型来源、接入方式、Prompt 设计、上下文管理、风控或评估指标。
- 结尾补一句与目标岗位的匹配点，明确自己不是只会调用接口，而是能做 Agent 工程落地。

**话术示例**
我这边是前端出身，但近一年在项目里承担了比较多 AI 应用落地和全栈开发相关的工作。比较有代表性的项目，是一个接入本地部署模型的对话系统，我负责从前端交互到后端智能体服务的落地，后端这边用 FastAPI 加 LangChain 去做对话编排和能力封装，前端负责对话交互和流式展示。这个项目里我重点做的不是简单调接口，而是把模型接入、Prompt 设计、上下文管理和业务集成真正串起来，所以它和 AI Agent 工程师这个岗位比较贴合。

### 2. 本地模型接入方式与前后端架构设计【6 分】

**问题**：你们本地部署的模型是什么？你在项目里是调用方还是模型侧负责人？FastAPI 和 LangChain 的整体架构，以及和前端的配合方式是怎么设计的？

**我的答案要点**
- 记录过简，待补充。
- 从提问可推断，你说明了自己主要是调用本地部署模型接口的一方，不负责底层模型训练或部署。
- 提到了后端使用 FastAPI 和 LangChain 搭建对话系统。
- 可能介绍了前端对接聊天接口、展示对话内容的实现方式。

**评价**
- 优点：至少把自己的职责边界说清了一部分，没有把“模型能力提供方”和“应用接入方”混为一谈。
- 不足：这题的关键是把系统拆清楚，但从面试官继续追问来看，你没有把“模型服务层、Agent 编排层、业务接口层、前端展示层”讲成一条完整链路。缺少分层、数据流和异常处理说明，容易让回答停留在“用了什么框架”。

**参考答案要点**
- 明确区分四层：模型推理服务、Agent 编排服务、业务系统接口层、前端交互层。
- 说明自己负责的是哪几层，以及通过什么接口把能力串起来。
- LangChain 不要只说“用了它”，要说明用到了哪些模块，比如 Prompt Template、Memory、Retriever、Tool、Chain 或 AgentExecutor。
- 前端部分要补齐请求方式、流式协议、状态管理和错误兜底。

**话术示例**
这个项目里，底层模型本身不是我负责训练和部署的，我主要负责模型能力在业务里的应用接入。我的架构会拆成四层。最底下是本地模型推理服务，对外提供统一推理接口；上面一层是我用 FastAPI 搭的 AI 服务层，负责鉴权、会话管理、日志和业务封装；LangChain 主要用于 Prompt 编排、上下文组织和工具调用；再往上是前端交互层，负责对话输入、流式输出展示和状态管理。这样拆分的好处是模型、应用逻辑和前端体验都能独立演进。

### 3. 如何降低大模型幻觉【5.5 分】

**问题**：你在设计这个 Agent 时，是怎么降低大模型幻觉率的？

**我的答案要点**
- 记录过简，待补充。
- 从面试节奏看，你的回答没有形成完整的方法论，因此面试官很快转向上下文管理继续追问。

**评价**
- 优点：你至少知道“幻觉治理”是 Agent 落地的关键问题，没有完全回避这个方向。
- 不足：缺少体系化回答。面试官想听的不是泛泛而谈的“优化提示词”或“控制输出”，而是输入约束、知识来源、工具调用、结果校验和评估闭环这些工程化措施。

**参考答案要点**
- 优先让模型基于可信上下文回答，而不是自由发挥。
- 通过 RAG、工具调用、结构化输出、关键词约束、答案模板等方式收窄生成空间。
- 对关键结果增加后处理校验，比如字段校验、规则校验、引用校验。
- 对高风险场景设计拒答、追问、降级策略。
- 用评测集持续看准确率、拒答率、命中率，而不是只靠主观感受。

**话术示例**
我降低幻觉的思路，核心不是只靠一句 Prompt，而是尽量减少模型自由发挥的空间。第一，如果场景允许，我会先给它可信上下文，比如通过知识库召回或者工具查询，把可参考信息喂进去；第二，我会把输出格式做结构化约束，降低它随意扩写的概率；第三，对关键字段再做代码侧校验，比如格式、枚举值或者规则检查；第四，如果模型没有足够依据，就让它明确拒答或者追问，而不是硬编。真正要把幻觉率降下来，还是要靠“可信输入 + 约束输出 + 结果校验 + 持续评测”这套组合。

### 4. 长对话上下文压缩与准确率指标【5 分】

**问题**：长对话场景下，你怎么做上下文管理、压缩时机和压缩力度控制？如果只按阈值压缩，怎么避免上下文被切断后不连贯？项目里有没有建立准确率指标？

**我的答案要点**
- 从面试官打断可知，你一开始把问题答偏到了“会话如何存储”。
- 在上下文压缩时机、语义片段保留和连贯性保证方面，没有给出明确方案。
- 项目里没有建立较完整的结果准确率指标体系。

**评价**
- 优点：你至少意识到了会话状态和历史消息是需要管理的。
- 不足：这题暴露出你对长上下文治理的理解还停留在“存没存、截没截”层面，没有真正进入“摘要、分层记忆、语义片段、触发策略、评估指标”这些 Agent 工程核心点。面试官在这里已经明确感受到你对上下文压缩方案理解不足。

**参考答案要点**
- 不要把“存储会话”和“管理上下文”混为一谈。
- 可采用分层记忆：近期原始消息 + 历史摘要 + 关键事实槽位。
- 压缩触发可基于 token 阈值、轮次阈值、主题切换或成本阈值，不应只用单一长度阈值。
- 压缩时优先保留任务目标、用户偏好、关键事实、未完成事项，而不是机械截断中间轮次。
- 可通过滑动窗口、主题块摘要、实体槽位提取等方式降低不连贯风险。
- 指标上至少建立人工标注集，观察答案准确率、关键信息遗漏率、摘要偏移率、用户追问率。

**话术示例**
这题我会把它拆开回答。会话存储只是把历史记下来，但上下文管理的重点是“每一轮到底喂什么给模型”。如果进入长对话，我通常不会简单地按长度硬裁，而是做分层处理，比如最近几轮保留原文，较早内容压成摘要，再把关键事实像用户目标、约束条件、未完成事项单独提出来做结构化保存。压缩触发也不只看 token 超限，还会看轮次、主题切换和成本。这样即使压缩，也能优先保住真正影响后续回答的语义锚点。除此之外，我还会配一套评估集，看摘要后是否出现关键信息丢失、回答偏题或者追问率上升。

### 5. 对话流式输出方案选型【6 分】

**问题**：你们现在对话用的是什么流式输出方案？为什么这样选？输出内容除了文本还有没有别的格式？

**我的答案要点**
- 记录过简，待补充。
- 从面试官提问可推断，你们当前采用了流式输出方案。
- 输出内容大概率以纯文本为主，没有形成多模态或结构化分段输出能力。

**评价**
- 优点：至少项目已经具备对话流式返回，说明你接触过真实交互链路，而不是只做离线问答。
- 不足：这题可以很好体现工程判断，但从追问节奏看，你没有把协议选型、前后端配合、体验优化和错误恢复讲清楚。尤其是为什么用 SSE、WebSocket 或分块 HTTP，这种取舍逻辑应该主动说。

**参考答案要点**
- 如果是服务端单向持续推送文本，优先说明 SSE；如果有双向实时控制，再谈 WebSocket。
- 说明为什么当前场景不需要更重的协议，或者为什么必须上更复杂方案。
- 前端要补齐打字机展示、中断、重试、超时、部分结果缓存。
- 如果输出不只有文本，还可设计结构化事件流，比如 `token`、`status`、`tool`、`final` 等事件类型。

**话术示例**
如果场景主要是服务端单向把生成内容持续往前端推，我一般会优先考虑 SSE，因为实现简单、浏览器支持好，也比较适合聊天流式输出。如果中间还需要更强的双向交互，比如前端随时控制工具执行或者多路状态同步，那才更偏 WebSocket。我们这类场景如果目前主要是文本生成，其实先把文本流打稳更重要，但我会预留事件类型，比如内容分片、状态通知、结束标记和错误事件，这样后面扩成结构化流也比较自然。

### 6. 知识库与 RAG 的理解【5 分】

**问题**：项目里有没有用内部知识库？你对 AI 知识库和 RAG 有什么理解？

**我的答案要点**
- 记录过简，待补充。
- 从面试官继续追问“你知道什么是 RAG”可以看出，你在这部分的回答比较模糊，没有形成清晰定义。

**评价**
- 优点：你没有完全回避知识库方向，说明对这个话题有基本接触。
- 不足：RAG 已经是 Agent 岗位的基础问题。如果回答仍停留在“把文档喂给模型”这种层面，会显得理解太浅。至少要能说明检索、召回、重排、拼接上下文和生成之间的关系。

**参考答案要点**
- RAG 是“检索增强生成”，先从外部知识源召回相关内容，再把结果作为上下文交给模型生成。
- 核心链路包括文档切分、向量化、索引构建、召回、重排、上下文拼装和回答生成。
- 它解决的是模型参数知识不新、不全、不可控的问题。
- 真正工程落地时，还要关注分块策略、召回质量、引用可追溯和缓存。

**话术示例**
我理解的 RAG，本质上不是“给模型多喂点资料”，而是先检索、再生成。也就是先把知识库文档做切分和索引，在用户提问时先召回最相关的片段，必要时再做重排，然后把这些高相关内容作为上下文交给模型回答。这样做的目的，是让答案更多基于外部可信知识，而不是单纯依赖模型参数里的记忆。真正落地时，关键不只是接个向量库，而是切块策略、召回质量、上下文拼接方式和引用可追溯性。

### 7. 个人 AI 工作流与部署发布自动化设计【5.5 分】

**问题**：你平常自己的 AI 工作流是什么样的？如果让 AI 打通从部署到发布的链路，你会怎么保证准确性与安全性，并设计自动化流程？

**我的答案要点**
- 你提到会把部署相关工作交给 AI 处理。
- 面试官继续追问后，说明你对“AI 参与部署”更多停留在使用层，没有完整展开自动化链路和风险控制。
- 你提到了链路里仍然存在人工审核阶段。

**评价**
- 优点：你已经在实际工作中尝试用 AI 提效，不是停留在概念层。
- 不足：这题的深度要求是“怎么设计可控的 AI 自动化链路”，不是“我会让 AI 帮我部署”。面试官想听的是权限边界、环境隔离、审批关卡、日志审计、回滚机制、验证步骤这些确定性设计，而你的回答显然没有把这条链路讲透。

**参考答案要点**
- 先区分 AI 适合做建议、脚本生成、变更说明、校验清单生成，不适合直接裸执行高风险生产操作。
- 自动化链路可设计为：变更解析 -> 风险评估 -> 脚本生成 -> 静态校验 -> 测试环境执行 -> 结果校验 -> 人工审批 -> 正式执行 -> 监控回滚。
- 高风险动作要做权限分级、环境隔离、审计留痕和强制确认。
- AI 的角色更适合当“辅助决策和自动编排器”，不是无约束执行者。

**话术示例**
如果让 AI 参与从部署到发布的链路，我不会让它直接对生产环境做无约束执行，而是把它放在“分析、生成、校验、编排”这些环节。比如先让 AI 读变更内容，生成部署步骤和风险清单，再结合固定规则做静态校验，然后先在测试环境执行，验证通过后进入人工审批，最后才触发正式发布。整个过程中要有权限分级、操作审计、失败回滚和监控告警。也就是说，AI 可以大幅提升流程效率，但生产链路里的最终控制权和关键兜底不能完全交给它。

### 9. LangChain 模块拆分与底层分层理解【5 分】

**问题**：你在项目里用 LangChain 时，是怎么拆分模块的？每个模块职责是什么？对 LangChain / LangGraph 这类框架的底层分层架构有了解吗？

**我的答案要点**
- 记录过简，待补充。
- 从面试官连续追问“有多少模块”“每个模块职责是什么”“底层怎么分层”来看，你的回答偏使用层，缺少框架级理解。

**评价**
- 优点：你有实际接触 LangChain 类框架的经验。
- 不足：这题说明你对框架还停留在“会调用”层面，没有形成模块拆分视角。Agent 岗位通常希望候选人至少能说清 Prompt、Model、Memory、Tool、Retriever、Chain 或 Graph 这些模块是如何协作的。

**参考答案要点**
- 从应用层看，可拆为 Prompt 编排、模型调用、记忆管理、工具调用、知识检索、输出解析。
- 从框架层看，本质是“模型抽象 + 数据流编排 + 状态管理 + 外部能力接入”。
- LangGraph 更强调节点、边和状态流转，适合复杂工作流和多 Agent 场景。
- 面试里不一定要背源码，但要能说出框架解决了什么抽象问题。

**话术示例**
如果从项目使用层去拆，我通常会把 LangChain 相关能力分成几块：Prompt 编排、模型调用封装、Memory 管理、Retriever 检索、Tool 调用和输出解析。它的价值，不是简单帮我调一次模型，而是把这些能力抽象成可组合的流程。如果再往底层理解，它其实是在做模型接口抽象、状态传递和工作流编排。像 LangGraph 这种框架，会把复杂流程拆成节点和状态流，更适合多步骤决策或者多 Agent 协作场景。

### 10. Agent 的 System Prompt 设计【5.5 分】

**问题**：你在 Agent 里面是怎么设计整个 system prompt 的？

**我的答案要点**
- 记录过简，待补充。
- 从面试官继续推进到后面的提示词设计题来看，你的回答没有形成稳定的 Prompt 设计框架。

**评价**
- 优点：你应该已经有在项目里写 Prompt 的经验。
- 不足：System Prompt 设计是 Agent 岗位的核心基本功。这题如果不能讲出角色、目标、输入上下文、约束、工具规则、输出格式、失败策略等层次，面试官会默认你更多是在靠试错写提示词，而不是在做可维护设计。

**参考答案要点**
- 先定义角色与目标，再给出任务边界和能力边界。
- 明确输入上下文来源、可用工具、禁止行为和输出格式。
- 对高风险场景加上拒答、追问、引用依据等规则。
- 把稳定规则放在 system 层，把具体任务输入放在 user 层。

**话术示例**
我设计 system prompt 时，一般会分几层。第一层是角色和目标，明确这个 Agent 是干什么的；第二层是输入上下文和任务边界，说明它可以依据哪些信息、不能做哪些假设；第三层是行为规则，比如什么时候必须追问、什么时候必须拒答、什么时候调用工具；第四层是输出格式，确保结果稳定可消费。这样设计的目的，是把长期稳定的规则固定在 system 层，而不是每次都在 user prompt 里临时拼。

### 11. 设计垂类 Sub-Agent 的思路【4.5 分】

**问题**：如果让你在现有 AI 编码工具体系里新建一个垂类 Agent 或 Sub-Agent，你会怎么设计它的 Agent 说明文件和能力边界？

**我的答案要点**
- 记录过简，待补充。
- 从面试官后续不断换问法可知，这题你没有很好接住，对现成 AI 编码产品里 Agent / Sub-Agent 组织方式了解不深。

**评价**
- 优点：至少没有完全拒绝回答，说明你愿意尝试从设计角度去组织思路。
- 不足：这题明显暴露出你对“如何把一个 Agent 产品化、规范化”思考不足。面试官连着换成“agent.md 怎么写”“sub-agent 怎么设计”，本质是在考你对角色说明、工具权限、输入输出边界、触发场景的抽象能力。

**参考答案要点**
- 先定义场景：这个 Sub-Agent 解决什么问题，不解决什么问题。
- 说明输入、输出、依赖上下文、可调用工具、禁止动作。
- 规定执行步骤、异常处理和升级条件。
- 如果是垂类 Agent，要强调领域知识、评判标准和结果格式，而不是只给一句角色描述。

**话术示例**
如果让我设计一个垂类 Sub-Agent，我不会只写一句“你是某某专家”，而是会把它当成一个受约束的执行单元来定义。先写清楚它服务的场景和目标，再写输入是什么、输出应该长什么样、允许用哪些工具、哪些事情不能做。接着我会给它一套稳定的执行步骤，比如先理解任务、再校验条件、再生成结果，遇到信息不足时必须追问，超出权限时必须升级。这样它才是一个可控的 Sub-Agent，而不是一个模糊角色。

### 12. 需求价值判断 Prompt 设计【5 分】

**问题**：如果让你设计一个提示词，让 AI 对产品文档进行评分，并判断一个需求值不值得做，你会怎么设计这个提示词的结构、分层和判断体系？

**我的答案要点**
- 记录过简，待补充。
- 从面试官持续引导“怎么做价值判断”“分结构分层怎么写”可以看出，你当时没有快速搭出一个清晰的评估框架。

**评价**
- 优点：这题本身偏设计题，不完全是背知识点，你至少有组织思路的空间。
- 不足：你没有及时把问题抽象成“输入维度 + 评估维度 + 评分规则 + 输出模板 + 结论阈值”这类结构，因此回答容易散。AI Agent 岗位很看重这种把模糊问题结构化的能力。

**参考答案要点**
- 先定义输入，包括产品背景、用户对象、核心问题、预期收益、约束条件。
- 设计评分维度，比如用户价值、业务价值、实施成本、风险、可验证性、战略一致性。
- 每个维度给评分标准和解释，避免模型自由发挥。
- 输出要求包括总分、分项理由、关键风险、是否建议推进、建议补充的信息。
- 若信息不足，要求模型明确列出缺失点，不直接武断给结论。

**话术示例**
如果让我设计这个 Prompt，我会先把它做成一个结构化评审器，而不是一句泛泛的“帮我评估下这个需求值不值得做”。输入里我会要求提供产品背景、目标用户、要解决的问题、预期收益、上线约束这些基础信息。评估维度我会拆成用户价值、业务价值、实现成本、风险、可验证性和战略一致性，每个维度都给出评分标准。输出时不仅要给总分，还要给分项理由、主要风险、建议推进还是暂缓，以及还缺哪些信息。这样模型做的不是拍脑袋判断，而是基于固定框架做决策辅助。
