### 3. HashMap 底层实现 【3 分】【错】

**问题**：HashMap 是怎么实现的？

**错误点**：未作答，表示"这方面底层原理没研究那么深"。

**我的答案要点**
- 未作答

**评价**
- 优点：坦诚表明不熟悉，没有胡说。
- 不足：HashMap 是 Java 基础高频题，即使以前端为主也应了解核心原理；完全放弃作答给面试官留下 Java 基础薄弱的印象。

**参考答案要点**
- 底层结构：数组 + 链表 + 红黑树（JDK 1.8+）
- 核心流程：`put` 时先计算 key 的 `hashCode`，再通过扰动函数降低碰撞，取模得到数组下标
- 链表转红黑树：链表长度 ≥ 8 且数组长度 ≥ 64 时转红黑树；反之退化回链表（长度 ≤ 6）
- 扩容：负载因子默认 0.75，达到阈值时 2 倍扩容并 rehash
- 线程不安全：并发场景应使用 `ConcurrentHashMap`（分段锁 / CAS + synchronized）

**话术示例**

> HashMap 底层是数组加链表加红黑树的结构。put 一个元素时，先对 key 的 hashCode 做扰动处理，然后取模得到数组下标，如果下标位置已有元素就形成链表。JDK 1.8 以后，链表长度到 8 且数组长度超过 64 的时候，会把链表转成红黑树，查询效率从 O(n) 提升到 O(log n)。扩容是默认 0.75 的负载因子，容量达到阈值就 2 倍扩容再 rehash。HashMap 本身线程不安全，高并发场景要用 ConcurrentHashMap。

**问题**：Spring 源码有看过吗？

**我的答案要点**

**评价**

**参考答案要点**
- IOC（控制反转）：Bean 的生命周期，`BeanDefinition` → 实例化 → 属性注入 → 初始化 → 使用 → 销毁
- AOP（面向切面）：基于动态代理（JDK 动态代理 / CGLIB），在不修改原始代码的前提下织入横切逻辑
- Spring Boot 自动配置：`@SpringBootApplication` → `@EnableAutoConfiguration` → `spring.factories` / `AutoConfiguration.imports`，条件注解（`@ConditionalOnClass` 等）按需装配

**话术示例**

> Spring 源码我没有逐行读过，但核心机制有了解。IOC 方面，Spring 在启动时扫描 Bean 定义，经过实例化、属性注入、初始化这几个阶段管理 Bean 的生命周期。AOP 是基于动态代理实现的，接口用 JDK 动态代理，普通类用 CGLIB，在方法前后织入切面逻辑。Spring Boot 的自动配置核心是 @EnableAutoConfiguration，它会读取 AutoConfiguration.imports 文件里的配置类，再配合条件注解判断是否装配，这样就做到了约定大于配置。

### 9. 使用 AI 开发过程中遇到的问题与解决方案 【9 分】

### 10. AI 边界区分 【9 分】

**问题**：你会区分你和 AI 的工作边界吗？

**我的答案要点**

- 人来做：通讯方式设计、项目配置、技术选型、架构拆分、组件结构分析
- AI 来做：规范明确的样板代码生成、组件内设计图还原、接口具体代码生成（耗时、重复的部分）

**评价**
- 优点：分工明确，有实际工程思维，而不是把所有事情都推给 AI。

- 核心原则：越「规范明确」的任务越适合给 AI；越需要全局视角和判断力的任务越应该由人来做

**话术示例**

> 我会有比较明确的分工。架构设计、技术选型、组件拆分思路、通信协议这些需要全局视角和判断力的，我自己来做。规范非常清晰的任务，比如按设计稿还原一个组件内部的样式、生成增删改查接口、写单测，这些比较重复和模板化，交给 AI 来做，节省大量时间。AI 生成完我会 Review，确保代码符合整体风格和架构方向。这样既发挥了 AI 的速度，又保证了代码质量。

**我的答案要点**

**参考答案要点**

  1. 将文档切分成 chunks
  2. 用 Embedding 模型将每个 chunk 转换为向量
  3. 存入向量数据库（如 FAISS、Chroma、Milvus、Qdrant）
- 在线阶段（检索生成）：
  1. 将用户问题用同一 Embedding 模型向量化
  2. 在向量数据库中计算余弦相似度，检索 Top-K 相关 chunks
  3. 将检索结果拼入 Prompt，连同问题一起送给 LLM 生成回答
- 核心价值：解决 LLM 训练数据截止日期问题，支持私有知识库查询

**话术示例**

> RAG 分两个阶段。离线阶段是构建索引：把文档切成小段，用 Embedding 模型把每段转成向量，存到向量数据库里。在线阶段是检索生成：用户问题来了先用同一个 Embedding 模型向量化，然后去向量数据库里做相似度搜索，找出最相关的几段文档，再把这些文档和问题一起拼成 Prompt 发给大模型，让模型基于检索到的内容来回答。RAG 的核心价值是解决了大模型没有实时数据、没有私有知识的问题，不需要重新训练模型就能让它"知道"你的业务文档。

**参考答案要点**
- 方案一（关键词 + 全文检索）：
  1. 图片上传时，用多模态大模型（如 GPT-4o Vision / Qwen-VL）解析图片内容，生成关键词列表（如 ["大海", "海浪", "蓝色", "水"]）
  2. 存入 Elasticsearch，利用分词 + 同义词词典做模糊匹配
  3. 缺点：依赖同义词词典，语义覆盖有限
- 方案二（向量数据库语义检索，推荐）：
  1. 图片上传时，用 CLIP 等多模态 Embedding 模型将图片转成向量（或将图片描述转成文本向量）
  2. 存入向量数据库（如 Milvus、Qdrant）
  3. 查询时将用户输入文本向量化，在向量数据库中做相似度搜索
  4. 优点：天然支持语义匹配（"水" → "大海"，"河流"，"游泳池"）
- 混合方案：向量检索（召回）+ 关键词过滤（精排）

**话术示例**

> 核心思路是在图片上传时做预处理，而不是查询时再解析，不然每次搜索都要扫全量图片，成本太高。上传时用多模态大模型（比如 GPT-4o Vision）解析图片，生成描述和关键词，然后存起来。查询时有两种方案：一种是用 Elasticsearch，利用分词和同义词词典做模糊关键词匹配，实现成本低，但语义覆盖依赖词典质量。更推荐的方案是用向量数据库——上传时用 CLIP 这类多模态 Embedding 模型，把图片内容转成向量存进去；查询时把用户输入的文字也向量化，做相似度搜索，这样"水"自然就能匹配到"大海"、"河流"，不需要维护同义词词典，语义理解更准确。

### 25. 需求不明确怎么处理 【8.5 分】
