### 1. 在鸿翔科技负责的核心项目【8 分】

**问题**
能介绍一下你在鸿翔科技负责的核心项目和主要职责吗？举一个具体的例子。

**我的答案要点**
- 雷达气象预警项目，从 0 到 1，4 人团队
- 承担约 40% 前端 + 60% 后端 + 全部智能体相关开发
- 前端：Vue + React，父子项目架构，iframe 嵌入，实现父子通信、统一登录、统一切换、权限管理、性能优化

- 智能体：Python 生态，工作流编排、工具绑定、会话管理、压缩逻辑，封装为微服务注册进 Java 微服务体系
- 邀请面试官选感兴趣方向展开

**评价**
- 优点：三层拆解（前端 / 后端 / 智能体）结构清晰，有数字支撑，主动邀请引导有节奏感。
- 不足：前端技术栈说"Vue + React"但没点明各自的具体职责划分；后端技术栈表述含糊（录音里出现"铭文生态""丑陋的生态"等口误），应说清楚 Spring Cloud + Nacos；智能体部分点到即止，缺少一句能引发追问的亮点句。

**参考答案要点**
- 项目定位一句话：全栈气象雷达预警平台，负责前后端加智能体全部交付。
- 前端：Vue 3 + React，基于 iframe 父子应用方案，解决多省份旧项目复用 + 统一管控。
- 后端：Spring Boot + MyBatis + Spring Cloud（Nacos 注册中心 + Gateway 网关），从单体拆成微服务承接多省份独立需求。
- 智能体：Python + LangChain/LangGraph + FastAPI，工作流编排 + 工具绑定 + 会话压缩，封装 HTTP 接口接入 Java 微服务体系。
- 用"人 / 技术 / 结果"三要素收尾，给面试官清晰记忆点。

**话术示例**

### 2. 如何保证代码质量【9 分】

**问题**
你在这个项目中是怎么保证代码质量的？能结合具体项目举个例子吗？

**我的答案要点**
- 可读性：ESLint + Stylelint + Prettier，保存自动格式化，语法问题自动标红
- 复用性：项目级（微前端架构/分支管理/微服务拆分）→ 代码级（前端：组合式函数/组件拆分，后端：DTO 分层/类抽象）
- 性能：前端（SSR/懒加载/缓存/Performance 面板/火焰图/长任务优化/requestIdleCallback/requestAnimationFrame/减少重排重绘）；后端（JMeter 压测/日志排查/多线程优化/数据库索引优化）
- AI 时代保证质量：人的能力要强于 AI；自己搭核心架构，AI 做样板代码，人做最终审核兜底

**评价**
- 优点：三维度框架清晰，技术点覆盖极全，AI 时代补充亮眼且有深度，思路非常成熟。
- 不足：回答过长，在现场有些罗列感；可以先报出框架（可读性/复用性/性能/AI 时代）再展开，节奏感更强；"真米特"应为 JMeter。

**参考答案要点**
- 可读性：项目统一配置 ESLint + Stylelint + Prettier，保存即格式化，降低 review 成本。
- 复用性：项目级用微前端/微服务架构隔离共用和差异；代码级前端用组合式函数/组件拆分，后端用 Service 分层 + DTO。
- 性能：前端定期用 Performance 面板看火焰图，长任务用 requestIdleCallback 拆分，动画走 CSS3 或 requestAnimationFrame；后端用 JMeter 做 1000 次/10s 压测，慢查询走索引优化（最左前缀原则、联合索引覆盖所有慢查参数），CPU 密集型用多线程数 = 核数，I/O 密集型用 2 倍核数线程池。
- AI 时代：人搭骨架（架构/目录/核心逻辑），AI 做样板代码（UI 还原/常规接口），人做功能验收 + 代码审查，不让项目变成黑盒。

**话术示例**
我从可读性、复用性、性能三个维度来说，最后补充一下 AI 时代的做法。可读性上，每个项目都配了 ESLint、Stylelint 和 Prettier，保存自动格式化，不需要人工干预，语义问题会标出来人工处理。复用性上，项目级靠微前端或微服务架构来隔离共用逻辑和差异需求；代码级前端用组合式函数和组件拆分，后端用 DTO 分层和 Service 类抽象，同一段逻辑只写一次。性能上，前端用 Performance 面板看火焰图，长任务用 requestIdleCallback 拆，动画走 CSS3 或 requestAnimationFrame，减少重排重绘；后端用 JMeter 做压测，1000 次请求 10 秒内跑，慢接口从网关日志开始往下排，数据库慢查询就设联合索引，保证所有慢查都能从左边命中索引。AI 时代特别要说的一点是：我来搭项目的核心架构，包括目录结构和关键流程，样板代码交给 AI，AI 做完我先验功能，再过一遍代码，确认没问题再提交，这样不会让项目变成黑盒。

### 3. 需求不清楚时如何判断和推进【7.5 分】

**问题**
你在工作中有没有遇到需求不太清楚的情况？当时你是怎么判断该做什么，又是怎么推进下去的？

**我的答案要点**
- 流程：甲方 → 项目经理 → 产品经理出 PRD → 需求评审会当场对齐 → 开发
- 每周开发前通读需求文档，列不清楚的清单，企业微信约产品经理当面过一遍
- 举例：山西省风格切换功能，先确认"是所有省份都要还是只有山西要"，确认是山西独有后写到山西分支，避免做公共化的冗余工作

**评价**
- 优点：先说流程再举例，结构清晰；主动澄清习惯展示得真实。
- 不足：举的例子比较平（只是一个分支决策），没体现出"需求本身模糊、自己推理填空"的能力；可以举一个需求描述含糊、需要主动拆解或提出方案的例子来说服力更强。

**参考答案要点**
- 标准做法：需求评审前熟读 PRD，列疑问清单，评审会当场对齐；开发期间遇到理解不一致，立即拉产品经理确认，不猜不假设。
- 补充更有力的例子方向：需求说"要展示预警信息"但没说格式，我主动提出两个方案（卡片式 vs 列表式），产品确认后推进，减少后期返工。
- 体现决策能力：如果一时联系不上产品，先做技术上通用性最强的方案，并在 MR 备注"待确认的设计决策"，让 review 时补齐。

**话术示例**
我们的流程是，产品经理在需求评审会前出好 PRD，评审时把需求讲一遍，当场把不清楚的对好。具体开发的时候，我每周开始前会把这周要做的需求全部读一遍，把理解不确定的地方列成清单，直接企业微信约产品经理过一遍，确认清楚再开发。举个例子，山西省要加风格切换功能，我第一时间确认了"是所有省份都要，还是只有山西要"，产品说只有山西，我就把这个功能写到山西自己的分支，没有放公共代码里，避免后续其他省份不需要时还要再拆。

### 4. 如何确保开发的功能真正解决了用户的问题【6.5 分】

**问题**
你怎么确保自己开发的功能真正解决了用户的问题？你会主动去了解用户反馈吗？

**我的答案要点**
- 这部分不需要开发来确保，这是项目经理的工作
- 我们的职责是像素级还原 UI 设计图和精准还原需求
- 甲方需求经由项目经理和产品经理过滤后，以设计稿形式交到开发端

**评价**
- 优点：边界清晰，分清职责，没有过度承诺。
- 不足：回答偏被动，给面试官"不关心用户价值"的印象；实际上可以在"精准还原需求"的基础上，补充"我也会主动关注甲方验收反馈"来展示用户意识；面试官随即换了角度追问方向偏差问题，说明这个回答没有让面试官满意。

**参考答案要点**
- 职责边界：直接需求对接在产品/PM 侧，开发保证精准实现是基线。
- 补充用户意识：开发期间会和产品确认"这个交互用户是否真的能理解"；验收阶段关注甲方反馈，主动问项目经理有没有用户提出的疑虑。
- 结合例子：某功能上线后甲方反馈操作路径不直觉，我和产品一起拆解用户行为，给出优化方案，不只是等产品派任务。

**话术示例**
直接的用户对接是产品经理负责，开发这端的职责是精准还原需求和设计稿。不过我也会在开发过程中关注用户侧——比如某个交互逻辑我觉得用户可能不太容易理解，我会主动跟产品确认，看是不是要加个引导。验收后如果甲方有反馈，我也会主动问项目经理，了解哪些地方没达到预期，这样下一个迭代可以提前把隐患消掉。

### 5. 做完功能才发现方向不对如何处理【7.5 分】

**问题**
在你的开发过程中，有没有遇到过做完功能才发现方向不对，或者和预期不符的情况？你是怎么处理的？

**我的答案要点**
- 技术层面不会出现，因为需求都确认得非常明确才开始实现
- 有遇到过甲方验收后觉得和自己想的不一样而改需求的情况
- 处理方式：项目经理和产品经理对接，任务落到我这里就是改功能；复用部分留下，差异部分删掉重写，提交为新的 Git 记录作备份
- 有了 Git 历史记录，如果客户反悔还想要原版，可以用 Git 历史找回

**评价**
- 优点：用 Git 版本管理作为变更备份，思路专业。
- 不足："技术上不会出现"说法稍显绝对，容易让面试官觉得候选人回避问题；实际上更好的姿态是承认有不确定性，然后说用什么手段降低风险；缺少一个具体例子支撑。

**参考答案要点**
- 预防：通过需求确认 checklist + 阶段性 demo 给产品/PM 确认，早发现早修正。
- 应对：需求变更后，先梳理"哪些逻辑可复用、哪些需要删改"，最小化改动范围；每次变更都作为独立 commit，commit message 写清楚变更原因，方便追溯和回滚。
- 举例：甲方验收时提出某省的图表展示方式和预期不符，我评估后保留了数据层，只重写了图表渲染层，1 天内完成交付，且保留了原版 commit。

**话术示例**
我的习惯是在开发之前把需求确认得比较充分，但需求变更确实难以完全避免。遇到过甲方验收后觉得跟自己设想不一样要改的情况，我的处理方式是先梳理原有代码里哪些逻辑可以保留、哪些要替换，尽量复用可以复用的部分，减少改动范围。每次变更都会作为独立 commit 推上去，commit message 写明变更原因，这样如果后续客户说还是想要原来那个版本，用 Git 历史能直接找回，不会真的丢掉。

### 6. 主动创造价值的例子【8.5 分】

**问题**
能举个例子，说说你主动做了什么事情——虽然没人安排你，但确实产生了价值或影响？

**我的答案要点**
- 团队地图库从 Leaflet 换成领导自研的 JS 地图框架（@tecxs 或类似包）
- 项目已全面 TS 化，但领导的框架是纯 JS 写的，使用时没有类型提示，不方便
- 主动封装了一个 TS 类型包，发布到公司内网 npm 服务
- 每用到一个新方法就完善一下包，逐步覆盖
- 发到团队群里供大家使用，领导认可，提升了部门整体开发效率

**评价**
- 优点：例子真实具体，"发现问题 → 主动解决 → 推广落地 → 获得认可"链路完整，主动性和价值创造都展示到位。
- 不足：没有说出具体的覆盖范围（多少个方法/多少人在用），如果有数字支撑说服力更强。

**参考答案要点**
- 背景：团队地图库换成了领导自研的 JS 框架，项目全面 TS 化，没有类型定义使用不便。
- 行动：主动写了配套的 TypeScript 声明包，发布到公司内网 npm，边用边完善覆盖方法。
- 结果：分享给全团队，领导认可，降低了大家调用地图 API 时的心智负担，提升了部门整体开发效率。
- 补充数字感：如"覆盖了核心 30+ API 方法，全组 5 人都在用"之类。

**话术示例**
我们团队的地图库切换到了领导自研的一个 JS 框架，但项目早就全面 TS 化了，领导的包没有类型定义，用起来没有类型提示也没有代码补全，效率比较低还容易出错。我就主动给这个包写了一套 TypeScript 声明文件，发布到公司内网 npm，每次用到一个新 API 就把它的类型补进去，慢慢把常用方法都覆盖了。然后我把这个包发到了团队群里，说大家用地图的时候可以顺手装进来，有类型校验会方便很多。领导后来跟我说这个动作他很认可，觉得提升了整个部门的开发效率。

### 7. 从零学复杂技术的经历【7 分】

**问题**
最近一次从零开始学一个比较复杂的技术是什么？你是怎么学的？又怎么知道自己真的掌握了？

**我的答案要点**
- Java 生态，去年年初开始
- 背景：竞选组长，领导提前打招呼，组长要前后端全栈掌控，提前自学
- 前后端概念相通，JS 与 Java 语法高度相似，新的主要是 Spring Cloud 生态（Nacos、Spring Cloud Gateway 等）
- 学习方式：时间充裕看官方文档；时间紧先问 AI 快速上手，边做边学
- 结果：顺利完成全站项目（雷达气象预警）

**评价**
- 优点：有真实背景，学习策略务实（文档 + AI + 实践），验证路径是上项目。
- 不足：面试官问了"怎么知道自己真的掌握了"，候选人没有正面回答这个问题，只说"学完顺利做了项目"；缺少自我验证机制的描述（如：能独立排查问题、能向他人讲清楚、在项目中独立做了哪些决策等）。

**参考答案要点**
- 学习方式：文档打底，AI 加速具体问题，项目实践消化。
- 判断掌握的标准：
  - 能独立做技术选型决策（如：拆微服务用 Nacos 还是 Eureka，为什么选 Nacos）
  - 能独立排查问题（微服务注册失败、Feign 调用超时等）
  - 能给团队讲清楚（如：给后端同学说明为什么要用这种分层方式）
- 具体说明在项目中独立完成了哪些关键决策，让"掌握了"有依据。

**话术示例**
最近从零开始学的是 Java 后端生态，主要是 Spring Boot 加 Spring Cloud 那一套。背景是我竞选组长前，领导让我先把后端补起来，因为组长要对整个项目负责。Java 和 JS 语法相似度挺高，迁移成本低，主要要学的是 Spring Cloud 生态，Nacos 做注册中心、Gateway 做网关这些。学习方式上，时间够就直接看官方文档，时间紧就先问 AI 把当下那个问题搞定，再在项目里边做边吸收。判断自己掌没掌握，我觉得最直接的标志是：我能独立做关键决策——比如单体要不要拆、怎么设计微服务边界、Nacos 的服务分组怎么配——这些我都是自己判断然后落地的，不需要问别人，出了问题也能自己排查，这时候我觉得就是真的掌握了。

### 8. 求职动机与薪酬期望【8 分】

- 可以转岗到军用部门，但领导同事全换，相当于重新开始，不如重新看机会
- 求职方向：全栈机会，有智能体方向更好，英语环境可以适应
- 当前薪资：22k，期望：28k

**评价**
- 优点：理由正当且诚实，求职方向清晰，与岗位契合度高，薪资说得直接清楚。
- 不足：可以补充一句主动的求职愿景（不只是"被动离开"，还有"主动想去做什么"），让回答更有主导感。

**参考答案要点**

### 9. 英文介绍复杂系统【7 分】

**问题**
能不能用英文给我介绍一下你做过的一个比较复杂的系统？用五六句话就可以了。

**我的答案要点**
- 介绍气象雷达预警系统
- 前端：父子应用架构，两个旧项目复用 + 三个新项目，iframe 嵌入，统一登录、统一切换、权限控制
- 后端：从单体迁移到微服务，解耦共用逻辑和省份独立需求
- 末尾有停顿和未完成句（"啥名词"、"I expected the..."）

**评价**
- 优点：内容框架正确，技术词汇（parent-child architecture、iframe、microservice、decouple）准确，逻辑完整。
- 不足：口语流畅度不足，出现"哈名词"（大声自问单词）、"I I I"等停顿，最后一句未说完；建议提前准备 5 句话模板，背熟再说，不要现场组织。

**参考答案要点**
- Sentence 1: 系统定位（名称 + 目的）
- Sentence 2: 前端架构（父子应用 + 嵌入方式 + 统一管控）
- Sentence 3: 前端挑战（性能优化 / 跨应用通信）
- Sentence 4: 后端架构（单体 → 微服务 + 原因）
- Sentence 5: 智能体部分（Python + LangGraph + 接入 Java 微服务）

**话术示例**
I worked on a meteorological radar warning system, which integrates weather monitoring and automated alert generation on a single platform. On the front end, I designed a parent-child application architecture using iframes to embed multiple sub-applications — two reused legacy projects and three new ones — with unified login, theme switching, and permission control managed by the parent app. To address performance issues, I optimized rendering by lazy loading sub-apps and reducing re-renders through component-level optimization. On the back end, the system was originally a monolith, but as multi-province requirements grew, I refactored it into a microservice architecture using Spring Cloud and Nacos, decoupling shared logic from province-specific features. I also built an AI agent service in Python using LangGraph to automate weather warning content generation, packaged it with FastAPI, and registered it into the existing Java microservice ecosystem.
