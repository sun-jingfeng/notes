### 5. 部署流水线（CI/CD 方案）【7 分】

**问题**
你们部署在哪里？发布流水线怎么做的？并发和弹性扩容怎么处理？

**我的答案要点**
- 公司测试环境 + 客户现场部署（大多数是内网环境）
- CI/CD：用 GitLab CI 绑定触发任务，自动拉取 + 打包 + 部署
- 前端：Nginx 镜像，打包后把 dist 目录放到映射目录
- 后端：微服务打成多个 jar 包 → 分别构建镜像 → 写 Docker Compose 文件编排，通过容器名通信，映射数据库端口等
- 客户那边：没有 GitLab CI，手动执行 Docker Compose 部署
- 没有 K8s，公司环境是自动管道，客户环境是手动
- 并发：要求每秒 100 次 / 10 秒 1000 次，压测通过即可，不通过就优化

**评价**
- 优点：前后端分别的 CI/CD 流程说得清晰，Docker Compose 编排方案合理；对客户环境（内网私有化）有明确的区分方案。
- 不足：对国内 Docker 镜像源封锁问题答得不完整（没有给出私有 Registry 方案）；没有 K8s 经验被面试官追问；弹性扩容没有方案，说明这块没有实践。

**参考答案要点**
- **CI/CD**：GitLab CI Pipeline，前端：拉代码 → npm build → dist 挂载到 Nginx 镜像 → 容器启动；后端：拉代码 → Maven 打包 → 构建各微服务 Docker 镜像 → Docker Compose 编排启动
- **私有化部署**：内网环境无法拉公网镜像 → 解决方案：搭建私有 Registry（Harbor）或将镜像 tar 包预先传入客户服务器，`docker load` 后再 compose up
- **国内镜像加速**：公司内网用私有镜像代理（如阿里云镜像加速 / 自建 Registry Proxy）；客户内网完全离线则提前打好镜像包
- **弹性扩容**：当前规模（100 req/s）不需要 K8s；如果需要扩容，Docker Compose 可以用 `--scale` 水平扩展无状态服务，数据库和 Redis 单独维护

**话术示例**
我们有两套环境，公司内是 GitLab CI 自动部署，新项目建一条 Pipeline，前端就是 build 完把 dist 挂到 Nginx 镜像里，后端微服务分别打镜像，然后用 Docker Compose 做编排，容器之间用容器名互相通信。客户那边是内网私有化部署，没有 GitLab，就是手动执行 Docker Compose。

内网镜像的问题我们是用公司的私有 Registry，项目依赖的基础镜像都提前推进去，到客户那边再从私有 Registry 拉，或者直接把镜像打成 tar 包随部署包一起带过去，客户那边 docker load 进来再 compose up。K8s 那套我们当时并发量不大，每秒 100 次就够了，没有上 K8s，简单用 Docker Compose 管就行了。

### 6. 国内 Docker 镜像封锁问题【5 分】

**问题**
国内 Docker Hub 镜像经常被封，你们私有化部署到客户那边是怎么处理这个影响的？有私有 Registry 吗？

**我的答案要点**
- 公司有自己的 npm 私有源（npm 私服）和后端私服
- 公司内网可以直接拉外网镜像
- 客户那边没有详细说明如何解决镜像源问题

**评价**
- 优点：提到了公司有私有源，说明有一定认知。
- 不足：这道题实际上是问 Docker 镜像源封锁的解决方案，回答偏题（npm 私服是包管理，不是 Docker 镜像 Registry）；没有给出完整方案（Harbor、镜像 tar 包预置、阿里云镜像加速等）；被面试官引导多次仍未给出完整答案，是本次面试的明显薄弱点。

**参考答案要点**
- **方案一（私有 Registry）**：搭建 Harbor 作为公司私有 Docker Registry，将常用基础镜像提前同步进去，CI/CD 流程直接从 Harbor 拉取；客户内网也可指向公司 Registry（需网络互通）
- **方案二（离线包）**：对完全离线的客户内网，提前在外网 `docker pull` 所有镜像，用 `docker save` 导出 tar 包，随部署包携带，客户环境 `docker load` 再使用
- **方案三（镜像代理）**：公司网络层配置镜像加速代理（如阿里云 ACR 镜像加速、自建 Squid 代理），在 `/etc/docker/daemon.json` 配置 `registry-mirrors`
- 这三种可组合使用：公司环境用 Harbor + 代理，客户内网用离线包

**话术示例**
这块我们当时主要是两个策略。公司测试环境用的是配了镜像加速代理，在 docker daemon 里配 registry-mirrors，指向阿里云或者公司自建的镜像代理，基本上拉取不受影响。客户内网是完全离线的，所以我们会提前在有网的环境把所有需要的镜像用 docker save 打成 tar 包，随部署包一起带过去，客户环境 docker load 进来再 compose up，这样完全不依赖外网。如果客户有条件搭私有 Registry，我们也会推荐用 Harbor 做镜像仓库，一次同步后续都走内网。

### 7. 消息队列（RabbitMQ）使用场景【7 分】

**问题**
你们消息队列是在什么场景下用的？具体是什么业务？

**我的答案要点**
- 出现性能问题时考虑引入 MQ
- 场景：预警发布功能，用户发布预警后不要求立即回执，用 RabbitMQ 将发送任务异步化
- 接收方是客户提供的接口，我们系统只负责发送
- 使用 Exchange 绑定发送者和消费者

**评价**
- 优点：有实际业务场景，异步解耦的动机清晰（不需要同步等待回执）。
- 不足：描述略简，没有说明 Exchange 类型（Direct/Topic/Fanout）；被追问消费者处理细节时回答不清楚。

**参考答案要点**
- **场景**：预警发布后需要推送给外部系统（客户接口），对实时性要求不高，用 MQ 异步解耦，避免外部接口慢或超时影响主流程
- **方案**：RabbitMQ，使用 Direct Exchange（或 Topic Exchange），消费者接收到消息后调用客户接口；消息消费失败通过死信队列处理
- **可靠性保证**：生产者开启 Publisher Confirm，消费者使用手动 ACK，只有调用客户接口成功后才 basicAck，失败则 basicNack 重新入队或进死信队列

**话术示例**
我们用 RabbitMQ 的场景是预警发布。用户发布一条预警，需要推送给客户提供的外部接口，但这个推送不要求实时完成，用户发完不用等它推过去。所以就把推送任务扔到 MQ 里，消费者异步去调客户接口，失败了走死信队列做后续处理。可靠性上用的是手动 ACK，消费者真的把消息处理完了（调用成功）才 ack，失败了 nack 回去重试或者进死信。

**评价**

- 不足：这是 RabbitMQ 基础知识，实际项目中用过 MQ 却说不出消费模式，说明对中间件的理解停在使用层面，底层模型没有系统化。

**参考答案要点**
RabbitMQ 官方文档定义的 6 种消息模型：

| 模型           | Exchange 类型 | 特点                                               |
| -------------- | ------------- | -------------------------------------------------- |
| 简单模式       | 无（默认）    | 一个生产者 → 一个队列 → 一个消费者                 |
| 工作队列       | 无（默认）    | 一个生产者 → 一个队列 → 多个消费者（竞争消费）     |
| 发布/订阅      | Fanout        | 一个消息 → 广播到所有绑定队列，所有消费者都收到    |
| 路由模式       | Direct        | 根据 routing key 精确路由到指定队列                |
| 主题模式       | Topic         | routing key 支持通配符（`*` 一个词，`#` 多个词）   |
| RPC 模式       | 无（默认）    | 生产者发请求，等待消费者处理后返回结果（同步语义） |

**话术示例**
RabbitMQ 有六种主要的消息模型。最简单的是一对一的简单模式，一个生产者一个消费者。工作队列是多个消费者竞争消费同一个队列，用来做任务分发和负载均衡。发布订阅用 Fanout Exchange，消息会广播给所有绑定的队列，适合一条消息多个系统都需要的场景。路由模式用 Direct Exchange，按 routing key 精确分发。Topic 模式是 Direct 的扩展，routing key 支持通配符，更灵活。最后还有 RPC 模式，消费者处理完后把结果回传给生产者，适合需要同步响应的场景。

### 9. 死信队列【6.5 分】

**问题**
你们有用过死信队列吗？死信队列是怎么工作的？

**我的答案要点**
- 了解死信队列
- 死信之后消息还会被处理
- 判断消息如果没被处理过，就重新投入队列

**评价**
- 优点：有基本认知，知道死信队列是处理未消费消息的机制。
- 不足：描述不准确——「没被处理过就重新投入」不够严谨，死信产生有三种情况（消息过期、队列满、被拒绝），死信队列是将死信路由到另一个队列做后续处理，不一定是简单重投；没有提到 DLX（Dead Letter Exchange）的配置方式。

**参考答案要点**
- **死信产生的三种情况**：① 消息 TTL 过期；② 队列长度超限（Queue max-length）；③ 消费者 basicNack/basicReject 且 requeue=false
- **处理机制**：配置 `x-dead-letter-exchange` 和 `x-dead-letter-routing-key`，死信会被路由到指定的 DLX，进入死信队列（DLQ）
- **典型用途**：延迟队列（TTL + DLX 模拟）、异常消息人工处理（监听 DLQ 告警）、消息重试次数控制

**话术示例**
死信队列是专门接收死信的队列。消息变成死信有三种情况：一是 TTL 到期，二是队列满了被丢弃，三是消费者 nack 且不重新入队。处理方式是在原队列上配一个 Dead Letter Exchange，死信进来之后会被路由到这个 DLX，然后进入死信队列。死信队列里的消息可以单独消费，通常用来做告警、人工处理、或者配合 TTL 实现延迟重试。

### 10. Redis 使用场景【8 分】

**问题**
你们 Redis 用在哪些地方？

**我的答案要点**
- 后端：CPU 密集型任务的计算结果缓存（气象矩阵数据，key = 时间 + 气象要素）
- 智能体：存会话记录（LangChain Memory）、存计算结果数据
- 两处都用了 Redis

**评价**

- 不足：没有提到 Redis 数据结构的选型（String/Hash/List 等）；会话记录用 Redis 可以提一下为什么不直接用 LangChain 的内置 Memory（持久化需求）。

**参考答案要点**

**话术示例**

### 11. 为什么用 Redis 而不用数据库（气象数据特性）【8.5 分】

**问题**
这些气象数据为什么存 Redis 而不存数据库？

**我的答案要点**
- 气象数据中有矩阵数据（如色斑图、PNG 格式），需要解析成网状数据
- 数据中有灵活参数（如分辨率），不能预先把所有组合都算一遍存入数据库
- 只能现查现算，算完缓存进 Redis 供下次同参数使用
- 访问量不大，存的时间可以比较久（一周/一个月）

**评价**
- 优点：业务动机解释得很好，说清了为什么不适合数据库（参数组合太多、无法预先持久化）；逻辑自洽。
- 不足：可以补充「Redis 适合的数据特征」做对比，加深说服力（如：数据无需持久化强一致、读多写少、生命周期有限）。

**参考答案要点**
- **不适合数据库的理由**：气象矩阵数据的计算结果依赖多个灵活参数（时间、要素类型、分辨率等），参数组合空间大，无法提前预计算全部结果存入数据库
- **适合 Redis 的理由**：① 数据是派生结果，不需要强持久化；② 生命周期有限（过期后重新算即可）；③ 读多写少（同参数查询频繁）；④ 访问延迟要求低（缓存毫秒级响应 vs 重新计算秒级）
- 相比数据库，Redis 在这个场景下无需表结构设计，key 直接对应参数组合，使用更简单

**话术示例**
主要是这个气象数据的特性决定的。气象矩阵数据的计算结果依赖好几个参数，像时间、气象要素类型、还有分辨率这些，参数是灵活传进来的，组合空间太大，不可能把所有组合都提前算一遍存数据库。所以是现查现算，算完了把结果放进 Redis，key 就是那几个参数拼起来。下次同样参数进来直接命中缓存，不用重算。而且这个数据本来就不需要强持久化，它就是一个派生结果，过期了重新算一遍就行，放 Redis 比放数据库简单多了。

### 12. Redis 过期时间设置策略【7 分】

**问题**
你们 Redis 里放的数据会设过期时间吗？一般怎么设？

**我的答案要点**
- 会设过期时间
- 访问量不大，一般设比较久，一周或一个月
- 在缓存雪崩那题里提到：设置时间可以加随机数，防止大量 key 同时过期

**评价**
- 优点：有实际业务背景支撑（低访问量可以存得久），防雪崩用随机 TTL 是正确思路。
- 不足：没有说明不同类型数据 TTL 的设置原则；「空缓存」的 TTL 应该比正常 TTL 短这点被面试官引导问出来后，答得也比较模糊（只说「比正式时间会短一些」）。

**参考答案要点**
- **正常数据 TTL**：根据数据更新频率和访问量设定；高频更新的数据 TTL 短（分钟级），低频更新的数据 TTL 长（小时/天级）；本项目气象计算结果更新周期长，设一周到一个月合理
- **空缓存 TTL（防穿透）**：null 值缓存要设置较短的 TTL（如 2～5 分钟），防止真正的数据入库后仍命中空缓存；不能和正常 TTL 一样长
- **防雪崩**：TTL = 基础值 + Random(0, 基础值 × 10%)，错开大量 key 同时到期
- **不同类型区别对待**：会话数据（30 分钟无操作过期）、计算缓存（时效性低可更长）、空值缓存（短 TTL）

**话术示例**
TTL 设置上主要分三种情况。正常的计算结果缓存，我们根据数据更新频率来定，气象数据变化慢，设一周到一个月没问题。空值缓存要单独处理，TTL 要明显比正常值短，比如 2 到 5 分钟，不然真正的数据进数据库了还是走空缓存。另外为了防缓存雪崩，TTL 不能全设成一个固定值，加个随机数进去，比如基础值加上 0 到 10% 的随机偏移，让大量 key 的过期时间错开。

### 15. 智能体架构设计（LangChain 流程编排）【8.5 分】

**问题**

- **节点设计**：① 地理编码工具调用（经纬度→地名）→ ② 要素路由（条件边，分发到不同处理链）→ ③ 各要素专属数据处理 Model + 工具（PNG 解析/JSON 计算）→ ④ 文案生成 → ⑤ 结构化输出（独立 Model，含 output parser）

**话术示例**

### 16. 手写代码：Redis 缓存保护（穿透/击穿/雪崩/一致性）【6.5 分】

**问题**
手写 Redis 分布式缓存一致性、并发控制、缓存保护（穿透、击穿、雪崩）、优雅降级策略，以及缓存预热和异步更新的实现。

**我的答案要点**
- 用伪代码完成了核心逻辑（具体 API 记不住）
- **缓存穿透**：查询到 null 值时存空缓存（设 5 分钟 TTL）
- **缓存击穿**：加分布式锁，锁住后查数据库并回写缓存，其他线程等待后重新查缓存
- **缓存雪崩**：TTL 加随机数，防止大量 key 同时过期
- **未完成**：一致性（先更新 DB 再删缓存）、缓存预热、异步更新、降级策略

**评价**
- 优点：三个缓存问题的核心思路是正确的；有实际项目做支撑，思路来自真实经验；诚实说明 API 记不住但思路有。
- 不足：代码量偏少（主要是伪代码），一致性、预热、降级策略完全没写；具体 API（Redisson、RLock 等）因为依赖 AI 辅助已经生疏；这是后端面试中最核心的考点之一，不完整会对印象有影响。

**参考答案要点**

**缓存穿透**（查不存在的 key 打穿数据库）：
- 方案一：空值缓存（key 不存在时存 `""` 或特殊标记，TTL 2～5 分钟）
- 方案二：布隆过滤器（BloomFilter）提前过滤不存在的 key，性能更好，无误判的 key 不打到数据库

**缓存击穿**（热点 key 过期后大量并发直打 DB）：
- 加互斥锁（Redisson `RLock`）：只有一个线程查数据库并回写缓存，其他线程等待后重新从缓存取
- 逻辑过期方案：value 中存过期时间字段，读到"逻辑过期"后异步刷新缓存，当前请求返回旧值（牺牲一致性换可用性）

**缓存雪崩**（大量 key 同时过期 / Redis 宕机）：
- TTL 加随机偏移：`TTL = base + random(0, base * 0.1)`
- Redis 高可用（主从复制 + 哨兵 / Cluster）
- 熔断降级：Redis 不可用时，降级为查数据库并做限流

**缓存一致性**（更新数据库后如何保持缓存一致）：
- **推荐方案（Cache Aside Pattern）**：先更新数据库，再删除缓存（而非更新缓存）
- 原因：更新缓存可能有并发写的竞态问题；删除缓存后下次查询重新从 DB 加载，保证数据最新
- 延迟双删：极端情况下（读写并发），更新 DB → 删缓存 → 延迟 N ms → 再删一次

**缓存预热**（应用启动时提前加载热点数据）：
- Spring Boot 中用 `@PostConstruct` 或实现 `ApplicationRunner` 在启动时查询热点数据写入 Redis
- 大规模场景：结合消息队列或定时任务批量预热

**优雅降级**（Redis 异常时的降级处理）：
- try-catch Redis 操作，异常时降级到直接查数据库
- 结合 Sentinel / Hystrix 做熔断，防止数据库被打垮
- 降级时可返回兜底数据或提示"服务繁忙"

**话术示例**
缓存三件套的思路是这样的。穿透是查一个数据库里根本没有的 key，解决方案有两种，一是把 null 结果也缓存进去，设个短 TTL，比如 5 分钟；二是用布隆过滤器，在查缓存之前先过滤掉一定不存在的 key，性能更好。

击穿是热点 key 到期后大量请求同时打到数据库，用互斥锁解决，Redisson 的 `tryLock`，只让一个线程进去查数据库并回写缓存，其他线程等一会儿再重新从缓存取。

雪崩是大量 key 同时到期，在设 TTL 的时候加一个随机偏移量，让过期时间错开。另外 Redis 本身要做高可用，主从加哨兵或者 Cluster。Redis 真的挂了就降级，走数据库，同时上限流防止把数据库打死。

一致性的话用 Cache Aside 模式，先更新数据库，再删缓存，不直接更新缓存，因为并发写的时候更新缓存容易有竞态。极端情况下可以做延迟双删，更新完再等一段时间删第二次。

### 17. 先更新数据库还是先更新缓存【7 分】

**问题**
更新数据时，是先更新数据库还是先更新/删除缓存？

**我的答案要点**
- 先更新数据库，再更新/删除缓存
- 这是我们项目的做法

**评价**
- 优点：操作顺序正确（先 DB 后 Cache）。
- 不足：没有解释为什么不能先更新缓存（会有并发脏数据问题）；没有区分「更新缓存」和「删除缓存」的差别；面试官问「你代码里写了吗」时承认没写，露出短板。

**参考答案要点**
- **先更新 DB，再删除缓存**（Cache Aside Pattern，推荐）
- **为什么删除而不是更新缓存**：并发写场景下，两个线程先后更新缓存，可能后写的反而是旧值，造成脏缓存；删除让下次查询重新从 DB 加载，保证最新
- **为什么不能先删缓存再更新 DB**：两步之间有时间窗口，其他线程可能读到旧 DB 数据并回写缓存，更新 DB 完成后缓存已经是脏的
- **延迟双删**：先删缓存 → 更新 DB → 延迟 N ms → 再删缓存，可减少时间窗口内的脏数据概率（适合最终一致性场景）

**话术示例**
我们用的是先更新数据库，再删除缓存，Cache Aside 模式。注意是删缓存而不是更新缓存，原因是并发写的场景下，两个线程同时更新缓存，可能后写的反而是旧值，造成脏缓存。删了让下次查询重新从数据库加载，保证数据一定是最新的。顺序上为什么先更新 DB 而不是先删缓存，是因为先删缓存再更新 DB 的话，两步中间有个时间窗口，别的线程可能读到旧 DB 数据又把旧值写回缓存，等 DB 更新完，缓存就变成脏的了。要求更强的一致性可以用延迟双删来进一步降低脏数据概率。
