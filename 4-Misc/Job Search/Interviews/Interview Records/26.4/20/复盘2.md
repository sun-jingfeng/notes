### 3. AI Agent 工作流编排展开讲 【8 分】

**问题**：你的工作流编排那块展开讲讲。

**我的答案要点**
- 用 LangGraph 自己搭工作流（业务垂直，工具都是自己绑的 Python 函数）
- 前端传参：气象要素、时间、地图经纬度范围、提示词
- Java 后端生成原始数据路径，再将路径 + 气象要素 + 提示词 + 经纬度传给智能体微服务
- 工作流节点顺序：
  1. 地名转换节点（调工具将经纬度转为地名，供文案使用）
  2. 按气象要素路由（不同要素数据格式不同）
  3. 数据还原节点：PNG → 读取栅格数据；JSON → 计算矩阵；每种要素绑定独立模型
  4. 文案生成节点（统一节点）
  5. 结构化输出（硬编码格式，满足甲方排版要求）
- 包装成 HTTP 服务，通过 Nacos 注册到 Java 服务中

**评价**
- 优点：工作流节点描述清晰，技术决策（独立模型 + 气象要素路由）有合理理由；架构整体连贯。
- 不足：没有提到错误处理或重试机制；工具调用失败如何处理未提及；"地名转换工具"具体用什么 API 未说清。

**参考答案要点**
- 技术选型：LangGraph（Python）替代 Spring AI，原因是 Python AI 生态更成熟、工具链更丰富
- 整体链路：前端 → Java 后端（生成数据路径）→ Python 智能体微服务 → 结构化文案 → 返回前端
- 节点设计：地名转换 → 要素路由 → 数据还原（各要素独立模型绑定专属工具）→ 文案生成 → 结构化输出
- 多模型策略：每种气象要素绑定独立 LLM 实例 + 专属工具，避免工具冲突，提升垂直精度
- 服务化：FastAPI 包装，Nacos 注册，与 Java 服务无缝集成
- 补充可提：工具调用超时重试、流式输出（SSE）给前端

**话术示例**

> 工作流是用 LangGraph 自己搭的，选 Python 主要是 AI 生态比 Spring AI 成熟得多，工具绑定也更灵活。整体链路是：前端传气象要素、时间、经纬度和提示词给 Java，Java 拼出原始数据的存储路径，再把路径和参数一起传给 Python 智能体服务。
>
> 工作流的第一个节点是地名转换，因为前端传的只有经纬度，文案里需要具体地名，所以先调工具把经纬度转成地名。然后根据气象要素做路由，因为不同要素的数据格式不一样——有的是 PNG 栅格图，有的是 JSON 矩阵——所以我给每种要素单独声明了一个 LLM 实例，绑定各自专属的解析工具。数据还原之后进入统一的文案生成节点，最后做结构化输出——因为甲方对文案排版有要求，这部分用硬编码来保证格式固定。整个服务用 FastAPI 包装，通过 Nacos 注册到 Java 体系里。

### 4. RAG / 知识库了解 【6 分】

**问题**：有没有 RAG 相关经验？

**我的答案要点**
- 项目中未实际做 RAG
- 了解原理：先查外部知识库，把相关资料和提示词一起喂给模型，解决模型训练数据缺失问题
- 大模型本身只做"读文字→返回文字"，实时数据 / 私有数据需要额外工具或知识库

**评价**
- 优点：原理方向基本正确，能说清 RAG 解决的痛点。
- 不足：未提向量化（Embedding）与向量数据库；没有提到检索阶段（相似度计算、Top-K 召回）；表述较口语化，"知识库" 和 "工具" 概念略有混淆（RAG 是知识检索，不是工具调用）。

**参考答案要点**
- RAG = Retrieval-Augmented Generation，检索增强生成
- 核心流程：
  1. 离线阶段：将私有文档切块 → Embedding 模型向量化 → 存入向量数据库（如 Chroma、Milvus、Pinecone）
  2. 在线阶段：用户提问 → 同样向量化 → 在向量数据库做相似度检索（Top-K）→ 将检索到的片段 + 原始问题组合成 Prompt → 喂给 LLM → 生成答案
- 解决的问题：私有数据不在训练集中；实时数据无法直接进模型；减少幻觉（有据可查）
- RAG vs Fine-tuning：RAG 成本低、知识可实时更新；Fine-tuning 适合让模型掌握特定风格或能力

**话术示例**

> RAG 是检索增强生成，主要解决大模型训练数据不包含私有或实时数据的问题。核心分两个阶段：离线阶段把私有文档切块，用 Embedding 模型向量化后存到向量数据库；在线阶段用户提问时同样做向量化，然后在向量数据库里做相似度检索，取出最相关的几段内容，和原始问题一起拼成 Prompt 喂给大模型，让它基于这些上下文生成答案。这样大模型就有了外挂的知识库，答案更有依据，幻觉也更少。我们项目里没有用 RAG，但这套思路和我们用 LangGraph 绑工具的逻辑是互补的——工具适合结构化数据查询，RAG 适合非结构化文档检索。

### 12. 数据库性能优化 【7.5 分】

**问题**：数据库这块熟吗？说说看。

**我的答案要点**
- 整体思路：先压测定位性能瓶颈接口，再顺着日志查到业务层或数据库层
- 慢查询：通过 MySQL 慢查询日志找到慢 SQL
- 缓存层优化：Redis 缓存热数据，减少数据库查询次数
- 索引优化：针对慢查询设计合理索引，遵循最左前缀原则，避免前模糊匹配、不等值条件破坏索引
- 覆盖索引：让查询数据都在索引里，避免回表
- 深分页优化：使用游标分页（Keyset Pagination）替代 LIMIT OFFSET

**评价**
- 优点：思路清晰，从定位到优化有完整链路；覆盖索引和游标分页属于进阶知识点，加分项。
- 不足：没有提到 `EXPLAIN` 分析执行计划；没有提到 SQL 层面的优化（避免 SELECT \*、减少子查询等）；Redis 缓存策略（缓存穿透/击穿/雪崩）未涉及。

**参考答案要点**
- 定位：JMeter / Arthas 压测 → 慢查询日志 → `EXPLAIN` 分析执行计划（重点看 type、key、rows、Extra）
- 索引优化：联合索引遵循最左前缀、避免列上做函数运算、避免前模糊匹配
- 覆盖索引：`SELECT` 字段都在索引列中，避免回表（Extra 显示 Using index）
- 分页优化：深分页用游标分页（`WHERE id > last_id LIMIT n`），避免 `OFFSET` 扫描大量数据
- 缓存：Redis 缓存热数据，注意缓存穿透（空值缓存/布隆过滤器）、缓存击穿（分布式锁）、缓存雪崩（TTL 随机化）

**话术示例**

> 我的做法是先用压测工具找到慢接口，然后顺着日志看是业务层还是数据库层的问题。数据库层的话，先开慢查询日志找出慢 SQL，再用 EXPLAIN 看执行计划，重点看 type 是不是走了全表扫描，key 有没有用上索引。优化方向主要有几个：一是设计合理的联合索引，遵循最左前缀，避免前模糊匹配和列上做函数导致索引失效；二是用覆盖索引让查询数据都在索引里，避免回表；三是深分页的场景用游标分页替代 LIMIT OFFSET，避免扫描大量数据。再往前一层是缓存——用 Redis 缓存热数据，同时要处理好缓存穿透、击穿、雪崩的问题。
