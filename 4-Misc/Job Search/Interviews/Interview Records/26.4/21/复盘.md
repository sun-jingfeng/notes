### 1. 项目架构选型与从 0~1 落地（气象雷达监测系统）【8 分】

**问题**
作为项目负责人，当时如何选择项目架构和技术选型的？

**我的答案要点**
- 前端约束：旧项目必须复用，新旧共同组成新系统 → 选型在微前端 vs iframe（FM）之间比较
  - 同源部署，iframe 父子通信方便，无需手动处理样式隔离
  - 缓存 + 同步预加载解决 iframe 加载慢问题
  - 路由不同步可接受
  - 最终选 iframe，主要考虑开发效率
  - 实现：父子通信、共用登录系统、权限控制、统一明暗切换
- 后端：Spring Boot + Zipkin，单体起步；多省份复用需求出现后 → 共用逻辑抽公共微服务，各省独立微服务
- 性能难点：Redis 缓存 + 多线程并发计算 + Sentinel 熔断 + 备选策略
- 智能体：选 Python（LangChain + LangGraph）而非 Java 生态 → AI 生态 Python 更成熟；包装成 FastAPI，注册到 Nacos 与 Java 服务通信

**评价**
- 优点：前后端与智能体整体脉络清晰，选型理由有逻辑支撑，覆盖了决策背景、方案对比、后续优化
- 不足：微前端 vs iframe 的对比说得略宽泛，微前端的具体问题只提到样式；性能优化部分讲得较快、缺数据支撑

**参考答案要点**
- 前端选型：「同源 + 旧项目复用」场景下 iframe 比 qiankun 接入成本更低；通信方案（postMessage + window 全局对象挂载静态参数）；缓存解决加载慢
- 后端：单体 → 微服务拆分（共用 2/3 抽公共服务，差异 1/3 各自维护）
- 性能：Redis 缓存热点数据 + 线程池并发 + Sentinel 熔断降级
- 智能体：LangChain / LangGraph 编排工作流，FastAPI 暴露接口，Nacos 服务注册

**话术示例**
前端最大的约束是旧项目必须复用，新旧项目要在一个统一界面里共同展示。选型在微前端和 iframe 之间做了比较，我们是同源部署，通信成本低，也不需要手动处理微前端的样式隔离问题，iframe 本身的加载慢问题通过预加载加缓存解决了，最终选了 iframe。父子通信分两套：父项目在 window 上挂全局对象传静态参数（比如 token key），动态消息用 postMessage；还封了一个 TS 声明包发布到私有 npm，子项目统一安装，方便类型安全地扩展属性。后端从单体到微服务是因为多省份复用需求出现了，大概 2/3 逻辑是共用的，1/3 是各省个性化的，就把共用部分抽成公共微服务，各省单独维护自己的服务。后来公司大模型上线，我负责智能预警文案生成，选了 Python + LangChain + LangGraph，AI 生态 Python 更成熟，用 FastAPI 包成接口，注册到 Nacos 跟 Java 服务打通。

### 5. Vue2 vs Vue3 核心差异【8 分】

**问题**
介绍一下 Vue2 和 Vue3 之间最具突破性的差异。

**我的答案要点**
- 开发体验：Options API → Composition API，逻辑更聚合，可读性更好
- 响应式原理：Vue2 用 Object.defineProperty 递归转换（getter/setter），数组需重写方法；Vue3 用 Proxy，有懒代理效果，性能更好
- Diff 算法：Vue3 有静态提升，静态节点不参与 Diff 对比
- 配套工具：Pinia 代替 Vuex（语法简洁灵活），Vite 代替 webpack（原生 ESM + 浏览器缓存，HMR 极快）

**评价**
- 优点：覆盖开发体验、响应式、Diff 算法、配套工具四个维度，技术点扎实，对 Vue2 defineProperty 缺陷理解准确
- 不足：Vue3 响应式的「懒代理」描述不够精准（reactive 是深代理，shallowReactive 是浅代理，惰性体现在嵌套对象访问时才代理）；Diff 算法除静态提升外可补充 patch flag 和最长递增子序列优化

**参考答案要点**
- Composition API：同一逻辑的 data / computed / watch / methods 放一起，逻辑内聚，可抽 composable 复用
- 响应式：Vue2 defineProperty 初始化时递归全量转换，数组需重写 7 个方法（push/pop 等）；Vue3 Proxy 惰性——嵌套对象访问时才对子对象代理，无需全量递归
- Diff 优化：静态节点提升（hoistStatic）跳过对比；patch flag 标记动态绑定；列表 Diff 用最长递增子序列（LIS）减少节点移动次数
- Pinia vs Vuex：去掉 mutations，action 直接修改状态，TypeScript 类型推断更好
- Vite：开发时浏览器原生 ESM 按需编译 + HMR 精准更新；生产用 Rollup 打包

**话术示例**
Vue2 到 Vue3 最核心的变化是两块：响应式系统和 Composition API。响应式上，Vue2 用 Object.defineProperty 做递归转换，每个属性在初始化时都要加 getter/setter，深层对象开销大，数组还得重写 push、pop 这些方法，不能通过索引直接改值。Vue3 换成了 Proxy，最大的好处是惰性——嵌套对象不会在初始化时全部代理，等你真正访问到某个嵌套属性时才代理那一层，性能提升很明显。Composition API 是开发体验的核心变化，以前用 Options API，一个功能的数据、计算属性、方法分散在三个地方，组件大了要来回翻。现在用 Composition API 可以把同一功能的所有逻辑放在一起，还能抽成 composable 复用。Diff 算法 Vue3 也做了优化，静态节点会被提升，不参与每次更新的对比；还有 patch flag 精确标记哪些绑定是动态的，列表 Diff 用最长递增子序列减少节点移动。工具链上 Pinia 和 Vite 体验比 Vuex 和 webpack 好太多，Vite 利用浏览器原生 ESM，改一行代码只更新那一个模块，热更新几乎瞬时。

### 6. 微前端/父子项目集成挑战（通信、样式污染）【8 分】

**问题**
父子项目集成时，样式污染、登录状态同步等挑战是怎么处理的？

**我的答案要点**
- 登录状态同步：父项目在 window 上挂全局对象，存静态参数（token key 等），子项目用同样的 key 取 token；封了 TS 类型声明包发布私有 npm，子项目安装后类型安全地访问这些属性
- 动态消息通信：window.postMessage，例如子项目截图按钮触发父项目截图操作
- 样式污染（另一项目经历）：用 PostCSS 插件给所有 CSS 类加容器选择器前缀，屏蔽外部框架自带样式

**评价**
- 优点：通信方案清晰（静态 + 动态两套机制），TS 包的设计体现工程化思维，样式污染有具体解决手段
- 不足：样式污染处理方案表述略绕（可以直接说 `postcss-prefix-selector` 或 Tailwind prefix 配置）；如果面试官追问 qiankun 等框架的样式隔离机制，可补充 Shadow DOM 和 CSS Module 方案

**参考答案要点**
- 静态参数共享：window 全局对象挂载（token key / 主题配置等），封 `declare global` 类型声明包发布私有 npm，统一类型安全访问
- 动态通信：postMessage，子向父发消息触发父级操作（如截图）
- 样式隔离（同源 iframe）：iframe 天然隔离，不需额外处理
- Tailwind 样式污染处理：在 Tailwind config 配置 `prefix` 或用 `postcss-prefix-selector` 插件，给所有生成样式加容器选择器前缀，隔离框架自带样式
- 微前端框架（qiankun）：Shadow DOM 隔离或 CSS Module，手动处理全局样式污染

**话术示例**
父子通信分两层。静态参数，比如 token 存的 key、主题色配置这些，我在父项目的 window 上挂了一个全局对象，子项目用同样的 key 去取就行了。为了让 TypeScript 不报错，我写了一个 `declare global` 的类型声明包，发布到私有 npm，子项目装这个包之后访问这些属性就有类型提示了，我加一个属性也只需要更新这个包，通知其他同事升级一下就行。动态消息用 postMessage，比如截图按钮在子项目里，截图逻辑在父项目，子项目就 postMessage 发个事件给父项目来触发。样式污染这块，我们 iframe 方案本身是隔离的，不用处理。之前做另一个项目遇到过，引入的 UI 库把页面所有标签都加了样式，我用 `postcss-prefix-selector` 插件给所有样式加了一个外层容器选择器前缀，让我的样式优先级更高，把框架自带的覆盖掉了。

### 7. 线上崩溃/白屏监控与安全防护【6 分】

**问题**
子应用加载后如果某个节点报错导致白屏崩溃，你们是如何做线上监控、报警和防护的？

**我的答案要点**
- 当前公司：靠测试发现，没有线上监控系统
- 上家公司：用了 Sentry 做前端错误监控，报错后发短信通知
- （初始回答跑偏：答的是接口报错时显示空状态图，而非白屏崩溃防护）

**评价**
- 优点：能主动区分两家公司实际情况，诚实
- 不足：一开始答非所问，从接口空状态答到 Sentry；对监控工具的了解只停留在名字层面，缺乏 ErrorBoundary / 降级 UI / Feature Flag 等防护策略的描述

**参考答案要点**
- 运行时防护：React ErrorBoundary（或 Vue 的 `onErrorCaptured`）捕获渲染错误，展示降级 UI；iframe 方案可在父项目监听 iframe load / error 事件做兜底
- 入口保护：结合 Feature Flag / 配置平台动态关闭问题功能入口，避免用户重复触发崩溃
- 监控方案：Sentry（JS 错误捕获 + Source Map 反解 + 告警通知）；阿里云 ARMS、fundebug 是同类方案
- 核心指标：JS Error 率、崩溃率（Crash Rate）、白屏率（FCP 异常）
- 告警：设错误量阈值触发告警（钉钉 / 短信），快速定位版本

**话术示例**
白屏防护分两层来说。第一层是运行时防护，在 Vue 里用 `onErrorCaptured` 或者在 React 里用 ErrorBoundary 包住关键子模块，捕获渲染错误后展示降级 UI，不会让整个页面崩掉。如果是 iframe 方案，可以在父项目监听 iframe 的 load 和 error 事件做兜底处理。第二层是监控告警，我们用 Sentry，它能捕获前端的 JS 错误，配上 Source Map 可以直接定位到源码哪一行，同时设错误量阈值，超了就推钉钉或短信通知，能快速知道哪个版本引入的问题。如果是更进一步的防护，可以结合 Feature Flag 在配置平台动态关闭问题功能的入口，等修复完再开放，避免用户持续触发崩溃。

### 8. 对 AI 的看法与使用理念【8 分】

**问题**
对 AI 这个东西有什么看法或期待？

**我的答案要点**
- 程序员必须学会利用 AI 提效，否则开发效率差距太大
- 不能全托 AI：上下文太短，AI 只知道当下任务，长期全托容易积累隐患
- 解决方式：MCP + 提示词 + 私有化技术规范 AI 行为；任务拆解垂直化提问
- 程序员需具备验收 AI 产出的能力

**评价**
- 优点：观点有层次（用但不依赖），提到 MCP 和提示词工程等具体手段，对 AI 局限性（上下文短）分析到位
- 不足：可以补充「用 AI 做什么、不用 AI 做什么」的边界判断，让回答更具体

**参考答案要点**
- AI 是提效工具而非替代品：样板代码、静态页面还原、接口对接等重复性工作交给 AI，架构决策、核心链路、组件设计自己把控
- 规范 AI 行为：MCP 工具 + 项目级提示词（.cursorrules / system prompt）约束 AI 上下文
- 任务拆解：任务越垂直，AI 产出质量越高；避免大而全的提问
- 验收能力：AI 产出必须经过人工 review，具备判断质量的能力才能真正驾驭 AI

**话术示例**
AI 是必须用的，不用的话开发效率差距很大。但怎么用是关键。AI 最大的局限是上下文太短，它只知道当下这个任务，不了解整个项目的历史和架构决策，如果全部交给 AI，项目到后期会越来越多隐藏问题。我的做法是：架构设计、核心链路、关键组件这些我自己来，样板代码、静态页面还原、接口对接这些重复性的工作给 AI 做，做完我看一下质量没问题就提交。为了让 AI 产出更稳定，我会给每类任务积累固定的提示词，也会用 MCP 和项目级配置文件来约束它的行为，让它输出符合我们项目规范的代码。任务拆得越垂直，AI 的输出质量越高，大而全的需求直接扔给它容易翻车。

### 9. AI 在工作中的实际占比【8 分】

**问题**
近一两年工作中 AI 的使用占比大概是多少？

**我的答案要点**
- 前年：几乎 0%，只用 Copilot 代码补全
- 去年开始：公司推动 AI 提效，自己主动尝试各种工具（ChatGPT、Claude 等）
- 现在：AI 产出代码约 75%，剩余 25% 自己写（项目基础架构、组件拆分、关键链路）
- 积累了针对不同任务类型的提示词模板

**评价**
- 优点：数字具体（75%），边界划分清晰，有持续积累的意识
- 不足：可以补一句工具选型的演化路径，体现对 AI 工具的横向了解

**参考答案要点**
- 演化路径：Copilot 代码补全 → ChatGPT / Claude 问答辅助 → 任务级提示词 + MCP → 系统化提效
- 当前比例：AI 产出 ~75% 代码，自己写 ~25%（架构 / 核心链路 / 组件拆分）
- 工作流：任务拆解 → 垂直提问 → AI 产出 → 人工 review → 提交

**话术示例**
前年我基本只用 Copilot 的代码补全，AI 占比几乎是 0。去年公司开始推 AI 提效，我就开始系统地去试各种工具，ChatGPT、Claude 都用过，慢慢摸出了自己的一套用法。现在我的代码里大概 75% 是 AI 产出的，主要是样板代码、静态页面还原、接口层这些。剩下 25% 我自己写，主要是项目基础架构、关键业务链路、组件拆分设计这些。每类任务我都积累了对应的提示词模板，让 AI 产出更符合项目规范，review 成本也低很多。
