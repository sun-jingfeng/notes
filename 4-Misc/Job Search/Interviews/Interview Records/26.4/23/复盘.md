### 5. 最有挑战的技术问题（性能优化） 【9 分】

**问题**
在你做前端这几年，遇到过最有挑战性的技术问题是什么？

**我的答案要点**
- 性能优化是最有挑战的，业务实现相对简单，2 年后基本都能做到
- **案例一：色斑图联播加载慢**
  - 场景：时间轴上十几个时间点，每秒播一张 100～300 KB 的 PNG 气象色斑图
  - 网速慢时会有卡顿
  - 方案：强制缓存（因为历史气象数据不会改变）
  - 写了一个组合式函数，参数是响应式的时间数组和气象要素；参数变化时提前用 fetch 请求一遍触发强制缓存；如果缓存过程中参数变了就中断之前的缓存任务，重新缓存新数据；结果通过返回值暴露给调用方
- **案例二：色斑图计算导致页面卡死 2 秒**
  - 场景：后端返回数组数据，前端计算矩阵再生成色斑图，45 帧图一生成，页面卡死 2 秒
  - 用 Performance 面板定位到一段连续 2 秒的长火焰图，找到具体代码位置
  - 方案：纯数学计算，迁移到 Web Worker，用 postMessage 把结果传回主线程

**评价**
- 优点：两个案例都有完整的"场景 → 问题 → 分析 → 方案"闭环；Performance 面板定位卡顿的方法有说服力；强制缓存的选型理由（数据不可变）解释得很到位。
- 不足：案例一可以补充"为什么不用协商缓存"的对比；案例二可以提一下任务切片（requestAnimationFrame/scheduler）作为 Worker 不可用时的备选方案。

**参考答案要点**
- 前端性能两个核心：加载速度慢 + 运行时卡顿
- 加载速度：懒加载、按需加载、缓存预加载（强制缓存/协商缓存分场景）
- 运行时卡顿：JS 单线程，浏览器每帧 ~16.7ms，宏任务超时就掉帧
  - 纯计算：Web Worker + postMessage
  - 涉及 DOM：requestAnimationFrame + 任务切片（时间切片 / scheduler）
- Performance 面板：火焰图定位长任务，再对应到源码

**话术示例**
我觉得最有挑战的是性能这块。业务实现做到一两年基本都没什么难度，但性能想做到极致还是得花心思。

举两个我做过的例子。第一个是色斑图联播的加载慢问题。我们产品会把一段时间内的气象降水做成动画，时间轴上大概十几个时间点，每秒播一张 PNG，每张图 100 到 300 KB，网速慢的时候会卡。我判断历史气象数据一旦生成就不会再变，所以用的是强制缓存。我写了一个组合式函数，接受响应式的时间数组和气象要素作为参数，参数一变就提前把对应的图片 fetch 一遍触发缓存，如果参数中途再改就终止之前的缓存任务重新缓存新的，结果通过返回值给调用方直接取，播放时基本不再有卡顿。

第二个是一个计算量很大的色斑图生成，后端返回数组，前端自己算矩阵再生成图，生成 45 帧时页面会卡死整整 2 秒。我用 Performance 面板一看，火焰图里有一段连续 2 秒的长任务，顺着代码位置找到了是一个数学计算函数。因为是纯计算不涉及 DOM，直接把它挪到 Web Worker 里跑，用 postMessage 把结果传回主线程，页面卡死问题就解决了。

### 6. Web Worker 大数据传输（Transferable Objects） 【3 分】【错】

**问题**
主线程和 Worker 线程之间要传递大批量数据（比如几个 GB 的文件），怎么实现秒传？

**错误点**：不知道 Transferable Objects（可转移对象）和 SharedArrayBuffer，误以为应走流式传输或写入硬盘再传路径。

**我的答案要点**
- 想到流式传输，但认为满足不了"秒传"
- 认为大文件不应读入内存，而是存到硬盘，把访问地址传给主线程
- 在浏览器中可以用 IndexedDB 存大文件，再传引用

**评价**
- 优点：方向上想到了"避免全量读入内存"是合理直觉。
- 不足：没有提到 Transferable Objects 和 SharedArrayBuffer，这两个才是浏览器中 Worker 大数据传输的核心机制；IndexedDB 存文件再传引用会引入额外的读写延迟，并非最优。

**参考答案要点**
- **Transferable Objects（可转移对象）**：ArrayBuffer、MessagePort、ImageBitmap 等，通过 `postMessage(data, [transfer])` 传递时发生所有权转移，零拷贝，原始线程中的引用失效，速度极快
- **SharedArrayBuffer**：主线程与 Worker 共享同一块内存，通过 `Atomics` API 做并发安全的读写，适合需要双向实时访问的大数据场景；注意需要跨域隔离头（COOP + COEP）
- 二者对比：Transferable 是单次转移（所有权独占），SharedArrayBuffer 是持续共享（双方都能读写）

**话术示例**
浏览器里主线程和 Worker 之间传大数据，有两个专门的机制。一个是可转移对象（Transferable Objects），比如 ArrayBuffer，在 postMessage 时把它放进第二个参数的 transfer 数组里，浏览器会直接转移这块内存的所有权，不做拷贝，速度非常快，但转移后主线程那边的引用就失效了。另一个是 SharedArrayBuffer，主线程和 Worker 共用同一块内存，谁都能直接读写，配合 Atomics API 做并发控制，适合需要双方持续访问的场景，不过要求页面开启跨域隔离（需要设置 COOP 和 COEP 响应头）。如果是几个 GB 的二进制数据一次性传过去，用 ArrayBuffer + Transferable 是最合适的。

### 7. iframe 通信方式 【7.5 分】

**问题**
iframe 和父页面之间如何通信？

**我的答案要点**
- 同源部署可以共享本地存储，也能访问对方的 window 属性
- 通信方式：window 属性共享、localStorage / sessionStorage、postMessage
- 实际用法：静态配置（项目启动前就固定的数据）写到子项目的 window 对象，配了 TS 类型声明让子项目有类型提示
- 主题、暗亮切换标志位用 localStorage 共享，保证 key 一致即可互通
- 动态操作（如截图功能：按钮在子项目，操作在父项目）用 postMessage，子项目写监听器响应

**评价**
- 优点：覆盖了三种方式，并结合实际场景说明了各自的适用场合，逻辑清晰；TS 类型声明这个细节有加分。
- 不足：没有提到非同源情况下 postMessage 的跨域注意事项（origin 校验）；localStorage 在跨域 iframe 下不共享。

**参考答案要点**
- **同源**：window.parent / window.frames 直接访问，localStorage/sessionStorage 共享，postMessage
- **非同源**：只能用 postMessage，接收方需校验 `event.origin` 防止恶意消息
- postMessage 格式：`targetWindow.postMessage(data, targetOrigin)`，接收方 `window.addEventListener('message', handler)`
- 安全性：严格校验 origin，不接受通配符 `*`

**话术示例**
同源部署的话，父子 iframe 之间通信比较灵活，有三种主要方式。

第一种是 window 属性共享，比如一些项目启动前就固定的配置数据，我会直接挂到子项目的 window 对象上，同时配上 TypeScript 的类型声明文件，子项目就能有类型提示，不会报错。

第二种是 localStorage，像主题、暗亮模式这种全局状态，只要父子项目用的 key 一致，localStorage 里一改大家都能读到，适合这种持久化的标志位。

第三种是 postMessage，适合动态操作，比如截图按钮在子项目里，但截图逻辑在父项目里，子项目就在 window 上注册 message 监听器，父项目用 postMessage 触发就行。

非同源的话只能用 postMessage，但要注意在接收方校验 event.origin，防止接收到恶意页面发来的消息。

### 9. CSS box-sizing 属性 【8 分】

**问题**
CSS 里 box-sizing 有哪些值，作用是什么？

**我的答案要点**
- 两个值：content-box（默认）和 border-box
- border-box：边框和 padding 计入总宽度，盒子实际占据的空间就是 width 设置的值
- content-box：border 和 padding 不计入 width，实际占用空间需要自己额外计算

**评价**
- 优点：两个值和核心区别都说清楚了，表述方式直观。
- 不足：可以补充"全局重置为 border-box 是行业标配做法"。

**参考答案要点**
- `content-box`（默认）：width/height 只包含内容区，border + padding 在外扩
- `border-box`：width/height 包含内容区 + padding + border，布局更直观
- 工程实践：通常在全局 CSS 中 `*, *::before, *::after { box-sizing: border-box }`

**话术示例**
box-sizing 有两个值。默认是 content-box，就是 width 只算内容区，border 和 padding 是额外加上去的，实际占位要自己加起来算。改成 border-box 之后，width 就是这个盒子最终占的总宽，border 和 padding 都包含在里面，布局直观很多，不容易出现宽度算错的问题，所以工程上一般都会在全局把它重置为 border-box。

- 作用：解决 margin 塌陷问题（父子 margin 合并）

**评价**
- 优点：核心概念（独立渲染、互不影响）和典型应用场景（margin 塌陷）说到了。
- 不足：触发条件只提了 overflow: hidden，漏掉了 float、position: absolute/fixed、display: inline-block/flex/grid 等；也没有提 BFC 还能用于清除浮动（包含浮动子元素）。

**参考答案要点**
- **概念**：Block Formatting Context，独立的块级格式化上下文，内部子元素布局不影响外部
- **触发条件**：
  - `overflow` 不为 `visible`（hidden / auto / scroll）
  - `float` 不为 `none`
  - `position: absolute` 或 `fixed`
  - `display: inline-block / flex / grid / table-cell` 等
- **作用**：
  - 解决父子 margin 塌陷（给父元素触发 BFC）
  - 清除浮动（父元素包含浮动子元素时，触发 BFC 可让父元素高度撑开）
  - 阻止元素被浮动元素覆盖（自适应两栏布局）

**话术示例**
BFC 就是块级格式化上下文，可以理解为一个独立的布局区域，内部的元素和外部互不影响。触发 BFC 的方式有很多：overflow 设置成 hidden、auto、scroll 都可以；float 不为 none；position 设置成 absolute 或 fixed；display 设置成 flex、grid、inline-block 等也都能触发。BFC 主要有几个用处：一是解决父子 margin 塌陷，给父元素触发 BFC 就行；二是清除浮动，父元素触发 BFC 后高度会包含浮动的子元素；三是做自适应两栏布局，让非浮动的那一侧触发 BFC，就不会被浮动元素覆盖。

### 11. CSS em 与 rem 的区别 【8 分】

**问题**
CSS 里 em 和 rem 的区别是什么？

**我的答案要点**
- `em`：相对于父元素的字体大小
- `rem`：相对于 html 根元素的字体大小
- rem 布局：移动端适配常用，设置 html font-size，所有尺寸用 rem，适配时只改根字体大小，或用媒体查询自动切换

**评价**
- 优点：概念准确，rem 布局的移动端适配思路说到位了。

**参考答案要点**

### 12. CSS visibility: hidden 与 display: none 的区别 【7.5 分】

**问题**
CSS 里 visibility 和 display: none 的区别是什么？

**我的答案要点**
- `display: none`：节点完全不占位置
- `visibility: hidden`：占位（保留空间），但不可见，事件也没有了

**评价**
- 优点：占位与否的核心区别说准确了，事件也一并提到了。
- 不足：`opacity: 0` 作为第三种对比方式值得补充（占位、不可见、但事件仍然可以触发）；另外 visibility: hidden 对子元素的影响（子元素可以设置 visibility: visible 显示出来）这个细节可以补充。

**参考答案要点**
- `display: none`：元素从渲染树中移除，不占位，无法交互，会触发回流
- `visibility: hidden`：占位，不可见，无法交互（pointer-events 被禁用），不触发回流；子元素可单独设置 `visibility: visible` 来显示
- `opacity: 0`：占位，不可见，但可以接收事件（点击仍然触发）
- 三者对比是前端常见面试点

**话术示例**
`display: none` 是彻底把元素从渲染树里移除，不占任何空间，也不能交互，改变它会触发回流。`visibility: hidden` 是占位但不显示，也没办法点击，不会触发回流；有个细节是子元素可以单独设置 `visibility: visible` 来让自己显示出来，这点和 display: none 不一样。还有个常被拿来对比的是 `opacity: 0`，它也占位、也不可见，但事件还是正常触发的，所以透明但可点击的场景用 opacity。

### 13. CSS 选择器 +、>、~ 的区别 【6 分】

**问题**
CSS 选择器里 +、>、~ 各有什么用，区别是什么？

**我的答案要点**
- `+`：相邻兄弟选择器；列表从第二个元素开始加左边距常用此写法
- `>`：直接子元素选择器；加 > 防止类名重复时样式冲突
- `~`：不太熟悉

**评价**
- 优点：+ 和 > 的使用场景举例实际，说明是真正在用的。
- 不足：~ 通用兄弟选择器不清楚，是盲区，需要补全。

**参考答案要点**

- `>`（直接子代选择器）：只选直接子元素，不穿透嵌套层级，避免样式污染深层同名类

### 14. JavaScript 原型链 【7.5 分】

**问题**
解释一下原型链，怎么理解？

**我的答案要点**
- 找属性时，对象自身没有就去原型链（`__proto__`）上找，原型链上还没有就真没有，最终到 `Object.prototype` 为 null
- 每个对象都有 `__proto__` 指向其原型对象，原型对象也有自己的原型
- 原型对象上有 `constructor` 属性指向构造函数，构造函数的实例就是这个对象
- ES6 的 class 出现之前，类继承是通过把一个对象的 prototype 设置成另一个对象来实现

**评价**
- 优点：属性查找链、`__proto__`、constructor 的关系都说清楚了，ES5 vs ES6 的对比有加分。
- 不足：`__proto__` 和 `prototype` 的区别可以说得更清晰（`__proto__` 是实例属性，`prototype` 是函数属性）；`Object.create(null)` 创建无原型链对象可以作为扩展点。

**参考答案要点**
- 每个对象都有内部槽 `[[Prototype]]`（`__proto__` 是对它的访问器），指向其原型对象
- 属性查找：沿原型链逐级查找，直到 `Object.prototype.__proto__ === null` 为止
- `prototype`：函数专属属性，`new` 调用时新对象的 `__proto__` 指向该函数的 `prototype`
- `constructor`：`prototype` 对象上的属性，指回构造函数本身
- 继承：将子类构造函数的 `prototype` 赋值为父类实例，即可实现原型链继承；ES6 class 语法糖底层仍是此机制

**话术示例**
原型链本质上是 JavaScript 的属性查找机制。当我们访问一个对象的属性时，如果对象自身没有，就会沿着 `__proto__` 去原型对象上找，原型对象还没有就继续往上找，一直到 `Object.prototype`，再往上就是 null，找不到就返回 undefined。

每个对象的 `__proto__` 指向它的原型，而函数有一个 `prototype` 属性，用 new 调用时，新创建的实例的 `__proto__` 就会指向这个函数的 `prototype`。`prototype` 对象上还有一个 `constructor` 属性，指回构造函数本身，形成一个闭环。

ES6 class 出现之前，继承就是通过把子类构造函数的 `prototype` 赋值为父类的实例来实现的，ES6 的 class 只是语法糖，底层机制还是这一套。

### 15. for...in 与原型链属性可枚举性（代码题） 【5 分】【错】

**问题**
（面试官发代码到聊天框）这段代码的输出结果是什么？（代码涉及 for...in 遍历一个对象，该对象原型链上挂了属性 c，自身有属性 a、b）

**错误点**：初始判断认为 for...in 只输出 a、b，不输出原型链上的 c，与实际相反。

**我的答案要点**
- for...in 遍历键，for...of 遍历值
- Object.keys() 不输出原型链属性，for...in 会（后来面试官确认，对原型链属性 c 会被输出）
- enumerable 属性描述符控制属性是否可被遍历；系统内置属性 enumerable 为 false（不可枚举），控制台中显示颜色不同

**评价**
- 优点：Object.defineProperty 和 enumerable 的解释是正确的，且对控制台可枚举/不可枚举属性颜色不同有实际观察。
- 不足：初始预测 c 不会被 for...in 遍历到，判断有误；应先确认原型链属性的 enumerable 是 true 还是 false，再判断。

**参考答案要点**
- `for...in`：遍历对象**自身及原型链上所有可枚举（enumerable: true）属性**的键
- `Object.keys()`：只遍历自身可枚举属性的键，不包含原型链
- `Object.getOwnPropertyNames()`：自身所有属性键（含不可枚举），不含原型链
- `Object.defineProperty` 中 `enumerable: false` → for...in 遍历不到；自定义挂在原型上且 enumerable 默认为 true 的属性 → for...in 会遍历到
- 区分方法：`Object.prototype.hasOwnProperty(key)` 判断是否为自身属性

**话术示例**
for...in 遍历的是对象自身及原型链上所有 enumerable 为 true 的属性键。如果在原型对象上用 `obj.prototype.c = xxx` 直接赋值的方式挂属性，enumerable 默认是 true，for...in 就会遍历到 c。如果用 Object.defineProperty 挂的且设了 enumerable: false，才遍历不到。Object.keys() 则只返回自身的可枚举属性键，不包含原型链上的。所以 for...in 和 Object.keys() 的核心区别就是有没有包含继承属性。实际开发中，for...in 遍历对象时通常配合 hasOwnProperty 过滤掉原型链属性，只处理自身属性。

### 16. 防抖与节流的区别 【9 分】

**问题**
防抖和节流的区别是什么？

**我的答案要点**
- 防抖（debounce）：类似王者荣耀回城，触发后等待指定时间再执行，等待期间再次触发就重置计时，直到等待时间结束才执行
- 节流（throttle）：类似坦克炮的冷却时间，执行一次后冷却期内无论触发多少次都不执行，冷却结束才能再次触发

**评价**
- 优点：两个比喻非常形象且准确，表达清晰，面试中容易让人记住。
- 不足：可以补充各自的典型使用场景（防抖：搜索框输入、窗口 resize；节流：scroll 事件、按钮点击防重复提交）。

**参考答案要点**
- **防抖**：最后一次触发后等待 n ms 再执行，等待期间重新触发就重置计时；适合"操作结束后才执行"的场景（搜索联想、resize 完成后计算布局）
- **节流**：第一次触发后 n ms 内不再执行，n ms 后才能再次触发；适合"高频事件降频执行"的场景（scroll 进度条、拖拽、按钮防重复点击）

**话术示例**
防抖就像王者荣耀里的回城，按下回城键开始读条，如果读条期间被打断了，就要重新读条，必须完整等完倒计时才能回城。在代码里就是每次触发都重置计时器，只有停止触发后等够指定时间才真正执行，比如搜索框输入停顿后再请求接口。

节流就像坦克大炮有冷却时间，发射一炮之后必须等冷却结束才能再发，冷却期间的触发全部丢弃。在代码里就是第一次触发后锁住一段时间，时间内再触发不响应，比如 scroll 事件监听，1s 内只执行一次计算，避免频繁触发造成性能问题。

### 17. Promise 静态方法与实例方法 【7 分】

**问题**
Promise 有哪些静态方法，哪些实例方法，常用哪些？

**我的答案要点**
- 静态方法：`Promise.all`、`Promise.allSettled`、`Promise.any`、`Promise.race`
- 最常用：`Promise.all`；`Promise.allSettled` 偶尔用
- `all` vs `allSettled`：all 一个失败则整体失败；allSettled 无论成功失败都返回所有结果
- 静态方法还有 `Promise.resolve`、`Promise.reject`（直接生成已决议/已拒绝的 Promise）
- 实例方法：`.then`（最常用，第一个参数成功回调，第二个参数失败回调）、`.catch`、`.finally`
- 实际开发多用 async/await 替代 .then 链

**评价**
- 优点：四个静态方法全部列出，all vs allSettled 区别说准确，实例方法覆盖完整。
- 不足：`Promise.any` 和 `Promise.race` 的区别可以说一下（any 等第一个成功，race 等第一个完成不论成败）；`.then` 的返回值（仍是 Promise，支持链式调用）可以补充。

**参考答案要点**
- 静态方法：
  - `Promise.all(arr)`：全部成功才 resolve，一个失败就整体 reject
  - `Promise.allSettled(arr)`：全部完成后返回每个结果的 `{status, value/reason}`，不短路
  - `Promise.race(arr)`：第一个完成（无论成功失败）就返回
  - `Promise.any(arr)`：第一个成功就返回；全部失败才 reject（AggregateError）
  - `Promise.resolve(v)` / `Promise.reject(e)`：快速创建已决议/已拒绝的 Promise
- 实例方法：
  - `.then(onFulfilled, onRejected)`：处理成功/失败，返回新 Promise
  - `.catch(onRejected)`：等同于 `.then(null, onRejected)`
  - `.finally(onFinally)`：不管结果如何都执行，常用于关闭 loading

**话术示例**
Promise 的静态方法主要有四个：`all`、`allSettled`、`race`、`any`。`all` 是全部成功才 resolve，一个失败就整体 reject，适合多个接口都必须成功才能继续的场景。`allSettled` 是等所有 Promise 都结束，不管成功失败，把每个结果都返回给你，适合允许部分失败的并行请求。`race` 是谁先完成返回谁，不论成功失败。`any` 是谁先成功返回谁，全部失败才 reject。另外 `Promise.resolve` 和 `Promise.reject` 可以快速创建已决议的 Promise。

实例方法主要是 `.then`、`.catch`、`.finally`。then 有两个参数，第一个是成功回调，第二个是失败回调，返回的还是 Promise 所以可以链式调用。catch 等同于 then 的第二个参数的简写，finally 不管成功失败都执行，常用来关 loading 状态。实际开发中我更多用 async/await，比 then 链可读性好很多。

### 18. 浏览器 Observer API 【5.5 分】

**问题**
浏览器的 Observer API 你用过哪些，在什么场景下用的？

**我的答案要点**
- 用过 IntersectionObserver：观测元素是否进入视口，做图片懒加载
- 自定义指令：把图片 src 放到指令值中而不给 src 赋值，IntersectionObserver 监测到元素进入视口后才把值赋给 src 触发加载
- 其他 Observer 没用过

**评价**
- 优点：IntersectionObserver 的使用方式和配合自定义指令的思路都正确，贴合实际工程。
- 不足：MutationObserver、ResizeObserver、PerformanceObserver 都是常见的 Observer，可以了解基本用途。

**参考答案要点**
- **IntersectionObserver**：监听元素与视口（或指定容器）的交叉状态，常用于懒加载、无限滚动、曝光埋点
- **MutationObserver**：监听 DOM 树的变化（子节点增删、属性变化、文本变化），替代已废弃的 MutationEvent
- **ResizeObserver**：监听元素尺寸变化，比 window resize 事件更精准，常用于响应式组件
- **PerformanceObserver**：监听性能条目（LCP、FID、CLS 等），可用于性能监控上报

**话术示例**
我用得最多的是 IntersectionObserver，主要做图片懒加载。做法是自定义一个 Vue 指令，把图片真实 src 存到指令的 binding.value 里，img 标签本身不给 src 赋值，然后用 IntersectionObserver 监听这个 img 元素，一旦它出现在视口里，就把 binding.value 赋给 src，触发加载。这样首屏只加载视口内的图片，性能好很多。

另外还有几个 Observer 我了解但没怎么用：MutationObserver 监听 DOM 树变化，ResizeObserver 监听元素尺寸变化比 window resize 更精准，PerformanceObserver 可以采集 LCP、CLS 这些性能指标，做性能监控上报。

### 19. script 标签的 async 与 defer 属性 【5 分】【错】

**问题**
script 标签里的 async 和 defer 属性各起什么作用？

**错误点**：把 async 描述为"同步执行"，用词与实际含义相反；async 是异步加载、加载完立即执行（不等 HTML 解析完毕），并非同步。

**我的答案要点**
- 没有这两个属性时，每个 script 标签都是一个宏任务，按序加载并阻塞 HTML 解析
- async：文件拉取成功后立刻执行（称为"同步执行"——用词有误）
- defer：拉取后先不执行，等主线程执行完再统一执行

**评价**
- 优点：defer 的执行时机（HTML 解析完后）方向正确；提到了无属性时阻塞 HTML 解析的问题。
- 不足：async 说成"同步执行"是关键错误，应为"异步加载、加载完毕立即执行、不保证顺序、会打断 HTML 解析"；defer 的"按顺序"特性没有提到。

**参考答案要点**
- **无属性**：同步，下载时阻塞 HTML 解析，下载并执行完再继续解析
- **async**：异步并行下载，下载完**立即执行**（中断 HTML 解析），多个 async 脚本执行顺序不保证，适合无依赖的独立脚本（如埋点）
- **defer**：异步并行下载，**等 HTML 全部解析完成后**，按脚本出现的顺序依次执行，适合有依赖关系的脚本

**话术示例**
script 标签默认是同步的，浏览器解析到它就停下来，等脚本下载并执行完才继续解析 HTML，会阻塞页面渲染。

加 `async` 之后，脚本会和 HTML 解析并行下载，但下载完成后会立即执行，执行期间会打断 HTML 解析。多个 async 脚本之间的执行顺序不固定，谁先下完谁先执行，适合没有依赖关系的独立脚本，比如统计埋点。

加 `defer` 之后，也是和 HTML 解析并行下载，但下载完不立即执行，而是等 HTML 全部解析完之后，再按照脚本在文档中出现的顺序依次执行。适合有依赖关系的脚本，现代打包的 script 标签通常都加 defer。

### 20. Vue ref 与 reactive 的区别 【6 分】

**问题**
Vue 中 ref 和 reactive 的核心区别是什么？

**我的答案要点**
- ref 可以引用任何类型的值，访问时需要 `.value`
- reactive 主要用于对象类型，直接访问属性，不需要 `.value`
- 深层响应式处理方面，reactive 天然深响应，ref 内部对对象也会用 reactive 包装
- 实际项目中主要用 VueUse 里的 API，较少直接用原生 ref/reactive

**评价**
- 优点：访问方式的区别（.value）说到了，实际使用习惯也如实说明。
- 不足：ref 和 reactive 的核心设计差异（ref 可以被替换整个值、reactive 的响应性会丢失问题）没有说清楚；reactive 解构后响应性丢失是一个重要的坑。

**参考答案要点**
- `ref`：接受任意类型，返回 `{value}` 包装对象；JS 中访问需 `.value`，模板中自动解包；整个对象可以被替换且保持响应性
- `reactive`：只接受对象/数组/Map/Set；不需要 `.value`；直接解构会丢失响应性（需用 `toRefs` 或 `storeToRefs`）；不能被整体替换
- 实践建议：统一用 ref（Vue 官方也建议，更一致）；组合式函数返回的响应式数据用 `toRefs` 解构

**话术示例**
ref 可以接受任何类型的值，在 JS 里访问需要加 `.value`，模板里会自动解包。reactive 只能接受对象类型，属性可以直接访问，不需要 `.value`，但有个坑是直接解构后响应性会丢失，必须用 toRefs 来保持。还有一个区别是 ref 可以整体重新赋值，响应性不会断；reactive 不能这样整体替换，否则原来的响应式引用就失效了。Vue 官方现在推荐统一用 ref，代码风格更一致。

React 里的 Suspense 是怎么感知到子元素里 Promise 状态变化的？

**参考答案要点**
- `<Suspense>` 捕获子树中抛出的 Promise（throw a Promise），当子组件在渲染期间抛出 Promise 时，Suspense 捕获并显示 fallback 内容，Promise resolve 后切换显示真实子内容

### 24. 检测组件重渲染原因的 Hook 设计 【5 分】

**问题**
如果让你写一个自定义 Hook，用来检测一个组件重新渲染的原因，你会怎么写？

**我的答案要点**
- 配合生命周期和响应数据进行检测
- 把组件的参数（props）传进 Hook，在重新渲染时打印

**评价**
- 优点：方向是对的，知道要拿 props/state 做比较。
- 不足：没有说出核心实现：用 useRef 保存上一次的 props/state，在 useEffect 里对比前后变化，打印出哪个字段发生了变化。

**参考答案要点**
```tsx
function useWhyDidYouUpdate(name: string, props: Record<string, any>) {
  const prevProps = useRef<Record<string, any>>({})
  useEffect(() => {
    const changedProps: Record<string, {prev: any; curr: any}> = {}
    for (const key of Object.keys(props)) {
      if (prevProps.current[key] !== props[key]) {
        changedProps[key] = { prev: prevProps.current[key], curr: props[key] }
      }
    }
    if (Object.keys(changedProps).length > 0) {
      console.log(`[${name}] re-render caused by:`, changedProps)
    }
    prevProps.current = props
  })
}
```
- 核心：useRef 保存上一轮的 props，每次渲染后用 useEffect 做对比
- 组件里调用：`useWhyDidYouUpdate('MyComponent', { count, name, ... })`
- 也可以扩展到 state（从 useReducer 或 useState 拿到状态快照一并传入）

**话术示例**
核心思路是用 useRef 保存上一次渲染时的 props 快照，然后在 useEffect 里对比本次 props 和上次的差异，把发生了变化的字段打印出来。Hook 接受一个名字参数方便区分是哪个组件，以及一个 props 对象；每次 useEffect 跑完就把当前 props 存到 ref 里作为下一次比较的基准。这样每次组件重渲染，控制台就会打出"哪个字段的值从什么变成了什么"，很方便定位性能问题。

### 25. TypeScript type 与 interface 的区别 【8 分】

**问题**
TypeScript 里 type 和 interface 有什么区别？

**我的答案要点**
- interface 支持声明合并（同名 interface 自动合并属性），type 不支持重名声明
- type 支持联合类型（|），可以做枚举型类型约束
- 实际开发中以 type 为主，interface 在需要合并的场景才用

**评价**
- 优点：最核心的区别（声明合并）准确；实际使用场景有自己的判断标准。
- 不足：type 能做交叉类型（&）、条件类型、映射类型等，这些 interface 不支持；interface 可以被 implements（类可以实现接口），type 对于一般对象也可以 implements 但约定上用 interface；extends 的用法也可以提一下。

**参考答案要点**
- **interface**：只能描述对象/函数/类结构；支持声明合并（同名自动合并）；支持 `extends` 继承其他 interface；可被 `implements`
- **type**：可以描述任意类型（原始类型、联合、交叉、元组、条件类型、映射类型等）；不支持声明合并；更灵活，适合复杂类型组合
- **选择原则**：对外暴露的 API 类型、第三方可扩展的类型用 interface（方便 augmentation）；组件 props、内部工具类型、联合/交叉组合用 type

**话术示例**
interface 只能描述对象或函数的结构，但它支持声明合并，两个同名的 interface 会自动把属性合并在一起，这在需要扩展第三方类型定义的时候很有用。type 可以描述任意类型，包括原始类型、联合类型、交叉类型、条件类型、映射类型等，灵活得多，但不支持同名合并。

实际用的话，我的习惯是默认用 type，因为大多数场景都不需要合并；组件 props、函数参数类型都用 type。只有在需要声明合并，比如给第三方库扩充类型，或者定义可以被类 implements 的接口契约时，才用 interface。

### 26. TypeScript 联合类型与交叉类型的区别 【4 分】【错】

**问题**
TypeScript 里联合类型（|）和交叉类型（&）的使用有什么区别？

**错误点**：认为两个对象类型交叉（A & B）的结果是"取共有属性"，实际是取所有属性的合并（两者都有）。

**我的答案要点**
- 联合类型（|）：类型可以是其中任意一种，常用于字符串字面量枚举（如气象要素类型）
- 交叉类型（&）：以为是两个对象类型的共有属性（**错误**）

**评价**
- 优点：联合类型的应用场景（字符串字面量枚举）举例好，实用。
- 不足：交叉类型的理解相反了：A & B 要求对象同时满足 A 和 B 的所有属性，结果是属性的合并（并集），而不是取交集（共有属性）。

**参考答案要点**
- **联合类型（A | B）**：值可以是 A 或 B 其中之一；访问成员时只能访问两者共有的属性（类型保护后可访问各自属性）
- **交叉类型（A & B）**：值必须同时满足 A 和 B 的所有约束；对象类型的 & 结果包含 A 和 B 的所有属性，是属性的合集
- 口诀：联合是"或"，访问时取交集成员；交叉是"且"，结果是属性并集
- 实用场景：用 & 混入（Mixin）多个类型，比如 `type WithId<T> = T & { id: string }`

**话术示例**
联合类型是"或"的关系，A | B 表示值是 A 或 B 之一，常用来约束参数范围，比如气象要素只能是"降雨"、"大风"、"冰雹"这几个字符串字面量。

交叉类型是"且"的关系，A & B 表示值必须同时满足 A 和 B，对象类型 & 的结果是把两边的属性全部合并到一起，是两个类型属性的并集，不是取共有属性。这个容易记反，可以这样记：交叉类型要求"同时是 A 又是 B"，自然得有 A 的所有属性，也得有 B 的所有属性，结果属性只多不少。常见用法是用 & 给类型混入通用字段，比如给任意类型加一个 id 字段。

### 27. TypeScript as const 的作用 【7 分】

**问题**
在 TypeScript 里声明一个常量对象时，后面加 as const 起什么作用？

**我的答案要点**
- 防止类型被拓宽（widening），让类型保持为字面量类型
- 类似 JS 中的 Object.freeze，但是是 TS 类型层面的约束
- 不想写复杂类型推断时可以用 as const 快速锁定

**评价**
- 优点：核心作用（防止类型拓宽）和对比 Object.freeze 的类比都是准确的。
- 不足：没有说"所有属性变为 readonly"这个效果；对数组的影响（变为 readonly 元组，长度固定）可以补充。

**参考答案要点**
- 效果：① 所有属性变为 `readonly`；② 类型推断为字面量类型而非宽泛类型（如 `'left'` 而非 `string`）；③ 数组推断为 readonly 元组
- 对比：`Object.freeze` 是运行时限制，`as const` 是编译时限制，二者可以同时用
- 典型场景：枚举替代品（路由 path、事件名常量对象）；用 `typeof obj[keyof typeof obj]` 获取所有值的联合类型

**话术示例**
`as const` 主要有两个效果：一是让所有属性变成 readonly；二是把类型推断收窄为字面量类型，比如 `{ dir: 'left' }` 不加 as const 时 dir 的类型是 string，加了之后就是字面量类型 `'left'`。

对数组同样有效，加了 as const 后数组变成 readonly 元组，长度和每个位置的类型都固定了。

和 Object.freeze 的区别是，Object.freeze 是运行时冻结，as const 是编译时的类型约束，两者不冲突，可以同时用。常见用法是定义常量对象替代枚举，然后用 `typeof obj[keyof typeof obj]` 提取所有值的联合类型，既安全又方便。
