### 2. CSS 明暗主题切换（父子项目）【7 分】

**问题**：简历里有一个 CSS 主题切换，父子项目的明暗主题切换是怎么做的？

**我的答案要点**
- 单项目切换：
  - `<html>` 标签上加 `dark` class 作为标志位
  - CSS 写两套变量：`:root { --xxx }` 和 `:root.dark { --xxx }`，通过 class 驱动
  - 状态管理（Pinia）存 `theme` 字段，用于驱动图片、文案等不能纯靠 CSS 变量处理的内容
  - localStorage 持久化标志位
- 父子项目同步：提到了要同步，但未展开具体方案

**评价**
- 优点：单项目切换描述完整，分层清晰（CSS 变量层 + 状态层 + 持久化层）。
- 不足：父子项目同步方案完全未展开，是被问的核心点；Canvas 相关的主题切换未涉及。

**参考答案要点**
- 单项目：`html.dark` class 驱动 CSS 变量切换 + Pinia `theme` 字段驱动动态内容 + `localStorage` 持久化
- 父子项目同步（微前端场景）：
  - 父应用切换主题时，通过**全局事件总线**（`window.dispatchEvent` 自定义事件）或**共享状态通道**（qiankun 的 `initGlobalState`）通知子应用
  - 子应用监听事件后同步更新自身 `html.dark` class 和内部状态
  - 也可用 `localStorage` 监听（`storage` 事件）作为兜底：子应用监听 `window.addEventListener('storage', ...)` 感知 key 变化后同步

**话术示例**

> 主题切换分两层来说。单项目这边，我们在 `<html>` 标签上维护一个 `dark` class，CSS 里写两套变量：`:root` 一套默认亮色，`:root.dark` 一套暗色，这样只要切换 class，CSS 自动响应。对于图片、文案这类 CSS 变量覆盖不到的动态内容，在 Pinia 里存一个 `theme` 字段来驱动。同时在 `localStorage` 里持久化，刷新页面也能还原主题。
>
> 父子项目同步我们用的是 qiankun 的 `initGlobalState`，父应用切换主题时更新全局状态，子应用通过 `onGlobalStateChange` 回调感知，再同步更新自身的 `html.dark` class 和内部 Pinia 状态。如果不用 qiankun，也可以用 `window.dispatchEvent` 抛自定义事件，或者靠 `localStorage` 的 `storage` 事件做跨页面监听。

### 4. 长任务优化（Web Worker & 生成器函数）【8 分】

**问题**：简历里写到用生成器函数和 Web Worker 优化长任务，能具体说一下吗？

**我的答案要点**
- 业务场景：读取数据 → 生成色盘图 → 插入文档，生成时页面卡住约两秒
- 用 Performance 面板 + 火焰图定位到一段两秒的 JS 执行，找到具体代码是一个颜色差值计算算法
- 长任务优化两种方式：Web Worker 或生成器函数（迭代器），根据场景选择
- 该场景是纯数学计算，不涉及 DOM 操作，选 Web Worker
- 把算法移到 Worker 线程单独执行，用 `postMessage` 将结果返回主线程

**评价**
- 优点：流程完整，从问题发现（性能工具）到方案选型（Worker vs 生成器）到落地都讲清楚了。
- 不足：生成器函数方案没有展开说，面试官对两者选型标准也追问了（见下题）。

**参考答案要点**
- 定位方法：Performance 面板火焰图，找到长红色任务块，向下定位具体函数
- 两种优化方案：
  - **Web Worker**：把任务移出主线程，适合纯计算、无 DOM 依赖的场景；缺点是数据需可结构化克隆（无 DOM 引用、无循环引用），通信有序列化开销
  - **生成器函数 + scheduler**：把长任务切片，每次 `yield` 让出主线程，适合需要访问 DOM 或需要与主线程实时交互的场景；通常配合 `requestIdleCallback` 或 `MessageChannel` 实现调度
- 本场景选 Web Worker：纯计算、结果通过 `postMessage` 返回，没有 DOM 访问需求

**话术示例**

> 当时测试反馈一个页面生成色盘图时卡住两秒。我用浏览器 Performance 面板查了一下，火焰图里看到一段很长的 JS 执行块，点进去定位到源码，是一个颜色差值算法跑了两秒。
>
> 长任务一般两种处理方式：一是 Web Worker，把任务放到独立线程；二是用生成器函数配合调度器，每次 yield 让出主线程。选哪种主要看要不要操作 DOM。这个算法是纯数学计算，不需要 DOM，而且参数都是结构化数据，可以直接 postMessage 传进去，所以选了 Web Worker。算完之后 Worker 把结果 postMessage 回主线程，主线程再渲染，卡顿完全消失了。

### 5. Web Worker vs 主线程的选择标准 【8 分】

**问题**：什么情况下放到 Web Worker，什么情况下留在主线程？

**我的答案要点**
- 核心判断：是否需要访问 DOM
- 如果每次任务循环都需要更新 DOM（如动画），要留在主线程
- 如果不需要 DOM，且传递的参数是结构化数据（无循环引用），用 Web Worker

**评价**
- 优点：核心标准清晰，DOM 依赖这个维度抓到了关键。
- 不足：未提及 Worker 数据传输的序列化开销限制（大型 ArrayBuffer 可用 Transferable Objects 零拷贝传输）；未提及调试便利性等工程因素。

**参考答案要点**
- 用 Web Worker 的条件：
  - 不需要访问 DOM
  - 传递的数据可结构化克隆（无 DOM 节点、无函数引用、无循环引用）
  - 任务耗时较长（>50ms），会明显阻塞主线程
  - 典型场景：图像处理、加密计算、数据解析、大数组排序
- 留在主线程 + 生成器/scheduler 的场景：
  - 任务需要访问 DOM 或 BOM
  - 需要与 React/Vue 渲染周期配合（如逐步渲染列表）
  - 数据量小、通信开销大于收益
- Transferable Objects：传大型 `ArrayBuffer`、`ImageBitmap` 时可使用零拷贝传输，避免序列化瓶颈

**话术示例**

> 选择标准主要看两点：一是需不需要操作 DOM，二是数据能不能结构化传输。
>
> 需要 DOM 的任务没办法放 Worker，只能留在主线程，这时可以用生成器函数配合 requestIdleCallback 或 MessageChannel 做任务切片，每切一次让浏览器有机会渲染一帧。不需要 DOM、参数也是普通对象或基础类型、没有循环引用，就可以扔给 Worker。如果传的是大型 ArrayBuffer 或 ImageBitmap，可以用 Transferable Objects 做零拷贝传输，避免序列化带来的额外耗时。

### 7. Vite 为什么比较快 【6.5 分】【错】

**问题**：项目性能优化用到了 Vite，Vite 为什么比较快？

**错误点**：将 Rollup 描述为"基于某种语言写的、比 JS 快几十倍"，混淆了 Rollup 和 esbuild 的角色。

**我的答案要点**
- 围绕按需编译和浏览器缓存展开
- 浏览器原生支持 ES 模块，Vite 开发服务器把源码按模块单独处理，通过 HTTP 请求 + 浏览器缓存传递
- 打包时用 Rollup，说 Rollup 基于某种语言写的比 webpack 快几十倍（错误点）

**评价**
- 优点：核心原理（ESM + 按需编译 + 浏览器缓存）表述正确。
- 不足：将 esbuild 的特性（Go 语言实现，速度极快）误归到 Rollup 上；没有区分开发模式和生产打包的两套不同机制。

**参考答案要点**
- **开发模式**：
  - 不打包，直接利用浏览器原生 **ES Modules (ESM)** 加载模块
  - 使用 **esbuild**（Go 语言编写，比传统 JS bundler 快 10~100 倍）做依赖预构建（pre-bundling），将 node_modules 里的 CommonJS 转成 ESM，并合并碎片化小模块
  - HMR 粒度极细，只更新变化的单个模块，配合浏览器模块缓存极速热更
- **生产打包**：
  - 使用 **Rollup**（JS 实现，但 tree-shaking 优秀）生成优化后的静态资源
  - 也可切换 esbuild 或 Oxc/SWC 等 Rust/Go 工具链进一步提速
- Rollup 和 esbuild 是两个不同工具，esbuild 才是"用 Go 写的、快几十倍"

**话术示例**

> Vite 快主要分两块，开发模式和生产打包不一样。
>
> 开发模式下 Vite 不打包，直接利用浏览器的原生 ES Modules 能力，源码改了哪个文件就只处理那一个，浏览器直接请求，还能利用模块缓存，所以启动和热更都非常快。同时 Vite 会用 esbuild 做依赖预构建，把 node_modules 里的 CommonJS 包统一转成 ESM。esbuild 是用 Go 写的，速度比传统 JS bundler 快了一两个数量级，所以首次依赖预构建也很快。
>
> 生产打包用的是 Rollup，它在 tree-shaking 上做得很好，能打出体积较小的包。Rollup 和 esbuild 是两个不同的工具，不要混。

### 8. Vue2 vs Vue3 的提升 【8 分】

**问题**：Vue3 相比 Vue2 主要有哪些提升和优化？

**我的答案要点**
- **响应式升级**：Vue2 用 `Object.defineProperty` 递归转换，数组用重写原型方法；存在无法检测数组 index 赋值和动态新增属性的缺陷（需用 `$set`/`$delete`）
- **Vue3 用 `Proxy`**：13 个 trap，代理普通类型用 getter/setter，代理深层对象时懒代理（只在访问时才递归代理），性能更好
- **Diff 算法优化**：静态节点提升（不涉及动态数据的 DOM 直接跳过对比）
- **组合式 API**：代替 Options API，功能相关的数据、侦听器、函数写在一起，可维护性好
- **按需引入 + 自动引入**：打包体积更小
- **生态升级**：Vuex → Pinia，Webpack → Vite，速度更快、更灵活

**评价**
- 优点：覆盖面广，响应式原理、Diff、API 风格、生态都提到了，技术细节基本准确。
- 不足：Diff 优化的描述中只提到了静态节点提升（hoistStatic），未提到 patchFlags；`Proxy` 的 trap 数量说"13 个"不是关键点，更关键的是懒代理的思路。

**参考答案要点**
- **响应式**：`Proxy` 替换 `Object.defineProperty`，解决数组 index 和动态属性无法触发响应的问题；深层对象懒代理，只在访问时才递归，性能更好
- **Diff 优化**：
  - **静态节点提升（hoistStatic）**：编译阶段把不含响应数据的节点提升到渲染函数外，复用 VNode，跳过 diff
  - **patchFlags**：编译阶段给动态节点打标记，运行时只对比标记的部分（如只有文本变了就只更新文本），跳过全量 props 对比
- **组合式 API**：逻辑复用能力大幅提升，可提取为 composable，Options API 里难以按业务复用
- **Fragment / Teleport / Suspense** 等新组件特性
- **TypeScript 支持**：Vue3 源码用 TS 重写，类型推导更完善

**话术示例**

> Vue3 对比 Vue2 的改进主要在三块。
>
> 响应式方面，Vue2 用 Object.defineProperty 递归转换，有两个著名缺陷：数组下标赋值和动态新增属性都不能触发响应，要用 $set。Vue3 换成 Proxy，直接代理整个对象，这两个问题都没了。深层对象是懒代理，访问到哪层才代理哪层，不再一开始就递归全部，性能更好。
>
> Diff 方面，Vue3 在编译阶段做了两个优化：一是静态节点提升，不含动态数据的节点生成一次 VNode 复用，diff 时直接跳过；二是 patchFlags，动态节点按变化类型打标记，运行时只对比有标记的属性，不做全量对比。
>
> 开发体验方面，组合式 API 让一个功能的数据、侦听器、函数可以写在一起，可以提取成 composable 复用，比 Options API 的 mixin 清晰很多。再加上 Vite 和 Pinia 替代了 Webpack 和 Vuex，整个开发体验提升明显。

### 9. Vue 项目跨域解决方案 【8 分】

**问题**：在 Vue 项目里怎么解决跨域问题？

**我的答案要点**
- 开发环境：Vite/Webpack DevServer 的代理服务器配置
- 生产环境：CORS，后端配响应头，允许前端域名
- Canvas 图片跨域：设置 `crossOrigin` 属性

**评价**
- 优点：覆盖三个典型场景，开发 / 生产 / Canvas 区分清楚。
- 不足：CORS 响应头可以说得更具体（`Access-Control-Allow-Origin`）；生产环境也可以通过 Nginx 反向代理处理跨域，未提及。

**参考答案要点**
- **开发环境**：`vite.config` 中配 `server.proxy`，将 `/api/*` 代理到后端地址；代理请求在 Node.js 层发出，没有浏览器同源限制
- **生产环境**：
  - 方案一：后端配 CORS 响应头（`Access-Control-Allow-Origin: https://xxx.com` + 必要的预检响应头），推荐只允许具体域名，不用 `*`
  - 方案二：Nginx 反向代理，前端和 API 统一在同一域名下，彻底消除跨域
- **Canvas 图片跨域**：给 `<img>` 设置 `crossOrigin="anonymous"`，并确保图片服务器返回允许跨域的响应头，否则 `canvas.toDataURL()` 会报 tainted canvas 错误

**话术示例**

> 跨域分开发和生产两个阶段。开发阶段用 Vite 的 proxy 配置，把 /api 的请求代理到后端地址，代理是在 Node.js 里发出的，没有浏览器同源限制，前端感知不到跨域。
>
> 生产阶段主要两种方案：一是后端配 CORS 响应头，加 Access-Control-Allow-Origin 指定前端域名就可以，注意不要用 * 通配符，安全性差；二是用 Nginx 做反向代理，让前端和 API 在同一域名下，跨域问题从根本上消除。
>
> 还有一种特殊情况是 Canvas 引用外部图片，需要给 img 标签加 crossOrigin="anonymous"，同时图片服务器也要允许跨域，不然 canvas.toDataURL 会报污染错误。

### 10. SSR 了解吗 【7.5 分】

**问题**：SSR 你有了解过吗？

**我的答案要点**
- SSR（服务端渲染） vs SSG（静态生成） vs SPA 的区分
- SPA：HTML 壳 + JS 生成 DOM，首屏慢，SEO 不友好，不占服务器资源
- SSR：服务端渲染 HTML 返回，首屏快，SEO 友好，占服务器资源
- 框架：React → Next.js，Vue → Nuxt.js
- Next.js 现在升级成全栈框架，可以写 Server Action / API Route

**评价**
- 优点：三种模式区分清晰，框架对应准确。
- 不足：Next.js/Nuxt 的渲染模式（ISR 增量静态再生）没提；水合（Hydration）过程没说；"不占用服务器资源"只是 SPA 的特点，不是缺陷，表述稍显混乱。

**参考答案要点**
- **SPA**：JS 在客户端生成 DOM，首屏白屏、SEO 差，但服务器只需托管静态文件
- **SSR**：每次请求服务端动态渲染完整 HTML 返回，首屏快、SEO 好，但有服务器计算成本和 TTFB 开销；客户端拿到 HTML 后还需**水合（Hydration）**使页面变为可交互
- **SSG**：构建时生成静态 HTML，TTFB 最快，适合内容不频繁变化的页面（博客、文档）；配合 **ISR**（增量静态再生）可定时重新生成
- 框架：Next.js（React）、Nuxt.js（Vue），两者均支持混合模式（部分页面 SSR，部分 SSG）

**话术示例**

> SSR 是服务端渲染，服务器接到请求后直接返回渲染好的 HTML，浏览器不用等 JS 执行完才有内容，所以首屏很快，也对 SEO 友好。拿到 HTML 后客户端还会走一次水合，把事件绑上去让页面可交互。代价是有服务器计算压力和 TTFB 开销。
>
> 与之对应的是 SSG，构建时就把所有 HTML 生成好，访问时直接返回静态文件，速度最快，适合内容变化不频繁的页面；如果内容需要定期更新，可以配合 ISR 定时增量重新生成。SPA 就是传统方式，全靠客户端 JS 渲染，首屏慢、SEO 差，但服务器只需要托管静态文件，运维成本低。
>
> React 这边主要用 Next.js，Vue 用 Nuxt.js，两个框架都支持在同一项目里混合 SSR 和 SSG。

- **渲染层**：
  - `transform`/`opacity` 替代触发重排的属性，利用 GPU 合成层
  - CSS 动画 + `requestAnimationFrame` 保证帧率
  - 减少强制同步布局（避免读写交替触发 layout thrashing）
- **框架层**：`shallowRef`/`shallowReactive` 避免深层响应式开销；`v-memo`/`shouldComponentUpdate` 减少重渲染
- **加载层**：路由懒加载、图片懒加载（Intersection Observer）、预加载（`<link rel="preload">`）
- **列表优化**：虚拟列表（只渲染可视区 DOM）
- **网络层**：合理的 HTTP 缓存（Cache-Control）、资源压缩（gzip/br）、CDN、HTTP/2 多路复用

**话术示例**

### 13. 气象 AI 检测：流式返回 vs 完整返回 【8 分】

**问题**：气象预警 AI 检测和前端交互用的是流式返回还是完整返回？

**我的答案要点**
- 当前场景是完整返回（一次性接口）
- 也了解流式返回：
  - **WebSocket**（全双工）：适合持续双向通信，如雷达图实时数据、聊天室；前后端各有对应 SDK
  - **SSE / fetch 流式**：适合服务端单向推送，有明确结束标志（如 AI 逐 token 输出），前端用 `fetch` 的 `ReadableStream` 消费，后端 Java/Python 有对应流式输出 API

**评价**
- 优点：主动扩展了解的内容，清晰区分了两类流式方案及适用场景，技术准确。
- 不足：未提到 SSE（Server-Sent Events）作为独立协议（基于 HTTP，比 WebSocket 更轻量），前端用 `EventSource` API 消费；直接说"fetch 流式"是正确但更底层的描述。

**参考答案要点**
- **完整返回**：普通 HTTP 请求，等结果全部生成后一次性返回，适合耗时短、结果确定的场景
- **SSE（Server-Sent Events）**：基于 HTTP 的服务端单向推送，前端用 `EventSource` API 或 `fetch` + `ReadableStream`；有明确结束事件；AI 逐 token 输出的标准方案；后端 Spring MVC 的 `SseEmitter` 或 Python 的 `StreamingResponse`

**话术示例**

> 我们气象预警这个场景处理时间短，用的是普通完整返回，等模型生成好再一次性返回。
>
> 如果需要流式，主要分两种。一种是 SSE，基于 HTTP，服务端单向推送，前端用 EventSource API 监听，有明确的结束事件，很适合 AI 逐 token 输出这种场景；后端 Spring 里用 SseEmitter，Python 用 StreamingResponse，都很容易对接。另一种是 WebSocket，全双工、持久连接，适合需要客户端也持续发消息的场景，比如雷达图一直在接收服务端推来的实时数据，或者聊天室。WebSocket 比 SSE 重一些，如果只是服务端往客户端推，SSE 够用。

### 14. 权限端到端设计 【8 分】

**问题**：用户登录后触发一个敏感操作，从点击到最终触发经过了哪些权限校验（前端 / 网关 / 下游）？

**我的答案要点**
- **前端**：
  - 页面级：动态路由注册，登录时获取用户权限，递归注册有权限的路由；无权限的路由不注册
  - 元素级：`v-if` 绑定权限标志位，控制按钮/操作是否展示
- **后端**：
  - 用 Spring Security，接口上配注解标注所需权限标志
  - 请求进来时，网关（过滤器）从 token 中解析用户 ID，查权限配置，注册到 SecurityContext
  - Spring Security 自动拦截，若用户权限标志不满足接口要求，返回 403

**评价**
- 优点：前端和后端两层都覆盖了，动态路由 + 元素级 + 接口级三个粒度清晰。
- 不足：网关层（如 Spring Cloud Gateway）的统一鉴权没有单独说明（与 Spring Security 在应用层的鉴权是不同位置）；Token 有效性验证（JWT 签名校验）没提；接口注解叫 `@PreAuthorize`，当时说忘了。

**参考答案要点**
- **前端（体验层）**：
  - 动态路由：登录后根据权限标志递归生成可访问路由表，通过 `router.addRoute` 注册；无权限路由不存在，URL 直接访问也会 404 或重定向
  - 元素级：自定义指令 `v-permission` 或 `v-if` 控制按钮渲染
- **网关层**（如 Gateway/Nginx）：
  - 所有请求先到网关，验证 JWT 签名和有效期
  - 解析 token，提取用户 ID 并附加到请求头，透传给下游服务
- **应用层**（Spring Security）：
  - 使用 `@PreAuthorize("hasAuthority('xxx')")` 注解标注接口所需权限
  - 过滤器链从请求头取用户 ID，查库得到角色和权限集合，写入 `SecurityContextHolder`
  - 框架自动对比 SecurityContext 中的权限与接口注解要求，不满足则返回 403
- 前端校验是**体验保护**（防止误操作），后端校验是**安全保障**（真正的权限边界）

**话术示例**

> 权限校验分三层。
>
> 前端是体验层，主要防止用户误操作。页面级别用动态路由，登录时拿到用户权限标志，递归判断哪些路由有权限，通过 router.addRoute 动态注册，没权限的路由根本不存在。元素级别用 v-if 或自定义指令，有权限才渲染按钮。
>
> 网关层是第一道真正的安全防线，所有请求先到 Spring Cloud Gateway，验证 JWT 签名和有效期，通过后解析 token 里的用户 ID，附加到请求头透传给下游微服务。
>
> 应用层用 Spring Security，接口上加 @PreAuthorize 注解配置所需权限标志。请求到达时，过滤器从请求头取用户 ID，查数据库得到角色和权限集合，写入 SecurityContextHolder，框架自动对比，权限不足直接返回 403。前端那层是用户体验层，真正的安全边界在后端。

### 15. RBAC 了解吗 【8 分】

**问题**：你知道 RBAC 吗？

**我的答案要点**
- Role-Based Access Control，基于角色的权限控制
- 三张表：权限表（存权限标志）、角色表（存角色）、用户-角色关联表
- 给角色分配权限，再把角色分配给用户
- 查询时合并该用户所有角色的权限标志位，得到一个完整的权限数组

**评价**
- 优点：概念定义准确，表结构设计描述清晰，流程完整。
- 不足：可以补充 RBAC1（角色继承）的概念；"权限标志"本质是什么（permission code、resource+action 等）没有展开。

**参考答案要点**
- **RBAC 核心模型**：User → Role → Permission 三层映射
- **表结构（标准五表）**：用户表、角色表、权限表（permission code 或 resource:action）、用户-角色关联表、角色-权限关联表
- **查询流程**：通过用户 ID → 查关联角色 → 展开角色对应的所有权限 → 合并去重得到权限集合
- **扩展**：RBAC1 支持角色继承（如"超级管理员"继承"普通管理员"的所有权限）；实际项目中权限粒度可细化到 resource + action（如 `user:delete`）

**话术示例**

> RBAC 是基于角色的权限控制，是目前几乎所有权限系统的基础模型。核心是三层：用户、角色、权限。实现上通常是五张表：用户表、角色表、权限表，加上用户和角色的关联表、角色和权限的关联表。
>
> 流程是：先把权限分配给角色，再把角色分配给用户。查权限时通过用户 ID 查出他的所有角色，再展开每个角色对应的权限列表，合并去重，就得到这个用户完整的权限集合。权限的粒度可以是简单的功能 code，也可以细化成 resource:action 的形式，比如 user:delete 表示删除用户这个操作的权限。

### 16. 数据库分库分表 【6 分】

**问题**：数据库分库分表了解吗？

**我的答案要点**
- 了解概念，但实际项目数据量小，没有用过
- 数据量特别大时（单表几十万条）不适合放一张表，需要拆分成多表多库存储

**评价**
- 优点：诚实说明无实战经验。
- 不足：概念层面只停在"拆表"的表象，没有说清楚分库分表的具体策略（水平分表 vs 垂直分表）、分片键选择、跨库查询问题等核心知识点。"几十万条"触发分表的数据量阈值偏低，通常是千万级别。

**参考答案要点**
- **水平分表（分片）**：同一表结构，按分片键（如 user_id 取模）把数据分到多个库/表；解决单表数据量过大（通常千万级以上）导致的查询性能下降
- **垂直分库**：按业务模块拆库（如用户库、订单库），降低单库负载，符合微服务拆分原则
- **垂直分表**：把一张宽表拆成多张窄表（常用列和不常用列分离），减少单次查询 IO
- **挑战**：
  - 跨库/跨表 JOIN 变复杂，通常在应用层组装
  - 分布式事务（需要 Seata 等方案）
  - 全局唯一 ID（雪花算法 Snowflake）
- 常用中间件：ShardingSphere、MyCat

**话术示例**

> 分库分表我了解思路但没有实战过。分库分表主要分两个维度。垂直方向是按业务拆，比如把用户相关的表放用户库，订单相关的表放订单库，这和微服务的边界是一致的；或者把一张大宽表拆成常用列和不常用列两张窄表，减少查询时的 IO。
>
> 水平方向是按数据量拆，同一张表的数据按分片键（比如用户 ID 取模）分散到多张表或多个库里，通常单表数据量到千万级以上才考虑。挑战主要是三个：跨表 JOIN 要在应用层手动拼，分布式事务要用 Seata 这类框架，还有全局唯一 ID 不能用自增主键，要用雪花算法。中间件的话一般用 ShardingSphere。

### 17. 算法题：无重复字符的最长子串 【7 分】

**问题**：给定一个字符串，找出其中不含有重复字符的最长子串的长度。（例：`"dvdf"` → 3）

**我的答案要点**
- 思路：滑动窗口，维护一个临时子串，循环遍历
- 遇到重复字符时清零，以当前字符为起点重新开始
- 初始提交存在 bug：`"dvdf"` 返回 2 而非 3（指针移动逻辑过于简单粗暴）
- 被指出 bug 后修复：改为找到重复字符在窗口中的位置，移动左指针至其后一位

**评价**
- 优点：思路正确（滑动窗口），能在提示后快速定位并修复 bug。
- 不足：初版代码有 bug，说明对滑动窗口的左指针收缩逻辑理解不够精准；面试中需要经验证才发现错误，有减分。

  - 用 `Map` 存每个字符上次出现的索引
  - 遍历字符串，若当前字符在 Map 中存在且其索引 ≥ 左指针 `left`，则将 `left` 移动到 `map.get(char) + 1`
  - 更新 Map 中字符的最新位置，更新最大长度
  - 时间复杂度 O(n)，空间复杂度 O(min(m, n))（m 为字符集大小）
- 关键点：左指针不能倒退（`map.get(char) >= left` 这个判断必须有，否则处理 `"abba"` 之类的串时 left 会错误回退）

```javascript
function lengthOfLongestSubstring(s) {
    const map = new Map();
    let maxLen = 0;
    let left = 0;
    for (let right = 0; right < s.length; right++) {
        if (map.has(s[right]) && map.get(s[right]) >= left) {
            left = map.get(s[right]) + 1;
        }
        map.set(s[right], right);
        maxLen = Math.max(maxLen, right - left + 1);
    }
    return maxLen;
}
```

**话术示例**

> 这道题用滑动窗口，维护一个左右指针表示当前无重复子串的范围。用一个 Map 记录每个字符上次出现的下标。右指针依次往右扫，遇到当前字符在 Map 里有记录，而且那个下标大于等于 left，说明它在当前窗口内，就把 left 移到它的下一位，缩小窗口。注意 left 只能前进不能倒退，要加 `>= left` 的判断。每一步都更新 Map 里的位置，并记录最大窗口长度，最后返回即可。时间复杂度 O(n)。
