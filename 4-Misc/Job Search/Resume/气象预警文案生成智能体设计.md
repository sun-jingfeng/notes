# 气象预警文案生成智能体设计

> 只记录当前已经确定的方案，作为后续落地与面试讲解的统一口径。

***

## 一、功能定位

### 1.1 功能目标

**气象预警文案生成智能体** 用于在预警发布场景中，根据当前时间、选中的气象要素、地图当前视窗范围内的业务数据，自动生成可直接查看、复制、重新生成的预警文案。

这个功能不是通用聊天，也不是纯模板拼接，而是一个**业务型智能体能力**：

- 输入来自业务系统当前上下文
- 智能体负责补齐必要信息
- 输出为同步返回的预警文案结果

***

### 1.2 当前已拍板的总体方案

| 项目 | 已确定方案 |
| ---- | ---------- |
| **模型部署方式** | 大模型工程师负责私有化部署 |
| **模型接入方式** | 通过私有 SDK 调用，不直接对接公网 API |
| **智能体服务形态** | 单独拆分为 Python 微服务 |
| **原系统关系** | 原有 Java 微服务继续负责业务系统，新增 Python `agent-service` 负责智能体能力 |
| **返回方式** | 同步返回 |
| **前端体验** | 请求期间显示 Loading，返回后展示文案并支持复制 |
| **按钮交互** | 首次点击为“生成”，有结果后按钮变为“重新生成” |
| **地名获取方式** | 不手写算法，不让模型脑补，统一通过工具调用获取 |
| **数据传递方式** | Java 根据参数生成数据文件路径传给 agent-service，agent-service 自行读取数据并处理，处理结果存入 Redis |
| **智能体编排框架** | LangGraph，支持路由分支与多工具节点编排 |

***

## 二、系统落地形态

### 2.1 服务拆分

当前确定的落地形态如下：

    前端页面
        ↓
    Java 业务系统（原有微服务）
        ↓
    Python agent-service
        ↓
    私有部署大模型 + 私有 SDK
        ↓
    工具调用（业务工具 / 地名解析工具）

这个拆分方式适合已有微服务架构，原因如下：

- 不破坏原有 Java 业务系统主链路
- 智能体逻辑单独收敛到 `agent-service`
- 后续 Prompt、工具调用、工作流调整更方便
- 后续其他项目也可以复用这套智能体服务

***

### 2.2 各层职责

| 层级 | 主要职责 |
| ---- | -------- |
| **前端** | 收集当前时间、选中的气象要素、地图视窗经纬度范围、用户提示词，发起生成请求，展示结果 |
| **Java 业务系统** | 根据时间 + 气象要素生成数据文件路径，将文件路径 + 经纬度范围 + 气象要素 + 用户提示词转发给 agent-service，不直接读取或传输原始数据 |
| **Python agent-service** | 负责智能体编排（LangGraph）：经纬度转地名、要素路由、读取并处理数据文件、缓存处理结果、调用模型、结构化输出 |
| **Redis** | 缓存 agent-service 处理后的结构化数据，供重复参数请求复用 |
| **私有大模型** | 负责生成文案，不直接暴露给前端 |
| **工具层** | 负责经纬度转地名、数据文件读取与处理等确定性能力 |

***

## 三、模型接入方案

### 3.1 为什么定为私有部署

当前项目面向国企、军工等对数据敏感度较高的客户，因此模型方案优先采用**私有化部署**。

核心原因如下：

- 原始业务数据不出公网
- 更符合内网与保密场景要求
- 便于客户侧独立部署和运维
- 更容易结合权限、审计、调用留痕做合规控制

***

### 3.2 为什么定为私有 SDK

当前不采用“业务代码直接拼 HTTP 请求调用模型接口”的方式，而是定为：

**大模型工程师完成模型私有部署，并封装私有 SDK；智能体服务通过私有 SDK 调用模型。**

这个方案的好处如下：

| 优点 | 说明 |
| ---- | ---- |
| **接入简单** | 智能体服务像调用普通模型 SDK 一样调用 |
| **屏蔽细节** | 无需关注底层模型服务的 HTTP 协议细节 |
| **便于切换模型** | 模型变更时，对业务侧影响较小 |
| **统一规范** | 便于统一鉴权、超时、日志、返回格式 |

***

### 3.3 当前统一口径

- 大模型工程师负责模型私有部署
- 大模型工程师负责提供私有 SDK
- 智能体服务通过私有 SDK 调用模型
- 业务系统不直接对接公网模型 API

***

## 四、前端交互方案

### 4.1 返回方式

当前确定为**同步返回**。

用户点击生成后：

- 前端进入 Loading 状态
- 等待几秒返回结果
- 返回后直接展示文案结果

这种方式适合当前文案生成场景，因为单次生成内容较短，交互目标明确，不需要复杂的流式对话体验。

***

### 4.2 页面交互规则

| 场景 | 交互规则 |
| ---- | -------- |
| **首次生成** | 按钮显示“生成” |
| **生成中** | 按钮禁用或展示 Loading |
| **生成成功** | 展示文案结果，支持复制 |
| **已有结果后再次触发** | 按钮显示“重新生成” |

***

### 4.3 当前结果能力

当前先确定最小交互闭环：

- 展示生成后的预警文案
- 支持一键复制结果
- 支持重新生成

后续如果继续增强，再考虑编辑、对比、版本留痕等能力。

***

## 五、上下文输入方案

### 5.1 前端可提供的上下文

当前已经明确，前端侧能稳定提供的上下文如下：

| 字段 | 是否确定 | 说明 |
| ---- | -------- | ---- |
| **时间** | 是 | 当前选中的时间 |
| **气象要素** | 是 | 当前选中的气象要素 |
| **地图视窗经纬度范围** | 是 | 当前地图插件可导出的经纬度边界 |
| **用户提示词** | 是 | 用户在界面输入的补充说明或特殊要求，透传给模型 |
| **区域名称** | 否 | 前端拿不到现成地名，由 agent-service 通过工具节点获取 |

当前没有区域名称这个参数，只有经纬度范围。

***

### 5.2 为什么不让前端传地名

因为当前地图插件只能导出当前视窗的经纬度范围，不能直接转成地点名称。

所以当前方案不要求前端做人名、地名解析，也不在前端增加额外算法逻辑。

***

### 5.3 数据获取与传递方式

当前确定方案：

**Java 根据时间 + 气象要素生成数据文件路径，将路径传给 agent-service；agent-service 自行读取原始数据文件，完成过滤与处理，并将处理结果存入 Redis。**

原因如下：

- 原始数据文件体积大（可达几百 KB），不适合在服务间逐级传输
- Java 只负责定位数据文件，不读取、不传输数据本身，职责更清晰
- agent-service 按需读取，处理结果存入 Redis，相同参数的重复请求可直接命中缓存，跳过读文件和处理步骤

数据流转顺序如下：

    前端传时间 + 气象要素 + 当前视窗经纬度范围 + 用户提示词
        ↓
    Java 根据时间 + 气象要素生成数据文件路径
    Java 将文件路径 + 经纬度范围 + 气象要素 + 用户提示词传给 agent-service
        ↓
    agent-service 先查 Redis（key = 要素 + 时间 + 经纬度范围哈希）
    命中则直接使用缓存；未命中则读取文件、按经纬度范围过滤、处理数据
        ↓
    处理结果存入 Redis（设 TTL），供后续复用

***

## 六、经纬度到地名方案

### 6.1 不采用的方案

当前明确不采用以下两种方式：

- 不自己手写经纬度转地名算法
- 不让模型凭空脑补地名

原因如下：

- 自己写算法成本高，且会和已有 GIS / 地图能力重复
- 让模型直接猜地名不可靠，容易产生错误

***

### 6.2 已确定方案

当前确定方案为：

**经纬度到地名的转换，交给智能体通过工具调用完成。**

也就是说：

- 智能体拿到经纬度范围
- 智能体调用专门的工具
- 工具返回标准地名或行政区划信息
- 智能体基于工具结果生成最终文案

***

### 6.3 这个方案的核心原则

**地名属于确定性信息，应该交给工具，不应该交给模型自由生成。**

***

## 七、端到端流程定稿

### 7.1 当前流程

当前已确定的端到端流程如下：

    前端点击“生成”
        ↓
    前端传递时间、气象要素、当前视窗经纬度范围、用户提示词
        ↓
    Java 根据时间 + 气象要素生成数据文件路径
    Java 将文件路径 + 经纬度范围 + 气象要素 + 用户提示词传给 agent-service
        ↓
    agent-service（LangGraph 工作流）开始执行
        ↓
    [工具节点] 经纬度范围 → 调用工具 → 返回地名
        ↓
    [路由节点] 按气象要素路由到对应处理节点
        ↓
    [要素处理节点] 查 Redis 缓存
        命中 → 直接取缓存数据
        未命中 → 读取数据文件 → 按经纬度过滤 → 处理数据 → 存入 Redis（设 TTL）
        ↓
    [模型调用节点] 将地名 + 处理后数据 + 用户提示词 → 通过私有 SDK 调用私有部署大模型
        ↓
    [结构化输出节点] 解析模型结果，输出标准格式
        ↓
    agent-service 同步返回结果给 Java
        ↓
    Java 返回结果给前端
        ↓
    前端结束 Loading，展示文案并支持复制
        ↓
    按钮由“生成”切换为“重新生成”

***

### 7.2 当前最小可用闭环

当前阶段的最小闭环已经比较清晰：

- 有独立的 Python `agent-service`（LangGraph 编排）
- 有私有部署模型
- 有私有 SDK
- 有同步生成交互
- 有 Java 生成文件路径、agent-service 读取并处理数据的分工
- 有 Redis 缓存处理结果
- 有经纬度转地名工具节点
- 有按气象要素路由的处理节点
- 有结构化输出节点
- 有结果展示与重新生成

这个闭环已经足够支撑第一版功能落地。

## 九、当前技术选型

### 9.1 第一版建议技术栈

基于当前已经确定的方案，第一版建议技术栈如下：

| 技术 | 作用 |
| ---- | ---- |
| **Python** | 开发独立的 `agent-service` |
| **FastAPI** | 把智能体能力封装成可调用的微服务接口 |
| **私有大模型 SDK** | 调用内网私有部署大模型 |
| **LangGraph** | 编排多节点工作流：工具节点、路由节点、要素处理节点、模型调用、结构化输出 |
| **Redis** | 缓存处理后的结构化数据，减少重复读文件和处理开销 |
| **Pydantic** | 定义请求参数、响应结构、工具输入输出结构 |
| **httpx / requests** | 调 Java 业务接口、调工具接口 |
| **Docker** | 部署 `agent-service` |

***

### 9.2 各技术分别负责什么

**Python：**

- 作为智能体微服务的开发语言
- 承接模型调用、工具调用、上下文组装等逻辑

***

**FastAPI：**

- 对外暴露生成文案接口
- 接收前端或 Java 服务传来的上下文参数
- 返回同步生成结果

***

**私有大模型 SDK：**

- 连接内网私有部署模型
- 屏蔽底层模型服务细节
- 统一模型调用方式

***

**LangGraph：**

- 编排多节点有向工作流
- 实现按气象要素的路由分支
- 管理各节点的状态传递
- 组织工具调用、模型调用、结构化输出的执行顺序

***

**Pydantic：**

- 约束请求参数格式
- 约束响应结果格式
- 约束工具调用参数格式

这样可以减少上下文传参混乱的问题。

***

**Redis：**

- 存储 agent-service 对原始数据处理后的结构化结果
- key 由气象要素 + 时间 + 经纬度范围哈希组合生成
- 设 TTL，避免数据陈旧或内存堆积
- 相同参数的重复请求直接命中缓存，跳过读文件和处理步骤

***

**httpx / requests：**

- 读取业务数据文件
- 调用地名解析等工具接口

这类库负责通用 HTTP 请求，不负责智能体编排。

***

**Docker：**

- 打包并部署 Python `agent-service`
- 便于后续在测试环境、客户环境中部署

***

### 9.3 为什么用 LangGraph 而不是 LangChain

当前这版方案的工作流特征是：

- 有多个功能节点（工具节点、路由节点、要素处理节点、模型调用、结构化输出）
- 有按气象要素的分支路由，不同要素走不同处理逻辑
- 节点之间有明确的状态传递（地名、处理后数据、用户提示词等）

这已经是 LangGraph 的典型适用场景。LangChain 更适合线性的单链路调用，一旦出现路由分支和多节点状态管理，用 LangChain 手动维护反而更复杂。

LangGraph 在这里解决的核心问题：

| 问题 | LangGraph 的解法 |
| ---- | ---------------- |
| 按要素路由 | 路由节点 + 条件边 |
| 多节点状态共享 | 统一 State 对象贯穿全图 |
| 工具节点与模型节点解耦 | 各节点独立定义，图结构组织执行顺序 |
| 结构化输出 | 独立输出节点，统一格式处理 |

***

### 9.4 当前技术口径

当前这版方案的技术口径可以统一为：

**Python + FastAPI + 私有大模型 SDK + LangGraph + Redis + Pydantic + HTTP 调用 + Docker**

这套技术已经足够支撑当前第一版功能落地。

***

## 十、当前已经拍板的结论

- 架构上：`Python agent-service（LangGraph）+ Java 原有业务微服务`
- 模型上：`私有部署 + 私有 SDK`
- 输入上：`时间 + 气象要素 + 当前视窗经纬度范围 + 用户提示词`
- 数据上：`Java 生成文件路径 → agent-service 读取 + 处理 → 结果存 Redis`
- 地名上：`通过工具节点调用获取，不靠模型脑补`
- 编排上：`工具节点 → 路由节点 → 要素处理节点 → 模型调用 → 结构化输出`
- 交互上：`同步返回 + Loading + 展示复制 + 重新生成`

***

## 十一、一句话总结

**当前确定的落地方案是：在原有 Java 微服务架构之外，单独增加一个 Python `agent-service`（LangGraph 编排）；前端传时间、气象要素、当前视窗经纬度范围和用户提示词，Java 根据参数生成数据文件路径并转发给 agent-service；agent-service 通过 LangGraph 工作流依次完成经纬度转地名、按要素路由、读取并处理数据文件（结果存 Redis 供复用）、调用私有部署大模型生成文案、结构化输出，最终以同步方式返回结果并支持复制与重新生成。**
