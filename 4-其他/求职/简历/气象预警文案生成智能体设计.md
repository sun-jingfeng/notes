# 气象预警文案生成智能体设计

> 只记录当前已经确定的方案，作为后续落地与面试讲解的统一口径。

***

## 一、功能定位

### 1.1 功能目标

**气象预警文案生成智能体** 用于在预警发布场景中，根据当前时间、选中的气象要素、地图当前视窗范围内的业务数据，自动生成可直接查看、复制、重新生成的预警文案。

这个功能不是通用聊天，也不是纯模板拼接，而是一个**业务型智能体能力**：

- 输入来自业务系统当前上下文
- 智能体负责补齐必要信息
- 输出为同步返回的预警文案结果

***

### 1.2 当前已拍板的总体方案

| 项目 | 已确定方案 |
| ---- | ---------- |
| **模型部署方式** | 大模型工程师负责私有化部署 |
| **模型接入方式** | 通过私有 SDK 调用，不直接对接公网 API |
| **智能体服务形态** | 单独拆分为 Python 微服务 |
| **原系统关系** | 原有 Java 微服务继续负责业务系统，新增 Python `agent-service` 负责智能体能力 |
| **返回方式** | 同步返回 |
| **前端体验** | 请求期间显示 Loading，返回后展示文案并支持复制 |
| **按钮交互** | 首次点击为“生成”，有结果后按钮变为“重新生成” |
| **地名获取方式** | 不手写算法，不让模型脑补，统一通过工具调用获取 |

***

## 二、系统落地形态

### 2.1 服务拆分

当前确定的落地形态如下：

    前端页面
        ↓
    Java 业务系统（原有微服务）
        ↓
    Python agent-service
        ↓
    私有部署大模型 + 私有 SDK
        ↓
    工具调用（业务工具 / 地名解析工具）

这个拆分方式适合已有微服务架构，原因如下：

- 不破坏原有 Java 业务系统主链路
- 智能体逻辑单独收敛到 `agent-service`
- 后续 Prompt、工具调用、工作流调整更方便
- 后续其他项目也可以复用这套智能体服务

***

### 2.2 各层职责

| 层级 | 主要职责 |
| ---- | -------- |
| **前端** | 收集当前时间、选中的气象要素、地图视窗经纬度范围，发起生成请求，展示结果 |
| **Java 业务系统** | 负责原有业务能力，对外提供业务数据接口，或作为系统入口转发请求 |
| **Python agent-service** | 负责智能体编排、工具调用、上下文组装、模型调用、结果返回 |
| **私有大模型** | 负责生成文案，不直接暴露给前端 |
| **工具层** | 负责经纬度转地名、业务数据查询等确定性能力 |

***

## 三、模型接入方案

### 3.1 为什么定为私有部署

当前项目面向国企、军工等对数据敏感度较高的客户，因此模型方案优先采用**私有化部署**。

核心原因如下：

- 原始业务数据不出公网
- 更符合内网与保密场景要求
- 便于客户侧独立部署和运维
- 更容易结合权限、审计、调用留痕做合规控制

***

### 3.2 为什么定为私有 SDK

当前不采用“业务代码直接拼 HTTP 请求调用模型接口”的方式，而是定为：

**大模型工程师完成模型私有部署，并封装私有 SDK；智能体服务通过私有 SDK 调用模型。**

这个方案的好处如下：

| 优点 | 说明 |
| ---- | ---- |
| **接入简单** | 智能体服务像调用普通模型 SDK 一样调用 |
| **屏蔽细节** | 无需关注底层模型服务的 HTTP 协议细节 |
| **便于切换模型** | 模型变更时，对业务侧影响较小 |
| **统一规范** | 便于统一鉴权、超时、日志、返回格式 |

***

### 3.3 当前统一口径

- 大模型工程师负责模型私有部署
- 大模型工程师负责提供私有 SDK
- 智能体服务通过私有 SDK 调用模型
- 业务系统不直接对接公网模型 API

***

## 四、前端交互方案

### 4.1 返回方式

当前确定为**同步返回**。

用户点击生成后：

- 前端进入 Loading 状态
- 等待几秒返回结果
- 返回后直接展示文案结果

这种方式适合当前文案生成场景，因为单次生成内容较短，交互目标明确，不需要复杂的流式对话体验。

***

### 4.2 页面交互规则

| 场景 | 交互规则 |
| ---- | -------- |
| **首次生成** | 按钮显示“生成” |
| **生成中** | 按钮禁用或展示 Loading |
| **生成成功** | 展示文案结果，支持复制 |
| **已有结果后再次触发** | 按钮显示“重新生成” |

***

### 4.3 当前结果能力

当前先确定最小交互闭环：

- 展示生成后的预警文案
- 支持一键复制结果
- 支持重新生成

后续如果继续增强，再考虑编辑、对比、版本留痕等能力。

***

## 五、上下文输入方案

### 5.1 前端可提供的上下文

当前已经明确，前端侧能稳定提供的上下文如下：

| 字段 | 是否确定 | 说明 |
| ---- | -------- | ---- |
| **时间** | 是 | 当前选中的时间 |
| **气象要素** | 是 | 当前选中的气象要素 |
| **地图视窗经纬度范围** | 是 | 当前地图插件可导出的经纬度边界 |
| **区域名称** | 否 | 前端拿不到现成地名 |

当前没有区域名称这个参数，只有经纬度范围。

***

### 5.2 为什么不让前端传地名

因为当前地图插件只能导出当前视窗的经纬度范围，不能直接转成地点名称。

所以当前方案不要求前端做人名、地名解析，也不在前端增加额外算法逻辑。

***

### 5.3 后端原始数据获取方式

当前已确定：

**后端可以根据“时间 + 选中的气象要素”直接查询原始业务数据。**

因为各省份的数据本身就是按这两个维度生成和组织的，所以这两个字段足够作为原始数据查询入口。

数据处理顺序如下：

    前端传时间 + 气象要素 + 当前视窗经纬度范围
        ↓
    后端根据时间 + 气象要素查询原始业务数据
        ↓
    后端再根据经纬度范围过滤出当前视窗内数据
        ↓
    将过滤后的有效数据交给智能体

这个方案当前成立。

***

## 六、经纬度到地名方案

### 6.1 不采用的方案

当前明确不采用以下两种方式：

- 不自己手写经纬度转地名算法
- 不让模型凭空脑补地名

原因如下：

- 自己写算法成本高，且会和已有 GIS / 地图能力重复
- 让模型直接猜地名不可靠，容易产生错误

***

### 6.2 已确定方案

当前确定方案为：

**经纬度到地名的转换，交给智能体通过工具调用完成。**

也就是说：

- 智能体拿到经纬度范围
- 智能体调用专门的工具
- 工具返回标准地名或行政区划信息
- 智能体基于工具结果生成最终文案

***

### 6.3 这个方案的核心原则

**地名属于确定性信息，应该交给工具，不应该交给模型自由生成。**

***

## 七、端到端流程定稿

### 7.1 当前流程

当前已确定的端到端流程如下：

    前端点击“生成”
        ↓
    前端传递时间、气象要素、当前视窗经纬度范围
        ↓
    Python agent-service 接收请求
        ↓
    agent-service 根据时间 + 气象要素查询原始业务数据
        ↓
    agent-service 根据经纬度范围过滤有效数据
        ↓
    agent-service 调用工具完成经纬度到地名转换
        ↓
    agent-service 通过私有 SDK 调用私有部署大模型
        ↓
    同步返回生成结果
        ↓
    前端结束 Loading，展示文案并支持复制
        ↓
    按钮由“生成”切换为“重新生成”

***

### 7.2 当前最小可用闭环

当前阶段的最小闭环已经比较清晰：

- 有独立的 Python `agent-service`
- 有私有部署模型
- 有私有 SDK
- 有同步生成交互
- 有业务数据过滤逻辑
- 有经纬度转地名工具调用
- 有结果展示与重新生成

这个闭环已经足够支撑第一版功能落地。

***

- Prompt 具体写法

这些内容后续再单独讨论。

## 九、当前技术选型

### 9.1 第一版建议技术栈

基于当前已经确定的方案，第一版建议技术栈如下：

| 技术 | 作用 |
| ---- | ---- |
| **Python** | 开发独立的 `agent-service` |
| **FastAPI** | 把智能体能力封装成可调用的微服务接口 |
| **私有大模型 SDK** | 调用内网私有部署大模型 |
| **LangChain** | 管理 Prompt、工具调用、模型调用链路、输出解析 |
| **Pydantic** | 定义请求参数、响应结构、工具输入输出结构 |
| **httpx / requests** | 调 Java 业务接口、调工具接口 |
| **Docker** | 部署 `agent-service` |

***

### 9.2 各技术分别负责什么

**Python：**

- 作为智能体微服务的开发语言
- 承接模型调用、工具调用、上下文组装等逻辑

***

**FastAPI：**

- 对外暴露生成文案接口
- 接收前端或 Java 服务传来的上下文参数
- 返回同步生成结果

***

**私有大模型 SDK：**

- 连接内网私有部署模型
- 屏蔽底层模型服务细节
- 统一模型调用方式

***

**LangChain：**

- 管理 System Prompt 和用户输入
- 组织模型调用流程
- 让模型按需调用工具
- 解析模型输出结果

当前阶段如果只是单次同步生成、工具调用链路不复杂，`LangChain` 就够用了。

***

**Pydantic：**

- 约束请求参数格式
- 约束响应结果格式
- 约束工具调用参数格式

这样可以减少上下文传参混乱的问题。

***

**httpx / requests：**

- 调用 Java 业务系统接口获取原始业务数据
- 调用地名解析等工具接口

这类库负责通用 HTTP 请求，不负责智能体编排。

***

**Docker：**

- 打包并部署 Python `agent-service`
- 便于后续在测试环境、客户环境中部署

***

### 9.3 为什么当前先不上 LangGraph

当前这版方案的特征是：

- 同步返回
- 单轮生成
- 工具链路不长
- 没有复杂状态流转
- 没有多分支工作流

所以第一版更适合先用 `LangChain`，不急着上 `LangGraph`。

`LangGraph` 更适合以下场景：

- 多步骤决策
- 多工具分支路由
- 失败重试编排
- 人工介入节点
- 长流程状态管理

当前阶段先不上，并不代表以后不用，而是为了控制第一版复杂度。

***

### 9.4 当前技术口径

当前这版方案的技术口径可以统一为：

**Python + FastAPI + 私有大模型 SDK + LangChain + Pydantic + HTTP 调用 + Docker**

这套技术已经足够支撑当前第一版功能落地。

***

## 十、当前已经拍板的结论

- 架构上：`Python agent-service + Java 原有业务微服务`
- 模型上：`私有部署 + 私有 SDK`
- 输入上：`时间 + 气象要素 + 当前视窗经纬度范围`
- 地名上：`通过工具调用获取，不靠模型脑补`
- 交互上：`同步返回 + Loading + 展示复制 + 重新生成`

***

## 十一、一句话总结

**当前确定的落地方案是：在原有 Java 微服务架构之外，单独增加一个 Python `agent-service`，通过私有 SDK 调用私有部署大模型；前端只传时间、气象要素和当前视窗经纬度范围，后端查询并过滤原始业务数据，再由智能体调用工具完成地名解析并生成预警文案，最终以同步方式返回结果并支持复制与重新生成。**
