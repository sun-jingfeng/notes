Later, to support the needs of multiple provinces, reuse shared capabilities, and decouple dedicated features, we gradually refactored it into a microservice architecture. ### 5. 这个项目里最大的技术挑战是什么 / What was the biggest technical challenge in that project?

**中文版：**

这个项目的技术挑战主要集中在前端、后端和智能体三个方面。前端最大的难点是要复用之前两个已有项目，同时再开发三个新项目，并且最终要以一个统一系统的形式对外展示。为了解决这个问题，我设计了父子项目架构以及它们之间的通信机制，最终实现了统一登录、统一风格切换和统一权限控制。后端最大的难点是微服务拆分。因为我们既要支持不同省份的差异化需求，又要复用原来的通用逻辑，所以我把原有单体系统拆成了微服务，把公共能力抽成公用微服务，同时为每个省份单独建立微服务来承载特定需求。智能体这部分的难点在于需要接入原有的 Java 微服务体系。当时可以选 Spring AI 或 Python 方案，最终考虑到 Python 生态更成熟，所以选择用 Python 实现智能体微服务，再接入现有的 Java 微服务架构。

**English Version:**

The technical challenges in this project were mainly on the front end, the back end, and the AI side. On the front end, the biggest challenge was that we had to reuse two existing projects, build three new ones, and eventually present them as one unified system. To solve this, I designed the parent-child application architecture and the communication mechanism between the parent and child applications. Based on that structure, we implemented unified login, unified theme switching, and unified permission control. On the back end, the biggest challenge was splitting the system into microservices. Because we needed to support province-specific requirements while still reusing the original shared logic, I refactored the original monolithic system into microservices, extracted common capabilities into shared microservices, and created dedicated microservices for each province to handle its specific requirements. For the AI part, the main challenge was integrating the new capability into the existing Java microservice system. At that time, we could choose either Spring AI or a Python-based solution. In the end, we chose Python because its ecosystem was more mature for this use case. We then built the AI agent as a Python microservice and integrated it into the existing Java microservice architecture.

### 6. 介绍一下你如何使用 AI 提效 / Could you explain how you use AI to improve development efficiency?

**中文版：**

我们公司从去年年初开始推动 AI 提效。最开始前端使用 Cursor，后端使用 IntelliJ IDEA 里的 Copilot 插件，后面逐步统一到了 Claude Code。除此之外，我也沉淀了一些提升和 AI 沟通效率与准确度的方法，比如 rules、skills 和 MCP。在我理解里，rules 和 skills 主要是提示词持久化相关的能力。Rules 一般配置在全局层面，用来约束一些基础信息，比如 Vue 项目默认使用 Vue 3，React 项目使用 React 19，Java 项目使用 Java 11。Skills 一般放在项目里，用来约束具体任务的生成规范，比如前端组件生成、组合式函数生成，或者后端接口生成等。在实际使用过程中，我们也会持续完善这些 AI skills。一个项目做得越久，这些规则和技能越完善，AI 生成的代码就会越接近团队的预期。我对 MCP 的理解是，AI 接入外部工具和上下文的一种标准方式。我目前主要接入过 Figma MCP。接入之前，我们需要把设计图截图发给 AI；接入之后，AI 可以直接读取设计图节点信息，这样沟通会更准确，理解偏差也会更少。

**English Version:**

Our company started promoting AI-assisted development in early last year. At first, we used Cursor for front-end work and the Copilot plugin in IntelliJ IDEA for back-end work. Later, we gradually standardized on Claude Code. In addition, I also built up some practical ways to improve both the efficiency and the accuracy of communication with AI, such as rules, skills, and MCP. In my understanding, rules and skills are mainly used for prompt persistence. Rules are usually defined at the global level and used to specify baseline conventions, such as using Vue 3 for Vue projects, React 19 for React projects, and Java 11 for Java projects. Skills are usually defined at the project level and used to specify generation standards for specific tasks, such as front-end component generation, composable generation, or back-end API generation. In real projects, we keep refining these skills over time. The longer a project runs, the more complete these rules and skills become, and the closer the generated code gets to the team’s expectations. My understanding of MCP is that it is a standard way for AI to connect to external tools and context. The main MCP I have used so far is Figma MCP. Before using MCP, we had to send screenshots of the design to AI manually. After integrating MCP, AI could directly read design node information, which made communication more accurate and reduced misunderstandings.
