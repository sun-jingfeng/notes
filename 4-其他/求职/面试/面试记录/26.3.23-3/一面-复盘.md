### 4. Redis 使用场景

**问题**：Redis 用过吗？主要用在什么场景？

**我的答案要点**
- 主要用作后端缓存。
- 在雷达监测系统里，后端要读取一段 JSON 数据并做特定插值算法计算，过程比较耗时。
- 用 JMeter 压测后发现这是性能瓶颈。
- 如果时间和气象要素相同，结果也相同，所以把结果缓存到 Redis，后续直接读取。

**评价**
- 优点：这是本场回答里比较好的一个点，有明确场景、性能瓶颈、压测、缓存命中条件，业务链路是完整的。
- 不足：最后一句“用 Redis 做缓存”过于收口，没有顺手补缓存 key 设计、过期策略、为什么适合放 Redis，这样会少一点技术说服力。

**参考答案要点**
- Redis 最常见的场景是热点数据缓存、计数器、分布式锁、会话缓存等。
- 你的项目案例里，属于“高耗时计算结果缓存”，命中条件明确，非常适合用 Redis String 直接缓存结果。
- 可以补充 key 设计，如“业务维度 + 时间 + 气象要素”；再补 TTL 和缓存一致性思路。

**话术示例**
Redis 我主要用在缓存场景。比如我做过一个雷达监测项目，后端要读取原始 JSON 数据，再跑一段插值算法算出结果，这个过程比较耗时。我们用 JMeter 压测后定位到这里是瓶颈，而且这个结果在“时间 + 气象要素”相同的情况下是可复用的，所以就把结果缓存到 Redis。这样相同条件下就不用重复计算，直接命中缓存，接口响应会快很多。

### 5. Redis 为什么快

**问题**：Redis 效率高的原理是什么？

**我的答案要点**
- 主要是用内存存储。
- 也可以持久化到硬盘。
- 更细节的原理不了解。

**评价**
- 优点：至少抓住了“基于内存”这个最核心的点。
- 不足：回答明显偏浅，停在“内存快”；没有继续说单线程事件驱动、IO 多路复用、数据结构高效这些常见面试点。

**参考答案要点**
- Redis 快的核心原因有 4 个：基于内存、单线程避免锁竞争、IO 多路复用提高网络处理效率、底层数据结构高效。
- 持久化不是“快”的原因，而是“可靠性”的补充。
- 如果面试官继续追问，可再补 RDB、AOF、混合持久化。

**话术示例**
Redis 快最核心还是因为它是基于内存的，读写不用像 MySQL 那样频繁走磁盘。除此之外，它的执行模型比较轻，单线程处理命令可以减少线程切换和锁竞争，网络层也用了 IO 多路复用，所以整体吞吐会比较高。再加上它针对不同场景做了比较高效的数据结构设计，所以在缓存这类场景里性能会很突出。至于持久化，那更多是数据可靠性的补充，不是它快的主要原因。

### 6. Spring Bean 的作用域与生命周期

**问题**：Spring Bean 的生命周期是怎么样的？

**我的答案要点**
- 回答里主要讲了作用域：单例、每次使用新建、每次请求新建。
- 说单例 Bean 在进入 MVC 容器时注册，服务结束时销毁。
- 说 prototype 在使用时创建。
- 说 request 作用域会在每次请求到来时创建，用于存储个性化信息。

**评价**
- 优点：答到了 singleton、prototype、request 这些作用域，也理解了“无状态单例”和“请求级实例”的差异。
- 不足：题目问的是生命周期，但你主要答成了“作用域”；生命周期的标准流程基本没说出来，例如实例化、依赖注入、初始化回调、销毁回调。

**参考答案要点**
- 先区分两个概念：作用域是“创建几个”，生命周期是“从创建到销毁经历什么阶段”。
- 单例 Bean 生命周期大致是：实例化 → 依赖注入 → Aware 回调 → `@PostConstruct` → `afterPropertiesSet` / `init-method` → 使用 → `@PreDestroy` / `destroy-method`。
- 作用域常见有 singleton、prototype、request、session。

**话术示例**
这一题我会先区分作用域和生命周期。作用域是这个 Bean 创建几个，常见有 singleton、prototype、request、session；生命周期是它从创建到销毁要经历哪些阶段。单例 Bean 的典型生命周期是先实例化，然后做依赖注入，接着执行一些初始化回调，比如 `@PostConstruct`、`afterPropertiesSet`，之后进入正常使用阶段，容器关闭时再执行销毁回调。也就是说，作用域回答的是“几个实例”，生命周期回答的是“这一个实例怎么走完一生”。

### 7. ORM 框架与 MyBatis 一级、二级缓存

**问题**：ORM 用的是什么？MyBatis 一级缓存和二级缓存有什么区别？

**我的答案要点**
- 回答 ORM 用的是 MyBatis。
- 对一级缓存和二级缓存表示不了解。

**评价**
- 优点：至少明确了项目里 ORM 框架的实际选型。
- 不足：MyBatis 一级、二级缓存是很常规的问题，直接答“不知道”会比较伤；如果不知道细节，也应该先答出“一级是 SqlSession 级，二级是 Mapper 级”这一层。

**参考答案要点**
- 一级缓存是 SqlSession 级别，同一个 SqlSession 内相同查询条件会命中缓存；发生增删改、手动清缓存或关闭 Session 后会失效。
- 二级缓存是 Mapper / namespace 级别，跨 SqlSession 共享，需要显式开启。
- 实战里二级缓存一般不太常用，尤其分布式场景更常用 Redis 这类集中式缓存。

**话术示例**
我们项目里 ORM 主要用的是 MyBatis。它的一级缓存是 SqlSession 级别，也就是同一个 SqlSession 里，如果同样的查询执行多次，可以直接命中缓存；但只要发生增删改，或者 Session 关闭了，这个缓存就失效了。二级缓存是 Mapper 级别，跨 SqlSession 共享，需要额外开启。不过在实际项目里，尤其是分布式场景，我更倾向于用 Redis 这类集中式缓存，控制会更清晰。

### 9. 线上内存泄漏与问题排查

**问题**：线上出现过内存泄漏吗？如果排查，用什么方式？

**我的答案要点**
- 没真正遇到过内存泄漏。
- 遇到问题时一般从接口入口开始排查。
- 先查 Nginx 日志，再查 Docker 容器日志，再查宿主机映射出来的 Java 程序日志。
- 如果是服务内部问题，再继续往里查。

**评价**
- 优点：虽然没遇到内存泄漏，但排查链路有一定工程实践感，知道按入口层层往下看日志。
- 不足：题目核心是“内存泄漏如何排查”，而你回答成了“普通线上问题怎么排查”；缺少 JVM 相关的排查手段，比如堆转储、GC 日志、`jmap`、`jstack`、监控指标等。

**参考答案要点**
- 先确认是不是内存问题，看堆内存、GC 频率、Full GC 是否异常。
- 常见排查手段：监控平台、GC 日志、`jstat` 看 GC、`jmap -dump` 导出堆、MAT 分析对象占用、`jstack` 看线程状态。
- 同时保留你原本的工程排查链路：网关日志、容器日志、应用日志、traceId。

**话术示例**
我实际项目里没有遇到过非常明确的内存泄漏案例，但如果线上怀疑是这个问题，我会分两层处理。第一层是常规链路排查，先看 Nginx、容器、应用日志，确认是不是接口异常、流量突增或者下游阻塞；第二层才是 JVM 视角，去看内存曲线、GC 情况、Full GC 是否频繁，必要时用 `jmap` 导堆，再用 MAT 分析是哪些对象一直没释放。如果只是普通接口报错，我会按日志链路查；如果确认是内存泄漏，就一定要回到堆和 GC 数据上看。

### 10. AI 应用落地项目介绍

**问题**：你做过什么样的 AI 项目？介绍一下 AI 在业务里的落地。

**我的答案要点**
- 项目是气象预警系统，使用者是企业气象台工作人员。
- 之前预警文案需要人工撰写，后来加了 AI 自动生成功能。
- 前端把用户选中的时间、气象要素和原始信息传给后端。
- 后端根据这些信息获取硬盘上的原始数据。
- 算法会产出两份数据，一份给前端做色斑图等展示，一份给 AI，AI 用的数据更精简。
- 后端拿到原始数据后调用智能体微服务。

- 支持 sessionId，可重复生成，会把会话结果持久化到 Redis。
- Python 智能体服务单独拆成微服务，和原有 Java 微服务正常通信。

**评价**
- 优点：这是本场最有价值的一题。你把业务背景、输入、数据处理、微服务拆分、私有化部署、会话持久化都讲到了，说明确实做过落地，而不是停留在 Demo。
- 不足：表达有些绕，信息点很多但没有分层，容易让面试官听漏重点；另外没有主动强调“你的职责到底在哪”，比如你负责前端接入、接口设计、微服务联调、session 机制，还是整体方案推进。

**参考答案要点**
- 这题最好按“业务背景 → 链路设计 → 技术实现 → 难点与价值”来讲。
- 业务背景：原来人工写预警文案，效率低且一致性差。
- 链路设计：前端传筛选条件，后端聚合原始数据和算法结果，AI 微服务生成文案并返回。
- 技术实现：私有化模型、LangChain / LangGraph 编排、sessionId 续写、多服务通信、Redis 持久化会话。
- 最后补业务价值：提升出稿效率、支持重复生成、和现有系统无缝集成。

**话术示例**
我做过一个气象预警系统里的 AI 文案生成功能。这个场景原来是业务人员根据气象数据手工写预警文案，效率比较低，而且文案风格不够统一。我们做法是前端把用户选中的时间、气象要素和相关上下文传给后端，后端再结合原始数据和算法产出的精简数据，去调用独立的 AI 微服务生成文案。

这个 AI 微服务是单独拆出来的 Python 服务，和原有 Java 微服务通过接口通信，底层接的是私有化模型，流程编排上用了 LangChain、LangGraph 这类框架。为了支持用户重复生成和上下文延续，我们还引入了 sessionId，并把会话结果存在 Redis 里。这个功能的核心价值不是做一个聊天框，而是把 AI 接进原有业务流程里，让它真正服务业务人员的预警出稿流程。

### 12. 多线程使用场景

**问题**：开发中用过多线程吗？

**我的答案要点**
- 用过。
- 还是在前面那个算法计算场景里，JMeter 压测发现性能瓶颈。
- 计算逻辑是网格状结构，可以分片算，最后再组合。
- 所以除了 Redis 缓存之外，还用了线程池并发计算。
- 线程数策略是读取 CPU 核数，小于 8 用 CPU 核数，大于 8 就按 8。
- 认为这是 CPU 密集型任务，所以用这种方式提高速度。

**评价**
- 优点：这个回答不错，能说出业务背景、为什么适合并行、线程数为什么这么定，说明不是随便套线程池。
- 不足：表达上可以再严谨一点，比如“按 CPU 核数或上限 8”是经验值，不是固定公式；还可以补一句为什么不用无限开线程。

**参考答案要点**
- CPU 密集型任务适合线程数接近 CPU 核数，避免过多线程切换。
- 你的场景属于可拆分、可并行计算后汇总的典型案例。
- 回答时可以补线程池而不是手动 new Thread 的原因：复用线程、控制并发、便于管理。

**话术示例**
用过，最典型的是一个计算型接口优化场景。我们通过压测发现某段算法计算很耗时，而这段计算本身可以按网格分片并行处理，最后再汇总结果，所以就用了线程池把任务拆开并发执行。因为这是 CPU 密集型任务，所以线程数我会尽量贴近 CPU 核数，不会无限往上开，避免线程切换成本把收益吃掉。这样配合缓存一起做，性能提升会更明显。

### 13. 线程池是固定大小还是自定义

**问题**：线程池用的是自定义线程池还是固定大小的？

**我的答案要点**
- 用的是固定大小线程池。
- 线程数按 CPU 核数和 8 的上限来定。

**评价**
- 优点：回答直接，没有绕。
- 不足：如果只是说“固定大小”，下一步就很容易被追问为什么不用自定义，以及固定线程池的局限；最好主动补上这是针对该场景的权衡，而不是只会这一种。

**参考答案要点**
- 固定线程池适合任务量相对稳定、线程数可预估的场景，配置简单。
- 自定义线程池适合更复杂的生产场景，可以控制核心线程数、最大线程数、队列大小、拒绝策略。
- 你的场景属于单一 CPU 密集型任务，所以固定大小线程池是合理选型。

**话术示例**
我当时用的是固定大小线程池，因为那个场景比较单一，就是 CPU 密集型的并行计算任务，线程数也比较容易估出来，所以固定大小够用了。如果是更通用的生产场景，我会更倾向于自己基于 `ThreadPoolExecutor` 配核心线程数、最大线程数、阻塞队列和拒绝策略，这样控制力会更强。

### 14. 自定义线程池核心参数

**问题**：自定义线程池里的几个核心参数了解吗？

**我的答案要点**
- 表示不是很了解。
- 说明项目里主要用的是固定线程数的线程池。

**评价**
- 优点：边界清楚，没有硬答。
- 不足：线程池核心参数属于 Java 并发高频题，这里直接失分比较明显，后续要补上。

**参考答案要点**
- `ThreadPoolExecutor` 关键参数包括：核心线程数、最大线程数、空闲线程存活时间、阻塞队列、线程工厂、拒绝策略。
- 常见拒绝策略有 `AbortPolicy`、`CallerRunsPolicy`、`DiscardPolicy`、`DiscardOldestPolicy`。
- 面试时先说这些，再结合 CPU 密集型 / IO 密集型场景说线程数思路。

**话术示例**
如果是自定义线程池，我会基于 `ThreadPoolExecutor` 来配，核心参数主要有核心线程数、最大线程数、空闲线程存活时间、任务队列、线程工厂和拒绝策略。像 CPU 密集型任务，线程数一般会比较贴近 CPU 核数；如果是 IO 密集型，线程数可以适当放大一些。另外拒绝策略我也会根据场景选，比如有些场景可以让调用方自己执行，有些场景直接拒绝更安全。
