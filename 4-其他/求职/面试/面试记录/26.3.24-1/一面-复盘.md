### 2. Python 是怎么切入 Java 微服务的

**问题**：这个项目是 Java 和 Python 混合开发吗，还是 Python 只是别人做的一部分？

**我的答案要点**
- 原有后端服务和接口数据获取主要是 Java 微服务。
- 后来增加了智能文案生成功能，这部分用 Python 写成一个新的微服务。
- 新微服务通过注册和 HTTP 通信并入了原有的 Java 微服务体系。
- 这部分 Python 微服务是自己实现的。

**评价**
- 优点：把“原有 Java 服务 + 新增 Python 微服务”的关系讲清楚了，也说明了自己是主要实现者。
- 不足：可以再补一句这个 Python 服务在整体链路中的输入、输出和边界，否则还不够立体。

**参考答案要点**
- 先说原系统结构，再说新增能力和接入方式。
- 明确 Python 微服务负责什么，不负责什么。
- 说明为什么这种拆法对现有系统侵入小、可演进。

**话术示例**
这个项目本身原来就是一套 Java 微服务体系，原有的数据获取、业务接口这些都在 Java 侧。后来新增了智能文案生成需求，我没有直接改原有服务，而是单独用 Python 做了一个微服务，通过服务注册和 HTTP 调用并入原来的体系。这样做的好处是对原系统侵入比较小，而且后续如果别的项目也要接这套能力，可以直接复用这部分服务。

### 3. 为什么选择 Python 来做智能体微服务

**问题**：当时为什么考虑用 Python，而不是继续用 Java？

**我的答案要点**
- 公司当时在推动 AI 提效和智能体落地，并且是内网自部署大模型。
- 自己从 0 开始设计这块方案，做过调研。
- 判断 Python 在智能体生态上更成熟，相关 SDK 和框架更多。
- 如果只是短期接入可以用 Java，但如果考虑长期复用，更适合用 Python 生态。
- 因此自己临时补了 Python 语法并用 Python 实现。

**评价**
- 优点：这题答得比较好，有“业务背景 + 技术调研 + 方案权衡 + 最终决策”的完整链路。
- 不足：可以进一步补充具体用了哪些框架或能力，以及为什么“长期复用”在你们场景里成立。

**参考答案要点**
- 选择语言不要只说“生态好”，要说清业务目标、交付周期和长期维护成本。
- Python 的优势可以概括为 AI SDK 完整、原型验证快、社区资料多。
- Java 的优势是和现有体系一致、团队熟悉度高，但 AI 生态相对没那么丰富。
- 最后强调这是一个“面向复用和演进”的选择，不是单纯跟风。

**话术示例**
当时我们不是为了炫技去引入 Python，而是先看需求本质。这个能力后面很可能不只服务一个项目，如果只做一次性接入，用 Java 当然也能做，但从长期复用和后续演进看，Python 在大模型和智能体这块的生态更成熟，很多 SDK、工作流和工具调用能力都更完整。所以我当时做完调研之后，决定把这一层单独用 Python 写成微服务，再通过标准接口接回原来的 Java 体系，这样既不破坏原系统，又方便后续扩展。

### 9. 你对 Spring 的 IOC 和 AOP 了解多少

**问题**：Spring 的两大核心 IOC 和 AOP，你了解多少？

**我的答案要点**
- 开始对面试官的发音有点没听清，后续确认是在问 IOC 和 AOP。
- 解释了 IOC 容器的自动配置、Bean 管理和依赖注入。
- 讲到了 Bean 生命周期，提到单例、请求级、每次新建等作用域。
- 解释了 AOP 是切面编程，可以在方法前后织入通用逻辑。

**评价**
- 优点：核心方向答对了，至少知道 IOC 是管 Bean 和注入，AOP 是处理横切逻辑。
- 不足：术语表达不够稳，出现了 IOC、MVC、Spring Boot、容器几个概念混讲的情况；另外一些表述不够严谨，比如“请求拦截器在容器外”这类说法容易被追问。

**参考答案要点**
- IOC 的核心是对象创建和依赖关系交给容器管理，常见体现就是依赖注入。
- AOP 的核心是把日志、事务、权限校验这类横切逻辑从业务代码里抽离出来，通过代理在方法执行前后织入。
- 回答时要把“容器管理对象”和“方法级增强”这两个核心点说准。

**话术示例**
我对这两个核心概念是有实际使用经验的。IOC 本质上就是把对象的创建和依赖关系交给 Spring 容器管理，开发时更多体现为依赖注入，这样类和类之间会更解耦。AOP 则是把日志、事务、鉴权这类横切逻辑从业务代码里抽出来，通过代理的方式在方法执行前后统一织入，所以它特别适合做通用能力而不是业务主流程。

### 10. 你在开发里具体怎么用 IOC 和 AOP

**问题**：你平时开发过程中，哪些地方用过容器注入和 AOP？

### 12. 你怎么理解索引优化

**问题**：你写了熟悉索引优化，能展开说一下应用场景和思路吗？

**我的答案要点**
- 索引主要用于提升查询效率。
- 某些列被高频查询时可以建立索引。
- 提到了最左前缀原则。
- 提到模糊查询字段尽量放后面。
- 把索引检索类比成了排序后类似二分查找。

**评价**
- 优点：知道索引核心目标、最左前缀原则这些基础点。
- 不足：回答还偏概念化，没有结合实际 SQL 场景；另外底层原理说成“类似二分法”不够准确，更合理的表述应该落到 B+ 树、回表、覆盖索引和索引失效场景。

**参考答案要点**
- 从“什么查询慢”切入，比纯讲概念更好。
- 常见优化点包括：高频筛选列建索引、联合索引顺序贴合查询条件、尽量命中覆盖索引、避免函数计算和前导模糊匹配导致索引失效。
- 最好补一句通过执行计划验证，而不是凭感觉建索引。

**话术示例**
我理解索引优化不是简单地给字段都建索引，而是围绕高频查询场景去设计。比如列表查询经常按时间、状态、地区这类字段筛选，那就要结合 where 条件顺序去设计联合索引，并通过执行计划看有没有真正命中。实际优化时我会关注最左前缀、回表成本、覆盖索引和索引失效场景，比如前导模糊匹配、函数操作、类型隐式转换这些都可能让索引用不上。

### 13. 事务隔离级别你了解吗

**问题**：数据库事务隔离级别你知道吗？

**我的答案要点**
- 先把事务分成数据库事务、Spring 事务、Seata 分布式事务三层来回答。
- 当面试官明确问数据库事务隔离级别后，承认自己这块不太了解。

**评价**
- 优点：没有硬编，听不准时先确认问题范围，这点是对的。
- 不足：这是比较基础的数据库题，直接不会会明显扣分，而且前面对事务分层的展开没有命中问题本身。

**参考答案要点**
- 数据库常见隔离级别有读未提交、读已提交、可重复读、串行化。

- MySQL InnoDB 默认是可重复读，可以顺带补一句 MVCC 和间隙锁的概念。

**话术示例**
如果问数据库层面的事务隔离级别，常见的是四种，分别是读未提交、读已提交、可重复读和串行化。它们主要是在脏读、不可重复读和幻读之间做取舍。像 MySQL InnoDB 默认是可重复读，实际项目里如果没有特别强的一致性要求，很多场景会结合数据库默认级别和业务补偿手段一起处理。

### 22. 你怎么理解 Promise

**问题**：刚才提到 Promise，你讲一下你对 Promise 的理解。

**我的答案要点**
- 说 Promise 是为了解决 JavaScript 异步问题和回调地狱。
- 提到了 `resolve`、`reject` 两种状态流转方向。
- 说 `async/await` 可以看作对 Promise 用法的进一步优化。
- 提到了一些常见 API，但名称和作用的表述有点混乱。

**评价**
- 优点：主线是对的，知道 Promise 出现的背景和核心价值。
- 不足：这题细节失分比较明显，比如状态应该是 pending、fulfilled、rejected；API 方面 `Promise.all`、`allSettled`、`finally` 的说法也不够准确。

**参考答案要点**
- Promise 是异步编程的一种统一抽象，核心是把异步结果表示为未来某个时刻会完成或失败的对象。
- 三种状态是 pending、fulfilled、rejected，状态一旦确定就不会再变。
- 常见 API 包括 `then`、`catch`、`finally`、`Promise.all`、`Promise.race`、`Promise.allSettled`。
- `async/await` 是基于 Promise 的语法糖，不是替代底层机制。

**话术示例**
我理解 Promise 的核心作用是把异步结果标准化，让异步流程不再只能靠层层回调去组织。一个 Promise 在执行过程中会经历 pending、fulfilled、rejected 这些状态，而且状态一旦确定就不会再反复变化。平时开发里最常用的是 `then`、`catch` 和 `finally`，多个异步任务并行时会用 `Promise.all` 或 `Promise.allSettled`。后来的 `async/await` 本质上也是建立在 Promise 之上的语法糖，只是让代码写起来更像同步流程。

- 优点：有主动反问，而且问题围绕业务和技术栈，说明你在判断岗位匹配度。
- 不足：还可以继续追问团队规模、岗位职责、日常工作比例、文档要求和项目周期，这样信息会更有决策价值。

**参考答案要点**
- 反问建议优先围绕业务场景、岗位预期、团队协作方式和当前核心挑战。
- 技术栈当然可以问，但更重要的是问“进去之后第一阶段要解决什么问题”。

**话术示例**
我会优先想了解两类信息。第一类是业务和项目形态，比如目前主要是长期产品演进还是以项目交付为主，岗位进去后最先要承担的核心职责是什么。第二类是团队协作方式，比如前后端和测试怎么配合，对文档和过程规范的要求大概有多高。这样我能更准确判断自己过去的项目交付经验能不能快速衔接上来。
