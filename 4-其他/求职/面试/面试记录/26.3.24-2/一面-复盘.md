### 1. 自我介绍

- 前端以 React、Vue 为主，后端主要用 Java。
- 做过项目负责人和技术小组组长。
- 有前后端全栈交付能力，也会用 AI 提效。

- 主动说明自己不做原生 iOS / Android 开发。

**评价**
- 优点：学历、年限、技术栈、带人经历和全栈能力都提到了，整体信息比较全，也比较真实。
- 不足：没有先给自己的核心定位，比如“前端出身的全栈技术负责人”；最后主动展开“不会原生移动端”，在对方还没深问前会把注意力带到弱项上。

**参考答案要点**
- 开头先给定位：前端出身，近几年扩展到 Java 全栈，并承担项目负责人 / 小组长角色。

- 主动和岗位对齐：如果岗位需要搭软件部门、管技术路线、盯交付，我的经历是贴近的。

**话术示例**
我本科是吉林大学软件工程专业，做 Web 开发大概 4 年，前端是我的主方向，React 和 Vue 都做过，后端主要是 Java。过去这几年我不只是做单点开发，也做过项目负责人和技术小组组长，既参与具体开发，也会负责方案制定、任务分配和推进交付。我的优势是既能落代码，也能从项目和团队视角去推动事情落地，这一点和需要搭建软件部门、把控交付的岗位比较匹配。

### 2. 带技术小组的经历

**问题**：你刚才提到带过技术小组，这段经历主要是做什么的？

**我的答案要点**
- 去年年初被选为技术小组组长，负责一条雷达预警业务线。
- 团队规模约 6 人，自己既做前端也做后端。
- 项目从领导下发到自己这里，再由自己分配给组员。
- 分配任务时会考虑谁手里有没有活、谁做过类似模块、谁更适合新技术或老项目维护。
- 自己深度参与开发，不是纯管理岗。
- 分工原则是尽量降低沟通成本，提高开发效率。

**评价**
- 优点：回答里能体现资源分配思路、识人用人的方式，以及自己不是只做管理的风格，说明你确实做过小团队带队。
- 不足：更像“任务分配经验”，但对开发总监岗位更关键的是目标管理、风险管理、跨团队协同、交付结果和过程机制，这部分没有打出来；团队人数表述在转写里略有歧义，正式面试时要说清楚。

**参考答案要点**
- 先交代团队规模、业务线、你承担的角色。
- 再讲你的管理动作：任务拆分、人员匹配、进度跟踪、方案把关、风险兜底。
- 最后讲结果：交付效率、项目数量、是否按期上线、团队协作是否顺畅。
- 如果岗位偏管理，还要补一句你如何把技术管理和业务结果结合起来。

**话术示例**
我带过一条雷达预警业务线的小组，团队大概 6 人，我自己既参与开发，也负责项目推进。项目任务一般会先到我这里，我再根据成员手上的工作量、过往经验和擅长方向做拆分。比如新功能、探索性强的任务会给学习能力和主观能动性更强的人，老项目维护会给对存量系统更熟的人，这样能降低沟通成本，也更利于效率和质量。对我来说，带团队不是只分任务，而是要把人和事匹配好，把项目稳定往前推。

### 3. 技术方案选型与架构设计

**问题**：在项目开发过程中，你会参与技术方案选型或者架构设计吗？

**我的答案要点**
- 如果自己参与项目，通常就是项目负责人，核心方案会由自己主导。
- 前端场景中，做过新系统复用旧系统页面的方案设计。
- 采用父子应用嵌入思路，把旧系统页面嵌到新系统里，同时设计父子应用之间、子应用之间的通信链路。
- 后端场景中，原来是单体项目，后面随着省份版本增多，拆成微服务。
- 共用逻辑放到公共微服务，各省差异化逻辑放到各自微服务中。
- 方案确定后会和组员沟通优缺点，让大家接受后再执行。

**评价**
- 优点：这题答得比较好，既有前端案例，也有后端案例，能说明你不是只会写代码，而是真正参与过架构层决策。
- 不足：表达略绕，技术术语不够收敛；没有突出“为什么这样选、替代方案是什么、最终效果如何”，所以说服力还可以再增强。

**参考答案要点**
- 用“背景约束 → 方案选择 → 为什么这样选 → 落地效果”四段式来答。
- 前端案例强调“复用旧系统、控制重写成本、打通通信链路”。
- 后端案例强调“抽公共能力、隔离省份差异、保证复用和可维护性”。
- 补一句你的角色：主导方案、推动共识、保证可落地，而不是只提一个想法。

**话术示例**
会的，只要我是项目负责人，技术方案和架构设计一般都会深度参与。比如前端我做过一个新系统要复用旧系统页面的场景，当时的核心约束是不允许把旧页面全部重写，所以我采用的是父子应用嵌入的思路，把旧系统能力接进新系统，同时把父子应用之间、子应用之间的通信链路先设计清楚。后端这边也做过从单体往微服务演进的方案，核心是把公共逻辑抽出来，把各省份的差异化需求隔离开。我的习惯不是只给一个方案，而是把为什么这么做、优劣势是什么讲清楚，再推动团队一起落地。

### 4. 把 AI 或算法接入业务系统的经验

**问题**：你之前有没有把 AI 或算法放到软件系统架构里的经验？

**我的答案要点**
- 有过相关经历，是离职前几个月接入的一个智能生成文案功能。
- 场景是气象预警类项目，用智能体输出预警文案。
- 由于服务对象多是事业单位或国企，所以采用本地模型。
- 这个项目没有写进简历，但确实参与了落地。
- 自己介入的是一个智能生成文案系统的接入工作。

**评价**
- 优点：能给出真实业务场景，不是泛泛说“做过 AI”；提到本地模型，也符合政企项目的常见约束。
- 不足：第一轮回答偏粗，只说了“做过”但没有迅速讲清楚业务背景、系统链路、你的职责和最终价值，容易让面试官继续追着问。

**参考答案要点**
- 先说业务背景：原来哪些工作靠人工完成，为什么要引入 AI。
- 再说系统链路：前端 / 后端 / 算法 / 模型服务之间怎么串起来。
- 再说你的职责：你负责的是应用接入、服务封装、会话管理还是底层模型。
- 最后说结果：效率提升、流程打通、和原有系统无缝融合。

**话术示例**
有，我做过一个气象预警场景下的 AI 文案生成接入。这个业务原来更多依赖人工整理数据后输出预警文案，效率和一致性都比较受限，所以后面引入了本地化部署的大模型能力。我参与的重点不是底层模型训练，而是把这套能力真正接进现有业务系统里，让它能在原有流程中稳定产出可用的预警文案。

### 5. 智能体本身是不是你来搭建的

**问题**：智能体本身的搭建也是你在做吗？

**我的答案要点**
- 不是自己从零搭建的。
- 底层智能体 / 大模型相关工作由新招的同事或其他人员负责。
- 自己更多负责后续接入和业务侧落地。

**评价**
- 优点：回答真实，没有把别人的工作说成自己的，这一点是加分的。
- 不足：答完“不是”以后没有立刻把话题切回“我的责任是什么”，会让你的贡献显得偏被动。

**参考答案要点**
- 先坦诚分工边界，不抢模型侧功劳。
- 立刻补上自己的职责：服务封装、系统接入、会话管理、流程编排、联调上线。
- 强调“我负责把模型能力变成业务能力”，这样价值会更清楚。

**话术示例**
底层智能体和模型能力本身不是我从零搭的，这部分更多是算法或专门的同事在做。我这边主要负责的是业务接入和应用层落地，比如把模型能力封装成可调用的服务，接进现有 Java 后台体系里，再把会话、配置、调用链路这些补齐。也就是说，我的重点不是造模型，而是把模型真正变成业务里可用的一环。

### 6. 智能体是怎么放进原有系统里的

**问题**：智能体最后是以什么方式交付到系统里？你是怎么把它放进现有系统当中的？

**我的答案要点**
- 以 SDK 的方式接入。
- 因为智能体生态很多工具在 Python 侧，所以自己写了一个 Python 微服务。
- Python 语法是为这个场景补的，能完成服务侧开发。
- 这个 Python 微服务和 Java 微服务一样，按统一方式注册到服务体系中。
- 接入时沿用了已有的注册发现方式，嵌入到原有 Java 后台服务链路里。
- 自己负责了工具配置、网络请求、流程编排、聊天记录存储和新建会话等功能。

**评价**
- 优点：这题实际很能打，因为你已经讲出了“SDK + Python 微服务 + 接入原有 Java 微服务体系 + 会话持久化”这条完整落地链路，说明你不是只做页面调用。
- 不足：表达时有些口语和弱化表述，比如“Python 是现学的”“语法级掌握”，这会削弱面试官对交付能力的感知；另外“流程编排 / 会话管理 / 持久化”这些亮点可以更主动地说完整。

**参考答案要点**
- 讲清架构链路：模型能力由算法侧提供，业务侧通过 SDK 或接口调用。
- 为了适配 Python 生态和现有 Java 系统，中间封装一层 Python 微服务。
- 微服务负责业务流程编排、参数封装、会话管理、存储持久化、对外接口暴露。
- 最终通过统一注册发现机制接入现有系统，减少对原有架构的侵入。

**话术示例**
当时智能体能力是通过 SDK 的方式提供给我们的。因为这类能力和工具链很多都在 Python 生态里，所以我中间封装了一层 Python 微服务，把模型调用和业务系统之间隔开。这个服务不是简单转发，我在里面补了流程编排、工具配置、网络请求、聊天记录持久化和会话管理这些能力。最后它再和原有 Java 微服务一样，接入现有的服务注册发现体系里，这样原系统基本不用推翻重来，只是在原链路上多了一层 AI 能力。

### 7. 模型部署方式和你的职责边界

**问题**：模型本身是怎么部署的？是不是算法团队部署好后，你通过 SDK 或网络接口去调用它？

**我的答案要点**
- 模型的本地化部署不是自己做的，由其他同事完成。
- 自己拿到的是一个已经封装好的能力包，接入后可以创建对话、发送消息并拿到返回。
- 自己主要负责把这个能力写成服务，并连接到之前的 Java 服务器中。
- SDK 内部实现不是自己写的，自己负责的是业务接入侧。

**评价**
- 优点：职责边界比较清楚，没有夸大自己做过底层部署。
- 不足：这段回答被面试官带着走，显得有点被动确认；如果下次遇到类似问题，应该更主动地把部署形态、调用方式和自己的职责闭环讲完整。

**参考答案要点**
- 模型通常由算法 / 平台侧完成本地化部署，运行在独立算力环境上。
- 业务开发侧拿到的是 SDK 或服务接口，然后做服务封装与业务编排。
- 你的核心价值在于把模型能力接入业务流程，并补足权限、会话、日志、异常处理、持久化这些应用层能力。
- 这样回答既真实，也能体现你在系统集成上的价值。

**话术示例**
这部分职责我会分清楚。模型的本地化部署和底层运行环境一般是算法或平台侧完成，我拿到的是已经可以调用的 SDK 或服务能力。我的工作重点是在业务侧把这项能力接起来，包括封装成服务、接进原有系统、补会话和持久化能力、处理调用链路和异常情况。所以从职责上看，我不是做底层模型部署的人，但我是把这项能力真正落到业务系统里的那个人。

### 8. 离职原因

**问题**：你现在是离职状态吗？方便透露一下离职原因吗？

**我的答案要点**
- 是离职状态，离职时间是去年 12 月。

- 当时公司给过转岗机会，但转去的是相对独立、技术栈更封闭的部门。
- 自己判断那相当于重新开始，所以选择出来看看新的机会。
- 希望找一个发展更好的平台。

**评价**

**参考答案要点**
- 离职原因保持客观、中性、可验证。
- 强调是业务调整，不是个人问题。
- 说明自己做过转岗评估，最终是基于职业方向和技术成长做出的选择。
- 结尾把话题引回求职目标：希望找到更匹配自己能力结构的岗位。

**话术示例**
我目前是离职状态，主要原因是之前负责的那条业务线因为甲方合作变化，不再继续做了，这属于业务层面的客观调整。公司当时也提供过转岗机会，但对应部门的技术体系和业务方向跟我过去积累差异比较大，我评估下来相当于重新开始，所以更希望借这个机会找一个和自己能力结构、职业方向更匹配的平台。

## 四、待改进与盲区

### 4.1 岗位匹配表达

| --- | --- | --- |

### 4.2 技术回答

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **AI 接入项目介绍** | 第一轮回答偏概括，没有立刻把业务背景、系统链路、个人职责和结果讲完整。 | 练成 60 到 90 秒标准答案，结构固定为“背景 → 架构 → 我的职责 → 价值”。 |
| **智能体接入链路** | 亮点很多，但表达略乱，部分技术词不够稳定。 | 固化关键词：本地模型、SDK、Python 微服务、服务注册发现、会话管理、持久化。 |
| **方案选型题** | 缺少“为什么选这套方案”和“效果如何”的收口。 | 每个案例都补上约束、替代方案、收益三件事。 |

### 4.3 表达与结构

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **结论前置不够** | 多数回答是先讲细节，再慢慢讲到重点，容易让面试官抓不到主线。 | 先一句话说结论，再展开过程和例子。 |
| **会主动弱化自己** | 比如“Python 是现学的”“这部分我不会”，容易削弱交付感。 | 改成“为了落地这个场景，我快速补齐了 Python 服务侧开发能力”。 |
| **缺少结果量化** | 讲了做法，但很少讲结果，比如复用成本节省、交付效率、系统可维护性提升。 | 后续准备每个项目至少 1 到 2 个结果指标或业务收益。 |

## 五、后续行动

### 5.1 短期（针对二面 / 同类岗位）

1. 准备一版 60 秒的管理岗自我介绍，核心定位改成“前端出身的全栈技术负责人 / 小团队带队者”。
2. 单独准备三道高频管理题：怎么搭软件团队、怎么管理外包、怎么做交付验收。
3. 把 AI 接入项目整理成一版 90 秒稳定话术，结构固定为“业务背景、架构链路、职责边界、业务价值”。
4. 准备“如果入职后如何统一公司软件技术路线”的回答，贴近这个岗位的真实需求。

### 5.2 中期（知识补全）

1. 补齐软件项目管理相关内容：需求拆解、里程碑管理、验收测试、上线流程、运维协同。
2. 补齐对外包管理的表达框架：供应商选择、过程管控、质量门槛、风险兜底。
3. 梳理本地模型接入的通用架构图，形成可复用的表达模板。

### 5.3 简历与话术

1. 考虑把“AI 预警文案生成接入”补进简历或项目储备话术里，哪怕不单列项目，也可以作为亮点补充。
2. 把“小组长经历”从“分任务”升级成“带队推进交付”的表达，补结果和产出。
3. 所有项目答案都补一个“为什么这么设计”和“最终带来什么收益”的收口句。

## 六、小结

这场一面里，你的真实项目经历、带小组经验和 AI 接入落地经验是有竞争力的，尤其是架构选型和系统接入这两块，不像只背概念的人。问题主要不在技术能力本身，而在岗位匹配表达上，你还没有完全把自己切到“软件部门负责人 / 外包管理接口人”的视角。下一步重点不是补更多零散技术点，而是把“管理价值、交付能力、技术统筹能力”这三件事用更稳定的话术打出来。
