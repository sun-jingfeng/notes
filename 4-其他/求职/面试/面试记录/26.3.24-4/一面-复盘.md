## 二、逐题复盘（问题 → 我的答案 → 评价 → 参考答案 → 话术）

### 1. 介绍这一年里做过的 AI 智能体落地项目【8 分】

**问题**：这一年里有没有围绕 AI 智能体做过比较具体的项目？当前有哪些场景、解决了什么问题、用了哪些技术？

**我的答案要点**
- 回答分成两块：一块是编码提效，一块是智能体落地。
- 公司从去年年初开始推动 AI 提效和智能体落地，面向的是事业单位或国企场景，因此使用的是私有化部署模型。
- 自己做过一个“智能生成预警文案”的功能，业务场景是气象项目中的预警文案生成。
- 原有体系是 Java 微服务，自己额外用 Python 写了一个微服务，把智能体 SDK 能力接进原有 Java 微服务集群。
- 设计上包含会话创建、上下文续聊、工具调用、图式节点编排等能力。
- 前端传入已选气象要素和时间，Java 侧读取业务数据后喂给模型，模型返回标准化文案给前端展示和复制。
- 会话信息带 `sessionId`，重复生成时会基于历史上下文续聊。
- 会话缓存使用 Redis，缓存时长一天；服务注册与调用沿用了原有微服务体系。

**评价**
- 优点：这题核心经历是有说服力的，讲出了真实业务场景、系统链路、技术选型和自己负责的内容，不像只停留在“会用 AI”这个层面。
- 不足：回答顺序有点散，专有名词也受转写影响比较乱，没有第一时间把“背景、架构、职责、结果”四件事打清楚；另外缺少上线后的业务收益或效率提升说明。

**参考答案要点**
- 先讲业务背景：原来预警文案更多依赖人工整理和编写，效率和一致性受限，所以引入 AI 生成功能。
- 再讲架构方案：保留原有 Java 微服务体系，在中间新增一层 Python 微服务，负责承接智能体 SDK、会话管理、上下文续聊和编排逻辑。
- 再讲自己职责：负责把智能体能力真正接入现有业务系统，包括接口设计、会话管理、缓存、服务注册、前后端联调。
- 再讲设计理由：选择 Python 是因为智能体生态更成熟，能更快利用现有工具和编排能力，同时对原有 Java 系统侵入较小。
- 最后讲价值：把模型能力变成业务流程里可直接使用的功能，而不是单独做一个演示系统。

**话术示例**
我去年做过一个比较完整的 AI 落地场景，是在气象项目里增加智能预警文案生成。这个场景原来更多依赖人工根据业务数据整理文案，效率和标准化程度都比较受限制，所以后面接入了私有化部署的大模型能力。原有后端体系是 Java 微服务，我没有去推翻原架构，而是中间补了一层 Python 微服务，专门负责承接智能体 SDK、会话管理、上下文续聊和编排逻辑，再通过现有服务注册和调用链路接回原系统。我的职责重点不是底层训练模型，而是把这项能力稳定接进业务流程里，让前端可以直接根据页面已选气象要素拿到可复制、可使用的预警文案。

### 2. 这个智能体项目有没有真正部署到客户环境【6 分】

**问题**：去年做过的智能体项目里，有没有已经生产上线，或者至少已经部署到客户那边的？有没有验收？

**我的答案要点**
- 业务是给气象局这类客户使用的，通常不是公网环境，而是部署在客户侧内网。
- 这个功能已经部署到客户环境。
- 项目最终验收状态自己不了解，主要由项目经理对接。
- 但可以确认的是，这项能力已经能在客户现场部署。

**评价**
- 优点：回答比较诚实，没有把自己不掌握的信息硬说成已验收或大规模上线。
- 不足：表达上略偏保守，容易让面试官听成“是否真的用起来还不确定”。这题更好的答法应该把“已部署、可运行、验收边界不在我这里”区分清楚。

**参考答案要点**
- 先明确交付形态：这是客户侧内网部署，不是互联网公开上线。
- 再明确进度：相关功能已经部署到客户环境，具备实际使用条件。
- 再划清职责边界：项目验收由项目经理或商务推进，自己负责的是功能实现、联调和可部署性。
- 如果没有量化数据，就不要编造，但要把“已经落地到客户环境”这件事说稳。

**话术示例**
这个项目的交付形态和互联网产品不一样，它主要是部署在客户内网环境里。就我负责的这部分来说，这个智能文案生成功能已经部署到客户侧，说明它不是停留在 Demo，而是进入了实际交付链路。至于最终项目验收节点是不是已经完全走完，这部分更多是项目经理在对接，我不掌握最终商务口径，但从研发落地角度看，这项能力已经具备了可部署、可联调、可使用的条件。

### 3. Cursor、OpenCode、Copilot 这些工具在业务里怎么用【7 分】

**问题**：你对 Cursor、OpenCode、Copilot 这些工具比较熟悉，那在实际业务里有没有具体应用？

**我的答案要点**
- 回答是有，且用得比较多的是 Cursor，OpenCode 相对少一些，主要还是在编辑器里使用 AI。
- 日常开发大头还是前后端项目开发，前端更多在 Cursor 里做，后端在 IDEA 里通过插件配合使用。
- 认为这些工具的核心价值，不只是写代码更快，而是和 AI 沟通的成本更低。
- 之前直接让 AI 写代码，任务一复杂就容易跑偏；后面通过 `Rules` 和 `Skills` 把规则持久化之后，首轮结果更稳定。
- `Rules` 里会放基础全局信息，比如 Java 版本、JDK 版本这类环境和默认约束。
- `Skills` 里会放项目级任务规范，比如组件拆分、项目配置、其他垂直任务模板。
- 自己会根据已有项目代码，让 AI 先提炼一版任务规范，再在后续开发中不断补充完善。

**评价**
- 优点：这题体现出你不是把 AI 当搜索框来用，而是已经形成了“沉淀规则、复用上下文、持续迭代”的工程化用法，这一点很加分。
- 不足：回答里工具名、模型名、配置名都挤在一起，信息很多但主线不够清晰。下次最好先说方法论，再说工具和例子。

**参考答案要点**
- 先给使用原则：AI 负责高重复、低歧义、易验证的工作，人来负责架构边界、任务拆分和最终验收。
- 再给工具分工：IDE 类工具负责项目内读代码和改代码，Agent / CLI 类工具负责环境、脚本、跨文件任务，聊天类工具负责方案讨论和知识查证。
- 再讲沉淀方式：把跨项目稳定的信息沉淀成 `Rules`，把项目内高频任务说明沉淀成 `Skills`。
- 最后讲收益：减少重复提示、提升首轮命中率、降低 AI 输出风格漂移。

**话术示例**
我在业务里用这些工具已经不是临时提问的方式了，而是把它们当成开发流程的一部分。我的原则是，人来定架构、边界和验收标准，AI 去做高重复、低歧义、容易验证的工作。具体分工上，像 Cursor 这类 IDE 工具更适合在项目上下文里直接改代码，后端我也会在 IDEA 里通过插件配合使用；如果是方案讨论或者查资料，会用聊天类工具；如果是跨文件或者脚本任务，再考虑 Agent 类工具。为了让输出更稳定，我会把跨项目通用的信息沉淀到 `Rules`，把项目里的高频任务规范沉淀到 `Skills`，这样后面和 AI 协作的成本会越来越低。

### 4. 这些 Rules 和 Skills 是放在平台里还是放在项目里【7 分】

**问题**：你说的这些规则，是放在某个平台里统一调用，还是直接放到项目里？

**我的答案要点**
- 回答是放到项目里，而不是单独做一个统一平台。
- 每个项目会有自己的一套 `Skills` 文件。
- 这些文件通常放在项目根目录。
- 实际驱动它们的还是 Cursor、Copilot 这类工具，在读取项目上下文时会一起读取这些规则文件。

**评价**
- 优点：核心信息是答出来了，说明你知道“规则资产”要和项目一起走，才能真正服务当前代码库。
- 不足：这一段和面试官有一个小的理解偏差，对“平台”这个词没有第一时间对齐，导致中间来回确认了两轮。以后碰到模糊词，先反问确认会更稳。

**参考答案要点**
- 先直接回答结论：规则文件是跟项目走的，放在项目根目录，而不是做成一个脱离项目的独立平台。
- 再说明原因：不同项目的技术栈、组件体系、目录结构和约束不同，项目级沉淀更贴合实际。
- 再补充使用方式：AI 工具在读取项目上下文时会一起读取这些文件，从而影响输出行为。

**话术示例**
我这套规则不是单独放在一个平台里统一调，而是跟项目绑定的，通常就放在项目根目录。原因很简单，不同项目的技术栈、组件体系和工程约束都不一样，只有跟着项目走，这些规则才真的有用。实际使用的时候，像 Cursor、Copilot 这类工具在读取项目上下文时，也会一起读取这些规则文件，所以 AI 生成结果会更贴近当前项目。

### 5. 你对 MCP 的理解和实践是什么【7 分】

**问题**：你现在说的 MCP，具体是做模型网关，还是说你怎么理解和使用它？

**我的答案要点**
- 回答是自己有在使用 MCP。
- 重点举的是设计稿实现的场景，尤其是 Figma 相关的接入。
- 以前如果让 AI 帮忙还原设计图，通常只能截图给 AI，再让它猜页面结构。
- 有了 MCP 之后，可以直接把设计稿地址给 AI，让它读取设计稿底层数据，而不是只看截图。
- 除了设计平台外，其他常见平台如果有对应接入，也可以通过 MCP 接给 AI 使用。

**评价**
- 优点：方向是对的，你抓住了 MCP 的真正价值之一，就是把上下文从“截图和文字描述”升级成“结构化数据接入”。
- 不足：这题的定义还是偏口语，没有先把 MCP 是什么一句话讲准；另外面试官把问题往“模型网关”方向问时，你也可以顺手区分“协议层”和“网关层”的概念，显得更专业。

**参考答案要点**
- 一句话定义：MCP 是一种让模型以统一方式连接外部工具和数据源的协议或接入方式。
- 业务价值：减少手工搬运上下文，提升模型拿到的信息准确度，并让模型具备更强的执行闭环能力。
- 个人实践：自己主要在设计稿实现场景里使用过 MCP，让 AI 直接读取设计稿结构，提高页面还原精度。
- 如果被追问“是不是模型网关”，可以补充：它更偏协议和工具接入层，不完全等同于统一模型网关。

**话术示例**
我对 MCP 的理解是，它更像一种统一的工具接入协议，让模型不只是听我描述，而是能直接连接外部工具和数据源。对我来说最有价值的实践是在设计稿实现这类场景里，比如以前我只能把设计稿截图发给 AI，它很多时候是在猜结构；接入 MCP 之后，我可以直接把设计稿链接给它，它拿到的是更结构化的底层信息，所以页面还原的准确度会明显更高。它和模型网关不是一个层面的概念，模型网关更偏统一模型访问，而 MCP 更偏工具和上下文接入。

## 四、待改进与盲区

### 4.1 技术回答

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **AI 项目介绍** | 信息很多，但顺序偏散，容易让面试官抓不到主线。 | 固化成“背景 → 架构 → 我的职责 → 结果”四段式，控制在 60 到 90 秒。 |
| **上线与验收表达** | “已部署”和“是否完成最终验收”没有明显拆开。 | 先明确客户侧部署已完成，再说明验收归项目经理跟进，研发侧已达到可部署可使用状态。 |

| 问题 | 不足 | 可补内容 |

## 五、后续行动

### 5.1 短期（针对二面 / 同类岗位）

1. 把 AI 项目介绍整理成一版 90 秒稳定话术，固定成“业务背景、架构链路、职责边界、落地价值”四段式。
2. 单独准备“已部署但验收不由我负责”这类边界表达，避免下次回答显得偏虚或偏保守。
3. 准备一版 AI 工具使用方法论，核心句式统一成“人定边界，AI 做重复实现，人做验收和收口”。
4. 准备一版 MCP 标准答案，至少能清楚区分它和模型网关、普通截图识图的差别。

### 5.2 中期（知识与表达补全）

1. 把自己实际用过的 AI 工具、模型、框架、微服务组件整理成一张术语表，统一说法。
2. 补齐“智能体接入到现有系统”的通用架构表达模板，后续遇到类似岗位可直接复用。
3. 为每个项目补 1 到 2 个结果指标或业务收益点，即使没有精确数据，也要能说清价值方向。

### 5.3 简历与话术

1. 考虑把“智能生成预警文案”作为 AI 落地亮点补进简历或项目扩展话术里。
2. 在简历或项目介绍中明确写出“Java 微服务 + Python 微服务 + 私有化模型接入”的关键词，提升岗位匹配度。
3. 后续所有项目回答都补一句“为什么这么设计”和“一句话价值总结”，减少只讲实现不讲结果的问题。

## 六、小结

这场一面的核心亮点，是你确实有 AI 能力接入业务系统的落地经历，而不是只会用编码助手生成代码。问题主要不在经历本身，而在表达上还不够收束，尤其是技术主线、术语准确性和业务价值收口这三块。只要把 AI 项目介绍、工具使用方法论和 MCP 定义这几题再打磨一轮，二面面对同类岗位时竞争力会更稳定。
