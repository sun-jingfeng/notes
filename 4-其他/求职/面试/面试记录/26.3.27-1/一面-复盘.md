### 1. 当前公司做什么项目，面向什么客户，团队规模怎样

**问题**：你们现在主要做什么项目，面向什么客户，团队规模大概怎样？

**我的答案要点**
- 当前公司主要做定制化气象软件，通过项目竞标和关系资源承接项目。
- 客户主要是国企、事业单位。
- 部门合并前前后端合计约 15 人，合并后约 30 人。
- 公司从 2025 年开始推动准全栈，后续项目不再严格区分前后端，要求一个人能完成项目交付。

**评价**
- 优点：把公司业务模式、客户类型、组织变化都说到了，能让面试官较快建立你的工作背景。
- 不足：第一题本质上是在让你铺垫项目背景，你的回答信息是够的，但略偏平铺直叙，没有主动把“这种环境为什么锻炼了我的全链路交付能力”顺手带出来。

**参考答案要点**
- 先用一句话定义公司业务：面向政企客户交付定制化气象软件。
- 再补客户画像和交付特点：项目制、定制化、稳定性要求高、偏交付型。
- 最后顺势引到个人能力成长：组织调整后开始要求准全栈，这让自己从前端进一步扩展到全链路交付。

**话术示例**
我上一家公司主要做定制化气象软件，客户以国企和事业单位为主，基本是项目制交付。我们会根据不同客户的业务场景去做气象预警、大屏展示这类系统。团队原来是前后端分工更明确，后来部门合并之后开始推动准全栈，一个人要能把前后端和交付链路一起接住，所以我也是在这个阶段把自己的能力从前端进一步扩到了全栈和智能体落地。

### 2. 你这个小组长主要负责什么

**问题**：你这个小组长带多少人，主要负责什么，绩效是不是你来打？

**我的答案要点**
- 小组一共 6 个人。
- 绩效主要由上级领导来打。
- 自己主要负责任务分配。
- 在具体项目中会担任项目负责人。
- 小组主要面向雷达预警这条业务线。

**评价**
- 优点：回答真实，没有把管理职责夸大，项目负责人和任务分配这两个点也能说明你确实承担过带人和推进职责。
- 不足：可以把“小组长”这件事答得更像能力证明，而不是岗位说明。比如补一句你如何拆任务、如何协调前后端、如何保证交付节奏，会更能体现带队价值。

**参考答案要点**
- 说明团队规模和自己在组织中的定位。
- 强调核心职责不是行政管理，而是任务拆解、方案推进、风险收口和项目交付。
- 如果绩效权不在自己手里，也可以补一句自己实际承担的影响力，比如评审、排期、协作推进。

**话术示例**
我当时带的是一个 6 人小组，严格来说不是那种完全行政化的管理岗，绩效还是领导来定。我更多承担的是项目推进型角色，比如任务拆解、人员分工、进度跟进，以及项目里的关键问题收口。具体到项目上，我经常也是项目负责人，所以我比较擅长的是一边自己下场做开发，一边把交付节奏和协作链路带起来。

### 3. 雷达预警业务线的产品形态和技术栈

**问题**：雷达预警这条业务线具体是做什么的，产品大概是什么样子，技术栈和整体架构怎样？

**我的答案要点**
- 雷达预警业务线本质上是定制化的气象预警软件。
- 产品以大屏为主，类似气象展示系统，通过散点图、风向站、预警点位等展示气象要素和预警信息。
- 前端技术栈是 React，早期也用过 Vue，新项目统一使用 React。
- 后端一直是 Java。
- 智能体相关功能使用 Python 开发。

**评价**
- 优点：核心信息完整，项目形态、前后端栈、智能体栈都讲清楚了，能够支撑你“全栈 + AI 应用”这个人设。
- 不足：这一题本来是很好的项目亮点题，但你讲得还不够聚焦。少了两层关键信息：一是业务痛点是什么，二是系统里最难的部分是什么。没有这两层，项目更像介绍产品，而不像介绍自己的价值。

**参考答案要点**
- 先说业务目标：服务气象局工作人员，对预警信息进行展示、研判和生成。
- 再说产品形态：大屏、地图、点位、时序信息、预警信息联动。
- 再说技术架构：前端 React、后端 Java、智能体 Python 微服务，按能力拆层。
- 最后补个人负责内容：自己负责哪些部分，做了什么关键推进。

**话术示例**
我们这条业务线做的是雷达预警类的气象软件，主要给气象局工作人员用，核心目标是把气象要素、预警点位和预警信息更直观地展示出来，并辅助他们做后续处置。产品形态上以大屏为主，会结合地图、点位、时序信息去展示。技术上前端现在统一是 React，后端一直是 Java，后来为了加智能体能力，我们又补了一层 Python 微服务。这个项目对我来说比较有代表性，因为它既有传统 Web 交付，也有后来接智能体能力的扩展。

### 4. 智能体是什么时候开始做的，是否已经上线

**问题**：智能体这块是什么时候开始做的，目前上线了吗？

**我的答案要点**
- 公司在 2025 年上半年开始推动 AI 相关建设和模型部署。
- 到 2025 年下半年，项目里开始正式加入智能体相关功能。
- 当前功能已经交付上线。

**评价**
- 优点：时间线交代清楚，也说明不是 Demo，而是真正交付过。
- 不足：可以顺带补一句“为什么在那个时间点开始做”，比如模型能力、内部部署条件、业务需求成熟度等，这样显得你对项目演进路径更有认知。

**参考答案要点**
- 给清楚时间线：先有内部模型部署，再有项目内落地。
- 说明触发条件：业务上需要更高效率地产出预警文案，技术上也具备可用条件。
- 强调结果：不是试验性质，而是已经作为交付能力落地。

**话术示例**
智能体这块是 2025 年下半年开始正式落到项目里的。前面公司先做了一段时间内部模型部署和基础能力准备，等模型真正能在内网稳定使用之后，我们才开始往项目里加智能体功能。最后这块不是停留在试验阶段，而是已经跟项目一起交付出去了，这一点其实也能说明我做的不是纸面上的 AI 方案，而是实际落地过的能力。

### 5. 你们是怎么接入模型的

**问题**：你简历里写的是基于 LangChain 做的，是怎么接的？是不是有团队专门封装了 SDK？

**我的答案要点**
- 使用的是公司内部团队基于 LangChain 封装后的 SDK。
- 项目环境主要在内网，不能直接使用云端 API。
- 使用的是公司自己部署的本地模型，而不是原生云端服务。

**评价**
- 优点：把“为什么不能直接调公有云模型”这个约束说清楚了，符合政企项目和内网环境的真实场景。
- 不足：这题还可以更完整一点。你可以再补一句自己在这条链路里具体负责什么，是主要使用封装能力，还是也参与了接入、调试、业务适配。否则容易让人觉得你只是调用现成 SDK。

**参考答案要点**
- 先说明接入形态：内部封装 SDK + 本地模型 + 内网部署。
- 再讲原因：安全、合规、网络环境约束。
- 最后讲自己的工作：围绕业务场景做工作流、工具调用、接口联通和提示词/规则配置，而不是底层模型训练。

**话术示例**
我们不是直接去调公有云 API，而是公司内部先基于 LangChain 做了一层 SDK 封装，我这边在项目里用的是这层封装后的能力。因为我们的项目大多跑在内网环境里，安全和合规要求比较高，所以模型也是公司自己本地部署的。我的工作重点不在底层模型训练，而是在业务侧把这套能力接进来，比如工作流编排、工具调用、接口打通，以及让它真正服务具体的预警文案生成场景。

### 6. 智能体整体是怎么实现的，有没有 RAG

**问题**：你们这个智能体主要包含哪几部分，有没有 RAG 或知识库之类的设计？

**我的答案要点**
- 你对“模块”这个提法一开始理解得不够顺，后面转成介绍实现方式。
- 原有后端是 Java 微服务。
- 后来单独开发了一个 Python 微服务，并通过注册中心与原来的 Java 微服务通信。
- 智能体内部包括对话创建、工具创建、节点配置、路由规则等。
- 做了部分缓存处理。
- 没有外部联网或知识库能力，都是本地能力。

**评价**
- 优点：最终还是把技术实现链路讲出来了，能看出你知道系统不是单一接口，而是有微服务拆分和工作流编排。
- 不足：这一题的失分点主要在第一反应。面试官问“模块”时，你没有立刻把它抽象成“模型层、路由层、工具层、数据层”这种结构，而是先卡了一下。类似问题在 AI 岗会很常见，建议你把自己的项目提前抽象成固定框架来回答。

**参考答案要点**
- 可以把智能体拆成几层来讲：接入层、路由层、工具层、模型执行层、缓存/状态层。
- 如果没有 RAG，就明确说当前没有知识库检索，主要是基于结构化业务数据和工具调用完成任务。
- 再补系统关系：Python 微服务承接智能体能力，和原 Java 业务服务解耦通信。

**话术示例**
如果按模块来拆，我会把我们这个智能体分成几层来看。第一层是接入层，前端或者业务接口把时间、气象要素这些参数传进来；第二层是路由和工作流层，负责判断该走哪类处理逻辑；第三层是工具层，不同业务场景会绑定不同的数据获取和处理工具；第四层是模型执行层，用来组织对话和生成结果；另外还有缓存这类辅助层。我们当前没有做 RAG 或外部知识库检索，主要还是基于本地业务数据和工具调用来完成预警文案生成。

### 7. 关键字路由是怎么做的

**问题**：你说的关键字路由具体是怎么实现的，是正则匹配还是别的方式？

**我的答案要点**
- 路由既有正则表达式，也有关键词包含匹配。
- 当出现某些特定关键词时，会路由到对应工具。
- 整体偏规则驱动，而不是语义级复杂意图识别。

**评价**
- 优点：回答直接，说明你清楚当前方案的真实实现，没有把规则路由说成很高级的智能决策。
- 不足：你可以进一步主动解释为什么这样设计，比如业务域固定、术语集中、实现简单稳定、可控性高。这样面试官会觉得这是你有意选择的工程方案，而不是能力不足的权宜之计。

**参考答案要点**
- 先说实现方式：正则 + 关键词匹配。
- 再说采用原因：业务语义相对收敛，规则可维护、稳定、成本低。
- 最后补边界：这类方案适合固定业务域，不适合开放域复杂意图路由。

**话术示例**
我们目前的路由没有做得特别复杂，主要还是正则和关键词包含匹配这两种方式。这样做的原因是业务域比较固定，像降水、预警点位、时间范围这些词都比较集中，用规则路由其实已经能满足需求，而且可控性更高、排查也更方便。它的边界我也比较清楚，就是适合这种垂直业务场景，如果以后做开放域问答或者更复杂的意图识别，可能就需要更强的语义路由能力。

### 8. 智能体具体解决了什么业务问题，输入输出是什么

**问题**：你整个智能体主要完成什么业务功能，它的输入输出是什么？

**我的答案要点**
- 智能体的核心业务功能是生成预警文案。
- 使用者主要是气象局工作人员。
- 原来流程是工作人员自己在系统里查看预警信息，再手动发布公告。
- 后来增加了根据当前预警信息自动生成文案的能力。
- 前端会传时间和气象要素给后端。
- 后端再去调原始数据，把原始数据和时间等上下文一起传给智能体。
- 智能体根据这些元数据生成预警文案。

**评价**
- 优点：这一题答得比较到位，业务价值、用户角色、原流程和优化后的流程都交代清楚了，属于本场回答里比较完整的一题。
- 不足：可以再补一句效果指标，比如节省了哪些人工操作、提高了什么效率、人工是否还要审核。哪怕没有精确数字，也可以给出定性收益。

**参考答案要点**
- 先说明业务痛点：原来人工查看预警信息并手动编写公告，效率低且依赖经验。
- 再说明输入：时间、气象要素、原始预警数据。
- 再说明输出：结构化或自然语言的预警文案，供人工审核或直接使用。
- 最后补结果：减少重复劳动，提升出文效率，但仍保留人工确认。

**话术示例**
我们这个智能体最核心的业务价值就是自动生成预警文案。以前工作人员要先在系统里看当前预警信息，再自己组织语言发公告，这个过程比较重复，也比较依赖人工经验。现在前端把时间和气象要素传给后端之后，后端会去拿对应的原始数据，再把这些上下文一起交给智能体，让它生成对应的预警文案。这样做的好处是能把重复性的文案组织工作自动化掉，但最终我认为还是应该保留人工审核，这样业务上更稳妥。

### 9. 你们是怎么用 LangGraph 组织工作流的

**问题**：你们是用 LangGraph 之类的工作流来组织的吗，里面核心有几个节点？

**我的答案要点**
- 目前基本使用 LangGraph 来组织工作流。
- 核心节点大概有七八个。
- 最开始是路由节点。
- 后面会创建不同处理不同类型数据的模型实例。
- 不同业务场景对应不同工具方法，例如降水分析和预警点使用的工具不同。
- 不同业务会创建对应的垂直对话模型，并绑定各自的工具。
- 通过路由让不同模型选择自己的工具并完成处理。

**评价**
- 优点：你讲出了“按业务拆垂直模型实例 + 绑定不同工具 + 路由分发”这个核心思路，说明你理解的不是单链路调用，而是有一定编排结构。
- 不足：术语表达略乱，特别是在口语和转写条件下，LangChain、LangGraph、工具节点、模型实例这些词容易混。建议后续把这一段练成固定答法，先讲结构，再讲节点数，最后讲一个具体链路。

**参考答案要点**
- 先讲工作流思路：入口路由节点决定走哪类业务链路。
- 再讲节点类型：数据准备、工具调用、模型生成、结果输出。
- 再讲为什么按业务拆实例：不同任务依赖的数据和工具不一样，拆开更清晰、可控。
- 最后补一句工程价值：方便扩展和调试。

**话术示例**
我们这块是按工作流思路来组织的，入口先有一个路由节点，判断当前请求更偏哪类业务场景。后面再进入对应的处理链路，不同链路会绑定不同的数据获取工具、分析工具和模型实例。比如降水分析和预警点相关的处理，它们依赖的数据和工具就不一样，所以我会把它们拆成更垂直的处理单元。这样做的好处是链路清晰，也方便后续扩展和排查。

### 10. 这套智能体有没有接外部知识库，其他地方还有没有用大模型

**问题**：这里面会涉及外部知识库吗？除了这一块，其他地方还有没有用到大模型能力？

**我的答案要点**
- 当前没有联网能力，也没有接外部知识库。
- 整体是本地能力闭环。
- 除了预警文案生成这块之外，其他业务暂时还是传统 Web 开发，没有进一步接入大模型能力。

**评价**
- 优点：边界答得清楚，不会为了显得“AI 用得多”而夸大应用范围。
- 不足：可以更主动一点，补一句为什么只在这一块落地最合适，比如因为文案生成最匹配大模型能力，ROI 最直接。这样会让你显得有产品和技术判断，而不是“只做了一点点”。

**参考答案要点**
- 明确当前范围：没有知识库、没有开放域联网，主要是单点业务场景落地。
- 说明原因：先从最适合大模型的文本生成场景切入，收益更直接。
- 补一句扩展思路：后续若做问答、知识辅助、规则解释，再考虑知识库或检索增强。

**话术示例**
我们当前这套智能体没有接外部知识库，也没有联网能力，整体还是在本地闭环里跑的。大模型目前主要就是用在预警文案生成这个场景上，其他业务部分还是传统 Web 开发。这个选择其实是有意为之，因为文案生成是最适合大模型发挥价值、也最容易在业务上看到收益的场景，后续如果要继续扩展，再去考虑知识库检索或者问答类能力会更合适。

### 11. 上一家公司做什么，你当时主要负责什么

**问题**：我看你之前在百炼智能待过一段时间，那边是做什么的，你主要做什么？

**我的答案要点**
- 百炼智能主要做 B 端智能货车相关系统。
- 业务模式是 SaaS 收费，客户是企业。
- 你在那边主要做前端。
- 你后续是从前端逐步转向全栈。

**评价**
- 优点：这题能辅助说明你的职业演进路径，从纯前端到全栈，和当前岗位要求是匹配的。
- 不足：回答偏短，少了“我在那里做过什么有代表性的东西”。这种经历题如果只讲公司做什么，会浪费展示空间。

**参考答案要点**
- 先说公司业务和服务对象。
- 再说自己承担的职责和核心成果。
- 最后把它和现在的能力演进衔接起来，说明为什么自己能从前端成长到全链路交付。

**话术示例**
我之前在百炼智能那段经历主要还是偏前端，当时公司做的是 B 端智能货车相关系统，整体是 SaaS 交付模式，客户以企业为主。那段经历对我最大的价值是把前端工程能力打得比较扎实，后面到了新的环境，随着项目要求一个人承担更多链路，我才逐步把能力扩展到后端和更完整的项目交付上。

***

### 12. 智能体项目开始做时，你的 Python 能力够不够

**问题**：你们这边智能体项目是去年开始做的吧，当时你的 Python 能力怎么样？

**我的答案要点**
- 智能体功能大概是 2025 年七八月份开始加的。
- 当时公司自己的模型已经部署完成，可以使用。
- 你认为自己有语法级别的 Python 掌握，写一个智能体没有问题。

**评价**
- 优点：你没有回避“不是纯 Python 出身”这个事实，回答比较诚实。
- 不足：这一题的风险在于“语法级别掌握”听起来会偏弱，容易让面试官担心你的 Python 工程能力。更好的答法应该是强调你在项目驱动下已经能完成服务开发、接口联通、工作流编排和落地交付，而不是停留在语法层面。

**参考答案要点**
- 可以承认自己不是长期纯 Python 开发出身。
- 但要强调能力边界：足以完成智能体服务开发、接口封装、工作流编排、调试和交付。
- 如果底层工程化深度还不够，也要把短板说成“还在持续补强”，不要让自己显得只会语法。

**话术示例**
我不是那种长期做 Python 后端出身的人，这一点我会如实说。但到了智能体项目阶段，我的 Python 能力已经足够支持业务落地了，比如写微服务、做接口封装、接工作流、调工具链路，这些我都能完成。换句话说，我的优势不在于炫 Python 语法，而在于能把它放进真实项目里解决问题并交付出来。当然更深的 Python 工程化细节，我也还在持续补强。

### 13. 目前在职状态和离职原因

**问题**：你现在还在职吗，去年 12 月离职的原因是什么？

**我的答案要点**
- 你已经离职，时间是 2025 年 12 月。
- 离职后先回老家休整，2026 年 3 月初来北京重新找工作。
- 离职原因是业务线解散，雷达预警业务原本每年能接到三四个项目，后续因为业务关系变化导致项目承接变差。

**评价**
- 优点：离职原因基本算客观，也给出了时间线。
- 不足：最后一句“领导和那面的关系不好”这种表述风险很大，容易显得情绪化，也会给面试官留下你评价前公司管理层的印象。离职原因最好统一收束成业务调整、业务线收缩、项目减少。

**参考答案要点**
- 状态直接说清楚：已离职，可尽快到岗。
- 离职原因尽量客观中性：业务线调整、项目减少、组织变化。
- 强调自己不是被动躺平，而是在空档期做了休整和能力补充，当前求职方向也更明确。

**话术示例**
我现在是离职状态，去年 12 月离开的，可以比较快到岗。离职的主要原因是当时业务线做了调整，项目机会明显减少，继续待下去对我后续成长帮助有限，所以我选择出来看新的机会。中间我也做了一段休整和方向梳理，现在再找工作，目标会更聚焦在全栈交付和智能体落地相关的岗位上。

### 14. 反问环节：对方做什么产品，岗位是不是要求全栈和智能体能力

**问题**：你最后问了对方什么，对方给了什么信息？

**我的答案要点**
- 你询问了对方公司主要做什么产品。
- 对方表示主要做智能客服类产品，包括文本机器人、语音机器人等。
- 你进一步确认是否涉及外部应用与智能体结合。
- 对方表示大部分产品都包含 AI 能力，而且在大语言模型出现之前就已经在做相关产品。
- 你又确认岗位是否要求全栈交付和智能体开发能力。
- 对方表示当前主要招的是 Python 方向，偏 LangChain / LangGraph 这类能力。
- 对方前端和后端分别有专门岗位，但也在使用外部 AI 编程工具。
- 你最后补充自己有单人完成前后端项目交付和智能体落地的能力。

**评价**
- 优点：反问没有浪费，问到了产品方向、AI 占比、岗位能力模型，整体是有效信息获取。
- 不足：最后这段自我补充有一点仓促，更好的方式是把它收成一句更强的岗位匹配总结，比如“我过去的经历和你们这个岗位的要求有较高重合度”。另外，如果能再问一句团队当前最需要这个岗位解决什么问题，会更有价值。

**参考答案要点**
- 反问优先问三类问题：产品方向、岗位核心诉求、当前最紧急业务问题。
- 在听完岗位描述后，主动做一次 20 秒匹配总结。
- 如果岗位偏 Python / 智能体，可以顺势强调自己虽不是纯 Python 出身，但有真实项目落地和全链路交付经验。

**话术示例**
我一般会在反问环节重点确认三件事：第一是你们现在核心产品和业务场景是什么，第二是这个岗位最核心的能力要求是什么，第三是入职后最先要解决的问题是什么。因为这场面试里对方明确提到了智能客服、Python 和智能体开发，所以我后面其实可以更主动地做一个匹配总结，比如我过去已经做过前后端一体化交付，也做过智能体落地，这和岗位要求是比较贴近的。

## 四、待改进与盲区

### 4.1 技术回答

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **智能体架构抽象不够稳定** | 被问到“模块”“RAG”时第一反应有些卡顿，没有立刻把项目抽象成固定结构。 | 提前准备一套统一框架：接入层、路由层、工具层、模型层、缓存层、输出层。 |
| **工作流术语表达偏乱** | LangChain、LangGraph、SDK、节点、模型实例这些词在口语里容易混。 | 统一术语口径，练习一版 1 分钟标准表述，避免现场口误。 |
| **Python 能力表述偏弱** | “语法级别掌握”会让面试官误判你工程能力不足。 | 改成“能完成智能体微服务、接口封装、工作流编排和项目交付，底层工程化仍在持续加强”。 |
| **规则路由的工程取舍没有讲出来** | 只说了正则和关键词匹配，没说为什么这么设计。 | 补充业务域固定、规则可控、维护成本低、便于排查这类工程理由。 |

### 4.2 表达与结构

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **项目题回答偏“介绍产品”** | 讲了系统是什么，但没有始终围绕“业务痛点、技术方案、个人贡献、结果”这个主线。 | 后续项目题统一按“四段式”回答：背景、问题、方案、结果。 |
| **有些题缺少收束句** | 回答完信息点后，没有顺手把结论再落回岗位匹配或个人价值。 | 每题最后补一句“这体现了我什么能力”。 |
| **离职原因表述有风险** | 提到前公司领导关系问题，容易显得不够职业。 | 统一改成业务线调整、项目减少、组织变化。 |

### 4.3 术语与专有名词

| 问题 | 不足 | 可补内容 |
| --- | --- | --- |
| **转写暴露出术语易混** | 录音转写中出现了“right”“lock up”“狼狗APP”“rights”等失真词，说明现场发音和术语连续表达可能不够稳。 | 重点把 LangChain、LangGraph、RAG、SDK、关键词路由、微服务注册通信这些词练熟。 |
| **AI 岗常见概念准备不够体系化** | 面试官一提 RAG、模块划分，就暴露出准备不够模板化。 | 建议把“智能体架构、RAG、工作流、工具调用、模型接入、评估与缓存”各准备一版标准答法。 |

## 五、后续行动

1. 把当前这个气象预警智能体项目整理成一版 3 分钟项目介绍，固定结构为“业务背景 → 系统架构 → 智能体方案 → 个人贡献 → 上线结果”。
2. 单独准备一版 AI 岗高频追问答案，包括“有没有 RAG”“为什么不用 RAG”“工作流怎么拆”“路由怎么做”“Python 在项目里负责到什么深度”。
3. 把 LangChain、LangGraph、RAG、SDK、微服务通信、关键词路由这些术语统一成稳定口径，避免面试时说乱。
4. 重写离职原因话术，收束为“业务线调整和项目机会减少”，不要再提具体人际或关系因素。
5. 准备一段更强的岗位匹配总结，适用于反问之后的收口，例如“我过去的经历和你们当前岗位在全链路交付、智能体落地上有较高重合度”。
6. 把 Python 能力表述从“会语法”升级成“能支撑真实业务落地，但还在继续补工程化深度”，避免被误判能力层级。

## 六、小结

这场一面的优势在于项目经历真实，尤其是气象预警场景下的智能体落地，具备一定区分度。主要问题不在于没有做事，而在于对 AI 项目的抽象表达还不够成熟，导致一些本来有含金量的内容没有被清晰讲出来。下一步重点不是补更多项目，而是把现有项目整理成更标准、更像 AI 岗候选人的表达方式。
