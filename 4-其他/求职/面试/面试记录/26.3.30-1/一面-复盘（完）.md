### 1. 最近这个项目里，你具体做了什么，承担什么角色【6.5 分】

**问题**：结合最近的项目，讲一下你用了哪些技术、承担了什么角色、具体做了哪些工作。

**我的答案要点**
- 介绍了最近的雷达预警项目。
- 项目总人数约 40 人。
- 自己前后端都做，除自己外还有 2 个前端和 1 个后端协作。
- 自己大致承担前端 40%、后端 60% 的工作量。
- 前端是父子项目结构，后端从单体逐步拆成微服务。
- 后续又加入了智能体功能，智能体部分用 Python 微服务接入 Java 微服务体系。

**评价**
- 优点：项目体量、技术跨度、个人占比和全栈角色都交代到了，能证明你不是只做单点开发。
- 不足：这题本来是建立面试官第一印象的关键题，但你的回答停留在“项目概况”，没有迅速落到“我具体负责什么业务、解决了什么问题、产出了什么结果”上，导致后面面试官连续追问。

**参考答案要点**
- 先用一句话定义项目：雷达预警系统，服务气象业务场景。
- 再说自己的定位：既做前端，也承担较多后端开发，同时是项目负责人 / 小组长角色。
- 再说自己真正负责的内容：前端哪些页面或模块、后端哪些服务、智能体接入哪一段链路。
- 最后补项目价值：比如支撑省份差异化需求、提高预警信息处理效率、完成 AI 能力接入。

**话术示例**
我最近做的是一个雷达预警项目，整体是面向气象预警场景的系统。这个项目团队大概 40 人，我在其中既做前端也做后端，实际承担的后端工作会更多一些，同时也承担了项目负责人和小组长的职责。前端这边我负责核心页面和联动逻辑，后端这边我参与了从单体到微服务的拆分，以及后面智能体能力接入原有 Java 微服务体系这部分工作。这个项目对我来说比较有代表性，因为它既有传统 Web 交付，也有全栈协作和 AI 落地。

### 2. 你在 Java 服务和微服务拆分里到底落地做了什么【6 分】

**问题**：你刚才说后端从单体拆成微服务，那具体拆成了哪些部分？你自己承担的是哪几块？这些服务分别做什么，落地用了哪些技术？

**我的答案要点**
- 回答了从单体拆到微服务的大方向。
- 提到有共享服务，承接所有省份共用的逻辑；各省份再有各自独立的微服务做定制化需求。
- 使用了 Nacos 做服务注册与配置管理。
- 服务间调用使用 OpenFeign。
- 为了防止雪崩和做熔断降级，使用了 Sentinel。
- 预警消息提示这类异步能力后来改成消息队列处理。
- 进一步举了一个性能瓶颈例子：矩阵数据计算有压力时，通过熔断后的兜底方案降低计算精度，但仍返回前端可用结果。

**评价**
- 优点：你说到了微服务改造里几个关键基础设施，也提到了性能瓶颈、降级和消息队列，说明你不是完全没做过后端。
- 不足：这是本场最明显的失分点之一。面试官想听的是“你写过哪些具体服务、具体业务职责、具体代码和问题”，而你回答成了“微服务常见技术栈介绍”。技术名词很多，但业务边界、服务清单、个人职责都不够具体，所以面试官才会连续强调“我要听你项目里真实落地的内容”。

**参考答案要点**
- 先给出拆分思路：共享能力放公共服务，省份差异化能力放各自的定制服务。
- 再说自己负责的真实服务或模块名称；如果现场不方便讲全量，至少说 2 到 3 个最核心的服务。
- 对每个服务按“职责 + 我做了什么 + 用到什么技术 + 解决了什么问题”展开。
- 技术栈不要孤立罗列，要和业务动作绑定：为什么用 Nacos、哪段调用用 OpenFeign、哪类高风险接口配置了 Sentinel、哪类通知链路改成了消息队列。
- 如果服务名一时说不全，也要明确说明“共享预警数据服务、消息通知链路、省份定制服务”这种层次，而不是只讲框架。

**话术示例**
这个项目后端一开始是单体，后面拆成微服务时，我们先按“共性能力”和“省份定制能力”去分。共性部分抽到共享服务里，比如预警数据的通用处理、部分公共配置和通用接口；省份差异化需求则放到各省自己的服务里。我自己主要参与了这两块里的接口开发和服务治理工作，包括把服务注册到 Nacos、通过 OpenFeign 去调用共享服务，以及对高风险链路做 Sentinel 的熔断和降级配置。项目里还有一类预警弹窗通知，原来是同步调用，后来改成消息队列异步处理，目的是降低主链路阻塞。面试里如果再被问到这题，我要重点把“我负责的具体服务职责”说清楚，而不是只讲框架名。

### 3. 你现在是怎么用 AI 做开发提效和项目落地的【7.5 分】

**问题**：你简历里写了 AI 提效和智能体落地，这块你现在具体是怎么做的？

**我的答案要点**
- 公司从去年开始推动 AI 提效。
- 前端和后端都在实际开发中使用 AI。
- 自己会先搭基础框架，再让 AI 处理机械化、重复性的工作。
- 前端会先拆清组件职责、定义传参方式、先写一个样例组件，再让 AI 参考同风格生成其他组件。
- 后端会先把接口分层、实体类和基础结构搭好，再让 AI 去补同一路径下的类似请求。
- 提到会做提示词持久化，沉淀 `rules` 和 `skills`。
- `rules` 用于全局约束，如技术栈和项目基础规则；`skills` 用于具体任务规范。
- 后续会在开发过程中不断补充和完善这些规范，让 AI 输出更贴合既有风格。
- 还提到接入 MCP 后，设计稿理解会更精确。

**评价**
- 优点：这题整体答得还可以，体现了你不是单纯“让 AI 直接写代码”，而是已经形成了“人搭骨架、AI 做重复实现、人审查收口”的工程化协作方式。
- 不足：信息点很多，但主线略散。工具、规则、技能、MCP、设计稿、前后端案例全部挤在一起，缺少一个稳定的表达框架。另一个问题是你说了“怎么做”，但还可以更明确地说“为什么这样做能避免 AI 跑偏”。

**参考答案要点**
- 先讲原则：人负责架构、边界、拆任务和验收，AI 负责高重复、低歧义、容易验证的实现。
- 再讲落地方法：先人工搭结构，再让 AI 按已有样例扩展。
- 再讲规范沉淀：用 `rules` 记录全局约束，用 `skills` 记录项目内高频任务范式。
- 最后讲收益：减少重复提示、降低输出风格漂移、提升首轮命中率和整体开发效率。

**话术示例**
我现在用 AI 做开发提效，核心思路不是把任务整块丢给它，而是我先把结构和边界定清楚，再让 AI 去完成高重复、低歧义的实现。比如前端我会先把页面拆成组件，把组件职责、参数和一个样例组件先写出来，后面再让 AI 参考这个样例去补其他组件；后端也是先把接口分层、实体和基础结构搭好，再让 AI 去补同类接口。为了减少每次重复说明，我会把全局约束沉淀成 rules，把项目里的高频任务规范沉淀成 skills，这样 AI 后面的输出会更稳定。我的原则一直是，人定边界，AI 做重复实现，人来审核和收口。

### 4. 大项目和多人协作里，怎么降低 AI 上下文偏移【7 分】

**问题**：在稍大一些的项目、多人协作的场景下，随着上下文越来越多，AI 很容易跑偏。你会怎么处理这个问题？

**我的答案要点**
- 多人协作上，先通过分支隔离降低互相影响。
- 任务拆分要足够细，把一次提问尽量限定在具体需求范围里。
- 给 AI 提需求时要尽量圈定问题边界，让代码集中在一个明确需求内。
- 如果是全局问题，比如权限控制，要明确告诉 AI 本次只解决哪一部分，不要波及其他代码。
- 必要时可以主动把涉及文件列给 AI，让它聚焦在更小范围内。
- 更谨慎时可以先让 AI 做计划和分析，再由人审核计划之后再执行。

**评价**
- 优点：这题答出了方法论，尤其是“人为切割问题”“先规划再执行”“明确范围和文件”的思路是对的，和真正的工程实践也一致。
- 不足：开头先落在 Git 分支协作上，有点偏离了面试官真正关心的“AI 上下文管理”主题。你后半段答得比前半段好，说明方向是对的，但可以更快把重点前置。

**参考答案要点**
- 先正面回答：大项目里核心不是把更多上下文一次性塞给 AI，而是把任务切小、目标切清、影响范围圈定。
- 再讲具体手段：限定需求范围、限定文件范围、限定改动边界、必要时先出计划。
- 再讲多人协作：通过分支和职责分工减少并发冲突，但这只是外围手段，不是解决上下文漂移的核心。
- 最后讲验收：每一步都要有人审，不能把大项目交给 AI 全自动完成。

**话术示例**
我对这个问题的理解是，大项目里不是上下文给得越多越好，关键是要把问题切小、把边界说清楚。我的做法一般是先把任务拆成很具体的子问题，再明确告诉 AI 这次只处理哪一块、涉及哪些文件、不能影响哪些部分。如果任务风险比较高，我会先让它出一版计划，我先审核计划没问题，再让它动代码。多人协作里分支隔离当然也重要，但那更多是团队协作层面的手段；真正减少 AI 跑偏，还是靠人主动做任务切割和边界控制。

### 5. 引入 AI 之后，你自己的效率提升了多少，你在团队里是什么角色【7 分】

**问题**：引入 AI 之后，你个人效率大概提升多少？你在团队里是不是承担了小组长或项目负责人的角色？

**我的答案要点**
- 认为个人效率提升在 3 倍以上。
- 当前项目中除自己外还有 2 个前端和 1 个后端组员。
- 自己既是小组长，也是项目负责人。

**评价**
- 优点：回答简洁直接，角色也说清楚了，能体现你不只是执行者。
- 不足：这题如果只回答“3 倍以上”，说服力会偏弱。最好补一层“效率提升体现在哪”，比如样板代码生成、组件扩展、接口补齐、联调准备、文档整理等。角色方面也可以再落一句“我负责什么”，这样更像真实负责人，而不只是职位名。

**参考答案要点**
- 效率提升不要只给倍数，要补维度：编码速度、样板生成、重复功能开发、联调前准备等。
- 负责人角色要说职责：任务拆解、分工推进、关键问题收口、项目节奏控制。
- 如果没有量化数据，用“重复实现类任务提升明显，复杂架构类任务仍需人工主导”这种说法更稳。

**话术示例**
如果说整体体感，我自己的开发效率提升在 3 倍以上，尤其是在组件扩展、同类接口补齐、样板代码生成这类重复实现任务上会特别明显。但我不会把这个理解成所有事情都快 3 倍，像架构设计、关键链路和最终验收，还是得靠人主导。团队角色上，我既是小组长，也是项目负责人，除了自己写代码，还会做任务拆解、分工推进和关键问题收口。

### 6. 你的技术背景是怎么演进到现在这个全栈方向的【7 分】

**问题**：你前端主要是 Vue 和 React 吗？是不是从前端转到全栈的？后端 Java 和 Python 是从什么时候开始做的？

**我的答案要点**
- 前端之前主要用 Vue，后面随着公司节奏调整又统一用了 React。
- 自己觉得 Vue 更熟练一些，但 React 也在实际项目中使用。
- 职业起点是前端。
- 从去年开始，随着部门改革和公司推动准全栈，开始补后端能力。
- 后端主要使用 Java，也做了 Python 微服务相关工作。

**评价**
- 优点：技术成长路径是清楚的，和你当前“Vue / React + Java + Python”的组合能对应上。
- 不足：这题答得比较平，没有把“为什么你能转得过来”说出来。你其实可以顺手补一句：因为过去一直做项目负责人、懂业务链路，再加上公司推全栈和 AI 提效，所以完成了从前端到全链路交付的扩展。

**参考答案要点**
- 先讲当前技术覆盖：前端 Vue / React，后端 Java，AI / 智能体侧有 Python 实践。
- 再讲演进路径：先前端，后全栈，再到 AI 接入。
- 最后讲原因：组织变化、项目要求、个人主动补齐，最终形成可独立承担更多交付链路的能力。

**话术示例**
我最开始是以前端为主，Vue 用得更早也更熟，后面公司技术栈逐步统一到 React，我也在实际项目里持续使用。真正往全栈方向转，是从去年公司推动准全栈开始的，因为后面一个项目里不再严格分前后端，很多时候要一个人把更多链路接住，所以我开始系统补 Java 后端能力。再往后因为项目里接了智能体能力，我又做了 Python 微服务相关的工作，所以现在我更像是从前端起步，逐步扩展到全栈和 AI 接入这一条线。

2. 单独准备“微服务拆分与我负责的具体服务”答案，至少能稳定说出 2 到 3 个真实服务或模块的职责、接口和问题处理。
3. 把 AI 提效方法论压缩成一版短答案，核心只保留“人定边界、AI 做重复实现、人审查收口”。
4. 为“效率提升 3 倍以上”补充支撑场景，例如组件扩展、同类接口补齐、样板代码生成、联调准备等。
5. 统一一版技术术语表，至少把 Nacos、OpenFeign、Sentinel、消息队列、中间件名称说准。
6. 针对下一轮面试，补一版“从前端到全栈再到 AI 接入”的成长路径话术，让岗位匹配度表达得更顺。

***

## 六、小结

这场面试的核心优势，是你的项目体量、全栈跨度和 AI 提效实践都是真实存在的，岗位匹配度也比较高。短板不在经历本身，而在于回答时容易停留在框架层，缺少“我具体写了什么、负责了什么、解决了什么问题”的落点。只要把项目介绍和微服务落地这两题重新打磨一轮，你后面的说服力会明显提升。
