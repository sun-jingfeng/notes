**话术示例**

后面处理上，我会把任务放到自定义线程池里做隔离，同时把原先可能存在共享可变对象的地方改成无状态或局部变量处理，再配合超时、熔断和降级。验证阶段不是只看接口恢复，还会做压测和结果一致性校验，确保并发上来以后既快又不会算错。

### 6. 自定义线程池参数设计【6.5 分】

**问题**

自定义线程池的核心线程数、最大线程数、队列大小是怎么配置的，为什么这样配？

**我的答案要点**

- 记录显示你讲过线程池配置思路，但具体数值和依据未保留。
- 结合上下文，这道题应该围绕多线程计算场景展开。

**评价**

- 优点：能进入线程池参数层面的回答，说明不是只会用默认线程池。
- 不足：如果没有从 CPU 密集型还是 IO 密集型、任务耗时、机器核数、峰值流量、队列容忍度来解释，回答会比较泛。

**参考答案要点**

- 先区分任务类型：CPU 密集型线程数通常接近 CPU 核数，IO 密集型可适当放大。
- 核心线程数基于稳定流量设计，最大线程数基于峰值和机器承载设计。
- 队列大小要和超时、降级、拒绝策略一起设计，不能一味放大，否则只是延迟问题暴露。
- 拒绝策略要结合业务选，例如快速失败、记录日志、降级兜底。
- 参数最好来自压测和监控，不是拍脑袋。

**话术示例**

线程池参数我不会脱离场景单独定。首先要看任务是 CPU 密集还是 IO 密集，如果偏计算型，核心线程数一般会贴近 CPU 核数；如果有较多等待下游的时间，最大线程数可以适当放大一些。

队列也不是越大越好，因为队列太大只会把问题从“失败”变成“长时间排队”。我更倾向于结合接口超时、机器资源和业务容忍度一起定，然后再通过压测去验证活跃线程数、队列积压和 RT 曲线，最后把参数调到一个稳定区间。

### 7. 熔断降级触发机制【6.5 分】

你提到熔断后降低计算精度，降级逻辑是根据哪些指标触发的？

**我的答案要点**

- 提到了熔断后降低计算精度作为降级方案。
- 具体触发指标在记录中没有保留，待补充。

**评价**

- 优点：回答里有“服务可用性优先”的意识，不是只谈功能正确性。
- 不足：如果说不清楚触发条件，降级就容易被理解成拍脑袋。生产环境里通常要有明确的 RT、错误率、线程池积压、下游超时等指标门槛。

**参考答案要点**

- 可以用 Sentinel 或自研规则基于滑动窗口统计。

降级后的目标也要清楚，不是简单报错，而是尽量保核心功能可用。像计算场景里可以返回低精度结果、缓存结果或者裁剪掉非关键计算项。恢复时也会设回切阈值，避免服务在降级和恢复之间来回抖动。

### 8. 并发改造后的线程安全验证【6.5 分】

**问题**

多线程改造后，你怎么验证没有引入线程安全问题，比如数据错乱或结果不一致？

**我的答案要点**

- 面试官明确追问了数据错乱、结果不一致、测试或验证方法。
- 原回答细节未记录，待补充。

**评价**

- 优点：如果你有回答，说明你知道并发改造不能只看性能，还要看正确性。
- 不足：这题最好把“功能正确性验证”和“压测稳定性验证”分开讲；很多人只讲压测，忽略结果一致性校验。

**参考答案要点**

- 先做单线程基线结果，作为并发版本的对照样本。
- 用固定输入多次压测，对比结果是否一致。
- 对共享对象、缓存、集合写入、上下文传递等高风险点做专项测试。
- 压测同时观察异常日志、线程池指标、CPU、GC 和接口 RT。
- 必要时引入幂等校验、校验和、结果快照比对。

**话术示例**

并发改造之后，我不会只看吞吐有没有提升，还会先拿单线程版本跑出一份基线结果，然后用相同输入去跑并发版本，多轮比对结果是否一致。因为很多并发问题不是直接报错，而是偶发算错，这种只看 RT 是发现不了的。

另外我也会重点盯共享状态相关的地方，比如是否有可变对象被多个线程复用、集合是不是线程安全、上下文数据有没有串线程。最后再结合压测和监控看性能指标，确保正确性和稳定性都过关。

### 9. GC 与线上排障案例【6.5 分】

**问题**

请讲一次你排查 JVM 或 GC 相关线上问题的过程，看过哪些关键证据，如何下结论。

**我的答案要点**

- 从面试官反馈看，你的排查流程主要基于日志进行定位。
- 更具体的 GC 日志、线程 CPU、热点方法等证据未完整记录。

**评价**

- 优点：至少有先从现象和日志切入的排查习惯。
- 不足：这题如果只停留在“看日志”，深度不够。JVM 问题通常要讲指标、日志和工具三件套：GC 日志、线程/CPU、堆内存或热点方法分析。

**参考答案要点**

- 先确认故障现象：RT 变慢、CPU 飙高、Full GC 频繁、内存持续上涨。
- 证据链包括 JVM 指标、GC 日志、线程 dump、top/jstack、Arthas、APM。
- 如果是 GC 问题，要说清楚年轻代回收频率、老年代占用、停顿时间、是否发生 Full GC。
- 如果不是 GC，也要能通过证据排除 GC，把方向收敛到线程阻塞、锁竞争或慢 SQL。

**话术示例**

我排查 JVM 或 GC 问题时，不会一上来就猜结论，而是先看现象到底是 RT 变慢、CPU 高，还是内存持续上涨。接着会结合 JVM 指标和 GC 日志去判断是不是 GC 频率异常、停顿时间变长，或者老年代压力过大。

如果 GC 迹象不明显，我会继续看线程栈、热点方法和下游调用耗时，把问题往线程阻塞、锁竞争或者 SQL 慢查询这些方向收敛。核心是证据链要完整，最后能解释为什么是这个根因，而不是拍脑袋判断。

**问题**

如果接口平时 200ms，突然变成 2 秒以上但没有报错，你会怎么排查？会看哪些 JVM 指标和工具？

**我的答案要点**

- 面试官是基于你前面的回答继续追问，说明你的回答未完全覆盖这一类“慢但不报错”的场景。
- 具体回答内容记录过简，待补充。

**评价**

- 优点：这是典型线上问题，补齐后很适合作为高频答题模板。
- 不足：慢请求排查不能只谈 GC，还要覆盖线程池、数据库、缓存、下游服务、网络和锁竞争，否则会显得视角偏窄。

**参考答案要点**

- 看应用指标：QPS、RT、错误率、线程池活跃数、连接池使用率。
- 看 JVM：堆使用率、Young GC/Full GC 次数、停顿时间、CPU、线程数。
- 看依赖：慢 SQL、Redis RT、外部接口耗时、MQ 堆积。
- 工具可讲 APM、Arthas、jstack、jstat、jmap、数据库慢日志、链路追踪。

**话术示例**

这种“慢但不报错”的情况，我一般先做分层定位。先看是单接口还是全链路变慢，再看是应用自身慢，还是下游依赖把时间拖长了。应用层我会先看 RT、QPS、线程池、连接池这些指标，JVM 层再看堆内存、GC 次数、停顿时间、线程数和 CPU。

如果 JVM 没有明显异常，我就继续往下游查，比如数据库慢 SQL、缓存命中率、外部接口耗时、网络抖动这些。工具上会结合 APM、链路追踪、Arthas 和数据库慢日志一起看，尽快把问题收敛到具体一层。

### 11. 业务状态流设计与可追踪性【6 分】

**问题**

请讲一个你设计或维护过的关键业务状态流，说明状态、流转规则，以及如何保证状态机正确性和可追溯。

**我的答案要点**

- 面试官先给了订单、工单等例子，说明你当时没有立即给出足够贴近自身项目的案例。
- 后续又追问气象雷达项目里是否有“审核、发布、入库、推送”等类似流程。
- 具体回答记录不足，待补充。

**评价**

- 优点：如果能补成项目内真实流程，这题能很好体现业务抽象能力。
- 不足：你在这类题上可能准备不足，没有第一时间把项目里的“采集、处理、审核、发布、推送”这类状态链路抽出来；这会让面试官怀疑你更多停留在开发实现层而不是业务建模层。

**参考答案要点**

- 即便项目不是订单，也可以抽象出状态流，例如“数据采集 -> 清洗处理 -> 审核 -> 发布 -> 推送”。
- 状态流转要有明确前置条件、允许的转移路径和操作者约束。
- 正确性保证可通过枚举状态、状态机校验、乐观锁、条件更新、流程日志实现。
- 可追溯性可通过状态变更记录表、操作日志、审计字段、事件记录实现。

**话术示例**

虽然我的项目不是典型订单系统，但同样有业务状态流。比如一条数据从采集、处理、审核、发布到最终推送，其实就是一条完整状态链。设计时我会先把状态枚举清楚，再定义每个状态允许流向哪些下一状态，以及什么条件下才能流转。

为了保证状态不乱跳，我通常会在更新时带上当前状态做条件判断，必要时再加版本号或乐观锁。为了可追溯，我会把每次状态变化、操作人、时间和原因记录下来，这样后面查问题能回放整个过程。

### 12. 接口幂等设计【7 分】

**问题**

你在项目中有没有做过需要保证幂等性的接口？如何保证重复调用不会产生副作用，部分失败怎么处理？

**我的答案要点**

- 面试官专门解释了“幂等”的含义，说明你当时可能回答不够直接或没快速切到真实案例。
- 原始记录未保留你的具体方案，待补充。

**评价**

- 优点：这题是工程化高频题，补齐后复用价值很高。
- 不足：如果连到支付、防重复提交、状态更新这类标准场景都不能迅速举例，会比较伤分；建议至少准备一个“唯一请求号 + 状态机校验”的真实模板。

**参考答案要点**

- 常见手段包括唯一业务键、请求幂等号、防重表、Redis setnx、数据库唯一索引、状态机条件更新。
- 对状态变更类接口，可结合“当前状态 + 目标状态”做条件更新，避免重复推进。
- 对第三方调用，要记录请求流水、响应结果和重试状态。
- 部分失败要区分“本地执行成功但响应丢失”和“本地未成功”，配合补偿或重试机制。

**话术示例**

幂等接口我一般会结合业务场景选方案。如果是一次性操作，比如提交或状态变更，我会优先找业务唯一键，再配合数据库唯一约束或者 Redis 防重，确保同一个请求不会被重复执行。

如果是状态流转类接口，我还会把当前状态作为更新条件，比如只有在“待处理”状态下才能更新成“已处理”，这样即使重复请求进来，也不会把状态推乱。对于第三方调用，我会保留调用流水和结果，方便重试和补偿。

### 13. 数据一致性与异构数据处理【6.5 分】

**问题**

你有没有处理过数据一致性或数据异构的问题，比如多服务同步、缓存与数据库一致性、分布式事务等？

**我的答案要点**

- 面试官提到了多个服务之间数据同步、缓存和数据库一致性、分布式事务等方向。
- 从后续追问看，你应该提到了 Seata 或分布式事务相关概念。
- 具体案例、方案和边界条件记录不完整。

**评价**

- 优点：至少触达到了一致性问题的关键词，不是完全陌生。
- 不足：这题最怕只会说概念，不会讲真实取舍。面试官后续马上追问“你实际用过吗”，说明需要你把“知道 Seata”和“真正落地过”区分开。

**参考答案要点**

- 优先按场景分：单服务内本地事务、跨服务最终一致性、缓存一致性、主从延迟或异构数据同步。
- 缓存一致性常见做法是先更新数据库，再删除缓存，并配合重试和订阅补偿。
- 跨服务一致性优先避免强事务，能拆就拆，不能拆再考虑可靠消息、补偿、对账。
- 分布式事务框架如 Seata 要说明适用边界、侵入性和复杂度，不要默认当银弹。

**话术示例**

数据一致性我一般会先看场景，而不是一上来就谈分布式事务。如果是在单个服务内部，优先用本地事务解决；如果是跨服务，我更倾向于把它设计成最终一致，比如通过消息、补偿和对账来兜住。

像缓存和数据库一致性这种，我通常会采用先更新数据库再删除缓存的方式，再配合重试机制减少脏数据窗口。Seata 这类框架我会了解，但只有在业务确实需要强一致、而且能接受复杂度时才会考虑，不会默认上来就用。

### 14. 公共服务与省份服务的跨服务一致性【6 分】

**问题**

在气象雷达项目里，公共微服务和省份微服务之间有没有需要保证数据一致性的实际案例？如果一个失败了怎么办？你实际是否用过 Seata？

**我的答案要点**

- 面试官显式追问你是否“实际用过 Seata”，说明你前面可能提到了相关概念但案例不够落地。
- 原始回答细节未记录，待补充。

**评价**

- 优点：问题已经贴近你的项目背景，回答空间其实很好。
- 不足：如果没有拿出一个公共配置同步、业务数据下发、状态回写之类的真实案例，面试官会觉得你对跨服务一致性更多是停留在理论层面。

**参考答案要点**

- 可以举“公共服务维护模板或配置，省份服务消费后生成本地数据”的场景。
- 先讲为什么不直接做强一致，而是通过主从职责划分、事件通知、补偿重试实现最终一致。
- 若没实际用过 Seata，要明确说“了解，但项目中主要还是本地事务 + 补偿机制”。
- 面试中承认边界比硬说用过更稳。

**话术示例**

如果公共服务和省份服务之间要保持一致，我会先看这个操作是不是必须强一致。很多业务其实没必要为了一个更新动作引入分布式强事务，更现实的做法是把主写职责放在一个服务里，另一个服务通过事件通知、重试和补偿去完成同步。

如果面试官问到 Seata，我会如实说我了解它的基本机制和适用场景，但项目里如果主要采用的是本地事务加补偿，就直接说明，不会把“了解过”说成“深度落地过”。

### 15. 外部系统对接与接口容错【7 分】

**问题**

你有没有对接过外部系统或第三方接口？接口契约怎么管理，版本变化和字段兼容怎么处理，做了哪些容错措施？

**我的答案要点**

- 面试官关注接口契约、版本兼容、字段兼容、熔断、降级、超时重试等内容。
- 原回答细节未记录，待补充。

**评价**

- 优点：这是典型可工程化展开的问题，容易准备成模板题。
- 不足：如果没有真实对接案例，回答很容易泛；建议以后固定准备一个第三方数据源或外部系统对接案例，按“契约、兼容、容错、监控”四段式说。

**参考答案要点**

- 契约管理可通过接口文档、字段字典、版本号、联调环境和 Mock 流程保证。
- 字段兼容遵循向后兼容原则，新增字段不影响旧逻辑，核心字段做非空和枚举校验。
- 容错措施包括超时设置、重试策略、幂等控制、熔断降级、异常告警、兜底返回。
- 对接后要补监控：成功率、RT、超时率、重试率、报文审计。

**话术示例**

做外部系统对接时，我会把重点放在四件事上：接口契约、兼容处理、容错和监控。契约上要把字段含义、必填规则、版本范围和异常码约定清楚，尽量不要靠口头同步。

调用层面我会配置超时、必要的重试和熔断降级，同时对关键请求保留请求响应日志，方便排查兼容问题。字段兼容上优先按向后兼容设计，新增字段不影响旧逻辑，核心字段再做校验和告警。

### 16. AI 落地项目经验【7.5 分】

**问题**

你做过哪些 AI 相关项目？负责哪些部分？怎么集成到系统里，如何处理 AI 不确定性、降级和容错？

**我的答案要点**

- 从面试官总结看，你提到了 LangChain、LangGraph 相关实践。
- 提到了不同场景的垂直化处理和输出模板控制。
- 说明你有一定 AI 落地经验，但完整案例细节没有记录下来。

**评价**

- 优点：这是整场面试里较有辨识度的部分，面试官也给了正向反馈，说明这块回答相对有亮点。
- 不足：如果能进一步补上业务场景、链路结构、评估方式、兜底策略和可观测性，会更像生产级 AI 工程回答，而不是工具使用经验。

**参考答案要点**

- 先说明业务场景，例如知识问答、文本分类、异常归因、文档检索、辅助决策。
- 再说明架构：模型层、检索层、工作流编排层、业务服务层、监控与评估层。
- AI 不确定性处理重点讲提示词约束、结构化输出、模板校验、敏感词过滤、置信度阈值、人工兜底。
- 降级容错可以讲缓存答案、规则兜底、小模型回退、关闭非核心 AI 能力。

**话术示例**

我做 AI 落地时，不会把它当成一个单独聊天能力，而是把它放进具体业务链路里。比如知识问答、文本分类或者异常分析这类场景，我会把模型调用、检索、工作流编排和业务服务整合起来，让它成为系统里一个可控的能力模块。

AI 最大的问题是不确定性，所以我会重点做结构化输出约束、模板控制、结果校验和兜底策略。比如低置信度时回退到规则结果，或者返回保守答案；同时把请求、响应、命中率和异常情况纳入监控，这样 AI 才能真正在线上稳定使用。
