### 3. 平时怎么用 AI 做开发提效【7.5 分】

**问题**：你平常会用哪些 AI 编程工具，具体怎么帮助开发提效？

**我的答案要点**
- 从去年年初开始在项目中系统使用 AI 提效，熟练期大约一年。
- 认为当前大约三分之二代码由 AI 产出，剩余三分之一自己写。
- 前端会先自己搭基础框架、组件结构和少量样例，再让 AI 补机械性代码。
- 后端也会先定基础框架、依赖和边界，再让 AI 按既定模式补接口实现。
- 会通过项目级规则、任务级 skills、MCP 接入设计稿等方式提升生成准确度。

**评价**
- 优点：这题答出了方法论，不是泛泛说“我会用 AI”，而是清楚说明了人先定结构、AI 再补重复劳动的协作模式。
- 不足：可以再补一句“哪些关键内容必须自己收口”，例如架构、边界、验收和上线前复查，这样工程把控感会更强。

**参考答案要点**
- 强调 AI 更适合重复性、模式化、可参照已有代码的任务。
- 人负责架构、边界、规范、关键实现和最终验收。
- 说明自己会把经验沉淀成规则、模板、skills，提升后续复用效率。
- 提到 MCP 等能力时，重点落在“减少信息损耗、提高还原精度”。

**话术示例**
我用 AI 提效的思路不是让它完全自由发挥，而是我先把结构和规则定好。前端我会先拆组件、定传参和基础样例，再让 AI 去补重复页面和样板逻辑；后端我会先把框架、依赖、目录和接口边界搭好，再让 AI 去扩展具体实现。平时我也会把反复强调的约束沉淀成项目规则和 task skills，这样后面生成的代码会越来越接近团队期望。对我来说，AI 是提速工具，但架构判断和最终收口一定还是我来做。

### 5. Cursor、Claude Code 这类工具的区别【6.5 分】

**问题**：你觉得 Cursor、Claude Code 这类 AI 编程工具有什么区别？

**我的答案要点**
- 认为 Cursor 更像独立编辑器，早期优势是能直接读项目上下文并直接写代码。
- 认为 Claude Code 更偏命令行工作流，但现在也有插件和编辑器内使用方式。
- 提到不同平台底层模型和任务处理机制不同，会导致代码质量有差异。
- 整体判断是现在这些工具的体验差距没有早期那么大。

**评价**
- 优点：有实际使用体验，知道编辑器形态、命令行形态、模型差异和任务处理方式这些维度。
- 不足：这题答得不够稳，术语有些混，产品定位、使用形态和模型能力混在一起说，容易给人“用过但没总结成体系”的感觉。更好的方式是按“产品形态、上下文获取、任务执行方式、适用场景”四个维度对比。

**参考答案要点**
- 先区分产品形态：编辑器型、插件型、命令行代理型。
- 再区分能力实现：上下文收集方式、计划执行能力、可操作终端/文件系统的深度。
- 最后讲结论：没有绝对好坏，关键看任务类型和个人工作流。

**话术示例**
我会把这类工具先按形态分开看。像 Cursor 更偏编辑器内工作流，优势是代码浏览、上下文感知和改文件体验更顺；像 Claude Code 这类更偏代理式、命令行式的能力，适合执行多步任务、搜索代码和处理工程操作。底层模型会影响代码质量，但真正拉开差距的，很多时候不是模型名字本身，而是它怎么收集上下文、怎么规划任务、能不能直接执行操作。所以我一般不是只看模型，而是看它和我当前任务是否匹配。

**问题**：你有没有观察过 Cursor 之前和最近代码读取方式的区别？

- 在面试官提示后，意识到可能和上下文读取方式变化有关。

**评价**
- 优点：没有强行装懂，回答比较诚实。
- 不足：这题明显是对方熟悉的细节领域，你在被追问后才逐渐跟上，显得准备不足。即使没深入研究，也可以把观察和结论说得更结构化，比如“我感知到授权频率增加，但没有系统验证底层机制变化”。

**参考答案要点**

**话术示例**

### 8. 一个月还会手写多少代码【7 分】

**问题**：你现在大概一个月还会自己手写多少代码？

**我的答案要点**
- 以离职前最后一个月为例，手写代码量相比以前没有断崖式下降。
- 自己手写时间比纯手动开发时期少一些，大概是之前的一半多一点。
- AI 能并行生成多个模块，所以整体产出效率大约是之前的三倍。

**评价**
- 优点：回答里有相对清晰的对比维度，能体现“手写减少但总产出提升”。
- 不足：题目问的是“多少”，你没有给出更可感知的表达方式。即使不报具体行数，也可以换成“关键结构自己写，重复实现大多交给 AI”这样的结论，让答案更稳。

**参考答案要点**
- 不必执着于精确行数，但要给出清晰比例或工作分工。
- 强调手写的部分主要集中在结构、边界、关键逻辑和审核。
- 结论落到“代码量不重要，关键是有效产出和质量控制”。

**话术示例**
如果按纯手写代码的时间看，确实比以前少了不少，但并不是说我不写了，而是我把重复实现交给了 AI。现在我自己主要写的是项目结构、关键逻辑、边界处理和最后的收口，重复性代码很多是让 AI 去生成。所以如果看总产出，会比以前高很多；如果只看我亲手逐行敲的代码，占比会下降，但核心部分其实还是我在掌控。

### 10. 如果一行代码都不写，能不能靠 AI 端到端完成项目【7.5 分】

**问题**：如果你一行代码都不写，是否能靠 AI 把项目端到端完成？

**我的答案要点**
- 认为未来形态可以是 AI 负责产出、人负责审核和兜底。
- 强调软件开发对严谨性要求高，最终仍需要人审核。
- 认为要通过更完善的 skills、约束和 plan 模式控制 AI 的灵活性。
- 倾向先让 AI 出计划，人先审核方案，再让 AI 具体执行。

**评价**
- 优点：这题答得比较好，核心观点清晰，就是“AI 可以主产出，但不能无人监管”。这和工程实践比较一致。
- 不足：可以再补一句“哪些环节最需要人控”，比如需求澄清、架构决策、关键风险点、上线前验收，这样会更完整。

**参考答案要点**
- AI 可以覆盖很多执行层工作，但不适合代替工程责任主体。
- 人负责需求澄清、架构判断、计划确认、质量验收和风险兜底。
- 更推荐“先计划、再执行、再审查”的人机协作模式。

**话术示例**
如果说完全不手写代码，我觉得在执行层面未来是有可能越来越接近的，但前提一定是人来做方案判断和最终兜底。因为软件不是只要能跑就行，它还涉及边界、质量、可维护性和风险控制。我的思路会是先让 AI 出计划，人先审计划，确认方案没问题后再让它执行，最后再由人做验收。也就是说，AI 可以承担大量产出，但项目责任不能交给 AI。

### 11. 你常用什么模型，skills 里重点约束什么【7.5 分】

**问题**：你在编码时主要用什么模型？项目一开始设计时，你会在 skills 里重点约束什么？

**我的答案要点**
- 表示编码任务主要使用 Claude 4.6 一类偏强编码模型，其他综合性任务会用 GPT 5.4。
- 选择模型时会考虑成本和编码效果。
- 认为 skills 最重要的是约束节奏和结构。
- 前端会重点约束组件拆分粒度、传参和通信方式。
- 后端如果让 AI 参与拆分，会重点约束技术框架、边界划分和项目级配置。
- 具体单个接口实现的约束优先级低于整体结构约束。

**评价**
- 优点：回答的核心方向是对的，说明你知道模型选择是成本、能力和任务类型的平衡；也知道 skills 最值钱的是约束结构而不是约束几行具体代码。
- 不足：模型名称和版本表述偏口语化，容易因为说快了显得不够专业。建议正式场景里统一用准确产品名。

**参考答案要点**
- 模型选择按任务类型分层：编码、综合推理、通用问答。
- skills 重点约束结构、边界、风格、一致性和目录组织。
- 强调“宏观约束优先于微观实现”。

**话术示例**
我一般会按任务类型选模型，编码类任务优先选代码能力强、成本也可控的模型，综合分析和通用问题再用更均衡的模型。至于 skills，我觉得最重要的不是限制它某个接口怎么写，而是先把整体结构约束住。比如前端的组件拆分粒度、状态和传参方式，后端的模块边界、目录结构和项目级配置，这些一旦定稳了，后面 AI 生成的代码才更一致，也更接近真实可维护的工程代码。

### 12. 测试阶段怎么做，AI 怎么参与排查问题【7 分】

**问题**：开发完成后的测试阶段怎么配合？你们自己测什么，AI 会怎么参与排查问题？

**我的答案要点**
- 公司有独立测试团队，负责统一提测。
- 前端写完后直接提测，后端会补单元测试、保证接口输入输出跑通。
- 现在单元测试很多也会借助 AI 生成。
- 提测后如果发现问题，会先让 AI 参与排查；如果自己已知大概方向，也会先给 AI 指定排查方向。

**评价**
- 优点：答出了团队协作方式，也说明了 AI 在测试后期更适合做辅助定位和排查。
- 不足：可以再补一句“最终还是自己复核 AI 排查结果”，否则容易给人一种把排障也过度外包给 AI 的感觉。

**参考答案要点**
- 明确测试分工：开发自测、接口验证、提测、问题回归。
- AI 可以辅助生成单测、分析报错、定位可能原因。
- 最终问题确认和修复方案仍由开发负责。

**话术示例**
我们当时是有独立测试团队的，所以开发完成后会走正式提测流程。开发侧这边，前端会先做基本联调和自测，后端会把单元测试和接口输入输出先跑通。AI 在这个阶段我更多是拿来辅助，比如生成一部分单测、分析报错、帮助缩小排查范围。但最终问题是不是这个原因、修复方案怎么定，还是我自己来确认，不会直接把 AI 的结论当最终结论。

### 13. 对 Next.js、Node.js 这类技术的理解【5.5 分】【错】

**问题**：平时会了解像 Next.js、Node.js 这样的框架和后端技术吗？

**错误点**：把 Next.js、Node.js 的定位、演进和能力边界说乱了，术语表达不准确。

**我的答案要点**
- 表示自己对 Node.js、Next.js 都有了解。
- 回答里提到了 Node.js 是服务端运行环境，也提到了 Next.js 与首屏、SEO、服务端能力有关。
- 但整体表述比较混乱，概念边界不清，术语不够准确。

**评价**
- 优点：方向上知道 Node.js 是服务端 JavaScript 运行时，Next.js 与 SSR、SEO、全栈能力有关。
- 不足：这题属于明确的知识表达失真。Node.js、Next.js、React 生态关系、SSR/SSG/服务端能力这几层被混在一起，回答会直接影响面试官对你技术基础扎实程度的判断。

**参考答案要点**
- Node.js 是基于 Chrome V8 的 JavaScript 运行时，主要让 JavaScript 能在服务端运行。
- Next.js 是 React 生态里的全栈框架，支持 SSR、SSG、ISR、路由、接口能力等。
- Next.js 最初主要解决 React 应用首屏性能、SEO 和工程化问题，后来逐步扩展到全栈能力。
- 回答时区分“运行时”和“框架”，不要混淆。

**话术示例**
这两个我都了解，但它们不是同一层概念。Node.js 本质上是 JavaScript 在服务端的运行时环境，让我们可以用 JavaScript 或 TypeScript 去写服务端程序。Next.js 则是 React 生态里的全栈框架，最初大家更多用它解决 SSR、首屏性能和 SEO 问题，后来它把路由、数据获取、服务端渲染和部分后端能力都整合进来了。所以如果简单区分，Node.js 更偏运行时基础，Next.js 更偏上层框架能力。

### 14. 是否有部署和运维经验【7 分】

**问题**：之前有没有接触过部署和运维方向？

**我的答案要点**

- 提到使用 Jenkins 一类工具监听代码仓库提交并触发测试环境部署。

**评价**
- 优点：这题答得相对扎实，流程比较完整，能体现你不是只会点按钮，而是知道自动化部署背后的执行链路。
- 不足：如果能再补一句自己实际负责到什么程度，比如脚本维护、环境配置、日志排查、回滚处理，会更有说服力。

**参考答案要点**

- 前端突出构建产物发布，后端突出打包、镜像、容器化部署。
- 补一句对部署原理和问题定位都有实际参与。

**话术示例**
我有实际部署经验，而且主要走的是自动化部署流程。比如测试环境会通过 Jenkins 监听仓库提交触发构建，前端一般是拉代码、装依赖、打包，再把产物发布到 Nginx 对应位置；后端这边会先完成打包，再做镜像和容器化部署。除了正常发版，我对回滚、失败兜底这些流程也有了解，所以这块不是只知道概念，而是做过完整链路。

### 16. 反问岗位业务、团队和技术栈【7.5 分】

**问题**：你最后反问了哪些信息，收获了什么？

**我的答案要点**
- 反问了岗位具体业务内容。
- 了解到业务主要分为内部 AI 系统平台和 AI Agent 探索两大方向。
- 了解到系统包含内部管理后台和对外服务平台两部分。
- 反问了岗位对前后端技术栈是否有强要求，对方表示更看 AI 能力和交付能力。
- 反问了团队规模，得知目前几乎是从 0 到 1，技术团队很小，当前主要由面试官本人同时承担产品和研发。
- 了解到现阶段技术栈大致为 Next.js、Node.js、Python。

**评价**
- 优点：反问抓得比较准，覆盖了业务、技术栈、团队规模和职责边界，能帮助判断岗位真实性和风险。
- 不足：还可以再追问两个关键点，一是当前项目阶段和已完成度，二是你入职后的优先目标与考核标准。这个岗位明显是早期、小团队、强 AI 导向，风险和机会都大，最好问得更落地。

**参考答案要点**
- 反问优先关注业务是否真实、团队是否稳定、技术期望是否合理、岗位成功标准是否清晰。
- 对这类 0 到 1 团队，还应追问资源投入、协作分工和目标节奏。
- 反问结束后，要给自己形成岗位判断：机会点、风险点、是否匹配。

**话术示例**
我最后的反问主要是想确认三个事情。第一，这个岗位到底在做什么业务，结果听下来它既有内部 AI 系统平台，也有对外服务平台和 AI Agent 探索，方向是比较新的；第二，技术栈要求没有卡得特别死，更看重 AI 工具使用和实际交付能力；第三，团队目前还比较早期，研发规模很小，说明机会大，但同时对个人独立推进能力要求也会比较高。对我来说，这类岗位吸引力在于空间大，但也要重点评估节奏、资源和组织成熟度。
