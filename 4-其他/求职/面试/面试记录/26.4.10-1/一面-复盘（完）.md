### 3. 总结过方法论和规范吗【8 分】

**问题**
开发过程中，自己有没有总结过一些方法论，比如哪些技巧、哪些规范用得比较好？

**我的答案要点**
- 主要是指导 AI 来写规范，自己审核
- 前端组件通信经验：
  - 父子级别 → props 传参
  - 一个父组件跨多层子组件都需要某个参数 → provide/inject
  - 全局需要维护的变量 → 状态管理
  - 间隔较远的两个组件 → 事件总线
- 后端：分层写（Controller / Service / DAO），配置抽取到配置类
- 这些规则让 AI 根据代码自总结，自己审核；后续发现不符合的地方让 AI 补充更新
- 积累后的 rules 文件可在新项目直接复用

**评价**
- 优点：举例具体，组件通信的场景→选择思路清晰，有实际判断依据，不是背书。
- 不足：整体作答逻辑稍散，开头引入略慢；后端部分举例不够深，只说了分层和配置抽取。

**参考答案要点**
- **前端组件通信选择原则**：
  - 父子单向传递 → `props / emit`
  - 多层传递（祖孙，中间层不关心）→ `provide / inject`
  - 跨模块全局状态 → Pinia / Vuex（状态管理）
  - 非父子、跨层级事件通知 → 事件总线（mitt 等）
- **后端代码规范**：
  - 强制分层（Controller 只做入参校验和路由，Service 放业务，DAO/Mapper 放数据访问）
  - 配置值（数据库地址、阈值等）统一抽取到 application.yml 或配置类，不硬编码
  - 返回体统一封装为 `Result<T>` 或类似结构
- **沉淀机制**：让 AI 从代码中自动归纳规范 → 人工审核 → 存入 rules → 发现例外时增量补充 → 新项目直接复用。

**话术示例**
我们前端的组件通信有一个基本的判断框架：父子之间用 props 和 emit；如果是祖父→孙子这种跨层传参，中间层不需要关心这个值，就用 provide/inject；如果是全局都要维护的状态，比如用户信息或者权限列表，就放 Pinia；如果是两个没有层级关系的组件需要通信，就用 mitt 这类事件总线。后端主要是分层和配置抽取，Controller 负责参数校验和路由，业务逻辑放 Service，数据库操作放 Mapper，配置值统一放 yml 文件或配置类，不硬编码。这些规则我一般让 AI 先根据已有代码自己总结一版，我审核确认，然后后续发现有不符合的地方随时让 AI 追加，新项目可以直接迁移这套 rules。

### 6. 使用了哪些数据库 / B+ 树叶子节点【5.5 分】

**问题**
对于数据库你们用到哪些？/ 知道 B+ 树的叶子节点之间是什么联系吗？

**我的答案要点**
- 只用 MySQL
- B+ 树是索引的底层数据结构，是多分叉查找树
- 叶子节点之间有双向链表相连
- 再往细答不出来

**评价**
- 优点：B+ 树定位准确（索引底层结构、多分叉），双向链表这个关键点说出来了。
- 不足：数据库只说了 MySQL，没有展开（如用了哪些特性：事务、索引优化、读写分离等）；B+ 树叶子节点双向链表的作用没有说明（支持范围查询），也没提非叶子节点只存索引键不存数据这一重要特性。

**参考答案要点**
- **B+ 树核心特性**：
  - 多叉平衡查找树，所有数据记录都存在**叶子节点**，非叶子节点只存索引键（起导航作用）。
  - 叶子节点之间通过**双向链表**连接，支持高效的**范围查询**（顺序扫描叶子链表，无需回到根节点）。
  - 叶子节点按索引键有序排列，配合双向链表可做 `BETWEEN`、`>`、`<`、`ORDER BY` 等范围操作。
- **相比 B 树的优势**：B 树的数据分散在各层节点，范围查询需要中序遍历整棵树；B+ 树范围查询只需扫链表，效率更高。

**话术示例**
B+ 树是 MySQL InnoDB 索引的底层数据结构。它是一棵多叉平衡树，有一个关键特点是：非叶子节点只存索引键，不存真正的数据行，起导航作用；所有实际数据都存在叶子节点里。叶子节点之间用双向链表首尾相连，并且按索引键有序排列。这样设计的好处是支持高效的范围查询——比如 `BETWEEN`、`>`、`ORDER BY`——只需找到范围起点，然后沿着叶子链表顺序扫就行，不用每次都从根节点重新遍历。

### 7. 链表与数组的差异及查找时间复杂度【7 分】

**问题**
链表和数组，它们查询元素的时间复杂度各是多少？各自的优势是什么？

**我的答案要点**
- 链表：节点结构（数据 + 指针），指针指向下一个节点，单向链表从头到尾连接
- 数组：一段连续分配的内存，通过下标直接访问
- 链表：插入快（尤其是头部或尾部），中间插入需要先找位置
- 数组：查找快，尤其是排好序之后顺序查找
- 乱序查找时间复杂度：以为不同，后被面试官引导确认都是 O(n)，但答题时有些犹豫

**评价**
- 优点：数据结构本身描述清晰，基本特性对。
- 不足：① 链表插入"从中间最快"的说法不准确，中间插入需先遍历定位，复杂度 O(n)，真正 O(1) 的是**已知目标节点情况下的插入**；头/尾插入（维护了头尾指针）才是 O(1)。② 乱序查找时应该直接答 O(n)，两者相同，不该犹豫。③ 数组查找快的核心是**随机访问**（通过下标 O(1) 直接定位），不是"排序后顺序查找"。

**参考答案要点**
- **数组**：
  - 内存连续，支持 O(1) **随机访问**（下标直接计算偏移量）。
  - 在已知下标时查找是 O(1)；不知道下标、只知道值，需线性扫描，O(n)。
  - 插入/删除需移动后续元素，O(n)。
- **链表**：
  - 非连续内存，查找必须从头遍历，无论有序无序均为 O(n)。
  - **在已知节点引用的前提下**，插入和删除是 O(1)；如果需要先找到目标位置，则总体仍是 O(n)（遍历定位 O(n) + 操作 O(1)）。
- **结论**：
  - 随机访问（按下标）：数组 O(1)，链表 O(n)。
  - 按值查找（无序）：两者均 O(n)。
  - 已知位置后的插入/删除：数组 O(n)，链表 O(1)。

**话术示例**
数组的核心优势是随机访问：内存连续，通过下标可以直接计算出元素的内存偏移量，做到 O(1) 取到元素。如果只是按值查找（不知道下标），数组和链表一样都要线性扫描，都是 O(n)。链表的优势是**已知节点引用时**插入和删除是 O(1)——只需修改指针，不需要移动其他元素。但如果需要先找到插入位置，那个遍历过程本身就是 O(n)，所以整体还是 O(n)。简单记：数组擅长按下标访问（O(1)），链表擅长在已知位置做插入删除（O(1)）；纯按值查找，俩都是 O(n)。

### 8. 单向链表中间插入的操作步骤【7.5 分】

**问题**
如果从中间插入一个元素，需要做哪些操作？

**我的答案要点**
- 先找到中间位置（遍历）
- 切断目标位置的 next 指针
- 新建一个节点
- 把上一个节点的指针指向新节点
- 把新节点的指针指向下半段

**评价**
- 优点：操作步骤完整，逻辑顺序正确。
- 不足：没有主动说明需要保存"前驱节点"的引用（否则需要二次查找）；面试官追问"能不能只查一遍"时，才给出用变量临时存储的思路，可以在初次回答时就提前点明。

**参考答案要点**
- 找到插入位置时，同时保存目标节点和其**前驱节点**（prev）的引用，用两个指针推进（或单指针提前停在前驱节点）。
- 操作步骤（一次遍历完成）：
  1. 用 `prev` 指针定位到**插入位置的前一个节点**（遍历时提前停在 `prev = prev.next` 那一步）。
  2. `next = prev.next`（保存后继节点）。
  3. 新建节点 `node`，`node.next = next`。
  4. `prev.next = node`。
- 全程只遍历一次，O(n) 定位，O(1) 修改指针。

**话术示例**
插入的关键是一次遍历就把前驱节点和后继节点都拿到。做法是通过 prev 指针遍历，让 prev 停在插入位置的前一个节点：先把 `next = prev.next` 保存下来，然后创建新节点，把新节点的 next 指向 next，再把 prev 的 next 指向新节点。这样整个过程只需遍历一遍，修改指针是 O(1)，总体 O(n)。

**评价**
- 优点：思路方向（用相对速度/追及法）是对的，能想到用"分针-时针多走的圈数"来数重合次数。
- 不足：算法本身算错了，且在面试官给提示后没有及时把答案修正到 22。基础数学逻辑题，现场应求稳，算不出来直接说"我现场算一下"，不要凭直觉给数字。

**参考答案要点**
- **方法（追及法）**：分针速度 = 1 圈/小时，时针速度 = 1/12 圈/小时，相对速度 = 11/12 圈/小时。
- 每隔 12/11 小时重合一次。
- 12 小时内重合次数：12 ÷ (12/11) = 11 次。
- 24 小时内重合次数：11 × 2 = **22 次**。
- **直觉验证**：每个"整点段"（0→1，1→2，…，10→11）都会重合一次（共 11 次/12 小时）；11→12 之间**不会额外重合**，下一次重合正好在 12:00，已算入下一个十一段的起点。

**话术示例**
用追及法。分针每小时转一圈，时针每小时转 1/12 圈，所以分针相对时针的速度是 11/12 圈每小时，每隔 12/11 小时追上一次。12 小时内追上 12 ÷ (12/11) = 11 次，24 小时就是 22 次。也可以这样直观理解：从 12:00 到 23:59:59，0→1、1→2……10→11 这 11 个小时段各重合一次，共 11 次，然后再乘以 2 个 12 小时，得到 22 次。11→12 之间不重合，因为下一次恰好落在 12:00 整。

### 11. Spring AOP 注解如何实现切面【8 分】

**问题**
Spring AOP 有了解吗？它的注解是如何实现切面注入的？

**我的答案要点**
- 使用 `@Aspect` 注解定义切面类
- 定义切入点（Pointcut）和切入方式（Advice 类型）
- 实际项目中用的是**环绕通知（Around Advice）**，记录每个接口的入参、返回数据和响应时间
- 实现依赖 Spring MVC 容器
- Spring Boot 为被切入的方法创建代理，注入时注入的是代理而不是原始对象
- 代理内依次执行前置逻辑、原始方法逻辑、后置逻辑

**评价**
- 优点：有实际项目经验（接口日志），描述了核心链路（@Aspect → 切入点 → 代理 → Around 通知），有工程感。
- 不足：对代理创建时机的描述略宽泛（"Spring MVC 容器"之说不够精准，是 Spring IoC 容器在 Bean 初始化阶段通过 BeanPostProcessor 创建代理）；切入点表达式（`@Pointcut`）的写法没提。

**参考答案要点**
- **@Aspect**：标记一个类为切面类，需配合 `@Component` 纳入 Spring 容器。
- **@Pointcut**：定义切入点表达式（如 `execution(* com.example.controller.*.*(..))`），复用性好。
- **Advice 类型**：`@Before`（前置）、`@After`（后置）、`@AfterReturning`（返回后）、`@AfterThrowing`（异常后）、`@Around`（环绕，最强，可控制是否执行原始方法）。
- **代理创建原理**：Spring IoC 容器在 Bean 初始化阶段，通过 `AnnotationAwareAspectJAutoProxyCreator`（一种 `BeanPostProcessor`）检测目标 Bean 是否匹配切入点，匹配则创建代理对象（JDK 动态代理或 CGLIB 代理），注入到其他 Bean 时注入的是代理。
- **Around 执行结构**：`ProceedingJoinPoint.proceed()` 前的代码 = 前置逻辑，proceed() = 调用原始方法，proceed() 后的代码 = 后置逻辑；可通过 try-catch 捕获异常。

**话术示例**
Spring AOP 用起来是这样：先写一个类，加 `@Aspect` 和 `@Component`，让 Spring 容器管理它。然后用 `@Pointcut` 定义切入点表达式——比如 `execution(* com.example.controller.*.*(..))` 表示拦截 controller 层的所有方法。最后用 `@Around` 这类通知注解写具体逻辑，环绕通知里通过 `ProceedingJoinPoint.proceed()` 调用原始方法，前后可以插入任意代码，我在项目里就是用它记接口的入参、响应数据和耗时。底层原理是 Spring IoC 容器在初始化 Bean 时，有一个叫 `AnnotationAwareAspectJAutoProxyCreator` 的 BeanPostProcessor 会检查这个 Bean 有没有匹配的切入点，有的话就给它创建代理对象。后续其他地方注入这个 Bean，拿到的其实是代理，执行方法时代理里会把切面逻辑和原始方法按顺序串起来执行。

### 12. AOP 动态代理原理 / JDK 动态代理 vs CGLIB【4 分】【错】

**错误点**：只提到了 JDK 反射/接口这一条路，不知道无接口时用 CGLIB；JDK 动态代理 vs CGLIB 的区别完全空白。

**问题**
AOP 底层的动态代理是如何实现的？JDK 动态代理和 CGLIB 动态代理有什么不同，各自的使用场景是什么？

**我的答案要点**
- 提到底层用 Java 反射实现
- 面试官补充：JDK 动态代理只能用于有接口的类
- 没有接口时怎么办 → 答不出来（CGLIB）
- JDK 动态代理 vs CGLIB 的区别 → 未了解

**评价**
- 优点：知道 JDK 动态代理基于接口，方向正确。
- 不足：对 CGLIB 完全不了解；是 Spring AOP 中的核心知识点，属于明显盲区。

**参考答案要点**
- **JDK 动态代理**：
  - 代理目标**必须实现接口**。
  - 通过 `java.lang.reflect.Proxy` 在运行时生成一个实现了相同接口的代理类，方法调用通过 `InvocationHandler` 的 `invoke` 拦截。
  - 底层确实通过反射调用目标方法。
- **CGLIB 动态代理**：
  - 代理目标**不需要接口**，通过**字节码生成**（ASM 库）动态创建目标类的**子类**，重写方法后插入切面逻辑。
  - 要求目标类和方法不能是 `final`（final 类/方法无法被继承/重写）。
- **Spring AOP 选择策略**：
  - 目标类实现了接口 → 默认用 JDK 动态代理。
  - 目标类没有接口，或配置了 `proxyTargetClass = true` → 用 CGLIB。
  - Spring Boot 2.x 起默认优先使用 CGLIB（即使有接口）。
- **性能对比**：CGLIB 代理创建开销稍高（字节码生成），但调用性能与 JDK 代理相当；现代版本差异可忽略不计。

**话术示例**
Spring AOP 的动态代理有两种实现方式。第一种是 JDK 动态代理，要求目标类必须实现接口，运行时通过 `java.lang.reflect.Proxy` 生成一个实现相同接口的代理类，方法调用会被 `InvocationHandler` 的 invoke 方法拦截，Spring 在 invoke 里执行切面逻辑后再通过反射调原始方法。第二种是 CGLIB，它不需要目标类有接口，而是用 ASM 库在运行时动态生成目标类的子类，通过重写父类方法的方式植入切面——所以 final 类和 final 方法是不能被 CGLIB 代理的。Spring 的选择策略是：有接口时默认用 JDK 代理，没有接口时用 CGLIB；Spring Boot 2.x 之后默认优先用 CGLIB，即使有接口。
