### 3. 智能体落地经验（预警文案生成） 【7.5 分】

**问题**：你们的智能体功能具体是怎么做的？

**我的答案要点**：
- 项目：气象雷达预警系统，含预警文案智能生成功能
- 模型：本地部署（内网环境，无法访问外网）
- 调用浪潮大模型，用 Python + FastAPI 搭建微服务，集成到 Java 后端
- 我负责：功能设计 + 技术选型 + 智能体接入实现

**评价**：
- 优点：技术细节清晰，说明了为什么选本地部署（内网限制），体现了方案设计意识；提到微服务拆分集成，说明有架构思维。
- 不足：没有说清"智能体如何基于气象数据生成文案"的具体链路（数据输入→模型→文案输出），面试官追问时稍显模糊；模型名称（"浪颤"）发音不清晰。

**参考答案要点**：
- 背景：内网限制，选择本地部署大模型（浪潮）
- 技术架构：
  - Python + FastAPI 封装模型调用为独立微服务
  - Java 后端通过 HTTP 调用该微服务
  - 前端触发预警，后端组织气象数据作为 prompt，调用模型生成文案，返回展示
- 我的贡献：与产品经理共同设计功能逻辑，独立完成 Python 微服务 + Java 集成

**话术示例**：

> 这个功能是在气象雷达预警系统里，检测到预警事件时系统自动生成预警文案。因为甲方是内网环境，没法用公共 API，所以我们在本地部署了浪潮大模型。
>
> 技术上用 Python 加 FastAPI 搭了一个独立的模型微服务，Java 后端通过 HTTP 调用这个服务。前端触发预警后，后端会把气象数据组织成 prompt 发给模型，模型返回文案再展示给用户。我主要负责这个微服务的设计和实现，以及和 Java 后端的集成，功能需求是我和产品经理一起设计的。

### 4. 大模型技术选型（本地部署 vs API） 【7 分】

**问题**：你们的大模型是自研的还是调现成的？有用过 dify、Coze 这类工具吗？

**我的答案要点**：

- 没有用 dify/Coze，自己写了 Python 调用服务

**评价**：
- 优点：澄清了"自研"的误解，诚实说明了方案选择的原因（内网）。
- 不足：面试官提到 dify/Coze 时没有主动说明自己了解这些工具；对它们的定位（低代码 Agent 平台）也没有展开，暴露了对这类工具的了解深度有限。

**参考答案要点**：
- 模型是"拿来用"的，非自研

- 选择自己写调用层而非 dify/Coze 的原因：需要深度集成进现有 Java 微服务体系，自写 FastAPI 微服务更灵活、侵入性更小
- 了解 dify/Coze 的定位：适合快速搭建工作流 Agent，标准化场景效率高，但不便于深度集成进已有架构

**话术示例**：

> 我们没有自研模型，用的是训练好的大模型，通过本地部署的方式调用。因为甲方是内网，没法用公共 API，所以选择了本地部署。
>
> dify 和 Coze 我了解，它们适合快速搭建 Agent 工作流，标准化场景下效率很高。我们当时没用，是因为需要把功能深度集成进现有的 Java 微服务体系，自己写一个 FastAPI 的调用服务更灵活，对已有架构的侵入性也更小。

### 10. 气象雷达系统技术架构 【7 分】

**问题**：概述一下气象雷达系统的技术架构，关联了哪些技术方案，最终呈现什么功能？

**我的答案要点**：
- 数据来源：母公司航天宏图硬件 → 天擎系统 → 本地算法拉取
- 文件格式：PNG（色斑图，RGB 位存储矩阵数据）+ JSON
- 前端：解析 PNG 的 RGB 位值，还原气象数值，结合图例渲染色斑图
- 后端：组织数据访问路径 + 用户权限管理
- 数据库：MySQL，存用户权限信息；气象数据不入库，按路径直接访问

**评价**：
- 优点：数据流向清晰（来源→存储→访问），PNG 用 RGB 位存矩阵的技术细节有深度。
- 不足：没有一句话说明系统的业务价值（最终给甲方解决了什么问题）；对 PNG 的生成过程（"算法工程师用什么数据做的"）描述太简单。

**参考答案要点**：
- 业务定位：为气象局等客户提供定制化气象雷达预警监测能力
- 数据链路：航天宏图硬件采集 → 天擎平台 → 本地算法拉取 → PNG/JSON 文件存硬盘 → 前端按时间/要素路径访问
- 前端核心：解析 PNG 的 RGB 编码，还原降水/风向/雷暴等气象要素数值，叠加图例渲染色斑图
- 后端：路径拼接、权限控制、用户管理；气象数据不走数据库，直接文件访问
- AI 接入：预警触发时，后端组织数据为 prompt → 调本地大模型微服务 → 输出预警文案

**话术示例**：

> 我们系统主要给气象局这类客户提供雷达气象监测和预警能力。数据来自母公司航天宏图的硬件设备，经天擎系统处理后，算法程序定期把数据拉取到本地，文件格式是 PNG 和 JSON，PNG 用 RGB 位来存储气象矩阵数据，体积小、传输效率高。
>
> 前端通过时间和气象要素拼成访问路径，读取 PNG 文件，解析出每个像素对应的气象值，再配合图例渲染成色斑图。后端主要做路径管理和用户权限控制。智能体功能是预警触发时，后端把相关数据组成 prompt，调本地服务生成预警文案，自动展示给用户。

### 12. AI 开发工具的局限性 【8.5 分】

**问题**：AI 开发工具有什么局限（缺点）？

**我的答案要点**：
- 核心局限：上下文窗口短，记不住项目历史
- 纯 AI 开发的风险：项目变大后难以维护（AI 改一处，可能引入其他问题）
- 最佳实践：人把控整体框架，AI 做细节实现，人审核后提交
- 适合 AI 的内容：机械、规范化、公式化的代码
- 人的角色：懂代码、能审核输出、把握全局

**评价**：
- 优点：回答完整有深度，既说了技术限制（上下文），又说了实践层面的风险和最佳实践；有辩证思维，加分明显。
- 不足：可以补充幻觉（hallucination）问题，以及对行业领域知识的局限（AI 不懂行业特定规范）。

**参考答案要点**：
- 上下文限制：项目变大后，AI 对历史代码理解有限，局部修改可能破坏全局逻辑
- 幻觉问题：AI 可能生成"看起来正确、实则有逻辑漏洞"的代码，需人审核
- 领域知识局限：对行业特定规范/约定不了解，纯靠 AI 容易生成通用但不合规的代码
- 最佳实践：人把控架构和业务边界，AI 负责规范化填充，人审核确认后提交

**话术示例**：

> AI 最大的限制我觉得是上下文窗口，项目做大了之后 AI 对历史代码不了解，改一个 bug 可能在不了解全局的情况下引入新问题。所以如果纯靠 AI 写，项目到后期会很难维护。
>
> 另外还有幻觉问题，AI 写出来的代码有时候看起来没问题，逻辑上有漏洞，这需要有经验的人来审核。所以最好的模式是：人来把控架构和业务边界，AI 做规范化的实现，人审核通过后才提交，这样既提效又能保障质量。

### 14. 系统建设与对接任务（开放式） 【6 分】

**问题**：给你一个任务：需求已明确，建设一个新业务系统，并与已有系统集成（包括企业微信/钉钉消息推送、统一登录平台等），你怎么做？

**我的答案要点**：
- 先确认是否有产品经理
- 产品经理出需求文档，我了解后做功能设计、技术选型、开发
- 外部平台用官方 SDK，查技术文档对接
- 内部系统找之前的技术人员了解接口

**评价**：
- 优点：提到分工与 SDK 对接思路，思路基本清晰。
- 不足：回答停留在流程层面，没有展示架构设计能力；对"统一登录（SSO）""消息推送链路设计""数据流"等关键技术细节完全没有涉及，这才是考察核心。

**参考答案要点**：
- 需求侧：拿到需求文档 → 拆功能模块 → 梳理依赖与集成点
- 技术设计：
  - 统一登录：对接 SSO（OAuth2 / 企业微信身份验证），避免各系统重复登录
  - 消息推送：企业微信/钉钉 Webhook 机器人或应用消息 API，明确触发条件（事件驱动 vs 定时）
  - 系统集成：明确各依赖系统的接口形式（REST / 消息队列 / Webhook），设计适配层
  - 数据流：明确哪些数据由哪个系统产生、哪些系统消费，避免数据孤岛
- 开发策略：先跑通核心集成链路的 PoC，验证后再推进功能开发
- 上线策略：小范围灰度 → 全量上线

**话术示例**：

> 拿到需求文档后，我会先梳理功能模块和集成点，弄清楚哪些地方要和外部系统交互。企业微信或钉钉的消息推送，如果是通知类的，可以用 Webhook 机器人或应用消息 API，看是事件驱动还是定时推送来设计触发逻辑；统一登录的话，要对接他们的 OAuth2 或者企业内的 SSO，这块要提前和基础设施团队对齐。
>
> 内部系统的对接，我会先找之前的技术同学了解接口形式，是 REST 还是消息队列，数据结构是什么，再做适配层。整体策略是先跑通核心集成链路的 PoC，验证通了再推功能开发，这样可以早发现集成问题，不用等到最后阶段才踩坑。

### 15. 数据库经验 【5 分】

**问题**：数据库用的怎么样？MySQL、Oracle、MongoDB 等用过吗？

**我的答案要点**：
- 只用过 MySQL
- 其他数据库差距不大，主要是存储结构、安全性、性能上有区别
- 接入方式比较统一

**评价**：
- 优点：没有编造经验。
- 不足：用"接入方式统一"来带过不同数据库，显得理解停留在表面；Oracle、MongoDB 与 MySQL 的根本差异没有体现；这个岗位可能需要对接不同业务系统的数据源，数据库知识面偏窄是风险。

**参考答案要点**：
- 实际使用：MySQL（项目主力，熟悉增删改查、索引优化、事务）
- 了解但未深度使用：
  - Oracle：企业级特性（存储过程、分区），语法差异（序列代替自增主键等），多用于大型政企场景
  - MongoDB：文档型，适合非结构化/半结构化数据（日志、灵活字段业务数据），与关系型的取舍
  - Redis：缓存与消息队列场景，分布式环境下的 session 和热点数据
- 底层 SQL 原理共通，可快速上手其他数据库

**话术示例**：

> 我主要用的是 MySQL，增删改查、索引优化、事务这些用得比较熟。Oracle 和 MongoDB 了解原理但没有深度项目经验。Oracle 主要是企业级场景，有存储过程和分区特性，语法上和 MySQL 也有差异，比如主键自增得用序列来实现，政企系统里用得比较多。MongoDB 是文档型的，适合结构不固定的数据，不需要预先建表，日志存储或者字段变化频繁的场景下比关系型更合适。如果项目需要，我可以快速上手，查询优化的核心思路是共通的。
