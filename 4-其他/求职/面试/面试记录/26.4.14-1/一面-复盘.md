### 2. AI 智能体项目介绍【8.5 分】

### 3. 工具调用：自然语言"查上周一天气"如何实现【8 分】

**问题**
如果用户输入"我想查一下上周一的天气"，智能体要提取哪些信息，怎么调天气 API？

**我的答案要点**
- 模型训练后数据固定，无法直接获取实时或历史天气，需要外部工具
- 注册一个查天气的 Python 工具，绑定到模型
- 在 LangGraph 中建立专门的"查天气"节点，绑定该工具
- 判断用户意图，如果是查天气就路由到该节点
- 模型调用工具 → 获取访问结果 → 模型根据结果回答用户

**评价**
- 优点：思路正确，外部工具调用的流程说清楚了，LangGraph 节点路由的思路也提到了。
- 不足：没有提到如何从自然语言中提取"上周一"这个时间实体和地理位置实体再传给工具；即工具的入参如何从用户输入里解析出来（LLM 的 function calling 参数提取能力）没有点明。

**参考答案要点**
- LLM 具备 function calling 能力，可以从自然语言里自动提取工具需要的参数（如 `date: "上周一"`, `location: "北京"` 等）
- 工具定义时声明参数的 name、type 与 description，LLM 会据此提取并填参
- 在 LangGraph 中可以设一个 Tool Node，绑定天气查询工具，路由判断后触发
- 工具执行结果以 ToolMessage 形式回传，LLM 再据此生成自然语言回复

**话术示例**
像这种"查上周一天气"，模型本身训练截止后就拿不到实时数据，所以需要给模型绑一个外部工具。LangGraph 里我会新建一个 Tool Node，注册一个查天气的 Python 函数；函数的参数我会用类型注解加描述写清楚，比如 date 是日期字符串、city 是城市名。用户输入进来之后，LLM 靠 function calling 能力自动从自然语言里提取出这些参数，然后调工具，工具的返回值以 ToolMessage 的形式给回模型，模型再组织成自然语言回答用户。

### 4. 智能体与系统的输入设计【7.5 分】

**问题**
智能体的输入是什么，主要实现了哪些功能？

**我的答案要点**
- 4 个输入：气象要素、时间轴所选时间、地图经纬度范围、用户输入的提示词
- 后端先根据气象要素和时间取原始气象数据，再连同其他参数发给智能体
- 针对色斑图（PNG 格式，RGB 位编码气象数值，有放大系数）和 JSON 点位数据（插值生成矩阵）均有对应工具解析
- 每种气象要素独立建模，绑定各自的数据处理工具，统一格式化文案节点输出

**评价**
- 优点：数据解析细节扎实，色斑图的 RGB 编码原理和解码过程说得清楚，体现了技术深度。
- 不足：提示词是前端唯一自由输入的字段，可以主动说明"其他参数都是系统约束的选择，不需要 NLP 提取"，这样与后面的槽位问题能更好地衔接。

**参考答案要点**
- 输入分两类：结构化参数（气象要素/时间/经纬度，由系统 UI 约束选择）+ 自由文本（用户提示词）
- 色斑图解析：PNG 的 RGB 值 × 放大系数 = 真实气象数值
- JSON 点位数据：克里金插值（Kriging interpolation）生成矩阵
- 多模型+多工具路由架构：按要素路由 → 专属子模型 → 绑定工具 → 统一格式化节点

**话术示例**
输入一共 4 个：气象要素、时间、经纬度范围，这三个在前端 UI 里是约束选择，不是自由输入的；还有一段用户手写的提示词。后端先用气象要素和时间拿到原始气象数据，再把这些参数一起发给智能体。数据解析这块比较有意思，色斑图用的是 PNG 格式，把气象数值编码进 RGB 位，读的时候要先乘以一个放大系数还原成真实值；JSON 点位数据用克里金插值生成矩阵，不同要素的解析方式不一样，所以我对每种要素都单独建了一个子模型，绑各自的工具，最后走统一的格式化节点出文案。

### 7. 了解 RAG 吗【2 分】【错】

**问题**
你有了解过 RAG 服务吗？就是做知识库向量化、向量查询那种。

**我的答案要点**
- 表示不了解
- 猜测它也是一种外部工具，可以绑到模型上让模型使用

**错误点**：RAG 是检索增强生成的核心技术，做 AI 智能体必须掌握，说"不了解"是明显的知识盲区。

**评价**
- 优点：没有硬扯，大方承认自己不了解，态度诚实。
- 不足：RAG（Retrieval-Augmented Generation）是 AI 智能体开发中的基础知识，该岗位必考，答"不了解"是扣分项。

**参考答案要点**
- RAG = Retrieval-Augmented Generation，检索增强生成
- 核心流程：文档预处理（切片 → Embedding → 存入向量数据库）→ 用户查询时将 query 向量化 → 在向量数据库中做相似度检索（如余弦相似度）→ 把检索结果作为上下文拼入 Prompt → LLM 生成回答
- 作用：让 LLM 访问外部私有知识库，解决训练数据截止、私有数据无法训练的问题
- 常见实现：LangChain 的 RetrievalQA / RAG chain，向量数据库用 Chroma、Milvus、Pinecone、Faiss 等
- 与 fine-tuning 的区别：RAG 是推理时检索注入，fine-tuning 是训练时学习；RAG 更灵活、成本更低
- 在 LangGraph 中可以把向量检索封装成一个 Tool Node，让 Agent 按需调用

**话术示例**
RAG 是检索增强生成，思路是把私有文档先做向量化存到向量数据库里，用户查询的时候把问题也向量化，在数据库里做相似度检索，把最相关的几段文档片段拼进 Prompt，LLM 再基于这个上下文生成回答。这样可以让模型低成本地访问私有知识库，不需要重新训练。我们项目里虽然没有用到 RAG，但如果要加一个"查历史预警案例"这类功能，用 RAG 是很合适的，把历史文案向量化存起来，查询时检索相似案例注入上下文。

**评价**

- 不足：流式显示只说"可以实现"，没有说具体是 SSE 还是 WebSocket；认证没有展开（JWT？Token？）；三服务通信的具体协议（HTTP/SSE/WebSocket）没有说清楚；数字人绘制提到 Canvas 但没有说具体用什么库（如 Three.js、Live2D 等）。

**参考答案要点**

**话术示例**

### 13. 对话历史管理与缓存压缩算法【9 分】

**问题**
智能体的历史对话是怎么管理的？用什么做缓存的？是长期缓存还是滑动窗口？压缩算法怎么压缩？

**我的答案要点**
- 用 session ID 关联会话，在 Redis 中存取
- 全量存储对话，设定体积阈值，序列化后判断长度
- 超过阈值触发压缩：保留最近 5 轮完整对话 + 让模型将 5 轮之前的历史凝缩成一段摘要
- 系统提示词和中间提示词原封不动保留
- 新会话 = 系统提示词 + 中间提示词 + 摘要 + 最近 5 轮

**评价**
- 优点：压缩策略设计合理，有具体轮数配置（最近 5 轮），有体积判断机制，手动实现说明了工程能力。面试官对这块明显比较认可。
- 不足："滑动窗口"概念不熟悉，但实际实现的就是一种滚动保留策略，可以直接说"这就是一种滑动窗口加摘要的混合策略"。

**参考答案要点**
- 存储：Redis，key 为 session ID，value 为序列化的 message list
- 压缩触发：序列化后判断字节长度是否超过配置阈值
- 压缩策略：滑动窗口 + 摘要
  - 保留最近 N 轮（默认 5 轮）完整消息
  - 早期消息由 LLM 生成摘要，压入一条 system/summary message
  - 系统提示词和固定 prompt 原封不动保留
  - 重新拼装为新的 message list 存回 Redis
- 过期策略：可设 key TTL，长时间未操作的会话自动清除

**话术示例**
会话历史用 Redis 存，key 是 session ID，value 是序列化后的 message list。每次读会话之后判断一下序列化后的字节长度，超过阈值就压缩。压缩策略是滑动窗口加摘要的组合：最近的 5 轮消息完整保留，5 轮之前的那些历史让 LLM 做一次凝缩，生成一段摘要消息；系统提示词和中间固定 prompt 原封不动保留；最后把系统提示词 + 摘要 + 最近 5 轮重新拼成一个新的 message list 存回 Redis。这样既保证了最近对话的完整语义，又控制了 token 消耗。

### 14. 工具是否使用 MCP 协议【4 分】

**问题**
你们的工具封装成 MCP 服务了吗？一般智能体不都是调 MCP 协议吗？

**我的答案要点**
- 没有用 MCP，直接把工具注册到 LangChain 微服务中
- 通过 HTTP 请求通信

**评价**
- 优点：没有假装了解，如实说明了自己的实现方式。
- 不足：对 MCP（Model Context Protocol）完全不了解，是一个重要的知识盲区，对于做智能体开发的岗位这是一个减分项。

**参考答案要点**
- MCP（Model Context Protocol）是 Anthropic 提出的开放协议，标准化了 LLM 与外部工具/数据源的通信方式
- 核心概念：MCP Server（暴露工具/资源）、MCP Client（LLM/Agent 侧），通过标准化 JSON-RPC 协议通信
- 优势：工具可以跨 Agent 框架复用，减少重复开发；Claude、Cursor、Windsurf 等都内置了 MCP Client
- 与直接注册工具的区别：直接注册工具与框架强耦合（只能在 LangChain 里用），MCP Server 可被任何支持 MCP 的 Client 调用
- 我们项目用的是 LangChain 原生工具绑定，是更轻量的做法，适合项目内部使用；MCP 适合要跨框架/跨系统复用的场景

**话术示例**
我们项目里用的是 LangChain 原生的工具绑定方式，把 Python 函数直接注册为 Tool，和框架的耦合度比较高。MCP 是 Anthropic 提出的一个开放协议，把工具、资源的暴露方式标准化了，LLM 侧作为 MCP Client，工具侧作为 MCP Server，双方走标准的 JSON-RPC 通信。好处是工具可以跨框架复用，不只能在 LangChain 里用。我们当时场景比较单一，就没有用 MCP，直接用 LangChain 原生绑定；如果是要做一套供多个 Agent 或多个系统复用的工具库，用 MCP 标准化会更合适。

### 15. 历史文案与当前天气数据冲突时如何决策【8 分】

**问题**
如果检索到的历史文案说是"暴雨"，但当前数据查出来是"大雨"，智能体怎么决策？

**我的答案要点**
- 每次请求都有独立的时间、气象要素、区域参数
- 后端根据最新参数获取最新气象数据，作为权威数据源
- 智能体每次以当前参数生成文案，不考虑上次文案的预测内容
- 历史会话仅在用户主动"重新生成"时参考

**评价**
- 优点：逻辑清晰，边界说得很清楚——"以当前数据为准，历史会话只用于重新生成时的语义延续"，这个设计决策是正确的。
- 不足：可以主动说明这个设计的原因（气象数据有时效性，预测会随时间更新，历史预测不代表当前事实），以及如果要做数据一致性校验该怎么处理。

**参考答案要点**
- 每次调用以当前参数 + 当前数据为权威依据，历史文案是过去某一时刻的预测，不应覆盖新的观测数据
- 气象预测本身随时间迭代更新，暴雨降级为大雨是正常的
- 历史会话的作用：提供语义上下文（如用户此前要求的文案风格、偏好的措辞）而非提供数据依据
- 如果需要展示"预测演变"可作为一个单独功能，把历史文案和当前文案都展示出来，让用户对比

**话术示例**
数据层面以当前为准。气象预测本来就会随时间更新，上次预报暴雨、这次更新为大雨，这是正常的；历史文案是当时的预测结论，不是事实，不应该影响当前的判断。所以每次生成文案，智能体只看这次请求传来的参数和对应的最新气象数据；历史会话的价值在于保留用户对文案风格或措辞的偏好，给大模型一个语义上下文参考，而不是提供数据依据。如果要展示"预测版本演变"，可以做一个单独的对比视图，不应该混进文案生成的决策链里。

### 17. 高并发处理策略【9 分】

**问题**
大并发场景下你们是怎么处理的？能具体讲讲？

**我的答案要点**
- 压测工具 JMeter：1000 次请求在 10 秒内发完，不能有失败请求
- 发现克里金插值（Kriging）接口是瓶颈：原来 2~3 秒，计算 CPU 密集型
- 优化方案：自定义线程池 + FutureTask 分片并行计算
  - 线程池配置：min=2，max=min(CPU 核数, 8)
  - 矩阵拆分后分片计算，结果拼装
  - 优化后降到几百毫秒
- 熔断降级：仍是最慢接口，高并发时触发熔断，降级为低精度计算做兜底
- Redis 缓存：相同要素+时间的结果缓存，只计算一次
- 缓存穿透：空值也存 Redis（存 null 占位）
- 缓存击穿：热点 key 失效时加互斥锁，只让一个线程去计算，其他等待后走缓存

**评价**
- 优点：有完整的压测 → 定位 → 多层优化（计算优化 + 熔断 + 缓存）的过程，数字具体，面试官明显满意。
- 不足：缓存雪崩（大量 key 同时失效）没有提到，可以补一句。

**参考答案要点**
- 性能定位：日志分析找到慢接口，区分 CPU 密集型 vs I/O 密集型
- CPU 密集型优化：线程池分片并行（线程数 ≤ CPU 核数），FutureTask 收集结果
- 熔断降级：Sentinel/Resilience4j 或自定义计数器，触发熔断后走降级逻辑（如低精度计算）
- Redis 缓存三问题：
  - 缓存穿透：空值存 Redis（TTL 短一些），或布隆过滤器
  - 缓存击穿：互斥锁（Redis SETNX），热点 key 不过期
  - 缓存雪崩：key TTL 加随机偏移，错峰失效

**话术示例**
并发优化我可以举个具体例子。压测工具用的 JMeter，要求 1000 次请求在 10 秒内全部成功。压测跑起来发现一个接口特别慢，是克里金插值算法接口，从 JSON 点位数据生成矩阵，原来要 2~3 秒，把整条链路都拖慢了。分析是 CPU 密集型，就用线程池加 FutureTask 分片并行，矩阵拆成多片独立计算再拼，线程数上限设为 CPU 核数最多 8，优化后降到几百毫秒。但它还是最慢的，于是加了熔断，高并发时触发熔断就走降级逻辑——用低精度模式计算，牺牲一点精度保住响应；同时用 Redis 缓存计算结果，同样参数只算一次。缓存这边处理了三种问题：穿透用空值占位；击穿用互斥锁，只让一个线程去算，其他等一会再拿缓存；雪崩就是 key 的 TTL 加随机偏移，避免同时失效。

### 19. Vue 生态与响应式原理【8.5 分】

**问题**
介绍一下 Vue 的生态，或者它的一些原理。

**我的答案要点**
- Vue 2：`Object.defineProperty` 实现响应式，发布订阅模式；缺陷：不支持新增属性的响应、不能通过索引修改数组（需用 `$set`/`$delete`），数组重写了 7 个方法；深层对象递归转换性能差；Options API 功能碎片化难维护
- Vue 3：`Proxy` 代理，懒代理（深层对象惰性响应），按需引入体积小，Diff 算法优化（静态提升），整体性能/体积/开发体验优于 Vue 2

**评价**
- 优点：Vue 2 的响应式原理说得准确，缺陷说到位，Vue 3 的改进点也对应上了，有明显的深度。
- 不足：Vue 3 的编译时优化（静态提升、Patch Flag）可以更具体；Composition API 的优势只提了"代码维护性"，可以说说为什么（按逻辑聚合而非按选项拆散）；生态方面（Vite、Pinia、VueRouter 4）没有提到。

**参考答案要点**
- **Vue 2 响应式**：`Object.defineProperty` getter/setter，`Dep`（依赖收集器）+ `Watcher`（订阅者），发布订阅模式；数组重写 push/pop/shift/unshift/splice/sort/reverse 7 个方法；缺陷：新增属性不响应（已有 getter/setter 的才响应）、深层递归初始化性能差
- **Vue 3 响应式**：`Proxy` 拦截整个对象，`Reflect` 转发操作；`reactive` 懒代理（访问到深层才递归包装），`ref` 包装基本类型；`track/trigger` 替代 Dep/Watcher
- **编译优化**：静态节点提升（hoistStatic）、Patch Flag 标记动态节点（跳过静态节点 Diff）、Block Tree
- **Composition API vs Options API**：按逻辑关注点聚合，同一功能的数据/计算/副作用写在一起，方便提取 composable 复用
- **生态**：Vite（极速 HMR + Rollup 打包）、Pinia（轻量状态管理，TS 友好）、Vue Router 4

**话术示例**
Vue 2 的响应式核心是 `Object.defineProperty`，初始化时遍历 data，对每个属性都设置 getter 和 setter，getter 里做依赖收集，setter 里触发通知，背后是 Dep 和 Watcher 的发布订阅模式。但它有个明显缺陷：只能拦截已有属性，对象里后加的属性不是响应式的，需要用 `$set`；数组的话重写了 7 个变异方法来触发更新，但通过索引直接改不响应；另外深层对象是递归初始化，性能开销比较大。Vue 3 换成了 `Proxy`，直接代理整个对象，天然支持新增属性响应；深层对象是懒代理，访问到才递归，性能更好。编译层面加了静态提升和 Patch Flag，Diff 的时候直接跳过静态节点，只对比有 flag 的动态节点，大幅减少对比量。配合 Vite 的极速 HMR，整体开发体验比 Vue 2 强很多。
