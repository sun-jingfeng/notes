### 4. AI 编程的限制与提效手段 【8.5 分】

**问题**：在用 AI 编程的过程中，你觉得目前 AI 还有哪些限制和瓶颈？你们是通过哪些手段来提高 AI 编码的准确率和效率的？

**我的答案要点**

- 限制一：代码风格灵活性差，生成代码与现有风格不符 → 用提示词持久化（cursor rules）解决
- 限制二：准确率问题 → 用 MCP 接入平台（如 Figma MCP 读取设计图）提高输入精度
- 限制三：上下文窗口太短（约 200K），无法理解完整项目历史 → 由人维护项目全局视角，提问时指定相关文件、垂直化问题

**评价**

- 优点：从「已解决的问题」和「仍存在的瓶颈」两个维度回答，结构清晰；举例具体（MCP + Figma、cursor rules）；"上下文短"是真实痛点，答得准确。
- 不足：「提示词持久化」这个词不是业界通用说法，可以直接说 cursor rules 或 system prompt；可以补充一个「提问垂直化」的具体示例让回答更生动。

**参考答案要点**

- 瓶颈一：风格一致性 → cursor rules（项目级 + 全局级）固化编码规范，让 AI 每次生成都遵循同一套约定。
- 瓶颈二：上下文窗口有限，AI 不知道项目历史 → 提问时附上相关文件，把问题拆细、垂直化；人负责维护项目整体节奏和历史脉络。
- 瓶颈三：输入精度（截图 → MCP）→ 接入 Figma MCP，直接发设计图链接，减少截图带来的信息损失。
- 提效手段小结：cursor rules 规范输出 + 垂直化提问缩小范围 + MCP 提升输入精度 + 人做最终把关。

**话术示例**

> AI 目前最大的几个瓶颈：第一是风格一致性，它不知道你项目之前怎么写的，每次生成都可能和你的代码风格不符。这个问题我们用 cursor rules 来解决，把项目的编码规范、组件拆分方式、接口风格都固化进去，让 AI 每次生成时先读这些规则，输出就会越来越接近预期。  
> 第二个是上下文窗口太短，AI 不知道你项目的历史，你让它改一个问题，它可能不知道这个功能之前经历过什么。我的做法是提问时指定相关文件，把问题说得足够具体，不要大而全；同时人要对项目全局有掌控，不能把一个完整项目全甩给 AI 然后自己不管。  
> 第三是输入精度，之前发截图给 AI 信息损失大，接入 Figma MCP 之后直接发设计图链接，AI 自己读图，精度和效率都明显提升了。

### 6. 微前端选型：iframe vs 微前端框架 【8 分】

**问题**：你当时考虑了微前端方案和 iframe，微前端你说有一些问题，具体说说？最终选 iframe 是基于哪些考虑？

**我的答案要点**

- 乾坤：不具备原生样式隔离，需要手动实现
- micro-app：调研时路由存在问题
- 微前端框架整体：父子通信、子系统间通信、样式隔离等都要用框架 API 手动处理，开发成本高
- iframe：同源部署下父子通信方便，综合开发成本低，最终选 iframe

**评价**

- 优点：对比了两种微前端框架的具体问题点，调研过程清晰；最终决策有依据（开发成本 + 同源条件）。
- 不足：对乾坤的描述略有误差（乾坤有 CSS 沙箱机制，但在特定场景下确实存在样式泄漏问题，表述可以更准确）；可以补一句"这个项目满足同源部署条件，所以 iframe 的限制是可接受的"来说明决策前提。

**参考答案要点**

- 乾坤：CSS 沙箱（shadow DOM / scoped CSS）在某些场景下存在泄漏，且全局样式注入、第三方组件库等需要额外处理；父子通信需要用 `initGlobalState` API。
- micro-app：基于 Web Components，路由劫持机制和宿主路由有时冲突；样式隔离相对较好，但整体定制成本仍高。
- 选 iframe 的核心理由：①本项目同源部署，`localStorage` / `sessionStorage` 共享，通信无跨域问题；②原生样式隔离，零配置；③两个现有子系统直接复用，无需改造。
- 决策前提说清楚：同源 + 子系统相对独立 + 用户切换频率低 → 适合 iframe。

**话术示例**

> 当时主要对比了乾坤和 micro-app。乾坤的 CSS 沙箱在某些场景下会有样式泄漏，全局组件库的样式还需要额外处理；父子通信要用它自己的 `initGlobalState` API，子系统改造成本不小。micro-app 基于 Web Components，样式隔离相对好一些，但调研时路由劫持和宿主路由有冲突，排查起来比较麻烦。  
> 最终选 iframe 主要是三点：第一，我们是同源部署，存储共享，通信直接用 `window.postMessage` 或共享 storage 就行；第二，iframe 原生样式隔离，两个现有子系统不需要任何改造直接嵌进来；第三，确认过产品，用户在这几个子系统之间切换频率不高，iframe 重新加载的问题可以接受。综合下来 iframe 的开发成本最低，且满足业务需求。

### 7. iframe 的缺点 【7.5 分】

**问题**：你觉得 iframe 自身相对微前端方案会有哪些缺点？

**我的答案要点**

- 最好同源部署，非同源时 `localStorage` 不互通，通信麻烦
- 切换页面时 iframe 内容重新加载，不像微前端有路由缓存效果
- 路由不同步，每个子系统有自己独立的路由上下文
- 以上缺点对当前项目都可接受

**评价**

- 优点：列出了 iframe 的主要缺点，且都结合了具体场景说明；最后点明"这些缺陷对我们项目都可接受"体现了取舍判断。
- 不足：可以补充 iframe 的 SEO 问题（虽然 ToB 场景不关注）和 `history` 路由状态无法持久化的问题；"切换重新加载"的描述可以更精确——每次切换都会销毁 iframe，再切回时重新挂载。

**参考答案要点**

- 通信限制：非同源无法共享 `localStorage`，需要用 `postMessage`，且有跨域安全限制。
- 状态丢失：切换子系统时 iframe 被销毁，页面状态无法保持（除非用多个 iframe 元素同时挂载并通过 `display: none` 切换来缓存）。
- 路由不同步：子系统路由变化不会同步到宿主 URL，刷新后丢失子系统内的路由状态。
- 性能：每个 iframe 是独立渲染上下文，资源无法共享（如公共依赖会被重复加载）。
- 可接受前提：同源部署 + 子系统间切换不频繁 + 无 SEO 需求 → 上述缺点均可接受。

**话术示例**

> iframe 主要有几个缺点：第一是通信，最好同源部署，非同源的话 `localStorage` 不共享，只能靠 `postMessage`，有跨域限制；第二是状态丢失，默认情况下切换子系统时 iframe 会销毁重建，子系统内的页面状态也会丢，虽然可以用多 iframe + `display: none` 的方式做缓存，但如果子系统多的话内存开销会比较大；第三是路由不同步，子系统内跳了几个页面，宿主 URL 不会变，刷新后子系统路由状态会丢失；第四是资源隔离，每个 iframe 独立渲染，公共依赖无法共享，包体积会有重复。  
> 这些问题在我们项目里都是可接受的，同源部署、用户切换不频繁、也不需要 SEO，所以最终选了 iframe。

### 8. iframe 首屏性能优化（预缓存） 【8 分】

**问题**：你提到过 iframe 有性能问题，具体不好的表现是什么？怎么解决的？

**我的答案要点**

- 问题：首次进入第二个子系统页面时白屏约 1 秒
- 解决：首屏加载完成后，提前把其余几个子系统页面用请求方式预加载一遍，后续切换时加载速度明显提升
- 懒加载：权限树节点展开时实时请求，不一次性加载所有权限数据

**评价**

- 优点：预缓存思路正确，是 iframe 场景下的实用优化手段；懒加载的场景（权限树）描述具体。
- 不足：「用请求的方式获取一下」表述不够精确，可以说清楚是通过 `fetch`/`XMLHttpRequest` 预请求 HTML 入口，或者是提前创建隐藏 iframe 节点；预缓存的时机（首屏 onload 之后）和触发方式可以补充。

**参考答案要点**

- 问题本质：iframe 首次挂载时需要重新解析 HTML、加载 JS/CSS 资源，导致白屏。
- 预缓存方案：首屏 `onload` 后，在后台依次创建隐藏 iframe（`visibility: hidden` 或 `display: none`），提前完成资源加载和脚本初始化；用户切换时直接显示已初始化的 iframe，消除白屏。
- 权限树懒加载：权限节点数据量大，初始只加载根节点，展开时按需请求子节点，降低首屏请求量和渲染压力。

**话术示例**

> iframe 的性能问题主要是首次切换到某个子系统时，它要重新加载 HTML、解析 JS 和 CSS，会有将近一秒的白屏。我的解决方案是在主壳首屏加载完成之后，在后台提前把剩余几个子系统的 iframe 创建出来但隐藏掉，让它们完成资源加载和脚本初始化。用户真正切换过去时，iframe 已经初始化好了，直接显示，白屏问题基本消除。  
> 另外权限树那块用了懒加载，权限节点比较多，初始只请求根节点，用户展开某个节点时再实时请求子节点，减少首屏的请求量。

### 9. 后端微服务架构——公共逻辑复用 【8 分】

**问题**：你提到公共逻辑放在一个服务里、各省份有各自的服务，实际项目中有没有出现某些省份原本不同的逻辑后来趋同了，需要重构到公共服务的情况？你们怎么处理的？

**我的答案要点**

- 写之前会先和产品确认：这个功能是所有省份都有，还是只有某个省份有
- 如果后来需求变了，某省份的独立逻辑变成公共的了，就重构，把代码从省份微服务挪到公共微服务

**评价**

- 优点：有提前确认需求的习惯，能降低返工概率；对需求变化有明确的处理方式（重构）。
- 不足：没有提到重构时的具体操作（如接口兼容性、其他省份如何同步更新）；可以补充"如何保证重构时不影响已上线省份的服务"。

**参考答案要点**

- 预防：功能开发前与产品确认作用域（全省通用 vs 省份独有），减少后期重构频率。
- 变化处理：将省份微服务中的逻辑提取到公共微服务，保持接口签名不变（或做兼容处理），省份微服务改为调用公共服务，原省份服务逻辑删除或保留兜底。
- 工程保障：通过接口版本号或特性开关控制各省份服务的功能开关，避免全量上线时影响其他省份。

**话术示例**

> 写之前我会先跟产品确认：这个功能是所有省份都要，还是只有这一家要？确认清楚了再决定写到哪里。  
> 也确实遇到过省份独有的功能后来变成通用的情况，处理方式是把那段逻辑从省份微服务提到公共微服务里，接口签名尽量保持不变，省份微服务改成调公共服务的接口，再把自己原来的实现逻辑删掉。重构前会先确保新的公共逻辑在一个省份跑通、测试没问题，再逐步让其他省份切过来。

***

### 10. 前端多省份分支管理策略 【7.5 分】

**问题**：前端这边也会因为不同省份的页面功能和展示不一样，做了对应拆分吗？

**我的答案要点**

- 用分支管理：主分支放公共逻辑，每个省份建一个分支
- 公共逻辑提交到主分支，省份分支用 `cherry-pick` 拉取需要的提交
- 某些提交不是所有省份都需要，用 cherry-pick 可以精准选取

**评价**

- 优点：思路清晰，解释了为什么用 cherry-pick 而不是 merge（需要精准控制哪些提交进哪个省份）。
- 不足：没有主动提到这种方式的风险和代价（长期 cherry-pick 导致分支历史分叉、后续 merge 困难），留了一个被追问的口子。

**参考答案要点**

- 分支策略：主分支（`main`）存公共逻辑；每个省份独立分支（如 `province/tianjin`）。
- cherry-pick 的适用场景：公共提交不是每次都全省份同步，某些功能只有部分省份要，cherry-pick 实现精准选取。
- 风险说明：长期 cherry-pick 会导致各省份分支与主分支历史越来越不一致，出现冲突时需手动解决；定期评估是否有必要做一次全量 rebase/merge 来对齐历史。

**话术示例**

> 前端这边是分支管理：主分支放公共逻辑，每个省份建一个独立分支。公共的改动提交到主分支，省份分支通过 cherry-pick 拉取需要的提交。  
> 选 cherry-pick 而不是直接 merge 主要是因为，并不是每次主分支的改动所有省份都需要，有些功能只有几个省份要、其他省份暂时不需要。如果直接 merge 就会把不需要的功能也带进来，cherry-pick 可以精准控制。  
> 当然代价是长期下来各省份分支和主分支的历史会越来越分叉，出现冲突时需要手动解决，这部分确实有一定维护成本。

***

### 11. cherry-pick 导致分支分叉问题 【7 分】

**问题**：cherry-pick 操作多了之后，你后面可能就没法做 merge 了，因为主分支和其他分支上同一个文件的代码已经有差异了，会有这种情况吗？

**我的答案要点**

- 确认会有：cherry-pick 之后有时候有冲突，手动解决
- 大多数情况没冲突，因为功能按模块划分
- 少数有文字性差异（如省份名称不同），手动改一下

**评价**

- 优点：承认了问题存在，没有回避；说明了大多数情况可控的原因（按功能模块划分，减少文件级冲突）。
- 不足：对"长期无法 merge"这个更深的问题没有正面回应——面试官问的核心是分支历史的永久性分叉，而不只是冲突。可以补充：这种架构下各省份分支本来就是发散的，不追求最终合并，是预期内的设计选择。

**参考答案要点**

- 正面承认：这种多省份分支策略，本质上就是接受各分支历史永久分叉，不追求统一合并，这是预期内的架构取舍。
- 冲突类型：文字性差异（省份名称、地区 ID 等参数）为主，逻辑性冲突少，因为功能代码按模块文件划分，跨文件冲突概率低。
- 缓解手段：cherry-pick 时及时解决冲突不积压；公共逻辑提取到公共文件/组件，减少各省份分支中与公共逻辑重叠的代码量，降低冲突面。

**话术示例**

> 确实会有，这种策略本身就是预期内的分叉，不追求最终把各省份分支合回主分支，各省份分支就是独立维护的。  
> 实际遇到的冲突大多是文字性的，比如省份名称、查询参数里的地区 ID，因为业务代码我们是按功能模块拆文件的，同一个文件里跨省份有逻辑差异的情况比较少，所以冲突频率不高，遇到了手动改一下。  
> 长期来看，减少冲突的根本办法是把公共逻辑尽量抽到公共文件里，各省份分支只保留真正有差异的代码，这样 cherry-pick 的冲突面就会越来越小。

### 12. 笔试题：短链生成平台 【7 分】

**问题**：用 AI 完成一个短链生成平台，要求：输入 URL → 生成随机短链 → 短链可跳转；不存在时返回 404；同一 IP 每分钟限制生成 10 次，超出返回 429。时间 30 分钟，尽量完善。

**我的答案要点**

- 用 Claude 4.6 生成前后端代码
- 数据库持久化存储，服务重启后数据不丢失
- 遇到前端用 GET、后端用 POST 的方法不匹配问题，AI 修复后解决
- 最终前后端联调跑通，功能可用
- 代码 review 时发现：URL 只校验了 HTTP/HTTPS 协议头，未做内网 IP 限制；短链生成用随机字符串，小概率可能重复，未做去重保障

**评价**

- 优点：30 分钟内用 AI 完成了可运行的前后端项目，数据库持久化，核心功能通过测试；能对生成代码做 review，主动识别了安全问题。
- 不足：前后端 HTTP 方法不一致是比较基础的联调问题，AI 应在初始 prompt 中通过规范约定避免；短链重复生成问题没有在开发阶段主动发现，是被面试官引导才发现的；内网 IP SSRF 安全漏洞未提前考虑。

**参考答案要点**

- 短链去重：生成后查数据库是否已存在，存在则重新生成；或使用雪花 ID / UUID + Base62 编码确保唯一性。
- SSRF 防护：校验 URL 是否指向私有 IP 段（`10.x.x.x`、`172.16.x.x`、`192.168.x.x`、`127.x.x.x`、`localhost`），拒绝内网地址，防止服务端请求伪造。
- 输入校验完整性：① 协议必须是 HTTP/HTTPS；② 排除私有 IP；③ URL 格式合法性（可用正则或 URL 解析库）。
- AI 编程最佳实践：在初始 prompt 中明确前后端接口约定（方法、路径、数据格式），避免联调阶段才发现方法不一致。

**话术示例**

> 用 AI 写这类项目，初始 prompt 里我会把接口约定写清楚：前端用什么方法、后端路径怎么定义、请求体格式是什么，这样前后端生成出来就不会有方法不一致的问题。  
> 短链去重我会用数据库唯一索引兜底：生成后先查是否已存在，如果存在重新生成；或者直接用 UUID 加 Base62 编码，碰撞概率极低。  
> 安全方面，URL 输入除了校验 HTTP/HTTPS 协议头，还要过滤内网 IP 段，防止 SSRF 攻击——不能让用户构造一个指向内网服务的 URL 让我们的服务去帮他转发请求。
