### 2. 介绍一个智能体搭建案例 【7.5 分】

**问题**：因为公司主要做智能体搭建，你介绍一个智能体搭建的案例。

**我的答案要点**

- 项目：气象雷达监测预警，功能：智能预警文案生成
- 技术选型：Spring AI vs Python 生态，最终选 Python（LangChain），生态更成熟
- 前端传参：气象要素、时间、经纬度范围、用户输入提示词
- Java 后端根据参数生成气象数据文件路径，再转发给 Python 微服务
- Python 微服务内部：工作流编排 + 工具绑定 + 会话管理，包装为 FastAPI HTTP 服务，用 Nacos 注册
- 工作流节点：① 地名生成节点（经纬度 → 文字地名）；② 气象要素路由节点（按要素分发到不同模型节点）；③ 各要素模型节点（PNG 色斑图读取 RGB 像素还原矩阵 / JSON 点位数据处理）；④ 结构化输出节点（硬编码格式要求）
- 数据缓存：时间 + 气象要素确定后数据唯一，处理结果用 Redis 缓存
- 会话管理：支持续聊/重新生成；有会话 ID，用 Redis 缓存会话；会话过长时压缩（保留最近 5 轮完整对话 + 摘要旧对话 + 完整保留系统提示词）

**评价**

- 优点：细节丰富，展示了真实落地经验；涵盖工作流编排、工具绑定、会话管理、缓存压缩多个关键点；技术选型有理由。
- 不足：讲述顺序偏流水账，缺少「先说结论 → 再说架构 → 最后讲亮点」的结构；对非技术面试官来说，大量技术细节可能导致失焦；没有主动点出核心亮点（会话压缩算法是自研，可单独强调）；可以用一句话总结项目价值（如"把原本需要人工写报告的工作自动化了"）。

**参考答案要点**

- 先说项目价值：「这个功能把气象员手工写预警文案的工作自动化了，用户选好要素和区域，系统自动生成结构化的专业文案并支持续聊修改。」
- 架构三层：前端 → Java 后端（数据路径解析）→ Python 智能体微服务（LangChain 工作流）
- 工作流四节点：地名解析 → 要素路由 → 数据处理（按要素分策略）→ 结构化输出
- 亮点一：每种气象要素独立模型节点 + 专属工具，垂直化处理减少幻觉
- 亮点二：自研会话压缩算法（无现成库）：保留近 5 轮完整 + 旧轮摘要 + 系统提示词全保留
- 亮点三：FastAPI 包装为微服务 + Nacos 注册，接入现有后端体系

**话术示例**

> 这个项目是气象雷达预警系统里的智能预警文案生成功能，目标是让用户选好气象要素和地图范围，AI 自动生成一段专业预警文案，还支持不满意时续聊重新生成。  
> 架构上分三层：前端传参，Java 后端解析出气象数据文件路径，然后把路径、要素、经纬度、提示词一起发给我开发的 Python 智能体微服务。  
> 微服务内部是 LangChain 工作流，有四个节点：第一个是地名解析，把经纬度转成文字地名；第二个是要素路由，因为色斑图是 PNG 要读像素还原数据、点位是 JSON 结构，处理逻辑不一样，所以按要素路由到各自专属的模型节点去处理，这样垂直化处理能减少幻觉；最后一个是结构化输出，按固定格式生成文案。  
> 会话管理我自研了一套压缩算法，因为没有现成包，思路是保留最近 5 轮完整对话，再用模型把更早的对话摘要压缩，系统提示词完整保留，整体控制在不超过 token 阈值。最后用 FastAPI 包装成 HTTP 服务，注册到 Nacos。

### 7. 你对智能体的理解 【6.5 分】

**问题**：你对智能体是一个什么东西，有什么理解？

**我的答案要点**

- 最简单的理解：模型 + "哈尼斯"（harness，智能体框架层）
- 认为工作流编排很关键，同一模型在不同平台能力有肉眼可见差距
- 举例：Claude Sonnet 4.6 在 Cursor、Claude.ai、Copilot 中体验不同，Cursor 最强
- 差别本质在于智能体框架部分不同：思考方式、工具选择、记忆管理、工作流编排
- 落到项目中：程序员的主要工作就是开发这个框架层（harness）

**评价**

- 优点：有实际使用体验支撑，举例具体生动；能从开发者视角讲清楚智能体的本质。
- 不足：「哈尼斯」是自造音译词，并非业界通用术语（业界更多说 Agent Framework / Agentic Loop / orchestration layer），直接用这个词面试官可能听不懂；对智能体的定义可以更系统，补充 Memory / Planning / Tool Use / Action 四要素；"尼斯"这个词贯穿整段，对非技术面试官来说理解成本高，应简化表达。

**参考答案要点**

- 标准定义：智能体 = 大模型 + 记忆（Memory）+ 工具（Tools）+ 规划能力（Planning/Orchestration）
- 工作流编排是核心：同一模型，不同编排策略效果差异显著（以 Claude Sonnet 在不同产品中的差距为例）
- 模型只负责「接收消息、生成输出」，其他所有东西（如何思考、如何选工具、记忆如何管理、多轮对话如何串联）都是上层框架决定的
- 开发者的核心工作：设计和实现这个框架层，包括工作流节点、工具调用逻辑、会话管理、提示词体系
- 落地价值：把专业任务（如气象文案生成）分解为可编排的节点，让模型聚焦在各自擅长的子任务上，减少幻觉、提升稳定性

**话术示例**

> 我理解智能体的本质是：大模型本身只做一件事，就是接收输入、生成输出，它没有记忆、不会自主选工具、不会规划任务流程。  
> 让模型变成一个"智能体"，需要在它之上构建一套框架，负责管理记忆、决定什么时候调用什么工具、怎么把复杂任务分解成多步骤来完成。这就是为什么同一个 Claude Sonnet 模型，在 Cursor 里写代码比在其他平台强很多——区别不在模型，在于上面这套框架设计得好不好。  
> 从开发者角度来说，做智能体开发的核心工作就是设计和实现这个框架层：工作流怎么编排、工具怎么绑定、会话记忆怎么管理，这些决定了智能体最终的能力上限。

**问题**：你了解欧文克劳吗？最近用过 open claude 吗？

**评价**

**参考答案要点**

- 核心定位：Claude Desktop 是一个计算机控制级智能体，通过 Computer Use 能力操作本地应用和文件系统
- MCP（Model Context Protocol）：Anthropic 提出的标准化工具调用协议，允许第三方开发 MCP server 拓展 Claude 的能力（文件系统、数据库、地图、浏览器等），社区生态活跃
- 使用场景判断：操作系统级任务（整理文件、网页抓取、自动化流程）Claude Desktop 很擅长；代码开发场景仍偏向 Cursor / Copilot 这类编辑器内 Agent
- 关键词：Computer Use / MCP / Agent 生态

**话术示例**

> 用过，刚出来的时候就下载体验了。本来想接 Claude API 用满血版本，但因为网络问题没成功，后来接的是本地跑的模型。  
> Claude Desktop 的定位我理解是一个操作系统级的智能体，通过 Computer Use 能力可以操作本地应用、浏览器、文件系统，相当于把整台电脑交给 AI 去控制，对于自动化任务挺有价值的。  
> 它的插件体系用的是 MCP，是 Anthropic 推出的一个标准化工具调用协议，社区里有很多第三方的 MCP server，比如存储、数据库、地图之类的，能把它的能力扩展很多。  
> 实际用下来，我觉得它做代码以外的操作任务挺好用的，但写代码还是更习惯在 Cursor 这类编辑器里用，因为专门为代码场景优化过的 Agent 效果还是更好。

- AI 负责规范化/公式化样板代码（接口调用、组件 UI 还原等）
- 工作流：AI 出代码 → 功能测试 → 逐行 review → 确认无问题才提交

**评价**

- 优点：比例具体有说服力；区分了哪些场景用 AI、哪些自己写，体现了成熟的 AI 使用思路；提到 review 流程，表明对代码质量有把控意识。
- 不足：可以进一步说明 AI 辅助带来的效率提升（如同样的工作量节省了多少时间），量化更有说服力。

**参考答案要点**

- AI 产出占比约 75%，自己手写约 25%
- 自己写的部分：基础框架（项目结构 / 模块拆分）、通信协议设计（接口规范 / 数据结构）、核心业务逻辑、智能体工作流编排
- AI 写的部分：样板代码（接口调用、表单、列表组件、UI 还原）、测试用例、文档
- 质量保障：AI 出代码后必须走功能测试 + 逐行 review 才算收进来，不盲目信任
- 效率提升：整体开发效率提升约 2-3 倍，同样的工作量可以更快交付或做更多的事

**话术示例**

> 目前大概 75% 的代码由 AI 产出，25% 是我自己手写。  
> 我自己写的主要是这几类：基础框架搭建、模块结构拆分、通信协议设计这些比较核心的部分，以及业务逻辑里比较关键的节点。AI 负责的是那些比较规范化的样板代码，比如具体的接口调用、照着设计图还原 UI 组件，这类代码有固定套路、量又大，交给 AI 效率高很多。  
> 但我有一个习惯：AI 写完我一定先跑一遍功能测试，再逐行 review 一遍代码，确认没问题才算这段代码收进来了，不会盲目信任 AI 的输出。整体来看，效率大概提升了两三倍。
