### 2. 项目中智能体落地的设计与实现【9 分】

**问题**
你在项目里是怎么接入智能体的，主要应用了哪些能力？这块的设计和架构是你来负责的吗？

**我的答案要点**
- 项目：气象雷达预警系统，功能为智能预警文案生成
- 数据流：前端传气象要素 + 经纬度 + 用户提示词 → Java 后端获取数据存储地址 → Python 智能体微服务
- 气象数据不入库，由算法处理后存硬盘，地址动态生成
- 工作流（LangGraph）节点编排：
  1. 经纬度 → 地名转换（绑定 Python 地名转换工具）

  3. 结构化输出节点（硬编码格式，符合客户要求）

- 会话压缩：序列化后判断长度，超阈值时保留系统提示词 + 最近若干轮完整会话 + 压缩早期会话（用模型压缩）

**评价**

**参考答案要点**
- 项目背景：气象雷达预警系统，公司首批智能体落地项目，核心功能是根据气象数据 + 用户提示词自动生成预警文案
- 技术方案：Python + **LangGraph** 搭建智能体微服务，**FastAPI** 包装后注册到 Java 主服务
- 工作流节点：地名解析（工具绑定）→ 气象要素路由（按类型分发到专属子模型）→ 结构化输出
- 工具绑定：每种气象要素数据格式不同（PNG/RGB 二进制、JSON 点位），分别绑定对应读取和处理工具，保证垂直性
- 会话管理：前端携带会话 ID，智能体侧按 ID 查找/新建会话，支持续聊
- 会话压缩：上下文超阈值后保留系统提示词 + 最近 N 轮完整对话 + 模型压缩早期对话，防止 context 无限增长

**话术示例**
这个功能是在气象雷达预警项目里落地的，目标是根据气象数据和用户输入的提示词，自动生成一段结构化的预警文案。

整体架构是：前端把气象要素、经纬度和提示词发给 Java 后端，后端根据经纬度和气象要素生成数据的存取地址，再连同这些参数一起发给我用 Python 搭建的智能体微服务。微服务用的是 LangGraph，做工作流的节点编排。

工作流里主要有三步：第一步是地名解析，把经纬度转成文案里可读的地名，绑定了 Python 的地理编码工具来做；第二步是路由，因为不同气象要素的数据格式不一样，比如色板图是 PNG 的 RGB 二进制，点位数据是 JSON，我给每种类型都建了独立的子模型并绑定了对应的处理工具；第三步是结构化输出，按照客户要求的格式硬编码输出。

另外还做了会话管理，支持用户改完提示词重新生成，也就是续聊。前端带着会话 ID 传过来，服务端根据 ID 找历史会话或者新建。为了控制上下文长度，我还手写了一个压缩策略，超过阈值后，保留系统提示词和最近几轮完整对话，早期的对话用模型压缩一遍，再组合成新的上下文。最后整个微服务用 FastAPI 包装成接口，注册进 Java 服务里。

### 5. 高并发场景下前后端优化方案【7.5 分】

**问题**
如果要支持更高并发，同时对首屏加载速度也有要求，前后端分别应该怎么优化？

**我的答案要点**
**前端：**
- 首屏要求高 → SSR（服务端渲染），不做纯 SPA
- 懒加载 / 按需加载，保证核心内容优先加载
- CPU 密集型任务移到后端；前端不得不做时用 Web Worker 或时间切片
- 重排重绘优化：不打断浏览器默认绘制周期，用 transform 替代几何属性变更
- Vue 响应式：深层响应（reactive）和浅层响应（shallowReactive）按需拆分声明
- Performance 面板检测内存泄漏和卡顿，定位后具体优化

**后端：**
- 压测（JMeter，1000 次 / 10 秒），有失败或慢请求则不合格
- 性能瓶颈多在业务层或数据库，Tomcat 等容器本身吞吐量足够
- 业务层 CPU 密集型：多线程分片计算 + CompletableFuture 组装结果 + 缓存（参数不变则复用计算结果）
- 数据库慢查询：查 MySQL 慢查询日志，统计慢请求参数，设计覆盖这些查询的复合索引
- 索引规则：最左前缀原则、索引头避免不等判断和模糊查询
- 深分页优化：子查询分页（延迟关联）+ 减少回表次数

**评价**
- 优点：前后端都覆盖到，有具体项目案例支撑（矩阵计算多线程 + CompletableFuture + 缓存），数据库部分有实操深度（慢查询日志 → 索引设计 → 深分页）。
- 不足：前端 SSR 的讲解止于"需要服务器渲染"，没有进一步说 SSR 对 TTFB、FCP 的影响原理；Web Worker 在口语中表述不够清晰；没提到 HTTP 缓存（CDN、Cache-Control）、连接池、限流熔断等常见高并发手段。

**参考答案要点**
**前端：**
- 首屏优先：核心路由 SSR（减少 FCP 时间），非核心页面可保持 CSR
- 资源加载：路由级懒加载、组件异步导入、图片懒加载；静态资源走 CDN + 长缓存
- 渲染性能：用 transform/opacity 替代几何属性（触发 Composite 而非 Layout）；避免强制同步布局；requestAnimationFrame 控制动画节奏
- CPU 密集：Web Worker 隔离计算，避免阻塞主线程；长列表用虚拟滚动
- Vue 响应式：大数据结构用 shallowReactive/shallowRef，减少不必要的深层追踪

**后端：**
- 压测基线：JMeter 确认 TPS 目标，识别慢接口
- 业务层：CPU 密集型任务线程池并行 + CompletableFuture 合并结果；幂等计算结果写缓存（Redis）
- 数据库：慢查询日志定位慢 SQL → 设计复合索引（最左原则、避免索引失效场景）→ 深分页用延迟关联或游标分页；读写分离应对高读负载
- 接口层：接入限流（令牌桶/漏桶）和熔断（Hystrix/Sentinel）防止雪崩
- 连接池：数据库连接池（HikariCP）合理配置，避免连接耗尽

**话术示例**
高并发下首屏加载要求高，前端首先要考虑 SSR，把关键页面放到服务端渲染，这样 FCP 会快很多，不用等 JS 下载解析完再渲染。其他页面可以做路由懒加载和组件异步导入，保证用户最需要看到的内容先出来。静态资源走 CDN 加长缓存，减少源站压力。渲染上注意用 transform 替代 top/left 这类几何属性，只触发合成而不触发重排，对动画流畅度帮助很大。如果前端有 CPU 密集型计算，比如大数据处理，可以用 Web Worker 放到独立线程，不阻塞主线程渲染。

后端先用 JMeter 压测，确定 TPS 基线，找出慢接口。性能瓶颈一般不在 Tomcat 这层，多在业务层和数据库。业务层如果有耗时的计算任务，可以用线程池分片并行，CompletableFuture 合并结果；如果计算是幂等的，结果缓存到 Redis，下次相同参数直接返回。数据库慢查询先查慢查询日志，分析高频慢 SQL 的查询参数，设计覆盖这些参数的复合索引，注意最左前缀原则，索引列上不要做范围查询或模糊查询开头。深分页场景用延迟关联或游标分页，减少回表。流量大的时候还要在接口层加限流和熔断，防止突发流量把服务打垮。

- 需求层面：保持尊重 PM 的决策权，遇到明显与行业惯例不符或影响用户体验的设计会主动反馈，最终决定权在 PM
- 技术落地层面：自己负责的范围独立决策（可维护性、扩展性、开发成本优先）；涉及共用模块或对接规范时，主动与团队对齐，能讲清楚方案的设计理由和其他方案的不足，推动团队共识
- 举例：智能体微服务的接入方案，涉及前后端和 Python 服务的数据流和参数规约，主要由本人设计并推动各端对齐落地

**话术示例**
需求这块我一般尊重 PM 的决策，毕竟他对客户和业务背景了解更多。但如果我觉得某个设计明显不符合行业惯例，或者用起来会有问题，我会直接跟 PM 说，把我的想法和理由讲清楚，最终怎么定还是他来拍。

技术落地这块，自己负责的模块我会独立做技术选型，主要考虑可维护性、后续扩展空间和开发成本。如果是影响多人的公共方案，我会主动把设计思路同步给大家，有人有不同意见时，我会把自己的设计理由讲清楚，也会指出他们方案可能的问题，让大家真正理解并认可，这样后续落地配合起来也会顺很多。比如智能体接入项目里，前端传什么参数、后端怎么转给 Python 服务、各层的数据格式，这些规约都是我设计的，当时也是跟前后端同事对齐确认过才落地的。
