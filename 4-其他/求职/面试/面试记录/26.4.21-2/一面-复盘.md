### 5. 流式返回（SSE）的底层原理 【4.5 分】【错】

**问题**
流式返回 API 底层是怎么做到流式的？SSE / WebSocket 的连接是怎么建立的？

**我的答案要点**
- 流式返回遵循流式传输网络协议，通讯双方都遵守即可
- WebSocket 前端用 WebSocket API，后端用对应 API
- SSE 就是流式返回，前端侦听，后端有数据就发
- 底层原理不太了解

**错误点**：将 WebSocket 和 SSE 的底层建连机制混淆，仅停留在"遵循协议"的描述，未说出关键原理。

**评价**
- 优点：知道两者都是流式协议，知道使用场景区别（SSE 适合单向流，WebSocket 适合全双工）。
- 不足：未能说出 SSE 的本质（HTTP 长连接 + `text/event-stream`）；未说出 WebSocket 握手升级过程（HTTP Upgrade）；这是面试官明确追问的点，属于明显失分项。

**参考答案要点**
- **SSE（Server-Sent Events）**：
  - 本质是 HTTP 长连接，`Content-Type: text/event-stream`
  - 客户端发一次普通 HTTP GET 请求，服务端不关闭连接，持续往响应流写数据
  - 数据格式：`data: ...\n\n`，浏览器通过 `EventSource` API 接收
  - 单向（服务端 → 客户端），天然支持断线重连（`Last-Event-ID`）
  - LLM 流式输出场景首选，因为只需要服务端推数据
- **WebSocket**：
  - 先发 HTTP 请求，请求头带 `Upgrade: websocket` + `Connection: Upgrade` 触发协议升级
  - 服务端返回 101 Switching Protocols，之后连接变为 WebSocket 全双工 TCP 连接
  - 全双工，适合双向实时通信（聊天、协同编辑）
- LLM 流式返回选 SSE 而非 WebSocket 的原因：单向推送，SSE 更轻量；天然 HTTP，穿透代理更容易

**话术示例**
SSE 本质是 HTTP 长连接，客户端用 `EventSource` 发一个普通 GET 请求，服务端把 `Content-Type` 设置成 `text/event-stream`，然后不关闭连接，持续往响应流里写 `data: ...\n\n` 格式的数据，浏览器就能持续收到。它是单向的，服务端推给客户端，适合 LLM 流式输出这种场景。WebSocket 不一样，它先发一个带 `Upgrade: websocket` 头的 HTTP 请求，服务端返回 101，然后这条连接就从 HTTP 升级成 WebSocket 全双工 TCP 连接，双方都可以主动发数据，适合聊天、协同这类场景。

### 6. JWT 结构与验证机制 【6 分】

**问题**
你了解 JWT 吗？它的结构是什么？

**我的答案要点**
- 包含用户 ID
- 包含过期时间
- 可以取出 ID，也能验证 token 是否有效

**评价**
- 优点：知道 JWT 的基本用途（携带用户信息、验证有效性）。
- 不足：未说出三段式结构（Header.Payload.Signature）；未说出签名算法（HS256/RS256）；未说出服务端如何验证签名；回答停在"用户 ID + 过期时间"层面，较浅。

**参考答案要点**
- **三段结构**：`Header.Payload.Signature`，Base64Url 编码，用 `.` 分隔
  - **Header**：算法类型（如 `HS256`）+ token 类型（`JWT`）
  - **Payload**：声明（Claims），常见字段：`sub`（用户 ID）、`exp`（过期时间）、`iat`（签发时间）、自定义字段
  - **Signature**：`HMAC_SHA256(Base64(Header) + "." + Base64(Payload), secret)` —— 防篡改
- **验证流程**：服务端用密钥对 Header + Payload 重新签名，与收到的 Signature 比对；再检查 `exp` 是否过期
- **优点**：无状态，服务端不需要存 session；可跨域、跨服务传递
- **注意**：Payload 只是 Base64 编码，不加密，不应放敏感信息（密码等）

**话术示例**
JWT 分三段，用点分隔：Header、Payload、Signature。Header 里放算法类型，比如 HS256；Payload 里放声明，常见的有用户 ID、过期时间、签发时间，也可以放自定义字段；Signature 是用密钥对前两段做 HMAC 签名，用来防止内容被篡改。服务端收到 token 之后，用同一个密钥重新签一次，跟收到的签名对比，一致就说明没被篡改，再检查一下 `exp` 过期时间就完成验证了。需要注意的是 Payload 只是 Base64 编码，不是加密，所以不能放密码这类敏感信息。

### 7. 解决模型幻觉（气象预警文案场景）【9 分】

**问题**
气象智能体生成文案，你们怎么解决模型幻觉问题？

**我的答案要点**
- 核心方法：任务垂直化
- 每种气象要素对应独立的处理节点和工具
- 工作流第一节点：经纬度转地名
- 后续节点：气象要素路由 → 工具还原数据 → 生成文案
- 最后汇总到结构化输出节点，统一返回
- 依据：任务越大、历史越长，模型越容易忘掉 prompt，产生幻觉

**评价**
- 优点：有具体实践，逻辑清晰，答出了"任务垂直化 + 工具绑定 + 结构化输出"三个关键点，且给出了实际工作流设计，有说服力。
- 不足：未提 RAG（外置知识库）作为补充手段；可以补充"结构化输出约束格式"减少幻觉的思路。

**参考答案要点**
- **任务垂直化**：将大任务拆分为小任务节点，每个节点只处理一种气象要素，减少上下文污染
- **工具绑定**：每个节点绑定专用数据处理工具，模型不靠"记忆"而是靠工具调用获取准确数据
- **结构化输出**：最终汇总节点强制要求结构化格式（JSON Schema），减少自由发挥导致的幻觉
- **Prompt 约束**：每个节点 system prompt 聚焦单一任务，减少角色混淆
- （可补充）**RAG**：如果有历史文案或气象知识库，可通过 RAG 提供参考，进一步约束输出方向

**话术示例**
我们主要用任务垂直化来解决幻觉。我的经验是，一旦任务太大或者历史记录太长，模型就容易忘掉之前的约束，开始瞎说。所以我在 LangGraph 里为每种气象要素单独建了一个节点，每个节点只处理一种要素，并且绑定了专用的数据处理工具，模型不用靠记忆来还原数据，直接调工具拿结果。第一个节点是经纬度转地名，后面根据传入的气象要素类型路由到对应节点，最后汇总到一个结构化输出节点，强制要求格式，避免自由发挥。通过任务垂直化加工具绑定，幻觉问题基本就压下去了。

### 8. RAG 原理与好坏评估 【6.5 分】

**问题**
RAG 是什么？怎么评估 RAG 的好坏？

**我的答案要点**
- RAG：外置知识库，模型训练后知识固定，RAG 提供额外数据
- 工作机制：提前建向量库，推理时先查库，把检索结果和 prompt 一起喂给模型
- 评估：取决于训练数据质量和工作流编排是否合理；检索到的内容越相关，准确率越高

**评价**
- 优点：RAG 原理解释正确，类比联网搜索很直观。
- 不足：评估 RAG 好坏时只说了"数据质量 + 编排合理"，没有提标准评估维度（检索相关性、生成忠实度等），缺乏系统性。

**参考答案要点**
- **RAG 原理**：离线阶段将知识库文本向量化存入向量数据库；推理时将用户 query 向量化，相似度检索 Top-K 文档；将检索结果拼入 prompt，喂给 LLM 生成答案
- **评估 RAG 好坏的维度**：
  - **检索质量**：Precision（检索到的是否相关）、Recall（相关内容是否都检索到）、MRR（相关文档排名）
  - **生成质量**：Faithfulness（生成答案是否基于检索内容，不编造）、Answer Relevance（答案是否回答了问题）
  - **端到端**：用标注好的问答对做基准测试，对比有无 RAG 的准确率差异
  - 工具：**RAGAS** 框架可自动评估上述指标

**话术示例**
RAG 分两个阶段。离线阶段把知识库文本向量化，存到向量数据库里。推理时，用户的 query 也向量化，去库里做相似度检索，找到最相关的几段文档，然后把这些文档和原始 query 一起拼进 prompt 喂给模型，模型基于这些材料来回答，这样就实现了外置知识库的效果。评估 RAG 好坏主要看两块：一是检索质量，检索到的内容是不是真的相关，有没有漏掉重要内容；二是生成质量，模型的回答有没有忠实于检索到的材料，有没有自己编造。可以用 RAGAS 这样的框架来自动化评估这些指标。

### 9. Claude Code 长任务原理 【5 分】

**问题**
像 Claude Code 这样的工具，能长时间持续干活，你知道它是怎么做到的吗？

**我的答案要点**
- 不确定具体实现
- 猜测是工作流编排做了长任务循环：先分解，然后每一步做什么，编排可能很复杂
- 可能用了 LangGraph 类似的机制

**评价**
- 优点：诚实，没有乱答；猜测方向（任务分解 + 循环）有一定依据。
- 不足：对 Agent 循环（ReAct Loop）和工具调用机制的理解不够深，可以学习后补充。

**参考答案要点**
- **Agent Loop（ReAct 模式）**：Reasoning + Acting 循环——模型先思考下一步做什么（Thought），然后选择一个工具调用（Action），拿到工具返回结果（Observation），再继续思考，如此循环直到任务完成
- **工具调用（Tool Calling/Function Calling）**：模型可以调用预定义工具（读文件、写文件、执行命令、搜索代码），工具返回结果注入上下文，模型基于结果继续推理
- **上下文管理**：长任务会超过 context window，通常通过滚动上下文、压缩历史、分阶段总结来维持有效记忆
- **与普通 Cursor 补全的区别**：Claude Code 是 stateful agent loop，可跨多个文件、多个步骤自主执行；Cursor 内联补全是单次推理

**话术示例**
Claude Code 能干长任务，核心是 Agent Loop，也叫 ReAct 模式。模型每一轮先推理下一步该做什么，然后调用一个工具，比如读文件、写文件、执行命令，拿到结果之后再继续推理，循环下去直到任务完成。这和普通的代码补全不一样，补全是单次推理，而 Claude Code 是有状态的循环，可以跨文件、跨步骤自主执行。长任务超出 context window 的问题，通常通过滚动上下文或分阶段压缩历史来解决。

### 10. React Hooks 的作用与原理 【8 分】

**问题**
给我介绍一下 React Hooks，它有什么用？

**我的答案要点**
- Hooks 本质是纯逻辑拆分，区别于组件拆分（带 DOM 结构）
- 分官方 Hooks 和自定义 Hooks
- 官方 Hooks 暴露了 React 核心逻辑的切入点（生命周期、响应式数据）
- React 的响应式是通过 Fiber 架构驱动的，核心收集所有 hook，生命周期驱动更新，diff 算法执行 DOM 操作
- 自定义 Hooks 可以在内部使用官方 Hooks，实现逻辑复用
- 类似 Vue 的组合式函数

**评价**
- 优点：能讲清楚 Hooks 的本质（逻辑复用）和与 Vue composables 的类比，提到 Fiber 调度说明有一定深度认知。
- 不足：对 Fiber 和 Hooks 关系的表述略模糊（说"收集所有 hook 然后更新"不够精准）；可以举一两个常用 Hook 的具体使用场景增加实感。

**参考答案要点**
- **Hooks 出现的背景**：class 组件状态逻辑难以复用，生命周期里逻辑混杂；Hooks 让函数组件具备状态和副作用能力
- **核心 Hooks**：
  - `useState`：组件内响应式状态
  - `useEffect`：副作用（数据请求、订阅、DOM 操作），依赖数组控制触发时机
  - `useCallback` / `useMemo`：缓存函数 / 值，避免不必要渲染
  - `useRef`：持久化可变引用，不触发渲染
  - `useContext`：跨组件传值
- **自定义 Hook**：以 `use` 开头的函数，内部可调用官方 Hooks，实现逻辑复用（如 `useFetch`、`useDebounce`）
- **Fiber 与 Hooks**：每个函数组件对应一个 Fiber 节点，Hooks 的状态以链表形式存储在 Fiber 上，调用顺序固定（不能在条件语句里调 Hook）

**话术示例**
Hooks 解决的核心问题是逻辑复用。以前用 class 组件，状态和副作用逻辑分散在各个生命周期里，很难提取和复用。Hooks 让函数组件也能有状态和副作用，比如 `useState` 管状态，`useEffect` 处理副作用，`useRef` 持久化引用。更重要的是可以自定义 Hook，把一段逻辑封装成以 `use` 开头的函数，在内部调用官方 Hook，然后在任何组件里复用，类似 Vue 的组合式函数。底层上，Hooks 的状态是以链表形式挂在组件对应的 Fiber 节点上，所以调用顺序必须固定，不能在条件语句里调用 Hook。

### 11. TS 代码审查（登录接口错误处理）【7 分】

**问题**
这段 AI 生成的 TS 代码（登录接口实现）有什么问题？

**我的答案要点**
- 只处理了成功情况，没有处理失败情况
- 如果 `db.findOne()` 报错或找不到用户，没有处理
- `await` 之后如果报错没有处理
- 用户名密码不匹配的情况也没有处理
- 没有 `try/catch`，报错会直接抛出

**评价**
- 优点：准确识别了最主要的问题（缺少错误处理、缺少 try/catch）；逻辑清晰，表述有条理。
- 不足：代码细节不完整（面试中通过语音描述，未能看到完整代码），可能还有其他问题（如密码是否明文比较、缺少参数校验、缺少返回类型声明等）未提及。

**参考答案要点**
- **缺少 try/catch**：`await` 操作应包裹在 try/catch 中，避免未捕获的 Promise rejection
- **缺少用户不存在的处理**：`db.findOne()` 返回 null 时应返回 401，不应继续执行
- **缺少密码不匹配的处理**：仅比对成功情况，未处理密码错误
- **密码安全**：密码不应明文存储和比对，应使用 bcrypt 等哈希对比
- **缺少参数校验**：入参 `username` / `password` 应做非空和格式校验，避免注入
- **缺少返回类型声明**：TS 函数应有明确返回类型

**话术示例**
我看到几个问题。第一，整个函数没有 try/catch，一旦数据库操作报错，会直接抛出未捕获的异常。第二，只处理了成功路径，没有处理用户不存在的情况，`findOne` 返回 null 时应该直接返回 401。第三，密码不匹配的情况也没有处理，应该对比之后再决定是否返回成功。另外安全性上，密码应该用哈希存储，不能明文比对；入参也应该做非空校验，防止注入。
