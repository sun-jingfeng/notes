**评价**
- 优点：从业务场景出发，把数据流讲清楚了；区分了普通查询路径和智能体路径，整体感强。

**参考答案要点**

- 数据格式：色斑图为 PNG（RGB 通道编码气象值），需要在智能体中解码还原；其他要素为 JSON

- 不提前解析 PNG 的原因：PNG 体积大，HTTP 传输效率低，推迟到智能体节点再解析

**话术示例**

智能体那条链路是：后端把文件路径传进去，智能体读文件、按要素路由到对应节点处理，最后生成预警文案再返回到后端，后端转给前端展示。

### 4. 智能体输出格式错误如何处理 【7.5 分】

**问题**

**我的答案要点**
- 开发阶段有出现格式问题，功能完成后没有
- 使用 LangGraph 编排，有中继节点 + 根据气象要素分叉的路由节点
- 最后输出节点用**硬编码**方式生成结构化文案，不依赖模型提示词来控制格式
- 硬编码能 100% 保证输出格式符合预期

**评价**
- 优点：直接说出了「硬编码」这个关键设计决策，解释了为什么不让模型来控制格式，思路清晰。
- 不足：没有提到开发阶段具体遇到了什么格式问题、如何定位解决的，面试官若追问细节会略显单薄。

**参考答案要点**
- 开发阶段：模型依赖提示词控制格式，输出不稳定，容易缺字段或格式不一致
- 根本解决方案：最终输出节点硬编码结构化模板，模型只负责填充语义内容，结构由代码保证
- LangGraph 结构：中继节点 → 路由节点（按气象要素分叉）→ 各要素垂直处理节点 → 统一输出节点（硬编码）
- 收益：格式 100% 稳定，与模型版本无关

**话术示例**

后来的解决方式是：把格式控制从模型层移出来，最后的输出节点用硬编码的方式来组装结构化文案，模型只负责生成语义内容，比如预警描述这段话，组装成最终格式是代码做的，不依赖模型。这样就能 100% 保证输出格式符合预期，不受模型版本或提示词质量影响。LangGraph 的工作流编排在这里很有帮助，能把生成逻辑和格式化逻辑分开放在不同节点里。

### 5. LangChain 和 LangGraph 的区别 【7 分】

**问题**
你用了 LangGraph，LangChain 和 LangGraph 的主要区别是什么？

**我的答案要点**
- LangChain：针对单个动作节点的开发（Chain 的概念）
- LangGraph：是 LangChain 的超集，将多个 Chain 组合成图，通过路由实现工作流编排
- 简单场景（统一聊天机器人、工具绑定）用 LangChain 即可
- 复杂场景（任务差异大、需要人为分流、减少幻觉）用 LangGraph
- LangGraph 中每个节点就是一个 LangChain 节点（模型 + 工具绑定）

**评价**
- 优点：抓住了核心区别（链 vs 图），以实际项目为例解释了选型理由，有说服力。
- 不足：「LangGraph 是 LangChain 的超集」说法不够准确，LangGraph 是构建在 LangChain 之上的独立库，并非超集关系；对 LangChain 的描述稍模糊，LCEL（LangChain Expression Language）才是「链」的核心概念。

**参考答案要点**
- LangChain：提供 Chain、LCEL 等构建单一调用链的工具，适合线性流程（输入 → 模型 → 工具 → 输出）
- LangGraph：构建在 LangChain 之上的独立库，将节点（Node）和边（Edge）组织成有向图（DAG 或含环），支持复杂路由、条件分支、状态管理
- LangGraph 节点：每个节点可以是一个 LangChain Runnable / Chain，绑定工具、提示词等
- 选型原则：线性、统一的流程用 LangChain；需要分支、循环、多 Agent 协作或状态持久化时用 LangGraph

**话术示例**
LangChain 提供的是链式调用的能力，适合线性流程：比如一个请求进来，经过模型处理，调一个工具，返回结果，这种比较统一的场景用 LangChain 就够了。

LangGraph 是构建在 LangChain 之上的独立库，它把这些节点组织成一张图，支持条件分支和路由。比如我的项目里，不同气象要素的处理逻辑差异很大，我就在 LangGraph 里给每种要素单独建一个节点，绑自己的工具和系统提示词，入口有个路由节点根据要素把请求分发到对应节点。这样任务垂直，减少幻觉，也好维护。LangGraph 里每个节点本质上就是一个 LangChain 的 Runnable。

### 7. 大屏实时数据监听的处理 【7.5 分】

**问题**
大屏实时监听数据变化，数据量大的时候有做过什么处理？

**我的答案要点**
- 核心参数：时间 + 气象要素，其他数据都依赖这两个
- 存在级联关系：气象要素变 → 起始时间变 → 再触发气象展示，会多重触发
- 简单场景：同步任务 + 不改变侦听源，直接用普通 watcher 触发任务链
- 复杂场景（级联）：阶梯侦听器——气象要素 watcher 触发时，先 stop 二级（时间）watcher，获取最新时间，时间稳定后再重建二级 watcher，将多次变化合并为一次，避免下游重复触发

**评价**
- 优点：区分了同步/异步场景，阶梯侦听器的设计思路有亮点，能有效解决级联触发问题。
- 不足：「阶梯侦听器」是自创说法，可以更直白地说「手动控制 watcher 的生命周期」；也可以补充防抖（debounce）作为另一种思路。

**参考答案要点**
- 核心思路：识别数据依赖层级，避免级联触发
- 简单场景：watch 监听单一数据源，同步执行后续任务
- 级联场景：手动管理 watcher 生命周期
  - 一级 watcher（气象要素）触发 → 立即 stop 二级 watcher → 请求最新时间 → 时间到位后重建二级 watcher
  - 效果：下游只感知到一次联动变化，不会多重触发
- 补充方案：对频繁输入类场景，也可以用防抖（debounce）将短时间内的多次变化合并

**话术示例**
我们的数据核心是两个参数：时间和气象要素，几乎所有展示数据都依赖它们。问题在于这两个参数之间有级联关系，气象要素一变，可用的时间范围会变，时间一变又会触发气象数据更新，如果不处理就会多重触发。

简单场景我直接用 watch，数据一变就更新。但有级联关系的时候，我是这么做的：在气象要素的 watcher 里，先把监听时间变化的那个 watcher stop 掉，然后去取最新的时间范围。等时间数据回来、确定下来之后，再重新创建时间的 watcher。这样对下游来说，气象要素和时间的变化是同时到达的，只触发一次更新，不会出现两次重复渲染。本质上就是手动控制 watcher 的生命周期，把多次级联变化合并成一次。

### 8. iframe 父子项目通信实现 【7.5 分】

**问题**
你做的父子项目联动是怎么实现的？

**我的答案要点**
- 业务背景：系统有 5 个页面，其中 2 个是已有系统，需要复用
- 技术选型：对比了 qiankun、Module Federation 和 iframe 三个方案
- qiankun 问题：样式污染难处理，父子通信需要预注册，对原有项目有侵入性
- 最终选择：iframe（同源部署），路由不同步业务可接受，首次加载慢通过预加载解决
- 通信方式：
  1. `window.top` 访问父项目全局属性（配套 TS 类型声明包，发布为本地 npm 包）
  2. 共享 localStorage（统一登录 token、主题标志位）
  3. `postMessage`（子项目触发父项目操作，如截图）

**评价**
- 优点：有完整的技术选型对比过程，最终选择 iframe 的理由有业务依据；通信方案覆盖了静态配置、状态共享、事件触发三种场景；TS 类型包的做法有工程化思维。
- 不足：iframe 的局限性（SEO 差、浏览器历史管理复杂）没有主动提及；选 iframe 的核心优势「同源部署使安全限制最小化」可以再强调。

**参考答案要点**
- 方案对比：qiankun（侵入性强、样式污染复杂）→ Module Federation（构建耦合、需改造）→ iframe（路由不同步、首屏慢，但同源通信极简）
- 选择 iframe 的核心理由：同源部署下通信成本最低，`window.top` 和 localStorage 直接可用；路由不同步业务可接受；首屏慢通过预加载解决
- 通信方案：
  - 静态属性：父项目挂全局属性到 `window`，配套 TS 声明包（本地 npm）同步类型
  - 实时状态：localStorage 共享，watcher 监听同一 key 实现联动（主题切换、token 共享 = 统一登录）
  - 事件触发：子项目用 `window.top.postMessage`，父项目监听执行操作（如截图）

**话术示例**
当时业务背景是：系统有 5 个页面，其中 2 个是已有系统，需要直接复用，不能重新开发。我对比了 qiankun、Module Federation 和 iframe 三个方案。

qiankun 需要改造原有项目接入微前端、注册子应用，对现有代码侵入性比较强，样式隔离也比较麻烦。Module Federation 是构建层面的集成，改造成本也不低。最后选了 iframe，主要原因是我们是同源部署，同源下 iframe 的通信限制基本没有——子项目可以直接访问 `window.top` 拿到父项目的属性，localStorage 也是共用的，通信成本最低。路由不同步的问题跟产品确认过是可以接受的，首次加载慢用预加载解决了。

通信具体分三层：静态配置类（比如主题标志位的存储 key、token 的 key）直接挂在父项目的 `window` 上，我还配套写了 TS 类型声明打成本地 npm 包，子项目装一下就有类型提示；实时状态类（比如 token、主题切换）用 localStorage 同步，父子项目 watch 同一个 key；事件触发类（比如子项目里的截图按钮要触发父项目的截图功能）用 `postMessage` 来传。

### 10. React Fiber 架构解决了什么问题 【7 分】

**问题**
你觉得 React 里面的 Fiber 架构主要解决了什么样的问题？

**我的答案要点**
- 旧版渲染任务过长，超过 16.7ms，导致页面卡顿
- Fiber 核心：任务分片，每个 Fiber 节点独立渲染
- 渲染过程中计时，任务片过长时让出主线程，执行浏览器固有生命周期，再继续
- 每个 Fiber 节点记录 hooks（链表结构，数量和顺序不能变）
- 更新时遍历 hooks 数组，对比变化

**评价**
- 优点：说出了核心问题（单次渲染过长 → 卡顿），提到了任务分片、让出主线程、hooks 链表等关键点，方向正确。
- 不足：「好像是计时器」这句说明候选人对 React 调度器（Scheduler）的实现细节不确定；对「让出主线程」的具体机制（使用 **MessageChannel** 模拟宏任务，而非 setTimeout）没有说清楚；Fiber 的两个阶段（Render 阶段可中断 + Commit 阶段不可中断）未提及。

**参考答案要点**
- 旧版问题：Stack Reconciler 同步递归，无法中断，长任务阻塞主线程，帧率低于 60fps 导致卡顿
- Fiber 核心机制：
  1. **任务分片（Time Slicing）**：将渲染任务拆成 Fiber 节点单元，每次只处理一个节点
  2. **可中断恢复**：Render 阶段（Reconciliation）可中断；Commit 阶段（DOM 操作）不可中断，保证 DOM 一致性
  3. **调度器（Scheduler）**：使用 **MessageChannel** 实现宏任务切片，让出主线程给浏览器处理事件和渲染
  4. **优先级调度**：不同更新有不同优先级，高优先级（如用户输入）可打断低优先级渲染
- Fiber 节点结构：链表（child / sibling / return 指针）；hooks 以链表形式存储，顺序和数量固定，运行时不可变

**话术示例**
旧版 React 用的是 Stack Reconciler，渲染整棵树是一次同步递归，一旦组件树很大，这个过程可能超过 16.7 毫秒，浏览器就没法准时渲染下一帧，页面就会卡。

Fiber 的核心解决方案是任务分片：把渲染任务拆成一个个 Fiber 节点，每次只处理一个节点，处理完之后检查一下有没有更紧急的任务。如果有，就先暂停，让出主线程让浏览器去处理用户事件或者绘制，之后再继续。让出主线程这个动作在实现上用的是 **MessageChannel**，模拟出一个宏任务，保证浏览器能插进来执行。

整个渲染过程分两个阶段：Render 阶段负责找出哪些节点需要更新，这个阶段是可以中断的；Commit 阶段是真正操作 DOM 的，不能中断，保证 DOM 的一致性。

Hooks 的数量和顺序不能在运行时改变，就是因为 Fiber 里 hooks 是用链表存的，每次更新按顺序取，如果顺序变了就对不上了。
