### 2. 嵌套对象 BFS 遍历——按层输出键名二维数组 【8 分】

**问题**：给定一个嵌套 Map / Object，对其进行层序遍历，输出一个二维数组，每项为该层所有键名，忽略值。

**我的答案要点**：
- 用 TypeScript 实现
- 思路正确，快速完成

**评价**：
- 优点：第一时间识别出 BFS 层序遍历思路，选用 TS 书写，完成速度快，面试官无异议。
- 不足：逐字稿未保留代码，无法确认边界处理（null 值、Map 类型判断等）是否完善。

**参考答案要点**：
- BFS：维护一个队列，初始放入根对象；每轮取出当前层所有节点，收集 key，将值为对象的 value 入队作为下一层
- 判断是否继续递推：`typeof value === 'object' && value !== null`（排除 `typeof null === 'object'` 陷阱）
- 若输入为 `Map`，用 `map.keys()` / `map.values()` 代替 `Object.entries`
- 结果：每轮 key 列表作为结果二维数组的一项

```typescript
function levelKeys(root: Record<string, unknown>): string[][] {
  const result: string[][] = [];
  let queue: Record<string, unknown>[] = [root];

  while (queue.length > 0) {
    const nextQueue: Record<string, unknown>[] = [];
    const levelKeys: string[] = [];

    for (const node of queue) {
      for (const [key, val] of Object.entries(node)) {
        levelKeys.push(key);
        if (val !== null && typeof val === 'object') {
          nextQueue.push(val as Record<string, unknown>);
        }
      }
    }

    if (levelKeys.length) result.push(levelKeys);
    queue = nextQueue;
  }

  return result;
}
```

**话术示例**：
> 这道题本质是层序遍历。我用一个队列，初始放入根对象，每轮把当前层所有节点取出，收集它们的 key，然后把值是对象的 value 入队作为下一层，直到队列为空。输出的二维数组每一项就是当层的 key 集合。有一个细节要注意：判断 value 是否为对象时要排除 null，因为 typeof null 也是 'object'，不排除的话会把 null 值错误地推入队列。

### 3. 事件循环执行顺序 【7.5 分】

**问题**：给定一段包含同步代码、Promise（微任务）、setTimeout/setInterval（宏任务）的代码，写出各 console.log 的输出顺序。

**我的答案要点**：
- 识别：同步任务直接执行，Promise.then 为微任务，setTimeout 为宏任务
- 执行顺序：同步 → 微任务队列清空 → 取下一个宏任务 → 重复
- 最终答案（面试官题目代码中的序号顺序）：3 → 4 → 1 → 2 → 1 → 2 → 7 → 8（面试官确认正确）

**评价**：
- 优点：最终答案正确，能区分宏任务和微任务层级。
- 不足：有短暂思考过程，中间重新检查了一遍，说明对复杂嵌套场景（宏任务中触发新的微任务）的直觉还不够熟练。

**参考答案要点**：
- **执行顺序规则**：
  1. 同步代码（Call Stack）全部执行完
  2. 清空微任务队列（Promise.then / queueMicrotask / MutationObserver）
  3. 取出下一个宏任务（setTimeout / setInterval / I/O callback）执行
  4. 执行完后再次清空微任务队列
  5. 重复 3 → 4
- **宏任务中嵌套微任务**：宏任务执行期间产生的微任务，在该宏任务完成后、下一个宏任务开始前被清空
- **async/await**：`await` 后的代码等同于 `Promise.then` 回调，属于微任务

**话术示例**：
> 事件循环的执行顺序是：先把当前调用栈里所有同步代码跑完，然后清空微任务队列（Promise.then、queueMicrotask 等），清完之后再取一个宏任务（setTimeout、setInterval）执行，执行完再清一次微任务队列，如此循环。特别注意宏任务执行过程中如果产生了新的微任务，这些微任务会在该宏任务结束后、下一个宏任务开始前被立即处理，不会等到下一轮。

### 4. React Context vs 状态管理库——选型与更新机制差异 【7 分】

**问题**：项目中同时可以用 React Context 和 Pinia/Redux 这类状态管理库，请说说你会怎么在两者之间做选型，以及它们在数据更新机制上有什么本质差异？

**我的答案要点**：
- 选型：
  - Props 直传：父子组件间少量数据
  - Context：一个父组件需要向树状多个子组件传递数据（如大屏父组件对所有子组件透传配置）
  - 状态管理库（Pinia/Redux）：跨页面、互无关联的组件共享同一份数据（如用户信息、权限）
  - 事件总线：两个较远的平级组件单向通信
- 更新机制差异（在追问后给出）：
  - Context：广播机制，Context 中只要有任何值变化，所有消费该 Context 的组件都会重新渲染，即使该组件只依赖其中一个字段
  - 状态管理库：精准更新，只有使用了发生变化的那部分状态的组件才会重渲染

**评价**：
- 优点：选型场景覆盖全面，条理清晰，最终给出了正确的更新机制差异。
- 不足：起初一时没反应过来 Context 的名字（"康泰斯"）；更新机制差异未主动提及，需面试官追问才给出，说明对这个知识点的掌握停留在「会用」层面，对底层机制的表达还不够主动。

**参考答案要点**：
- **Context 的广播机制（重要）**：Context 对象被更新时，React 会向下遍历所有消费该 Context 的组件并触发重渲染，不论组件实际依赖哪个字段；这是 Context 使用需谨慎、不适合高频更新场景的根本原因
- **解决 Context 过度渲染**：拆分 Context、配合 `useMemo` / `React.memo`、或直接改用状态管理库
- **Redux/Zustand/Pinia 的精准更新**：通过 selector 订阅特定 slice，只有该 slice 变化才触发重渲染
- **选型口诀**：局部树状传递 → Context；全局/跨树共享 → 状态管理库；高频更新字段 → 避免放入 Context

**话术示例**：
> 我的选型思路是看数据的共享范围和更新频率。如果只是父到子的少量传参，直接 props；如果是一个父组件下面所有子组件都要用同一份配置，用 Context 透传很合适。但如果是用户信息、权限这种整个应用任何页面都可能用到的、或者两个毫不相关的组件要共享的数据，就放到 Redux 或 Zustand 这样的状态管理库里。
>
> 两者在更新机制上有本质区别。Context 是广播机制——Context 的 value 一旦变化，所有消费这个 Context 的组件都会重渲染，哪怕你只依赖了里面的一个字段，其他字段变了你也跑不掉。所以在一些代码规范工具里会提示谨慎使用 Context，就是这个原因。而状态管理库是精准订阅，你用 selector 订阅了哪个 slice，只有那个 slice 变化你才重渲染，不会有这种副作用。

### 5. 虚拟列表——无限滚动下的性能优化方案 【8 分】

**问题**：手机端上滑加载，用户已浏览了 1 万条商品，服务端已做好分页（每次 20 条），如何保证滚动不掉帧、性能保持良好？请列举可行的优化方案。

**我的答案要点**：
- 核心思路：只渲染可视区域内的节点（虚拟化）
  - 判断 DOM 节点距视口顶部的距离；超出阈值则隐藏节点、只保留数据
  - 上滑/下滑时用滑动窗口动态生成/隐藏节点，确保用户能流畅看到内容
- 图片懒加载：使用 `IntersectionObserver`，进入视口再加载图片；写成自定义指令
- CSS 动画用 transform 替代 top/left，走合成层，减少重排重绘
- 骨架屏：占位保持尺寸不变，减少布局抖动带来的渲染开销
- 在面试官追问频繁创建/销毁 DOM 导致白屏问题后，提出：复用 DOM 节点，只更新数据而非销毁再重建（类似 React Reconciler 的 key 复用策略）；通过改变 CSS visibility 而非实际删除节点

**评价**：
- 优点：核心虚拟化思路准确；懒加载、transform、骨架屏等辅助手段覆盖全面；DOM 复用的思路在面试官引导后迅速给出正确方向。
- 不足：DOM 复用（虚拟列表的本质）应主动提出，不应等待追问；对虚拟列表「定高/不定高」两种情形未区分；第三方库（如 `react-virtualized`、`vue-virtual-scroller`）可顺带提及展示知识广度。

**参考答案要点**：
- **虚拟列表核心**：只渲染可视区域（+ 上下各一屏的缓冲）的 DOM；用绝对定位或 `transform: translateY` 撑开容器总高度，给用户完整滚动感
- **DOM 复用**：渲染固定数量的 DOM 节点（如 20~40 个），滚动时只更新节点内的数据，而非删除旧节点再创建新节点，大幅降低 GC 压力和布局计算量
- **定高场景**：`itemHeight × totalCount` 算总高，`scrollTop / itemHeight` 算起始索引，实现简单
- **不定高场景**：预估高度 + 渲染后更新实际高度缓存，或使用 `ResizeObserver` 动态修正
- **图片懒加载**：`IntersectionObserver` + 自定义指令，进入视口再替换 `src`
- **动画性能**：位移用 `transform`、透明度用 `opacity`，不触发重排，走合成线程
- **第三方方案**：`react-window`、`react-virtualized`、`vue-virtual-scroller`

**话术示例**：
> 核心方案是虚拟列表——不管列表有多少条，DOM 里只保留可视区域加上上下各一屏缓冲区内的节点，数量固定，比如 40 个。滚动时我不删除旧节点再创建新节点，而是复用这 40 个 DOM，只把它们的数据换掉，同时用 `transform: translateY` 把节点移到对应位置。这样 GC 压力很小，也不会因为频繁创建销毁 DOM 导致白屏。
>
> 辅助优化方面：图片用 `IntersectionObserver` 做懒加载，进入视口才加载；滚动动画改用 `transform` 而不是 `top`，走合成层不触发重排；列表 item 提前设好尺寸，配合骨架屏，防止高度跳变引起额外的布局计算。如果不想自己实现，社区有 `react-window`、`vue-virtual-scroller` 这些成熟的虚拟列表库可以直接用。

### 6. Redis 缓存知识与崩溃恢复方案 【6.5 分】

**问题**：你了解哪些 Redis 缓存问题（穿透/击穿/雪崩）？Redis 崩溃后如何快速恢复、保证数据不丢？

**我的答案要点**：
- 提到了缓存穿透、击穿、雪崩，并说项目中有对应代码处理
- 数据库用 MySQL + MyBatis Plus
- Redis 单体部署；了解集群部署：
  - 哨兵模式（Sentinel）：主节点（Master）负责写，从节点（Slave）分担读压力；主节点宕机后哨兵自动选出新主节点
  - 这种机制可在崩溃后自动恢复服务

**评价**：
- 优点：哨兵模式的描述基本正确，覆盖了主从结构和自动故障转移。
- 不足：
  1. 缓存穿透/击穿/雪崩只是一笔带过，未展开解决方案（布隆过滤器、互斥锁/分布式锁、随机 TTL 等）
  2. 崩溃恢复仅说了哨兵切主，未提 RDB（快照）和 AOF（追加日志）两种持久化机制——这才是"数据不丢"的关键；哨兵只解决高可用，数据恢复靠持久化

**参考答案要点**：
- **缓存穿透**：查询数据库和缓存都不存在的 key，大量恶意请求直打 DB → 解决：布隆过滤器拦截非法 key；或缓存空结果（TTL 短）
- **缓存击穿**：热点 key 过期，大量并发同时去 DB 查 → 解决：互斥锁（分布式锁）只让一个请求重建缓存；或设置热点 key 永不过期 + 逻辑过期
- **缓存雪崩**：大批 key 同时过期 → 解决：TTL 加随机抖动；Redis 集群多节点；降级熔断
- **持久化（数据不丢的核心）**：
  - RDB：定期全量快照，恢复快但可能丢失最后一次快照后的数据
  - AOF：每条写命令追加日志，丢失数据少（可配置为每秒 fsync），但文件大、恢复慢
  - 生产推荐：RDB + AOF 混合持久化
- **高可用（服务不停）**：
  - 哨兵模式：1 主 N 从 + 哨兵集群，主宕后自动选主
  - Cluster 模式：数据分片 + 多主多从，横向扩展 + 高可用

**话术示例**：
> 三个经典问题的解决思路分别是：穿透用布隆过滤器过滤非法 key，或把不存在的 key 也缓存一个短 TTL 的空结果；击穿用分布式锁，只让第一个请求去 DB 重建缓存，其他等待；雪崩在 TTL 上加随机抖动，避免大批 key 同时到期，再结合多节点部署做冗余。
>
> 崩溃恢复要分两个层面。服务高可用靠哨兵或 Cluster——主节点宕机后哨兵自动选出新主，应用切换到新主继续服务，这解决的是"服务不停"的问题。数据不丢靠持久化——RDB 定期做快照、AOF 记录每条写命令，生产环境一般两者都开，RDB + AOF 混合模式，崩溃后先加载 RDB 快速恢复基础数据，再用 AOF 补齐增量，把丢失窗口压到很小。

### 7. 数据库慢查询优化与索引原理 【8 分】

**问题**：线上服务慢，排查发现是数据库查询慢，如何优化？为什么 MySQL 用 B+ 树索引而不用红黑树？

**我的答案要点**：
- 通过压测（JMeter）定位瓶颈是 CPU 密集型还是 I/O 密集型，还是数据库
- 开启慢查询日志，找到慢 SQL，分析字段规律，针对性建索引
- 建索引遵循最左前缀原则，避免前模糊匹配（`LIKE '%xxx'`）和前不等式（`<>`）
- 利用覆盖索引消除回表（把查询所需字段全部覆盖到索引中）
- 也可用游标分页代替 `LIMIT offset` 的深度翻页
- B+ 树 vs 红黑树：B+ 树是多叉树，树更矮，磁盘 I/O 次数少

**评价**：
- 优点：思路完整——从定位到建索引到消除回表，链路清晰；B+ 树的核心优势（多叉矮树、减少磁盘 I/O）表述准确。
- 不足：未提及 `EXPLAIN` 分析执行计划；索引失效场景（隐式类型转换、函数操作字段等）可以补充；B+ 树叶节点链表结构（利于范围查询）未提及。

**参考答案要点**：
- **定位**：`EXPLAIN` 查看执行计划（key、type、rows、Extra 字段），type 为 `ALL` 说明全表扫描
- **慢查询日志**：`slow_query_log`，找出超过阈值的 SQL
- **索引优化**：
  - 最左前缀原则：联合索引从左到右匹配，中间断掉后续失效
  - 覆盖索引：查询字段全在索引中，无需回表
  - 避免索引失效：`LIKE '%xxx'` 前缀通配、函数操作（`YEAR(create_time)`）、隐式类型转换
  - 游标分页：`WHERE id > lastId LIMIT n`，替代 `LIMIT offset` 避免深度翻页性能退化
- **B+ 树优势**：
  - 多叉树（阶数由磁盘页大小决定，通常几百），同等数据量下树高远低于二叉树（红黑树），磁盘 I/O 次数少
  - 非叶节点只存 key 不存 data，一个磁盘页能放更多 key，进一步降低树高
  - 叶节点通过链表相连，范围查询直接遍历叶节点链表，效率高

**话术示例**：
> 排查慢查询我的思路是：先用 `EXPLAIN` 看执行计划，如果 type 是 ALL 说明全表扫描，必须加索引。配合慢查询日志找到具体慢 SQL，分析查询条件，建一个覆盖查询字段的联合索引；建索引时要注意最左前缀原则，别在字段上加函数、别用前置通配符，否则索引失效。如果有回表，可以把 SELECT 的字段也加进索引做成覆盖索引。深度翻页的话，用游标分页 `WHERE id > lastId LIMIT n` 替代 `LIMIT offset`。
>
> B+ 树比红黑树更适合做数据库索引，核心原因是磁盘 I/O。数据库数据存在磁盘上，每次查找都要读磁盘页，I/O 次数越少越好。红黑树是二叉树，数据量大的时候树很高，I/O 次数多。B+ 树是多叉树，一个节点可以放几百个 key，同样的数据量树高只有三四层，查一条数据只需三四次 I/O。另外 B+ 树的叶节点是一个链表，范围查询只需遍历链表，不用回溯，非常高效。

### 8. 超大表优化——亿级用户表的查询性能 【6.5 分】

**问题**：核心用户表数据量达亿级，缓存失效时必须走数据库查询，且更新频繁、缓存 TTL 极短，数据库压力极大，如何优化？

**我的答案要点**：
- 想到了分库分表的概念：把大表拆成多张表分散存储
- 提到分表比分库更常用（不是所有表都需要拆）
- 提到有现成的工具库可以帮助路由查询到对应的分表（如通过用户 ID 快速定位到哪张表）

**评价**：
- 优点：方向正确，点出了分表场景和工具的存在。
- 不足：缺少分片策略的具体描述（Range 分片、Hash 分片、取模分片等），以及分表后分布式主键（雪花算法、UUID）和跨表聚合查询的处理方式；未提及 ShardingSphere、MyCat 等具体中间件名称。

**参考答案要点**：
- **分表策略**：
  - 水平分表（Sharding）：将同一张表按规则（如 `user_id % N`）拆分成多张结构相同的子表，减少单表数据量
  - 垂直分表：将大宽表的冷热字段拆到不同表，减少单行数据量，提高热数据 cache 命中率
- **分片键选择**：用户表通常用 `user_id` 做分片键；避免热点（范围分片可能导致热点，Hash 分片更均匀）
- **分布式主键**：分表后不能用自增 ID，需雪花算法（Snowflake）或 UUID 保证全局唯一
- **跨表查询**：尽量避免跨分片 JOIN；复杂聚合查询走 OLAP 数仓（如 ClickHouse）
- **中间件**：ShardingSphere（Apache）、MyCat；屏蔽底层路由逻辑，对应用透明
- **冷热数据分离**：历史数据归档到冷表或对象存储，热表只保留近期数据

**话术示例**：
> 亿级用户表的核心方案是水平分表——把用户数据按 `user_id % N` 拆成 N 张结构相同的子表，单表数据量降下来，查询和索引性能都会好很多。分片键一般选 user_id，Hash 取模分布比较均匀，避免热点。分表后自增 ID 不能用了，要换成雪花算法或 UUID 生成全局唯一主键。
>
> 中间件方面可以用 ShardingSphere，它在应用层和数据库之间做了一层路由，应用端写普通 SQL，ShardingSphere 自动路由到对应分表，对代码基本透明。跨分表的复杂聚合查询要尽量避免，如果有统计分析需求，建议走单独的数仓或 OLAP 引擎，别在分表上做聚合。另外冷数据可以定期归档，让热表只保留高频访问的近期数据，进一步降低单表体量。

### 9. Spring 嵌套事务失效——为什么操作一成功但整体未回滚 【7.5 分】

**问题**：在 Spring 事务中，操作一和操作二是嵌套事务。操作一成功、操作二失败，预期整体回滚，但实际发现没有回滚，可能是什么原因？

**我的答案要点**：
- 事务传播行为（Propagation）的设置会决定内外事务是否共用同一个事务边界
- 如果内层事务把异常 catch 住消化掉了，外层事务感知不到异常，但两者共用的回滚标志位（rollback-only）已被标记为失败，最终外层事务还是会回滚，导致意外行为
- 面试官确认：这是"大面积失效"的典型原因

**评价**：
- 优点：准确命中了"异常被内层 catch 吞掉 + 共享 rollback-only 标志"这一最典型的失效场景，面试官直接确认。
- 不足：未补充其他常见失效原因（自调用 self-invocation 绕过 AOP 代理、`REQUIRES_NEW` 导致独立事务互不影响、非受检异常 vs 受检异常的默认回滚规则等）。

**参考答案要点**：
- **原因一（最典型）：内层 catch 吞异常**：内外共用同一物理事务时，内层方法抛出异常会把事务标记为 rollback-only；若内层 catch 了异常未继续抛出，外层无感知但标志位已置为失败，Spring 提交时检测到 rollback-only 会强制回滚，抛出 `UnexpectedRollbackException`
- **原因二：传播行为配置**：内层用 `REQUIRES_NEW`，开启独立事务，外层事务挂起；内层回滚只影响自身，外层事务不感知，数据不一致
- **原因三：自调用（Self-invocation）**：同一个 Bean 内部直接调用 `@Transactional` 方法，绕过 Spring AOP 代理，事务注解失效
- **原因四：异常类型**：Spring 默认只对 `RuntimeException`（非受检异常）触发回滚，受检异常（`Exception`）不回滚；需通过 `@Transactional(rollbackFor = Exception.class)` 显式配置
- **原因五：数据库引擎**：MyISAM 不支持事务，需确认表引擎为 InnoDB

**话术示例**：
> 最常见的原因是内层事务吞掉了异常。如果内外共用同一个物理事务，内层方法抛出异常的瞬间 Spring 就把这个事务标记成了 rollback-only；但如果内层用 try-catch 把异常消化了，没有继续往外抛，外层方法感知不到有异常，会正常往下走，等到最后提交时 Spring 发现事务是 rollback-only 就会强制回滚，同时抛出一个 UnexpectedRollbackException。这就是为什么代码看起来没报错，但数据还是没提交的原因。
>
> 另一个常踩的坑是同类自调用——在同一个 Bean 里，A 方法直接调用加了 @Transactional 的 B 方法，这个调用不经过 Spring AOP 代理，事务注解直接失效。还有就是受检异常默认不触发回滚，要加 `rollbackFor = Exception.class` 才保险。

### 10. AI 辅助开发的实践经验 【9 分】

**问题**：你们团队如何借助 AI 工具进行提效？你有哪些实操经验或好的案例？

**我的答案要点**：
- 背景：公司合并部门后担任业务线组长，推动 AI 提效和智能体落地
- 内网项目不能联网，团队在本地部署开源模型
- 工具：前端用 Cursor，后端用 IDE AI 插件（Copilot 系）
- 围绕 AI 的两个核心缺陷积累经验：
  1. 代码质量不稳定 → 用 Cursor Rules / System Prompt 做提示词持久化，提高输出符合预期的概率
  2. 上下文窗口有限 → 人工把控核心架构，AI 只处理样板代码；自己先拆组件、定服务边界，再让 AI 填充实现
- 出现 MCP 后接入 Figma 等工具，提升与设计稿对齐的效率
- 核心逻辑与架构由人主导，样板代码（UI 还原、CRUD、接口层）交给 AI
- AI 生成代码必须过审，核心模块自己写
- 效果：约 75% 的样板代码由 AI 生成，工作效率提升约 3 倍

**评价**：
- 优点：回答结构完整，有具体实操细节（本地部署、Cursor Rules、MCP 接入），能区分 AI 擅长的领域和人需要主导的领域，体现了成熟的 AI 协作认知；面试官高度认同。
- 不足：可补充一个具体数字化案例（如某次用 AI 实现了什么功能，节省了多少时间），说服力更强。

**参考答案要点**：
- **工具选型**：Cursor（前端）、Copilot / IDE 插件（后端）；内网项目用本地模型（Ollama + 开源模型）
- **提示词工程**：Cursor Rules / `.cursorrules` 做全局提示词持久化；任务级 system prompt 减少重复沟通
- **MCP（Model Context Protocol）**：让 AI 直接读取 Figma 设计、代码库上下文，无需截图沟通
- **分工策略（核心）**：
  - AI 负责：UI 还原、CRUD 样板、接口层、第三方库接入（ECharts、地图等）
  - 人负责：架构设计、服务边界划分、组件拆分、核心算法、代码审查
- **质量管控**：AI 生成代码必须 review，核心模块不交给 AI；识别 AI 的幻觉和不合理实现
- **量化效果**：75% 样板代码由 AI 生成，效率提升约 3 倍

**话术示例**：
> 我们团队 AI 提效主要分两个方向。工具上前端用 Cursor，后端用 IDE 的 AI 插件；因为很多是内网项目不能联网，我们也在本地用 Ollama 部署了开源模型。
>
> 实操层面我重点解决了 AI 的两个核心缺陷：一是生成代码质量不稳定，我用 Cursor Rules 做提示词持久化，把项目规范、技术栈偏好、组件拆分原则固化成全局提示词，让每次生成都更符合预期；二是上下文窗口有限，解决方式是我不做甩手掌柜——架构设计、服务边界、组件拆分这些核心决策我自己来，把结构定好之后，让 AI 去填 UI 还原、接口层这些样板代码，生成完我再过一遍。MCP 出来之后接了 Figma，再也不用截图发给 AI 了，效率又上了一个台阶。现在大概有 75% 的代码是 AI 生成的，整体效率比原来提升了三倍左右。
