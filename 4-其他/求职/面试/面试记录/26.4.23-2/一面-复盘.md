### 6. JWT 认证与接口权限 【6 分】

**问题**
你这里面用到了 Spring 的 JWT 认证和接口权限，这一块是怎么做的？

**我的答案要点**

- 前端：动态路由注册，根据权限标志位控制路由
- 后端：接口进来前根据用户 ID 查权限，看该接口是否有权限
- 每个接口配权限标志位，有第三方框架支持（忘了名字）
- JWT 存储用户 ID 和过期时间

**评价**

- 优点：前后端两层校验的思路是对的，结合了路由权限和接口权限。
- 不足：忘记了框架名（Spring Security + Sa-Token 是常用选项，前者更主流），说"忘了叫啥"在面试中失分明显；JWT 存储内容描述不够准确（标准说法是 payload 中存 userId、roles、exp 等）；接口权限注解（如 `@PreAuthorize`）没有提到。

**参考答案要点**

- 前端：路由权限通过动态路由实现——登录后请求接口获取用户权限列表，根据权限动态注册路由，未授权路由不挂载。
- 后端：使用 Spring Security 或 Sa-Token，登录成功后签发 JWT，客户端每次请求带上 Token；Filter/拦截器解析 Token，提取 userId 和 roles；接口用 `@PreAuthorize` 或自定义注解标注所需权限；框架自动比对 Token 中的 roles 与接口所需权限。
- JWT Payload：一般存 userId、username、roles、exp（过期时间）。

**话术示例**

> 权限这块分两层。前端是动态路由——登录后从接口拿到用户的权限列表，根据权限动态注册路由，没有权限的路由就不挂载，前端页面直接不可访问。  
> 后端用的是 Spring Security，登录成功后签发 JWT，Token 里存了 userId、roles 和过期时间。每次请求进来，先经过过滤器解析 Token，验证有效期和签名，然后把用户信息注入 SecurityContext；接口上用 `@PreAuthorize` 注解声明所需权限，框架自动比对。这样前后端两层都做了校验，缺一不可。

### 7. JWT 的优势 【7.5 分】

**问题**
JWT 的优势在哪？

**我的答案要点**

- 自完备性：拿到 Token 后不需要查数据库，Token 本身携带用户信息（ID、过期时间）
- 对比 Session：Session 需要服务端维护 Session 存储，JWT 是无状态的

**评价**

- 优点：核心优势"无状态 / 自完备"答出来了，对比 Session 的区别也点到了。
- 不足：没有提到分布式场景下 JWT 的优势（Session 需要共享存储，JWT 无需）；也没有提到 JWT 的劣势（无法主动失效，Token 泄露风险）；面试官可能想听更全面的对比。

**参考答案要点**

- 无状态：服务端不存储 Session，天然支持水平扩展，适合分布式/微服务场景。
- 自完备：Token payload 中携带用户信息，验证时无需查库，减少 I/O。
- 跨域友好：Token 放在 Authorization header，比 Cookie 更灵活。
- 劣势（主动提出更好）：Token 签发后无法主动撤销（除非引入黑名单机制）；payload 可以 Base64 解码，不应存敏感信息。

**话术示例**

> JWT 最大的优势是无状态。传统 Session 需要服务端存储 Session 数据，集群场景还要做 Session 共享；JWT 的验证逻辑完全在服务端，只需要验证签名和有效期，不用查库，天然支持水平扩展，特别适合微服务架构。  
> 另外 JWT 的 payload 里可以携带用户基本信息，比如 userId 和 roles，鉴权时直接从 Token 里取，省掉一次数据库查询。当然它也有缺点——Token 一旦签发就不能主动失效，如果要做强制下线，需要额外引入黑名单机制。

### 8. 微前端/iframe 间的安全通信 【5 分】

**问题**
父子 iframe 项目之间的安全保障是怎么做的？单点登录是怎么实现的？

**我的答案要点**

- 认为跨域和 JWT 是独立的问题，iframe 同源部署没有跨域问题
- 统一登录：同源部署共享 localStorage，父项目在 window 上挂全局属性存 token，子项目通过 `window.top.globalData.token` 取值；若独立部署则自己登录
- 单点登录（SSO）：某省有自己的登录系统，用户在第三方系统登录成功后跳转回我方系统并携带认证参数，前端提取参数传给后端验证，验证通过后签发 token

**评价**

- 优点：统一登录和单点登录的区分很好，说明了两个不同场景；SSO 流程描述准确。
- 不足：面试官问 JWT 在跨 iframe 间如何安全传输，候选人理解为"跨域问题"，绕过了问题本质；跨域时 token 安全传输（如 postMessage + 来源验证）没有回答；答非所问导致扣分。

**参考答案要点**

- 同源场景：共享 localStorage/sessionStorage，父子直接读取，无安全风险。
- 跨源场景：不能直接访问对方 storage；可以通过 `postMessage` 传递 token，接收方需严格校验 `event.origin` 白名单，防止 XSS 劫持。
- 统一登录实现：父项目登录后将 token 写入 `window` 全局对象，子项目通过 `window.top` 读取；同源环境下安全可行。
- SSO 实现：第三方系统登录成功后携带签名参数跳转回本系统，后端验证参数合法性（可以是 HMAC 签名或 OAuth2 code），验证通过签发本系统 JWT。

**话术示例**

> 我们项目是同源部署，所以父子 iframe 之间直接共享 localStorage，父项目把 token 写到 `window.globalData` 上，子项目通过 `window.top.globalData` 取值，没有跨域限制。  
> 如果是跨源场景，就不能直接访问对方的 storage，通常的做法是用 `postMessage` 传 token，接收方要严格校验 `event.origin`，只接受白名单内的来源，防止被恶意页面劫持。  
> SSO 我们有一个省的项目接入了第三方登录系统，流程是：用户在第三方系统登录后，携带认证参数跳转回我方页面，前端把参数传给后端，后端验证签名合法性，通过后签发本系统的 JWT，后续流程就和普通登录一样了。

### 9. RabbitMQ 在项目中的作用 【7 分】

**问题**
你在项目里 RabbitMQ 承担什么功能？

**我的答案要点**

- 消息队列，设计初衷是逻辑解耦、削峰填谷
- 项目并发不高，但用了两个场景：预警消息发送 + 缓存任务触发
- 预警消息：系统通过给定接口推送给客户
- 缓存任务：数据预计算完成后异步写入 Redis，不要求实时，只要在请求前完成即可

**评价**

- 优点：场景描述具体，两个用途都说清楚了；"不要求实时，只要请求前完成"的解释体现了对消息队列异步特性的理解。
- 不足：没有说明为什么缓存任务用 MQ 而不直接同步写 Redis（面试官后续追问了）；削峰填谷的概念提了但场景不匹配，实际项目并发不高，用这个理由有些牵强。

**参考答案要点**

- 预警消息发送：业务触发点（系统生成预警）和实际执行点（调用第三方接口发送）通过 MQ 解耦，发送失败可重试，不影响主流程。
- 缓存预热：数据预计算是耗时任务，计算完成后通过 MQ 异步通知缓存写入服务，实现计算与缓存写入的解耦；相比直接调用，MQ 提供了重试、积压可见、服务解耦等好处。
- 为什么不直接调用：直接调用是同步强依赖，任何一方异常都会影响主流程；MQ 做到发布者与消费者无直接依赖。

**话术示例**

> 项目里 MQ 主要用在两个场景。第一个是预警消息发送——系统生成预警后，把消息发到 MQ，由独立的消费者负责调第三方接口推送，发送失败可以重试，不影响主业务流程，做到了逻辑解耦。  
> 第二个是缓存预热——有些数据需要预计算，计算完成后要写入 Redis。我们没有直接同步调用，而是通过 MQ 异步通知缓存写入服务。这样做的好处是，计算服务和缓存写入服务互相解耦，即使缓存服务短暂不可用，消息也不会丢失，等服务恢复后自动消费。

### 10. 为什么不直接用 Redis 而用 RabbitMQ 触发缓存 【5 分】

**问题**
为什么不直接用 Redis，而要用 MQ 来触发缓存写入？

**我的答案要点**

- 缓存流程的最后一步是先拿到数据、计算完再存入 Redis
- MQ 对标的是"直接接口调用"，是任务触发的连接方式，通过注册消息源、路由、绑定消费者来连接链路

**评价**

- 优点：方向大致正确，意识到了 MQ 是做解耦用的。
- 不足：回答逻辑混乱，没有清晰说明"Redis 直接写"和"MQ 触发写"两种方案的区别；面试官核心想听的是解耦和异步的价值，以及 MQ 相比同步调用的优势，候选人没有组织好语言。

**参考答案要点**

- 直接写 Redis 方案：计算完成后在同一个方法里同步调用 Redis 写入，强耦合，计算服务和缓存服务绑在一起。
- MQ 方案优势：计算完成后只发一条消息，不关心谁来消费；缓存写入服务独立消费，两者解耦；Redis 出问题不影响计算服务；消息可持久化，不丢失。
- 本质区别：MQ 解决的是"谁来触发谁"的耦合问题，Redis 解决的是"数据存哪"，两者职责不同。

**话术示例**

> "直接写 Redis"是同步调用，计算完成后在同一个流程里立刻写入，计算服务和缓存写入强耦合在一起。如果 Redis 短暂不可用，计算流程就会失败。  
> 用 MQ 的话，计算完成后只发一条消息出去，不关心后续谁来处理；缓存写入服务作为独立消费者，按自己的节奏消费消息写入 Redis。Redis 出问题也不影响计算主流程，消息积压在队列里，等服务恢复后再消费。职责分离，也更健壮。

### 11. RabbitMQ 核心组件 【7 分】

**问题**
说一下 RabbitMQ 里面核心的几个组件是什么？

**我的答案要点**

- 生产者、交换机（Exchange）、消费者
- 生产者：触发发送消息的一方
- 交换机：联动枢纽
- 消费者：执行具体业务逻辑的一方
- 声明时三者一起在消费者侧声明

**评价**

- 优点：三个核心角色都说对了，业务场景举例清楚。
- 不足：漏掉了**队列（Queue）**这个核心组件——MQ 中 Exchange 将消息路由到 Queue，消费者订阅 Queue，不是直接订阅 Exchange；Exchange 类型（direct、topic、fanout、headers）没有提到。

**参考答案要点**

- 生产者（Producer）：发送消息的一方。
- 交换机（Exchange）：接收生产者消息，按路由规则转发到对应 Queue；类型有 direct（精确匹配）、topic（通配符）、fanout（广播）。
- 队列（Queue）：消息暂存的地方，消费者从 Queue 中取消息。
- 消费者（Consumer）：订阅 Queue，处理消息的一方。
- 绑定（Binding）：Exchange 和 Queue 之间的路由规则配置。
- 消息流：Producer → Exchange → (Binding/RoutingKey) → Queue → Consumer。

**话术示例**

> RabbitMQ 有四个核心组件。生产者负责发消息；交换机负责接收消息并按路由规则转发，Exchange 有几种类型，direct 是精确匹配 routing key，topic 支持通配符，fanout 是广播；队列是消息实际存放的地方，消费者订阅队列来消费消息；Binding 是 Exchange 和 Queue 之间的路由配置，把它们绑定起来。消息的流转路径就是：Producer → Exchange → Queue → Consumer。

### 12. 能否绕过 Exchange 直接写队列 【7 分】

**问题**
能不能不要交换机，直接把消息写到队列里？为什么要引入交换机这个组件？

**我的答案要点**

- 可以，简单场景下直接绑定一个队列就行
- 交换机的价值是可扩展性——一个消费者、不需要路由时可以不用交换机

**评价**

- 优点：方向对，知道 RabbitMQ 有默认交换机可以实现"直连队列"；解释了交换机的作用是扩展性。
- 不足：技术细节不够准确——RabbitMQ 中"直接发到队列"实际上是使用了**默认交换机（Default Exchange）**，路由键等于队列名，并不是真正绕过了 Exchange；可以说得更精确。

**参考答案要点**

- 可以"看起来"直接发到队列：使用 RabbitMQ 的**默认交换机（Default Exchange）**，routing key 设为队列名，消息会直接路由到对应队列；生产者代码里不需要显式声明 Exchange。
- 引入交换机的价值：① 一条消息路由到多个队列（fanout / topic）；② 按不同 routing key 分发到不同消费者；③ 生产者和队列解耦，不需要知道队列名，只需知道 Exchange 和 routing key。
- 结论：简单一对一场景可以用默认交换机；一对多或动态路由场景必须用 Exchange。

**话术示例**

> 技术上可以"直接发到队列"，但其实 RabbitMQ 底层还是走了一个**默认交换机**，只是不需要显式声明，routing key 设成队列名，消息就直接路由过去了。  
> 引入交换机的价值主要是两点：第一是一对多路由——一条消息可以通过 fanout 广播到多个队列，或者用 topic 按通配符分发给不同消费者；第二是解耦——生产者只需要知道往哪个 Exchange 发、用什么 routing key，不需要关心后面有几个队列，队列可以随时增减，不影响生产者代码。

### 14. Linux CPU 负载高的排查 【4 分】

**问题**
程序部署上线后，Linux 系统 CPU 负载比较高，你会怎么排查？用哪些命令？

**我的答案要点**

- CPU 满了一般是出了问题
- 先看应用报错，再看服务器资源状态
- Linux 有指令能查看 CPU 状态，但具体指令记不住

**评价**

- 优点：排查思路（先看应用，再看系统资源）方向大致对。
- 不足：没有说出任何具体命令，`top`、`htop`、`ps aux`、`jstack`、`jstat` 一个没提，这是基础运维知识，面试官明确问了"用哪些命令"，等于没答；失分严重。

**参考答案要点**

- 系统层排查：`top` / `htop` 查看整体 CPU 使用率，定位是哪个进程占用高；`ps aux --sort=-%cpu | head` 按 CPU 降序列出进程。
- Java 应用排查：`top -H -p <pid>` 查看进程内哪个线程 CPU 高；获取线程 ID（十进制转十六进制）；`jstack <pid>` 打印线程堆栈，找到对应线程的调用链，定位死循环或频繁 GC 问题。
- 频繁 GC 导致 CPU 高：`jstat -gcutil <pid> 1000` 监控 GC 情况，看是否频繁 Full GC；结合 `jmap -heap <pid>` 查堆内存分布。
- 常见原因：死循环、频繁 Full GC、大量线程上下文切换、正则回溯。

**话术示例**

> CPU 负载高，我的排查路径是这样的。  
> 第一步用 `top` 看整体情况，找出是哪个进程 CPU 占用高。如果是 Java 进程，用 `top -H -p <pid>` 再下钻到线程级别，找出具体是哪个线程在耗 CPU。  
> 第二步把高 CPU 线程的 ID 转成十六进制，然后用 `jstack <pid>` 打印线程堆栈，在堆栈里找到这个线程的调用链，看是不是死循环或者某段代码频繁执行。  
> 如果是频繁 GC 导致 CPU 高，用 `jstat -gcutil <pid> 1000` 观察 GC 频率，结合堆内存情况判断是不是内存泄漏或者堆设置太小。

### 15. 开发中遇到最大的故障 【7 分】

**评价**

- 优点：故障描述真实，排查思路有层次（先看服务器，再看应用，最后定位代码）；提到了 JVM 崩溃快照和 GC 监控，有实际经验。

**话术示例**

### 16. 前后端各三个核心监控指标 【3 分】

**问题**
系统部署到客户那边，前端和后端各提三个核心监控指标，你会提哪三个？

**我的答案要点**

- 理解偏差，认为是"上线前的性能达标指标"（如任务片长度、每秒请求压力）
- 没有给出生产环境的实时监控指标

**评价**

- 优点：无。
- 不足：完全答偏，混淆了"上线前性能测试基准"和"生产环境运行时监控指标"；面试官两次确认，候选人仍未纠正方向；这是一道加分题，等于白送了。

**参考答案要点**

**后端三个核心监控指标：**

1. **接口响应时间（P95/P99）**：95% / 99% 的请求响应耗时，超过阈值（如 P99 > 2s）触发告警。
2. **错误率（Error Rate）**：5xx 错误占总请求的比例，超过 1% 触发告警，用于快速发现服务异常。
3. **JVM 堆内存使用率 / GC 频率**：防止内存泄漏导致 OOM，持续上涨或频繁 Full GC 要告警。

**前端三个核心监控指标：**

1. **JS 错误率（Error Rate）**：前端 JS 运行时报错数量，通过 Sentry 等工具收集，异常飙升说明有 Bug 上线。
2. **页面首屏加载时间（FCP / LCP）**：用户实际体验到的加载速度，超过阈值（如 LCP > 2.5s）表示性能劣化。
3. **接口请求成功率**：前端发出的 API 请求中，4xx / 5xx 的比例，用于感知后端异常对用户的影响。

**话术示例**

> 后端我会关注三个：第一是接口响应时间，主要看 P95 和 P99，这代表大多数用户的实际体验，超过阈值触发告警；第二是服务错误率，5xx 错误占比超过 1% 就需要立即介入；第三是 JVM 堆内存使用率，防止内存泄漏导致 OOM，堆使用率持续上涨或频繁 Full GC 都要告警。  
> 前端的话：第一是 JS 运行时错误率，通过 Sentry 这类工具收集，错误量突增说明有问题上线；第二是页面首屏加载时间（LCP），这是用户感知最直接的指标；第三是前端接口请求成功率，4xx / 5xx 比例升高能快速反映后端异常对用户的影响。
