### 2. 单体到微服务拆分的经验与踩坑【8 分】

**问题**
这次拆分是你主导的吗？拆的过程中有什么需要注意的点或总结的经验？

**我的答案要点**
- 重点在于提前定义拆分边界：共性需求（所有省份通用的）抽成公共微服务，差异化需求各省自己写。
- 落地时遇到的问题：
  - **服务间通信**：用 OpenFeign + Nacos 注册中心，微服务之间用服务名通信。
  - **雪崩效应**：单体没有这个问题，微服务里一个服务慢会拖累整个链路；引入 Sentinel 做熔断，设置策略（5秒内请求 >5 次且慢响应 >30% 则熔断），熔断后走降级备用策略（降低精度计算后返回）。
  - **性能瓶颈定位**：用 JMeter 压测，1000 次请求 10 秒发完；通过日志链路从入口往下查，找到最慢节点后用线程池优化数学计算。
  - **分布式事务**：单体里 Spring 的 `@Transactional` 足够，拆成微服务后跨服务事务需要 Seata 来协调。
  - **部署**：用 Docker 将所有微服务放入同一网络，相互之间通过服务名通信。
- 主要拆分顺序：先划边界 → 落地服务通信与注册 → 压测找瓶颈优化 → 处理分布式事务 → 部署。

**评价**
- 优点：拆分的思路和落地顺序完整，Nacos、OpenFeign、Sentinel、Seata、Docker 都主动点出，体现了真实落地经验。
- 不足：Sentinel 熔断策略说得很详细，但压测工具名"JMeter"的表述不够清晰；线程池优化可以补充具体使用（如 `ThreadPoolExecutor` 参数调优）。

**参考答案要点**
- **拆分边界**：先划清楚"哪些是所有版本共有的功能"（反复询问产品确认），共有的抽成独立微服务，差异化的保留在各自微服务中。
- **服务通信**：OpenFeign 声明式 HTTP 调用，Nacos 做服务注册与发现；部署时保证在同一 Docker 网络内，允许服务名互相访问。
- **雪崩防护**：Sentinel 熔断降级——5 秒内请求超过 N 次、慢响应率超过阈值时熔断，触发 fallback（如返回降精度结果）。
- **性能压测**：JMeter 模拟高并发，通过链路日志（从入口服务一路追查到下游）定位慢节点，CPU 密集型计算用线程池 (`ThreadPoolExecutor`) 异步处理。
- **分布式事务**：Seata 统一协调跨服务事务，利用全局事务管理器感知各分支事务状态，失败时统一回滚（AT 模式是常见选型，底层基于 undo_log 实现自动补偿）。
- **部署方案**：所有微服务编写 Dockerfile，在 docker-compose 中声明同一 network，服务间改用服务名通信，避免硬编码 IP。

**话术示例**
拆分的核心是先把边界定清楚，目标是复用共性、解耦差异。在落地之前，我会把每个新需求都先问产品：这个功能是所有省都有的，还是只有这个省自己的？确认之后，共有的就沉进公共微服务，差异化的留在各自服务里。

通信这块用的是 OpenFeign + Nacos，一个负责声明式调用，一个负责服务发现，部署时把所有服务放进同一个 Docker 网络，用服务名互相找到对方。

雪崩是微服务里特有的痛点，我们引入了 Sentinel 做熔断，如果一个下游服务在短时间内慢响应比例超过阈值，就自动熔断，调用 fallback 返回一个降精度的备用结果，避免拖垮整条链路。

分布式事务用的是 Seata，它相当于独立于各个服务之外的协调者，统一管理全局事务的状态，如果某个分支事务失败，就通知其他已提交的分支回滚。在 AT 模式下，底层是通过 undo_log 先记录操作，失败时自动补偿，业务代码侵入很少。

### 3. Seata 分布式事务的具体实现原理【6 分】

**问题**
Seata 具体是通过什么方式把分布式事务问题解决掉的？

**我的答案要点**
- 有一个独立于事务各方的"管理者"角色统筹所有分支事务。
- 各分支服务执行完毕后向管理者汇报状态；如果其中一个失败，触发其他分支回滚。
- 类比：在同一 JVM 的单体里，事务失败可以直接感知；微服务跨进程后互相没有直接通路，需要第三方协调。

**评价**
- 优点：概念方向正确，抓住了"全局协调者"这个核心思路，比喻清晰。
- 不足：没有说出具体模式名（AT 模式 / TCC / Saga）；AT 模式的 undo_log 机制、两阶段提交流程（prepare → commit/rollback）均未提及；对面试官追问"通过什么方式"的回答略显模糊。

**参考答案要点**
- **Seata 核心角色**：TC（事务协调器，独立服务）、TM（事务管理器，在业务代码里）、RM（资源管理器，每个微服务里）。
- **AT 模式（最常用）**：
  1. TM 向 TC 注册全局事务，获取全局事务 ID（XID）。
  2. 每个参与的 RM 在本地提交前，先写 undo_log 记录操作前的快照，再执行本地事务并提交，同时向 TC 汇报分支状态。
  3. TC 收集所有分支状态：全部成功 → 通知 RM 删除 undo_log（全局提交）；任一失败 → 通知 RM 根据 undo_log 反向补偿（全局回滚）。
- **与 2PC 的关系**：AT 模式属于改造版 2PC，核心优化点是本地事务可以先提交（不持有锁等待 TC 确认），通过 undo_log 实现"柔性回滚"，减少锁持有时间，吞吐量更高。
- **其他模式**：TCC（try-confirm-cancel，业务侵入大但控制粒度细）；Saga（适合长事务，各步骤有对应补偿事务）。

**话术示例**
Seata 里有三个角色：TC 是独立部署的事务协调器，TM 是在业务代码里发起全局事务的管理器，RM 是每个微服务里的资源管理器。

最常用的是 AT 模式，核心思路是两阶段提交加上 undo_log 补偿。第一阶段：每个参与的 RM 在本地执行自己的事务，提交之前先把操作前的数据快照写进 undo_log，然后提交本地事务，向 TC 汇报"我这边成功了"。第二阶段：TC 收到所有分支汇报后，如果全部成功就通知各 RM 删除 undo_log，提交完成；如果有任何一个失败，就通知其他 RM 读取 undo_log，把数据反向补偿回去，实现全局回滚。

和传统的 XA 两阶段相比，AT 模式的好处是本地事务可以先提交，不用一直持有行锁等 TC 确认，锁的持有时间更短，吞吐量更高。

### 4. 压测中 TPS 与事务性能瓶颈【7.5 分】

**问题**
压测过程中有没有压出分布式事务的性能瓶颈？写操作（TPS）的部分有没有专门测？

**我的答案要点**
- 系统主要是展示系统，增删改极少；气象数据由算法工程师提前处理好写在磁盘，后端只做读取和展示，数据库中只有用户信息、权限配置等少量表。
- 所以压测主要测的是查询（QPS），TPS 测试的场景几乎不存在，分布式事务的性能瓶颈在这个场景下没有实际压出来。

**评价**
- 优点：如实说清楚了业务场景的特殊性，没有强答不存在的测试经验，诚实且合理。
- 不足：可以更主动地给出"如果有高 TPS 写场景会怎么处理"的预判，展示思维深度。

**参考答案要点**
- 说明业务特征：气象数据提前离线生成（写磁盘），后端以读为主，数据库表量少、写操作频率低，所以压测重点是 QPS（查询性能），TPS 场景可忽略。
- 拓展：如果是高写场景，分布式事务的性能瓶颈通常出现在 TC 的全局锁（Seata AT 模式下对同一行加全局行锁）、undo_log 写入延迟、网络往返带来的提交延时上；常见优化手段是缩小事务粒度、异步消息补偿（最终一致）、只在核心写操作上用 Seata。

**话术示例**
我们这个系统的特殊性在于：气象数据是算法工程师离线处理后写到磁盘的，业务后端只负责读取数据路径和展示，数据库里只存用户信息和权限配置这些低频数据，几乎没有高频写操作。

所以压测的重点在查询性能，TPS 方向基本没有显著瓶颈要压，分布式事务的性能问题在这个场景下也没有实际暴露出来。

如果是高写并发的场景，Seata AT 模式的瓶颈通常来自全局行锁的竞争、undo_log 写入和网络往返带来的二阶段延迟，通常的应对是缩小事务粒度，或者把非强一致场景改成消息队列异步补偿，换成最终一致方案。

### 5. 大表查询性能优化【8 分】

**问题**
大数据查询场景的性能优化，你了解哪些手段？

**我的答案要点**
- 先通过慢查询日志定位哪个 SQL 慢。
- 建索引：注意最左前缀原则；如果查询从第二个索引列开始，或者前面有 `%xx%` 模糊匹配，或者有范围判断，索引优化会失效。
- 索引原理：排序后的树状结构，能把逐行扫描变成二分式查找。
- 大分页优化：分页越深越慢（数据库要逐行跳过），使用游标分页（记录上次返回的最大 ID，下次从该 ID 处开始查），避免 OFFSET 线性增长。
- 回表优化/覆盖索引：查询所需字段全在索引中，不用回到主键树再查完整行；如果数据跨度大要特别注意减少回表。
- 先用子查询取 ID（走覆盖索引），再 JOIN 取完整行，是减少回表的一种常用写法。

**评价**
- 优点：思路完整，从监控到索引原理到进阶优化（游标分页、覆盖索引）都有涉及，层次清楚。
- 不足：索引数据结构回答成了"红黑树"，实际是 B+ 树（见题 6 单独复盘）；可以补充索引失效的更多场景（类型隐式转换、函数作用于列等）。

**参考答案要点**
- **定位**：开启慢查询日志 + `EXPLAIN` 分析执行计划（重点看 type、rows、Extra 字段）。
- **索引建立**：高基数列、常用 WHERE/ORDER BY/JOIN 字段上建索引；联合索引遵循最左前缀；注意失效场景（`%`开头的 LIKE、函数包裹字段、类型不匹配、OR 不当等）。
- **深分页优化**：`LIMIT 100000, 10` 代价极高，用游标分页（`WHERE id > last_id LIMIT 10`）；或先用子查询取 ID（走覆盖索引）再 JOIN 取完整行（减少回表代价）。
- **覆盖索引**：查询字段全在索引中，无需回表，是性能最好的方案；`EXPLAIN` 里 `Extra: Using index` 表示命中覆盖索引。
- **其他手段**：读写分离（查询打只读副本）；分库分表（大表拆垂直/水平）；结合 Redis 缓存热点数据。

**话术示例**
查询优化一般从定位开始：先开慢查询日志，找到哪条 SQL 慢，再用 EXPLAIN 分析执行计划，重点看 type（最好是 ref 或 range，最差是 ALL 全表扫）、rows 预估扫描行数、Extra 里有没有 Using index 或 Using filesort。

锁定问题后，最常用的手段是建索引。建联合索引要注意最左前缀——查询条件要从索引的第一列开始，如果第一列跳过了，或者用了 `%` 开头的 LIKE，或者对列套了函数，索引就会失效。

深分页是个常见的坑：`LIMIT 100000, 10` 实际上要扫描 10 万行才能跳到目标位置，越翻越慢。优化方式是用游标分页，记录上次返回的最大 ID，下次直接 `WHERE id > last_id LIMIT 10`，就不需要再跳过前面的数据了。

另一个优化点是减少回表：如果查询的字段都在索引里，就能直接从索引树上拿到结果，不需要再回到主键树查完整行，性能提升明显。如果必须要回表，可以先用子查询只取 ID（走覆盖索引），凑齐之后再一次性 JOIN 取完整行，比散点回表效率高很多。

### 6. 索引的底层数据结构【错】【4 分】

**问题**
索引按什么数据结构存储，这个结构为什么能加快查询？

**错误点**：回答"红黑树"，MySQL InnoDB 索引实际使用 **B+ 树**，而非红黑树。

**我的答案要点**
- 说是"排好序的二叉树，好像叫红黑树"。
- 排序后可以用二分式查找代替逐行扫描。

**评价**
- 优点：方向感对（有序树 → 减少查询范围），逻辑合理。
- 不足：具体名字答错了，Redis 里的有序集合底层才用到跳表/红黑树；MySQL InnoDB 用的是 B+ 树，B+ 树的结构特征（多叉、只在叶子节点存数据、叶子节点双向链表）是面试高频考点，必须掌握。

**参考答案要点**
- **B+ 树**：MySQL InnoDB 引擎的索引数据结构，非叶子节点只存键值（不存数据），叶子节点存全量键值 + 数据（或主键指针），且叶子节点通过双向链表连接。
- **为什么用 B+ 树（而不是红黑树）**：
  1. B+ 树是 N 叉树，树高很低（一般 2～4 层），意味着磁盘 I/O 次数少，查询最多几次磁盘读取就能找到。
  2. 叶子节点链表结构支持高效范围查询（`BETWEEN`、`ORDER BY`）。
  3. 红黑树是二叉树，数据量大时树很高，磁盘 I/O 次数多，不适合磁盘存储的场景。
- **聚簇索引 vs 二级索引**：主键索引（聚簇）叶子节点直接存行数据；普通索引（二级）叶子节点存主键值，查到后还需回主键树取完整行（即回表）。

**话术示例**
MySQL InnoDB 的索引用的是 B+ 树，不是红黑树。B+ 树是 N 叉树，每个节点可以有很多子节点，所以同样的数据量下树的高度很低，通常只有两三层，每次查询的磁盘 I/O 次数就很少。

B+ 树有个特别的设计：非叶子节点只存键值用来导航，数据全部存在叶子节点上，而且所有叶子节点通过双向链表串起来。这样不仅单点查询快，范围查询也很高效，直接在叶子节点链表上顺序扫就行了。

红黑树是平衡二叉树，数据量很大时树的高度会很高，每层都可能对应一次磁盘 I/O，在数据库这种磁盘密集型场景下代价太大，所以才选了 B+ 树这种"矮而宽"的结构。

### 7. JVM OOM 排查步骤【7 分】

**问题**
JVM 内存溢出（OOM）了，服务挂掉，如何排查？

**我的答案要点**
- 先看服务器层面：CPU、内存、硬盘等基础指标，排除硬件原因。
- 应用层面：观察 JVM 堆内存，如果 GC 频繁触发且内存始终不降，怀疑内存泄漏。
- 往细排查：定位哪段代码持有了无法回收的引用。

**评价**
- 优点：排查思路由外到内（系统 → JVM → 代码），逻辑清晰。
- 不足：没有提到 `-XX:+HeapDumpOnOutOfMemoryError` 自动 dump、MAT/VisualVM 工具分析堆快照；OOM 有多种原因（堆溢出、元空间溢出、栈溢出）没有区分；没有提到 `jmap`、`jstat`、`jstack` 等诊断命令。

**参考答案要点**
- **先确认现象**：查看应用日志中的 OOM 异常信息，明确是哪种 OOM（`java.lang.OutOfMemoryError: Java heap space` / `Metaspace` / `StackOverflowError`）。
- **收集堆信息**：若已配置 `-XX:+HeapDumpOnOutOfMemoryError`，OOM 时自动生成 `.hprof` 文件；否则用 `jmap -dump:format=b,file=heap.hprof <pid>` 手动 dump。
- **分析堆快照**：用 MAT（Eclipse Memory Analyzer）或 VisualVM 分析 `.hprof`，找出占用内存最多的对象、其 GC Root 引用链，定位到具体代码。
- **辅助工具**：`jstat -gcutil <pid> 1000` 监控 GC 频率与各区占用；`jstack <pid>` 查看线程栈（排查线程泄漏）；Arthas 在线诊断。
- **常见根因**：集合/缓存无限增长、大文件未分块读取（一次性读入内存）、ThreadLocal 未 remove、类加载器泄漏（元空间）。

**话术示例**
碰到 OOM 先看日志里报的是哪种——`Java heap space` 是堆不够，`Metaspace` 是元空间满了，`StackOverflowError` 是栈太深，排查方向不一样。

堆溢出是最常见的情况，排查思路是先确认配置里有没有打开 `-XX:+HeapDumpOnOutOfMemoryError`，有的话 OOM 时会自动生成 `.hprof` 堆快照。如果没有，可以用 `jmap -dump` 手动导出，然后用 MAT 或 VisualVM 打开，找占用内存最多的对象，顺着 GC Root 引用链追到代码里。

同时可以配合 `jstat -gcutil` 看 GC 频率，如果 GC 一直在跑、Old 区始终不降，基本就是内存泄漏，常见原因是缓存或者集合被静态引用一直在增长、大文件一次性读入内存、ThreadLocal 使用完后没有 remove。

### 11. AI 代码越改越乱，如何应对【8.5 分】

**问题**
用 AI 写代码，不固定的情况下经常出现越改越乱，你怎么避免或处理？

**评价**
- 优点：抓住了核心矛盾（AI 无长期记忆、人必须填补），给出了可操作的方法。说话务实、不流于表面，面试官反应积极。

**话术示例**

### 12. 前端性能优化亮点（Vue3 响应式 + HTTP 缓存 + 长任务）【8.5 分】

**问题**
前端有什么特殊的亮点？

**我的答案要点**
- **响应式优化**：Vue3 有浅层响应（`shallowRef`）和深层响应之分；地图实例等大对象不需要深层监听，误用 `ref` 会产生大量冗余追踪。改用 `shallowRef` 或 `markRaw` 后明显减少不必要的响应式消耗。
- **HTTP 缓存预加载**：联播时每秒切换一张色斑图（几百 KB），来不及加载导致肉眼可见延迟。封装了一个 Composition Function：用户选定产品和时间轴后，提前把所有时间点的图片请求发出去缓存到浏览器；支持请求中断（切换产品时 AbortController 中断旧请求）；控制最大并发缓存数量（防止占用过多网络资源影响其他请求）。
- **Performance 面板 + 长任务优化**：Performance 录制火焰图；超过 16.7ms 的宏任务会导致浏览器掉帧；定位到具体代码后针对性优化；如果是布局/渲染耗时，从 DOM 操作层面优化。

**评价**
- 优点：三个方向都有真实项目背景，不是泛泛而谈；缓存方案细节（中断、并发控制）说得很到位，说明真正落地过。
- 不足：可以补充 Web Worker 用于计算密集任务（将长任务移出主线程）；`requestIdleCallback` 比 `setTimeout` 更适合低优先级任务排期。

**参考答案要点**
- **响应式精细化**：`shallowRef`/`shallowReactive` 用于只需知道是否存在的大对象（地图实例、ECharts 实例）；`markRaw` 完全跳过响应式追踪；避免把不需要响应式的对象放进 `reactive`/`ref` 深层。
- **HTTP 缓存 / 预加载**：利用浏览器 HTTP 缓存（响应 `Cache-Control` 头），提前并行发出所有资源请求；`AbortController` 配合 `AbortSignal` 实现请求中断；限制最大并发缓存数，防止挤占其他请求的带宽。
- **长任务优化**：Chrome Performance 面板录制 → 火焰图定位 > 16.7ms 的宏任务 → JS 计算密集型考虑 Web Worker；布局抖动（layout thrashing）→ 批量读 DOM / 批量写 DOM，避免交替操作触发多次回流；`requestAnimationFrame` 用于动画帧级别的操作；`requestIdleCallback` 用于低优先级的空闲任务。

**话术示例**
前端层面我比较有积累的方向是性能优化，来说三个实际做过的点。

第一个是 Vue3 响应式的精细化使用。接手过一个项目，里面把地图实例这种大对象用 `ref` 包了，导致 Vue 对它做深层追踪，有很多不必要的性能消耗。我优化时把这类对象改成 `shallowRef` 或者 `markRaw`，告诉 Vue 不需要追踪内部变化，只要知道它存不存在就好，优化后明显减轻了渲染压力。

第二个是预加载缓存。项目有一个气象图联播功能，每秒切一张色斑图（几百 KB 的图片），来不及加载就肉眼可见地卡。我封装了一个 Composition Function，用户选好产品和时间轴后，把这组时间点对应的所有图片请求提前并行发出，利用浏览器的 HTTP 缓存存起来；联播时直接命中缓存，流畅很多。同时加了两个保护：一是最大并发缓存数限制，防止把其他请求的带宽都占完；二是用 AbortController 在用户切换产品时中断前一组正在缓存的请求，避免无效请求堆积。

第三个是用 Performance 面板排查页面卡顿。遇到点击后鼠标一段时间不动的现象，用 Performance 录制后看火焰图，找到超过 16.7ms 的宏任务（16.7ms 是 60fps 的帧间隔，超过这个就会掉帧），点进去定位到具体的源码位置，针对性地优化。计算密集的任务可以考虑放到 Web Worker 里去，不占主线程。

### 14. 页面大量图片视频的加载优化【7.5 分】

**问题**
页面上图片视频很多（画在 Canvas 上），如何加快加载速度？

**我的答案要点**
- 如果有些内容不在视口内：懒加载，使用 IntersectionObserver 监听元素进入视口后再加载。
- 如果内容都在视口内需要同时展示：预加载，在其他页面/页面初始化时通过分片任务提前把首屏资源缓存；分片用 `setTimeout` 控制每片不超过 8ms，不阻塞主线程。
- 提到了 `<link rel="preload">` / `<link rel="prefetch">` 这类资源提示，但说不熟悉。

**评价**
- 优点：懒加载和预加载方案都给出了，且会说具体实现（IntersectionObserver、任务分片）。
- 不足：没有提到图片格式优化（WebP/AVIF）、Video 的逐帧 Canvas 绘制优化（requestAnimationFrame + drawImage）、CDN、HTTP/2 多路复用、OffscreenCanvas；`setTimeout` 任务分片提及"8ms"阈值，实际应该是 < 16.7ms（一帧周期），`requestIdleCallback` 更适合这种场景。

**参考答案要点**
- **格式压缩**：图片优先用 WebP/AVIF（体积更小）；视频选合适的编码（H.264/H.265），分辨率按展示尺寸匹配，不加载超规格资源。
- **懒加载**：`IntersectionObserver` 监听元素可见性，进入视口再设置 `src`；或 `loading="lazy"` 原生属性（仅 `<img>` / `<iframe>`）。
- **预加载**：`<link rel="preload">` / `prefetch` 声明式预加载；也可 `new Image()`/`fetch` 命令式预加载配合缓存。
- **并发控制**：批量预加载时限制同时发出的请求数（如并发 ≤ 4），避免占满带宽。
- **Canvas 视频帧优化**：`requestAnimationFrame` 驱动 `drawImage(video)` 绘制帧，只在视频 `playing` 时运行；OffscreenCanvas + Worker 把绘制移出主线程。
- **HTTP 层**：CDN 加速静态资源；HTTP/2 多路复用减少连接建立开销；合理设置 `Cache-Control` 复用缓存。

**话术示例**
如果页面上的图片视频有些在视口外，首先考虑懒加载，用 IntersectionObserver 监听元素进入视口时再触发加载，避免一上来就把所有资源全发出去。

如果内容都在首屏需要同时展示，懒加载就没意义了，要换成预加载的思路——在用户打开这个页面之前，趁着空闲时间提前把资源拉下来缓存好。实现上可以用 `requestIdleCallback` 把预加载任务排到浏览器空闲时执行，不影响当前页面的正常交互。

格式这块也值得优化，图片优先用 WebP 或 AVIF，体积比 JPEG 小很多；视频编码选合适的，展示尺寸是多少就加载对应分辨率的版本，不加载超规格的。

如果是画在 Canvas 上的视频，用 `requestAnimationFrame` 循环调 `drawImage(video)` 来绘制帧，在视频暂停或不可见时停掉循环，避免空转消耗。高复杂度的 Canvas 绘制可以考虑 OffscreenCanvas 推进 Worker，让主线程保持流畅。

再往上一层，CDN 加速静态资源 + HTTP/2 多路复用，能进一步减少资源加载的网络开销。

### 15. Cursor Rules / Function Calling / MCP 的区别【8 分】

**问题**
Cursor 里的 skills（Rules/Instructions）、Function Calling（Tool Use）、MCP，这三者有什么区别？

**我的答案要点**
- **Rules/Instructions（"死舅子"）**：提示词持久化。本质是降低重复沟通成本，把常用指令、规范写进文件让 AI 每次自动带上。有层级区分：全局 rules（所有对话生效）、任务级 instructions（特定任务/组件/配置对话里生效）。网上有质量较高的现成 rules 可以下载使用，也可以自己完善。
- **MCP（Model Context Protocol）**：AI 与外部平台的标准化集成协议。解决的问题是以前需要截图、语言描述来让 AI 了解外部数据，现在通过 MCP 直接读底层数据，提高精度和效率。典型应用：接入 Figma，AI 可以直接读设计图节点而不是看截图。
- **Function Calling / Tool Use**：给 AI 配置工具以增强能力。典型场景：数学计算（交给代码精确执行而不是模型"心算"）、实时数据查询（模型训练数据有截止日期，联网工具让它获取实时信息）。

**评价**
- 优点：三个概念都答出来了，MCP 解释得尤其清楚，Function Calling 的适用场景举例也很具体（数学计算、实时查询）。
- 不足：Rules 和 Instructions 在 Cursor 的具体用法（`.cursorrules`、`.cursor/rules`、`@instructions`）可以说得更精准；没有点出 MCP 与 Function Calling/Tool Use 的关系（MCP server 本质上也是通过 tool use 暴露能力给 AI）。

**参考答案要点**
- **Rules/Instructions（提示词持久化）**：
  - Cursor 里 `.cursorrules` 或 `.cursor/rules/*.mdc` 文件存规则，分全局规则（每次对话自动附加）和文件/任务级规则（路径匹配时激活）。
  - 作用：把「编码规范、技术栈偏好、项目结构约定」写进去，让 AI 每次回答都知道背景，减少反复解释。
- **Function Calling / Tool Use**：
  - 大模型原生能力，AI 可以输出结构化的"工具调用"请求（JSON），调用方执行后把结果返回给 AI 继续处理。
  - 典型用途：查实时数据、数学计算、执行代码、操作数据库；LangGraph 里的节点工具绑定本质上也是这个机制。
- **MCP（Model Context Protocol）**：
  - Anthropic 提出的开放协议，定义了 AI 宿主程序（如 Cursor）与外部工具/数据源之间的通信标准；MCP Server 通过 Tool Use 机制向 AI 暴露工具。
  - 上层抽象：MCP 相当于统一了"一个 AI 如何接入第三方能力"的标准，开发者只需实现 MCP Server，任何支持 MCP 的 AI 宿主都能直接用。
  - 与 Function Calling 的关系：MCP Server 的工具对外暴露形式仍然是 Tool Use；MCP 是更高层的"发现与集成标准"，Function Calling 是底层的"调用机制"。

**话术示例**
这三个东西层级不同。

Rules 和 Instructions 是提示词持久化——把编码规范、技术栈约定、项目结构写进 `.cursorrules` 或者任务级的 `.instructions.md` 文件，AI 每次对话会自动带上这些上下文，不用每次重复说"我用的是 React + TypeScript，不要用 class 组件"之类的话。Global rules 是全局生效的，task-level instructions 可以按文件路径或任务类型激活，粒度更细。

Function Calling / Tool Use 是大模型的原生能力——AI 在回答时可以输出一个结构化的工具调用请求，让调用方去执行，再把结果反馈给 AI 继续处理。典型场景是数学计算（让代码精确算，而不是让模型用概率"猜"）和实时数据查询（模型的训练数据有截止日期，联网工具帮它获取最新信息）。

MCP 是 Anthropic 提出的开放标准，解决的是"AI 如何统一地接入各种外部平台"的问题。以前想让 AI 操作 Figma，只能截图描述；有了 MCP，Figma 实现一个 MCP Server，AI 宿主（比如 Cursor）就能直接读取设计图的节点数据，不需要人工中转，精度更高。从底层机制看，MCP Server 向 AI 暴露工具的方式仍然是 Tool Use，MCP 是在此基础上定义了更高层的发现和集成标准，让工具接入有了统一协议。
