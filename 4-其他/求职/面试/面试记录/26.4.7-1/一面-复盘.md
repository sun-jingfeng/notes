### 2. AI 智能体项目场景展开【7.5 分】

**问题**
你的 AI 智能体项目具体是什么场景？文案生成是不是简单调 API 加提示词就能做，为什么需要用智能体框架？

**我的答案要点**
- 场景：气象预警文案生成；输入为用户选择的气象要素、当前时间、地图经纬度范围
- 后端根据时间和气象要素找到对应气象原始数据，连同经纬度范围一起传给大模型
- 模型不是直接输出文案，而是通过 LangGraph 搭建了一套工作流图：路由节点根据气象要素类型分流，不同分支绑定不同工具，最终走结构化输出节点
- 工具节点包括：坐标转地名、不同气象数据的解码 / 插值算法（这类数学计算不能交给模型做）
- 需要智能体的原因：涉及工具调用（数学计算不能靠模型）、会话管理（支持重新生成和续聊）、结构化输出

**评价**
- 优点：项目全貌介绍完整，覆盖了工作流图设计、工具绑定、路由、结构化输出、会话管理各环节，技术深度较好。
- 不足：开场没有主动说清"为什么要用智能体而非简单调 API"，导致面试官需要专门追问。整体表达较散，缺少一句清晰的"核心矛盾"点明为何这个场景需要智能体框架。

**参考答案要点**
- 先给出"为什么需要智能体"的判断标准：若存在多步推理、工具调用、条件分支、会话状态，就需要智能体编排而非单次 API 调用。
- 本项目三个核心理由：① 不同气象要素需要路由到不同处理节点（条件分支）；② 部分计算必须用函数工具而非模型（工具调用）；③ 用户可重新生成或续聊（会话管理）。
- 工作流图节点清单：坐标转地名节点 → 路由节点（按气象要素类型） → 各气象要素处理节点（含数据解码/插值工具） → 结构化输出节点。

**话术示例**
这个场景之所以不能只用提示词调接口，有三个核心原因。第一，不同气象要素对应的数据格式和处理逻辑完全不同，比如降水色斑图是 PNG 存的矩阵数据，需要解码；预警点位是 CSV 格式，需要插值还原；这些数学计算不能交给模型做，必须走函数工具。第二，文案里一定要有地名，但前端传来的只有地图经纬度，所以需要一个"坐标转地名"的工具节点。第三，用户可以对文案不满意后重新生成或续聊，需要完整的会话管理。基于这三点，我们用 LangGraph 搭了一个工作流图：先走坐标转地名，再做路由分流，每条分支绑自己的工具，最后统一走结构化输出节点。

### 3. 路由到不同节点的机制【8 分】

**问题**
你说了"不同模型"，不同模型有什么区别，哪些场景调哪些模型？

**我的答案要点**
- 澄清：模型实例其实是相同的，区别在于绑定了不同的工具
- 路由依据是用户选择的气象要素类型
- 不同气象要素的数据格式不同，需要绑定不同工具来处理，所以在工作流图里做了分流

**评价**
- 优点：及时澄清了"不同模型"的说法，避免了面试官误解。对分流逻辑解释清晰，技术点无误。
- 不足：最初表述时用了"不同模型"这个说法，造成了歧义，后续需要花时间纠正；专业表述应改为"不同工作流分支"或"不同节点"。

**参考答案要点**
- 准确说法：在 LangGraph 图中，不同分支节点绑定了不同的工具集；模型本身是统一调用的，节点不同只是 tools 参数不同。
- 路由节点的实现方式：在路由节点里通过条件边（conditional edge）判断当前气象要素类型，导向不同的处理节点。

**话术示例**
这里我刚才说法不太准确，其实不是"不同的模型"，而是工作流图里的不同分支节点，每个节点绑定的工具不一样。模型调用的是同一个，但是给它的 tools 列表不同。举个例子，降水色斑图分支需要一个"PNG 解码"工具，因为降水数据是用 RGB 通道编码存的，需要先还原出原始数值才能处理；预警点位分支则需要"稀疏点插值"工具，把几个离散点扩展成完整矩阵。路由节点在 LangGraph 里用条件边实现，根据传入的气象要素类型选择走哪条分支。

### 4. 经纬度转地名为何用 Function Calling 工具【7 分】

**问题**
经纬度转地名，为什么要设计成模型的工具而不是在业务代码里直接做？

**我的答案要点**
- 前端是一个可以自由缩放拖动的地图，不绑定任何具体地名，只传当前视口的经纬度范围
- 生成的文案里必须有地名，所以必须转换
- 这个转换逻辑是模型生成文案流程中的一部分，放到工作流节点里更自然

**评价**
- 优点：说清楚了"为什么有这个需求"——前端没有地名只有坐标。需求来源交代得清楚。
- 不足：没有正面回答"为什么是工具而不是业务代码"。面试官的问题核心在于"工具 vs 业务代码"的边界，应给出明确判断标准。

**参考答案要点**
- 判断是否需要设计成工具的标准：当模型在推理过程中需要根据上下文按需调用某个能力，且这个调用时机是动态的，就适合设计成工具。
- 本项目中，坐标转地名是模型生成文案的前置依赖，模型需要"知道现在处理的是哪个地方"，这个信息需要在推理链路里流转，而非在模型外提前处理好再传入。
- 工具的另一个好处是：如果后续某些场景不需要地名（如纯数据分析类节点），模型可以选择不调用该工具，灵活性更高。
- 底层实现调用了 Python 第三方包（如 geopy / reverse geocoding 类库），封装成工具函数后注册到 LangGraph 节点。

**话术示例**
把它设计成工具，而不是在模型外面提前处理好，主要是因为这个信息需要在模型推理链路里流转。前端传来的是用户当前看到的地图经纬度范围，模型在生成文案时需要知道"这是哪个地方"，这个判断是推理过程的一部分。如果在外部提前查好地名再传进去，只能是个固定字段，不够灵活；而设计成工具后，模型可以在需要时主动调用，生成的地名也能自然融入到后续节点的上下文里。底层实现是调了一个 Python 的逆地理编码库，封装成函数注册到图节点里就好了。

### 5. PNG 存储降水数据的合理性【5 分】

**问题**
为什么用 PNG 来存这样的数据？这是不是一个更高效的存储格式？有没有更好的方案？

**我的答案要点**
- 这是继承的方案，领导调研后确认 PNG 体积最小
- PNG 用 RGB 三通道编码降水数值，有一个放大/缩小系数，需要解码还原
- 文件大小一般在几十 KB 到三四百 KB 之间
- 数据来源是航天宏图的"天庭系统"，算法处理后输出的格式

**评价**
- 优点：如实说明了数据来源和方案背景，没有编造。
- 不足：对面试官质疑（"是否有更高效格式"）缺乏有效回应。实际上 PNG 用于存储科学数据是一种常见的、有明确原因的工程决策，应能说清楚为何 PNG 比 JSON/HDF5/NetCDF 等方案在这个场景下更优。

**参考答案要点**
- PNG 用于存储矩阵型空间数据的优势：① 无损压缩，压缩率高，体积远小于原始浮点数组；② 前端天然能渲染，可直接在地图上叠加展示色斑图；③ 读写库生态成熟，跨语言兼容性好。
- 局限性：精度受通道位数限制（标准 PNG 是 8-bit per channel），对高精度气象数据需要约定编码系数来扩展精度范围；读写需要双方约定编码规则。
- 其他备选格式如 HDF5、NetCDF 在气象领域常见，但前端不原生支持，需要额外解析中间件；JSON 体积过大；PNG 在"前端可直接渲染 + 体积小 + 支持矩阵数据"这三点的综合性价比最高。

**话术示例**
用 PNG 的原因主要有两点：一是无损压缩比高，同样的矩阵数据用 PNG 存比裸浮点数组小得多；二是前端天然支持，可以直接在地图上叠加渲染色斑图效果，不需要额外的格式转换层。代价是精度受 8-bit 通道限制，所以双方约定了一个编码系数，把原始浮点数压缩到 0-255 范围内存储，读取时反向解码还原。相比 NetCDF 或 HDF5 这类气象专用格式，PNG 的好处是前端不需要额外安装解析库，工程接入成本低很多。

### 8. 会话记忆管理方案【8 分】

**问题**
你的记忆管理是怎么做的？详细说说。

**我的答案要点**
- 前端传参中包含可选的 `session_id`，首次生成时不传，首次返回后前端持有该 ID
- 续聊或重新生成时传入 `session_id`，后端用 Redis 根据 ID 查找历史会话
- 未找到则新建，找到则续聊；Redis TTL 设为 24 小时
- 会话长度管理：序列化后判断长度，超过阈值则触发压缩
- 压缩策略：保留最近 N 轮（N 可通过环境变量配置），旧记录用另一个模型调用做 AI 摘要浓缩成一段话
- 不同消息角色处理不同：系统提示词（system）和工具消息（tool）原样保留，AI 消息和用户消息才做压缩
- 压缩后的内容创建新的对话，作为原会话的延续

**评价**
- 优点：方案完整，覆盖了 session 生命周期、存储、长度控制、压缩策略和不同角色消息的差异化处理，逻辑严谨。
- 不足：对"为什么保留 system 和 tool 消息不压缩"可以补充一句技术理由（这两类消息是模型行为约束和工具调用记录，压缩会破坏模型的行为一致性）。

**参考答案要点**
- Session 管理：`session_id` 由后端首次生成并返回，前端在需要续聊时带上；Redis 存储，TTL 24 小时。
- 长度控制触发点：读取会话时检查序列化后的 token 估算长度，超过阈值则压缩后再使用。
- 压缩策略：保留最近 N 轮（可配置），历史旧记录调用模型做摘要，压缩为一段 `assistant` 角色消息。
- 角色差异处理：`system` 消息保留（模型行为约束）；`tool` 消息保留（工具调用记录，影响 ReAct 链路正确性）；`user` + `assistant` 消息压缩。
- 压缩后重建：用压缩后的消息列表创建新的会话对象，替换原有上下文继续运行。

**话术示例**
会话管理的思路是这样的：前端在首次请求时不传 session_id，后端新建会话，生成 session_id 后返回给前端。前端如果要重新生成或续聊，就把这个 session_id 带上，后端拿它去 Redis 里查；查到就续聊，查不到就新建。Redis 的 TTL 设的 24 小时，到期自动清理。

长度控制方面，每次读取会话后先估算 token 数，超过阈值就触发压缩。压缩策略是保留最近 N 轮完整对话（N 在环境变量里配），更早的内容调一个模型来摘要，浓缩成一段简短描述放在前面。不同角色的消息处理方式不一样：system 提示词和 tool 消息原样保留，因为这两类会影响模型的行为约束和工具调用链路的完整性；主要压缩的是 user 和 assistant 的历史消息。压缩完之后用新的消息列表重建会话，作为这轮对话的新起点继续走。

### 9. Vue Router 路由守卫与异步拦截【5.5 分】

**问题**
Vue 的路由钩子里，如何在 `beforeEach` 里做异步操作（比如发请求判断用户权限），然后再决定是否放行？

**我的答案要点**
- `beforeEach` 是全局路由守卫，路由跳转前执行
- Vue Router v4（配合 Vue 3）支持返回 Promise，`beforeEach` 回调可以是 `async` 函数
- 直接在守卫里用 `async/await` 发请求，再根据结果 `return true`（放行）或 `return false`（阻止）
- 对 Vue Router v2 的 `next()` 风格语法不太确定，现场查了代码

**评价**
- 优点：Vue Router v4 的异步守卫方式说对了，思路正确。
- 不足：对 Vue Router v3（Vue 2 配套）的 `next()` 方式不够流利，面试中现查代码影响了节奏；两个版本的 API 差异应该能直接说清楚。

**参考答案要点**
- **Vue Router v3（Vue 2）**：`beforeEach(to, from, next)`，支持在回调里做异步操作，异步完成后调用 `next()` 放行，`next(false)` 阻止，`next('/login')` 重定向。回调不支持 `async/await` 直接返回，必须手动调用 `next()`。
- **Vue Router v4（Vue 3）**：`beforeEach(to, from)` 回调可以是 `async` 函数，直接返回 `true` 或 `undefined` 表示放行，返回 `false` 表示阻止，返回路由对象表示重定向；本身支持 Promise 返回值，原生兼容异步。
- 实际写法示例（v4）：
  ```js
  router.beforeEach(async (to, from) => {
    const isAdmin = await checkAdminPermission()
    if (to.path === '/admin' && !isAdmin) return '/login'
    return true
  })
  ```

**话术示例**
在 Vue Router v4 里，`beforeEach` 的回调天然支持 `async`，可以直接 `await` 发异步请求，根据结果返回 `true` 放行、返回 `false` 阻止，或者返回一个路由路径做重定向，写起来很自然。Vue Router v3 稍有不同，回调里多一个 `next` 参数，异步操作完成后必须手动调用 `next()` 放行，或者 `next(false)` 阻止，不能靠返回值，`next` 必须且只能调用一次，否则会有行为异常的问题。

### 10. Vue Router `next()` 为何升级为返回值【2 分】【错】

**问题**
为什么 Vue 2 的 `next()` 回调模式要升级成 Vue 3 的返回值模式？

**错误点**
当时未能作答，只是重述了问题本身，没有给出原因。

**我的答案要点**
- 未作答，只是重复了问题。

**评价**
- 优点：无。
- 不足：这是一个考察"API 设计演进动机"的问题，完全没答上来。

**参考答案要点**
- **`next()` 的缺陷**：`next` 回调必须在每条代码路径上被**恰好调用一次**，否则导航会挂起或行为异常。在有多个条件分支或异步流的守卫里很容易出错（忘记调用、调用两次、异步回调后忘记调用）。
- **返回值的优势**：函数只需要返回一个值（或 Promise resolve 一个值），消除了"必须手动调用 next"的约束，语义更清晰，配合 `async/await` 也更自然，不会出现忘记调用 `next` 的情况。
- 本质是从**命令式回调**风格迁移到**声明式返回值**风格，更符合现代 JavaScript 的异步编程习惯。

**话术示例**
`next()` 模式有一个隐患：守卫函数里必须在每一条分支路径上都恰好调用一次 `next`，多调或漏调都会导致导航挂起或出现意外行为，在异步逻辑里尤其容易忘。升级成返回值模式之后，守卫只需要返回一个值或者一个 Promise，框架拿到 resolve 的值再决定下一步，不再依赖开发者手动调用回调，彻底消除了这类隐患，也让 `async/await` 写起来更自然流畅。

### 11. 手写简易路由拦截器【6 分】

**问题**
实现一个简易路由拦截器，包含三个方法：`navigate(to)`、`getCurrentRoute()`、`beforeEach(fn)`。要求：调用 `navigate` 时，`beforeEach` 注册的钩子能拦截到；钩子里支持异步操作；钩子的返回值可以决定是否放行（类似 Vue Router v4 的语义）。

**我的答案要点**
- 用数组存储 `beforeEach` 注册的钩子函数
- `navigate(to)` 里依次调用所有钩子，用 `Promise.resolve()` 包装每个钩子的返回值以支持异步
- 根据钩子的 resolve 值判断是否放行：`false` 则阻止，否则继续下一个钩子，全部通过后更新当前路由
- `getCurrentRoute()` 直接返回当前路由状态
- 时间不够未完整展示代码，最后口头说明了思路

**评价**
- 优点：核心思路正确，用 `Promise.resolve()` 包装处理同步/异步钩子统一化的方式是标准做法；钩子串联逻辑清晰。
- 不足：时间不够导致代码未展示完整；最终实现中还遗留了一个小问题——面试官指出最后一步处理异步时仍然用到了 `async/await`（属于依赖原生异步语法），面试官的意图可能是希望用纯 Promise 链的方式实现。

**参考答案要点**
- 用 reduce 或 for 循环串联钩子，每个钩子返回的值（或 Promise resolve 的值）决定后续流程。
- 标准实现思路：逐个 `await Promise.resolve(guard(to, currentRoute))`，若结果为 `false` 则 `return`（阻止），否则继续；全部通过后更新 `currentRoute`。
- 完整参考实现：
  ```ts
  type Route = string
  type GuardResult = boolean | undefined | void
  type Guard = (to: Route, from: Route) => GuardResult | Promise<GuardResult>

  let currentRoute: Route = '/'
  const guards: Guard[] = []

  function beforeEach(fn: Guard) {
    guards.push(fn)
  }

  function getCurrentRoute(): Route {
    return currentRoute
  }

  async function navigate(to: Route): Promise<void> {
    const from = currentRoute
    for (const guard of guards) {
      const result = await Promise.resolve(guard(to, from))
      if (result === false) return
    }
    currentRoute = to
  }
  ```

**话术示例**
整体思路是这样的：`beforeEach` 只是把传入的钩子函数 push 到一个数组里。`navigate` 在跳转之前，遍历这个数组，依次调用每个钩子，用 `Promise.resolve()` 把结果包一层，这样不管钩子是同步的还是返回 Promise 的，都能统一 `await`。如果拿到的结果是 `false`，就直接 return，阻止跳转；否则继续下一个钩子，全部通过后再把 `currentRoute` 更新成目标路由。`getCurrentRoute` 就直接返回当前路由状态，很简单。
