### 3. 父子项目通信，以及为什么不用微前端框架【7 分】

**问题**：你刚提到页面是通过 iframe 这类方式嵌入的，父子项目之间怎么通信？为什么没有直接用微前端框架？

**我的答案要点**
- 说明微前端框架当时做过调研，也尝试过几种方案。
- 最终没有选微前端框架，主要因为项目时间紧，而 iframe 是浏览器原生能力，能更快落地。
- 认为 iframe 天然隔离样式，能降低样式冲突问题。
- 同源部署时，子项目可以通过 `window.top` 访问父项目的一些全局变量和本地存储能力。
- 静态信息通过挂全局变量并配套 TypeScript 声明的方式共享。
- 动态通信使用 `postMessage` 完成父传子、子传父。
- 共享的信息包括 token、主题风格、路由对象等。

**评价**
- 优点：答出了选型取舍，不是只说“会通信”，而是讲了为什么在当时场景下选择更轻、更快的方案。
- 不足：可以再补一句 iframe 方案的边界和代价，比如路由联动、部署约束、同源依赖、调试复杂度，这样选型会显得更完整。

**参考答案要点**
- 先给结论：这是在交付周期和复杂度之间做的工程取舍。
- 静态共享可通过同源下的全局变量、本地存储、统一配置处理。
- 动态通信用 `postMessage`，并设计消息类型和来源校验。
- 补充为什么没选微前端框架：接入成本、生命周期、通信协议、调试复杂度都更高。

**话术示例**
当时我们不是完全没考虑微前端框架，而是做了调研之后，结合项目周期做了取舍。因为页面要尽快交付，而且几块页面之间的关系没有复杂到必须引入完整微前端运行时，所以最后用了 iframe 这种更轻的方案。静态信息这边，在同源前提下我会通过父项目挂全局变量、统一本地存储键和配置的方式共享，比如 token、主题、基础路由对象；动态事件通信就通过 `postMessage` 做父子互传。这个方案的优点是快、隔离性强，代价是更依赖部署约束，所以本质上是工程取舍。

### 4. 智能体为什么选 Python，而不是 Spring AI 或 Node.js【6 分】

**问题**：你做智能体时为什么选 Python，不考虑直接用 Spring AI，或者单独用 Node.js / TypeScript 来做？

**我的答案要点**
- 回答时的核心结论是最终选了 Python。
- 理由主要是 AI 生态里很多工具和库更成熟，长期看更适合持续做智能体相关能力。
- 也提到当时实际对比主要放在 Spring AI 和 Python 之间，因为原有后端体系是 Java。
- 后续把 Python 服务独立包装成微服务，再接入原有 Java 微服务体系。

**评价**
- 优点：至少回答出了一个合理主线，就是“原有主系统是 Java，但 AI 相关生态更偏 Python，所以最终走服务拆分”。
- 不足：这题答得比较乱，尤其在面试官追问 Node.js 方案时，没有直接回到“也可以做独立服务，只是我基于团队主后端和生态成熟度选择 Python”。中间一度把语言选型和服务边界混在一起，显得判断框架不够清晰。

**参考答案要点**
- 技术选型应拆成两层：主系统语言栈怎么选，AI 能力服务用什么语言实现。
- 如果原系统是 Java，可以保留主链路在 Java，同时把 AI 能力拆成独立服务。
- Python 的优势在于 AI 工具链、社区成熟度、示例和新能力更新速度。
- Node.js 也能做，但如果团队后端核心是 Java，而 AI 生态又偏 Python，那么 Python 往往是更稳的专项服务选择。

**话术示例**
这题我会把它拆成两个维度看。第一，原有业务后端本身是 Java，所以主系统没有必要为了一个 AI 能力整体切技术栈；第二，智能体这块如果单独拆服务，我会更看重 AI 生态成熟度，而这方面 Python 确实更强。所以我最后的方案不是在 Java、Node.js、Python 里三选一替换整个后端，而是保留原有 Java 主服务，把 AI 能力独立成 Python 微服务，通过服务调用接进来。Node.js 当然也能做，但结合当时的团队背景和后续可扩展性，我认为 Python 更合适。

### 5. 微服务拆分与服务间调用的理解【5.5 分】

**问题**：既然 AI 能力可以拆成独立服务，那你们是怎么考虑服务间调用、隔离和系统可用性的？

**我的答案要点**
- 说明原有系统本身已经做过微服务拆分。
- 提到智能体能力最终也是包装成独立 Python 微服务并注册到现有体系。
- 回答里更多停留在“拆成服务”层面，对调用协议、熔断隔离、异步处理方式没有展开。

**评价**
- 优点：至少意识到了 AI 功能不应该直接揉进原单体，而是作为独立服务接入。
- 不足：这题核心不在“有没有拆服务”，而在“拆完之后怎么调用、怎么隔离风险、怎么保证主系统不被拖垮”。你的回答没有真正接住面试官这个点。

**参考答案要点**
- 先说明 AI 服务要独立部署，避免高 CPU、高延迟链路影响主业务。
- 服务间调用可以是 HTTP、RPC、消息队列或异步任务，具体看时延要求。
- 需要补充超时、重试、熔断、限流、降级和日志监控。
- 对耗时型生成任务，可设计成异步提交 + 状态查询，避免长链路阻塞。

**话术示例**
如果把 AI 能力拆成独立服务，重点其实不是拆本身，而是拆完以后怎么保证主链路稳定。我的思路会是让 AI 服务独立部署，通过明确的服务接口去调用，同时把超时、重试、限流和降级做好，避免它的高延迟把主业务拖住。如果任务比较重，我会更倾向做成异步任务，而不是让主请求一直阻塞等待。这样既能把 AI 能力接进来，也能把风险隔离开。

### 6. 强约束提示词应该放在哪一层【5.5 分】【错】

**问题**：如果你要对模型的输入输出做很强的约束，这段提示应该放在 message 的哪个角色位置更合适？

**错误点**：把强约束规则优先拼接到每次用户消息里，不是更优解；高优先级规则通常应放在 `system` 或等价的上层指令位置。

**我的答案要点**
- 你最开始的思路是把这类规则在每次用户提问时拼接进提示词。
- 也意识到聊天上下文是 message 数组，会随着轮次累积。
- 但没有正面回答“为什么放在某一层更合适”，也没有结合优先级和稳定性来解释。

**评价**
- 优点：至少意识到了规则需要稳定传入，而不是偶发性地补一句。
- 不足：对大模型消息分层和优先级理解不够，没接住面试官真正想问的“规则应该放在哪个层级最稳”。如果继续做 Agent 方向，这块属于必须补齐的基础。

**参考答案要点**
- 高优先级、全局性的行为约束，应放在 `system` 或等价的开发者指令层。
- 用户消息更适合承载当前任务输入，不适合反复塞全局规则。
- 需要强格式约束时，可结合 `system` 规则、结构化输出约束和后处理校验共同完成。
- 不要把“放在哪一层”和“是否每轮重复注入”混为一谈。

**话术示例**
如果是全局性的强约束，比如禁止输出某些内容、必须按固定结构返回，我会优先放在 `system` 这一层，或者放在等价的更高优先级指令层，因为这里更适合承载稳定规则。用户消息更适合表达当前这次任务的输入，不适合每轮都临时拼很重的全局约束。真正要把约束做稳，通常不是只靠一句提示词，而是提示层级、结构化输出和后处理校验一起配合。

### 7. Tool message 在消息数组里的位置要求【4.5 分】【错】

**问题**：tool message 在整个 message 数组里有什么要求，位置上要注意什么？

**错误点**：把 tool 相关内容理解成“初始化时提前写好的工具说明消息”是不准确的；真正的 `tool message` 需要和模型发起的工具调用结果在时序上正确配对。

**我的答案要点**
- 你把这题理解成“预先告诉模型有哪些工具可用”。
- 回答里提到了工具提前注册、初始化时传入说明信息。
- 但没有回答 tool call 和 tool result 在消息序列中的配对关系、顺序要求和上下文语义。

**评价**
- 优点：知道工具调用不是无中生有，模型需要知道有哪些工具可用。
- 不足：这题回答偏离题意了。面试官问的是底层协议层面的 message 顺序要求，不是上层框架里的工具注册说明。这里说明你对 Agent 框架封装之下的底层消息模型理解还不够扎实。

**参考答案要点**
- Assistant 发起工具调用后，工具执行结果要以对应的 `tool message` 形式回填。
- `tool message` 要和前面的工具调用在时序上紧邻或可正确关联，不能随意插在无关位置。
- 消息数组既要保证角色合法，也要保证工具调用链条完整，否则模型容易失去上下文一致性。
- 框架层的封装可以帮你拼装，但做 Agent 时最好理解底层协议约束。

**话术示例**
如果说的是底层消息协议里的 `tool message`，那重点不是“我提前告诉模型有哪些工具”，而是工具调用发生之后，结果怎么按正确顺序回填到消息数组里。通常 assistant 先发起工具调用，工具执行完之后，再以对应的 `tool message` 把结果补回去，而且这个消息要和前面的调用正确关联。也就是说，工具注册是一个层面，消息时序和配对是另一个层面，这两个不能混在一起。

### 8. 智能体里哪些问题交给模型，哪些交给传统逻辑，以及风控怎么设计【5.5 分】

**问题**：在做 Agent 的时候，哪些问题应该交给大模型，哪些应该交给传统逻辑？如果要做输入风控、输出风控和流式输出中的撤回处理，你会怎么设计？

**我的答案要点**
- 认为风控这类规则严格、判断标准明确的事情，应优先交给代码逻辑或现成风控 API 去做。
- 输入侧可以先经过风控节点，合格后再进入模型。
- 输出侧也不能直接返回，要在最终返回前加风控节点。
- 当被追问到流式输出中途发现敏感内容怎么处理时，意识到可以按流式分片做检测，但回答没有形成完整方案。

**评价**
- 优点：方向是对的，知道“确定性强、规则明确”的事情应该交给传统逻辑，而不是交给模型拍脑袋。
- 不足：对流式风控的处理没有真正展开。面试官想听的是“边生成边检测、缓冲输出、命中后终止并撤回”，而你只停留在笼统的“再处理一下”。这块工程设计深度还不够。

**参考答案要点**
- 大模型负责语义理解、文案生成、意图归纳、多轮对话等模糊性强的任务。
- 传统逻辑负责权限、风控、规则判断、格式校验、状态流转和外部系统约束。
- 输入风控放在进入模型前，输出风控放在展示前。
- 流式输出可采用“分片缓冲 + 异步风控检测 + 安全后再向前端释放”的策略；命中敏感内容时立即终止流并返回兜底话术。
- 风控设计要考虑同步检测与异步检测的延迟成本。

**话术示例**
我的划分原则是，模糊、需要语言理解和生成的事情交给模型，确定、强规则、可校验的事情交给传统逻辑。像权限、风控、格式校验、状态流转这些，我不会交给模型去判断。输入侧我会先做风控，再决定是否进模型；输出侧也不能直接把模型结果原样给用户，而是要经过审核。对于流式输出，我会更倾向做成分片缓冲和边生成边检测，确认安全后再往前端释放，一旦命中风险内容，就立即终止这次流并返回兜底响应，而不是等整段生成完再统一判断。

### 9. 前端性能优化排查与解决思路【8 分】

**问题**：如果用户反馈页面打开很卡，或者低端机上根本打不开，你会怎么分析并解决？

**我的答案要点**
- 先把“卡”区分成两类：一种是操作时明显掉帧，一种是用久了之后无响应。
- 对掉帧问题，认为核心可能是主线程长任务导致帧率下降。
- 会使用浏览器 `Performance` 面板录制问题操作，重点看火焰图里哪些任务片段过长，再映射回源码定位。
- 结合过往经验，提到可以用 Web Worker 处理不依赖 DOM 的重计算任务。
- 如果不能用 Worker，则考虑把任务切片，借助 `requestAnimationFrame` 或宏任务调度分批执行。
- 对长时间使用后无响应的问题，认为要往内存泄漏方向排查。
- 会使用浏览器 `Memory` 面板结合操作过程看内存曲线变化，再回到代码逻辑定位泄漏点。

**评价**
- 优点：这题答得比较好，已经具备从现象分类、工具定位到具体优化手段的完整分析链路，不是停留在“做懒加载、做缓存”这种泛答。
- 不足：如果再补一句网络层和首屏加载层面的排查，比如资源体积、分包、接口瀑布流，就会更完整，因为题目里“打开很慢”不一定都来自运行时卡顿。

**参考答案要点**
- 先分清是首屏慢、交互卡顿还是长时间运行后无响应。
- 首屏慢排查网络、资源体积、接口串行和初始化逻辑。
- 交互卡顿重点看主线程长任务、频繁重排重绘、大量同步计算。
- 长时间无响应重点排查内存泄漏、定时器、事件监听和缓存未释放。
- 工具上结合 `Performance`、`Memory`、网络面板和真实低端机环境综合判断。

**话术示例**
这类性能问题我会先拆类型，因为“卡”背后的原因可能完全不一样。如果是打开慢，我会先看资源体积、接口链路和初始化逻辑；如果是操作时掉帧，我会重点看主线程有没有长任务，用 `Performance` 面板录制并看火焰图定位；如果是运行久了无响应，我会往内存泄漏方向查，用 `Memory` 面板结合操作过程看内存曲线。优化手段上，不依赖 DOM 的重计算我会尽量放到 Web Worker，不能拆线程的就做任务切片和调度，把主线程让出来。这样分析和优化才是有针对性的。

### 10. Promise Limit 并发限制类的实现【5.5 分】

**问题**：让你实现一个 Promise 并发限制类，你会怎么设计和实现？

**我的答案要点**
- 一开始需要通过面试官不断澄清题意，包括传入的是返回 Promise 的函数，而不是 Promise 本身。
- 自己先尝试手写，但中途意识到首次调用和中途插入任务的场景都没有完全处理稳。
- 后面借助 AI 在原思路基础上做了调整。
- 最终在面试官提供的测试场景下跑通了限制并发 2 个任务的结果。

**评价**
- 优点：没有完全放弃，能边澄清边修正思路，最终把可运行结果做出来。
- 不足：这题暴露出你对并发控制类这类“状态管理 + 队列调度”问题的手感不够，尤其是类的 API、任务入队时机、运行中补任务、如何在完成后继续 drain 队列，这些点没有独立推顺。

**参考答案要点**
- 类内部核心状态包括最大并发数、当前运行数、任务队列。
- `add(task)` 时把任务包装进队列，并尝试调度。
- 当运行中数量小于上限时，立即取队首任务执行。
- 任务完成后在 `finally` 中递减运行数，并继续拉起后续任务。
- 若需要把执行结果透出，可让 `add` 返回一个 Promise，最终 resolve / reject 对应任务结果。

**话术示例**
这类题本质上就是一个队列调度器。我的设计会是类里面维护三个核心状态：最大并发数、当前运行数和等待队列。外部每次 `add` 传进来的是一个返回 Promise 的任务函数，我先把它放进队列里，然后尝试调度；只要当前运行数没到上限，就立刻取任务执行。任务结束后不管成功失败，都在 `finally` 里把运行数减一，然后继续从队列里取下一个任务。这样就能保证同一时刻运行中的任务数不会超过限制。

### 11. AI 帮你写完代码后，下一步应该做什么【6.5 分】

**问题**：如果你让 AI 帮你写完这段代码，下一步你会怎么验证它是真的对的？

**我的答案要点**
- 你回答了会先测一下。
- 也意识到像这种函数类题目，不能只看代码，要自己写测试用例验证。
- 在面试官提醒下，开始用更合适的测试场景去验证并发限制是否真的生效，而不是只看最终打印结果。

**评价**
- 优点：至少有“AI 产出后必须验证”的意识，没有把 AI 生成结果直接当真。
- 不足：验证动作起步还是偏弱，最开始更像“看结果能不能跑”，而不是先设计覆盖关键边界的测试样例。真正工程里，这一步应该更主动，不需要面试官再给测试思路。

**参考答案要点**
- 先明确关键行为，再围绕关键行为设计测试用例。
- 对这道题，至少要覆盖并发上限、生效顺序、长短任务交错、运行中追加任务、异常任务不阻塞队列等场景。
- AI 生成代码后，不能只看静态逻辑，要通过日志、断言或单元测试证明行为正确。

**话术示例**
如果 AI 帮我把代码写出来，我不会直接相信它，而是先把这段代码最核心的行为拆出来，再用测试去验证。像这道并发限制题，关键点不是它能不能打印结果，而是运行中的任务数有没有真的被限制住、先完成的短任务会不会拉起后续任务、异常会不会把整个队列卡死，以及运行中再追加任务还能不能正常调度。只有这些边界测过了，我才会认为它真的可用。
