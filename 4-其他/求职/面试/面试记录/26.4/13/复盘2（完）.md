### 4. 前端性能优化细节【9 分】

**问题**
前端的性能问题，具体讲一下。

**我的答案要点**
- **截图拖拽**：用 CSS `transform` 实现拖拽移动，不用 `top/left`，避免触发回流重排；`transform` 有独立渲染层，性能更好。
- **长 JS 任务（Kriging 插值）**：
  - 现象：色板图生成插件运行时页面卡顿 2 秒。
  - 排查：Chrome Performance 面板录制，看火焰图，定位到 Kriging 插值算法的数学计算耗时 1 秒多。
  - 优化：使用 Web Worker，把纯数学计算移到独立线程，算完后 `postMessage` 传回主线程。
  - 补充：Web Worker 可访问 DOM 限制 → 选它的原因是纯数学计算不需要 DOM；Generator 函数分片也是一种方案，但性能差一些。
- **预缓存（Cache-Control 强缓存）**：
  - 色板图 PNG 历史数据不会变，用强缓存缓存。
  - 用户选定产品+时间轴后，提前请求当天所有时间点的色板图。
  - 切换产品时用 `AbortController` 取消之前未完成的预缓存请求。
- **响应式声明优化**：
  - 地图对象等只需感知"是否存在"，不需侦听内部属性 → 用 `shallowRef` / `shallowReactive` 代替深层响应式 API；不需响应则用 `const`。

**评价**
- 优点：覆盖了多个维度（渲染层优化、主线程卸载、缓存策略、响应式粒度），每个点都有排查过程和方案选择理由，不只是背结论。
- 不足：Web Worker 和 Generator 对比时，表述略散，可以更精炼；AbortController 在口述中没有说出准确名称（说的是"纯抽出来"）。

**参考答案要点**
- CSS transform vs top/left：transform 不触发回流（reflow），只触发合成（composite），且走 GPU 独立渲染层。
- Web Worker：把 CPU 密集型纯计算移出主线程，通信用 `postMessage`；限制是无法访问 DOM / BOM，适合纯数学/数据处理场景。
- 强缓存预缓存：`Cache-Control: max-age`，历史静态资源永不过期；配合 `AbortController.abort()` 取消过期请求，防止资源浪费。
- Vue 响应式粒度：`ref` / `reactive` 深度追踪开销大，对只需判断存在性的复杂对象用 `shallowRef` / `shallowReactive`；不需响应的用普通 `const`。

**话术示例**
性能优化主要做了四块。第一块是截图拖拽，拖动时用 CSS `transform` 而不是 `top/left`，`transform` 不触发回流，走 GPU 独立渲染层，性能更好。第二块是 Kriging 插值卡顿，用 Chrome Performance 录制火焰图，定位到插值算法的纯数学计算占了 1 秒多，我用 Web Worker 把这块计算挪到独立线程，算完再 postMessage 传回主线程，主线程就不会被堵了。第三块是色板图预缓存，历史数据不会变，用强缓存缓存住；用户确定时间段后提前把所有时间点的 PNG 都拉下来，播放时直接走缓存；切换产品时用 AbortController 取消未完成的预缓存，避免浪费。第四块是响应式粒度，地图对象这类复杂对象只需要知道它有没有，不需要深度追踪，用 shallowRef 或 shallowReactive，能明显减少响应式的开销。

### 5. 为什么使用 iframe【7.5 分】

**问题**
为什么要考虑使用 iframe？

**我的答案要点**
- 背景：有 2 个旧系统无法重新开发，加 3 个新系统，共 5 个需在同一父页面展示。
- 技术选型比较 iframe 和微前端框架。
- 工期紧，同源部署下 iframe 通信（postMessage / window 属性 / localStorage）相对简单。
- 最终基于需求满足和开发效率选择 iframe。

**评价**
- 优点：交代了旧系统不能重新开发这一核心约束，选型逻辑合理。
- 不足：没有主动点明选 iframe 而非微前端的核心理由（同源 + 工期 + 不需要极致 URL 同步），属于被动回答，可以主动补充。

**参考答案要点**
- 约束：2 个旧系统已上线，没有时间重头开发，嵌入方式是唯一可选项。
- 选 iframe 而非微前端的理由：① 同源部署，使用 `window.parent` 等同源 API 和 localStorage 通信，足够简单；② 工期紧，iframe 开箱即用，无需处理 CSS/JS 隔离；③ 本项目是 B 端内部系统，子页面切换白屏 0.x 秒可接受，URL 不同步也可接受。
- 如果是 C 端、强调 URL 同步或子应用秒开，则倾向微前端。

**话术示例**
选 iframe 主要有三个原因：首先是约束，其中两个系统已经上线了，没有时间重新开发，只能嵌入；其次是这五个系统是同源部署的，通信用 `window.parent` 传属性或 localStorage 就够了，不需要微前端那套复杂的通信机制；第三是工期紧，iframe 是浏览器原生支持的，不用处理 CSS 和 JS 隔离，开发效率高。这个项目是 B 端内部系统，子应用切换有 0.x 秒白屏、URL 暂时不同步，业务上是可以接受的，所以选 iframe 更合适。

### 6. 从技术角度 iframe vs 微前端哪个更好【8 分】

**问题**
如果从技术角度来讲，你觉得 iframe 跟微前端哪一个更好？

**我的答案要点**
- **iframe 硬伤**：URL 不同步（父子各自维护路由）；子应用切换有 0.x 秒白屏；新开页面重新加载。
- **iframe 优点**：浏览器原生隔离，JS/CSS 无隔离问题；通信简单（postMessage、window 属性、localStorage 同源）；开发效率高，问题少。
- **微前端优点**：解决白屏问题，子应用秒切换；URL 同步（本质同一路由系统，通过 URL 变化驱动子应用路由）。
- **微前端缺点**：样式隔离需要手动解决；路由跳转有坑要查文档；工期紧时容易拖进度。
- 框架演进：single-spa → qiankun（阿里）→ 腾讯/京东等更简单的方案（如 MicroApp）。
- 结论：各有优缺点，B 端内部系统可选 iframe；C 端重视切换体验和 URL 同步则选微前端。

**评价**
- 优点：对比全面，有具体优缺点而非笼统表述，结论有场景区分。
- 不足：微前端框架演进顺序提到"腾讯"的框架有些模糊（京东的 MicroApp 较知名），可以点名说 MicroApp（京东）；样式污染解决方案（Shadow DOM / CSS Modules / BEM + scoped）没有点出来。

**参考答案要点**
- iframe：原生隔离天然解决 JS/CSS 污染；通信限于同源或 postMessage；硬伤是 URL 不同步（无法分享链接/刷新状态丢失）、白屏、新页加载慢。
- 微前端（qiankun / MicroApp / Wujie）：URL 同步、子应用秒切换；缺点是样式隔离需要配置（qiankun 的 strictStyleIsolation 用 Shadow DOM，但 Shadow DOM 有兼容性问题；MicroApp 用 CSS Scope 自动处理）；通信机制比 iframe 复杂一些，子应用卸载/重载时有生命周期坑。
- 选型原则：B 端 + 旧系统嵌入 + 工期紧 → iframe；C 端 + 需要 URL 同步 + 子应用秒切换 → 微前端框架。

**话术示例**
这两个各有场景，没有绝对的好坏。iframe 的优势是浏览器原生隔离，JS 和 CSS 天然不会互相污染，通信用 postMessage 或 window 属性，简单直接，开发效率高。但有两个硬伤：子应用切换有零点几秒白屏，和 URL 不同步——父子路由是分开维护的，刷新页面子应用的状态可能会丢，也没法把带子应用路由的完整链接分享给别人。微前端解决了这两个问题，子应用切换很快，路由统一维护，URL 完全同步。但代价是样式隔离需要额外配置——qiankun 用严格模式打开 Shadow DOM，MicroApp 用 CSS Scope 自动处理——路由跳转也有一些坑，需要查各自的文档。总体来说，B 端内部系统有旧系统要嵌入、工期也紧，iframe 更合适；如果是 C 端、追求体验和 URL 能直接分享，就该选微前端。

### 7. 常用 TypeScript 语法与类型【8 分】

**问题**
你常用的 TypeScript 语法都有哪些？

**我的答案要点**
- 一定写 TS，不写纯 JS。
- 声明类型用 `type`，对象需要融合/扩展用 `interface`。
- 接口参数和返回值都提前声明类型，调用时直接拿到带类型的结果。
- 第三方包 TS 类型：给领导的地图库（hzmap，JS 写的）写了独立的 TS 类型包（`@boss/hzmap-types`），发到内部 npm，安装后地图的所有方法自带类型。
- Window 类型扩展：父子项目通过 `window.top.localData` 传参，自定义属性没类型，用 `interface Window` 声明合并把自定义属性加到 Window 上，子项目安装类型包后不报错。

**评价**
- 优点：有两个真实项目案例（hzmap 类型包、Window 扩展），说明有实际工程化的 TS 使用经验，不是背语法。
- 不足：只提了 `type` / `interface` / 声明合并，未提泛型、工具类型（如 `Partial`、`Pick`、`ReturnType`）、条件类型等；面试官问的是"常用语法"，范围较广，可以简单罗列再举例。

**参考答案要点**
- 类型声明：`type` 用于联合/交叉/工具类型组合；`interface` 用于对象建模和声明合并（扩展内置类型如 Window）。
- 泛型：封装通用组件/函数时常用，如 `request<T>(url): Promise<T>`。
- 工具类型：`Partial<T>`（可选化）、`Required<T>`（必填化）、`Pick<T, K>` / `Omit<T, K>`（字段筛选）、`ReturnType<T>`（提取函数返回类型）。
- 类型守卫 / 断言：`as`、`is`、`instanceof`、`in` 用于类型收窄。
- 第三方类型扩展：独立 `.d.ts` 包发布到内部 npm，或直接在项目 `src/types/xxx.d.ts` 中声明。
- 声明合并：`interface Window` 扩展为全局通信属性加类型。

**话术示例**
我现在写代码一定用 TS，不写纯 JS。最常用的是 `type` 和 `interface`：类型别名、联合类型、交叉类型用 `type`；对象建模、需要声明合并扩展第三方类型的时候用 `interface`。泛型也经常用，封装请求函数或通用组件时基本都加泛型参数。工具类型用得也挺多，比如 `Partial`、`Pick`、`ReturnType`，写起来省事。项目里有个具体的案例：领导的地图库是 JS 写的，我给它单独写了一份类型声明包，发到内部 npm，大家安装之后地图方法就全有类型提示了。还有就是父子项目通过 `window.top` 传自定义参数时，我用 `interface Window` 声明合并把那些属性挂上去，子项目安装包后就不报 TS 错误了。

### 8. 开发组件或组件库时考虑哪些方面【8 分】

**问题**
如果让你开发一个组件或组件库，你都会考虑哪些东西？

**我的答案要点**
- **内部组件**：
  - 关注通信方式和数据放哪：哪些组件共用 → 放最高公共父组件。
  - 父子 → `props/emit`；多层透传 → `provide/inject`；跨层私密 → 事件总线；全局状态 → 状态管理（Pinia）。
  - 复用最大化原则：先封装通用基础层（如通用 ECharts 组件），再封装具体图表组件（柱状图、折线图），最后组合用于页面展示。
- **公共组件库**：
  - 封装核心逻辑，可选逻辑通过参数配置。
  - 样式支持外部灵活调节（CSS 变量 / scoped slot / prop 控制）。
  - 举例：时间轴组件每个项目都要用，但差距大，所以只封装必带核心逻辑，其余可选。

**评价**
- 优点：区分了内部组件和公共组件，有思路层次感，举例具体（时间轴）。
- 不足：没有提到可测试性（单元测试）、API 设计原则（最小必要 props）、文档注释、版本管理，这些对组件库评审很重要。

**参考答案要点**
- **边界划定**：共用数据放最高公共父组件，通信方式按关系选择（props/emit → provide/inject → mitt → Pinia）。
- **复用分层**：基础层（原子组件，如通用 ECharts 包装）→ 业务层（柱状图、折线图组件）→ 页面组件；每层只关注自己的逻辑。
- **API 设计（公共组件）**：最小必要 props，可选能力通过 props 开关；样式用 CSS 变量或 scoped slot 暴露自定义能力；默认行为合理，减少调用侧心智负担。
- **可维护性**：TS 类型全覆盖（props 类型、emits 类型）；提供 JSDoc 或组件说明文档；SemVer 版本管理，breaking change 大版本升级。
- **可测试性**：核心逻辑（如时间轴计算、播放控制）提取为纯函数，便于单元测试。

**话术示例**

### 9. React 与 Vue 原理对比【7.5 分】

**问题**
React 和 Vue 原理了解过吗？对比一下他们两个的差异，包括原理。

**我的答案要点**
- **Vue 2**：`Object.defineProperty` + 数组方法重写；不能通过索引改数组（要用 `$set`）；性能问题：初始化时递归转换整个对象。
- **Vue 3**：`Proxy` 代理（懒代理，按需）；Composition API（逻辑聚合，可维护性好）；按需引入；diff 算法优化（静态节点提升，跳过静态节点只比对动态节点）。
- **React**：
  - Hooks：规则明确（数量和顺序不能变，因为用索引寻找 Hook 状态；只能在函数组件内用，脱离 React 环境就失去响应式）。
  - Fiber（16+）：把每个虚拟节点作为一个 Fiber 节点处理，渲染任务切片，时间过长让出主线程，主线程空闲再继续渲染。
  - 手动触发更新（setState），不像 Vue 自动收集依赖。
  - React 18 → 19 优化了样板代码（不用每次都写 props 参数）；状态管理从 Redux → Zustand/Jotai；SSR 方向 Next.js。
- 对比总结：Vue 响应式更省心（自动收集依赖），React 更灵活但规则多（Hooks 顺序、手动触发）；Vue 响应式 API 在独立 JS 文件中也可用，React Hooks 必须在组件内。

**评价**
- 优点：覆盖了 Vue 2/3 响应式原理的核心差异、React Fiber 和 Hooks 规则，有纵深。
- 不足：Fiber 的描述不够准确——Fiber 的核心是"可中断的增量渲染 + 优先级调度"，不只是"切时间片"；React 的响应式（Hooks）与 Vue 对比的本质是"推模型（Vue，依赖追踪主动推送）vs 拉模型（React，render 函数重新执行拉取最新状态）"没有点出来；Vue 3 静态节点提升说的是 Block Tree / PatchFlag 标记，不只是"跳过"，可以说的更准。

**参考答案要点**
- **Vue 2 响应式**：`Object.defineProperty` 劫持，初始化时递归遍历整个对象；数组需重写 7 个方法，索引/length 赋值无法检测，需要 `$set`。
- **Vue 3 响应式**：`Proxy` 代理，天然支持数组索引和新增属性；惰性代理（访问嵌套属性时才创建代理），性能更好；响应式模块（`@vue/reactivity`）独立，可在非 Vue 环境使用。
- **Vue 3 diff 优化**：编译阶段给动态节点加 PatchFlag，运行时 diff 只比对有 flag 的节点；静态节点提升（hoistStatic），只创建一次 VNode，跳过 diff。
- **React Hooks**：基于调用顺序（链表/数组索引）匹配状态，所以不能放在条件/循环内；只能在函数组件顶层调用，离开 React runtime 就失效。
- **React Fiber**：链表结构 VNode，支持任务中断和恢复；调度器（Scheduler）基于 `MessageChannel` 切分时间片（每帧约 5ms），高优先级任务（用户交互）可打断低优先级渲染任务（并发模式核心）。
- **核心区别**：Vue 响应式是推模型（依赖追踪，数据变就通知），React 是拉模型（setState → 触发 render → 重新执行函数体拉状态）。

**话术示例**
Vue 2 用 Object.defineProperty 做响应式，初始化时递归遍历整个对象转换成 getter/setter，深层对象性能损耗明显；数组比较特殊，重写了 push、splice 这些方法，但通过索引直接赋值检测不到，需要用 $set。Vue 3 改成了 Proxy，支持数组索引和新增属性，而且是惰性代理，访问嵌套属性时才创建代理，性能好很多；diff 方面引入了 PatchFlag，编译时给动态节点打标记，运行时只 diff 有标记的节点，静态节点整体提升，完全跳过 diff。React 这边核心是两块：一是 Hooks，它基于调用顺序（内部用链表/数组索引）匹配状态，所以 Hooks 不能放在条件分支或循环里，也只能在函数组件内用；二是 Fiber，本质是一种可中断的增量渲染机制，把渲染拆成一个个小任务，调度器按优先级执行，用户交互触发的更新可以打断低优先级的渲染，这是 React 并发模式的基础。从根本上说，Vue 是推模型——数据变化通过依赖追踪自动推送更新，React 是拉模型——setState 之后重新执行函数体拉取最新状态，两种设计各有权衡。

### 12. 数据量大时的查询性能优化【8 分】

**问题**
数据量比较大的时候，查询性能你怎么优化？

**我的答案要点**
- 先压测定位瓶颈：JMeter，标准 1000 次请求 10 秒内无失败无慢请求。
- 沿请求链路排查：Nacos → 网关 → 业务层 / 数据库。
- **业务层慢**：CPU 密集型 → 多线程并行计算；I/O 密集型 → 异步/线程池。
- **数据库慢**：看生产容器日志，找慢请求日志，分析规律，建索引。
- **建索引原则**：最左前缀原则；不等号、首位模糊匹配（`%xx`）不放最前面。
- **深分页**：游标分页 / 索引分页（避免 `OFFSET` 大量扫描）。

**评价**
- 优点：有完整的排查流程（压测→链路→业务/数据库），建索引有原则，深分页单独提出。
- 不足："真米特"指的是 JMeter，口述时名称不清晰，面试时要发音准确；慢查询日志的分析方式（`EXPLAIN` 执行计划）没提；覆盖索引、联合索引选列策略没展开。

**参考答案要点**
- **性能定位**：JMeter 压测（并发数 / 响应时间 / 错误率三维分析）→ Arthas / SkyWalking 链路追踪定位慢节点。
- **业务层优化**：CPU 密集 → `@Async` + 线程池 / CompletableFuture 并行；I/O 密集 → 异步非阻塞或 Reactor。
- **数据库优化**：
  - `EXPLAIN` 看执行计划（type、key、rows）。
  - 联合索引遵循最左前缀；高区分度列放前面；避免 `%` 开头的 LIKE、`!=`、函数调用打断索引。
  - 覆盖索引（index only scan）：查询字段都在索引里，不回表。
  - 深分页：用"上次最大 ID + WHERE id > lastId LIMIT n"的游标分页替代 `OFFSET`。
- **缓存**：高频查询结果缓存到 Redis，设置合理 TTL + 随机 jitter 防止缓存雪崩。

**话术示例**
查询性能优化我一般从三步走：先压测定位，然后分析链路，最后针对瓶颈点优化。压测用 JMeter，我们内部标准是 1000 次并发请求，10 秒内完成，错误率为零；如果有慢请求就开始排查。排查沿请求链路走，从注册中心、网关，再到业务层和数据库，看各段响应时间。业务层慢的话，CPU 密集型用 CompletableFuture 并行处理，把串行任务改成并行；数据库慢的话，先在生产环境查慢查询日志，再用 EXPLAIN 看执行计划，重点看 type 和 rows——type 是 ALL 说明全表扫，rows 很大说明扫了太多行。然后按最左前缀原则建联合索引，高区分度的列放前面，避免把范围查询或 % 开头的 LIKE 放索引最左侧。深分页的话，`OFFSET` 越大扫的行越多，改成游标分页——`WHERE id > lastId LIMIT n` 这种，直接定位到位置，不再扫前面那些数据。

### 14. 算法题：连续子数组的最大和【6 分】

**问题**
手写代码：输入一个整数数组，求连续子数组的最大和，只需返回和值。（投屏手写）

**我的答案要点**
- 理解了题意（只需返回和，不需要返回子数组本身）。
- 最终调试后得出正确答案（候选人确认最大值为 18）。
- 中间有调试过程，初版结果不对，经过调整后答对。

**评价**
- 优点：最终答题正确。
- 不足：有明显调试过程，说明对 Kadane's 算法不够熟练，手写时出现了逻辑错误；面试投屏下的解题流畅度不足，会给面试官留下"算法薄弱"的印象。

**参考答案要点**
Kadane's 算法（动态规划，时间复杂度 O(n)，空间复杂度 O(1)）：
- 维护两个变量：`curSum`（以当前元素结尾的最大子数组和）、`maxSum`（全局最大和）。
- 状态转移：`curSum = max(num, curSum + num)`（要么从当前元素重新开始，要么接续之前的子数组）。
- 更新全局最大：`maxSum = max(maxSum, curSum)`。

```python
def maxSubArray(nums):
    cur_sum = max_sum = nums[0]
    for num in nums[1:]:
        cur_sum = max(num, cur_sum + num)
        max_sum = max(max_sum, cur_sum)
    return max_sum
```

```java
public int maxSubArray(int[] nums) {
    int curSum = nums[0], maxSum = nums[0];
    for (int i = 1; i < nums.length; i++) {
        curSum = Math.max(nums[i], curSum + nums[i]);
        maxSum = Math.max(maxSum, curSum);
    }
    return maxSum;
}
```

**话术示例**
这道题用 Kadane's 算法，O(n) 一遍扫描。维护两个变量：`curSum` 表示以当前元素结尾的最大子数组和，`maxSum` 是全局最大值。对每个元素判断：是从这里重新开始更大，还是接着前面的子数组更大，取 max；然后更新全局最大。边界是用第一个元素初始化两个变量，避免全负数时返回 0 的错误。

**问题**

### 16. 使用哪些 AI 工具及功能【8.5 分】

- 自配代理访问 Claude（claude-sonnet-3.7/4），39 美元/月 1500 次请求。

**评价**
- 优点：介绍了工具层（Cursor）、规范层（rules 体系）、能力层（MCP），有系统性；使用模式区分体现了成熟的 AI 使用习惯。
- 不足：Claude 在 IDE 里的使用没有说清楚是 Cursor 内置还是单独 Claude.ai/API；MCP 的具体接入方式（`mcp.json` 配置）可以多一句。

**参考答案要点**
- **工具层**：Cursor 内置 Claude，后端通过 Cursor 或 Claude.ai 使用。
- **规范层**：`.cursorrules`（全局配置，项目技术栈、目录结构、代码规范）+ `.cursor/rules/`（任务级，覆盖具体模块的规范和流程）；规则先由 AI 从已有代码归纳，人工审核后使用，后续发现例外时追加补充。
- **能力层**：MCP 通过 `mcp.json` 配置服务，Figma MCP 让 AI 直读设计稿，减少信息传递损耗。
- **使用模式**：Agent mode（主）→ Plan mode（大任务）→ Chat mode（知识问答）。
- **成本管理**：Pro 39 美元/月 1500 次；对于大公司来说需要考虑团队级账号或 API 计费；个人使用可自托管代理。

**话术示例**
主要用 Cursor，后端也在 Cursor 里用内置的 Claude 模型。Cursor 里最核心的是两层规则体系：一层是 `.cursorrules` 做全局配置，把项目技术栈、目录结构、代码规范写进去，每次 AI 改代码都能看到这些上下文；另一层是任务级 rules，放在 `.cursor/rules/` 里，每个模块或功能类型一个文件，比如"前端组件怎么拆"、"后端接口层怎么写"，这些规则是先让 AI 根据已有代码自己归纳一版，我审核后定稿，后续发现不符合的地方随时追加。MCP 这块我接了 Figma，配置好 `mcp.json` 后 AI 可以直接读设计稿，不用截图，减少了很多沟通损耗。使用模式上，日常开发主要用 Agent mode，让 AI 自己读代码自主修改；任务特别大、改动面广的时候，先切 Plan mode，让 AI 先出方案，我确认没问题再让它执行；纯知识性的问题用 Chat mode。

### 17. AI 编程最佳实践【8.5 分】

**问题**
用 AI 编程，你觉得最佳实践是什么？

**我的答案要点**
- **成本管控**：Claude Pro 39 美元/月 1500 次请求，基本满足个人月度开发需求；之前用 20/60 美元订阅，超量后按次计费，不划算。
- **降低沟通成本**：用 MCP 和 rules 把提示词持久化，减少每次重复沟通的成本，提高 AI 输出精确度；rules 也是让 AI 先写、人来审核。
- **人机分工**：
  - AI 最大缺陷是上下文窗口限制（项目大时容易"牵一发而动全身"）。
  - 人负责：骨架搭建（最核心决策）、任务分配、最终审核和整体把控。
  - AI 负责：具体实现、机械化任务、样板代码。
- **策略总结**：人把控项目整体，AI 负责提效；骨架由人来，作业交给 AI。

**评价**
- 优点：回答从成本、沟通效率、人机分工三个维度切入，有实战感，不是泛泛而谈。
- 不足：没提到代码审查的具体方式（如 Git diff 配合 AI review）、安全/隐私代码不传 AI、上下文窗口耗尽的具体应对技巧（如分支任务、定期 summarize context）。

**参考答案要点**
- **成本**：个人开发 Claude Pro 39 美元/月；团队可考虑 API 计费 + 用量监控或 Claude Team 账号。
- **沟通效率**：rules 体系持久化规范，避免每次重复描述；MCP 减少人工传递设计/文档信息的步骤；提问时给出具体上下文（文件路径、函数名、期望输出），减少来回确认。
- **人机分工**：人负责架构、边界、安全和审核；AI 负责实现细节和样板代码；大任务先 Plan mode 看方案，避免 AI 改动超出预期。
- **上下文管理**：任务尽量拆小，避免单次对话处理过长；切换任务前用 "summarize context" 让 AI 压缩上下文；敏感代码（密钥、私有算法）不传入 AI 上下文。
- **代码审核**：对 AI 生成的代码做 diff review，重点看业务逻辑正确性和边界处理，不能全凭 AI 自查。

**话术示例**
我觉得 AI 编程的最佳实践核心是三件事：成本管控、沟通效率和人机分工。成本上，个人开发 Claude Pro 39 美元一个月 1500 次请求基本够用，团队用的话可以评估 API 计费加用量监控。沟通效率用 rules 体系来解决——把项目规范和任务规范都固化到规则文件里，不用每次重复描述；MCP 接入设计工具让 AI 直读，减少人工传图。提问时给足上下文（文件路径、期望输出），减少 AI 猜测和来回确认的次数。人机分工上，AI 最大的问题是上下文窗口短，项目大了容易改一处动全局，所以人必须把控骨架决策——架构、组件边界、数据流——然后把具体实现交给 AI，最后人来 review diff，重点检查业务逻辑和边界处理，不能只靠 AI 自查。总结就是：骨架由人来，作业交给 AI，人来最终把控。

### 4.2 技术原理表述

| 问题 | 正确说法 |
| --- | --- |
| React Fiber 描述不准确，说成了"把虚拟节点作为非本节点处理" | Fiber 的核心是**可中断的增量渲染 + 优先级调度**；链表结构代替树，每帧约 5ms 的时间片，高优先级任务可打断低优先级渲染 |
| Vue 3 diff 优化说成"跳过静态节点" | 更准确的说法是：编译阶段给**动态节点打 PatchFlag**，静态节点做**hoistStatic 提升**（只创建一次 VNode），运行时只 diff 有 flag 的节点 |
| TS 常用语法只提了 type/interface/声明合并 | 补充：泛型、工具类型（Partial/Pick/ReturnType/Omit）、类型守卫（is/instanceof/in）、条件类型 |
