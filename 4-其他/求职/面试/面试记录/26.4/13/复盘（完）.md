### 5. Seata 分布式事务原理 【5.5 分】

**问题**
分布式事务怎么用？能讲一下吗？

**我的答案要点**
- 主流框架是 Seata
- 有"事务协调者"和"事务管理者"
- 默认模式：所有事务通过"管理者"执行，记录每个节点状态
- 失败时协调者通知各参与者回滚
- 每个微服务的数据库里会生成 undo_log 表，记录操作时的数据快照，回滚时生成反向 SQL

**评价**
- 优点：Seata AT 模式的整体流程说到了（二阶段提交、undo_log、反向 SQL 回滚），方向正确。
- 不足：角色术语不准确（应为 TC / TM / RM，不是"协调者/管理者"这种笼统说法）；未说清楚一阶段已经本地提交只是释放了行锁、二阶段才做真正的全局提交/回滚；"安度log"发音不准，应为 undo log。

**参考答案要点**
- Seata 三个角色：
  - **TC**（Transaction Coordinator）：独立部署的 Seata Server，管理全局事务状态
  - **TM**（Transaction Manager）：标注 `@GlobalTransactional` 的服务，负责开启/提交/回滚全局事务
  - **RM**（Resource Manager）：各微服务，负责本地事务操作并向 TC 上报
- **AT 模式**两阶段：
  - 一阶段：RM 执行本地 SQL，**本地提交**（释放行锁），同时记录 **before image** 和 **after image** 到 `undo_log` 表
  - 二阶段-成功：TC 通知各 RM 删除 undo_log，完成清理
  - 二阶段-失败：TC 通知各 RM 根据 before image 生成**反向 SQL** 进行数据回滚，并删除 undo_log
- 适合对隔离性要求不极致的场景；高隔离性场景可用 TCC 模式（代价是侵入业务）

**话术示例**
Seata 里有三个核心角色：TC 是独立运行的事务协调服务器，TM 是发起全局事务的那个服务，RM 是各个参与者微服务。

流程是这样的：TM 在方法上加 `@GlobalTransactional`，向 TC 申请开启全局事务。各 RM 在执行本地 SQL 之前，Seata 会自动拦截，记录操作前后的数据快照（before image 和 after image）到本地的 undo_log 表，然后本地提交、释放行锁。

如果所有 RM 都成功，TC 通知大家删掉 undo_log，事务结束。如果有一个 RM 失败，TC 通知所有 RM 根据 before image 生成反向 SQL，把数据回滚回去。

我们用的是 AT 模式，侵入性低，业务代码改动小；如果对隔离性要求更高，可以考虑 TCC 模式，但需要手写 try/confirm/cancel 三个方法，代价更高。

### 6. 不用分布式事务的方案——分布式锁 【3 分】【错】

**错误点**：候选人提出"用锁把线程锁住"，这是 JVM 内的本地锁（synchronized/ReentrantLock），在多实例部署场景下完全无效；面试官提示"多个实例"后候选人表示不了解，未能说出**分布式锁**。

**问题**
如果不用分布式事务，还有什么其他方法？多个实例部署的情况下锁怎么用？

**我的答案要点**
- 可以用锁，执行时锁住线程，执行完释放
- 多实例情况下不了解

**评价**
- 优点：有"用锁"的基本方向意识。
- 不足：与多实例部署场景完全对不上，说的是 JVM 本地锁；分布式锁的概念（Redis SETNX / Redisson / ZooKeeper）是这里的核心考点，完全没答出来。

**参考答案要点**
- **本地锁的局限**：`synchronized`、`ReentrantLock` 只在单个 JVM 进程内有效，多实例部署时各自有独立锁，无法互斥
- **分布式锁**：用一个所有实例都能访问的外部存储实现互斥
  - **Redis 实现**：`SET key value NX PX milliseconds`，原子性地设置，持有锁的实例执行完删除；推荐用 **Redisson**，封装了 watchdog 自动续期、可重入、公平锁等
  - **ZooKeeper 实现**：临时顺序节点，谁的序号最小谁持有锁，节点删除后下一个节点收到通知；更可靠但性能低于 Redis
- 除分布式锁之外，也可以通过**数据库乐观锁**（version 字段 CAS 更新）来保证数据一致性，适合写冲突不频繁的场景

**话术示例**
如果不用分布式事务，可以用分布式锁来保证同一时刻只有一个实例在操作某份数据。本地的 synchronized 或 ReentrantLock 在多实例部署下是没用的，因为每个实例有自己的 JVM，锁不共享。

分布式锁通常用 Redis 来做，最简单的是 `SET key NX PX` 命令，原子性地抢锁，执行完之后删除 key 释放锁。生产上推荐用 Redisson，它封装了锁续期（watchdog）、可重入、解锁安全性等问题。如果对一致性要求更高，也可以用 ZooKeeper 的临时顺序节点来实现，但性能比 Redis 低一些。

### 8. 线程池使用场景 【8 分】

**问题**
Java 多线程池你用的哪个？一般用线程池都做些什么？

**我的答案要点**
- 用自定义线程池
- 场景：JMeter 压测发现某接口最慢，定位到是 CPU 密集型的数学插值计算（矩阵运算）
- 判断 CPU 密集型后，发现算法可分片并行计算（对格点矩阵做插值，可切片）
- 自定义线程池：核心线程数 2，最大线程数 = min(CPU 核数, 8)
- 拆片计算后合并结果

**评价**
- 优点：有具体场景（压测发现慢接口 → 根因分析 → 优化方案），逻辑链完整；CPU 密集型 vs IO 密集型的判断、线程数公式都说出来了，说明理解而非死记。
- 不足：没有说明最终性能提升效果（如响应时间从 Xms 降到 Yms）；线程池的拒绝策略、队列类型没提到。

**参考答案要点**
- **工具**：`ThreadPoolExecutor` 自定义，不用 `Executors` 工厂，原因是参数透明、可控
- **参数设计**：
  - 核心线程数：2（保底常驻）
  - 最大线程数：`Math.min(Runtime.getRuntime().availableProcessors(), 8)`
  - CPU 密集型公式：最大线程数 ≈ CPU 核数；IO 密集型：CPU 核数 × 2
- **任务拆分**：将矩阵按行或按块切片，分配给不同线程并行计算，最后合并（见第 9 题）
- **补充可提**：拒绝策略（CallerRunsPolicy 较安全）、队列选 LinkedBlockingQueue 并设上限

**话术示例**
我们当时用 JMeter 做压测，发现一个接口响应最慢，进去看是一段矩阵插值计算，是纯 CPU 密集型的。判断是 CPU 密集型之后，看了一下这个算法能不能拆片并行——插值矩阵是可以按块拆分的，各块互不依赖，最后再合并结果。

我就写了一个自定义的 ThreadPoolExecutor，核心线程数设 2，最大线程数取当前 CPU 核数和 8 的最小值，尽量不把 CPU 打满。把矩阵切成几片，每一片扔给线程池执行，最后用 CompletableFuture 等所有片都完成再合并。

### 9. 并发任务如何等待全部完成后合并结果 【6.5 分】

**问题**
你把计算拆成了几片并发去执行，你怎么能知道所有线程都执行完了，然后合到一起？

**我的答案要点**
- 用某个方法，类似前端的 Promise，点一下就能拿到结果，拿不到就会一直等

**评价**
- 优点：方向正确，知道有"阻塞等待结果"的机制，类比 Promise 体现了理解而非背题。
- 不足：没说出 `Future` / `CompletableFuture`；没说出 `.get()` 会阻塞等待；没说出 `CompletableFuture.allOf().join()` 这种等待所有任务完成的标准写法。

**参考答案要点**
- **`Future<T>`**：`ExecutorService.submit()` 返回 Future，调用 `.get()` 会阻塞直到该任务完成并返回结果
- **`CompletableFuture`**（推荐）：
  - `supplyAsync(() -> compute(slice), pool)` 提交任务，得到 `CompletableFuture<Result>`
  - 多个 future 用 `CompletableFuture.allOf(f1, f2, f3).join()` 等待全部完成
  - 然后用 `f1.get(), f2.get(), ...` 收集各片结果，合并
- **`CountDownLatch`**（也可以）：构造时传入任务数，每个线程完成后 `latch.countDown()`，主线程 `latch.await()` 阻塞等待归零

**话术示例**
提交任务用 `CompletableFuture.supplyAsync()` 加上自定义线程池，每一片计算返回一个 CompletableFuture。全部提交之后，用 `CompletableFuture.allOf(f1, f2, f3).join()` 等待所有任务完成——这一步会阻塞主线程，直到所有片都计算完。之后再挨个 `.get()` 拿结果，拼到一起。

也可以用 `CountDownLatch`，构造时传入任务数，每个线程完成后调一次 `countDown()`，主线程调 `await()` 等到计数归零再继续。两种都能做，CompletableFuture 更灵活，还可以链式处理后续逻辑。

### 10. @Transactional 注解失效场景 【2.5 分】【错】

**错误点**：候选人仅提到"AOP 会失效"，既无具体场景也无准确解释；实际上是 Spring AOP 代理机制在特定场景下无法拦截方法调用，导致事务注解形同虚设。

**问题**
`@Transactional` 注解有些场景下会失效，能讲一下哪些场景下会失效？（面试官举例：加在 private 方法上；方法内部调用第二个方法）

**我的答案要点**
- 提到"AOP 会失效"，但没有给出具体场景
- 追问后表示"没遇到过"

**评价**
- 优点：知道与 AOP 有关，方向勉强对。
- 不足：这是 Spring 事务的高频考点，没有答出任何具体场景，失分严重。

**参考答案要点**
Spring `@Transactional` 失效的核心原因是 **AOP 代理无法拦截**，常见场景：

1. **private / protected 方法**：Spring AOP 基于动态代理（JDK / CGLIB），无法代理非 public 方法，注解无效
2. **同类内部方法调用（自调用）**：方法 A 调方法 B，B 上加了 `@Transactional`，但 A 内部直接调 `this.B()`，走的是对象本身而非代理对象，拦截器不触发
3. **异常被 catch 吞掉**：事务回滚需要异常抛出到代理层，如果方法内部 try-catch 了异常且没有重新抛出，Spring 不知道发生了异常，不会回滚
4. **异常类型不匹配**：默认只回滚 `RuntimeException` 及其子类；如果抛的是受检异常（Checked Exception）却没有配置 `rollbackFor`，不会自动回滚
5. **非 Spring 管理的 Bean**：`new` 出来的对象，不走 Spring 容器，没有代理，事务注解无效
6. **多线程**：事务绑定在 ThreadLocal 上，跨线程调用时新线程没有当前事务

**话术示例**
`@Transactional` 失效的根本原因是 Spring AOP 代理没有生效，具体场景有这几种：

第一，加在 `private` 方法上会失效，因为动态代理只能代理 public 方法。

第二，同一个类里面方法 A 调方法 B，B 上加了注解但仍然失效——因为 A 调的是 `this.B()`，走的是对象本身而不是代理对象，代理的拦截器根本没触发。

第三，异常被 catch 吞掉。事务回滚要求异常抛到代理层，方法里把异常全 catch 掉了，Spring 不知道出了问题，不会触发回滚。

第四，抛的异常不是 `RuntimeException`，是受检异常，但又没配 `rollbackFor`，Spring 默认不回滚受检异常。

### 11. MySQL InnoDB 索引底层数据结构 【7.5 分】

**问题**
MySQL InnoDB 存储引擎底层用的什么数据结构？

**我的答案要点**
- B+ 树
- 与二叉树的区别：叉多，层级浅，减少 IO 次数
- 建索引后查询从全表扫描变成按序的树查询，提升查询速度

**评价**
- 优点：答出了 B+ 树，能说出"叉多层级少"这个本质，方向正确。
- 不足：没有说出 B+ 树与 B 树的区别（叶节点存数据 + 叶节点之间有双向链表）；没有提到聚簇索引 vs 非聚簇索引（主键索引 vs 二级索引）。

**参考答案要点**
- **B+ 树**：每个节点可以有多个子节点（阶数 = 页大小 / 键大小），比二叉树层级浅，磁盘 IO 次数少
- **B+ 树与 B 树的区别**：
  - B+ 树只在**叶节点**存实际数据，非叶节点只存键（减少非叶节点大小，每页放更多键，树更矮）
  - 叶节点之间有**双向链表**，支持高效范围查询
- **聚簇索引**：InnoDB 主键索引，叶节点直接存整行数据；表数据按主键顺序物理存储
- **二级索引**：叶节点存的是主键值，查询时先从二级索引找主键，再回主键索引（**回表**）

**话术示例**
InnoDB 用的是 B+ 树。B+ 树和普通二叉树的区别是它每个节点可以有很多个子节点，所以整棵树很矮，通常三四层就能覆盖几千万行数据，磁盘 IO 次数非常少。

B+ 树和 B 树还有个区别是 B+ 树只在叶节点存实际数据，非叶节点只存键，所以每个非叶节点能放更多的键，树更矮；叶节点之间还有双向链表，范围查询直接沿链表扫，效率很高。

InnoDB 里分聚簇索引和二级索引。主键索引是聚簇的，叶节点存的是整行数据；二级索引叶节点存的是主键值，查完二级索引还要拿主键去主键索引再查一次，这叫回表。

### 12. 如何给表设计索引 【8.5 分】

**问题**
如果给一个表加索引，你一般怎么考虑怎么加？

**我的答案要点**
- 先压测发现瓶颈，通过慢查询日志定位具体慢 SQL
- 分析多条慢 SQL 的共有特征，尽可能让一个索引覆盖更多请求
- 最左前缀原则：索引最左列不能有不等判断或前置通配符（`LIKE '%xxx'`）
- 覆盖索引：高频查询的字段全部纳入索引，避免回表

**评价**
- 优点：有完整的分析流程（压测 → 慢查询 → 设计原则 → 覆盖索引），回答逻辑清晰，实践性强，这道题答得很好。
- 不足：可以补充"不要在低基数字段建索引（如性别、状态）"；联合索引列顺序的选择原则（区分度高的列放左边）。

**参考答案要点**
- **定位**：开启慢查询日志（`slow_query_log`），分析 `EXPLAIN` 输出（type、key、rows）
- **设计联合索引**：
  - 把高频 WHERE 条件的字段组合成联合索引
  - 遵循**最左前缀**：查询条件必须从联合索引最左列开始，中间不能断，左边不能有范围查询（`>`/`<`/`!=`/`LIKE '%...'`）
  - 区分度高的列（基数大）放左边，提高过滤效率
- **覆盖索引**：SELECT 的字段全在联合索引里，直接从索引返回，不回表
- **注意事项**：
  - 不在低基数字段单独建索引（如 status 字段值少，区分度差）
  - 索引不是越多越好，会影响写入性能（每次写入要维护索引 B+ 树）
  - 对于大表加索引，考虑用 `pt-online-schema-change` 或 MySQL 8.0 instant DDL 避免锁表

**话术示例**
我一般先用压测工具找到慢接口，再用 MySQL 的慢查询日志加 EXPLAIN 定位到具体的慢 SQL。

设计索引的时候，我会把高频的 WHERE 条件抽出来，看多条慢 SQL 有没有共同的过滤字段，尽量用一个联合索引覆盖大多数查询。联合索引要注意最左前缀——查询一定要从最左列开始，左边字段不能有范围查询或前置通配符，不然索引会中途失效。

如果查询的字段就那几个，我会把它们都放进索引，这样查询可以直接从索引里拿数据，不用回表，性能会更好。

### 13. Redis 使用场景与缓存过期处理 【7 分】

**问题**
你们 Redis 存什么？缓存数据过期了怎么办？

**我的答案要点**
- 存后端处理好的气象数据（矩阵计算结果）
- PNG 等静态文件走前端强缓存，不入 Redis
- 矩阵数据计算耗时，算好后存 Redis，后续直接读取，一般设 1 个月过期
- 过期后再来请求，重新从文件读取计算，结果再存一次 Redis

**评价**
- 优点：说清楚了"为什么用 Redis 缓存这类数据"（计算耗时，结果稳定），缓存策略有依据（历史数据不变，TTL 设长）。
- 不足：没有用术语"缓存穿透""缓存击穿""缓存雪崩"点题，机会有点可惜；没有提到加互斥锁防止缓存重建时的并发打穿数据库/计算层。

**参考答案要点**
- **缓存对象**：计算耗时且结果稳定的数据（如矩阵插值结果），设较长 TTL（如 1 个月）
- **缓存 Miss 处理（旁路缓存，Cache-Aside）**：
  1. 查 Redis，未命中
  2. 从数据源（文件/数据库）读取并计算
  3. 写回 Redis，设 TTL
  4. 返回结果
- **注意：缓存击穿**（某个热点 key 过期，大量请求同时打到计算层）：加分布式互斥锁，只允许一个线程重建缓存，其他等待
- **缓存雪崩**（大量 key 同时过期）：TTL 加随机扰动，避免集中失效
- **缓存穿透**（请求不存在的数据，缓存和数据源都没有）：缓存空值或使用布隆过滤器

**话术示例**
我们 Redis 主要缓存的是计算耗时的矩阵数据，这类数据一旦生成就不会变，非常适合缓存。具体来说是后端把格点矩阵算好之后存进 Redis，TTL 设 1 个月；前端请求来了先查 Redis，命中直接返回，不命中再重新算然后写回 Redis。

这种场景有一个需要注意的地方：某个 key 过期之后如果同时来了大量请求（缓存击穿），会一起打到计算层，把服务或数据库打挂。我们这个场景请求量不大，基本不会遇到，但标准做法是在重建缓存时加一个分布式互斥锁，只让一个请求去重建，其他等它完成。

### 14. MQ 消息可靠性保障 【6 分】

**问题**
你们用 MQ 保证不丢消息、消息不重复发送是怎么做的？

**我的答案要点**
- 重复消息：网络抖动可能导致重复，用幂等性解决——相同操作效果一致，重复的操作直接丢弃
- 不丢消息：配置死信队列，把"认为是丢弃的消息"重新投回队列

**评价**
- 优点：幂等性的概念方向是对的；死信队列有提到，说明有一定了解。
- 不足：不丢消息和死信队列是两件事，混在一起说了；防丢消息的正确手段是**生产者 confirm + 消息持久化 + 消费者手动 ACK**，这些都没说到；死信队列（DLQ）的作用是处理无法正常消费的消息（失败多次后转移），不是防止消息丢失的主要手段。

**参考答案要点**
**防止消息丢失**（三段保障）：
1. **生产者侧**：开启 confirm 机制（RabbitMQ）或 acks=all（Kafka），Broker 确认收到才认为发送成功；失败则重试
2. **Broker 侧**：开启消息持久化（队列 + 消息都设为 durable/persistent），保证宕机后消息不丢
3. **消费者侧**：关闭自动 ACK，改为**手动 ACK**，业务处理成功后再 ACK；处理失败则 Nack 让消息重新入队或进死信队列

**防止重复消费（幂等）**：
- 网络重试、消费者重启都可能导致同一条消息被消费多次
- 方案：每条消息带唯一 ID（如业务 UUID），消费前查 Redis 或数据库是否已处理，已处理则跳过
- 或者设计业务操作本身幂等（同一 ID 的 SQL 用 `INSERT IGNORE` / `ON DUPLICATE KEY` 等）

**死信队列**：
- 处理**无法被正常消费**的消息（消费失败超次数 / 消息过期 / 队列满）
- 死信队列里的消息可以告警、人工处理或自动重试，防止"消息卡住"

**话术示例**
MQ 消息可靠性我分三块来讲。

第一是生产者侧，开启 confirm 机制，发出去的消息必须等 Broker 回一个确认，没确认就重试，从源头防止丢失。

第二是 Broker 侧，队列和消息都设成持久化，服务重启之后消息还在。

第三是消费者侧，把自动 ACK 改成手动 ACK，业务逻辑处理完之后才 ACK，如果处理失败就 Nack，让消息重新入队或者转进死信队列，人工介入处理。

防止重复消费的话，核心是幂等性。每条消息带唯一 ID，消费之前先查 Redis 看这条 ID 处理过没有，处理过就跳过；或者把写数据库的操作本身设计成幂等，比如用 `INSERT IGNORE`。

死信队列是另一回事，它是专门处理消费多次失败或者过期的消息，把这些处理不了的消息转移到一个单独的队列里，方便告警和人工处理，不是主要的防丢手段。
