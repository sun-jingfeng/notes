### 3. 智能体工作流搭建细节【8.5 分】

**问题**
你是怎么去搭建智能体的整个工作流的？

**我的答案要点**
- 前端传 4 个参数给后端：气象要素、时间轴时间、地图经纬度、用户自定义提示词
- 后端先根据气象要素+时间找到原始数据，再将原始数据+要素+提示词+地名+经纬度范围一起发给模型
- 工作流节点一：地名转化（经纬度 → 地名，绑定地名转化工具）
- 工作流节点二：气象要素路由（根据要素把任务路由到对应垂直节点）
- 每种差距较大的气象要素单独声明一个模型，绑定专属工具，垂直化处理
- 工作流节点三：结构化输出（硬编码，保证输出格式固定）
- FastAPI 封装成服务返回 Java，Java 再返前端

**评价**
- 优点：节点拆解清晰，数据流向完整，路由思路符合工程实践，"垂直化处理"的思路表达到位。
- 不足：没有提工作流引擎本身的特性（LangGraph 的 StateGraph、节点之间的状态传递方式）；模型层面的提示词设计没有展开。

**参考答案要点**
- 输入数据：气象要素 + 时间 + 经纬度 + 用户 prompt。
- LangGraph 基于 StateGraph 构建，每个节点是一个 function，节点间通过共享 State 传数据。
- 节点顺序：地名转化节点（工具调用）→ 路由节点（conditional_edge 按要素分流）→ 各要素垂直处理节点（各自绑定数据处理工具）→ 结构化输出节点（Pydantic 模型或 output_parser 约束格式）。
- 系统级提示词：放全局约束（格式、语气、长度限制），权重高于用户输入，减少幻觉。
- FastAPI + uvicorn 部署，Nacos 注册服务供 Java 调用。

**话术示例**
工作流是用 LangGraph 的 StateGraph 搭的，每个节点是一个函数，节点之间通过共享状态传数据。第一个节点做地名转化，调一个地名转化的工具，把经纬度范围换算成可读的地名。然后是路由节点，用 conditional_edge 按气象要素把任务分流，因为降水和风速的数据结构差异比较大，我给每类要素单独建了一个模型，绑了自己的工具，这样任务到了那个节点，模型收到的上下文是足够垂直聚焦的，幻觉也少。最后是结构化输出节点，用 Pydantic 模型约束输出格式，保证文案的节奏是固定的。整个服务用 FastAPI 封装，通过 Nacos 注册进 Java 微服务。

### 6. 模型幻觉的处理策略【7.5 分】

**问题**
你们接的是线下部署的模型，实际使用中有没有出现幻觉？你是怎么解决的？

**我的答案要点**
- 所有模型都会有幻觉，无法完全消除
- 提示词分层：系统级提示词（权重更高，模型"记"得更深）> 用户提示词；重要约束放系统级
- 结构化输出：硬编码 + API 约束，从底层保证输出格式符合节奏
- 任务分流：LangGraph 路由，每类要素单独模型+工具，任务足够垂直聚焦 → 减少无关联想

**评价**
- 优点：三个维度（提示词分层、结构化输出、任务垂直化）都覆盖了，思路清晰。
- 不足：没有提 RAG（如注入气象术语知识库）；没有提温度值（temperature）控制；没有提对输出做后验校验；提示词的角色（system/user/assistant）描述不够精确，"AI型提示词"表述不规范。

**参考答案要点**
- **提示词分层**：System prompt 放全局约束和格式要求（权重最高）；User prompt 带运行时参数；避免在 User 层放容易被覆盖的限制。
- **结构化输出**：用 Pydantic 模型或 `with_structured_output` 约束格式，从解析层保证输出可机器读取，不依赖模型自觉。
- **任务垂直化**：LangGraph conditional_edge 路由，每个要素节点的系统提示词高度专注于该要素，减少跨领域联想。
- **温度控制**：生成文案类任务 temperature 调低（0.2~0.4），减少随机性。
- **后验校验**：输出后可做关键字段校验（地名是否在合理范围、数值是否在气象合理区间），异常则重试或走降级。

**话术示例**
幻觉这个问题我主要从三个层面去控制。第一是提示词分层，重要的格式要求和约束我放到 System prompt 里，它的权重比 User prompt 高，模型不容易遗忘；第二是结构化输出，我用 Pydantic 模型约束输出字段，相当于在解析层加了一道硬性保证，不靠模型自觉；第三是任务垂直化，LangGraph 路由之后，每个节点的上下文只包含当前要素的数据和提示词，任务足够聚焦，跑偏的概率就低很多。另外生成类任务我会把 temperature 调低，0.2 到 0.4 之间，减少随机性。

### 9. 气象数据多线程 + 缓存性能优化【8.5 分】

**问题**
你在气象预警智能体里，是怎么设计多线程与缓存机制来提升数据处理效率的？

**我的答案要点**
- 性能测试：10秒1000次请求，发现多个接口报错，顺日志定位到一个公共微服务的某接口特别慢
- 根因：克里金插值算法计算约需 2 秒，CPU 密集型任务
- 解决一：自定义线程池（核心线程数=2，最大线程数=min(CPU核数, 8)），用 Future 将计算拆片并行后组装，耗时从 ~2s 降至几百毫秒
- 解决二：Redis 缓存计算结果（气象要素+时间 → 唯一计算结果，无需重复计算）
- 解决三：Sentinel 熔断降级策略，降级方案为低精度计算同节奏返回

**评价**
- 优点：问题定位思路清晰（日志→接口→算法类型），三种方案组合有层次感，线程池参数有依据（CPU密集型取CPU核数），Sentinel 降级方案落地可信。
- 不足：Future 组装的细节（CompletableFuture vs Future + get）没有说；线程池用了哪个实现（ThreadPoolExecutor 还是 Spring TaskExecutor）没提；Redis TTL 策略没有说。

**参考答案要点**
- **性能分析**：CPU 密集型 → 多线程并行；I/O 密集型 → 异步/NIO；本题是算法类 CPU 密集型。
- **线程池**：`ThreadPoolExecutor`，核心线程数 = 2，最大线程数 = `Math.min(Runtime.getRuntime().availableProcessors(), 8)`；CPU 密集型任务最大线程数不超过 CPU 核数，避免线程切换开销。
- **并行拆分**：将克里金差值输入数据分片，每片提交一个 `Callable`，用 `CompletableFuture.allOf` 等待所有片段完成后合并结果。
- **Redis 缓存**：以 `气象要素+时间` 为 key，TTL 设为数据时效窗口（如 1 小时），命中缓存直接返回，跳过计算。
- **Sentinel 降级**：主策略是正常精度计算；超时/异常时触发降级，走低精度计算快速返回，保证接口不 504。

**话术示例**
这个问题是在压测时发现的，10 秒 1000 次请求有一批接口报错，顺日志追下去锁定到一个公共微服务里用了克里金插值算法的接口，单次计算大概 2 秒，把所有依赖它的接口都拖慢了。分析下来是 CPU 密集型，所以用多线程来解决：我建了一个自定义 ThreadPoolExecutor，最大线程数取 CPU 核数和 8 的较小值，把差值计算的输入数据分片，每片提交一个 Callable，最后用 CompletableFuture.allOf 汇总结果，计算时间从 2 秒左右降到几百毫秒。同时加了 Redis 缓存，以气象要素加时间戳做 key，相同参数的结果只算一次，后续命中缓存直接返回。还配了 Sentinel 熔断降级，降级方案走低精度计算，保证接口在极端情况下也有响应。

### 10. 前端产品问题的发现与修复（联播卡顿）【8 分】

**问题**
前端发现了产品问题，你怎么来做修复？举个例子。

**我的答案要点**
- 产品经理反馈联播不流畅，每次切换气象图卡顿约 0.5 秒
- 气象色斑图是 PNG，大小 100KB~500KB
- 分析：图片未预加载，每次播放才去请求，卡顿是网络等待
- 解决：预加载 + 浏览器强制缓存
- 实现：监听用户选中的时间和时间轴所有点位，有变化就预加载所有对应数据
- 数据生成后不会变更，所以配置强缓存（Cache-Control: max-age）
- 切换气象要素时中止上一次预加载，重新预加载新要素数据

**评价**
- 优点：问题定位准确（网络加载不是渲染慢），方案合理，强缓存选型有依据（数据不变），预加载时机设计合理。
- 不足：没有提 Prefetch/preload link 标签方案；没有提 Service Worker 做离线缓存；没有提监听使用的具体 API（watch/watchEffect 还是 ResizeObserver）；没有说弱网 fallback。

**参考答案要点**
- **问题定位**：联播卡顿 ≠ 渲染慢，排查网络面板，确认是图片请求等待时间长。
- **预加载策略**：
  - 监听时间轴状态（`watch` / 时间轴 store），用户交互触发时提前并发请求后续 N 帧数据。
  - 使用 `new Image()` 或 `fetch` + `responseType: blob` 提前拉取，让浏览器缓存资源。
- **强缓存配置**：服务端对色斑图静态资源设置 `Cache-Control: max-age=86400, immutable`（数据生成后 URL 固定不变）。
- **切换要素时取消**：AbortController 取消上一批 fetch，避免无效流量和内存泄漏。
- **优先级调度**：当前帧最高优先级，向后预加载 3-5 帧，向前不预加（用户极少倒播）。

**话术示例**
产品经理说联播时每次切换都会卡一下，大概 0.5 秒。我先排查了一下，打开 Network 面板看请求，每张色斑图是 100 到 500KB 的 PNG，播放到那一帧才去请求，卡顿是网络等待时间，不是渲染问题。解决思路是预加载加强缓存：我监听了时间轴的状态，用户一和时间轴交互，就立刻并发请求后续若干帧的图片，用 fetch 把图片拉下来让浏览器缓存；服务端对这些静态资源设强缓存，因为同参数的色斑图数据生成后不会变，URL 不变，所以缓存一直有效。切换气象要素时用 AbortController 取消上一批请求，重新预加载新要素的数据，避免无用流量。

### 11. 气象业务介绍与系统难点【7 分】

**问题**
你们气象平台主要做什么的？这套系统难点在哪？

**我的答案要点**
- 业务：为气象局/事业单位定制 PC 端气象可视化系统
- 界面：中间大地图 + 左右统计图表 + 底部时间轴 + 地图控件（经纬度测绘、截图、预警点位）
- 功能：选中气象要素+时间 → 地图展示预警信息（如色斑图展示降水强度）
- 难点一：参数联动，地图经纬度变化要求左右图表实时更新
- 难点二：缓存控制与性能，长时间联播需缓存管理，否则越来越慢
- 难点三：预警点位高性能操作，300+ 点播放时不能销毁重建，要用性能好的方式复用

**评价**
- 优点：业务描述清晰，难点举例具体、有技术细节支撑。
- 不足：被面试官"感觉比较简单"带跑了一点，可以更有力地还原复杂度；没有提地图（如 Leaflet/OpenLayers）的技术选型；预警点位没有说用了什么方案（如 Canvas 覆盖层 / WebGL）。

**参考答案要点**
- 业务定位：定制化政企气象可视化系统，类 PC 版墨迹天气，但附带实时预警、气象要素分析。
- 地图技术：通常基于 Leaflet 或 OpenLayers，结合气象专用数据格式（GRIB2、NetCDF）。
- 复杂度来源：
  1. **多维联动**：地图视窗变化 → 触发多个图表数据重新请求和渲染，需要统一状态树管理（Pinia/Vuex）。
  2. **高帧率渲染**：联播 0.5s/帧，在帧切换间隙完成下一帧数据加载，需预加载 + 强缓存。
  3. **大量覆盖物管理**：300+ 预警点位，频繁更新用 DOM 操作代价高，需要地图框架的 Canvas 层或 WebGL 渲染。
  4. **数据格式处理**：气象原始数据需要在前端做插值渲染（或后端处理后以图片/瓦片形式下发）。

**话术示例**
核心业务是给气象局或事业单位定制大屏可视化系统，用户通过时间轴和气象要素选择器，驱动地图上的色斑图、等值线、预警点位实时更新，配合左右的统计图表联动展示。难点在几个地方：第一是多维联动，地图视窗变了，左右十几个图表的数据都要跟着重新请求，状态管理的粒度要设计得很细；第二是联播的性能，0.5 秒一帧，要求下一帧在当前帧播放的间隙就完成预加载，稍有延迟就卡顿；第三是 300 多个预警点位的高频更新，用 DOM 直接删了重建代价太高，得走地图的 Canvas 图层或者复用已有对象，这部分对底层地图框架的理解要求比较高。

### 13. 用 AI 独立完成全栈项目的可行性【7.5 分】

**问题**
有没有考虑过一个人用 AI（Cursor）把整个项目做完？试过吗？

**我的答案要点**

- 当前项目任务量大才分给多人，如果体量合适一个人做得下来
- Python 是项目中现学现用的，有 AI 辅助后学习成本大幅降低
- 认为"一个程序员 + AI 完成一个完整小项目"是未来现实方向

**评价**
- 优点：有底气，有实际依据（Python 现学现用，AI 微服务全部独立完成），表达有前瞻性。
- 不足：没有量化"体量范围"（多大规模项目一个人能做）；"未来是很现实的"表达略显口语化，在正式面试场合可以更精练；没有落到与对方岗位的连接点上（对方是 API/SDK 产品，一个人做完小项目的能力正是他们需要的）。

**参考答案要点**

- 合理边界：单人全栈适合 2 周内能交付的体量（3~5 个实体/模块），再大需要拆分或专人负责某层。
- 对接岗位：对于提供 API 服务的平台，这种"一人打通前后端 + AI"的能力正是能快速验证产品 idea 的关键。

**话术示例**
