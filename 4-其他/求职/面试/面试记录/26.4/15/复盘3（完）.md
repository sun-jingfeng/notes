### 3. 项目中最有挑战的模块 【8 分】

**问题**：讲一下这两个项目里你觉得比较有挑战的模块？

**我的答案要点**

- 核心难点：5 个已有 / 新开发子项目需在统一父壳下展示
- 技术选型：iframe（微前端方案）
- 实现了：父子通信、样式隔离（自定义）、样式切换、权限控制
- 后端：微服务拆分，不同省份业务逻辑复用，性能优化
- 智能体：本地部署智能体，Python 微服务，集成到后端

**评价**

- 优点：覆盖了微前端难点的核心方向（通信、隔离、权限），有前后端 + 智能体的完整视角，体现了全栈能力。
- 不足：说的是"iframe"，但没有主动说清为什么选 iframe 而不是 qiankun/Module Federation；缺少量化指标（性能优化提升了多少？）；智能体部分点到为止，没有展开技术亮点。

**参考答案要点**

- 说清选型理由：5 个项目技术栈不统一，不需要共享运行时，选 iframe 的好处是隔离彻底、接入成本低，代价是通信需要 postMessage 封装。
- 父子通信：封装了 postMessage 协议层，定义消息类型枚举，统一收发。
- 样式隔离：每个子项目有独立 CSS 变量体系，主题切换通过父壳广播，子项目监听并更新变量。
- 权限：父壳统一鉴权，通过 postMessage 把权限 token 下发给子项目。
- 量化：若有指标应主动说出（如加载时间、首屏 FCP 优化幅度）。

**话术示例**

> 最有挑战的是微前端的架构搭建。当时要把 5 个不同技术栈的子系统整合到一个统一的父壳里，考虑到这几个项目要独立部署、隔离彻底、接入成本低，最终选了 iframe 方案。主要攻克了三块：第一是父子通信，我封装了一层 postMessage 协议，定义了统一的消息类型枚举，让父子之间事件传递标准化；第二是主题样式切换，各子项目用 CSS 变量维护主题，父壳广播主题变更，子项目监听并响应；第三是权限，父壳统一鉴权后把 token 下发给子项目，子项目不做独立鉴权。这套方案上线后稳定运行，后续接入新省份的版本基本零改动。

### 4. AI 开发工作流 【8.5 分】

**问题**：你能介绍一下你的开发工作流，比如用了哪些 AI 工具，过程是怎样的？

**我的答案要点**

- 前端用 Cursor，先拆组件结构、搭环境，细节组件让 Cursor + MCP（接 Figma）自动实现
- 后端用 IDEA 的 Copilot，先搭三层架构和配置，具体接口实现交给 AI
- 人负责：整体节奏把控、核心代码、任务拆分、项目级配置
- AI 负责：垂直碎片任务、样板代码、组件细节
- 通过 Rules/Instructions 定义项目规范，持续完善 Skills

**评价**

- 优点：工作流描述清晰，有明确的人机分工思路，提到了 MCP + Figma 的接法是加分亮点，规范化 Prompt 工程的概念也体现了对 AI 协作的深度思考。
- 不足：没有提到版本控制和代码 Review 的流程；「特色/车色」等 AI 工具名称表达不清晰（录音转写问题），正式表达应用标准名称（Cursor、Claude）。

**参考答案要点**

- 工具链：Cursor（前端）、IDEA + Copilot（后端）、Claude API / Copilot Chat（问答）
- 流程三段：① 人搭骨架（项目结构、路由、状态管理方案、接口规范）→ ② AI 填肉（组件实现、CRUD 接口、样板代码）→ ③ 人做 Review（逻辑正确性、安全、可维护性）
- MCP 接 Figma：Cursor 通过 MCP 直接读取 Figma 节点数据，生成组件代码，还原度高于截图传图。
- Prompt 工程：项目级 `.cursorrules` 定义技术栈规范，全局 Rules 定义编码风格，随项目演进持续迭代。
- 人的核心价值：上下文记忆、任务分解、架构决策、最终 Review。

**话术示例**

> 我的开发流程大概分三段。首先是人来搭骨架：前端我先把页面拆分成组件树、定好状态管理和路由方案，后端先搭三层结构和配置体系，这些由我手写，因为涉及到全局架构决策。然后是让 AI 填肉：前端用 Cursor，结合 MCP 直连 Figma，让它读取设计节点直接生成组件代码；后端用 IDEA 的 Copilot 写具体的接口实现和 Service 层逻辑。最后是我做 Review：AI 生成的代码我会检查逻辑正确性、潜在 bug 和可维护性问题。同时我会在项目里维护一套 `.cursorrules`，定义技术规范，这样 AI 输出越来越符合预期，返工率越来越低。

### 5. AI 工具使用中遇到的问题 【7.5 分】

**问题**：你用 Cursor、Copilot、Claude 这三个工具，遇到过哪些问题？

**我的答案要点**

- Claude（Anthropic 官方）：国内限制，需要国外手机号，闲鱼购号 100+/月，已不用
- Cursor：20 美元/高级模型额度太少，降级模型质量差，"不合适"，用得少
- Copilot（GitHub Copilot）：10 美元 300 次或 39 美元 1500 次，性价比高，现主力使用
- 提效策略：项目级 Rules + 全局 Instructions + 任务细拆

**评价**

- 优点：对工具的费用、额度、使用感受有清晰的一手经验，体现了真实使用而非只是了解，成本意识强。
- 不足：工具名称在口头表达中不够标准（"车牌乐特""偷拍了"等，转写问题）；没有提到使用这些工具遇到的**技术或质量层面**的挑战，比如上下文窗口限制、幻觉问题、代码一致性；面试官同时也在问技术挑战，只讲价格略显表浅。

**参考答案要点**

- 上下文窗口限制：AI 每次只记得当前会话，跨文件、跨会话的上下文需要人工维护，解法是通过 `.cursorrules` 和 `CONTEXT.md` 注入项目背景。
- 幻觉 / 错误率：AI 会自信地生成错误代码，必须结合单测或人工 Review，不能盲目信任。
- 成本控制：对不需要最强模型的任务（如格式化、注释生成）降级模型，核心逻辑用旗舰模型，降低浪费。
- 代码风格漂移：多人 + AI 协同时代码风格容易不一致，需要 ESLint / Prettier + Rules 约束。

**话术示例**

> 遇到的问题主要分两类，一类是成本，一类是质量。成本上，Claude 官方国内访问受限，我用过一段时间后因为续费成本高切换到了 GitHub Copilot，39 美元 1500 次请求，前后端都够用。质量上，最大的挑战是上下文窗口限制，AI 只记得当前会话，跨文件的架构决策它根本不知道，所以我会在项目里维护一个 `.cursorrules` 文件，把技术栈、命名规范、组件拆分规则全写进去，让 AI 每次生成都有上下文基础。另外 AI 偶尔会有幻觉，我的原则是核心逻辑必须自己过一遍，不能直接合并。

### 7. 测试协作流程与 AI 改进方案 【6 分】

**问题**：前后端和测试之间怎么协调？有没有 CI 流程？你觉得有什么可以改进的？

**我的答案要点**

- 现有流程：通过提测系统提交代码仓库地址 + 需求文档，测试拉代码跑功能测试，bug 以工作流形式分配，开发自己处理后标完成，测试复验
- 认为现有流程"挺高效""比较合规，有留痕"
- 结合 AI 改进方向：每个人用自己垂直领域的 AI 工具提效（开发用 Cursor/Copilot，测试让 AI 先跑一遍，产品经理让 AI 写需求文档）
- 激进方案：合并岗位，一个程序员用 AI 搞定前后端算法，产品/项目经理合为一人

**评价**

- 优点：能区分保守和激进两个层次思考，视角开阔；对现有流程的评价诚实，没有过度吹捧也没有无谓批评。
- 不足：对"是否有 CI/CD 流程"这个问题基本没有正面回答，说明公司可能确实没有自动化流水线，但也没有主动提出这是一个改进方向；提到"让 AI 先测"但没有具体说用什么工具、怎么实现（如 AI 驱动的 E2E 测试、接口自动化测试）；改进方案停留在概念层面，缺乏落地路径。

**参考答案要点**

- 补充 CI/CD 改进方向：在 GitLab/GitHub Actions 中加入自动化流水线，push 代码自动触发 lint、单测、构建，减少低级 bug 流入测试。
- AI 辅助测试的具体落地：用 AI（如 Playwright + AI 生成测试用例）做 E2E 自动化，或用 AI 根据需求文档自动生成测试用例初稿，测试人员复核而非从零写。
- 接口契约先行：后端接口用 OpenAPI/Swagger 定义，前端 mock 数据基于契约生成，减少联调等待时间。

**话术示例**

> 目前是通过提测系统走流程，有留痕，流程本身是合理的。但如果从效率角度看，有几个可以改进的地方：第一是引入 CI 流水线，在 push 代码时自动跑 lint 和单测，把低级 bug 挡在提测之前；第二是用 AI 辅助生成测试用例，比如基于需求文档让 AI 先出一版测试用例初稿，测试人员做审核补充，而不是从零写，节省人力；第三是接口契约前置，后端先用 Swagger 定义接口，前端基于 mock 并行开发，不等后端完成才联调，整体可以缩短 20%～30% 的联调周期。

### 8. 用 AI 提升整体研发效率 【8 分】

**问题**：假设以前研发效率是 100%，用了 AI 之后开发提升了 30%，但测试没变。如果想提升更多，你觉得应该怎么做？

**我的答案要点**

- 保守方案：每个角色用自己垂直领域的 AI 工具（开发用 Cursor/Copilot，测试先让 AI 测，产品用 AI 写需求文档）
- 激进方案：岗位合并，一人全栈（前端+后端+算法），产品/项目经理合并，UI 用 AI 生成设计

**评价**

- 优点：两层思考框架清晰，逻辑自洽；激进方案的"岗位合并"方向与 AI 时代趋势吻合，有前瞻性。
- 不足：没有提到"瓶颈识别"这一步——在提效讨论中，先找到瓶颈在哪（测试？需求变更？联调等待？）再针对性提效，更有说服力；激进方案中"产品/项目/UI 合并"的可行性需要结合具体场景说，不是所有公司都能这么做。

**参考答案要点**

- 先识别瓶颈：开发提效 30% 但测试没变，说明瓶颈在测试。下一步应优先对测试环节引入 AI（自动化测试生成、回归测试自动化）。
- 系统性提效路径：① 开发（已做）→ ② 测试（AI 辅助用例生成 + 自动化回归）→ ③ 需求澄清（AI 辅助文档生成、歧义检测）→ ④ 部署（CI/CD 自动化）
- 激进路径：全栈+AI 模式，减少交接耗时（交接是效率损耗的最大来源之一）。

**话术示例**

> 开发提效了但测试没变，说明现在的瓶颈已经从开发转移到了测试。我会优先在测试环节引入 AI，比如用 AI 根据需求文档自动生成测试用例初稿，测试人员只做审核和补充；再比如对高频的回归场景引入 Playwright 做自动化回归，这部分 AI 也可以辅助生成脚本。往更激进的方向走，就是缩短交接链路——减少角色边界，一个人用 AI 扛前后端，产品和项目经理合并，交接变少了，效率的提升是系统性的，不只是某一个环节快了。

### 9. 前端页面卡顿排查思路 【9 分】

**问题**：页面卡，打开开发者工具，你接下来怎么做？

**我的答案要点**

- 区分两种卡顿：帧率低型（字面上的卡顿）和内存泄露型（页面无响应/崩溃）
- 帧率低：用 Performance 面板录制，看火焰图，找超过 16.7ms 的任务片，定位到源码，针对性优化（避免重排重绘）
- 内存泄露：用 Memory 面板，关注 GC 后没有释放的内存，结合业务操作定位泄露时机
- 提到 60fps = 每帧 16.7ms

**评价**

- 优点：技术细节准确，帧率计算（60fps / 16.7ms）、火焰图分析、Memory 面板的 GC 节点观察，均是真实掌握的技能，表述清晰有深度，是本场最好的回答。
- 不足：可以再补充一个"快速定位起点"的方法——先看 FPS/CPU 利用率曲线找到问题发生的时间段，再放大到那一段做精细分析，而不是直接全量录制；内存泄露部分可以举一个常见场景（如未清除的定时器、未解绑的事件监听）。

**参考答案要点**

- 第一步先看 FPS 曲线和 CPU 利用率，定位到卡顿发生的时间区间。
- 帧率低排查：Performance 录制 → 火焰图 → 找 Long Task（>50ms 是标准，>16.7ms 是帧率影响）→ 定位到自己的代码 → 优化（防抖/节流/虚拟列表/Web Worker 分担计算）。
- 内存泄露排查：Memory → Heap Snapshot 对比 / Allocation Timeline → 找持续增长的对象 → 常见来源：未清除的 `setInterval/setTimeout`、未解绑的事件监听、闭包持有大对象、错误的 Vue/React 组件引用。
- 补充：卡顿也可能由主线程被 JS 阻塞，可考虑 Web Worker 迁移计算密集型逻辑。

**话术示例**

> 我会先看 Performance 面板里的 FPS 曲线，找到帧率明显下降的时间区间，然后放大那段录制，看火焰图里有没有超过 16.7ms 的长任务——16.7ms 是 60fps 每帧的时间预算，超过就会掉帧。如果找到了长任务，点进去可以定位到源码，再针对性优化，比如用防抖、节流、虚拟列表，或者把计算密集的逻辑移到 Web Worker。如果是那种过一会儿页面整个无响应的情况，我会打开 Memory 面板做堆快照，对比操作前后的对象数量，重点看 GC 之后还在增长的对象——常见来源是没清除的定时器、没解绑的事件监听，或者闭包意外持有了大对象。

### 12. 模仿竞品快速上线的方案 【7 分】

**问题**：假设要高保真模仿一个竞品前端，要求质量高且快，你会怎么做？

**我的答案要点**

- 功能分析：让 AI 分析竞品功能，列出功能清单
- 找竞品不足，顺手补上
- 设计图：截图或让 AI 生成，开发用成熟技术栈
- 前端用 Cursor/Copilot，后端用 IDEA Copilot，照着 AI 写样板代码
- UI：拆组件 → 连 Figma MCP → AI 实现细节
- 交互：AI 读需求文档，先实现，人运行一遍验收，再做代码 Review

**评价**

- 优点：流程比较完整，提到了 MCP 接 Figma 做还原，以及"人运行一遍 + 代码 Review"的质量保证环节，有落地可行性。
- 不足：对"怎么保证高保真还原"的回答停留在"UI 截图 + 肉眼复核"，没有提到像素对比工具、Storybook 组件隔离测试等工程手段；对"如何保证质量高"的回答不够有针对性，混入了很多功能分析内容，没有聚焦 UI/交互细节。

**参考答案要点**

- UI 还原：① 截图发给 AI 生成初版代码；② 用 Cursor 接 Figma MCP 获取精确标注；③ 人工视觉对比或借助像素对比工具（如 Percy、BackstopJS）做自动化对比。
- 交互还原：先整理竞品的所有用户操作路径（点击、hover、表单、拖拽），逐一实现并手动验证。
- 组件化思路：按竞品页面拆出复用组件，组件级别对比而非页面级别，粒度更细、更好保证一致性。
- 快速：组件并行开发，人维护组件拆分表，AI 各自实现，最后组装。

**话术示例**

> 我会分三步走。第一步，拿竞品截图或通过 MCP 接 Figma（如果竞品有设计稿的话）让 AI 生成组件代码初版，然后用 Cursor 逐组件对比截图做精修，保证 UI 还原度。第二步，梳理竞品的所有交互路径——点击、hover、表单、动画——逐一实现并自己手动跑一遍，有条件的话用 Playwright 跑 E2E 对比。第三步是组件化并行开发，我把页面拆成独立组件分配给 AI 实现，自己做最终的组装和视觉对比 Review。质量保证的核心是"组件级对比"而不是"页面级对比"，粒度越细、漏掉的细节越少。

### 13. 人与 AI 在开发中的分工 【8 分】

**问题**：在这个过程里，人主要做什么，AI 主要做什么？

**我的答案要点**

- 人：框架搭建、结果审核、任务拆分、项目级把控
- AI：垂直碎片任务、重复性工作、组件实现、接口实现
- 人把控项目节奏，因为 AI 上下文有限，记不住之前的决策
- AI 有时出错，人做最终把关，保证稳定性和可维护性

**评价**

- 优点：人机分工的理解准确有深度，特别是"AI 上下文有限、人来记忆上下文"这一点是真实痛点的总结，体现了对 AI 局限性的清醒认知。
- 不足：可以更进一步说"人的核心价值是什么"，即：架构决策、跨系统一致性、业务 domain 知识——这些是 AI 无法替代的；表达上略显散，可以更结构化。

**参考答案要点**

- 人的不可替代性：架构决策（技术选型、模块拆分）、业务理解（把业务 domain 翻译成代码逻辑）、跨会话上下文（AI 只记当前窗口，系统全局只有人知道）、最终质量把关（安全、可维护性）。
- AI 的优势区：公式化样板、高频重复、参考文档化实现、快速原型。
- 比喻：人是"架构师 + 项目经理"，AI 是"高速但需要方向的执行工程师"。

**话术示例**

> 我觉得人和 AI 的分工本质上是：人负责架构和判断，AI 负责执行和生产。人做的事情主要是三类：第一，架构决策——技术选型、模块拆分、接口契约，这些涉及系统全局，AI 看不到全貌；第二，业务 domain 转化——把甲方的需求转化为可以给 AI 下达的具体任务，这一步 AI 做不了；第三，质量把关——AI 会生成错误代码，特别是边界条件和安全性，必须有人审查。AI 主要做的是公式化的实现，比如组件 UI、CRUD 接口、样板配置，这类工作有规律可循、AI 速度远超人，交给它是最高效的。
