### 6. 智能体实现细节：工具与数据处理【7.5 分】

**问题**
智能体里注册了哪些工具？气象数据是怎么处理的？为什么用 PNG 存气象数据？

**我的答案要点**
- 工具：主要是各气象要素的数据读取与解析工具
- 气象数据用 PNG 存储（行业主流方案），因为相较纯文本/JSON，PNG 体积更小
- 降水数据：PNG 图片，从 RGB 位值读取气象数值，需还原放大系数
- 预警点数据：JSON 格式，数组包对象
- 部分数据需要双线性插值算法（差值算法）还原成矩阵数据
- Java 服务只传文件路径（延迟加载原则），到最后一步才真正读文件

**评价**
- 优点：数据处理逻辑讲得比较专业，说清楚了 PNG 存储的行业背景和解析原理，展现了真实的项目经验。
- 不足：对于插值算法（bilinear interpolation）的具体说明不够准确（说成"差值算法"）；工具的数量、类型边界没有清晰列出。

**参考答案要点**
- 工具分类：① 文件读取工具（按要素路由，按路径读取原始文件）② 数据解析工具（PNG 位值还原、双线性插值重采样、JSON 解析）③ 文案格式化工具
- PNG 存储原因：色斑图（热力图）数据用二维矩阵表示，PNG 压缩比高，传输和存储代价远低于同等数据量的 JSON；是气象行业主流方案
- 双线性插值（Bilinear Interpolation）：当原始数据网格分辨率与目标分辨率不匹配时，通过周围 4 个像素加权估算目标点的值
- 延迟加载：数据链路全程只传路径，到工具层才实际读取，降低带宽与内存开销

**话术示例**
智能体里注册的工具主要分三类：数据读取、数据解析和文案格式化。数据读取工具根据气象要素拿到对应文件路径后才去读文件，全程只传路径，减少带宽消耗。数据解析这边，降水这类空间分布数据用 PNG 存储，这是气象行业的主流方案，体积比 JSON 小很多；解析时从 RGB 通道位值里反算气象数值，有个放大系数需要还原，部分要素还要做双线性插值把稀疏网格重采样成目标分辨率的矩阵。预警点这类点位数据是 JSON 格式，直接解析就行。处理完的数据再喂给格式化节点，模型就能生成结构化文案了。

### 7. LangChain 与 LangGraph 的核心差异【6.5 分】

**问题**
LangChain 和 LangGraph 有什么核心差异？LangChain 自己的 Chain 机制能不能实现类似的图编排功能？

**我的答案要点**
- LangChain：实现单个节点的功能（模型调用、工具绑定、记忆管理等）
- LangGraph：把多个 LangChain 节点编排成有向图，每个节点是一个 LangChain 节点，自定义路由
- 对 LangChain 的 LCEL（Chain 链式调用）了解不够，被追问时无法回答

**评价**
- 优点：对 LangGraph 的图节点编排理解方向正确。
- 不足：LangChain 与 LangGraph 的关系表述不准确（LangChain 不只是"单节点"，也有 Chain 链式组合）；不了解 LCEL（LangChain Expression Language），是明显盲区。

**参考答案要点**
- LangChain：提供构建块（Models、Prompts、Tools、Memory、Retrievers）以及 LCEL 链式调用，适合线性/顺序工作流；链是有向无环的
- LangGraph：构建在 LangChain 之上，引入**有环图**（支持循环、条件分支、并行节点），核心是 StateGraph（共享状态图），专为需要多步推理、工具调用循环、Agent 自主决策的场景设计
- 核心区别：LangChain Chain 是线性 DAG，LangGraph 支持循环（如 Agent 反复调用工具直到任务完成）
- 实际选型：简单线性任务用 LangChain；需要循环推理、多 Agent 协作、复杂路由的用 LangGraph

**话术示例**
LangChain 提供了很多基础构件，比如模型调用、工具绑定、记忆管理，也有 LCEL 这套链式 API 可以把这些构件串起来做线性工作流，但它的 Chain 本质上是有向无环的，不支持循环。LangGraph 是构建在 LangChain 之上的，引入了 StateGraph，也就是一个有状态的有向图，核心是它支持**有环结构**——比如 Agent 调完工具发现结果不够，可以再循环回去调，直到满足条件才走出口。我们的气象文案项目需要根据不同要素走不同的处理分支，所以选了 LangGraph，而不是用 LangChain 的顺序 Chain。

### 8. LangGraph 结构化输出如何实现【7 分】

**问题**
你们用 LangGraph 的结构化输出是怎么实现的？以前模型做结构化输出比较费劲，LangChain/LangGraph 是怎么处理的？

**我的答案要点**
- 调用了一个结构化输出的 API（名字类似 `with_structured_output`）
- 传入一个 Pydantic 类声明作为输出 Schema（有标题、时间、地点等字段）
- 模型会按照该 Schema 结构化输出

**评价**
- 优点：答到了核心——Pydantic Schema + `with_structured_output`，思路正确。
- 不足：API 名字说得不确定（"差不多是这样"），展示出了不够扎实；没有解释底层原理（function calling / JSON mode / Pydantic 强制约束）。

**参考答案要点**
- LangChain 提供 `model.with_structured_output(Schema)` 方法，Schema 用 Pydantic `BaseModel` 定义
- 底层原理：① 对于支持 function calling 的模型（如 GPT-4、Claude），LangChain 把 Pydantic Schema 转成 JSON Schema 注入为工具定义，模型通过 function calling 输出结构化参数 ② 对于不支持 function calling 的模型，回退到 JSON mode 或提示词约束 + 解析器
- Pydantic BaseModel 还能做自动类型校验和字段描述注入，字段的 `description` 会成为模型的提示，引导模型准确填值

**话术示例**
LangChain 有一个 `with_structured_output` 方法，把它挂在模型对象上就行，传入一个 Pydantic 的 `BaseModel` 子类作为输出的 Schema，字段名和类型就是你想要的结构，字段上还可以加 description，这个 description 会作为提示传给模型，帮它理解每个字段填什么。底层对于支持 function calling 的模型，LangChain 会把 Pydantic Schema 转成 JSON Schema 注入为一个工具定义，模型用 function calling 的方式返回结构化参数，解析准确度很高；对不支持的模型会回退到 JSON mode 或提示词约束。我们当时就是这么用的，定义了一个包含标题、时间、地点、文案正文等字段的 Pydantic 类，直接传给 `with_structured_output`，就能拿到结构化的文案对象了。

### 9. Sentinel 限流原理【4 分】

**问题**
你们用到了限流和熔断的组件（Sentinel），能介绍一下限流的原理是怎么实现的吗？

**我的答案要点**
- 通过性能测试发现业务层数学计算是瓶颈
- 先用多线程 + Redis 优化，仍不够
- 配置了 Sentinel，设置了降级策略（降低精度计算）
- 在注解上配置
- 具体限流原理不了解

**评价**
- 优点：会用，且有真实调优背景，知道为什么要限流。
- 不足：不了解 Sentinel 的核心限流算法，这是 Java 后端常考知识点，属于明显盲区。

**参考答案要点**
- Sentinel 核心限流算法：
  - **滑动时间窗口（Sliding Window）**：统计过去 N 秒内的请求数，超过阈值则拒绝，是最常用的 QPS 限流方式
  - **令牌桶（Token Bucket）**：以固定速率向桶中放令牌，请求需消耗令牌才能通过，适合允许一定突发流量的场景
  - **漏桶（Leaky Bucket）**：以固定速率处理请求，多余的排队或丢弃，输出严格均匀
- Sentinel 默认使用滑动时间窗口（基于 LeapArray 环形数组实现），时间窗口切割为多个小桶（bucket），统计每个桶内的请求指标
- 熔断（Circuit Breaker）：统计错误率或响应时间，超过阈值时打开熔断器，直接返回降级结果，一段时间后进入半开状态探测恢复

**话术示例**
Sentinel 的限流核心是滑动时间窗口，底层用一个环形数组（LeapArray）把时间窗口切成多个小桶，每个桶记录这段时间内的请求数和错误数。每次请求进来，先算过去 1 秒（或配置的时间窗口）内所有小桶的请求总数，如果超过 QPS 阈值就拒绝。除了滑动窗口，Sentinel 也支持令牌桶和漏桶模式，令牌桶允许一定突发流量，漏桶则保证匀速输出。熔断这边是监控错误率或 RT（响应时间），超阈值后断路器打开，请求直接走降级逻辑，过一段时间进入半开状态再探测。

### 10. Java 常用集合【6 分】

**问题**
Java 里面有哪些常用的集合？

**我的答案要点**
- List（如 ArrayList）、Map、Set
- 对标 JS 去理解记忆
- 知道有带排序的集合变体，但具体名字记不清

**评价**
- 优点：说出了核心三类。
- 不足：没有系统梳理集合框架（Collection → List/Set/Queue，Map 独立体系），也没说出 LinkedList、HashMap、LinkedHashMap、TreeMap、ArrayDeque 等常用实现类。

**参考答案要点**
- **List**：`ArrayList`（动态数组，随机访问 O(1)）、`LinkedList`（双向链表，插删 O(1)）、`CopyOnWriteArrayList`（线程安全）
- **Set**：`HashSet`（无序不重复）、`LinkedHashSet`（插入顺序）、`TreeSet`（自然排序，底层红黑树）
- **Map**：`HashMap`（无序，JDK8 后链表超 8 转红黑树）、`LinkedHashMap`（插入/访问顺序）、`TreeMap`（Key 排序，红黑树）、`ConcurrentHashMap`（线程安全，分段锁/CAS）

- 线程安全选项：`ConcurrentHashMap`、`CopyOnWriteArrayList`，不推荐用已废弃的 `Vector` / `Hashtable`

**话术示例**
Java 集合框架主要分两条线：一条是 Collection，下面有 List、Set、Queue；另一条是 Map。List 里最常用的是 ArrayList，底层动态数组，随机访问快；LinkedList 是双向链表，插删快但随机访问慢。Set 常用 HashSet 无序去重，TreeSet 自动排序。Map 这边 HashMap 最常用，JDK 8 之后链表超过 8 个节点会转成红黑树，性能更稳定；需要保持顺序用 LinkedHashMap，需要 Key 排序用 TreeMap。多线程场景用 ConcurrentHashMap，它用分段锁加 CAS 实现高并发安全，性能远好于老的 Hashtable。

### 11. async / await 的实现原理【4 分】【错】

**错误点**：只讲了 Promise 的历史演进，没有说出 async/await 底层是 Generator 函数 + 自动执行器的语法糖。

**问题**
async / await 是语法糖，你能说一下它的实现原理是什么吗？它在语法糖之下封装了什么？

**我的答案要点**
- 知道 async/await 是 Promise 的语法糖
- 讲了历史演进：回调地狱 → Promise 链式调用 → async/await 语法糖
- 不了解底层还原成更老的代码是什么结构

**评价**
- 优点：历史演进说清楚了，Promise 到 async/await 的动机讲对了。
- 不足：没有说出关键点：async/await 是 Generator + 自动执行器的语法糖，编译后 await 对应 yield，运行时自动推进 generator，这是该题的考查核心。

**参考答案要点**
- async/await 在编译层面是 **Generator 函数 + 自动执行器**的语法糖
- Generator 函数可以暂停（`yield`）并恢复（`.next()`），天然适合表达异步等待
- `async function` → 编译为 Generator 函数；`await expr` → 编译为 `yield expr`
- 自动执行器（如 `co` 库的原理）：封装了"拿到 yield 的 Promise，等它 resolve 后自动调 `.next(result)` 推进执行，reject 时调 `.throw(err)`"的循环逻辑
- 手写简化版自动执行器：
  ```js
  function run(genFn) {
    const gen = genFn()
    function step(val) {
      const { value, done } = gen.next(val)
      if (done) return
      value.then(step).catch(err => gen.throw(err))
    }
    step()
  }
  ```
- Babel 编译后实际是通过 `regeneratorRuntime` 或类似的状态机来实现，原理相同

**话术示例**
async/await 是 Generator 函数加自动执行器的语法糖。Generator 函数可以用 yield 暂停，然后外部调 .next() 恢复，天然能表达"等待一个异步操作完成"。async function 编译后本质是一个 Generator，await 对应 yield，每次 yield 一个 Promise；自动执行器拿到这个 Promise，等它 resolve 了再自动调 .next(result) 推进执行，reject 了就调 .throw(err) 抛错。这样开发者写起来像同步，运行时却是异步推进的。Node 早期的 co 库就是干这个的，后来语言层面把这个模式标准化成 async/await。

### 12. 链表反转（算法题）【7.5 分】

**问题**
给定一个链表的头节点，反转整个链表，返回反转后的链表头节点。

**我的答案要点**
- 使用迭代方式（prev、current、next 三指针）
- `next = curr.next → curr.next = prev → prev = curr → curr = next`，循环推进
- 基本写出了正确逻辑
- 面试官指出需要考虑空指针（null）的边界情况

**评价**
- 优点：核心逻辑正确，三指针迭代反转是最优方案（时间 O(n)，空间 O(1)）。
- 不足：没有主动处理 `head == null` 或 `head.next == null` 的边界条件，被面试官提示后才意识到。

**参考答案要点**
```js
// JavaScript 版
function reverseList(head) {
  if (!head || !head.next) return head  // 边界：空链表或只有一个节点
  let prev = null
  let curr = head
  while (curr) {
    const next = curr.next
    curr.next = prev
    prev = curr
    curr = next
  }
  return prev
}
```
- 时间复杂度 O(n)，空间复杂度 O(1)
- 边界条件：`head == null`（空链表）和 `head.next == null`（单节点）直接返回 head
- 递归解法（口述备用）：`reverseList(head.next)`，然后把尾节点指回来，但空间 O(n) 不如迭代

**话术示例**
用三个指针迭代解决。prev 初始化为 null，curr 从 head 开始。每一步：先把 curr.next 存到 next，然后把 curr.next 指向 prev 实现反转，再 prev 和 curr 各往前移一步。循环直到 curr 为 null，此时 prev 就是新的头节点。注意要先判断 head 为空或只有一个节点的边界，直接返回 head 就行，不然后续指针操作会空指针报错。
