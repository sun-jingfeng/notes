### 2. iframe 架构选型与父子通信方案【5.5 分】

**问题**：你们为什么要用 iframe？父子通信具体通了哪些数据、怎么通的？相比其他方案有什么优势？

**我的答案要点**
- 5个子系统全部独立部署，同一 IP + 端口下用路径区分，父项目负责登录、全局截图、子系统加载管理。
- 调研了 qiankun、micro-app 等微前端框架，最终选 iframe，原因：同源部署、通信方便、没有样式污染和注册问题、开发成本低。
- 静态数据：父项目在 `window` 上挂全局对象，子项目通过 `window.top` 访问；共用 localStorage（token key 统一、风格标志位统一），并配套 TypeScript 类型声明包安装到各子项目。
- 动态事件：子项目触发截图等事件，通过 `postMessage` 传给父项目。

**评价**
- 优点：能说出同源部署下 iframe 的核心优点（通信简单、无框架侵入），并给出了 localStorage + `window.top` + `postMessage` 组合方案，整体方案完整可落地。
- 不足：面试官指出"以上这些能力只需注入一个共享 SDK 就能实现，根本不需要 iframe"，你未能直接给出反驳或补充场景支撑（比如隔离沙箱、旧系统无法修改等）；两个旧系统为何必须通过 iframe 嵌入而非共用路由，也没有讲清楚。

**参考答案要点**
- iframe 最核心的不可替代点是**环境隔离**：旧系统可能有全局样式污染、全局变量冲突，或者根本不是你维护的代码，无法侵入式注入 SDK；iframe 天然隔离，不需要改旧代码。
- 如果两个旧系统可以被修改，确实可以只注入共享 SDK，不用 iframe；正确的回答方向是"旧系统不能改 / 改动成本太高 / 有隔离需求"，这才是 iframe 不可替代的场景。
- PostMessage 适合事件通知，localStorage 适合持久化状态，`window.top` 适合同源访问父级运行时对象，三者分工合理，可以主动说清楚分工逻辑。
- 使用 iframe 的已知代价（首屏二次请求、嵌套 HTML、页面内滚动、弹窗/全屏限制）也要主动提及，说明你是有意识地权衡取舍，而不是只知道"方便"。

**话术示例**
选 iframe 最核心的理由是旧系统不在我们的维护范围内，无法侵入式改造。微前端框架需要在每个子应用里注册，如果是别的团队维护的旧系统，这种改动成本很高；而 iframe 不需要改旧系统一行代码，直接嵌进来就能用。

通信这块我分三种情况处理：token 等需要跨子系统共享的认证状态，统一约定 localStorage key，同源下天然共享，子系统直接取用即可；风格切换之类的运行时配置，父项目把对象挂在 `window` 上，子项目通过 `window.top` 拿；截图这类事件驱动的动作，用 `postMessage` 通知父项目执行。

当然 iframe 也有代价，比如嵌套 HTML 的首屏开销、弹窗会被遮住、全屏受限等，我在这个项目里用的是同源、路径区分的独立系统，这些限制基本不影响主流程，所以综合来看 iframe 是最低成本最快落地的方案。

### 3. Vue 数据响应原理【7.5 分】

**问题**：Vue 的数据响应原理是什么？Vue 2 和 Vue 3 有什么区别？

**我的答案要点**
- Vue 2：通过 `Object.defineProperty` 在初始化时遍历 data 字段，将每个属性转为 getter/setter，setter 中触发依赖更新；数组则重写了7个变异方法（push/pop/shift/unshift/splice/sort/reverse），在其中触发通知。
- Vue 3：使用 `Proxy` 代理整个对象，通过 `get` 收集依赖、`set`/`deleteProperty` 触发更新，天然支持动态新增属性和数组下标修改。

**评价**
- 优点：Vue 2 和 Vue 3 的核心差异说清楚了，数组重写方法这个细节也提到了：这是很多人漏掉的点。
- 不足：没有提到 Vue 2 的核心问题——动态新增/删除属性无法被侦听（须用 `Vue.set` / `Vue.delete`），这正是引入 Proxy 的最重要动机；收集依赖的机制（`Dep` 和 `Watcher` / Vue 3 的 `track` 和 `trigger`）没有展开。

**参考答案要点**
- Vue 2 用 `Object.defineProperty`，缺陷是只能劫持已存在的属性，动态新增属性、通过下标修改数组均无法触发更新，需要 `Vue.set`/`this.$set` 或 `splice` 绕过。
- Vue 2 响应式在组件初始化时递归遍历 data，给每个属性创建 `Dep` 实例；组件渲染时访问属性触发 getter，将当前 `Watcher` 订阅到 `Dep`；属性变化触发 setter，`Dep` 通知所有 `Watcher` 重新渲染或执行回调。
- Vue 3 用 `Proxy` 包裹整个对象，惰性拦截访问/修改，结合 `track` / `trigger` 完成依赖收集与派发，支持动态新增属性、数组下标修改、`Map` / `Set` 响应式。
- Vue 3 还将响应式与组件系统解耦，可独立使用 `@vue/reactivity`。

**话术示例**
Vue 2 和 Vue 3 响应式的核心区别是拦截方式不同。Vue 2 用 `Object.defineProperty`，初始化时递归遍历 data 给每个属性加 getter/setter，getter 里收集依赖，setter 里派发更新；数组没办法用这方法，只能重写7个变异方法在里面手动触发。这个方案最大的问题是只能劫持已有属性，动态新增的属性或者直接改数组下标都没有响应式，只能用 `Vue.set` 或 `splice` 绕过。

Vue 3 换成了 `Proxy`，直接代理整个对象，所有属性访问和修改都走拦截器，天然支持动态新增、删除、数组下标修改，也支持 `Map`、`Set` 这些集合类型，并且是懒处理的，不需要初始化就把整个 data 树全跑一遍。

### 4. `a == 1 && a == 2 && a == 3` 如何为真【3 分】【错】

**问题**：写一个表达式，让 `a == 1 && a == 2 && a == 3` 的结果为 `true`，说出输出结果并解释原理。

**错误点**：完全没有想到答案，认为没有任何值能做到，实际上通过覆盖 `valueOf`（或 `Object.defineProperty` 的 `get`）可以让每次比较时返回递增值。

**我的答案要点**
- 没有想出答案，认为双等号类型转换无法让同一个值依次等于1、2、3。
- 承认平时不用 `==`，习惯用 `===`，因此对 `==` 的类型转换规则不太熟悉。

**评价**
- 优点：诚实说出没有答案，没有猜测硬答。
- 不足：这题考察的是 `==` 宽松比较会调用 `[Symbol.toPrimitive]` / `valueOf` 的机制，以及 `Object.defineProperty` 的 `get` 拦截能力；两个切入点都应知道，且面试官在后续直接提示了 `Object.defineProperty`，仍未在答题时会意过来。

**参考答案要点**
- 方法一：覆盖对象的 `valueOf`（或 `[Symbol.toPrimitive]`），每次调用返回递增值。
- 方法二：用 `Object.defineProperty` 给全局变量 `a` 定义 `get`，每次访问时返回内部计数器递增的值。
- `==` 比较时若一方是数字、另一方是对象，会调用对象的 `[Symbol.toPrimitive]('number')` → `valueOf()` → `toString()`。
- 面试中出现这道题，回答时要同时说出两种方式，并说明背后的 `ToPrimitive` 转换规则。

**话术示例**
这道题有两种经典做法。

第一种是利用 `==` 的类型转换——当右侧是数字、左侧是对象时，JS 会调用对象的 `valueOf`，所以可以让 `a` 是一个对象，重写 `valueOf`，让它每次调用都返回一个递增的计数器值：

```js
const a = {
  _n: 1,
  valueOf() { return this._n++; }
};
console.log(a == 1 && a == 2 && a == 3); // true
```

第二种是用 `Object.defineProperty` 在全局作用域上劫持 `a` 的读取，每次访问 `a` 时触发 `get`，同样返回递增值：

```js
let _n = 1;
Object.defineProperty(globalThis, 'a', {
  get() { return _n++; }
});
console.log(a == 1 && a == 2 && a == 3); // true
```

核心原理是 `==` 会触发 `ToPrimitive` 转换，而 `defineProperty` 会让每次读取变量都触发 `get`，这两个机制都能让 `a` 每次"看起来不一样"。

### 5. 实现一个事件总线（EventBus）【6.5 分】

**问题**：写一个事件总线，包含基础的 `on`、`emit`、`off`，并写出测试用例验证它能跑通。

**我的答案要点**
- 写出了包含 `on`、`emit`、`off` 方法的事件总线。
- 核心数据结构：用对象存储事件名到回调函数数组的映射。
- `on`：向对应数组 push 回调。
- `emit`：遍历数组依次调用回调并传参。
- `off`：从数组中 indexOf 找到对应回调并 splice 移除。
- 写了测试用例验证，运行通过；中途遇到对象字面量缺逗号的语法错误，调试修正后跑通。

**评价**
- 优点：核心功能完成，能写测试用例并运行验证，调试能力也展示出来了；逻辑结构正确。
- 不足：初版把方法写成了类的形式但用了对象字面量语法，导致语法错误，说明对 class vs 对象字面量两种写法边界不够熟练；没有主动补充 `once`（只触发一次后自动解绑）；对边界情况（事件名不存在时 emit、off 对不存在回调的容错）没有提及。

**参考答案要点**
- 推荐用 class 实现，逻辑更清晰，也与主流三方库（mitt、EventEmitter）风格一致。
- `events` 用 `Map<string, Function[]>` 或普通对象均可。
- `off` 要注意：`indexOf` 找不到时返回 `-1`，需要判断后再 `splice`；或用 `filter` 过滤。
- `once`：在 `on` 时包一层 wrapper，`emit` 后自动 `off`，同时需要把 wrapper 引用保存起来，以便能 `off`。
- `emit` 前应判断 key 是否存在、回调数组是否为空，避免 `undefined is not iterable` 报错。

**话术示例**
实现一个基本的 EventBus，我会用 class 来写：

```js
class EventBus {
  constructor() {
    this._events = {};
  }

  on(event, listener) {
    if (!this._events[event]) this._events[event] = [];
    this._events[event].push(listener);
    return this;
  }

  emit(event, ...args) {
    const listeners = this._events[event];
    if (!listeners) return this;
    listeners.forEach(fn => fn(...args));
    return this;
  }

  off(event, listener) {
    const listeners = this._events[event];
    if (!listeners) return this;
    const idx = listeners.indexOf(listener);
    if (idx !== -1) listeners.splice(idx, 1);
    return this;
  }

  once(event, listener) {
    const wrapper = (...args) => {
      listener(...args);
      this.off(event, wrapper);
    };
    this.on(event, wrapper);
    return this;
  }
}
```

使用验证：

```js
const bus = new EventBus();
const fn = (msg) => console.log('received:', msg);
bus.on('test', fn);
bus.emit('test', 'hello');  // received: hello
bus.off('test', fn);
bus.emit('test', 'world');  // 无输出，fn 已移除
```

`once` 的关键是用一个 wrapper 包一层，在执行完 listener 之后自动 `off(wrapper)`，否则会移除不掉。

### 6. 白屏时间长的排查与优化【8 分】

**问题**：打开一个页面发现白屏时间长（页面加载慢），你通过哪些方法定位并解决这个问题？

**我的答案要点**
- 使用 Chrome DevTools Performance 面板，刷新时录制，录制区间覆盖从页面开始加载到内容出现。
- 在截图列表中找到持续白屏的时间段，放大对应火焰图，分析主线程任务。
- 火焰图中有颜色标识，渲染/排版任务可以识别；找出耗时长的任务块分析具体原因。
- 如果是 SPA 首屏，通常是初始 JS 包过大导致 Parse/Evaluate 耗时长，进而延迟渲染。
- 优化手段：路由懒加载、按需引入；进一步可考虑 SSR。

**评价**
- 优点：工具选择正确（Performance 面板刷新录制），排查路径清晰（截图→火焰图→长任务→定位原因→优化），答案结构完整，属于本场表现最好的一题。
- 不足：没有提到 Lighthouse（整体指标快速诊断）、Network 面板（请求并发/阻塞/资源体积）；优化手段只提到懒加载和 SSR，缺少 preload/prefetch、HTTP 缓存策略、资源体积优化（tree-shaking、代码分割、图片压缩）等。

**参考答案要点**
- **先快速定位**：Lighthouse 跑一下，看 LCP / FCP / TBT 等核心指标，快速得出性能瓶颈方向。
- **Network 面板**：看 waterfall，重点关注阻塞渲染的资源（CSS/JS）、体积大的包、串行请求、DNS/TCP 耗时。
- **Performance 面板**：刷新录制，看主线程长任务、JS Evaluate 耗时、重排/重绘消耗。
- **常见优化方向**：
  - JS 包体积：代码分割、路由懒加载、tree-shaking、第三方库按需引入。
  - 资源加载：preload 关键资源、prefetch 次级路由、使用 CDN、开启 HTTP 缓存、图片压缩/WebP。
  - 渲染阻塞：CSS 放 head、JS defer/async、避免 document.write。
  - 服务端层面：SSR/SSG、接口聚合减少并发请求数、开启 gzip/brotli 压缩。

**话术示例**
遇到白屏时间长，我会分三步排查。

第一步，用 Lighthouse 跑一下整体指标，FCP 和 LCP 能直观告诉你问题是"内容出来慢"还是"最大内容出来慢"，TBT 高说明主线程有长任务，这样可以快速锁定方向。

第二步，打开 Network 面板看请求瀑布图，主要看两件事：有没有体积很大的 JS / CSS 阻塞了渲染，有没有不合理的串行请求或者没有缓存命中的重复加载。

第三步，进 Performance 面板做刷新录制，找到白屏这段时间对应的截图，放大这一段的主线程火焰图，看是 Parse/Evaluate JS 的时间太长，还是有大量重排重绘，再针对性地处理。

如果是 SPA 首屏，最常见的原因是初始 bundle 包太大，我会先做路由懒加载和按需引入，看体积能减多少；如果首屏体验指标要求很高，可以考虑上 SSR，让服务器先返回渲染好的 HTML，减少客户端白屏等待时间。

### 7. Vite 多入口打包配置【3 分】

**问题**：如果 Vite 打出来的包体积过大，想配置多入口文件，应该怎么配置？

**我的答案要点**
- 没有做过多入口项目，不知道如何配置。

**评价**
- 优点：如实回答，没有猜答。
- 不足：这是 Vite 工程化的基础考点，对于一个4年前端来说属于应该了解的范围，即使没有实际做过，也应有概念性认知。

**参考答案要点**
- Vite 的多入口配置在 `vite.config.ts` 的 `build.rollupOptions.input` 字段中设置。
- `input` 可以是字符串（单入口）、数组或对象（多入口）；多入口时常用对象写法，key 是 chunk 名，value 是入口 HTML 文件路径。
- 适用场景：MPA（多页面应用），每个页面有独立 HTML + JS 入口；或者需要单独打一些 SDK / worker 包。
- 多入口打包后，每个入口会生成独立 JS bundle，共用 vendor 等公共 chunk 可通过 `manualChunks` 进一步拆分。

```ts
// vite.config.ts
import { resolve } from 'path';
export default {
  build: {
    rollupOptions: {
      input: {
        main: resolve(__dirname, 'index.html'),
        page2: resolve(__dirname, 'src/page2/index.html'),
        sdk: resolve(__dirname, 'src/sdk/index.ts'),
      },
    },
  },
};
```

**话术示例**
Vite 多入口的配置在 `build.rollupOptions.input` 里。如果是多页面应用，每个页面对应一个 HTML 入口，就用对象格式，key 是输出 chunk 的名字，value 是对应 HTML 的绝对路径。Vite 底层用的是 Rollup，多入口会生成多个相互独立的 bundle，公共模块可以配 `manualChunks` 统一抽到一个 vendor chunk 里，避免多入口各自打一份重复代码。
