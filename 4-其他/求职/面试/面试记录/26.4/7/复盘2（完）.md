### 2. 智能体的执行过程 【8 分】

**问题**
智能体的执行过程是怎样的？

**我的答案要点**
- 前端：弹窗输入框 + 生成按钮，携带已选气象要素、时间点、当前地图经纬度范围、用户提示词
- Java：经纬度 → 地名（工具转换），查原始气象数据，将地名 + 数据 + 提示词传给 Python 智能体服务
- Python 智能体（LangGraph）：根据气象要素路由到不同节点（如降水节点、预警点位节点），各节点绑定对应工具，处理完后统一格式化输出节点，返回结果 + session ID
- session 管理：前端存 session ID，续聊时传回；无 ID 时新建会话；会话缓存在 Redis

**评价**
- 优点：整个链路讲清楚了，前端触发 → Java 数据处理 → Python 路由处理 → 返回，逻辑闭环，细节充分
- 不足：没有主动说明 session ID 的存储位置（Redis），等面试官追问才补充；"统一格式化输出节点"可以解释是通过 LangGraph 的节点硬编码来保证输出格式规范

**参考答案要点**
- 前端传参：气象要素（决定路由）、时间点、经纬度范围、用户提示词
- Java 预处理：坐标转地名（工具）、查精炼化气象要素数据、组装参数调用 Python 服务
- Python LangGraph：入口路由节点根据气象要素分流 → 各领域节点（自带专属工具）→ 统一格式化输出节点（硬编码控制文案节奏）→ 返回文案 + session ID
- 会话管理：session ID 存 Redis；有 ID = 续聊，无 ID = 新建；Redis 独立部署，应用重启后会话仍存在

**话术示例**
整个链路是这样的：前端是一个弹窗，用户可以输入提示词然后点生成，同时会自动带上当前页面的一些上下文——选中的气象要素、时间轴上的时间点，还有地图视窗的经纬度范围，这四个参数传给 Java 后端。

Java 这边先把经纬度转成实际地名，再根据气象要素和时间去查对应的精炼化气象数据，然后把地名、气象数据、提示词三样一起传给 Python 智能体服务。

Python 服务用 LangGraph 搭了一个图结构，入口是一个路由节点，根据气象要素类型把请求分流到不同的领域节点——比如降水有降水处理节点，预警点位有对应的处理节点，各节点绑定了自己专属的工具。处理完之后统一走一个格式化输出节点，这个节点是硬编码的，用来保证文案的节奏和格式符合客户要求。最终把文案和 session ID 一起返回给前端。

会话管理上，session ID 存在 Redis 里，Redis 是独立部署的。前端下次请求带上 session ID 就是续聊，不带就新建会话。因为 Redis 独立于应用服务，即使服务重启，之前的会话记录还能通过 session ID 找回来。

### 3. LangGraph session 是否持久化 【7 分】

**问题**
LangGraph 的 session 是持久化的吗？

**我的答案要点**
- Redis 独立部署，应用重启后如果传入之前的 session ID 还能找到对话内容

**评价**
- 优点：最终给出了正确答案
- 不足：一开始反应迟钝，没有听懂问题，经两次追问才明确回答；应该主动先说清楚"持久化方案是 Redis"

**参考答案要点**
- LangGraph 本身的 checkpointer 支持接入 Redis/数据库 作为持久化后端
- 我们用 RedisCheckpointer，将会话状态存到独立部署的 Redis 实例中
- 服务重启不影响会话，只要 Redis 数据未过期，凭 session ID 就能恢复对话上下文
- 若 Redis 未配置持久化（如 AOF/RDB），Redis 重启则会话丢失；需要根据场景决定是否开启 Redis 持久化

**话术示例**
是持久化的。我们用 LangGraph 的 checkpointer 机制把会话状态写入了 Redis，Redis 是独立部署的容器，和应用服务生命周期是分开的。所以应用重启之后，只要前端传回同一个 session ID，Redis 里的会话上下文还在，可以继续对话。

当然，这依赖 Redis 本身的稳定性。如果需要更强的持久化保障，还可以给 Redis 开启 AOF 或 RDB，防止 Redis 自身重启后数据丢失。

### 4. FastAPI 选型依据 【7.5 分】

你是怎么选择用 FastAPI 封装接口的？

**我的答案要点**
- 技术选型对比三个方向：Node.js/Express、Java Spring AI、Python
- Python AI 生态最强，选 Python
- 在 Python 生态里搜索常用 HTTP 服务器，FastAPI 是最常被推荐的选项

**评价**

- 不足：没有说出 FastAPI 相对于 Flask/Tornado 等 Python 框架的具体优势（异步、性能、自动文档、类型安全）

**参考答案要点**

### 5. 智能体的质量指标 【7.5 分】

**问题**
智能体有什么指标？比如准确度、用户采纳度等。

**我的答案要点**
- 响应时间：优化方案是把前端展示用的高精度数据精炼成专供智能体的精炼化数据，减少模型处理量
- 返回节奏：用 LangGraph 统一格式化节点硬编码，控制文案节奏符合客户要求

**评价**
- 优点：提到了两个具体的客户需求驱动的指标，并说明了优化手段
- 不足：没有主动提准确度/用户采纳度指标（即使没有做也应该说"我们 v1 阶段主要关注可用性，准确度指标后续规划"）；精炼化数据方案可以说得更清楚（为什么原数据太大：精度高、点位多）

**参考答案要点**
- 响应时间：原始前端展示数据精度高（密集格点），直接喂给模型导致 token 消耗大、响应慢；单独提炼一份按要素和时间点聚合的摘要数据，大幅降低输入长度
- 输出格式一致性（节奏）：通过 LangGraph 最后一个格式化节点硬编码，保证文案结构符合业务规范
- 可补充：准确度/采纳度是 v1 阶段未量化的指标，可通过人工打分或用户反馈（保留/重新生成比例）来收集；这是未来优化方向

**话术示例**
我们当时客户明确提了两个指标：一个是响应时间，一个是文案的输出节奏。

响应时间这块，最开始我们把前端展示用的数据直接喂给模型，但这份数据精度很高、格点密集，输入太长导致模型响应很慢。后来算法老师专门处理了一份精炼化的数据，按气象要素和时间节点做了聚合摘要，模型的思考时间明显缩短。

文案节奏这块，我们在 LangGraph 图结构的最后加了一个统一格式化节点，用硬编码的方式约束输出结构，保证返回的文案段落、字数节奏符合客户的业务规范。

至于准确度和用户采纳度，v1 阶段我们没有量化，主要靠客户反馈。后续如果要做，可以统计用户"重新生成"的次数来反映满意度，或者让业务人员对每条文案打分。

**问题**
页面上有流式显示的功能吗？

**我的答案要点**

### 7. 前端截图功能实现 【8.5 分】

**问题**
前端的截图功能是怎么实现的？

**我的答案要点**
- 组合式函数（Composable），导出一个 start 方法触发截图
- 生成拖动窗口，通过渲染函数（h()/renderFunction）插入到 document.body 根节点，实现全屏覆盖
- 鼠标事件：mousedown 记录起点并开始监听，mousemove 更新窗口大小/位置，mouseup 清除 mousemove 监听
- 性能优化：弹窗移动用 CSS transform 而非 left/top，避免重排重绘
- 边界处理：mousedown 时重置所有状态，防止鼠标拖出浏览器的异常情况
- 截图：根据弹窗的起始坐标和尺寸，用 html2canvas 截取对应区域

**评价**
- 优点：这题是全场最详细的回答，技术细节丰富；重排重绘优化、边界处理都主动提到，展示了工程化思维
- 不足：跨 iframe（微前端场景）的截图问题被问到时，候选人先问了一下范围才回答，可以一开始就说"单页截图和跨子应用截图两种场景分别怎么处理"

**参考答案要点**
- 封装形式：Vue 3 Composable（`useScreenshot()`），返回 `start()` 方法
- 遮罩层插入：用 `h()` 渲染函数生成 VNode，通过 `render(vnode, document.body)` 挂到 body，确保层级最高
- 拖拽实现三事件：`mousedown`（记录初始位置，绑定 `mousemove`/`mouseup` 到 document）→ `mousemove`（更新坐标/尺寸）→ `mouseup`（清除 `mousemove` 监听）
- 性能：transform 不触发 layout，GPU 合成层直接处理
- 边界：在 `mousedown` 时重置状态，防止上一次拖拽未完成时的脏状态
- 截图：`html2canvas(document.body, { x, y, width, height })` 截取选区
- 跨 iframe/微前端截图：html2canvas 默认无法跨域 iframe，需要将子应用也用 html2canvas 先渲染成 canvas，再合并到主画布

**话术示例**
截图功能是我自己写的一个公共组件，以 Vue 3 Composable 的形式提供，调用方只需要 `const { start } = useScreenshot()` 然后执行 `start()` 就能触发。

触发之后会生成一个可拖拽的选区窗口，挂载方式用的是渲染函数 `h()` 配合 `render(vnode, document.body)`，直接插到 body 根节点，所以不管调用方的层级有多深，遮罩都能覆盖全屏。

拖拽逻辑围绕三个事件：`mousedown` 记录起始点、绑定后两个事件到 document；`mousemove` 不断更新选区的位置和尺寸；`mouseup` 清除 `mousemove` 监听。有两个细节：一是移动时用 `transform: translate(x, y)` 而不是改 `left`/`top`，transform 走 GPU 合成层不触发重排，性能更好；二是每次 `mousedown` 都重置所有状态，防止鼠标拖出浏览器后再回来时状态异常。

选区确定之后，用 `html2canvas` 传入起始坐标和宽高，截取对应区域生成图片。

### 9. 后端权限模块设计 【7 分】

**问题**
后端的权限模块是怎么设计的？

**我的答案要点**
- RBAC 设计：角色、权限、用户三张表
- 前端负责权限分配操作（给角色分权、给用户绑角色）
- 后端提供级联查询接口：用户 → 角色 → 权限列表，返回权限标识符字符串数组

**评价**
- 优点：说清楚了 RBAC 核心逻辑
- 不足：没有说后端是否有接口级别的鉴权（如 `@PreAuthorize`）；也没提 JWT 在这里的作用（携带 userId，后端据此查权限）

**参考答案要点**
- RBAC 三张核心表：`user`、`role`、`permission`，外加 `user_role`、`role_permission` 两张关联表
- 接口鉴权：Spring Security + `@PreAuthorize("hasAuthority('xxx')")` 注解，或自定义拦截器/AOP 校验
- JWT 携带 userId → 后端拦截器解析 → 查库得到权限列表 → 存到 SecurityContext → 各接口按权限放行
- 前端基于权限数组做路由守卫和按钮级别的 `v-if` 控制

**话术示例**
权限模块是基于 RBAC 设计的，核心是三张表：用户表、角色表、权限表，加两张关联表（用户-角色、角色-权限）。

用户登录之后，后端根据 JWT 里的 userId 做级联查询：先查用户对应的角色，再查角色对应的权限，最终汇总成一个权限标识符数组下发给前端。

接口层面，用 Spring Security 的 `@PreAuthorize` 注解对需要鉴权的接口做保护，拦截器会在每次请求时解析 JWT、查权限，把结果放进 SecurityContext，后续注解就能直接用。

前端拿到权限数组之后做路由守卫和按钮级别的 `v-if` 控制，实现页面和操作的双重权限隔离。

**评价**

- 不足：没有说 JWT 为什么比普通 session token 好（无状态、自带 claims、服务端无需存储）；也没说 JWT 的组成结构（header.payload.signature）

服务端收到请求之后，不需要查数据库或者 session 存储，只要验证签名合法、token 没过期，就能直接从 payload 里解出 userId 来查权限。这对微服务特别友好，因为各个服务只要拿到同一个密钥就能独立验签，不依赖中心化的 session 存储。

### 11. UUID 能否替代 JWT 【5.5 分】【错】

**问题**
如果用 UUID 的话可以替代 JWT 吗？

**错误点**：UUID 可以"替代 JWT 是一个 token"，但不能替代 JWT 的无状态特性——UUID 本身不携带任何信息，必须配合服务端存储（如 Redis session），属于有状态方案。候选人说"应该可以"的判断方向有误。

**我的答案要点**
- UUID 生成唯一字符串
- 如果能存储用户信息、做签发时间校验，"觉得是可以的"

**评价**
- 优点：没有完全否认，保持了开放态度
- 不足：核心区别没说清楚：JWT 是自包含（Self-contained）、无状态的；UUID 只是一个随机唯一 ID，本身不携带任何信息，作为 token 使用必须在服务端维护一张 `uuid → 用户信息` 的映射表（本质是 session），是有状态方案。两者都能"做登录"，但架构模式完全不同

**参考答案要点**
- UUID 作为 token 的本质：不携带信息，纯随机 ID，服务端需维护 UUID→用户信息的映射（Redis/DB），是有状态 session 方案
- JWT 的本质：自包含 claims（userId + 过期时间等），服务端无需存储，验签后直接读取，是无状态方案
- 可以"替代"，但代价是引入服务端 session 存储，不再无状态，不适合微服务横向扩展（需要 session 共享或粘性会话）
- 场景选择：单体 + 简单场景 → UUID session 也可以；微服务/分布式 → JWT 更合适

**话术示例**
UUID 技术上可以用来做登录 token，但它和 JWT 的核心区别是：JWT 是自包含的，payload 里带了用户信息和过期时间，服务端验签完就能直接使用，不需要额外存储；而 UUID 本身只是一个随机 ID，不携带任何信息，要实现登录功能就得在服务端维护一张 UUID 到用户信息的映射表，本质上是有状态的 session 方案。

两种都能实现登录，但 JWT 适合微服务场景，因为各服务只需要验签，不依赖共享存储；UUID session 适合单体应用，简单直接，但分布式环境下需要额外做 session 共享。

### 12. JWT 改密码后原设备还能继续用吗 【5 分】

**问题**
JWT 没做额外校验，用户改了密码之后原来登录的设备还能继续用吗？

**我的答案要点**
- 承认项目里从未考虑过这个场景，也没有做相关校验
- 内部系统，用户改密码后旧 token 事实上仍然有效直到过期

**评价**
- 优点：诚实回答，没有硬撑；坦承是场景盲区而非刻意省略
- 不足：没有说出解决方案；这是 JWT 无状态的经典痛点，即便项目里没做，也应该能说出已知的改进方案

**参考答案要点**
- JWT 无状态的痛点：一旦签发就无法主动吊销，只能等过期
- 解决方案一（黑名单）：Redis 维护 token 黑名单，改密码时把旧 token 加入黑名单，每次请求额外查一次 Redis
- 解决方案二（版本号）：用户表加 `token_version` 字段，改密码时自增；JWT payload 里带上版本号，服务端验证版本号是否匹配
- 解决方案三（短有效期 + refresh token）：access token 5 分钟过期，refresh token 长有效期；改密码时撤销 refresh token，旧 access token 5 分钟后自动失效
- 项目中没做是因为业务场景较简单（内部系统），可以说明这是已知的技术债

**话术示例**
这是 JWT 无状态特性带来的一个经典问题：token 一旦签发就无法主动吊销，改密码之后旧 token 在过期之前还是有效的。

我们项目里确实没有处理这个场景，因为是内部系统，安全要求不高。但如果要解决，有几种方案：最简单的是在 Redis 里维护一个 token 黑名单，改密码时把旧 token 加进去，每次请求多查一次 Redis；或者在用户表里加一个 `token_version` 字段，改密码时版本号加一，JWT payload 里带上版本号，服务端验签时顺便比对版本号；也可以用短有效期的 access token 加 refresh token 的方案，access token 5 分钟过期，改密码时撤销 refresh token，旧 access token 很快就自然失效了。

### 13. 单机情况下 MQ 是否有必要 【4 分】【错】

**问题**
单机情况下消息队列（MQ）有必要吗？

**错误点**：候选人回答"其实就是为了使用它"，说明无法给出合理的业务理由，等同于承认 MQ 的使用没有必要性支撑，是方案决策上的缺失。

**我的答案要点**
- "其实主要就是为了使用它"（无法说出实际理由）

**评价**
- 优点：无
- 不足：这是本场最弱的回答。MQ 在单机下确实可以有其价值，应该答出具体场景：异步解耦、削峰填谷、单机内部模块间的消费解耦；也可以坦承"这个场景我们应用得比较基础，主要是为了模块解耦和后续多节点扩展做准备"

**参考答案要点**

**话术示例**
单机情况下 MQ 并不是没有价值。我们用它主要解决两个问题：一是异步削峰——气象预警是事件驱动的，有时候会同时触发大量预警，MQ 可以缓冲这些请求，让下游按能力稳定消费，避免直接把服务打垮；二是模块解耦——预警生成和消息通知是两个独立的模块，中间用 MQ 隔开，两边可以独立迭代。

当然，如果业务量很低，MQ 引入的运维成本可能大于收益。不过从另一个角度看，单机阶段就把 MQ 接入，后续扩展到多节点时就不需要大改架构，算是提前做了扩展性准备。

### 14. JVM 内存设计 【7 分】

**问题**
Java 的 JVM 内存是什么样子的？

**我的答案要点**
- 堆内存：存放对象实例
- 栈内存：当前执行的程序（栈帧）
- 垃圾回收机制，回收堆中的垃圾对象
- 内存泄漏排查：监控面板观察内存增长趋势，看 GC 后内存是否回落

**评价**
- 优点：覆盖了堆/栈的基本概念和内存泄漏排查思路
- 不足：JVM 内存模型不止堆和栈，漏掉了方法区/元空间（存类信息/常量/静态变量）、程序计数器、本地方法栈；堆的分代结构（新生代/老年代）没有提

**参考答案要点**
- **程序计数器**：每个线程私有，记录当前执行的字节码行号
- **虚拟机栈**：线程私有，存栈帧（局部变量、操作数栈、方法返回地址）；栈溢出 = StackOverflowError
- **本地方法栈**：执行 native 方法时使用
- **堆**：线程共享，存所有对象实例；分为新生代（Eden + S0 + S1）和老年代；GC 重点区域；OOM = OutOfMemoryError
- **方法区/元空间**（JDK 8+）：存类的元数据、静态变量、常量池；JDK 8 前叫 PermGen，易 OOM；JDK 8 后改为元空间（使用本地内存，不再有固定上限）
- 内存泄漏排查：监控堆内存增长 → GC 后是否回落 → MAT/JProfiler 分析堆转储（heap dump） → 定位持有引用的 GC root

**话术示例**
JVM 内存主要分五个区域。

线程私有的三块：程序计数器，记录当前线程执行到哪条字节码；虚拟机栈，每次方法调用会压一个栈帧进来，存局部变量和返回地址，递归太深就 StackOverflowError；本地方法栈，专门给 native 方法用。

线程共享的两块：堆内存是最大的一块，所有对象实例都在这里，分新生代（Eden + 两个 Survivor）和老年代，GC 主要就在这里工作，撑满了就 OOM；方法区（JDK 8 之后叫元空间）存的是类元数据、静态变量、常量池，JDK 8 之前是 PermGen，有固定上限很容易 OOM，改成元空间之后用的是本地内存，上限大很多。

排查内存泄漏的思路是：先看监控，看常驻内存是否在 GC 之后一直不回落；如果怀疑有泄漏，生成一份 heap dump，用 MAT 分析哪些对象占内存最多、谁持有了它们的引用，再去代码里对应找原因。

### 15. GC 算法选择 【5 分】

**问题**
GC 算法是怎么选的？

**我的答案要点**
- 全部用的默认，没有主动选择

**评价**
- 优点：如实回答
- 不足：应该说出"默认"在不同 JDK 版本下是什么算法，以及什么场景下会考虑切换

**参考答案要点**
- JDK 8 默认：Parallel GC（吞吐量优先，适合批处理）；可手动改为 CMS（低延迟，已废弃）或 G1
- JDK 9+ 默认：G1 GC（平衡吞吐量与延迟，大多数 Web 应用的合理默认）
- JDK 15+ 可选 ZGC / Shenandoah（超低停顿，适合对延迟极度敏感的服务）
- 场景选择思路：延迟敏感（Web API、实时推荐）→ G1/ZGC；吞吐量优先（离线批处理）→ Parallel GC；内存极小（< 256 MB）→ Serial GC
- 我们项目单机部署、并发量不高，G1（JDK 9+ 默认）完全够用

**话术示例**
我们用的是 JDK 的默认算法，没有手动指定。JDK 9 之后默认是 G1 GC，它在吞吐量和停顿时间之间取得了比较好的平衡，适合大多数 Web 应用场景。

如果要主动选的话，思路大概是：延迟很敏感的场景——比如实时 API、对响应时间有严格 SLA——可以考虑 ZGC（JDK 15+），停顿时间能控制在 1ms 以内；如果是离线批处理、吞吐量优先，Parallel GC 更合适；我们这个项目单机、并发不高，G1 默认就够了，没有调优的必要。

### 16. Java AOP 的实现 【7 分】

**问题**
Java AOP 是怎么实现的？

**我的答案要点**
- Spring AOP，切片（Aspect）+ 切点表达式（@Pointcut）+ @Around 通知
- 主要用途：记录每个接口的入参、出参、响应时间

**评价**
- 优点：说清楚了 AOP 的基本用法和实际应用场景
- 不足：没有说 Spring AOP 的底层原理（JDK 动态代理 vs CGLIB），也没有说 @Around 和 ProceedingJoinPoint 的关系

**参考答案要点**
- Spring AOP 底层：目标类实现了接口 → JDK 动态代理；没有实现接口 → CGLIB 字节码代理（生成子类）
- 核心注解：`@Aspect`（声明切面）、`@Pointcut`（定义切点表达式）、`@Around`（环绕通知，可以在方法执行前后都插入逻辑）

### 17. AOP 加入后的性能影响 【5 分】

**问题**
加了 AOP 之后和没加之前，性能差多少？

**我的答案要点**
- 没有留意过

**评价**
- 优点：诚实
- 不足：没有给出理论上的评估；AOP 的性能问题是有典型认知的，应该说得出来

**参考答案要点**
- AOP 性能开销来源：代理对象创建（启动时一次性，可忽略）+ 每次方法调用的额外反射调用和切面逻辑执行
- 实际代价：CGLIB 比 JDK 代理稍快（直接字节码调用 vs 反射）；切面本身执行的额外逻辑（如日志序列化、数据库写入）才是主要开销
- 基准数据：纯代理的调用开销通常在 微秒级，对于 HTTP 接口（毫秒级）来说可忽略；但如果切面里有 IO（写日志到数据库），那开销就在 IO 本身

**话术示例**
当时没有做专项基准测试。理论上 AOP 代理本身的调用开销非常小——CGLIB 是字节码级别的子类调用，额外开销在微秒量级，对于毫秒级的 HTTP 接口来说几乎可以忽略。

真正可能影响性能的是切面里的逻辑本身，比如我们用 AOP 记录日志，如果日志是同步写数据库，那这个 IO 才是瓶颈，跟 AOP 机制本身关系不大。更好的做法是切面里用 `@Async` 或者消息队列把日志异步写出去，让主线程不用等。

**参考答案要点**

**话术示例**
我们用的是单机模式，Redis 独立跑在一个 Docker 容器里，和 Java 服务部署在同一台服务器上。

| 单机下 MQ 必要性  | 无法说出理由，等同于承认无意义   | 异步削峰 / 模块解耦 / 扩展性三个角度                  |
| GC 算法           | 只说"默认"，不知道默认是什么     | JDK 9+ 默认 G1；场景选型：延迟 → ZGC，吞吐 → Parallel |
| AOP 性能          | 没有任何评估                     | 代理开销微秒级；切面 IO 才是瓶颈；用异步日志          |
| JVM 内存          | 漏掉方法区/元空间、程序计数器    | 五大内存区域：PC / 虚拟机栈 / 本地方法栈 / 堆 / 元空间 |
| AOP 底层原理      | 没有提 JDK 代理 vs CGLIB 的区别  | 实现接口 → JDK 动态代理；无接口 → CGLIB 字节码子类    |

### 4.2 表达与结构

- LangGraph session 持久化：被连续追问三次才答到位，应该主动先说"我们用 RedisCheckpointer 做持久化"
- 流式显示：只说"没有"，可以主动解释原因和改造方案，体现技术广度
- 权限模块：漏掉了 Spring Security 接口级鉴权部分，是权限方案的重要一环
